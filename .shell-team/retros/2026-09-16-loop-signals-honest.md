## Lesson candidates

- `[common]` 診断出力（deprecation notice や migration hint のような、成功パスでも出るメッセージ）を「単一行の refusal 契約」を持つスクリプトの複数のモードディスパッチ地点（本サイクルでは resolver 経由／validator 直接／`--verify` の3地点）に段階的に足すタスクは、1箇所を閉じるたびに未検査の別地点が残る、という同一クラスの再発を起こしやすい。拡張候補: 診断メッセージを持つスクリプトの spec は、Acceptance Criteria に「全モードディスパッチ地点の列挙」を明示的な fixture マトリクスとして要求する——列挙が漏れていれば AC 自体が不完全という指摘を凍結レビューの時点で入れる。発火条件: 1つのスクリプトが複数の独立した exit/refusal 経路を持ち、そのいずれかに診断行を追加する変更を行うとき。誰が助かるか: CLI ツールに opt-in の診断・警告出力を追加する任意のプロジェクトの実装者・レビュアー。source: `.shell-team/todo.md`（T-1144 `same-class-2`・`pre-commitment-trigger`）、`.shell-team/reviews/T-1144.md`（round1 Major1、round2 Major2、round3 Major1）。
- `[common]` rename／改名タスクでは、frozen spec 自身が改名対象トークンを説明のために引用する箇所（Decision Points・Assumptions）が、その改名の「トークンの残存を検出する」Acceptance Criterion 自身の対象範囲に含まれてしまい、凍結後に task 自身の記録が criterion を壊す、という構造的な自己矛盾が起きうる。拡張候補: 改名・置換系タスクの凍結時チェックに「凍結対象の criterion 自身が、この task の記録（spec・provenance・board・review）を count 対象に含んでいないか」を明示的な確認項目として追加する。発火条件: ある criterion がリポジトリ全体（または広いパスセット）に対して whole-tree の文字列カウント・grep を行い、かつその criterion 自身が属する spec がその文字列を説明目的で引用しているとき。誰が助かるか: 用語のリネーム・非推奨化・移行を検証する Acceptance Criteria を書く任意のプロジェクトの spec 著者。source: `.shell-team/interventions/T-1144.md`、board T-1144 の `refreeze-class (v1→v2)` 行。
- `[common]` adopter が過去に生成し、リポジトリの外側（gitignored な出力ディレクトリ等）に置いている成果物は、リネーム・削除系の変更の residual inventory から構造的に見落とされやすい——本サイクルでは Codex の4ラウンド中2ラウンドがこの class の新規欠陥（stale な生成ファイルの移行経路欠如、部分再生成での誤削除）だった。拡張候補: リネーム・削除タスクの spec の `## Blast radius`/`## Input space` に「このリポジトリの外側にあり、過去のバージョンの成果物として adopter が保持している可能性のあるファイル」を明示的な入力クラスとして常設項目にする。発火条件: あるタスクがリポジトリ内で生成規則を持つファイル（生成先が gitignored、または adopter のローカル環境）の命名・内容を変更するとき。誰が助かるか: 生成物を出力するコード生成・スキャフォールディング機構を持つ任意のプロジェクト。source: `.shell-team/reviews/T-1144.md`（round2 Major1、round3 Major2）。
- `[target-specific]` issue 本文がリレーする過去タスクの数値系列（レビュー・QA のラウンド系列など）は、pm-spec が一次記録（board・reviews）から再導出してから設計判断に使うべきで、鵜呑みにすると系列の形（単調性など）を誤って設計に組み込む——T-1145 の issue #491 がリレーした QA 系列 `1,1,1,0,0`（5値）は実際には9ラウンドの非単調系列 `1,1,1,0,0,0,0,1,0` であり、単調非増加を前提にした trend rule だとオペレーター自身が「収束した」と記録した loop を非収束と誤読していた。今回は pm-spec が自発的に検算したが、この検算手順自体は機構化されていない。発火条件: issue 本文またはコーディネーティングセッションが、このリポジトリの過去タスクの数値系列・カウントを要約・転記した形で spec の設計根拠に使われるとき。誰が助かるか: このリポジトリで issue からタスクを起こす pm-spec の著者、および同種のリレー入力を受けるレトロ自身。source: board T-1145 の `relay-finding` 行、`.shell-team/specs/T-1145-stop-digest-convergence.md` の Summarized-sources 節。
- `[target-specific]` `bin/close-out.sh` の board スキーマ検査は、`- count:` 行に整数以外の値（本サイクルでは「run-time に導出される、リテラルは記録しない」というプロース）が書かれた場合を1回、実際に拒否した——fail-closed なチェッカーが記録衛生を守る、という設計原則（本リポジトリの CLAUDE.md「Checkers must fail closed」）が実際に機能した具体例として、`- population-note:` という新しい語彙（カウント主張ではない導出値を記録するための行種別）を board の記法として明示的に文書化する候補。発火条件: board のある行が「値は実行時に導出され、事前に固定されたリテラルを持たない」性質の情報を記録しようとするとき。誰が助かるか: このリポジトリの board 記法（`bin/close-out.sh`／`bin/check-handoff.sh` が検査する語彙）を書く engineer・orchestrator。source: `git show d95a8b13`（board diff、commit message）。
