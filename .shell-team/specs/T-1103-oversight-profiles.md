## Problem

This repository's loop is designed for autonomous operation: it advances on its own attestations, and the three human gates that remain (the batch merge GO, sprint planning approval, and confirmation before a destructive or irreversible operation) are deliberately few. That is the right default for a single operator working alone, and it is what the loop ships. It is not usable in an organization whose IT governance imposes **segregation of duties** — where a change may not advance on the approval of the party that produced it, and where "the loop attested to itself" is not an auditable control. Such an adopter today has two options: abandon the loop, or hand-assemble the missing approval step outside it, which is exactly the workaround issue #332's author already reached for once and which leaves no record any gate reads.

The requirement is recorded first-hand at `.shell-team/specs/T-1092-specify-seam-review.md:65`, opened and read at that line: T-1092 shipped #332's Codex spec-review gate and **omitted** #332's own `human approves` step, because this operating environment fixes the human gates at three and forbids inventing a fourth. That line names the generalization the operator asked for instead — a *selectable* governance-controlled oversight profile, for environments whose IT governance imposes segregation of duties so that the human approver must be a different party from the developer — and records it as issue **#343**, explicitly not absorbed there. This task ships it, as a profile a host selects rather than a gate anyone else inherits.

**Goal (one sentence).** A host selects an **oversight profile** for its own repository, declared in `<base>/oversight.conf` and resolved by `bin/check-oversight.sh` through the same occupancy lattice `bin/resolve-executor.sh:297`–`:326` already fixes for a host config: `autonomous` is the shipped default an absent declaration resolves to and it changes nothing — no existing seam gains a requirement, no existing gate's verdict moves, and every board, spec and record that is conformant today stays conformant byte for byte; `governance-controlled` additionally requires, at each seam the declaration names from the closed set `specify-seam` / `pre-merge`, a conformant recorded approval on the task's own board entry whose `approver` handle is **distinct** from its `producer` handle after a stated ASCII normalization **and whose `approves=` anchor still names the artifact being gated**, and refuses fail-closed when that record is missing, malformed, duplicated for one seam, names the same party twice, or carries an anchor that has gone stale; a declaration this checker cannot fully evaluate — a non-regular-file occupant at the config path, an unreadable file, a grammar violation, an out-of-vocabulary seam name, `governance-controlled` declaring no seam at all, or a `seam` row under `autonomous` — **refuses** rather than resolving to `autonomous`, because a resolution that silently answered `autonomous` would disable every declared seam at once; **an enrolled repository cannot be de-enrolled by the declaration merely going missing** — once the task's own board carries a prior approval record, resolving `autonomous` from the *absent* arm refuses instead of passing, so the only silent path out of governance is an explicit host declaration whose bytes an auditor can diff; the three standing human gates and `both-gates-green` are unchanged in **both** profiles, an approval never substituting for `qa-verifier`'s PASS or `codex-reviewer`'s APPROVE on the delivered change; and an adopter reading the shipped documentation can tell which profile fits, what triggers the other, and what the mechanism does not guarantee.

**The two seams, and the honest reach of each.** At `specify-seam`, `skills/run/SKILL.md` step 2 gains a gate beside the five existing first-freeze bullets that **runs the checker and branches on its exit code** — the shape `:45`'s `bin/check-entry-mode.sh` bullet already uses, not the shape of the five reads — refusing the freeze on any non-zero exit exactly as a broken or vacuous `- check:` line does. At `pre-merge`, the teeth are `bin/close-out.sh`'s own exit status: a fail-closed gate mirroring the `check-spec-review.sh` gate wiring in `bin/close-out.sh:481`–`:522` line for line, with `1` mapped to a board-content refusal that leaves the board byte-untouched and every other non-zero mapped to `die`. That placement is a decision with a measured reason: a workflow under this repository's `.github/` runs only in this repository and never in an adopter's, so a CI step cannot be an adopter's pre-merge control, whereas `bin/close-out.sh` is a shipped script an adopter runs at exactly that boundary. What the pre-merge arm therefore reaches is a **callable, fail-closed refusal inside a shipped script** plus documented wiring instructions for an adopter who additionally wants it in their own CI; what it does **not** reach is any guarantee that an adopter ran `close-out.sh` at all before merging, and that limit is disclosed in the adopter-facing section rather than implied.

**Why the gate is not election-scoped, unlike its arm-A sibling.** `bin/close-out.sh:481`–`:493` scopes the spec-review gate to a captured board election, so a task that never elects pays for no directory resolution. That reasoning does not transfer: there is no per-task election to read here, the profile is a per-repository property, and the whole point of the `autonomous` default is that the checker itself answers "nothing is required" — cheaply, from one file's absence. So `close-out.sh` invokes the checker unconditionally and the checker's own resolution is what makes the autonomous path silent. The cost this accepts is stated rather than hidden: an install whose `bin/check-oversight.sh` or whose shipped `templates/oversight-default.conf` is missing or unreadable becomes a `die` at close-out for every task, the same fail-closed exposure `bin/check-binding.sh` and `bin/resolve-executor.sh` already carry for the binding config, and the same one the sibling-script screen exists to name precisely.

**Enrollment does not evaporate: the `autonomous`-from-absence arm is sticky once the board shows governed operation.** The occupancy lattice's absent arm is correct for a repository nobody ever enrolled and wrong for one that enrolled and stopped — deleting the config, renaming it, retargeting a symlink, or pointing resolution at an empty base all land on that one arm, and each would silently disable every declared seam at once, which is the exact failure direction duty B's reclassification into arm A exists to prevent. So the arm carries one additional condition, computed from bytes the checker already reads and needing no new file, no tombstone and no git history: when the effective profile is `autonomous` **and** that answer came from the **absent** arm **and** the task's own board entry carries at least one prior `- oversight-approval (` record, the checker **refuses** (`enrollment-vanished`, exit 2) instead of passing. The authorized way out of governance is therefore an explicit host declaration reading `profile autonomous` — a present file whose bytes appear in a diff and whose removal of a `governance-controlled` line an auditor reads — rather than a deletion that leaves nothing to read. Three properties of this shape are stated because they are what make it worth having rather than a gesture. It needs **no history at all**: the refusal is computed from the board's current bytes, so a rebase, squash, force-push or `gc` that erases the config's own trace still refuses at the next seam, and only an edit that removes the config **and** every approval record from the board erases the trace — a far louder change than deleting one untracked file. It is **not redirectable by the config affordances**: the board reaches the checker through `--board`, which the shipped callers resolve through `bin/team-paths.sh`, so redirecting where the *declaration* is read from does not redirect where the *evidence of governed operation* is read from. And its residual is exact and bounded: a repository that enrolls and de-enrolls **before any approval record exists** is still indistinguishable from one that never enrolled, because the stickiness is grounded in evidence of governed operation rather than in the declaration itself — disclosed below as item **(vi)** rather than left for a reader to discover.

**The approval is bound to what it approves, per seam, by an anchor the checker can compare.** A record that names no artifact survives every later rework round and reads as conformant while blessing content the approver never saw — an axis genuinely distinct from item **(iii)**'s "did the approver read it", because this one asks whether the thing they read is still the thing being gated. So the record carries a required `approves=` field whose accepted form is fixed by the seam. At `specify-seam` it is `v<N>`, the intent-block version the approval covers, and the checker refuses (`approval-stale`) when the task's board records an intent-hash version **greater than** `N` — which is exactly the class-B re-freeze case: at a first freeze no `- intent-hash` exists yet, so an approval naming `v1` is current, and once a ratified `v1`→`v2` re-freeze lands, that same record is stale and refuses. At `pre-merge` it is a forty-character commit id, and the checker refuses when the object does not exist in this repository, when it is **not an ancestor of `HEAD`** (so an approval naming a commit from a discarded, rebased or force-pushed branch refuses), or when the commit that last touched the task's own spec file is **not an ancestor of** the named commit (so an approval predating the spec's last edit refuses). Two consequences are stated rather than implied. The `pre-merge` arm runs `git` and therefore requires a git repository, refusing `not-a-git-repo` (exit 2) rather than passing when it is not in one; the `specify-seam` arm reads board bytes only and needs no git. And the anchor does **not** invalidate on commits merely added on top of it and reachable from `HEAD` — refusing those would make the gate unsatisfiable, since the close-out commit itself lands after the approval — which is disclosed below as item **(x)**.

**The approval record's physical form, and why it is the board.** The record is an indented sub-bullet on the task's own `## Active` board entry, one per declared seam: `- oversight-approval (<seam>): approver=<handle> — producer=<handle> — approves=<anchor> — date=<YYYY-MM-DD> — record=<locator>`, matched only at a line start under the board-entry continuation canon `bin/check-handoff.sh:95`–`:97` fixes, so a mid-line quotation of that grammar inside backticks — including in this spec — is not a record. Three alternatives were measured and rejected. `<runs>/gate-<task>.decl` is a **waiting** declaration that the shipped duty removes the moment the human's answer is acted on, and `runs/` is gitignored outright (`.shell-team/.gitignore:4`, read first-hand), so it is untracked by construction and cannot be an audit trail. `<reviews>/T-NNN.md` is the reviewer's own record and an approval is not a review verdict; putting one there would make the reviews directory carry two unrelated record families with one shape. A new file would add a fourth per-task record path plus whatever durability registration this loop's own record-durability machinery requires of one, for no gain, where the board already carries the `- freeze-attestation`, `- dispatch:` and `- entry-mode:` families and `skills/run/SKILL.md:45` — read first-hand — records that a shipped checker already returns a real exit code over two of them at a freeze.

**The identity is an opaque handle, and the comparison is closed over ASCII.** Measured, not assumed: `bin/check-pii-shapes.sh` fires on a mailbox-shaped string at any real deliverable domain and excludes only the GitHub noreply domains and the RFC-reserved names, and `bin/check-commit-identity.sh` accepts only the noreply `+login` form and **never echoes an identity value in a finding**. A tracked record therefore cannot carry a real name or address, so the only form that works across adopters is an **opaque handle** the adopter maps to a person outside the repository. Its grammar is `^[A-Za-z0-9][A-Za-z0-9._+-]{0,63}$`; the segregation-of-duties comparison is inequality after stripping the field's surrounding whitespace and lowercasing under `LC_ALL=C` with an ASCII-only translation, so `Alice` and `alice` are the **same** party and the control is not evadable by case-toggling; a handle carrying any byte outside that grammar — a non-ASCII byte among them — is **refused** rather than folded, because no bash normalization can decide Unicode confusables and a mechanism that pretended to would be worse than one that declines; and no refusal message echoes either handle's bytes, copying `check-commit-identity.sh`'s own no-echo discipline. The producer handle's source is the record's own `producer=` field, written by the party recording the approval: neither the board's producer *role* (`pm-spec`, `engineer` — a role, not a party, and never the human whose approval is at issue) nor the commit author (the last committer, not the artefact's producer) answers the question the control asks. The reason the commit author is rejected is **what it names, not that reading it needs git**: the `pre-merge` anchor above does invoke `git` to compare content ids, and the distinction held here is that a content id is a fact about the artifact while a commit author is an inference about a party — this mechanism derives no party from any commit.

**Composition with the `spec-review` dispatch axis, never replacement.** The profile is per-repository and the dispatch record is per-task, and neither derives from the other. A `governance-controlled` declaration naming `specify-seam` does **not** mandate `spec-review — cross-provider`: the two answer different questions — did an independent party approve this, versus were this spec's domain premises cross-reviewed — and deriving one from the other would silently overwrite a Plan-time decision the Routing Map owns. The two compose in all four combinations, and the composition is shown mechanically rather than argued: the seam gate's verdict is byte-identical across two board entries differing only in their `- dispatch: spec-review — …` value (**AC11**), `bin/check-oversight.sh` contains zero occurrences of the literal `spec-review`, and `DISPATCH_AXIS_TABLE` gains no row and no widened value set.

**What this mechanism claims, and what it does not close — enumerated rather than left to be discovered**, in the same `re-disclosed, not closed` idiom `skills/run/SKILL.md:52`–`:54` already uses. What it claims is stated first and deliberately narrowly: a **self-declared conflict check with a content anchor**, recorded as tracked workflow evidence — not an authenticated segregation-of-duties control. Every gap below is duty C's arm-B disclosure.

**(i)** Nothing **authenticates** a handle: no signature, no SSO or OIDC binding, no directory lookup, no ownership proof, and the same identity-ownership exclusion `bin/check-commit-identity.sh` already draws for commit authors applies here verbatim. Nor is the `producer=` handle bound to the change's actual producer, and nothing establishes that the `approver` is *eligible* to approve — so what the comparison enforces is that two self-declared labels differ, which is why this mechanism is named a self-declared conflict check above rather than an SoD control. **(ii)** One party can write **both** the `approver=` and the `producer=` field, so the control raises the cost of an accidental self-approval — two distinct handles must now be recorded — without raising the cost of a deliberate misstatement by a party that can write both. **(iii)** "The approver actually read and approved this" is a reading judgment, not a machine-checkable state, and a presence check is satisfied by a record nobody thought about. **(iv)** Nothing mechanically confirms that the `specify-seam` gate **ran**: its exit code is consulted where the five sibling gates are only read, which is narrower than their residual, but a coordinating session that skipped the invocation and transcribed a conformant record still passes. **(v)** Whether any of this satisfies a real organization's segregation-of-duties control, or reduces any measured control failure, is `undetermined` and no checker here measures it. **(vi)** The sticky arm is grounded in evidence of governed operation, so a repository that enrolls and de-enrolls **before its board carries any approval record** is still indistinguishable from one that never enrolled; and while the sticky refusal itself needs no history, the config file's own trace is erasable by ordinary history operations available to the same party the mechanism constrains — a rebase, a squash, a force-push, a `gc` over a config that was never committed, or a fresh rewritten clone. An adopter needing per-push re-approval pairs this with their own branch protection.

## Decision points, resolved

**DP-1 — declaration home and format: a host-authored `<base>/oversight.conf` plus a shipped `templates/oversight-default.conf`, validated by one script through one grammar.** Resolution is via `bin/team-paths.sh --get base`, so both supported layouts and a `$TEAM_RUN_BASE` override are covered without a hardcoded path, and the occupancy lattice at that one path follows `bin/resolve-executor.sh:297`–`:326` member for member (absent → shipped default; regular file → host; live symlink to a regular file → host, deliberately the same; unreadable → refuse; dangling symlink, directory, FIFO or any other present-or-symlink non-regular occupant → refuse before any parsing). The shipped default is resolved from the checker's **own installed directory**, never from the current working directory, so a decoy `templates/oversight-default.conf` in an adopter's tree cannot substitute a profile — `resolve-executor.sh:289`–`:296`'s own stated reason, copied. *The two alternatives, and why each is rejected.* **The loop contract YAML** (`<loops>/shell-team.contract.yaml`) is read by `bin/loop-guard.sh` and `bin/check-contract.sh` for budget and STOP semantics; adding an oversight key there would put a governance control inside the file whose parser decides retry economics, forcing both of those checkers' grammars to widen for a value neither consumes, and `bin/loop-guard.sh` is byte-locked by this task's own **AC8** for exactly that reason. **`CLAUDE.md` prose** is a trusted instruction channel, not a machine-readable declaration: nothing parses it, its content is free-form by design, and this repository's own security invariant treats it as operator configuration read by agents rather than by scripts — a fail-closed gate cannot rest on a file whose grammar is "whatever a person wrote". A separate `*.conf` with a closed grammar and a single validating sibling is the shape this repository already ships twice (`binding.conf`, and the adapter allowlist), and reusing it costs no new concept.

**DP-2 — seam vocabulary: the closed pair `specify-seam` / `pre-merge`, per-seam opt-in inside a whole-profile switch.** The profile line says *whether* governance applies at all; the `seam` rows say *where*. That is per-seam opt-in nested inside one profile value rather than two independent knobs, and it buys the two properties a single knob cannot: `governance-controlled` with **no** `seam` row is refused as vacuous (a profile that gates nothing is a declaration nobody can act on, and silently accepting it would read as governance while enforcing nothing), and a `seam` row under `autonomous` is refused as contradictory (rather than silently ignored, which would let a host believe a seam was gated when it was not). Both refusals are in **AC5**. *"Declared but never reached"* is settled explicitly and is not an error: the gate fires at the seam it is invoked from, so a declared seam a task never crosses is never evaluated, and no close-out sweep retroactively demands an approval for it. That is stated in `## Input space` as a reachable class precisely so nobody later reads the absence of such a sweep as a gap.

**DP-3 — identity thinness: an opaque ASCII handle, compared after a stated normalization, sourced from the record's own `producer=` field.** The constraint is measured, not assumed: `bin/check-pii-shapes.sh`'s `email-nonnoreply` shape fires on any mailbox at a real deliverable domain and excludes only the GitHub noreply domains and the RFC-reserved names, and `bin/check-commit-identity.sh` accepts only the noreply `+login` form and never echoes an identity value in a finding. A tracked record therefore cannot carry a real name or address, so the only cross-adopter form is a handle the adopter maps to a person outside the repository. *Producer-identity source, among the three candidates.* The **board producer role** (`pm-spec`, `engineer`) is rejected: a role is not a party, and every artefact in this loop is produced by an AI role, so comparing an approver against a role name would make the control trivially satisfiable and would not answer the question segregation of duties asks. The **commit author** is rejected for what it names rather than for what reading it costs: it identifies the last committer, not the artefact's producer, so it answers a different question however cheaply it is read. Stated explicitly because DP-12 later invokes `git` for the `pre-merge` anchor and the two must not read as contradictory: the rule held here is that **no party is ever inferred from a commit**, not that the checker never runs `git` — a commit id compared against `HEAD` is a fact about the artifact, whereas a commit author treated as the producer is an inference about a person, and only the second is excluded. The record's **own `producer=` field** is chosen: the party recording the approval names both sides explicitly, which makes the claim auditable and makes the "one party wrote both" exposure visible as duty C's residual **(ii)** rather than hidden behind a derivation. *Comparison normalization.* Strip the field's surrounding whitespace, then lowercase under `LC_ALL=C` with an ASCII-only translation, then compare for inequality — so `Alice`/`alice` is the same party and the control is not evadable by case-toggling (**AC12**). Unicode is handled by **exclusion, not normalization**: the handle grammar `^[A-Za-z0-9][A-Za-z0-9._+-]{0,63}$` refuses any byte outside it, because no bash normalization decides confusables and a mechanism that folded some homoglyphs and missed others would be worse than one that declines the class outright. Base-directory precedence: `--base DIR` (a testing affordance accepting any directory, including an absolute temp path) → `$TEAM_OVERSIGHT_BASE` (the same precedence `$TEAM_TODO` and `$TEAM_INTERVENTIONS_DIR` already hold, and what lets `bin/close-out.sh`'s subprocess be redirected without new flag plumbing) → `bash <sibling>/team-paths.sh --get base`, with `die` on resolver failure and no guessing fallback. `--config PATH` names a specific file directly, bypassing the lattice; an absent file named that way is exit 2 rather than a fallback. `--base` and `--config` are mutually exclusive. `$TEAM_RUN_BASE` is deliberately **not** the affordance: `bin/team-paths.sh`'s `validate_base()` rejects absolute paths, so a temp directory cannot be reached through it — that is measured, not assumed.

**Exit codes and the closed refusal set**, one token per non-zero exit printed to stderr, following `bin/check-binding.sh`'s own contract. `0` = the seam imposes nothing (profile `autonomous` with no prior approval record on the entry, or an explicit host `autonomous` declaration, or the seam is not declared) or the approval is conformant and its anchor current. `1` = a content refusal: `missing-schema`, `duplicate-schema`, `schema-not-first`, `unsupported-schema`, `unparseable-line`, `missing-profile`, `duplicate-profile`, `unknown-profile`, `unknown-seam`, `duplicate-seam`, `seam-under-autonomous`, `no-seam-declared`, `approval-missing`, `approval-malformed`, `approval-duplicate`, `bad-handle`, `approver-equals-producer`, `approval-anchor-malformed`, `approval-stale`. `2` = the input could not be evaluated: `usage`, `declaration-occupancy` (a non-regular-file occupant), `declaration-unreadable` (an unreadable regular file, or a missing shipped default), `enrollment-vanished`, `board-unresolvable`, `task-not-found`, `not-a-git-repo`. The config is **never sourced, evaluated as code or executed** — every field is a bare token.

**Why `enrollment-vanished` is exit 2 and not 1**, since it is the one refusal whose classification is not obvious: at close-out, `1` maps to `fail` (a board-content refusal the task's author repairs) and `2` maps to `die` (an environment the operator repairs). An enrolled repository whose declaration has gone missing is the second: nothing about the board is wrong, and the fix is to restore the declaration or to de-enrol explicitly — neither of which the task's author can do by editing their entry. Routing it to `fail` would send the operator to repair the wrong artifact.

**The record grammar**, matched only at a line start after indentation, so a mid-line quotation inside backticks is not a record:

```
  - oversight-approval (<seam>): approver=<handle> — producer=<handle> — approves=<anchor> — date=<YYYY-MM-DD> — record=<locator>
```

`<handle>` is `^[A-Za-z0-9][A-Za-z0-9._+-]{0,63}$`. `<anchor>` is `^v[0-9]+$` at `specify-seam` and `^[0-9a-f]{40}$` at `pre-merge`; a value matching neither the seam's own form is `approval-anchor-malformed`. `record=` is last and free-form, so an em dash inside a locator cannot forge a field — the same discipline the dispatch record uses. One record per declared seam per task; two for one seam is `approval-duplicate`.

**The two anchor-staleness comparisons, spelled out so the implementation does not have to re-derive them.** At `specify-seam`: read every `- intent-hash (v<N>):` sub-bullet on the task's entry, take the maximum `N` (zero when none exists), and refuse `approval-stale` when that maximum is **strictly greater** than the approval's own `N`. `>=` is wrong and would make every first freeze unsatisfiable, because this gate runs before the `- intent-hash (v1)` append — that is the single most likely implementation slip here, and **AC22** case 1 is the criterion that catches it. At `pre-merge`: refuse `approval-stale` when `git cat-file -e <anchor>^{commit}` fails, when `git merge-base --is-ancestor <anchor> HEAD` fails, or when `git log -1 --format=%H -- <the spec path read from the entry's own source line>` returns a commit that is **not** an ancestor of the anchor. When that `git log` returns nothing — a spec no commit has touched yet — the precedence clause is **skipped**, not failed; that is a reachable class, not an edge case to guard against.

**The sticky-enrollment condition, in the order it must be evaluated.** Occupancy and grammar refusals come **first**, so a dangling symlink or a malformed file reports its own condition rather than the enrollment one (**AC21** case 5 asserts the two messages differ). Only once a profile has successfully resolved to `autonomous` **from the absent arm** does the sticky check run: scan the task's own entry extent for `^[[:space:]]*- oversight-approval \(` and refuse `enrollment-vanished` when at least one is found. A profile that resolved to `autonomous` from a **present** declaration never reaches this check, whatever path the declaration was read from — that is the authorized de-enrollment, and it is what **AC21** cases 2 and 4 measure.

**Gotchas, each one measured rather than guessed.**

- **Read the whole file with `grep`/`sed`, never a `while IFS= read -r line` loop.** That loop's own non-zero exit is its continuation test, so it drops a final line carrying no trailing newline — and a dropped final `- oversight-approval` line would silently become `approval-missing`, a fail-*closed* direction here but still a wrong verdict. `bin/check-spec-review.sh:47`–`:50` states this for its own reason; the same applies.
- **`[ -f ]` alone cannot implement the lattice.** It is false for both "nothing there" and "something broken there", which have opposite correct outcomes. Use `[ -f ]` for the accepting arm, then `[ -e ] || [ -L ]` for the refusing arm — the `-L` is what catches a dangling or looping symlink, for which `-e` is false. Copy `bin/resolve-executor.sh:320`–`:326` structurally.
- **Strip a trailing CR per line before parsing**, both in the configuration file and on the board. A CRLF configuration is a reachable input class, and a `profile governance-controlled\r` that failed to match would resolve to nothing.
- **Lowercase with an ASCII-only translation under `LC_ALL=C`.** A locale-dependent case fold can behave differently on a Turkish locale for the letter `i`, which would make the control's verdict depend on the runner's environment. The charset already excludes non-ASCII, so an ASCII translation is complete for the accepted input set.
- **Never echo a handle in a refusal message.** `bin/check-commit-identity.sh`'s DP-3 gives the reason: a report that echoed the value turns a control into a leak in a public CI log. **AC12** asserts this per case.
- **Reject `--base` together with `--config`** rather than honouring whichever came last — `bin/team-paths.sh:83`'s `set_mode()` is the shipped idiom for this.
- **Neither shipped caller may pass `--base` or `--config`.** `skills/run/SKILL.md`'s gate bullet and `bin/close-out.sh`'s invocation resolve canonically and pass only `--seam`, `--task` and `--board`; **AC21** scans both files for those flags on any line naming the checker and reds if it finds one. The fixture harness reaches a scratch base through `$TEAM_OVERSIGHT_BASE`, which the subprocess inherits without either caller naming a flag — the same way `tests/close-out/run.sh` already redirects `$TEAM_TODO` and `$TEAM_INTERVENTIONS_DIR`. **The scan is per line, so this bites prose too**: do not *mention* `--base ` or `--config ` on any line of `skills/run/SKILL.md` that also names `check-oversight.sh`, even to explain that they are testing affordances. Put that explanation on its own line, or in `docs/adopting.md` where the flag scan does not reach.
- **The `pre-merge` arm needs a git repository; the `specify-seam` arm must not.** Refuse `not-a-git-repo` (exit 2) for the former outside a repository rather than passing, and do not make the latter depend on git at all — a fixture exercising `specify-seam` in a bare temp directory must still work, and **AC22**'s first three cases run exactly there.
- **The sticky check reads the task's own entry extent, not the whole board.** Use the same `## Active`-scoped, single-entry resolution the rest of the checker uses; a record on some *other* task's entry says nothing about this one, and scanning the whole file would make every task in an enrolled repository refuse forever after the first approval anywhere.
