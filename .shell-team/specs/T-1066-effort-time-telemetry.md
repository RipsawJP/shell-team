## Problem

Since this repository moved to sprint operation, a task cycle has grown visibly heavier — more review rounds, more freeze versions, engineer phases spanning multiple watchdog lifetimes — and nobody can currently say how much of that is the loop asking for more (rigor accreted through lesson promotion) and how much is each call simply taking longer (raw latency). The two have opposite responses: rigor growth is a design question about what the protocol demands, latency growth is an executor question about who runs it. With v2.0.0's binding config a role's provider, model and effort can now be reassigned, and T-1058 records the resolved binding on every span, so a before/after comparison is exactly how such a change should be evaluated — but without a baseline taken now, a future change's effect cannot be separated from whatever the background trend was already doing. The telemetry, the reviews corpus and the specs corpus already hold the raw material; what is missing is one committed reading of them with its population, its exclusions and its uncomputable parts stated honestly.

**DP2 — no `bin/` extension, and the command string is the evidence trail.** Issue #248 scopes `bin/` extensions out of itself ("this issue itself commits to no mechanism"), and `bin/rollup-runs.sh` measurably prints none of the suggested metrics — it folds by `run_id` and emits seven lines per run, none of them per-role wall-clock, per-round wall-clock or a duration-per-token ratio. So every figure in the note is produced by a throwaway read-only aggregation command quoted verbatim in the note itself, and the quoted command is what a later reader re-runs to check the number. A figure with no command beside it and no stated derivation does not belong in the note.

**DP3 — task attribution is a stated rule with its exceptions enumerated, never an unexamined regex.** The telemetry has no task-id field; a `run_id` such as `20260803T121547Z-t1022` carries the task only by naming convention, and three measured breaks defeat a naive pattern. The note states the rule it used, lists every `run_id` the rule could not bucket or bucketed specially, and states the de-duplication rule applied to the measured duplicate-`seq` pairs, whose rows are near-identical and would otherwise double-count both tokens and duration.

**DP4 — the population is declared with its exclusions, and completeness is never claimed without its accounting.** Every population figure in the note carries the command that produced it. The set of task ids with a review record but no telemetry is derived rather than transcribed — the issue's own suggested window opens at T-1053, and the earliest tasks in that window are among the ones the telemetry never recorded, so the window's shape is itself a finding rather than a parameter. One exclusion is the analysis's own reflection: the loop writes span and event rows for T-1066 while T-1066 runs, so those rows are excluded from the analyzed corpus and the exclusion is stated in the note. An analysis of the loop's cost that counted the cost of observing itself would be measuring its own shadow, and any equality drawn over an unfiltered file would be defeated by the next phase transition rather than by anything about the data.

No value is estimated, interpolated or produced for appearance.

**DP6 — the latency proxy's validity is evaluated in the note rather than assumed by it.** `duration_ms` per 1k `tokens` is the issue's suggested proxy for raw latency, and its inputs are measurably invocation-level totals that a longer ask inflates on both sides. **DP7 — no raw telemetry is committed, and no ignore policy moves.** The telemetry file is gitignored and machine-local; only aggregates land. The note carries no pasted span row, the `.gitignore` files are untouched, and the note passes this repository's PII-shape check before its first commit rather than relying on the CI backstop.

**DP8 — recommendation only.** The note names the metric set that should become the standing before/after instrument for an executor change and expresses it against the binding keys T-1058 already records, and it says plainly that no mechanism ships in this task.
