# drift-evaluator runs the reviewer-binding gate before its `codex --version` probe, and every gate site quotes the checker's own refusal token

**Status**: READY_FOR_ARCH
**Owner**: pm-spec

## Problem

T-1177 added `bin/check-review-provider.sh` and a fail-closed gate in front of every reviewer Codex call. Two follow-ups came out of its cross-provider review (issue #701). First, `agents/drift-evaluator.md` still tells the role to run `codex --version` in its Preconditions (`:18`), while the gate sits at loop step 3 (`:82`). T-1177's goal says the stop comes before any `codex --version`. Second, the run, goal, review and review-response skills, and `agents/code-reviewer.md` (`:172`, `:189`), give every non-zero exit of the checker one fixed label and reason: `reviewer-binding-not-codex` and "the binding is not Codex" (`BLOCKED — reviewer binding is not codex`). That is wrong on exit 2 (`binding-unresolved`, for example a malformed `binding.conf`, or `usage`). The run and goal skills also write that wrong label to telemetry. The stop itself is still correct: nothing is dispatched and Codex is never called.

**Goal (one sentence).** `drift-evaluator` runs `bin/check-review-provider.sh` before any other action, including its `codex --version` probe. Every gate site (the run, goal, review and review-response skills, `code-reviewer`, `drift-evaluator`) escalates with the token from the checker's own stderr line, taken from the closed set `reviewer-binding-not-codex` / `binding-unresolved` / `usage`. **Decisions frozen here** (each is promoted to a criterion):

- **D1 — gate first in `drift-evaluator`.** The gate becomes the first item of `## Preconditions`. It comes ahead of the `codex --version` bullet, and that bullet's own bytes do not change. This matches `agents/code-reviewer.md:14` ("the first step of every mode"). On a refusal the role returns `BLOCKED` with the token, writes no report and runs no `codex` command, `--version` included. Consequence, stated on purpose: a grounding-zero `OOD-novelty` report also carries the `- Codex CLI:` line, which comes from `codex --version`. So a refused gate yields `BLOCKED` and no report even when the spec has no intent block. It is never `OOD-novelty`. The gate text says so. Rejected alternative: moving `codex --version` after loop step 3. That would change the probe's provenance timing and the bytes T-1045 extracts. (**AC1**, **AC4**)
- **D2 — quote the checker's own token.** The token is the second colon-separated field of the checker's single stderr line (`check-review-provider: <token>: <detail>`). It comes from the closed set `reviewer-binding-not-codex` / `binding-unresolved` / `usage`. The detail is never quoted, because exit 1's detail carries the bound provider value. If stderr does not have that shape, or its field is outside the set (for example exit 126/127, or empty stderr), the site still stops `BLOCKED` and quotes the exit status instead of a token. No new checker token is introduced. The run and goal skills record `--label <token>`, the same token, or `exit-<N>` when no token is readable. (**AC1**, **AC2**, **AC3**)
- **D3 — one neutral refusal sentence.** At all six sites the fixed reason ("the `code-reviewer` binding is not Codex on a Claude Code host", `BLOCKED — reviewer binding is not codex`) is replaced by `BLOCKED — reviewer-binding gate refused` plus the token. That sentence is true for every token. The meaning of exit 1 (a non-Codex binding; an actual same-family review is #689) may stay as text that is explicitly conditional on that token. In `review-response`, a `BLOCKED` reply from `code-reviewer` itself is relayed with the reviewer's own reason and is no longer mapped to the binding. (**AC1**, **AC2**, **AC3**)
