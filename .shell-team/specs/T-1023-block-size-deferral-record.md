## Problem

`bin/gen-playbook-blocks.sh` warns, non-fatally, when a generated per-role playbook block exceeds `LINE_WARN_THRESHOLD=40` lines, and its remedy text tells the reader to "consider superseding stale entries". That remedy has now been measured inapplicable twice: the pre-publication repository ran an exhaustive pairwise domination sweep over all 74 then-active corpus entries on 2026-07-26 and found **zero** dominations, and this repository's T-1020 (issue #97, 2026-08-03) scored **22** of its 24 numbered candidates against a stricter three-condition predicate — the other 2 were excluded from scoring by a machine pre-filter before any successor was considered — and found **exactly one** ratifiable pair among the 22: `Scope: maintainer`, so zero block-line impact. Neither sweep produced retirement stock that would shrink a generated block, and for the same reason: the promotion discipline writes positioning sentences at write time, so the corpus does not accumulate the stock a sweep needs to find. Note the precision the record has to keep, because it is designed to be quoted standalone: the second sweep did **not** find nothing — it ratified and applied one retirement, and that retirement was maintainer-scoped, which is why it moved no block.

Only the warning *text* migrated into this repository at publication; the deferral record behind it did not. The consequence is already measured: the remedy phrase regenerated the sweep as issue #97, at the cost of a full adjudication round. Without the record in a citable place, a third sweep is a matter of time — the warning is a standing instruction to launch one, and nothing in the repository says it has already been answered twice.

## Goal

The pre-publication deferral record exists in this repository as a decision record at `docs/loop-engineering/playbook-block-size-deferral.md`, carrying five claims and four re-evaluation signals in a canonical, machine-locked form that cannot decay by paraphrase; and `bin/gen-playbook-blocks.sh`'s threshold warning points at that record instead of prescribing a sweep — replacing only the remedy tail, inside the single physical line the format string occupies, so that the byte-exact `file:line:content` pin in `tests/errexit-safe/run.sh` and the message-head match in `tests/gen-playbook-blocks/run.sh` both stay green with no re-measurement and no test change.

### Settled decisions

Each decision below is resolved. Nothing here is left to implementation judgment. D1–D6 restate the tech-lead's binding constraints; D7–D10 are this spec's own.

- **D1 — remedy wording: option A, head preserved, tail replaced.** The `warning:` vocabulary and the message head stay exactly as they are (`gen-playbook-blocks: warning: playbook-%s.md is %d lines (threshold %d)`), because `tests/gen-playbook-blocks/run.sh:567` matches `*'warning: playbook-engineer.md is'*` and must keep matching with zero test changes. Only the tail `— consider superseding stale entries` is replaced. **The frozen replacement, byte for byte:**

  `— do not launch a supersede sweep on this signal alone; the judgment inputs are recorded in the shell-team repository at docs/loop-engineering/playbook-block-size-deferral.md`

  It does not say the overage is harmless and it does not say the threshold is wrong: it says the judgment inputs already exist and names where. The literal contains **no apostrophe and no backtick** by construction — the format string is single-quoted bash, so an apostrophe in "shell-team's" would terminate the quote, which is why the wording is "in the shell-team repository at <path>" rather than the shorter possessive form.
- **D2 — the no-shift constraint, tightened to exactly one changed line.** `tests/errexit-safe/run.sh:313` pins `gen-playbook-blocks.sh:468` — the `printf`'s *argument* line, 8-space indent — by `file:line:content`. The format string is line **467**, one physical line. The edit is therefore confined to line 467 and nothing else in the file changes: no line is added or removed anywhere, the argument list is untouched (the record's path is embedded as a literal **inside the format string**, never as a fourth `printf` argument), and the header comment lines 40–42 are left byte-identical too. **This is a deliberate tightening of the tech-lead's constraint** (which permitted a line-neutral header edit): an absolute one-line equality lock (AC10) is a stronger no-shift proof than a line-count comparison, it keeps the `--help` window `sed -n '2,48p'` byte-identical rather than merely line-neutral, and the record already has an inbound reference from the warning itself, which the tech-lead designated as the doc's only one. Result: both `tests/errexit-safe/run.sh` checks and `tests/gen-playbook-blocks/run.sh:567` stay green with no re-measurement — the 8th payment of issue #123's class is not made.
- **D3 — claim fidelity is the task's only real failure mode, so every claim is locked by equality, not by containment.** Paraphrase decay is the specific hazard: "the harm was unobserved" degrading into "the harm is small" destroys the record's power to stop a third sweep, while leaving every word of the doc individually defensible. The doc therefore carries a **canonical block of eleven anchored lines** — `- claim-1:` … `- claim-5:`, `- cause:`, `- rejected-levers:`, `- signal-1:` … `- signal-4:` — each of which must equal a literal frozen in this spec's acceptance criteria (`grep -qxF`, full-line equality, plus a count of exactly one occurrence). Prose may surround the block freely; the block is the thing a future reader and a future checker are entitled to trust. AC2–AC6 are the per-claim fidelity locks; AC15 is the prose-reading item QA performs by reading, which is what covers decay in the surrounding prose that no grep can see.
