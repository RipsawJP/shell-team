# Freeze-sweep hardening: the stacked-branch base-ref discriminator and the borrowed-vocabulary count-premise sweep promoted from convention to two checked template lines in pm-spec's spec completion self-check

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1081

**Base ref / branch point — one discriminator for the whole spec.** Every base-side blob read below reads **the branch point**, resolved at check time by one two-arm expression that every criterion spells byte-identically:

```
B=$(if git show-ref --verify --quiet refs/heads/chore/lesson-promotion-2026-08-17; then git merge-base "chore/lesson-promotion-2026-08-17" HEAD; else git merge-base "develop" HEAD; fi) && test -n "$B"
```

The two arms exist because the correct ref has two eras. **Today** this branch is stacked on `chore/lesson-promotion-2026-08-17` (PR #312), which is open and unmerged, so `develop`'s tip does not contain it: a bare `develop` spelling would put that open car's files permanently inside every `<base>...HEAD` range, making this spec's byte-identity and scope-lock criteria structurally unsatisfiable rather than merely red. **After the batch GO** that car merges and its branch is deleted; `git merge-base develop HEAD` then resolves the same commit the first arm resolves today, because `develop` has come to contain it. The first arm is `git merge-base "$BR" HEAD` rather than a `rev-parse` of the branch tip on purpose: a rework round that advances `chore/lesson-promotion-2026-08-17` after this branch was cut moves that branch's tip but not the common ancestor, and the common ancestor is what "branch point" means here. The fallback is selected by an **explicit branch-existence test** (`git show-ref --verify --quiet`) rather than a `2>/dev/null ||` chain, because a `||` chain cannot distinguish "the predecessor branch is gone" (the expected era change, which must fall back) from "`git merge-base` failed for another reason" (which must fail closed). One residual case is disclosed rather than engineered away: a predecessor branch deleted **without** merging would make the second arm resolve `develop`'s tip, which is not this branch's point — that scenario invalidates the whole stack and is a route-back, not something a criterion should paper over. **No 40-hex literal is written into any criterion.** This spec is also the first instance of the very rule it ships, so the paragraph above is simultaneously this task's own discriminator and its dogfooding evidence (see **D5**, **D7**, **AC10**).

**Branch**: `feature/1081-freeze-sweep-hardening`, stacked on `chore/lesson-promotion-2026-08-17` (PR #312, open) at tip `5da079b`, then `develop`. PR base stays `develop`; the PR is held open and merges at the sprint batch GO.

## Problem

Two freeze-time disciplines exist in this repository as convention rather than as text anyone is obliged to read. The first — resolving a stacked branch's base ref through a two-arm expression (the predecessor branch's merge-base while that branch resolves, the integration branch's merge-base once it does not) — was invented once at T-1077's freeze and carried by hand through three more tasks; nothing in `agents/pm-spec.md` names the expression, so its survival depends on whoever writes the next spec having read the last one. The second is the gap that actually produced a defect: T-1080's **AC5** froze a literal zero-count premise about a token its own task did not coin, the freeze sweep scoped its measurement to the six literals that task introduced, and two already-merged sibling tasks had put the token in the file twice — the criterion was unsatisfiable by construction, the engineer escalated `BLOCKED`, and a class-B re-freeze was spent repairing it. Both disciplines belong in the checklist the spec author is required to run before setting `READY_FOR_ARCH`, and one of them already has a promoted corpus entry with no checklist item discharging it.

## Input space

**Reachable input classes** — what real usage of this repository and of an adopter's can produce, and what the two shipped items must handle correctly:

- **Which form the declaration takes is decided by two questions asked in this order**, so that every class below has exactly one disposition and the mirror gate has a decidable acceptance rule rather than a judgement call. **(1)** Does any criterion in the spec read a base-side blob? If not, the declaration is `not-applicable — <reason>` whatever the branch shape — there is nothing to discriminate. **(2)** If one does, does the branch have an open predecessor **at authoring time**? If yes, the declaration is the two-arm expression instantiated with that predecessor; if no, it is `not-applicable — <reason>` naming the branch's own actual base ref. Classification happens once, at authoring time, and a mid-task era change never reclassifies a spec.
- A spec frozen on a branch stacked behind **one** still-open predecessor PR (this task's own shape) and behind **several** (T-1080 sat behind PRs #305, #303 and #296 — measured from that spec's own `**Branch**` line). Question (2)'s `yes` branch: the two-arm expression, which is depth-independent by construction because it reads one predecessor branch and never the chain.
- A checkout in which the predecessor branch exists only as a remote-tracking ref — a fresh clone or a CI runner that fetched but created no local branch. Question (2)'s `yes` branch still: the predecessor is present, so the two-arm expression applies and the existence test must find it in whichever namespace it lives in rather than assuming `refs/heads/`.
- A spec frozen on a branch cut directly from the integration branch with no open predecessor. Question (2)'s `no` branch: the declaration is `not-applicable — <reason>` naming its own actual base ref — for example `not-applicable — cut directly from <integration-branch>; branch point is git merge-base "<integration-branch>" HEAD`. The two-arm *discriminator* is what does not apply here: with no predecessor there is nothing to instantiate the first arm with, so a spec of this class carrying the expression anyway would be declaring an arm it cannot resolve.
- A spec whose predecessor branch is **merged and deleted mid-task** — the era change the fallback arm exists for. It keeps the two-arm declaration it was classified into at authoring time, since the deletion never reclassifies it. Across this class's own era change the resolved branch point never moves, in two stages: while the merged predecessor still exists, both arms resolve the same commit; once it is deleted, the existence test selects the fallback arm, which resolves that same commit.
- A spec whose criteria read **no base-side blob at all** — question (1)'s `no` branch: `not-applicable — <reason>`. That question is asked first deliberately, because it outranks branch shape: a spec stacked behind an open predecessor whose criteria read no base-side blob still takes `not-applicable`, rather than declaring a discriminator with nothing to discriminate.
- A spec making **zero** literal count premises and a spec making several, mixing both classes: own-coinage (a literal the task itself invents, e.g. T-1080's six `concurrent-review-window`-family tokens) and borrowed (an invariant-lock id such as `both-gates-green`, a status flag such as `READY_FOR_QA`, a grammar family name such as `- substrate:`, or any token another document coined).
- Branch names of this repository's and an adopter's conventions, which contain `/` and `-` and digits (`chore/lesson-promotion-2026-08-17`, `feature/1079-tier2-judge`) — the expression is written so a `/` in a branch name is ordinary.
- An adopter whose integration branch is named something other than `develop` — the shipped fallback arm names the integration branch as a parameter for exactly this class.

**Out-of-scope synthetic extremes** — named concretely, and declined:

- A predecessor branch **deleted without being merged**. It makes the fallback arm resolve the integration branch's tip, which is not the branch point. Disclosed as a route-back that invalidates the stack; no criterion papers over it and no arm is added for it.
- A predecessor branch **rebased or force-pushed after this branch was cut**. The recorded common ancestor may no longer be an ancestor of the predecessor's new tip, so `git merge-base` resolves a commit that is no longer this branch's point. Disclosed as a route-back on the same footing as an unmerged deletion; no arm is added for it.
- Branch names containing whitespace, a newline, a shell metacharacter or a leading `-`. Every branch on this stack follows the `feature/<topic>` / `chore/<topic>` shape (`feature/1081-freeze-sweep-hardening`, `chore/lesson-promotion-2026-08-17`, `feature/1079-tier2-judge`), which cannot produce one, and no criterion below is written to survive one.

- Any adversarial input to a **mechanical parser** of either declaration or enumeration. No such parser exists in this task's scope, so its input space is empty by construction rather than by concession.
