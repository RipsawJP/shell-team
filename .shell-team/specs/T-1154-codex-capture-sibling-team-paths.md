# `bin/codex-capture.sh` resolves the reviews dir through the `team-paths.sh` sitting next to itself, so an adopter's plugin-root invocation without `--reviews-dir` works from the adopter's own repository

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1154

**Branch**: `feature/594-codex-capture-sibling-team-paths`, cut from `develop` at `3698c136`. **No predecessor pull request is open** (this is the first task of its sprint), so the branch point is `develop` itself. Every criterion below that reads a base-side blob names that commit through `git rev-parse --verify 3698c136^{commit}`, spelled byte-identically in each, so a checkout that does not carry the object fails closed instead of resolving something else. The literal is written on purpose rather than `git merge-base develop HEAD`: `develop` moves when later work merges.

## Problem

Both `agents/code-reviewer.md:10` and `agents/drift-evaluator.md:10` tell the role to invoke `codex-capture.sh` as `bash "<plugin root>/bin/codex-capture.sh"`, never assuming it is on `PATH`, and their `alloc` skeletons (`agents/code-reviewer.md:40`, `agents/drift-evaluator.md:85`) pass no `--reviews-dir`. With no `--reviews-dir`, `bin/codex-capture.sh:257`–`:264` looks for `team-paths.sh` on `PATH` and then for a cwd-relative `bin/team-paths.sh`, and otherwise exits `2`. In an adopter repository neither exists — the plugin is not on `PATH` there and the adopter has no `bin/team-paths.sh` — so the documented invocation dies before allocating anything. The same script's sibling `bin/team-paths.sh` is always shipped next to it, and `bin/close-out.sh:117`–`:127`, `:191` already resolves its own sibling that way. This repository's own dogfood never shows the defect, because its checkout root does carry `bin/team-paths.sh`.
