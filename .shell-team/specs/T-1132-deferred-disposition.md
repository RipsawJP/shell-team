# A third terminal fast-follow disposition value: `deferred: <reason>`

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1132

## Problem

The fast-follow disposition rule (T-068) admits a closed set of terminal values — `filed as issue #N` and `waived: <reason>` — plus a time-bound `pending: <reason> — <deadline>` that `bin/close-out.sh` refuses at close-out. For a file-an-issue intent the orchestrator opens the issue "via this repo's normal issue-creation flow, including a user-approval gate where that applies". In an adopting repository where issue creation needs the operator's approval, that sentence turns every reviewer deferral into a question back to the author before close-out can pass. It was observed in two consecutive runs of the same adopter, and in one of them the orchestrator worked around it by recording `waived:` together with a note that the finding was not actually waived — which misrecords the decision. The rule as shipped has no way to say "the author has not ruled yet, and the loop does not need them to rule before close-out".

## Goal

## Non-goals

- **No new gate class.** `bin/close-out.sh`'s refusal condition is unchanged: it still refuses on the literal `pending:` on an anchored disposition line and on nothing else. A reasonless `deferred:` is not mechanically refused, exactly as a reasonless `waived:` is not refused today; the reason's mandatoriness is a grammar obligation stated in prose on both skill surfaces.
- **`pending:` semantics are unchanged, in both directions.** It stays time-bound, it still must not survive close-out, and its permitted resolutions stay exactly `filed as issue #N` and `waived: <reason>`. A `pending:` already recorded is **not** resolvable to `deferred:`: its recorder committed to a deadline, and erasing that commitment would change the meaning of something already recorded. `deferred:` is chosen at the recording step in place of `pending:`, never as an escape from one.
- **The rejection message's bytes do not change.** `resolve it to a filed issue number or a waived reason before close-out` stays exactly as it is; it names the resolution set of a `pending:` placeholder, which the previous bullet leaves unchanged, so it stays accurate as well as locked.

## Input space

**Reachable input classes** — what a real board and a real run produce, all of which the implementation must handle correctly:

1. An entry with **no** `- fast-follow disposition (` sub-bullet at all (the reviewer wrote `no fast-follow deferrals`). The gate says nothing; close-out passes. Unchanged.
2. An entry whose disposition line carries only the pre-existing resolved forms, `filed as issue #N` and/or `waived: <reason>`. Passes. Unchanged.
3. An entry whose disposition line carries `deferred: <reason>` as its only value. Passes — the new class this task documents and fixtures.
4. An entry whose disposition line carries **two or more** findings' dispositions, including two or more `deferred:` values, mixed freely with `filed as issue #N` and `waived: <reason>`. Passes. This is why the surfacing duty's wording must read correctly for N ≥ 2.
5. An entry whose disposition line carries `pending:` — alone, or mixed with any other value including `deferred:`. Refused, exit 1, board byte-identical. Unchanged.
6. A `deferred:` whose **reason text** contains the literal `pending:`. Refused, by the same whole-line grep as class 5. Ruled on rather than engineered around: the grammar forbids it, and the refusal is accepted as correct fail-closed behaviour.
7. Hand-off **prose** elsewhere in the entry that quotes the anchor string and a disposition value mid-line, without being a line-start disposition sub-bullet. Not a disposition line; the anchored first grep already excludes it. Unchanged.
8. Either supported layout — the default `.shell-team/` base directory and the legacy `tasks/` one — since the gate reads whichever board `bin/team-paths.sh` resolves and scans only the closing task's own Active entry range.
9. Zero deferrals in a run that had some other disposition: the `undispositioned fast-follows` heading is omitted rather than printed empty.

**Out-of-scope synthetic extremes** — named concretely, and declined:

- Near-miss spellings of the new value (`Deferred:`, `deferred :`, `defer:`, `DEFERRED:`). No disposition value has a mechanical vocabulary check today — the gate matches the single literal `pending:` and nothing else — and this task adds none, so such a line passes close-out exactly as any other reason string does. Detecting them would be the new gate class the Non-goals exclude.
- Invisible-character evasion inside a reason or a value: zero-width spaces, a BOM before the bullet dash, U+2011 non-breaking hyphens, right-to-left marks. There is no vocabulary matcher for these to evade, so they are not a defect class this task can have.
