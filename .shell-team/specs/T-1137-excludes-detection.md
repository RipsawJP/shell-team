# A globally-hidden base dir reads as the misconfiguration it is: the README states the durability consequence, and `not-durable` refuses instead of describing a steady state

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1137

## Problem

An adopter whose machine-wide `core.excludesFile` lists the base dir can scaffold, run the loop to close-out, and end with the board, the spec, every provenance and interventions entry, the review record and the telemetry rows existing only in one working tree — unrecoverable if it is lost. The gate built to prevent exactly that fired (`check-durability.sh` returned `not-durable`), and the run continued anyway, because the refusal reads as a describable environment fact rather than as a refusal. Two of the three gaps issue #475 names are cheap prose the loop can close now: the README presents global excludes as one of two supported choices and describes its cost as a *visibility* problem, so an adopter who reads only the README picks it and inherits a consequence the README never states; and `not-durable`'s message names a reason token without ever saying that a hidden base dir is a misconfiguration the loop does not support. The third gap — having `team-init` ask git at init whether the base dir is ignored — is measured below to be forbidden by merged frozen intent, twice over, and is refused here on that ground rather than attempted; `## Scope ruling` records the measurement, the decision and the one condition that would reopen it.
