## Problem

An adopter whose resolved base dir is git-ignored gets a loop that reports success while committing nothing: every record the loop writes — board, provenance, interventions, reviews — lands in a directory git refuses to stage, the commit-immediately disciplines (interventions T-1002, provenance T-074) no-op silently, and the seam gates plus the T-073 uncommitted-diff guard all stay green. That is GitHub issue #167.

Two tasks have now tried to answer that by **asking git the question inside the plugin**, and the mechanism has failed cross-provider review three times. T-1042's probe drew seven Majors across two rounds. T-1046 v1 drew a Major on the verdict-acquisition layer on the first round it ever had (`GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n` environment injection). T-1046 v2 replaced that enumeration with an `env -i` allow-list — a genuine strategy change, not a longer list — and round 2's adversarial pass defeated it twice more, at two different privilege tiers:

- **Blocker** — an exported bash function named `env` intercepts the sanitizing call before `PATH` is ever consulted, because bash resolves shell functions ahead of a `PATH` lookup. The allow-list never executes. Reachable at the *same* environment-variable-only tier as round 1's finding, and the identical root cause would let an exported function named `git` bypass the mechanism even more directly.
- **Major** — `env -i` clears the *process* environment but not git's *file-based* system-scope configuration (`$(prefix)/etc/gitconfig`, read live under the exact allow-list on the machine this was measured on), and a system-scope `core.excludesFile` flips the verdict identically to any other scope. v2's Input space never named that config scope at all.

v2's `## Same-class-2 pre-commitment` had recorded the acquisition layer's budget as **zero rounds remaining** and named its fallback verbatim in advance. It fired. **This v3 executes that fallback and nothing else**: the probe is deleted, the plugin ships the *question* rather than an answer to it, and #167 closes as **answered** rather than as mechanised. The choice among dispositions is not re-opened here — the pre-commitment's own text forbids presenting the menu a third time, and this spec does not present it.

## What this costs

Stated plainly, because it is a real cost and not a framing. Sprint v1.7.0's goal item for issue #167 was to **close it with a mechanism**. v3 closes it with documentation. The contract that produced this outcome was written before the outcome was known, by the same role, and ruled out re-presenting the choice. Executing it is therefore not a quiet descope: it is the contract working. What would be a quiet descope is executing it without saying that the goal item was not met as ratified — so it is said here, on the board, and in `## Non-goals`.

Two things are preserved rather than lost. The **knowledge** is in the git history of this file: three frozen versions, fourteen measured channel-admissibility rows, and a review record naming four distinct defeat vectors — a far better input to any future attempt than the empty page T-1042 started from. And #167's *user-facing* value is partly delivered: the adopter who reads the adoption guide learns the failure mode, gets a command that answers it in one line, and learns what to do about each answer.

## Input space

**Reachable input classes** — what the deliverable really meets. The shipped artifact is two blocks of documentation, so its input surface is the set of situations in which the command they print gets run, plus the contexts it is run from.

- **Repository states an adopter runs the command in**: an ordinary work tree at its root; a work tree whose base dir is ignored by the repo's own `.gitignore`; one ignored by `.git/info/exclude`; one ignored by a global `core.excludesFile` reached through `HOME`; one where a repo-level `!<base>/` re-include overrides a global rule (this repository's own state, and the remedy the surrounding documentation recommends); a bare repository; a directory with no repository anywhere in its ancestry; a repository git refuses to operate on or cannot read. The block's three answers must be true across all of them, which is why AC5 exercises one state from each answer class rather than one state overall.
- **Base-dir resolution classes**: the default `.shell-team`; the legacy layout's `tasks` (selected by `ROOT/tasks/loops/shell-team.contract.yaml`); an explicit `TEAM_RUN_BASE`, including the hostile-but-permitted shapes `validate_base` accepts (a leading `:`, `!` or `-`, and the glob metacharacters `*`, `?`, `[…]`). The block's substitution-free fallback names all three resolution rules, so a reader on any of them can follow it.
- **Execution contexts** (D12): a repository root with the plugin's `bin/` on `PATH`, where the printed command runs verbatim; and a shell where `team-paths.sh` is not resolvable, where the block's written-out form applies. Both are ordinary — an adopter reading the adoption guide may not have loaded the plugin yet.
- **Readers of the documents**: a markdown renderer (GitHub's, principally) and a plain-text reader. The block is plain prose plus one indented command line, so both render it readably.

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect, so a finding that escalates one of them is answerable rather than open-ended.

- **Every environment-injection and configuration-scope channel**, named exhaustively because this is where the previous two versions died: `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_DIR`/`GIT_WORK_TREE` redirection, `XDG_CONFIG_HOME`, `GIT_CONFIG_NOSYSTEM`, an exported shell function named `env` or `git`, a hostile `PATH` or `HOME`, and system-scope `$(prefix)/etc/gitconfig`. **This class is out of scope by construction, not by concession**: no shipped code invokes git, and the adopter runs the printed command in their own shell, where their own environment and their own configuration are theirs. A finding of the form "an ambient variable changes what this command answers" describes the adopter reading their own machine's configuration, which is the point of the command.
- **A shell in which the adopter has redefined `git` itself.** Out of scope for the same reason, one level up: a document cannot defend a reader against their own shell.
- **A markdown renderer that reflows or re-indents the command line.** The shipped bytes are what this spec freezes; a renderer's presentation of them is not defended, and the substitution-free fallback exists precisely so a reader who cannot copy the line exactly can still act.
- **A symlink, a submodule gitlink, or a regular file placed exactly at the resolved base path** (D10 iii). Still an issue candidate, still not answered here.
- **Base dir names `validate_base` already rejects** — absolute paths, `~`-paths, anything containing whitespace, any `.`/`..`/empty component. They never resolve, so the command is never built from them.
- **A git build whose observed behaviour contradicts its own installed documentation**, and a future git that changes `check-ignore -v`'s output format. AC5 turns red if either happens, which is the correct response to it.
- **A TOCTOU race** — an ignore rule or the base dir changing between the adopter's check and their next command. The block is advice, guards no security boundary, and says nothing that a later change could falsify retroactively.
- **Ever-larger repositories, ever-deeper ignore-rule sets, ever-longer base dir names, or ever-more languages.** One command, two documents; a demand to bound a cost, fix a width, or add a third translation is out of scope.
- **Every surface other than `docs/adopting.md` and `docs/adopting.ja.md`** — the README, the skills, the agents, `AGENTS.md`, and any per-loop-step notice. Named here as well as under `## Non-goals`, because the escalation this task is most exposed to is "here is one more place this advice belongs"; the answer is a fresh task with its own budget, not a widened diff.
