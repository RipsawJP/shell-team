## Problem

An adopter whose resolved base dir is git-ignored gets a loop that reports success while committing nothing: every record the loop writes — board, provenance, interventions, reviews — lands in a directory git refuses to stage, the commit-immediately disciplines (interventions T-1002, provenance T-074) no-op silently, and the seam gates plus the T-073 uncommitted-diff guard all stay green. That is GitHub issue #167.

T-1042 tried to answer it and could not. Its probe drew **seven** Major findings across two consecutive cross-provider rounds (M1-M4, then NM1-NM3), which fired that spec's own same-class-2 pre-commitment; disposition (i) split the work out into this task. The synthesis recorded there is the design input, and it is not "seven bugs": it is **one root cause with seven faces — the probe asked git questions whose answers it read through channels git does not guarantee**. A localised diagnostic string (NM1). A configuration key that does not exist (NM2). A stream shared with tracing output (NM3). A pathspec grammar `check-ignore` does not accept (M1). A query form whose answer depends on whether the directory happens to exist yet (M3). A message asserting a fact that is false in one of the two shipped layouts (M4).

This task therefore does not patch that probe. It settles, up front and in frozen text, **which channels may carry a verdict at all**, builds a decision table over exactly those channels, and ships an implementation that is a transcription of the table.

### The admissibility rule

**A channel may carry a load-bearing verdict only if both hold: (1) its contract is stated in locally installed git documentation, and (2) the value read is a machine channel — an exit status, a documented plumbing or porcelain format, or NUL-delimited output. A human-readable diagnostic never asserts anything; at most it justifies declining.** Every row of the decision table below cites the documented guarantee it rests on. A channel that fails either half is not "used carefully" — it is not used.

### Measured channel admissibility

Restated here from the measurement run named in `## Summarized sources`, so the frozen text does not depend on an ephemeral file.

| channel | verdict | measured ground |
|---|---|---|
| `git check-ignore` exit status 0 / 1 / 128 | **admissible** | matches `git-check-ignore(1)`'s EXIT STATUS section verbatim in every case tried; the one channel with zero daylight between documentation and observation |
| `git check-ignore` bare-form query, glob-shaped name with a tracked glob-colliding path present | inadmissible | silent false negative; undisclosed by the man page |
| `git check-ignore` query whose first character is `:` (any form, `--stdin -z` included) | inadmissible | silent false negative; root cause documented in `gitglossary(7)`'s pathspec grammar, not cross-referenced from `check-ignore(1)` |
| `git check-ignore` with `:(literal)`, `--literal-pathspecs`, or `GIT_LITERAL_PATHSPECS=1` | inadmissible, usable only to decline | all three are unconditionally fatal (128) on this subcommand, for every base name |
| `git check-ignore --stdin -z` as a literal-pathname escape hatch | inadmissible | reproduces both false-negative classes identically to bare argv |
| `git check-ignore` query of the form `./<base>/` (trailing slash, `./` prefix, no explicit magic) | **admissible** | correct in all four dir-shape × existence combinations tried; closes the not-yet-created-dir gap, the tracked-glob-collision false negative and the colon-leading false negative together |
| `git rev-parse --is-inside-work-tree` read as `rc=0 ∧ stdout ∈ {true,false}`, streams genuinely separate, `LC_ALL=C` pinned | **admissible** | fully documented "print true/false" contract; measured immune to `GIT_TRACE` once stdout and stderr are separate destinations |
| `git rev-parse` nonzero exit as a discriminator for *which* fatal condition occurred | inadmissible | at least five distinct root causes collapse to the identical 128; the only separating signal is locale-dependent stderr text |
| `git ls-files` exit status without `--error-unmatch` | inadmissible | documented to be 0 regardless of match |
| `git ls-files --error-unmatch` exit status 0 / 1 | admissible, **not used** (D4) | matches its man-page clause exactly; the condition it would serve is dropped |
| `git status --porcelain=v2 --ignored=matching -z` | admissible, **not used** | inherits the not-yet-created-dir blind spot with no available normalization, so it buys nothing the `./<base>/` query does not already have |
| `env -u GIT_DIR -u … LC_ALL=C git …` neutralization prefix | **admissible as hygiene** | bash-3.2-viable, no arrays; `-u` on an unset variable is a documented no-op |

### The frozen decision table

Nine rows. Row ids `DT0`-`DT8` are the mechanism's whole classification: every state the emitter can be in resolves to exactly one row, and the implementation is a transcription of this table. Rows are evaluated in id order; the first row whose measured input matches decides the outcome and no later probe runs. Outcome classes are exactly three: **IGNORED** (emit `V1`), **UNDETERMINABLE** (emit `V2`), **SILENCE** (emit nothing).

| row | probe | measured input | outcome | documented guarantee relied on | reachable |
|---|---|---|---|---|---|
| DT0 | none | the `git` executable is not resolvable on `PATH` | SILENCE | no git channel exists to read; a scaffolder that has no git cannot report a git verdict | yes, statically guarded |
| DT1 | `rev-parse --is-inside-work-tree` | `rc=0` and stdout is exactly `true` | continue to DT5 | `git-rev-parse(1)`: the flag prints `true` or `false` | yes |
| DT2 | `rev-parse --is-inside-work-tree` | `rc=0` and stdout is exactly `false` | SILENCE | same clause; with no work tree there is no work-tree ignore answer to report, and `check-ignore` is documented to require one | yes, a bare repository |
| DT3 | `rev-parse --is-inside-work-tree` | `rc=0` and stdout is neither `true` nor `false` | SILENCE | the value is outside the documented print contract, so nothing determinate was read | no — unreachable through documented behaviour; the row exists so the classification is total and the implementation has no fall-through |
| DT4 | `rev-parse --is-inside-work-tree` | `rc` is nonzero | SILENCE | at least five distinct fatal causes collapse to the identical exit status, and the only separating signal is a human-readable diagnostic, which the admissibility rule forbids from asserting | yes, and this is the row that deletes T-1042's "outside a git work tree" notice |
| DT5 | `check-ignore -q -- "./<base>/"` | `rc=0` | **IGNORED**, emit `V1` | `git-check-ignore(1)` EXIT STATUS: "0 — One or more of the provided paths is ignored." | yes |
| DT6 | `check-ignore -q -- "./<base>/"` | `rc=1` | SILENCE | same section: "1 — None of the provided paths are ignored." | yes |
| DT7 | `check-ignore -q -- "./<base>/"` | `rc=128` | **UNDETERMINABLE**, emit `V2` | same section: "128 — A fatal error was encountered." | yes |
| DT8 | `check-ignore -q -- "./<base>/"` | `rc` is none of 0, 1, 128 | **UNDETERMINABLE**, emit `V2` | the value is outside the documented exit-status set, so nothing determinate was read | no — unreachable through documented behaviour; the row exists so the classification is total and no unexpected status can fall through to silence |

Three invocation constraints bind every git call the emitter makes, and are part of the frozen table rather than implementation latitude, because each is the direct remedy for one of the seven historical faces:

- **Normalized query.** The `check-ignore` pathspec is the base dir rendered with a `./` prefix and a single trailing slash, carrying no explicit pathspec-magic annotation of any kind. Its first character is therefore never `:`, and it is never a bare directory name.
- **Separated streams.** Every probe's stdout and stderr go to genuinely separate destinations. `2>&1` appears nowhere in the emitter.
- **Neutralized environment.** Every probe runs with `LC_ALL=C` and with `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS`, `GIT_ICASE_PATHSPECS`, `GIT_NOGLOB_PATHSPECS`, `GIT_TRACE`, `GIT_TRACE2`, `GIT_TRACE2_EVENT`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` unset for the duration of the call.

### Settled decisions

Each decision below is resolved; nothing here is left to implementation judgment. Every text this task ships is frozen byte for byte in this section, and every acceptance criterion reads its expected bytes **out of this file** rather than restating them, so a criterion cannot drift from the text it guards.

- **D1 — the deliverable is the table, and the code is its transcription.** T-1042's mechanism failed four times because each round patched the *place* the last finding landed. The unit of review here is the nine-row table above: a finding against this mechanism is a finding that some reachable state is missing a row, that a row cites a guarantee its channel does not actually give, or that the implementation disagrees with a row. `DT3` and `DT8` are kept as rows although they are unreachable through documented behaviour, because their absence is what turns an out-of-contract value into a silent fall-through.
- **D2 — the notice is advisory, and this is re-argued rather than inherited.** `docs/adopting.md` states that whether to git-ignore the base dir is the adopter's call and that the plugin will not make that edit for them. An ignored base dir is therefore a **supported configuration**, not an error, and a scaffolder must not fail on one: `bin/team-init.sh` exits 0 in all three outcome classes and its documented exit contract (0 success, 2 usage error) is unchanged. The repository's fail-closed invariant governs **checkers that return verdicts**; `team-init` is a scaffolder, and the applicable form of fail-closed here is `DT7`/`DT8` — a channel that cannot evaluate its input never reports "not ignored", it reports undeterminable. The rows that decline silently (`DT0`, `DT2`, `DT3`, `DT4`) are not fail-open: in each of them no work-tree context was established through an admissible channel, so there is no verdict to withhold.
- **D3 — three outcome classes, two of which emit; T-1042's "outside a git work tree" notice is deleted.** That notice cannot be reconstructed: the state it named is reachable through a nonzero `rev-parse` exit that is indistinguishable from a corrupt gitfile, a corrupt repository directory, a bogus `GIT_DIR` and a dubious-ownership refusal, and the only thing that separates them is diagnostic text. The one sub-case that *is* determinate — `rc=0` with stdout `false`, a bare repository — is a state where the ignore question has no work-tree answer at all. Both therefore route to SILENCE (`DT2`, `DT4`). This is a deliberate reduction in helpfulness bought with soundness, and it is the single largest visible difference from T-1042's design.
- **D4 — the tracked-file half of T-1042's two-part warning condition is dropped, and the `ls-files` channel with it.** Three grounds. (i) The documented remedy for an ignored base dir is a repo-level `!<base>/` re-include, and a re-include makes `check-ignore` answer `1` — so the shape the tracked-file test was protecting against already resolves to SILENCE through `DT6`, without a second channel. (ii) `V1` is reworded to report **what git answered** ("the resolved base dir is matched by a git ignore rule") rather than to predict committability, and that statement stays true even when the base dir has been force-added, so the false-positive the second channel existed to prevent is no longer a false statement. (iii) Every additional channel is an additional admissibility surface, and this task's same-class-2 budget for the verdict-acquisition layer is **one** round. The `ls-files` error-swallowing minor T-1042 carried forward is thereby moot, not deferred.
- **D5 — no acknowledgement flag, re-settled with a new fact.** The persistence objection stands: the only natural home for an acknowledgement is a file under the base dir, which is precisely the directory that is ignored, so the acknowledgement would itself be uncommittable and would not survive a fresh clone or a second machine. The new fact is that the emitter is `team-init` only (D6), which fires once per adoption rather than once per loop step — so the total noise a flag could suppress is one message per adoption, which does not buy a persistence mechanism. An environment variable was considered and declined for the same reason in reverse: it shifts the burden to every invocation environment to silence a message that fires once.
- **D6 — one emitter: `bin/team-init.sh`, after scaffolding, on stderr through `log_warn`.** `bin/team-paths.sh` gains nothing and is byte-identical to the base ref (AC7), which is the strongest available form of T-1042's `--export`/`--get` byte-identity constraint: those modes cannot change because the file does not change. Grounds for choosing `team-init` over `--print`: the issue's scenario is adoption-time, `team-init` runs once per adoption so the notice never becomes per-invocation noise, and the after-scaffolding ordering has a natural site there and none in a pure path resolver. Choosing one emitter also deletes T-1042's one-body/two-implementations byte-identity lock and its parallel-surface symmetry table outright — there is no parallel surface. The notice goes to **stderr** so the scaffolding report on stdout stays parseable, and it routes through the existing `log_warn` helper so the `WARN: ` prefix and the errexit guard (D10) are shared with the script's other diagnostics rather than duplicated.
- **D7 — `validate_base` is NOT tightened to reject a leading `:`, and the blast radius is why.** The measurement's own recommendation was to tighten it at the shared choke point. Declined here on three grounds. (i) The gap it would close is already closed for this mechanism: the normalized `./<base>/` query answers correctly for a colon-leading base, measured, so this task has no open hazard to fix. (ii) `validate_base` is the single choke point every adopter's `TEAM_RUN_BASE` passes through, and tightening it would newly **reject a value the resolver has always accepted** — a breaking change to a published contract, bundled into a task about a notice. (iii) A pathspec hazard in some *other* consumer of the base value is a finding about that consumer, with its own blast radius and its own fixtures. Recorded as an issue candidate. AC6 promotes this ruling to a criterion in both directions: the colon-leading base must still be accepted by the resolver **and** must still be reported ignored.
- **D8 — query normalization and invocation hygiene are frozen, not left to judgment.** The three invocation constraints stated under the decision table are each the direct remedy for a historical face (M1/M3/NM2 for the query form, NM3 for stream separation, NM1 and the ambient-`GIT_*` minor for the neutralized environment), so they are frozen alongside the rows they protect. What is **not** frozen is how the emitter is factored into functions or variables; that is implementation.
- **D9 — fixture isolation and explicit excludes pinning.** Every fixture that needs a real repository is its own `git init`-ed work tree under a `$TMPDIR`-backed root, never under this repository's own tree, and pins `core.excludesFile` through the fixture repo's **persisted** config (`git -C <dir> config core.excludesFile …`), never a transient `-c` flag on the test's own command, because the git call under test is made inside the script and a `-c` on the outer invocation never reaches it. One fixture (`LX08`) deliberately pins a **hostile** excludes file that itself ignores the base dir, to prove the notice honours the global-excludes source, and its twin adds a repo-level `!<base>/` re-include to prove the documented remedy silences it. The pre-existing non-git fixtures under the suite's own tree stay where they are; if any of them becomes environment-sensitive because the probe now runs inside this repository's work tree, the fixture root moves — the notice does not weaken.
- **D10 — inherited disposals, by name.** (i) The `log_warn()` errexit guard (a `|| true` on its own `printf … >&2`, reverted with T-1042's descope) **lands here**, because this task makes that helper reachable on a normal `team-init` run: without it a closed stderr makes the advisory notice abort the whole scaffolder under `set -euo pipefail`, which is exactly the contradiction D2 forbids. It gets a criterion (AC8), a protected-content-lock row in `tests/errexit-safe/run.sh` part (iv) — where its `; }` shape belongs, since a stripped guard would match none of part (iii)'s patterns — and a closed-stderr behavioural assertion. Fixing the definition also closes the three pre-existing `skipped existing file` call sites. (ii) The `ls-files` error-swallowing minor is **moot**: D4 removes the channel. (iii) A symlink or submodule gitlink placed exactly at the resolved base path is declared an **input-space boundary** below and recorded as an issue candidate; it is not fixed here, because the fix is a different question (what a base dir is permitted to be) with its own blast radius.
- **D11 — no new suite, no CI change, and exactly one documentation sentence per language.** Every fixture extends `tests/team-init/run.sh` and `tests/errexit-safe/run.sh`, both already wired, so `.github/workflows/check-handoff.yml` is byte-identical. `docs/adopting.md` and `docs/adopting.ja.md` each gain at least one added line naming `team-init`, describing the report and its advisory nature, with **zero removed lines** — a user-visible message that no document mentions is a documentation defect, and a larger documentation delta is surface this task's review budget cannot afford.

## Input space

**Reachable input classes** — what the emitter really receives, and what it must handle correctly:

- **A resolved base dir path** as `bin/team-paths.sh` emits it: a repo-relative subpath with no whitespace and no `.`/`..`/empty component, and — because `validate_base` permits them and D7 keeps permitting them — possibly beginning with `:`, `!` or `-`, or containing the glob metacharacters `*`, `?` and `[…]`. All six of those hostile-but-permitted shapes were measured against the shipped query form; five are answered correctly by the trailing-slash normalization alone and the sixth (leading `:`) by the `./` prefix.
- **A target directory that is** any of: an ordinary work tree; a bare repository; a directory with no repository anywhere in its ancestry; a directory whose `.git` is an invalid gitfile; a directory whose `.git/` exists but lacks `HEAD`/objects; a directory reached with a bogus `GIT_DIR` exported; a subdirectory of a work tree rather than its root.
- **Ignore rules arriving from all four sources** — the repo's `.gitignore`, `.git/info/exclude`, a `core.excludesFile` (including one that is hostile, i.e. names the base dir itself), and a re-include negation — in both the bare form (`base`) and the directory form (`base/`), with the base dir present or absent on disk at query time.
- **An ambient environment carrying any of** `GIT_TRACE`, `GIT_TRACE2`, `GIT_TRACE2_EVENT`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS`, `GIT_ICASE_PATHSPECS`, `GIT_NOGLOB_PATHSPECS`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, and any locale settings including a non-English one.
- **A closed stderr** (`2>&-`), which a fail-closed gate, a CI wrapper or a `2>&-` composition can supply to any script.
- **Any git version whose behaviour matches its own installed documentation.** The admissibility rule is anchored on documented contracts, so a version change that keeps its documented contracts is in scope and one that breaks them is not (see below).

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect, so a finding that escalates one of them is answerable rather than open-ended:

- **A real dubious-ownership state constructed with `chown`.** It cannot be built in this environment, and it lands on the same `DT4` row as four other fatal causes by construction; the row is exercised through a stubbed `git`, which is the boundary this spec protects rather than a real ownership state.
- **A git build whose observed behaviour contradicts its own installed documentation.** The whole design rests on documented contracts, and `LX09` is the fixture that turns red if that assumption ever breaks — which is the correct response to it, not a code path.
- **A symlink or a submodule gitlink placed exactly at the resolved base path**, and a base path that is a file rather than a directory. Declared a boundary here as well as a Non-goal, and recorded as an issue candidate: the fix is a ruling about what a base dir may be, not about which channel answers a question.
- **A TOCTOU race** — an ignore rule, an index entry or the base dir itself changing between the two probes, or between a probe and the operator's next command. The mechanism is advisory, guards no security boundary, and a real fix needs index-level coordination disproportionate to the risk.
- **Base dir names that `validate_base` already rejects** — absolute paths, `~`-paths, anything containing whitespace (a newline included), and any `.`/`..`/empty component. They never reach the emitter.
- **Ever-larger repositories, ever-deeper ignore-rule sets, or ever-longer base dir names.** The mechanism is two git invocations; a demand to bound their cost or to fix a width is out of scope.
- **Every surface other than `bin/team-init.sh`** — `team-paths.sh`'s three modes, the skills, the agents, and any per-loop-step invocation. Named here as well as under `## Non-goals`, because the escalation this task is most exposed to is "here is one more place the same check belongs"; the answer is a fresh task with its own budget, not a widened diff.
