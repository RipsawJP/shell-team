## Problem

An adopter whose resolved base dir is git-ignored gets a loop that reports success while committing nothing: every record the loop writes — board, provenance, interventions, reviews — lands in a directory git refuses to stage, the commit-immediately disciplines (interventions T-1002, provenance T-074) no-op silently, and the seam gates plus the T-073 uncommitted-diff guard all stay green. That is GitHub issue #167.

T-1042 tried to answer it and could not: its probe drew **seven** Major findings across two consecutive cross-provider rounds, firing that spec's same-class-2 pre-commitment, whose disposition (i) split the work out into this task. The synthesis recorded there is not "seven bugs" but **one root cause with seven faces — the probe asked git questions whose answers it read through channels git does not guarantee**.

T-1046 v1 answered that with an admissibility rule, a nine-row decision table over **two** channels, and a twelve-variable `env -u` blacklist as invocation hygiene. Cross-provider round 1 returned three Majors. One of them (finding 3) landed on the verdict-acquisition layer, whose threshold v1 had frozen at **one** round, so v1's own pre-commitment fired on the first round it ever had. The finding: `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>` are absent from the blacklist, so the ambient environment can inject an arbitrary `core.excludesFile` and flip the verdict on a repository whose own configuration says otherwise.

This v2 is the ruled disposition, and it is a **strategy change, not a longer list**. An omission class is not closed by extending the enumeration: the reviewer named six further unverified candidates, and the first person to look afterwards found a thirteenth channel nobody had named (`GIT_CONFIG_PARAMETERS`). Two independent instances plus six unresolved candidates in one round is the signal that enumeration was not converging. So the blacklist is replaced by an **allow-list** — `env -i` carrying exactly `PATH`, `HOME`, `TMPDIR` and `LC_ALL=C` — under which no ambient variable, named or unnamed, reaches git at all; and the mechanism is reduced to the **single** channel whose verdict survives review, deleting the classification layer, `V2` and the `rev-parse` channel with it.

## Goal

`bin/team-init.sh`, and no other surface, reports the resolved base dir's ignore status after scaffolding completes, reading **exactly one** channel — `git check-ignore -q -- "./<base>/"` — whose exit-status contract is stated in locally installed git documentation and whose value is a machine channel. ### The admissibility rule

**A channel may carry a load-bearing verdict only if both hold: (1) its contract is stated in locally installed git documentation, and (2) the value read is a machine channel — an exit status, a documented plumbing or porcelain format, or NUL-delimited output. A human-readable diagnostic never asserts anything; at most it justifies declining.** Every row of the decision table below cites the documented guarantee it rests on. A channel that fails either half is not "used carefully" — it is not used.

### The assertion rule

**The emitted text asserts nothing beyond (1) the exit status actually read and (2) a consequence that follows from git's own documented `gitignore(5)` semantics, stated only for the scope those semantics claim.** `gitignore(5)` scopes its rules to **untracked** paths — a tracked file is unaffected by any ignore rule — so a message predicting a commit-time consequence says so for records the loop *newly creates*, and says in the same breath that an already-tracked file under that directory is unaffected. This rule generalizes the admissibility rule from the channel to the sentence: a message that overclaims is the same defect as a channel that overreads, and cross-provider round 1's finding 1 is exactly that defect (v1's `V1` predicted "everything the loop writes … cannot be committed", which is false for a previously force-added tracked file, live-reproduced by the reviewer).

### The neutralization rule

**The probe's environment is an allow-list, never a blacklist.** Every git call the emitter makes runs under `env -i` carrying exactly four names: `PATH` and `HOME` and `TMPDIR` forwarded from the ambient environment, and `LC_ALL` pinned to `C`. Nothing else reaches git. The strategy changed from v1's `env -u` enumeration for a reason that is itself the ruling: **an omission class is not closed by extending the enumeration**. v1 froze twelve names; cross-provider round 1 named a thirteenth family it verified (`GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>`) and six more it did not verify; the first measurement run afterwards found a fourteenth (`GIT_CONFIG_PARAMETERS`) that nobody had named. Two verified instances and six open candidates in one round is a diverging list, not a converging one. An allow-list closes the class by construction: no `GIT_*` variable survives `env -i`, whether or not anyone has ever named it.

Three consequences are accepted deliberately rather than discovered later. (i) `PATH` and `HOME` are forwarded **on purpose** — `PATH` because the probe must find the same `git` the operator has, and `HOME` because a legitimate global `core.excludesFile` reached through `~/.gitconfig` is a real ignore source an adopter is entitled to be told about (measured: dropping `HOME` turns that case from "ignored" to "not ignored", silently losing the source). An operator's own `HOME` and `PATH` are their configuration, not an attack surface; a finding that "whoever controls `HOME` controls the verdict" is answered by this sentence rather than by a code change. (ii) An adopter who relies on an ambient `GIT_CONFIG_*`-injected `safe.directory` to work inside a repository they do not own loses that injection for this probe only, so git refuses, `check-ignore` exits 128, and the row that receives it is SILENCE. That is the conservative direction — never a false IGNORED — and it is consistent with the advisory ruling. (iii) Neutralization now happens at one site: every git call passes through a single probe helper, so the allow-list is one line to read and one line to review.

Three invocation constraints bind every git call the emitter makes, and are part of the frozen table rather than implementation latitude, because each is the direct remedy for a defect this mechanism has actually produced:

- **Normalized query.** The `check-ignore` pathspec is the base dir rendered with a `./` prefix and a single trailing slash, carrying no explicit pathspec-magic annotation of any kind. Its first character is therefore never `:`, and it is never a bare directory name.
- **Separated streams.** Every probe's stdout and stderr go to genuinely separate destinations. `2>&1` appears nowhere in the emitter.
- **Allow-listed environment.** Every probe runs under `env -i` carrying exactly `PATH`, `HOME`, `TMPDIR` and `LC_ALL=C`, per the neutralization rule above. No `env -u` and no enumerated `GIT_*` name appears anywhere in the emitter.

## Input space

**Reachable input classes** — what the emitter really receives, and what it must handle correctly:

- **A resolved base dir path** as `bin/team-paths.sh` emits it: a repo-relative subpath with no whitespace and no `.`/`..`/empty component, and — because `validate_base` permits them and D7 keeps permitting them — possibly beginning with `:`, `!` or `-`, or containing the glob metacharacters `*`, `?` and `[…]`. All six of those hostile-but-permitted shapes were measured against the shipped query form; five are answered correctly by the trailing-slash normalization alone and the sixth (leading `:`) by the `./` prefix.
- **A target directory that is** any of: an ordinary work tree; a subdirectory of a work tree rather than its root; a bare repository; a directory with no repository anywhere in its ancestry; a directory whose `.git` is an invalid gitfile; a directory whose `.git/` exists but lacks `HEAD`/objects; a repository git refuses to operate on. Under v2 the last five all reach `DT7` and are silent, which is the same outcome v1 produced for them through a different route.
- **Ignore rules arriving from all four sources** — the repo's `.gitignore`, `.git/info/exclude`, a `core.excludesFile` (repo-local, or global reached through `HOME`, including one that names the base dir itself), and a re-include negation — in both the bare form (`base`) and the directory form (`base/`), with the base dir present or absent on disk at query time.
- **An ambient environment carrying literally any variable**, named or unnamed in this spec — every `GIT_*` variable git documents, the two measured injection channels (`GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>` and `GIT_CONFIG_PARAMETERS`), the six candidates the cross-provider record named without verifying, any variable a future git version introduces, and any locale settings. This is a **deliberate widening** of v1's class, which enumerated twelve names plus locale; the allow-list is what makes the wider class tractable, and AC20 is its paired revert-detection lock. `PATH` and `HOME` are forwarded on purpose (neutralization rule (i)) and are the adopter's own configuration, not an input this spec defends against.
- **A closed stderr** (`2>&-`), which a fail-closed gate, a CI wrapper or a `2>&-` composition can supply to any script.
- **Any git version whose behaviour matches its own installed documentation.** The admissibility rule is anchored on documented contracts, so a version change that keeps its documented contracts is in scope and one that breaks them is not (see below).

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect, so a finding that escalates one of them is answerable rather than open-ended:

- **A hostile `PATH` that resolves `git` to a substituted binary, or a hostile `HOME` whose `.gitconfig` deliberately misreports.** Both are forwarded by design: the probe must find the operator's own git, and the operator's own global excludes are a real ignore source an adopter is entitled to hear about. A finding of the form "whoever controls `HOME` or `PATH` controls the verdict" is answered by neutralization rule (i) rather than by a code change, because narrowing either one would break a documented, measured behaviour (row E) to defend against the adopter's own configuration.
- **An environment in which an ambient `GIT_CONFIG_*`-injected `safe.directory` is what makes git willing to read the repository.** The allow-list drops it, git refuses, `check-ignore` exits 128 and the outcome is silence. That is the conservative direction and is stated as an accepted consequence in neutralization rule (ii), not a defect.
- **A real dubious-ownership state constructed with `chown`.** It cannot be built in this environment, and it lands on `DT7` with every other fatal cause by construction; the row is exercised through a bare repository and a stubbed `git`, which is the boundary this spec protects.
- **A git build whose observed behaviour contradicts its own installed documentation.** The whole design rests on documented contracts, and `LX09` is the fixture that turns red if that assumption ever breaks — which is the correct response to it, not a code path.
- **A symlink or a submodule gitlink placed exactly at the resolved base path**, and a base path that is a file rather than a directory. Declared a boundary here as well as a Non-goal, and recorded as an issue candidate: the fix is a ruling about what a base dir may be, not about which channel answers a question.
- **A TOCTOU race** — an ignore rule, an index entry or the base dir itself changing between the probe and the operator's next command. The mechanism is advisory, guards no security boundary, and a real fix needs index-level coordination disproportionate to the risk.
- **Base dir names that `validate_base` already rejects** — absolute paths, `~`-paths, anything containing whitespace (a newline included), and any `.`/`..`/empty component. They never reach the emitter.
- **Ever-larger repositories, ever-deeper ignore-rule sets, or ever-longer base dir names.** The mechanism is one git invocation; a demand to bound its cost or to fix a width is out of scope.
- **Every surface other than `bin/team-init.sh`** — `team-paths.sh`'s three modes, the skills, the agents, and any per-loop-step invocation. Named here as well as under `## Non-goals`, because the escalation this task is most exposed to is "here is one more place the same check belongs"; the answer is a fresh task with its own budget, not a widened diff.
