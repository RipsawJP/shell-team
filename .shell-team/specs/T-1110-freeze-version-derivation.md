# The freeze step re-derives the release version against the approved planning premise, and stops with a deviation notice when the premise has broken

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1110

## Problem

Version derivation in this loop fires only at GO-package assembly — after implementation and after the retro. During the r3-start sprint, a task's freeze declared `user-visible: yes` with a `mechanism` verification class, which broke the approved plan's premise (v2.3.1 PATCH, grounded on the sprint's only user-visible benefit staying behind an opt-in); nothing re-derived the version at that moment and nothing notified the operator, so the break surfaced only when the batch-GO package was being assembled and the sprint shipped as v2.4.0. The operator ruled this a **structural ordering defect** rather than an executor oversight: a derivation that fires at the end cannot catch a premise break when it happens, and the derivation belongs at the moment scope moves — the freeze step that declares `user-visible:` / `verification-class:`. The operator further withdrew the coordinating session's "not formally a violation" framing: **when an approved plan's premise breaks, the approval has lapsed** and work past that point is unapproved, which the standing scope-change stop-and-raise rule already covered — the failure was a missed application of an existing gate, not a gap in the rules. The loop today has no step at that moment, in `skills/run/SKILL.md` or anywhere else.
