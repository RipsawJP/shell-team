# CI parity: the adopter's own lint/format workflow steps are part of QA's verification surface

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1133

## Problem

A `run` on an adopter repository reached both gates green — QA `PASS` and a cross-provider `APPROVE` — and the pull request opened from that branch went red in CI on its first push, on the repository's own `ruff format --diff` over two test files the task had added. Nothing in the loop asks anyone to run that step: the scaffolded `<base>/test-recipe.md` carries only the unit-test command, and `agents/qa-verifier.md` has no rule that reaches the adopter's `.github/workflows`. The operator had to notice the red check, relay it back, and a formatting-only commit plus a second push followed. "Both gates green" therefore promises more coverage than it delivers, and the gap is invisible from inside the loop.

## Goal

<!-- BEGIN intent-block: T-1133 -->

When an adopter repository has `.github/workflows`, the lint/format/static steps those workflows run on pull requests are part of what QA verifies before it reports `PASS`, and the workflow files are the source of truth: QA reads them on every round, derives the lint/format/static steps they run on pull requests, runs those steps locally, and reports the derived list in its verdict; the recipe's `## CI parity` section is a record the engineer writes and refreshes under its existing append-back duty (QA never writes it), consulted as a starting point and reconciled against the current workflow files each round. Concretely: `agents/qa-verifier.md` gains one Rule making those steps a verification item whose non-zero exit fails the round, with an explicit statement — never a silent skip — for a step that cannot be run locally, and with behaviour unchanged for a repository that has no `.github/workflows`; `agents/engineer.md`'s existing recipe append-back duty names the new recipe section; `templates/test-recipe.md` gains a `## CI parity` section whose placeholders name the workflow file(s) read, the lint/format commands lifted from them, and the pinned versions; `bin/team-init.sh` prints one extra summary line pointing at that section when the scaffolded target has `.github/workflows`, and prints nothing extra when it does not; and `docs/adopting.md` and `docs/adopting.ja.md` each gain a section stating what "both gates green" does and does not cover with respect to the adopter's own CI.

- user-visible: yes — the QA gate's behaviour changes for every adopter whose repository has `.github/workflows`, reachable on shipped defaults with nothing to opt into, and the deliverable includes adopter-facing documentation (the scaffolded recipe section and a new section in both language versions of `docs/adopting.md`), which the `- adopter-surface:` line under **AC5** names. Recorded honestly as `yes` because the default-reachability test is met, **not** as a tier verdict: the release tier stays **PATCH** because the headline test fails — no adopter invokes anything new, an existing gate stops reporting a coverage it never had, which is bug-fix class (the operator's own planning derived PATCH on that ground; see `## Assumptions`).
- verification-class: mechanism — the diff reaches `bin/team-init.sh`, `tests/team-init/run.sh` and `templates/`, all of which the classification rule names as executing surfaces.
- verification-ceiling: unit-and-static — every criterion except **AC7** is a fixed-string read of a committed file, a committed-blob comparison, a checker's exit status, or the team-init fixture suite run in one bash process; none of those needs a real adopter environment. **AC7** is the single criterion marked `- above-ceiling:`, because this repository ships zero runtime dependencies (it cannot install a formatter to run in its own CI) and QA is an agent that a fixture cannot drive.
- base-ref-discriminator: not-applicable — this branch is cut directly from `develop` with no open predecessor pull request (T-1132's PR #469 is merged: `develop` at `bbba242` carries the merge commit `387136b`), so the two-arm existence test has no second arm to select. Every criterion that reads a base-side blob resolves it as `git merge-base develop HEAD`, this branch's own actual base ref, spelled identically in each such criterion.

## Non-goals

- **No new gate, flag, checker or status value.** The change lives inside the existing QA gate, the existing recipe file, and one existing summary block. No script gains a refusal condition, and the board grammar is untouched.
- **No reading of CI results from GitHub.** Nothing here queries an API, a check run, or a pull request's status; QA runs commands locally and reports what they returned.
- **No reproduction of a whole workflow.** Deploy steps, cloud-credential steps, container builds and anything else that needs an environment QA does not have are explicitly excluded from execution — QA states which step it could not run and why, which is the opposite of a silent skip.
- **No change to what a human must approve.** The merge GO, the freeze gate and every other human gate keep their present shape and count.
- **No formatter execution in this repository's own CI or fixtures.** `bin/` stays pure bash and zero-dependency, so no fixture installs or invokes `ruff`, `black`, `prettier` or any other formatter; the team-init fixture stops at workflow-directory detection, and the QA-side behaviour is verified by **AC7** above the declared ceiling.
- **QA never writes the recipe (T-073 boundary unchanged).** The recipe's `## CI parity` section is the engineer's record, written and refreshed under the append-back duty; QA reads it as a starting point, reconciles it against the current workflow files, and reports a missing or stale record in its verdict. `agents/qa-verifier.md`'s **Never destroy the working tree (T-073)** Rule keeps its single carve-out — QA's own hand-off append to the board — and gains no second one here, in that Rule's text or anywhere else.
- **No retroactive update of an already-scaffolded adopter recipe.** `templates/test-recipe.md` is copied through `copy_template_protected`, so a repository scaffolded before this task keeps its existing recipe file; its engineer/QA add the section through the existing append-back duty. The QA Rule applies to that repository regardless, because the Rule reads workflows and not the recipe.
- **No host-root write.** The new summary line changes no file at the target's root, exactly as every existing line in that block does not.
- **No scope-lock or diff-scope-closure criterion, and no per-task full-population blast-radius sweep.** Under the operator-approved lightweight mode A2 the sprint runs one two-arm sweep at release; `## Blast radius` carries predictions until then.
- No CHANGELOG entry, no version bump and no release step in this task.

## Pre-commitment

- **Droppable-first**: the `bin/team-init.sh` summary line together with its two-arm fixture (**AC4**, and the `bin/team-init.sh` half of **AC6**). It is the droppable one because the value of this task is carried by the QA Rule and the recipe section: a scaffolded repository whose summary printed nothing extra still gets the recipe section and still gets a QA gate that reads its workflows. If dropped, the rounds' findings travel with it as the requirement list of a fast-follow issue, and this spec's Non-goals absorb the drop rather than the criterion being weakened in place.
- **Never-dropped**: the qa-verifier Rule (**AC1**) and the `## CI parity` section (**AC3**). Defeat of either across two consecutive rounds stops the task and returns it to planning, because those two are the deliverable.
- **Trigger (same-class-2)**: two consecutive review rounds producing independent new defects in the same component. Factual condition — the same component drew a new, independent finding in each of two consecutive rounds; contextual condition — before a third repair round on that component starts. When the two disagree, the factual condition rules. On a trigger against the droppable component, execute the drop; on a trigger against a never-dropped component, stop.

## Input space

**Reachable input classes** — what a real scaffold target and a real adopter repository produce, all of which the implementation must handle correctly:

1. A target with no `.github/` directory at all: no extra summary line, scaffold otherwise byte-identical to today, and the QA Rule's condition is false so QA behaves exactly as it does today.
2. A target with `.github/` but no `workflows/` subdirectory: same as class 1 — the trigger is the `workflows` directory, not `.github`.
3. A target with `.github/workflows/` containing one or more workflow files, in any mix of `.yml` and `.yaml`: the summary line is printed **once**, independent of how many files are there.
4. A target with an empty `.github/workflows/` directory. Ruled on rather than left implicit: the directory's existence is the trigger, so the line prints. The line is a pointer at a recipe section, so printing it for a repository that has a workflows directory and no workflows in it costs a sentence and never misleads.
5. Either supported layout — the `.shell-team/` default and the legacy `tasks/` one — and a `$TEAM_RUN_BASE` override: the new line interpolates the resolved base exactly as the existing summary lines do, and the trigger is unaffected by which layout resolved.
6. A repeated `team-init` run on an already-scaffolded target: the line prints again, nothing is written twice, and the protected recipe is still never overwritten (an adopter's filled-in `## CI parity` section survives).
7. An adopter repository whose workflows contain steps that cannot run locally (a deploy, a cloud-credentialled test, a container build): QA names the step and why it could not run; the verdict is not silently narrowed.
8. An adopter repository whose workflows pin no tool version: QA records that no version is pinned rather than inventing one or skipping the step.
9. An adopter repository scaffolded before this task, whose recipe has no `## CI parity` section at all: the QA Rule still applies unchanged — QA derives the steps from the workflow files and runs them, because the workflow files are the source of truth and the recipe is only a starting point. QA does not create the section; it reports in its verdict that no record exists (naming the derived list), and the section arrives through the engineer's existing append-back duty.
10. An adopter repository with more than one workflow file whose lint steps differ: the recipe section and the QA Rule both read for N ≥ 2, which is why the plural-safe wording is asserted negatively in **AC3**.
11. An adopter repository whose `## CI parity` section is present but **stale** relative to its workflows — a lint/format/static step added to a workflow after the section was first filled in, which is ordinary repository maintenance rather than a synthetic extreme: QA runs the set it derived from the current workflow files, so the newly added step is verified on that round; the divergence between the recorded list and the derived one is reported in the verdict for the engineer to refresh under the append-back duty, and QA does not edit the record itself.

**Out-of-scope synthetic extremes** — named concretely, and declined:

- Malformed, adversarial or deliberately ambiguous workflow YAML. Nothing in this task parses YAML: `bin/team-init.sh` performs a directory-existence test, and QA reads workflows as an agent. There is no parser here for such input to defeat.
- Workflow paths engineered against a file walk: a symlinked `.github/workflows`, thousands of workflow files, file names containing newlines or control characters. No per-file enumeration is added, so these reach no new code path.
- Steps requiring network access, cloud credentials, a deploy target or a service container. Explicitly declined for execution; class 7 above is the handling.
- A lint step reachable only through indirection — a `make` target, a composite action, a reusable workflow hosted in another repository. Out of scope for mechanical lifting: QA records what it could not lift rather than guessing at it, and no criterion here claims such a step is detected.
- Executing a formatter (`ruff`, `black`, `prettier`, or any other) inside this repository's own CI or fixtures. Declined on the zero-dependency constraint; **AC7** carries the consequence above the ceiling instead of a fixture pretending to cover it.
- Near-miss spellings of the recipe heading (`## CI Parity`, `##CI parity`) in an adopter's own filled-in recipe. No mechanical vocabulary check over an adopter's recipe exists today and this task adds none; that would be the new gate class the Non-goals exclude.
