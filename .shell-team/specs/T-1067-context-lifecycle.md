## Problem

The operator's hypothesis (issue #249) is that running several issues as one continuous sprint accumulates context, and that this accumulation may be driving both token spend and sub-agent completion times up — with a per-issue reset as the obvious lever, and the stacked-PR train as the obvious reason not to pull it. Nobody can currently answer that, because the three things that actually accumulate are different things in different places: the orchestrator session's own context, a resumed sub-agent's transcript across rework rounds, and the launch brief the orchestrator writes into each new agent. They have different costs, different growth behaviour and different resets, and a discussion that does not separate them cannot reach a decision. T-1066 built the work-volume and latency baseline from the loop's telemetry; what is missing is the causal question that baseline was built to serve — is accumulation a driver, and what, if anything, is worth resetting at which boundary.

### Verdict scope (operator-ratified)

**Authorship: operator-ratified.** The primary record is the `- intervention: human-correction` entry dated 2026-08-14 in `.shell-team/interventions/T-1066.md`. This section restates that ruling for the gates that read this spec; it is not this spec's self-discipline and it is not re-litigated here.

For this deliverable — an internal investigation note whose purpose is to inform a decision about resetting context — **deliverable correctness means two things**, and a finding against either is verdict-gating: (1) the **computed values** are correct, meaning each figure names the source it was read from and reproduces when the command quoted beside it is re-run; and (2) the **conclusions' direction** is right, meaning what the note says its numbers support is what they support.

**Connective prose is not verdict-gating.** A finding about a sentence that joins, summarises or characterises values that are themselves correct — a totality word whose domain is wider than its command's, a label mismatch, a stale count in a narrative aside, an imprecise summary — is recorded as a **note** in the review record and does not on its own produce `REQUEST_CHANGES` or `FAIL`, provided every computed value it touches is correct and no conclusion's direction moves. **No escalation ratchet is created over prose classes**: repeated findings of a connective-prose class do not raise a gate's severity, do not create a halt condition, and do not on their own trigger a rework round; they accumulate as notes and are dispositioned at close-out.

This is a statement about what gates the verdict, not permission to be careless. A prose finding is still reported, and the engineer may still fix one — it simply does not stop the task.

**DP1 — the landing surface and the verification class are one decision.** The note lands in `docs/loop-engineering/`, beside the T-1066 trend note it consumes, where a new file reaches no executing surface — which is what lets the `no-mechanism` declaration above be true rather than merely asserted. **DP2 — the site labels are fixed first, and everything numeric carries one.** The three-label closed set is defined once in the note and every measured figure and comparison sentence carries exactly one label. A sentence relating two sites states the relation rather than leaving it to be inferred.

**DP3 — the attribution rule is stated with its exceptions enumerated, never left to an unexamined regex.** No transcript path component encodes a task id, a role or a round; the telemetry schema carries no task-id field. Whichever rule the note applies — session directory plus mtime, telemetry timestamp spans, distribution-only with no per-task attribution at all, or a per-round attribution explicitly declined — it is stated in the note together with every case it cannot resolve. A figure whose attribution rule cannot bucket its input is reported as unattributed, not silently dropped.

**DP4 — cross-sectional, not longitudinal.** Growth *curves* over a session's own history are very likely unobservable from what is recorded: a transcript file is read at whatever size it has now, not at the size it had three rounds ago. The honest substitute is a cross-sectional reading — a final size against a canonical round count, that count taken from the reviews corpus's own `^### Codex Review verdict` heading count rather than from telemetry. The note declares this design explicitly instead of presenting a snapshot as a trend, and any exhaustiveness word it uses names the domain its own command actually covered.

**DP5 — the second telemetry file is dispositioned explicitly, not silently ignored.** `.shell-team/runs/close-out.jsonl` exists, its `run_id` carries a task id directly, and every cost field on it is null. The note carries a one-line disposition — `used` with what it was used for, or `declined` with the measured reason — because a source that a previous analysis never opened is exactly the kind of thing a later reader assumes was considered.

**DP6 — the reset options are priced on three axes, and rehydration is one of them.** Each option is priced on orchestrator tokens, sub-agent wall-clock and rehydration cost. Rehydration is the axis a reset argument usually omits and the one that decides it: an orchestrator that resets per issue pays to re-read the substrate. Where an empirical proxy exists — a freshly launched sub-agent's own substrate-reading spend, which the telemetry already records — the note states whether it used it and why.

**DP7 — the consistency claim is tested, not assumed.** Issue #249 asserts that cross-PR consistency is carried by git-tracked files and machine gates rather than by retained context, and asks for that to be tested. The test's population, its command and its three-value verdict vocabulary (`supported` / `contradicted` / `undetermined`) are fixed before it is run, so the result cannot be reverse-fitted to the conclusion the note would prefer.

**DP8 — machine-local means aggregates only, and no identifier leaves the machine.** Transcript *content* is never read and never quoted; only sizes, counts and timestamps. No home-directory path, session UUID or agent id appears in the note, and any command it quotes resolves the transcript root through an environment-independent expression rather than a literal path. The note passes this repository's PII-shape check before its first commit rather than relying on the CI backstop.

**DP9 — self-measurement is excluded, and no criterion draws a live equality over a growing machine-local file.** This task's own telemetry rows and its own transcripts are excluded from the analysed corpus, with the exclusion and its positive control stated in the note. No acceptance criterion here compares a declared figure against a live re-derivation from a machine-local corpus that grows while the task runs: T-1066 shipped exactly one such clause and had to repair it pre-hash. Every criterion here is presence-and-structure shaped.

**DP10 — measure only what the recorded fields support.** Prompt-caching economics are reported to the extent the recorded fields reach and declined with a reason beyond it; no cache-hit rate is estimated and no vendor price model is used. Nothing is interpolated, and no inferential-statistics claim is made over this sample.

**DP11 — every red this task produces is disclosed and differenced, never repaired.** A criterion measured red at the base ref is never attributed to this pass; no merged criterion is repaired, re-based, widened or annotated, and no merged spec gains a `- stale-at:` sub-bullet from this task.
