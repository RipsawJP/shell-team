## Problem

T-1054 shipped a host-authored binding config and T-1055 shipped the adapter contract that says what an executor receives and returns. **Nothing consumes either.** Both loops still invoke each role the way v1 did, each role's model still comes from its own prompt's frontmatter pin, and the two rules the contract states normatively — an effort value the bound adapter does not declare fails closed, and board-transition authority is decided by the role and never by the adapter — are enforced by nothing at all: T-1055's pre-flight cross-check was carved out to a successor issue and what survived is byte-frozen prose.

Three gaps follow, and they are the kind that make everything built on top of them wrong rather than merely incomplete. First, a host can author a binding today and **no run behaves differently**, so the config is a document rather than a control. Second, "the executor is missing" has one shipped answer — `agents/codex-reviewer.md`'s "a missing CLI or failed auth is `BLOCKED`, never a substituted review" — and that answer is written for exactly one role; the other five have none, and #203's principle 2 (fail-closed, no substitution, no fallback chain) is therefore honoured in one place out of six. Third, a migration exists that nobody has written: an adopter who upgrades and has no binding config must keep running exactly as before, and the retirement of the frontmatter pins is the point at which "exactly as before" stops being automatic.

### Settled decisions

Every decision below is resolved. Where a decision departs from the most obvious reading of the routing map or the epic, its reason is stated at the decision, not deferred to review.

**DP1 — the name is `bin/resolve-executor.sh`, its answer is per role, and it is asked immediately before the role is invoked.** The `check-*` prefix in this repository names a script whose whole output is a verdict about an artifact; this script's output is a **resolution** a caller then consumes, which is `bin/team-paths.sh`'s shape and its precedent for the unprefixed name. The unit of the question is one role, not the whole binding, for a reason that is about failure timing rather than convenience: an availability answer is only true at the moment it is taken, so resolving all six at Step 0 would let a phase run five minutes later on a stale claim, and a role whose executor is missing would block phases that never invoke it. So Step 0 carries the **instruction** (the canonical block, which is where the choke point genuinely is) and each per-phase invocation point carries the **call**. Arguments are explicit and never inferred, copying `bin/check-durability.sh`'s `--ref` idiom: `--role <role>` is the production mode; `--print-resolved` is the probe-free mode DP7 exists for; `--help` prints the header. Combining the two modes, supplying neither, an unknown flag, a bare positional argument and a `--role` value outside the six bindable roles are each a refusal rather than a partial default.

**DP2 — one parser, two consumers, and the delegated output is re-asserted before it is trusted.** The resolver never reads the binding config's grammar. It runs `bin/check-binding.sh --config <path> --print-binding` and consumes the canonical `bound` rows, for the reason T-1041 settled for `check-intent.sh --print-hash` and T-1054 and T-1055 both reused: two implementations of one normalization drift, and the second one is always the one nobody tests. A config the sibling refuses is a refusal here too, with zero bytes on stdout — the resolver does not get a second opinion about a config the format's own validator rejected. **What is not inherited is the trust**: #225's requirement 1 records that the carved-out mode recognized the delegated `schema` line **by its first token alone**, so `schema`, `schema 999` and `schema 1 extra` were all accepted, and that defect is a property of the *consumer* rather than of the mode that was removed. This consumer therefore validates the field count and the version against its own supported set **before** accepting the line, requires exactly six `bound` rows one per inner-loop role with no other non-blank line, and reads every field of every row rather than the ones it happens to need. The same discipline applies to `bin/check-adapter.sh --print-contract`, whose `role-board-authority` rows DP4 consumes.

**DP3 — the effective binding is host config first, plugin default second, and the second one is the migration.** `<base>/binding.conf` (the base resolved through `bin/team-paths.sh`, never hardcoded) wins when it exists. When it does not, the resolver uses `templates/binding-default.conf`, resolved from its own installed directory with `cd DIR && pwd -P` — never the working directory, so an adopter's own `templates/` cannot substitute a binding, exactly as T-1054's AC6 decoy case pins for the adapter allowlist. This is what makes "no config" mean *v1-equivalent behaviour* rather than *no behaviour*: there is one code path, the same sibling validates both files, and a shipped default that is unreadable or invalid is a **refusal**, never a silent guess. The alternative — treating no-config as "skip resolution and run as v1" — was considered and rejected: it would leave the fail-closed availability guarantee unreachable for every adopter who has not authored a config, which is all of them, and the never-dropped item is the guarantee rather than the file.

**DP4 — the two normative rules are enforced where the role and the adapter are known together, which is exactly here.** T-1055's DP13 observed that the effort rule and the authority rule need the role and the adapter in one place, and that the mode which had both was carved out. Resolution is that place: the resolver holds the bound row (role, provider, model, effort, adapter) and can read both the adapter's own definition and the contract's authority rows. **The effort rule**: when the row's `effort` is not `-`, the bound adapter's definition must declare `capability effort supported` and must list that exact value among its `effort-value` rows; otherwise `capability-unsupported`, with nothing invoked and no default substituted. An `effort` of `-` resolves and means the provider or model default, which is the frozen sentence's own second half. **The authority rule**: the bound role's `role-board-authority` value comes from the delegated canonical contract, and when it is `writes` or `proposes` while the bound adapter declares `carries board-transition not-carried`, the pairing is `contract-violation`. Both tokens are drawn from `templates/task-envelope.txt`'s **existing** error-class vocabulary and **no new error class is minted** — the registry's own comment says those four exist because #203 names them as telemetry this task needs ready. The three tokens T-1055 carved out (`effort-unsupported`, `authority-channel-conflict`, `binding-invalid`) are **unspellable here**, in code and in comments, because that spec's AC7 measures their absence over `bin/*.sh` and `tests/*/run.sh`; where this task needs a name for "the effective binding would not resolve", it uses `binding-unresolved`.

**DP5 — the shipped default's model column is v1-equivalent by measurement, and the codex row carries `provider-configured` rather than this machine's Codex configuration.** For the five `claude-cli` roles the harness genuinely applies a model, and v1 applied the frontmatter pin, so each of those rows carries that role's own measured pin value — `tech-lead` and `pm-spec` on the planning tier, the other three on the execution tier, taken from the files rather than from this sentence. For `codex-reviewer` the measured invocation in `templates/adapters/codex-cli.txt` and `agents/codex-reviewer.md` carries **no model flag at all**, so v1 passed nothing and the executor ran whatever its own installation was configured for. Three candidate fills were considered and two rejected: a bare `-` is **refused by the shipped validator**, because `MODEL_RE` requires a leading alphanumeric and only `effort` has a "no value" spelling — measured, not assumed, and it forecloses inventing a sentinel without editing a validator this task may not touch; and transcribing the Codex model this development machine happens to be configured with would encode one host's configuration into every adopter's default, which is worse than a placeholder because it looks authoritative. So the row carries the ordinary token `provider-configured`, whose meaning the default file's own header states: the executor runs whatever its installation is configured for, and this adapter applies no model selection. That is exactly v1-equivalent, it needs no grammar change, and it is honest about the one column the contract has no mechanism for.

**DP6 — pin retirement is judged per role against what the pin actually governs, and its blocking premise is measured before either branch is taken.** For the five `claude-cli` roles the pin and the bound model govern the same thing, so they must not be able to disagree. **Which mechanism prevents disagreement depends on a harness capability this role cannot measure**, and both branches are pre-decided so the answer is not discovered mid-implementation. **Branch A** — the harness accepts a per-invocation model for a sub-agent: the five pins retire, the resolved row is the single source, and the canonical block says so. **Branch B** — it does not, and the frontmatter pin is the only thing that routes a sub-agent's model: the pins **stay**, and what ships instead is a two-directional equality lock between each pin and the shipped default's model token for that role, so the binding is the declared source of truth and neither side can move alone; pin retirement then travels to an issue naming the harness capability as its blocker. AC5 is satisfiable under either branch by construction and vacuous under neither, and the branch actually taken is recorded in provenance with the measurement behind it. **`codex-reviewer` is excluded from both branches, deliberately**: its `model: sonnet` configures the Claude **wrapper** that shells out to the Codex CLI, not the model that reviews, so retiring it would silently move the wrapper to the harness default while the bound row describes a different process entirely — the wrapper-versus-provider confusion that would break the cross-provider invariant in prose while leaving the code correct. That pin is asserted **unchanged against the base ref**, and the three advisory roles' pins likewise, since they are not bindable at all.

**DP7 — availability is probed from a compiled-in table keyed by provider, an absent entry is unavailable, and the in-process case is answered rather than skipped.** The probe cannot live in an adapter definition: `templates/task-envelope.txt` and `bin/check-adapter.sh` both forbid a command string, an argv list, an environment assignment or an executable path there, and every value is a bare token. So the table is compiled into the resolver, in the shape `bin/check-adapter.sh` already uses for its retired-channel set, and it is **exhaustive over the provider tokens the shipped allowlist declares** — a provider with no entry is `executor-unavailable` rather than assumed available, which is the fail-open hole this design's own future would otherwise open when a third adapter lands. For an **out-of-process** provider the executor is a separate process reached by a bare first token, availability is genuinely observable, and the probe is the read-only version query the contract document already records for this case; a missing binary or a failed auth is `executor-unavailable`, and substituting a same-family alternative is forbidden. For an **in-process** provider the executor *is* the harness running the caller, and this is where a tautology would be easy: probing a `claude` binary on `PATH` would measure a **different object** — a CLI installation, which can be absent while the harness runs perfectly and present while the harness cannot spawn a sub-agent — so a green result would assert something the observation does not support and a red one would break every adopter for a reason unrelated to the executor. The resolver therefore makes no claim it cannot ground: it prints `probe in-process` and the canonical block places the duty where the observation actually exists — the caller treats the harness's own sub-agent invocation failure as `executor-unavailable`, stops the phase and escalates, exactly as `agents/codex-reviewer.md` already does for its own CLI. This is a stated boundary rather than a silent skip, and it is why AC9 measures the table's exhaustiveness and the block's in-process duty rather than a probe that would be theatre.

**DP7a — a probe-free mode exists because CI has no executors, and it is not a fail-open seam.** The runner carries neither CLI, so no CI step may exercise the probing path; and "does this repository's effective binding resolve and satisfy both normative rules" is a question an operator wants answered anyway. `--print-resolved` answers exactly that, over all six roles, and **makes no availability claim at all** — it never probes, never prints a probe verdict, and is named in no loop instruction. The seam is closed by two mechanical facts rather than by intent: the canonical block spells `--role` and the two skills spell `--print-resolved` nowhere, and the production mode's availability step has no flag that disables it.

**DP8 — issue #221's production-caller half, whose form T-1055's AC12 already decided.** That criterion measures the registry-override flag as appearing in exactly one file across `bin/*.sh`, `skills/*/SKILL.md` and `agents/*.md`. Two consequences follow rather than being chosen: the new production caller may not spell that flag's name **anywhere in itself, comments included** — the discipline `bin/check-adapter.sh`'s own header already records — and the lock's body can only live under `tests/`, since AC12's pathspec does not reach there. So the resolver delegates without any override flag, and the suite asserts over the resolver's own source that no override flag of any of the four measured names is forwarded to either sibling, with the assertion paired to a positive control that the delegating command line is found at all.

**DP9 — the resolver writes nothing, which is a stronger claim than T-1056's and is made deliberately.** T-1056's classifier had one explicit write target and closed the surface around it (DP9a). This resolver has **none**: it has no output-file flag to add one, so the whole class — an environment-gated write, a debug dump, a cache, a lock file, a write to an observed input — is closed by construction rather than by enumeration. Stated as a contract because it is exactly the property a test seam is most tempting to breach: a resolver that could write to the binding it reads could fabricate a resolution from an invalid config. Where a fixture needs a mutated input, it builds one in a scratch copy of the installed tree and runs the copied script, which additionally exercises the real `$SCRIPT_DIR`-relative resolution rather than a test-only path — the technique T-1055's DP15 adopted for the same reason.

**DP10 — `templates/binding-template.conf` is left byte-untouched, and the scaffold installs the specimen inert.** The routing map anticipated replacing that file's `model-1`/`model-2` placeholders with real values. It is not done, for a measured reason: the specimen is the **host-facing example**, T-1054's AC2 and T-1055's AC11 both re-derive its six `bind` rows, and the v1-equivalent values now have their own home in `templates/binding-default.conf`, so editing the specimen would put the same facts in two places and move a file two merged criteria read for no gain. `bin/team-init.sh` copies that specimen into an adopting repository under a name the resolver's default lookup does **not** resolve, so an adopter who runs `team-init` gets the documentation without getting an executor assignment they did not choose — and the no-config-means-plugin-default path stays the path every adopter is on until they rename it deliberately.

**DP11 — #218's class boundary: convert every measured site, lock the two that matter behaviourally, and make the not-apply half of the table falsifiable.** The class is "resolves its own directory and crosses `$SCRIPT_DIR/..` to reach shipped data in `templates/`, with a logical `pwd`", and it has five members, enumerated with their sites in `## The logical-pwd class table`. All five are converted, because leaving a known-defective site in the script that **copies shipped templates into an adopter's tree** would be strictly worse than the issue that reported the class. Behavioural ancestor-symlink fixtures are required for two of them — `bin/check-durability.sh`, the issue's own subject, and `bin/team-init.sh`, the highest-impact member — modelled on `tests/check-binding/run.sh`'s reproduced case, each with a revert observation that the fixture reds under the pre-fix code. The other three are covered by a **static class lock** whose not-apply half is re-derived live and compared with the table's own declared residue in both directions, so a member that was silently missed fails the criterion instead of hiding in a count. Three files are named out of the class with their reasons in the same table.

**DP12 — the editorial batch is done here, and it is confined to one token.** Nine stale `T-1056` forward references sit in two shipped files this task already reasons about. Correcting them is cheap, and deferring them means every future reader of the contract document is pointed at the wrong task; the corpus's own guidance is to batch such corrections into one editorial pass rather than spend a ratification cycle per sentence, and this is that pass. It is confined to the task-id token and its one backticked cross-reference, and **the merged specs are not touched at all** — their occurrences sit inside frozen intent blocks. The document's own invariants are re-asserted independently by AC14 rather than trusted: exactly two `- normative: ` lines with their sentences byte-exact, zero occurrences of `--binding`, and the canon region still byte-identical to `--print-contract`'s output.

**DP13 — the threat model is accidents, identical to T-1054's, T-1055's and `bin/check-durability.sh`'s, for the identical reason.** A vendored install resolving to the wrong tree, a host binding an effort value the executor cannot honour, an adopter upgrading with no config, a stale forward reference. A hostile operator editing a shipped definition inside the plugin's own installation is out of scope, because `CLAUDE.md`'s security invariant makes the operator and the working directory trusted.

## Input space

**Reachable input classes** — what this task's deliverables really read and must handle correctly:

- **A binding config a host authored**, valid under `bin/check-binding.sh`: six `bind` rows in any order, with comments, blank lines, extra intra-row whitespace or CRLF line endings, `effort` either a declared value or the literal `-`, and any legal permutation of the two shipped adapters across the six roles — including `codex-reviewer` bound to `claude`/`claude-cli`, which T-1055's Non-goals keep legal.
- **No binding config at all** — the state every existing adopter upgrades in, and the one this repository itself runs in. The plugin-shipped default is what resolves, and that path is the migration.
- **A binding config the sibling validator refuses**, in each of the twenty ways its closed refusal matrix names: a missing file, a schema defect, a malformed row, a bad token, an unknown or duplicated role, a missing role, an unknown provider or adapter, a provider/adapter mismatch, or a registry defect. Each reaches this resolver as a refusal with zero bytes consumed.
- **A canonical form from the sibling that is well-formed, and one that is wrong in exactly one way** — the class #225's requirement 1 measured: a `schema` line with no version, an unsupported version, an extra field, or no schema line at all; five rows, seven rows, a duplicated role, a wrong field count, or one extra non-blank line.
- **An effort value the bound adapter does not declare**, and an adapter definition declaring `capability effort unsupported`, against any role. Both are reachable the moment a host edits either half, which is exactly what a host is invited to do.
- **A `writes`/`proposes` role bound to an adapter declaring `carries board-transition not-carried`** — reachable as soon as a third adapter or a definition edit exists, and the contradiction the frozen authority rule names.
- **All three layouts the resolver supports**: the default `.shell-team` base, the legacy `tasks` base, and an explicit `TEAM_RUN_BASE` override, with the config path derived in each and never assumed.
- **The plugin-shipped default, contract registry and adapter definitions as installed**, plus a decoy `templates/` in the working directory — reachable whenever the loop runs in a repository that carries its own `templates/` directory, which many do.
- **An installed tree reached through an ancestor directory symlink** — an adopter's `bin/` symlinked into the plugin's real `bin/`, ordinary vendoring with no hostile action, which T-1054's review reproduced against a sibling checker and which is #218's whole subject.
- **A host with one executor present and the other absent**, a host with neither, and a host where the out-of-process CLI exists but its authentication fails. Each is reachable on a real developer machine and on a CI runner, and each has one defined fail-closed outcome.
- **A role invoked in a session whose harness cannot spawn a sub-agent at all** — the in-process failure the caller, not the resolver, observes.
- **An adopting repository scaffolded by `bin/team-init.sh` twice**, and one where the scaffold target already exists as a file, a directory or a dangling symlink.

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect against:

- **A hostile operator.** Editing a shipped adapter definition or the default binding inside the plugin's own installation, planting a sibling script inside the installed `bin/`, or overriding a shell builtin to defeat the resolver. `CLAUDE.md`'s security invariant makes the operator and the working directory trusted, and T-1054, T-1055 and `bin/check-durability.sh` all scope their threat models identically; a finding whose only trigger is deliberate forgery inside the installation is `out-of-input-space`.
- **A dishonest or adversarial executor.** An executor that reports a version and then behaves as a different model, one that lies about its effort support, or one that returns a well-formed envelope describing work it did not do. The resolver decides *whether to invoke*; verifying what came back is the loop's existing gate structure and, for the contract's own fields, a later task's.
- **Whether the model token names a model that exists.** The resolver passes the model through opaquely and no shipped adapter declares a model-application mechanism; a finding that a typo in the model column is not caught is `out-of-input-space`, and `provider-configured` is the deliberate instance of that boundary (DP5).
- **Environment-variable neutralization, `GIT_*` enumeration, `GIT_DIR` redirection, replace refs, clean filters or LFS.** Named explicitly because sibling checkers name them, and for the same reason: they belong to a separate hardening issue.
- **Ever-larger or ever-longer synthetic input**: a config with thousands of comment lines, a canonical form with thousands of rows, a token longer than the sibling's own length cap, a `templates/adapters/` directory with hundreds of definitions. The sibling's declared width and length bounds are the boundary and a finding that only fires past them is `out-of-input-space`.
- **Non-ASCII or homoglyph role, provider, model, effort or adapter tokens.** Every vocabulary is closed and ASCII by construction; a homoglyph simply is not the token and is refused as unknown by the validator that owns that grammar.
- **A NUL byte or invalid UTF-8 inside a config, registry, definition or prompt block.** Authoring one independently breaks the file for every text tool in this repository.
- **Filenames containing a newline, a tab, or a byte `core.quotePath` would C-style-quote**, in any path this task reads or any path a criterion enumerates. This corpus commits none, exactly as the merged specs this one follows accepted.
- **A hostile `$TMPDIR`**: an attacker-controlled temp directory, a symlink race against `mktemp -d`, or a permission flip between creation and first write.
- **Concurrency between two resolutions of the same role.** The resolver writes nothing, so there is no shared mutable state to race over; a finding that two simultaneous invocations could disagree because the executor's availability changed between them is a statement about the world rather than about this deliverable, and is `out-of-input-space`.
- **A per-tick run-loop state file, a run-scoped binding lock, or telemetry rows carrying the resolved binding.** All three are explicitly declined (Non-goals), and a finding that the resolution is not recorded anywhere is `out-of-input-space` for this cut.
