```markdown
## 2026-08-05 — A temp-file registry appended inside a command substitution never reaches the parent shell, and its EXIT-trap cleanup then deletes nothing
- **Category**: tooling-ci
- **Applies-to**: engineer, qa-verifier
- **Scope**: loop
- **Status**: active
- **Source**: .shell-team/retros/2026-08-05.md
- **Rule**: A shell function reached through a command substitution runs in a subshell, so anything it appends to a cleanup registry — a temp-path array an `EXIT` trap later reads — is discarded when that subshell exits; keep the registry and the responsibility for removing a temp file in the caller's own shell scope, or do not create the temp file inside a function called that way, because the trap still fires, still finds an empty registry, and still exits zero while deleting nothing.
- **Why**: A newly shipped checker created two temp files on every ordinary invocation, inside a helper that each of its call sites reached through a command substitution. The append ran in the subshell and never reached the parent, so the `EXIT` trap read an empty registry on every run and removed nothing; by the time a cross-provider review measured the temp directory, the accumulation was past thirteen hundred files. Nothing visible failed on the way there — the fixtures passed and the exit codes were right — because a cleanup that deletes nothing behaves exactly like a cleanup that had nothing to delete.
- **How to apply**: When a script creates temp files, keep the tracking variable and the `trap ... EXIT` that reads it in one scope, and check every helper's call sites for the command-substitution shape before trusting a registry-plus-trap design. QA verifies cleanup by counting the files in the temp directory before and after a real run rather than by reading the trap, since a no-op trap reads correctly.
```

```markdown
## 2026-08-05 — A background agent is monitored by an active liveness check started at launch, because a completion notification cannot report a stall
- **Category**: process
- **Applies-to**: all
- **Scope**: loop
- **Status**: active
- **Source**: .shell-team/retros/2026-08-05.md
- **Rule**: Whoever launches an agent to run in the background starts an active liveness check at the same moment — something that samples, on its own schedule, whether the agent is still making progress and raises an alarm when it stops — because waiting for a completion notification cannot detect a stall even in principle: an agent that has stopped mid-run emits nothing, and that silence is indistinguishable from a healthy long run. Which mechanism supplies the signal is the operator's choice; what is required is that one exists, that it starts with the agent, and that a stall verdict is measured from its signals rather than inferred from elapsed time.
- **Why**: A background role stalled mid-task while the launching side treated its own completion notification as the monitoring mechanism; nothing observed the gap until a human noticed the run had overrun by a wide margin and corrected the operating rule. The failure is structural rather than incidental: a notification channel reports only the transition it is built to report, so a run that never reaches that transition is exactly the case the channel is silent about — and the same silence is also the healthy case, which is why waiting longer never resolves it.
- **How to apply**: Pair every background launch with a liveness check that starts at launch, and treat "no notification yet" as no information about the agent's state. On an alarm, verify against the signals the check samples before intervening, and prefer prompting a stalled agent over terminating it while any signal still shows progress; a role that cannot run such a check says so at launch rather than substituting patience for monitoring.
```

Traps in the criteria themselves, so you do not find them the expensive way:

- **Every frozen text is read out of this spec by AC1–AC6, AC8, AC10 and AC12.** If you retype one instead of copying it, a single smart quote or a collapsed double space fails the criterion, and the failure will look like a corpus problem rather than a transcription problem. Extract the fenced blocks with `awk`/`sed` into scratch files and splice those bytes programmatically, as T-1027's engineer pass did.
- **Every frozen field value carries characters that shell quoting mangles**: backticked fragments (`EXIT`, `trap ... EXIT`, `git show <ref>:<path>`), angle-bracket placeholders, straight double quotes, apostrophes and em-dashes. Extract each field's bytes into a scratch file and pass them as `--rule "$(cat "$T/rule")"` and so on; a variable's *contents* are never re-expanded, whereas anything you retype into the command line is at the mercy of whatever quoting you chose.
- **`bin/playbook-promote.sh --title` takes the heading text only.** The script writes `## <date> — <title>` itself, so the value is everything *after* the em-dash separator in the frozen heading — do not include the date and do not include the em-dash, or the entry key will not match the frozen block and AC1–AC3 and AC8 all fail together on what looks like a byte mismatch.
- **AC4 compares three places at once.** If only two of them move you get a red that names none of them; check the corpus line, T-1027's spec line and this spec's `W` block against each other by hand before you trust a green.
- **AC11's teeth are in the deletion column, not the addition count.** Any reflow, any "improvement" to an existing bullet, any regeneration that reorders a block turns a 0 into a positive number and fails. The generator appends at end of block; if a bullet moves, something else changed.
- **AC6 runs `bin/check-refreeze-class.sh` and expects exit status exactly 1.** A `0` means the delta was confined to `- check:` lines (it is not), and a `2` means the classifier could not evaluate the pair — most likely because the scratch copy of the base blob was empty or the marker pair did not survive the `git show`. Check the scratch file is non-empty before blaming the classifier.
- **`grep -c` under `set -euo pipefail`** aborts a script when the count is genuinely `0`; append `|| true` to the pipeline, never to the assignment, and keep the explicit assertion right after. Relevant if you write scratch verification around the mutation self-check.
- **The 40-line block-size warning will now fire for a third role.** It is not a failure and it is not a reason to shorten an entry or narrow an `Applies-to` list.

Pre-commitments, set before the first round and binding on every role on this branch:

Arguments to add candidates 1 or 4 to the corpus are **out of contract** outright, not merely re-routed.

Contextual trigger: a third round is about to start. **The factual trigger governs when the two disagree**, because rounds can be relabelled and independent defect classes cannot. On trigger, stop and propose the split: ship the three-entry promotion alone — commits 1, 2 and 4 of the separation above, the cheapest possible shape — and spin issue #136 into its own task, reverting T-1027's spec and ledger to v1. Two consecutive rounds is this repository's standing threshold and nothing here loosens it.

Task classification, stated so review rigour is calibrated rather than guessed: **this is not verification-mechanism work — no checker, parser or state tracker is written or extended, and `bin/` and `tests/` are byte-identical** — but it is not a plain pure-addition either.
