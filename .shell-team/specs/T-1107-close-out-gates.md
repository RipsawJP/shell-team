# `bin/close-out.sh` refuses to promote an entry that is not already at `READY_FOR_MERGE`, and discloses the issue-close procedure it would otherwise skip when `--issue` is omitted

**Status**: READY_FOR_ARCH
**Owner**: pm-spec

## tamper-arm-rule-v1 adjudication

`docs/loop-engineering/record-tamper-resistance.md` is read first-hand end to end (215 lines, through the fifth-promotion section T-1104 appended). `tamper-arm-rule-v1` is a two-question decision procedure over an **obligation**, asked in order, whose conjuncts are prescriptive tests on the obligation's own consequence and content and never observations of which scripts happen to exist today. Applied to the two obligations this task creates:

- **Obligation A — a close-out's target entry is already at `READY_FOR_MERGE` before its flag is rewritten.** Conjunct 1: its verdict gates a **close-out**, which is one of the three loop transitions the note's own parenthetical names outright (`## The rule as a decision procedure`, question 1). Conjunct 2: the judgment is a single string comparison against one token extracted from one board line by the rightmost-slot rule the file already implements at `bin/close-out.sh:463` — mechanically executable from committed bytes. Both hold → **arm-A-tested-primitive**, and its structural form is **already fully satisfied by an existing arm-A script**: `bin/close-out.sh` is a named script under `bin/` with its own `tests/close-out/run.sh` suite (measured: `.github/workflows/check-handoff.yml:134-135` runs it as its own step). Nothing is built and nothing is newly wired.
- **Obligation B — the operator learns that the issue-close procedure was skipped.** Conjunct 1 **fails**: the note has no verdict at all. It gates nothing, refuses nothing, and changes no exit status; it prints one line after the board write has already succeeded. Conjunct 2 would hold (the condition is `[ -z "$ISSUE" ]`), but question 1 requires **both**. So the obligation takes **arm-B-enumerated-instrument**: its correctness is settled by this spec's own enumerated `- check:` lines and by `tests/close-out/run.sh`'s fixtures, and adversarial guard-completeness of those lines is not a Major. That the *behaviour* is nonetheless covered by an arm-A script's own suite is exactly the shape the note's `## What decides the arm, and what never does` section describes.

**Whether obligation A is a sixth promotion is a genuine judgement, and this spec settles it rather than leaving it implicit.** Two readings exist. (i) *A new obligation*, on the T-1099 precedent — a new judgment landing inside an existing arm-A script still counted as the third promotion, because the trigger "counts obligations, not scripts". (ii) *A narrowing of an obligation already in arm A* — T-1022 already promoted the source-line judgment ("the Active line's status flag must be in the allowed vocabulary", `bin/close-out.sh:54`), and this task changes that judgment's **predicate width** on the identical subject (the same Active line), at the identical venue (immediately after that gate, `bin/close-out.sh:642`), over the identical datum (the rightmost backticked slot), from *member of `ALLOWED_FLAGS`* to *equal to `READY_FOR_MERGE`*. This spec takes reading **(ii)**, because every element the note uses to individuate an obligation — the transition gated, the bytes judged, the venue executing it — is shared with an obligation already in arm A, which is what makes it a widening of an existing promotion rather than a new one; T-1099 by contrast introduced a judgment (duplicate structural headings) that no promoted obligation had any part of. Consequently `docs/loop-engineering/record-tamper-resistance.md` is **not edited by this task**, the promotion counter does not advance, and **AC12** keeps `docs/loop-engineering/` out of the changed-and-added set.

**The classification is disclosed as testable rather than asserted.** If the elected spec review or `codex-reviewer` reaches reading (i), the correction is a one-section prose append to that note recording a sixth promotion — no mechanism changes either way, because arm A's structural form is already in place under both readings, and the re-evaluation trigger already fired on the third promotion and stays owed at a retro regardless (the note's own text records that the fourth and fifth promotions explicitly did not re-fire it). The arm-B pricing that governs this spec's own inline check lines is **not** the operator's 2026-08-22 dev-scaffold re-pricing: that carve-out's own text preserves full strength for shared `bin/` checkers, which is what this task's deliverable is. ## Problem

`bin/close-out.sh` rewrites the target task's status flag to `READY_FOR_MERGE` (`:463-468`) without ever reading the flag it is replacing. Measured today, `READY_FOR_MERGE` occurs in that file at exactly four places — `:9` and `:459` (prose), `:464` (the write target) and `:614` (a comment) — and at none of them is it compared against anything. T-1022's source-line gate (`:610-642`) does refuse a flag **outside** the vocabulary, by synthesizing a single-entry board and running `bin/check-handoff.sh` against it, but that checker's `ALLOWED_FLAGS` (`bin/check-handoff.sh:32-40`) accepts all seven flags, so a task sitting at `READY_FOR_QA`, `REWORK`, `BLOCKED`, `READY_FOR_ARCH`, `READY_FOR_ENG` or `READY_FOR_REVIEW` is silently promoted into `## Done` at `READY_FOR_MERGE`. Issue **#53** filed this as unverified; it is confirmed for that second subset and it is not hypothetical — `.shell-team/todo.md:1633` (**T-1089**) and `:1743` (**T-1086**) both sit in `## Active` at `BLOCKED` right now, and `close-out.sh --task T-1089` would today move a blocked task to done with no refusal. The legitimate pre-flip state is measured rather than assumed: `agents/codex-reviewer.md:131` (`APPROVE → set tasks/todo.md to READY_FOR_MERGE`) and `docs/adopting.md:753` (`A task is done only when the Codex reviewer sets READY_FOR_MERGE`) both make `READY_FOR_MERGE` the documented state a close-out starts from.

Separately, the script's whole knowledge about issue closing — the "develop merges do NOT auto-close" rationale, the `gh` form and the GitHub MCP form — sits inside `if [ -n "$ISSUE" ]; then` (`:691-697`). When `--issue` is omitted the block is skipped in silence: nothing tells the operator that a procedure exists and was not run. Issue **#266** records two occurrences of the resulting class (2026-07-28 and 2026-08-13, the operator correcting the same rediscovery both times). A **third** occurred on 2026-08-29 and is confirmed by primary observation rather than relayed: the coordinating session found issue **#366** still open after the v2.3.0 batch merge — T-1101's board line records `closes #366`, its PR merged to `develop`, and that task's close-out ran without `--issue`, so the batch GO's manual close list missed it — and closed it by hand with a bookkeeping comment. The mechanization exists; omitting one optional flag silences it.

**The honest cost of the first fix is stated here rather than discovered later.** A pre-flip gate narrows `close-out.sh`'s accept surface, so every fixture and every merged acceptance criterion that drives the script against a non-`READY_FOR_MERGE` board line changes verdict. Measured by shape at the branch point, **26** `- check:` lines across four merged specs are in that class (`## Blast radius` enumerates them by AC id), plus both close-out fixtures and the T-1022 differential harness's own corpus. Those merged criteria are **disclosed, never repaired** — repairing another task's frozen criterion is a class-B re-freeze of someone else's intent — and that cost is a first-class input to the pre-commitment's drop order below.
