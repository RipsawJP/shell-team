# One rule for how a behaviour-neutral change to committed records is described

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1142

## Problem

`CONTRIBUTING.md` states how a change gets merged and how a release is cut, and each changelog file declares its own entry style. None of the three states how to describe a change whose only content is maintenance of committed records — a change that alters no behaviour and touches only the records the loop writes. A description rule that is not written down is supplied by whoever writes the commit subject, the pull-request title and body, and the changelog entry, one description at a time; and the description a writer reaches for most naturally is a narration of the records' prior content, which is exactly the content such a change exists to stop carrying. The gap is a missing sentence in three published documents, not a missing mechanism.

- **Rewriting any existing changelog entry, or any existing line of the three edited files.** Every edit is an insertion; no released entry's wording is revisited, and no sentence already standing in the three self-description and section paragraphs is reworded.

- **Creating `CONTRIBUTING.ja.md`.** The file has no Japanese counterpart and gains none here; the rule's Japanese statement lives in the changelog file that does have one.

- **Running a full-population sweep, a whole CI-equivalent re-run, or any behaviour verification of a mechanism this task does not touch.** Priced out by the `no-mechanism` verification class declared above: the downstream analysis is read-set-scoped, CI-equivalence is scoped to the steps this diff's paths can reach, and no criterion below asserts the behaviour of a checker whose bytes this task leaves untouched, other than by that checker's own exit code.

- **Merging.** Both gates must be green and the pull request joins the stacked train awaiting the batch GO.

## Decision points, resolved

**DP-1 — the rule's single statement lives in `## How changes get merged`, not under a new heading.** The section already fixes what every change passes through, so a sentence about how a change is described belongs beside it rather than in a heading of its own that a reader has to find. `CONTRIBUTING.md` is read top to bottom by a contributor who has decided to open a pull request; a new top-level heading competes with the sections that describe the flow, while an addition inside the merge section is read by exactly the person about to write a commit subject. **AC1**'s byte-identical heading-list comparison is what holds this decision in place.

**DP-2 — `## Cutting a release` gets a pointer, not a copy.** The section already delegates changelog entry style to the changelog files themselves and already carries a cross-reference bullet pointing at another section rather than restating it. Two copies of one rule in one file is the shape that goes stale: the copy nobody edits is the copy the next reader finds. The release-level consequence — a release whose changes are all records maintenance takes a single housekeeping line — is stated there because that is where a release's entries are written, and it is the one clause that has no other home.

**DP-3 — the rule lands in each changelog's self-description paragraph, not in a release entry.** That paragraph is where each file declares its own entry style, which is precisely what the rule extends; a release entry would date the rule to one release and leave the declaration silent. The Japanese statement is authored in Japanese as that file's own text rather than translated from the English after the fact, matching how that paragraph was written in the first place.

**DP-4 — the EN/JA statements are audited clause by clause, and the audit lands on the board.** Two statements of one rule in two languages are the classic place a distinction is dropped silently, and a diff comparison cannot see it because the two texts are not comparable byte for byte. The audit is therefore an explicit per-clause table with the three-token vocabulary. It lands in the board's hand-off region rather than in the provenance file because the provenance schema admits no line other than its own triples — a table there is a schema violation, not a stylistic choice.

**DP-5 — every edit is an insertion.** The changelog files' existing paragraphs, and `CONTRIBUTING.md`'s existing bullets, are left byte-for-byte alone: the rule arrives as new lines. This is what makes **AC4**'s zero-deletion test meaningful, and it inherits the release procedure's own established caution that an edit anchored on an existing line can silently consume it.

**DP-6 — the negative criterion proxies a worked example by three citation shapes.** "Contains no example of a record's prior content" is not directly checkable — it is a judgement about meaning. What is checkable is that the added text cites no task id, no issue reference and no release version, since any illustration drawn from this repository's records would carry at least one of them. The proxy is stated as a proxy in **AC6**'s own body so that nobody later mistakes it for a complete test.
