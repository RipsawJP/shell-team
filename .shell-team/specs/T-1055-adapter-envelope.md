## Problem

T-1054 shipped a host-authored binding config: a host can now declare that `codex-reviewer` runs on the `codex` provider through the `codex-cli` adapter, and a fail-closed validator refuses anything it cannot fully evaluate. Nothing consumes that binding. `adapter` is a token from an allowlist and no document anywhere says what an adapter *is* — what it is handed, what it must give back, or what happens when a host assigns an `effort` value the executor has no way to honour.

Two gaps follow from that, and both are the kind that get expensive after something is built on top of them. First, the **contract** between the loop and an executor is currently implicit in one agent prompt (`agents/codex-reviewer.md`), where it exists as a specific recipe for one CLI rather than as a general statement; T-1056 (loop integration) and T-1057 (telemetry) would each re-derive it, differently. Second, `effort` is validated for *shape* and nothing else, so a host who writes `effort: high` against an executor with no effort knob gets silence — the exact "unknowingly running at a different tier" failure epic issue #203 names. This task closes both without invoking anything: it documents the contract, ships the two initial adapter definitions with their capabilities **measured rather than guessed**, and makes an unsupported effort value a refusal a host sees before a run rather than a surprise inside one.

### The task envelope (DP1)

The frozen field set, its directions and its requiredness. Direction is stated from the adapter's point of view: `in` is what an adapter receives, `out` is what it returns. A `conditional` field is always *declared*; its condition governs when a value is required, and the contract document states that condition for each one.

| Field | Direction | Requiredness | What it carries |
|---|---|---|---|
| `task-id` | in | required | the `T-NNN` this invocation serves |
| `role` | in | required | which of the six inner-loop roles is being run |
| `phase` | in | required | which loop phase this invocation serves |
| `request` | in | required | the work statement handed to the executor |
| `artifact-paths` | in | required | the operating paths the role reads and writes, as already resolved — never re-derived by the adapter |
| `working-dir` | in | required | the repository root the invocation runs in |
| `resolved-binding` | in | required | the bound row for this role: provider, model, effort, adapter |
| `status` | out | required | whether the invocation completed, from the contract's closed status vocabulary |
| `verdict` | out | conditional | the role's own outcome token, required when the role's phase produces one |
| `produced-artifacts` | out | required | the paths the invocation wrote — the envelope names them and never carries their content |
| `board-transition` | out | conditional | required when the role's board authority is `writes` or `proposes`; for a `proposes` role it is a **request** the orchestrator transcribes, never an act |
| `usage` | out | required | the resource accounting the executor reported; where the executor reports none, the adapter says so explicitly rather than omitting the field |
| `error-class` | out | conditional | required when `status` is not the success value, from the contract's closed error-class vocabulary |
| `adapter-version` | out | required | the version of the adapter definition that actually ran |

### Settled decisions

Every decision below is resolved. Where a decision departs from the most obvious reading of the epic, its reason is stated at the decision, not deferred to review.

**DP1 — the envelope is a contract, and this task ships no instance of one.** The field table above is normative; no file format for an envelope instance is defined, no code serializes or parses one, and `bin/check-adapter.sh` accepts no flag whose name begins `--envelope`. #203's own boundary sentence is what this implements: the substrate is files plus the board, and an envelope is the vocabulary in which a later component describes what it passed and what came back. The enforceable half is negative (AC9) because a contract with no instances has no positive behaviour to observe.

**DP2 — the contract is shipped twice, in two forms, for two readers, and the two are checked against each other.** `docs/loop-engineering/task-envelope.md` is the prose — meanings, conditions, the generalized invocation pattern, the measured effort mechanisms. `templates/task-envelope.txt` is the machine-readable half — the same field tokens, plus the closed vocabularies, in the line-oriented whitespace-delimited idiom `templates/binding-adapters.txt` and `templates/durability-records.txt` already use. Two documents of one contract is exactly the shape that drifts, so AC8 requires their field sets to be **equal in both directions**, each side re-derived at check time rather than compared against a literal.

**DP3 — the prose half lives in `docs/loop-engineering/` and ships English-only.** Its readers are maintainers, adapter authors and whoever implements T-1056 and T-1057 — not adopters, who are shipped nothing wired by this task. `docs/loop-engineering/` already holds exactly this class of internal-mechanism document and four of its five files carry no `*.ja.md` counterpart, which is the measured precedent. `README.md` and `docs/adopting.md` are declined for the same reason T-1054 declined all adopter-facing documentation: adopter documentation lands with the feature that is actually wired, in T-1056. The full candidate set and each decline's reason are in `## Surface decision table`.

**DP4 — the board-transition authority split is declared per role, in the registry, not only in prose.** One `role-board-authority <role> <writes|proposes|none>` row per inner-loop role, from a closed three-token vocabulary. `writes` means the role edits the board itself and the envelope's `board-transition` records what it wrote; `proposes` means the role returns the requested flag and the orchestrator transcribes it; `none` means the role requests no transition. This is the one part of #203's design point 5 that would otherwise exist only as body prose, which is precisely the shape that escapes a criterion-driven gate. The values are measured from each role's own shipped prompt (`## Summarized sources`), not assigned by this task.

**DP5 — an adapter definition is declarative and cannot spell a command.** Every value in a definition file is a bare token; no field is a command string, an argv list, an environment assignment or a path to an executable, and the checker refuses anything outside the declared token classes. #203 forbids the *config* from storing a raw shell command; extending the same property one level up to the adapter registry costs nothing and removes the obvious place the property would have leaked. How the envelope reaches the executor is declared as a `carries <field> <channel>` mapping onto the contract's closed channel vocabulary — a claim about which part of the existing substrate carries each field, not an instruction to execute. The concrete invocation shape stays prose in the contract document and code in T-1056, where it is reviewed as code.

**DP6 — one definition file per adapter, named for its own token, looked up rather than scanned.** `templates/adapters/<adapter-token>.txt`; a definition whose declared `adapter` token differs from its own basename is a refusal. This makes the lookup for a bound adapter deterministic (compose the path, do not search) and makes "the definition set" enumerable for the default whole-directory validation, without adding a row of any kind to `templates/binding-adapters.txt` — whose two-token grammar T-1054's validator enforces and which a third column would break.

**DP7 — the `effort` capability is measured against the real provider, and the shipped specimen is reconciled to whatever the measurement says.** For `codex-cli` the measurement is what the locally installed Codex CLI actually accepts; for `claude-cli` it is the harness's own effort semantics. Both branches are pre-decided so the conflict is not discovered mid-implementation: if the measured capability admits the value `high` on the `claude-cli` adapter, `templates/binding-template.conf` is untouched; if it does not, that file's `tech-lead` row has its **`effort` field and nothing else** changed to a value the measurement supports (`-` if none does), and the reason is recorded in provenance. Any other edit to that file is a scope violation. Either way the shipped specimen and the shipped definitions must agree, which AC6 asserts by running the cross-check against the real specimen.

**DP8 — no third adapter, and no edit to T-1054's validator.** The initial cut is the two allowlisted rows; #203 puts custom adapters out of scope, and `templates/binding-adapters.txt`'s own header defers a new row to this task, which declines it. T-1054's `templates/binding-adapters.txt`, `bin/check-binding.sh` and `tests/check-binding/run.sh` are pre-existing on this branch and not editable here (AC11, AC14). T-1054's AC2 carries a `- stale-at:` note anticipating that this task might add a registry row; it does not, so that criterion's declared sets still describe the shipped artifacts.

**DP9 — issue #221's split: this task ships the static invariant over today's tree, T-1056 owns the runtime lock.** The concern is a production path forwarding a testing affordance. This task creates no production caller of anything, so what it can honestly assert is that **no file under `bin/`, `skills/*/SKILL.md` or `agents/*.md` forwards a registry-override or definitions-override flag except the checker that defines it** — measured today (AC12) and true today. `bin/check-adapter.sh` therefore never spells the sibling validator's registry-override flag at all, in code or in comments, and delegates to it without one. The half this task cannot hold is the one that only exists once a production caller exists: T-1056 introduces the first, and re-asserting this invariant over its own new call sites is T-1056's, recorded here so it is inherited rather than rediscovered.

**DP10 — the cross-check delegates parsing and refuses rather than proceeding.** `--binding` runs `bin/check-binding.sh --config <path> --print-binding` and reads the canonical `bound` rows; it never parses the config's own grammar. A config that sibling refuses is `binding-invalid` at exit 2 with nothing written to stdout — the adapter layer does not get a second opinion about a config the format's own validator rejected. One parser, two consumers, for the reason T-1041 settled for `check-intent.sh --print-hash` and T-1054 reused: two implementations of one normalization drift.

**DP11 — resolution is physical from the first commit.** The contract registry and the definitions directory resolve from this script's own installed location using `cd DIR && pwd -P`, never a logical `pwd`, so an adapter's own `templates/` in the working directory — or an **ancestor** directory symlink from ordinary vendoring — cannot substitute either. This is not a hardening step discovered later: it is the defect a T-1054 review round reproduced against the sibling checker, and it ships correct here rather than being repaired after a round. `bin/check-durability.sh` carries the same defect and is issue #218's, deliberately untouched.

**DP12 — the threat model is accidents, identical to T-1054's and `bin/check-durability.sh`'s, for the identical reason.** A stray edit, a vendored install resolving to the wrong tree, a host binding an effort value the executor cannot honour. A hostile operator replacing a shipped definition inside the plugin's own installation is out of scope, because `CLAUDE.md`'s security invariant makes the operator and the working directory trusted.

- **All three layouts the resolver supports**: the default `.shell-team` base, the legacy `tasks` base, and an explicit `TEAM_RUN_BASE` override.
- **Absent inputs**: no definition file for a bound adapter, an unreadable contract registry, an empty definitions directory. Each is reachable and each fails closed.
- **The current working directory being a git repository**, which is the loop's own precondition, with `git` available.
- **The two real provider CLIs as installed on the executing machine**, read once, for the effort-capability measurement `AC17(b)` reports — including the outcome that a provider exposes no per-invocation effort mechanism at all.

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect against:

- **An actual executor invocation.** Nothing in this task calls a provider, so a finding whose only trigger is a live invocation, a network failure, a partial response, a timeout, a retry or a concurrent run is `out-of-input-space` for this cut and belongs to T-1056.
- **An envelope instance.** No instance format exists (DP1), so a finding about parsing, escaping, encoding or round-tripping an envelope payload has no artifact to attach to here.
- **A hostile operator.** Replacing a shipped definition inside the plugin's own installation, or overriding a shell builtin to defeat the parser. `CLAUDE.md`'s security invariant makes the operator and the working directory trusted, and `bin/check-durability.sh` and `bin/check-binding.sh` scope their own threat models identically.
- **Environment-variable neutralization, `GIT_*` enumeration, `GIT_DIR` redirection, replace refs, clean filters or LFS.** Named explicitly because two sibling checkers name them, and for the same reason: they belong to a separate hardening issue.
- **Ever-longer or ever-larger synthetic input**: field values beyond the 64-character cap, definitions with hundreds of rows, contract registries with thousands of fields, definition directories with thousands of files. - **A hostile `$TMPDIR`**: an attacker-controlled temp directory, a symlink race against `mktemp -d`, or a permission flip between creation and first write.
- **A concurrent writer** mutating the contract registry, a definition or the working tree mid-run.
