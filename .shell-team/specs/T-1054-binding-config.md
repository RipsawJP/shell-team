## Problem

Sprint v2.0.0 gives the host the ability to assign which executor runs each loop role (epic issue #203). Nothing in the repository can express that assignment today: every role runs on whatever model the harness happens to give it, and the one cross-provider boundary that exists (`codex-reviewer` shelling out to the Codex CLI) is hardcoded in an agent prompt rather than declared anywhere a checker can read.

Three things must exist before an adapter layer (T-1055) or any loop wiring (T-1056) can be built, and all three are the kind of surface that is dangerous to get wrong once: a **file format** a host authors and every later component parses identically; a **validator** that refuses anything it cannot fully evaluate, so a malformed or half-understood binding never silently degrades into a default; and an **integrity primitive** that detects a binding changing underneath a run in progress. Without the third, "the binding is immutable within a run" is a sentence in an issue rather than a property anything observes.

## Goal

<!-- BEGIN intent-block: T-1054 -->

Three artifacts ship together and nothing else does. **(1) A host-authored binding config format**: line-oriented, whitespace-delimited, pure-bash-parseable, never `source`d, resolved by default as `<base>/binding.conf` where `<base>` comes from `bin/team-paths.sh --get base`, carrying a required `schema` version line and exactly one `bind` row for each of the six inner-loop roles (`tech-lead`, `pm-spec`, `engineer`, `qa-verifier`, `codex-reviewer`, `ui-designer`), each row a fixed six-field tuple `bind <role> <provider> <model> <effort|-> <adapter>` in which every field is a bare token that cannot spell a shell command and `adapter` is a token from a plugin-shipped allowlist rather than an executable path. **(2) A fail-closed validator**, `bin/check-binding.sh`, pure bash, zero new runtime dependency, shellcheck-clean, whose every refusal is one token from a closed set with a fixed exit code, which never returns success on input it could not fully evaluate, and which never executes, sources or evaluates any byte of the config. **(3) The run-scoped integrity primitives** inside that same script: `--print-binding` emits the canonical resolved binding, `--print-lock` emits a self-describing lock document carrying the canonical binding and its `git hash-object` hash, and `--verify --lock <path>` re-derives and compares, refusing with `binding-changed` or `path-mismatch` — detection-and-stop, never write prevention, and never a write of any kind, since every mode's only output channel is stdout. A shipped specimen (`templates/binding-template.conf`) and adapter allowlist (`templates/binding-adapters.txt`) ship with them, a fixture suite (`tests/check-binding/run.sh`) exercises every refusal, and CI runs both. Nothing consumes the binding: no agent, skill, adapter or phase transition reads it, `.shell-team/binding.conf` is not created for this repository, `bin/team-paths.sh` gains no key and is byte-identical to the base ref, and every file T-1053 delivered on this branch is left exactly as that task shipped it.

### Settled decisions

Every decision below is resolved. Where a decision is a departure from the most obvious reading of the epic, its reason is stated at the decision, not deferred to review.

**DP1 — the config path is `<base>/binding.conf`, composed from the resolver, with an explicit `--config <path>` override.** Never hardcoded: `bin/check-binding.sh` invokes `bin/team-paths.sh --get base` from its own installed directory (`$SCRIPT_DIR`), exactly as `bin/check-durability.sh` composes `<base>/durability-mode`. The `.conf` extension is deliberate: several checkers and dogfood steps in this repository glob `<base>/*.md` or `.shell-team/**/*.md`, and a non-markdown extension keeps a config that is not prose out of every one of those sweeps.

**DP2 — `bin/team-paths.sh` gains no `binding` key, and the resolver's key set stays closed at ten.** Measured, not assumed: `tests/team-paths/run.sh:154-171` pins the key set at exactly ten in both directions, and its own comment records that T-1006's AC2 raised that pin from nine — so an eleventh key reddens that pin and the merged criteria behind it, for a benefit nothing needs. Nothing that reads a `TEAM_*` variable will ever read the binding: the epic makes the config read-only to every agent including the orchestrator, so no prompt-injected path is required. `bin/check-durability.sh` established the precedent for exactly this case and is cited rather than re-derived. The decision is locked by a negative criterion (AC3), not merely stated.

**DP3 — `effort` is positionally required and its absence is spelled `-`.** The epic makes `effort` optional; a positional grammar makes "optional" mean one of two things, and only one of them can be parsed without ambiguity. Every `bind` row therefore carries exactly six fields, and a row with five or seven is `unparseable-line` rather than a silent field shift. The literal `-` placeholder is the idiom `templates/durability-records.txt` already uses for "no value in this column". The format validates the field's *shape* only; whether the bound adapter can honour a given effort value is a capability question that belongs to T-1055 and is a Non-goal here.

**DP4 — a valid config binds all six inner-loop roles: no more, no fewer.** A partially-bound config would force every consumer to answer "what runs the unbound role?", and every answer to that question is a fallback chain, which the epic forbids outright. Completeness at the format level means the question cannot be asked. The whole-config case — no config file at all — is a different question, and it belongs to T-1056 (DP5).

**DP5 — the no-config contract boundary: this validator's job is "given a path, validate".** A missing, non-regular or unreadable config is the refusal `missing-config` at exit 2 — never exit 0, and never a silent default. T-1056 owns whether a repository with no binding config runs on v1 defaults; it makes that decision by branching on this token, so the token is part of the contract this task ships and is tested as such.

**DP6 — the adapter allowlist is a plugin-shipped registry, `templates/binding-adapters.txt`, resolved from the script's own installed directory.** Rows are `<adapter-token> <provider-token>`, both matching `^[a-z][a-z0-9-]*$`, each adapter token appearing at most once. Two consequences are the point of the design: a checked-out repository cannot register an adapter (the registry never resolves from the adopter's tree, the same property `templates/durability-records.txt` has), and the grammar cannot spell a command, a path or an argument list even if someone tries. The initial cut ships exactly two rows, `claude-cli claude` and `codex-cli codex`; custom adapters are out of scope per the epic. Because the registry pairs each adapter with one provider, a row whose provider and adapter are individually known but wrongly paired is its own refusal (`provider-adapter-mismatch`) rather than being accepted.

**DP7 — the canonical resolved binding is what gets hashed, not the config's bytes.** The canonical form is the `schema` line followed by one `bound <role> <provider> <model> <effort|-> <adapter>` row per role, single-space delimited, sorted by role under `LC_ALL=C`. A comment reflow, an added blank line, a CRLF conversion or a reordering of rows therefore does **not** trip the integrity check, while any change to a bound value does. This is a deliberate narrowing of "a change is mechanically detected": the property the epic protects is the *binding*, and a stop triggered by a comment edit is a false stop that trains its reader to ignore it. The keyword differs from the config's own (`bound`, not `bind`) so a canonical dump or a lock file can never be mistaken for — or fed back in as — a config.

**DP8 — the integrity primitives write nothing; stdout is their only output channel.** `--print-lock` emits the lock document; the caller redirects it. Nothing in this task creates a directory, truncates a file or overwrites a path, so the primitives carry no destructive-operation surface and no overwrite hazard at all, and `--verify` is provably read-only. This also keeps `bin/check-binding.sh` honest about its `check-` prefix, and it puts freeze and verify in one script for the reason T-1041 already settled for `check-intent.sh --print-hash`: one normalization pipeline, so the frozen value and the verified value can never come from two implementations of it.

**DP9 — where the baseline lives, and what its independence actually rests on.** The recommended storage location, documented in the script's own usage text and consumed by T-1056, is `<runs>/binding/<run-id>.lock` — under the resolver's `runs` key, which `templates/shell-team.gitignore` already marks as per-run, never-committed telemetry, and which is a different directory from the config it describes, so no hand edit or sweep aimed at `<base>/binding.conf` reaches it. The property that carries the weight is not the directory, though: it is that **the lock records the config path it was taken from and `--verify` never re-resolves that path**, so a base directory that resolves differently in a later phase is reported as `path-mismatch` instead of being quietly followed to a different file. Deliberately excluded: the lock is not a committed record and is not added to `templates/durability-records.txt` — it is per-run state whose value changes every run, and the durability barrier exists for records a task must leave behind.

**DP10 — the threat model is accidents, and this is a scoping decision rather than an omission.** A stray sweeping edit, a hand edit mid-run, a mis-resolved base directory: those are what the primitives detect. A hostile operator forging a lock to match a mutated config is out of scope, because `CLAUDE.md`'s security invariant makes the operator and the working directory trusted, and `bin/check-durability.sh`'s header states the identical boundary for the identical reason. No environment-variable neutralization, no shell-function override defence, no `GIT_*` enumeration ships here.

**DP11 — the validator enforces no cross-provider property.** It does not require `codex-reviewer` to be bound to a different provider than the rest. The shipped specimen encodes cross-provider review as the **default**, which is what the epic demotes the invariant to; making it a validation rule would decide a question #203 explicitly reopened and would do it in the one layer that cannot be overridden.

## Non-goals

- **No adapter layer.** Nothing composes an executable, argv or an environment from a binding; nothing invokes a provider. That is T-1055.
- **No loop integration.** No phase transition freezes or verifies anything, no skill or agent reads the config, no `run-id` is minted, and `<runs>/binding/` is not created. That is T-1056.
- **No v1-default migration behaviour.** What a repository with no binding config does is T-1056's decision; this task ships only the `missing-config` token it will branch on.
- **No `.shell-team/binding.conf` for this repository.** Binding this repo's own loop before the adapter layer exists would be a change with no reader.
- **No new resolver key**, and no edit to `bin/team-paths.sh` or `tests/team-paths/run.sh`.
- **No effort-capability semantics.** The format validates `effort`'s shape and nothing else; which values an adapter honours is T-1055's.
- **No custom-adapter mechanism**, no adapter discovery, no user-extensible registry.
- **No cross-provider enforcement** in the validator (DP11).
- **No write side, anywhere.** No mode of `bin/check-binding.sh` creates, truncates or overwrites a file.
- **No edit *by this task* to any `agents/*.md`, any `skills/*/SKILL.md`, `README.md`, `README.ja.md`, `CONTRIBUTING.md`, `CHANGELOG*.md` or anything under `docs/`.** Stated as a claim about this task's own edits rather than about the tree's state against the base ref, because two of those files — `agents/pm-spec.md` and `skills/run/SKILL.md` — already carry T-1053's committed changes on this stacked branch and a tree-state reading of this line would be false on arrival. The format's documentation is the script's header and the shipped specimen's comments; adopter-facing documentation lands with the feature that is actually wired, in T-1056.
- **No edit to any file T-1053 delivered on this branch** (`skills/run/SKILL.md`, `agents/pm-spec.md`, T-1053's spec and records) and no edit to any other merged spec.
- **No repair, re-basing, widening or annotation of any merged criterion this task's diff turns red**, and no merged spec gains a `- stale-at:` sub-bullet from this pass.

## Input space

**Reachable input classes** — what this task's deliverables really read and must handle correctly:

- **Host-authored binding config files**, hand-written or copied from the shipped specimen: ASCII tokens, LF or CRLF line endings, `#` comment lines, blank lines, arbitrary runs of spaces or tabs between fields, alignment padding, a trailing newline or its absence, and rows in any order.
- **Config files that are wrong in exactly one way** — the real failure mode of a hand-edited file. Every refusal class in the matrix is reachable from a plausible human edit: a copied row not renamed (`duplicate-role`), a role deleted (`missing-role`), an effort value dropped (`unparseable-line`), an adapter guessed (`unknown-adapter`), a provider and adapter mismatched after a rename (`provider-adapter-mismatch`), a schema left at an old version (`unsupported-schema`).
- **A config edited while a run is in progress**: a comment or whitespace edit, a row reordering (none of which change the binding), and a value change (which does). Both outcomes are reachable and each has a defined result.
- **All three layouts the resolver supports**: the default `.shell-team` base, the legacy `tasks` base, and an explicit `TEAM_RUN_BASE` override — the config path is derived, never assumed, in each.
- **Lock files this same script emitted**, and lock files damaged by an interrupted redirect (truncated mid-document, terminator absent) or edited by hand.
- **The plugin-shipped adapter registry as installed**, plus a decoy file of the same name in the working directory — reachable whenever the loop runs in a repository that happens to carry a `templates/` directory, which every adopter of this plugin's own conventions might.
- **The current working directory being a git repository**, which is the loop's own precondition, with `git` available; and a base directory that resolves to a different path in a later phase than it did at freeze time.
- **Absent inputs**: no config at the resolved path, no lock at the given path, an unreadable registry. Each is reachable and each fails closed.

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect against:

- **A hostile operator.** Forging a lock to match a mutated config, replacing the shipped registry in the plugin's own installation, or overriding a shell builtin to defeat the parser. `CLAUDE.md`'s security invariant makes the operator and the working directory trusted, and `bin/check-durability.sh` scopes its own threat model identically; the guarantee here is detection of accidents, and a finding whose only trigger is a deliberate forgery is `out-of-input-space`.
- **Environment-variable neutralization, `GIT_*` enumeration, `GIT_DIR` redirection, replace refs, clean filters or LFS.** Named explicitly because a sibling checker names them, and for the same reason: they belong to a separate hardening issue, not to this format.
- **Ever-longer or ever-larger synthetic input**: field values beyond the 64-character cap, rows with hundreds of fields, configs with thousands of rows, registries with thousands of adapters. Real host-authored data produces none of these; the cap is a declared boundary and a finding that only fires past it is `out-of-input-space`.
- **Non-ASCII tokens** in role, provider, adapter or effort fields, and Unicode homoglyph confusables. The role and adapter sets are closed and ASCII by construction; a homoglyph simply is not the token and is refused as unknown.
- **A NUL byte or invalid UTF-8 inside a config, a registry or a lock.** Committing or authoring one independently breaks the file for every text tool in this repository; it is a design question, not an input class to accommodate.
- **Filenames containing a newline, a tab, or a byte `core.quotePath` would C-style-quote**, in any path this task reads or any path a criterion enumerates. This corpus commits none, exactly as the merged specs this one follows accepted.
- **A hostile `$TMPDIR`**: an attacker-controlled temp directory, a symlink race against `mktemp -d`, or a permission flip between creation and first write.
- **A concurrent writer** mutating the config, the lock or the working tree during a run — a run-discipline matter for the executing side, not an input class these deliverables accommodate.
- **A working directory outside any git repository.** The hash pipeline is expected to fail closed there through its own guard rather than being widened to a git-free hash; AC16(g) requires the behaviour to be measured and reported rather than assumed.
- **Adapters beyond the shipped registry**, including any host-supplied or discovered adapter. Custom adapters are out of scope for the initial cut by the epic's own decision.
