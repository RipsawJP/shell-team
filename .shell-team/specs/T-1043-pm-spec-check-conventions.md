## Problem

`pm-spec` writes `- check:` lines with no stated convention for *how they observe the tree*. Two shapes it produced on one task both failed for reasons unrelated to the implementation under review: a `git diff --name-only <base>` that compares the base ref against the working tree, so an unrelated uncommitted change failed a scope-lock criterion; and an unscoped `! grep -rn <identifier>`, asserting an identifier was fully removed, that also read gitignored compiled caches older than the base ref. Both were resolved by QA re-running the intended measurement and adjudicating the raw result as an environment artifact, with evidence — the behaviour one wants, but work the check line should not have created.

The pre-freeze sweep ran on that task and **both lines passed it**: they are not mechanically broken, only over-broad. That is the fact that decides this task's shape. A sweep that executes a line cannot see over-breadth, so no new checker is written here; the remedy is a convention stated at the point the line is authored, in the one prompt region that governs authoring.

  Bullet **K1** — the diff-form convention:

<!-- frozen-begin: K1 -->
```markdown
- **A diff-based `- check:` line names a commit range, not the working tree.** Write `git diff <base>...HEAD` — the three-dot notation `agents/drift-evaluator.md` and `agents/codex-reviewer.md` already print, so the repository carries one notation rather than two; `git diff <base> HEAD` is the identical measurement whenever `<base>` is an ancestor of `HEAD`, which is the pinned-branch-point shape these specs use, and is equally acceptable. The **one-argument** form `git diff <base>` compares the base ref against whatever is on disk at read time, so an unrelated uncommitted edit fails a criterion that has nothing to say about it — do not write it unless the criterion's subject genuinely *is* the working tree (a post-mutation "the checkout is clean" assertion, for instance), and say so in the criterion's own body when it is. A scope lock is **not** that case: take its tracked half from the commit range and its untracked half from `git ls-files --others --exclude-standard`, which sees the strays a range cannot.
```
<!-- frozen-end: K1 -->

  Bullet **K2** — the grep-scope convention:

<!-- frozen-begin: K2 -->
```markdown
- **A `grep`-based absence `- check:` line scopes what it reads.** A criterion asserting that an identifier, token or path is gone names the files it reads outright, or — where the target set is genuinely a glob — restricts a recursive search with `--include=<glob>` and, where the tree needs it, `--exclude-dir=<dir>`. An unscoped `grep -rn <identifier> .` reads whatever happens to be on disk: one gitignored build artifact or compiled cache older than the base ref, invisible to every other check, is enough to fail a criterion whose source tree is clean. Naming the files is the stronger form and the default; `--include` is for the case where you cannot.
```
<!-- frozen-end: K2 -->
