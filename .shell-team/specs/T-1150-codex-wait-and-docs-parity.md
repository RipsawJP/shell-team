## Problem

On a Codex CLI host the loop's orchestrator dispatches each role by spawning a generated Codex custom agent, and nothing in the shipped dispatch text says how long to wait for that agent's turn. On a measured adopter run of v2.7.1 the orchestrator aborted `pm-spec`, `engineer` and `qa-verifier` after roughly eight to thirteen minutes each, recorded `work-abandoned` three times and finished those roles' work itself — while every one of the three was still working: each had answered a status nudge within a minute, `pm-spec` had just frozen a second spec version, the `engineer`'s fix commit landed one second before the abort, and `qa-verifier` had a green unit suite and a long acceptance-criteria run in flight. The same class fired once on the preceding run. The shipped text carries no statement that an answered nudge is progress, no statement that elapsed time alone never justifies an abort, and no duration class for the long steps a role legitimately runs, so the orchestrator had nothing to read and defaulted to its own impatience. The same run also produced a second defect on the same surface: the orchestrator self-attested a class-B re-freeze from v2 to v3 with no per-instance human GO, a gate the shipped text states for the Claude Code host and nowhere restates for this one. Alongside that dispatch gap, three already-filed staleness items sit on the same host-parity documentation surface — the README's reviewer labels, per-repo qualifier, host-neutral bullets and install deferral list; the Japanese distribution guide's missing sandbox section; and the release-notes template's Claude-only install boilerplate — each describing a mechanism that already ships on both hosts as though it shipped on one.
