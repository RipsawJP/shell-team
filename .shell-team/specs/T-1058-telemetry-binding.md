## Problem

T-1057 shipped `bin/resolve-executor.sh`: the loop now resolves, per role and immediately before invoking it, exactly which executor runs that role — provider, model, effort and adapter — and refuses fail-closed when it cannot. **That answer is then thrown away.** The one place a run's telemetry records anything about it is the span row's `model` field, whose value T-1057 moved onto the resolved row; provider, effort and adapter are recorded nowhere at all.

Two consequences follow, and they are the kind that make an invariant unfalsifiable rather than merely undocumented. First, **the cross-provider review invariant cannot be audited after the fact.** `CLAUDE.md` states it as a rule and `templates/binding-default.conf` ships it as the default, but a host may legally bind `codex-reviewer` to `claude`/`claude-cli` (T-1055's Non-goals keep that legal), and no artifact any run leaves behind can say whether a given review round was cross-provider or not. Second, `templates/task-envelope.txt`'s own comment says its four error classes exist "because #203 design point 4 names them as telemetry T-1057 needs ready" — the vocabulary is ready and **nothing records against it**: a phase whose resolution refused leaves no trace in the telemetry at all, so the fail-closed path is invisible to exactly the reporting layer that would show how often it fires.

### Settled decisions

Every decision below is resolved. Where a decision departs from the routing map's own recommendation, the departure and its reason are stated at the decision rather than deferred to review.

**DP1 — the span carries three new keys, `provider`, `effort` and `adapter`, appended after `parent_span_id`; `model` is reused and `probe_kind` is declined.** Individual keys rather than one composite: a composite would need its own separator grammar inside a JSON string value and would have to be re-split by every reader, and it buys nothing — T-1011's AC6 key-sequence lock reddens on the **first** added key exactly as it does on the third, so there is no criterion to economize against. `model` is not redefined: T-1057 already moved its value onto the resolved row, so the span's four binding fields are exactly fields 3–6 of the `resolved` line the loop already holds. **`probe_kind` is declined**, departing from the routing map's candidate list: it is not a property of the run but a static property of the provider token, compiled into the resolver's own table, so recording it on every row would put a second copy of a fixed mapping into every log line — the duplication class this repository's prompt-block and delegated-parser machinery exists to avoid — and nothing in the provider relation needs it. Appended rather than interleaved so a reader that consumed the first seventeen positionally is unaffected.

**DP2 — what is recorded is the *declared* binding, and the derived label inherits that boundary.** The resolver decides *whether an invocation may proceed*; it never observes what a provider actually did, and T-1057's own canonical block says so in as many words. A `provider` value on a span therefore means "this is the provider the effective binding named for this role at resolution time", and `cross-provider` means "the two spans' **declared** providers differ" — not "two different model families were verifiably involved". The block, this Goal and the reporter's own header state it in that form; a review finding that the label is not independently verified is answered by this boundary rather than by adding a verification mechanism this task's Non-goals decline.

**DP3 — the resolved row travels as flags, in the orchestrator's own context; no state file, no environment variable.** The orchestrator runs `resolve-executor.sh --role <role>` immediately before invoking that role and emits the span immediately after it returns, so the row is in scope for both — the same path `--model` already takes since T-1057. An environment variable is measurably not an option (`skills/run/SKILL.md` L24: env vars do not survive between Bash tool calls), and a state file is declined for the reason T-1057 declined its own: it would add a write path to the loop for an artifact nothing reads, and T-1056's DP9a-style write-surface reasoning applies with more force here because the resolver's zero-write property is a never-dropped item of this task's pre-commitment.

**DP4 — a refused phase writes no span row; the refusal is recorded with the existing `gate` event id.** Two candidates were considered and one rejected. Writing a span with `--status stopped` and null binding fields would record a **call that never happened** — the header of `bin/log-run.sh` defines a span as "one call into a sub-agent", and the resolver refuses *before* anything is invoked — and it would inflate every span count, status breakdown and health flag in the roll-up with non-events. So the refusal is recorded where the loop already records fail-closed seam gates: `--event gate --from <phase> --label <refusal token>`, which needs **no new event id, no new status value and no new field**, and which `bin/rollup-runs.sh` already skips so no count is disturbed. The five refusal tokens are `usage`, `binding-unresolved`, `capability-unsupported`, `contract-violation` and `executor-unavailable`, and the label carries whichever one was refused, verbatim. The instruction lands in this task's own canonical block rather than in `skills/run/SKILL.md`'s L120 event bullet, because that line exists at the branch point and the run surface's line-survival budget is spent.

**DP5 — no `error-class` field, and no join between the two vocabularies.** The routing map's recommendation is adopted with the measurement that grounds it: `templates/task-envelope.txt` declares **four** error classes and the resolver refuses with **five** tokens, and the two sets are not the same set — `usage` and `binding-unresolved` have no class, `invocation-failed` has no token. Freezing a join would create a second implementation of a vocabulary neither file owns, in the one script that must never gain a dependency it cannot validate. Where a refusal needs a name in telemetry it is the refusal token verbatim, in a free-text field (`--error` on a span, `--label` on the `gate` event) that is already free text — so the log records the token and nobody has to maintain a mapping.

**DP6 — the role-pair definition, stated as two sets and a per-span rule, with no cardinality-one assumption anywhere.** This is where the design weight sits, and each of the four questions is answered separately.
*Which roles are reviewers, and which author the work under review.* The **reviewer role set** is `{codex-reviewer}` and the **authoring role set** is `{engineer}`. Both are stated as sets, and the membership reason is stated so a later member joins the set instead of forcing this definition to be re-read: a cross-provider review's whole purpose is that the reviewer does not share the implementer's blind spots, and what a review round reads is the diff the implementation produced. `pm-spec` and `ui-designer` are deliberately **not** authoring roles for this relation — a spec and a design are inputs to the work, not the artifact under review — and `tech-lead` and the three advisory roles are neither. The key is the row's **`span`** field, not `phase`: `span` names the role, which is what the relation is defined over, while `phase` names where in the loop the call happened; both are free strings in the row, so neither is validated, and choosing the one that names the role is what makes the definition survive a phase being renamed.
*What the scope is.* One `run_id`, and within it **input order** rather than seq arithmetic — `bin/rollup-runs.sh` buffers rows in file order and sorts nothing, and adding a sort would be a behaviour change this task declines. A reviewer span's counterpart is the **nearest preceding authoring span in the same run**; the whole run is not the scope, because a fifth review round is a statement about the fifth implementation round rather than about the first, and `iteration` is not the scope either, because a rework round's engineer span and the review span that judges it are not guaranteed to share an iteration value the orchestrator computes independently.
*What multiple rounds produce.* **One output token per reviewer span**, in input order, each carrying its own span name and seq — never one boolean per run. Read against T-1055's real history, which ran **five** review rounds against five implementation rounds in one task: that run yields five tokens, they may differ from one another, and a per-run boolean would have to pick one of five answers or invent an aggregate nobody asked for. AC4 exercises exactly that shape with three rounds and requires at least two distinct outcomes in one run, so a formulation that collapsed to one answer per run cannot satisfy it.
*What an unknown produces.* **`undetermined`, fail-closed, never `false` and never `same-provider`** — when the reviewer span recorded no provider, when the nearest preceding authoring span recorded none, when no authoring span precedes the reviewer span at all, when the value is a token this reporter does not recognize, and for every row written before this task. That is why the output is a three-member token set rather than a boolean: a boolean has no room for "the log does not say", and the failure this closes is a legacy log reading as "same provider, therefore the invariant was violated" or as "cross-provider, therefore it held". `same-provider`, by contrast, is a **legitimate reachable outcome** and not a defect report: a host may legally bind `codex-reviewer` to `claude`, and this reporter says what the log records.

**DP7 — the derivation is printed by `bin/rollup-runs.sh`, computed from span rows only, and it stores nothing.** Two lines per run block, `providers:` and `review:`, always printed so an absent line is a defect rather than a silence. Computed from span rows only, which is what preserves the header's own promise and T-1011's AC22: this reporter already skips every event row before any pass runs, so a derivation that reads only what the passes read cannot make the mixed-file and span-only outputs differ. `bin/rollup-track.sh` is not edited — and that is **not** the same as its artifact being unaffected, which v1 of this spec wrongly asserted. Measured at the file: it captures this reporter's stdout verbatim (`SUMMARY="$(bash "$ROLLUP_RUNS" …)"`) and writes that capture inside a fenced block, so **the two derived lines reach the committed artifact with the wrapper byte-untouched**. Two things follow and neither is a filter. First, the artifact must keep being a faithful snapshot: a wrapper that stripped the two lines would make the tracked file disagree with what the same command prints, which is a worse defect than the one it would fix, so the capture is accepted. Second, because the destination is permanent, the bound moves from prose to a check — AC13 writes a real artifact and asserts each of the two lines against its closed shape, and asserts that no `model` value reaches it at all. T-1011's AC25 stays green for a **different reason than v1 gave**: not because the file is untouched, but because the derivation is computed from span rows only, so the artifact for a mixed input is still byte-identical to the artifact for its span-only variant, and neither carries a `kind` token. `bin/cluster-failures.sh` and `bin/gen-loop-replay.sh` do gain nothing, and their outputs are unaffected because neither reads a span key this task adds.

**DP8 — two-generation behaviour is fail-closed in all three populations, and the roll-up never fails over it.** A file of only pre-task rows prints `providers: (none)` and `undetermined` for every reviewer span; a mixed file prints per-span answers and marks the provider counts `(partial)`; a file of only new rows prints the full picture. In every case `bin/rollup-runs.sh` exits `0` — a missing field is data this reporter describes, never an error it raises — and `bin/log-run.sh`'s best-effort contract is untouched: a validation refusal writes nothing and exits `2`, every in-repo caller keeps its `|| true`, and no new path lets a telemetry failure stop a phase.

**DP9 — the write surface is exactly `bin/log-run.sh`, and it is the only one that moves.** `runs/` is volatile and gitignored, `bin/rollup-runs.sh` writes nothing and reads only its arguments, and `bin/resolve-executor.sh`'s zero write path is re-asserted here by byte-identity to the branch point rather than by a fresh static search — a stronger claim, and cheaper. No environment variable, debug flag or hook gains a write path in any of the three touched scripts.

**DP10 — the norm is a second canonical block, appended, rather than an edit to T-1057's.** This departs from the routing map's step list, which called for extending `templates/prompt-blocks/executor-resolution.md`, and the reason is measured on both sides. Editing that block reopens T-1057's **AC11**, which locks its content and requires exactly one registry row naming it, for a duty that is not resolution: this norm applies **after** a sub-agent returns, not before it is invoked, and its subject is the telemetry row rather than whether the phase may proceed. A separate block also keeps both skills' edits a **pure append**, which matters mechanically rather than aesthetically — T-1057's AC17 permits at most one branch-point line to be missing from `skills/run/SKILL.md` and that one is already spent on T-1057's own telemetry rewrite, so any rewrite of an existing line on that surface reddens a merged criterion. The block's text additionally avoids all eight alternatives of T-1056 AC14's escalation pattern, and AC6 measures each surface's count as **unchanged from the branch point** rather than trusting the wording.

**DP11 — the two span-only enumerations are locked to each other mechanically, not by discipline.** `bin/log-run.sh`'s `SPAN_ONLY_FLAGS` and `bin/check-run.sh`'s `SPAN_ONLY_KEYS` are the same set in two spellings, and T-1011's D2 made their symmetry a requirement without making it checkable. AC2 extracts both single-line arrays at check time, normalizes the flag spelling (`--` stripped, `-` to `_`) and requires **set equality in both directions**, plus a base-relative delta showing exactly the three new members were added and none removed. That clause is green at this base and must stay green, so it is a regression lock rather than a new-work assertion — and it is the mechanism that makes a future fourth field impossible to add to one side only.

**DP12 — the threat model is accidents, identical to T-1054's, T-1055's, T-1056's and T-1057's, for the identical reason.** A log written by an older writer and read by a newer reporter, a host binding both roles to one provider, a free-text `error` value whose bytes mimic a key, a fixture nobody re-generated. A hostile operator hand-editing a volatile run log to forge a binding is out of scope: `CLAUDE.md`'s security invariant makes the operator and the working directory trusted, and the log is neither committed nor an authority over anything.

- **The same roll-up captured into a git-tracked artifact by `bin/rollup-track.sh`** — reachable on every host that runs the outer-loop wiring, and the reason this task has a durable-output surface at all rather than only an ephemeral one. The two derived lines land in a committed file, so their content is bounded by AC13 to closed-vocabulary tokens, integers and two fixed idioms, and the wrapper's own write-time PII/secret guard stays the backstop for a log this task's writer did not produce. **v1 of this spec wrongly declared this class out of reach**; it is in scope, it is checked, and the honest statement of what it costs is that a hand-crafted log remains the guard's problem rather than this reporter's.

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect against:

- **A hostile operator.** Hand-editing a run log to forge a binding, or planting a log that claims a cross-provider review that never happened. `CLAUDE.md`'s security invariant makes the operator and the working directory trusted, the runs directory is gitignored and volatile, and no gate consumes this derivation — a finding whose only trigger is deliberate forgery is `out-of-input-space`.
- **A dishonest executor, and any claim about what actually ran.** An executor that reports one identity and behaves as another, or a binding that names a provider whose process was never started. What is recorded is the **declared** binding (DP2); a finding that `cross-provider` is not independently verified is answered by that boundary, not by a verification mechanism.
- **Whether a `provider`, `adapter` or `model` token names something that exists.** The token classes are shape checks; membership belongs to `bin/check-binding.sh`, which owns that grammar, and a third adapter must be able to log without this task's validation refusing it.
- **A non-monotonic or duplicated `seq`.** The orchestrator's contract is one monotonic counter per run; the derivation uses **input order** and prints `seq` only as an identifier, so a log that violates that contract produces identifiers that are not unique — a statement about the writer's caller rather than about this deliverable.
- **Ever-larger or ever-longer synthetic input**: a log of hundreds of thousands of rows, a run with hundreds of reviewer spans, a token longer than `bin/check-binding.sh`'s own 64-character cap, a `providers:` line whose width exceeds a terminal. The reachable classes above are the boundary and a finding that only fires past them is `out-of-input-space`.
- **Non-ASCII or homoglyph provider, effort or adapter tokens.** Every vocabulary these fields draw from is closed and ASCII by construction at the binding layer; a homoglyph simply is not the token and is refused by the character class.
- **A NUL byte or invalid UTF-8 inside a `.jsonl`.** Authoring one independently breaks the file for every text tool in this repository.
- **Filenames containing a newline, a tab, or a byte `core.quotePath` would C-style-quote**, in any path this task reads or any path a criterion enumerates. This corpus commits none, exactly as the merged specs this one follows accepted.
- **A hostile `$TMPDIR`**: an attacker-controlled temp directory, a symlink race against `mktemp -d`, or a permission flip between creation and first write.
- **Concurrent appends to one log.** Two orchestrators writing the same `<loop_id>.jsonl` at once is a property of `bin/log-run.sh`'s pre-existing `>>` append, unchanged by this task; a finding about interleaved writes is about that pre-existing behaviour.
- **Cross-run, cross-loop or cross-repository derivation**, a per-run aggregate verdict, and any consumption of the relation by a gate. All are declined in Non-goals, and a finding that the relation is not enforced anywhere is `out-of-input-space` for this cut.
