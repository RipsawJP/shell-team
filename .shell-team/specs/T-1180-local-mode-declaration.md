# One shared reader of `git config shell-team.mode`: under `local`, check-durability.sh skips and team-commit.sh refuses base-dir paths; `tracked` stays byte-identical

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1180

## Problem

Some adopters keep the base dir out of git on purpose. Issue #692 has two adopter repositories doing it today. In those repositories `bin/check-durability.sh` fails closed at every seam (`not-in-recorded-commit`), and the orchestrator has been absorbing that refusal for months. The adopter has no way to declare the mode they actually run in: the existing `<base>/durability-mode` opt-out has to be committed itself, which an ignored base dir makes impossible (#587). Issue #711 proposes a declared `local` mode in the clone's own git config. This task is #711's task A of three. It adds the one shared reader of that declaration and makes the two scripts that observe or perform record commits honour it. Role hand-offs, setup, init, close-out, the PII scan and the shipped docs stay with tasks B and C.

**Goal (one sentence).** A new `bin/team-mode.sh` prints exactly `tracked` or `local` for the current clone, selecting `local` only when the clone's own `.git/config` holds the exact value `local` for `shell-team.mode` and failing closed (exit 2) when git cannot read that config. Under `local`, `bin/check-durability.sh` prints the single line `check-durability: skipped: shell-team.mode is local — no durability observation was made` and exits 0 without examining any ref, blob, registry or `durability-mode` file. Under `local`, `bin/team-commit.sh` refuses, with exit 2 and before any write, any named path that lies under the resolved base dir. Under `tracked`, both scripts produce the same exit status, stdout, stderr and repository state as the base commit on every input where git can read the clone's config.

**Decisions frozen here** (each is promoted to a criterion):

- **D1 — one standalone resolver.** `bin/team-mode.sh` is a new tracked `100755` pure-bash script, the single reader both consumers call as a sibling, in the same way they already reach `team-paths.sh`. #711 tasks B and C call the same script. With no argument it prints one line, `tracked` or `local`, exits 0 and writes nothing to stderr. `--help` and `-h` print usage naming `shell-team.mode` to stdout, exit 0, need no repository and write nothing to cwd. Any other argument is a usage error (exit 2, nothing on stdout). It never reads ignore state: no non-comment line names `check-ignore`, `git status`, `gitignore`, `info/exclude` or `ls-files`. (**AC1**)
- **D2 — scope and outcome table.** Only the clone's own repository config counts. #711 says the declaration is "written once by the operator into the clone's own `.git/config`" and is "per-clone and never shared". A value at global or system scope, or one injected through `git -c`, `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_COUNT`, never selects `local`, because that would put every clone of every repository in local mode at once. The read's outcome table is closed. Git reports a value: `local` if the value is the exact byte string `local` (no case folding, no trimming), otherwise `tracked`. Git reports the key absent: `tracked`. Git reports anything else (a malformed `.git/config`, no repository at all, a repository git refuses to read): exit 2, nothing on stdout, a diagnostic on stderr. That last case is never silently read as `tracked`. Run from a subdirectory of the work tree, the resolver reads the same clone's config. (**AC1**, **AC7**)
- **D3 — `check-durability.sh` under `local`.** The mode is read after argument validation, so usage errors keep exit 2 and their messages in every mode. It is read before anything else is resolved or observed. Under `local` the script prints exactly the Goal's `skipped:` line on stdout, prints nothing on stderr and exits 0 for every `--phase`. It does so for an unborn repository, an ignored base dir, a missing or uncommitted record, a malformed `durability-mode` file and a `--ref` that names no commit. Its non-comment lines still contain no `git config` (the T-1048 fixture lock); the config is read only through `team-mode.sh`. A missing or unreadable `team-mode.sh`, a resolver exit other than 0, or a resolver output other than exactly `tracked` or `local` is `structural` (exit 2). The header's verdict list names the local-mode skip, and `--help` still prints through the `--records` option line. (**AC2**, **AC7**, **AC8**)
- **D4 — `team-commit.sh` under `local`.** The mode is read after every existing argument, environment and repository-state refusal, so each of those keeps its bytes and its order, and environment-injected config is already refused before the read. The resolver is called on every run. `team-paths.sh` is called only when the mode is `local`, so a tracked run needs no team-paths sibling. A missing or unreadable `team-mode.sh`, a resolver failure, an output outside `tracked`/`local`, or (in local mode) a missing or failing `team-paths.sh` is refused with class `mode` (`team-commit: refused (mode): …`, exit 2, nothing written). Its detail names the path and `shell-team.mode`, and the refusal comes before the first `git add`. When several paths are named and one is under the base dir, nothing at all is staged. (**AC4**, **AC7**, **AC8**)
- **D5 — the base-prefix test.** The base string is the one `team-paths.sh --get base` prints, normalised by removing one trailing `/`. `team-paths.sh` already rejects a leading `./`, `.`, `..` and empty components.
