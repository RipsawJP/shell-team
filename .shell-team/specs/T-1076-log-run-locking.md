## Problem

`bin/log-run.sh` is the single canonical writer for loop telemetry, and it has no serialization of any kind. Its append path assembles the whole row into one variable and emits it with one `printf '%s\n' "$ROW" >> "$RUNS_DIR/${LOOP_ID}.jsonl"` (assembly at lines 326–362, `mkdir -p` at 382, the append at 383), with no lock, no `O_EXCL` guard and no `set -C` anywhere — measured, and measured across the whole of `bin/`: a search for `flock|lockfile|noclobber|set -C` over `bin/` returns **no matches at all**. Row length is unbounded — `--error` is captured at line 193 and emitted at 355, `--label` at 202 and 336, and `jesc` (313–318) strips control characters but imposes no length bound — so the comfortable assumption that an `O_APPEND` write is one atomic syscall is not one this writer has earned. Today that is survivable because one process writes at a time. It stops being survivable at the next car: a Tier-1 verification fan-out runs several roles concurrently, each wanting to emit its own span, and the sprint's own concurrency probe already recorded that agent-level fan-out cannot self-emit spans until this lands. The counter has a second, already-visible defect: `--seq` is caller-supplied (captured at 181, validated at 214 against `^[0-9]{1,9}$` and nothing else), `bin/check-run.sh` never checks a `seq` **value** at all (its `seq` appearances are the two required-key arrays at lines 51 and 52, plus header prose — there is no cross-line state anywhere in it), and the machine-local corpus consequently carries duplicate `(run_id, seq)` pairs today, written by a single writer that simply lost count.

- user-visible: yes — this task adds two new adopter-reachable surfaces on a script the plugin puts on `PATH`: the accepted literal `--seq auto` on the existing `--seq` flag, and a new refusal (nothing written, a dedicated non-zero exit) when the append lock cannot be acquired inside a bounded wait, tunable through a new `TEAM_LOG_LOCK_TIMEOUT` environment variable. An adopter running `log-run.sh` in their own repository can observe all three.
- adopter-surface: `README.md`'s Operating-loop **Telemetry** bullet (line 173, the same bullet T-1072's `--instance` clause landed in) and its `README.ja.md` mirror — carried as an indented line under **AC12**, which is the criterion that makes it a freeze-time blocker rather than a fast-follow.
- verification-class: mechanism — the deliverable is a change to an executing surface (`bin/log-run.sh`, on `PATH` when the plugin is loaded) plus its CI-wired fixture suite (`tests/log-run/run.sh`). Nothing is priced down: the downstream-impact inventory is taken as a **full-population diff** over every merged spec's criteria run at the branch point and again at HEAD, CI-equivalence is run in full, and the mutation-probe matrix covers every criterion this spec freezes rather than only the check lines it adds.

**Goal (one sentence).** `bin/log-run.sh` serializes its append behind a portable, never-stealing directory lock so that concurrent writers can no longer interleave a row, gains a `--seq auto` mode that derives the next counter value per `run_id` from the target file under that same lock, and — when the lock cannot be acquired inside a bounded wait — writes **nothing** and exits with a dedicated code distinct from its validation error, with every uncontended row still byte-identical to what the branch-point writer produced.

**D1 — the lock is a directory created with `mkdir`, at a fixed path beside the file it guards.** The lock artifact is `<runs>/.<loop_id>.jsonl.lock`, a **directory**, created with a plain `mkdir` (never `mkdir -p`, whose success on an existing directory would defeat the whole mechanism). The reasons are stated rather than assumed: `mkdir` on a POSIX filesystem either creates the directory or fails, atomically, with no auxiliary file-descriptor state to juggle and no dependency on `flock`, which is **not** part of the macOS base system this repository's own host runs on; and the artifact's name is both dot-prefixed and `.lock`-suffixed, so it is invisible to the one glob enumeration of the runs directory that exists in this repository (`bin/gen-loop-replay.sh:239`, `*.jsonl`) twice over rather than once. The alternatives are rejected with their grounds: an `O_EXCL`/`noclobber` **file** lock is equally atomic but leaves a zero-byte file that a future reader could mistake for data and that `rmdir`'s safety property below does not cover; and "no lock at all, relying on a single `O_APPEND` write being atomic" is rejected outright because this writer's rows are measurably unbounded in length (`--error`, `--label`), so that option would require adding a row-length bound to the contract — a silent narrowing of an existing accepted input class, which this task declines to make while pretending it is free.

**D2 — refusal semantics: a dropped row beats a torn row.** When the lock cannot be acquired within the bounded wait, the writer writes **nothing** and exits **3** — a code distinct from `2` (validation error, nothing written) and from `1` (row written, self-check failed), documented in the script's own header contract. This is the one place where this repository's fail-closed discipline and this script's own "telemetry must never break the loop" contract point in opposite directions, and the conflict is resolved in favour of both at once: the writer fails closed (it never writes a row it cannot write safely), while the loop is unaffected because **every** caller already discards the exit status — the one executing caller wraps it in `|| true` and every prompt-text caller instructs the same. The bounded wait is **10 seconds** by default, overridable through `TEAM_LOG_LOCK_TIMEOUT` (a positive integer number of seconds); a value that is absent, non-integer, zero or negative falls back to the default and emits a warning naming the variable on stderr, following the same shape `bin/check-acs.sh` already uses for `CHECK_ACS_TIMEOUT`. The retry granularity is the implementation's choice **measured on the host rather than assumed**: fractional `sleep` is a GNU extension that this repository has not verified on its own `/bin/sh`, so the engineer either measures that it works and records the measurement, or uses whole-second steps.

**D3 — a stale lock is never stolen, and release can never destroy contents.** The writer **never** removes a lock it did not create — no age heuristic, no PID probe, no silent steal. It releases its own lock with `rmdir`, never `rm -rf`: `rmdir` refuses a non-empty directory, so a release path can never delete something another process put there, and the string `rm -rf` must not appear in the script at all. Release is wired to `EXIT`, `INT` and `TERM` and fires only when this process actually acquired the lock. The residual case is disclosed rather than engineered away: a writer killed with `SIGKILL` while holding the lock leaves the directory behind, and every subsequent write to that file refuses until an operator removes it — so the refusal message on stderr must name the lock directory's full path and be legible enough that the remedy is obvious from the message alone.

**D4 — `--seq auto` derives the counter per `run_id`, inside the same critical section.** The new accepted literal is exactly `auto`, on the existing `--seq` flag, case-sensitively (`AUTO` and `Auto` stay validation errors). Precedence is unambiguous: a caller-supplied integer always wins and is written verbatim, exactly as before; the file is consulted **only** when the literal `auto` is passed. The derived value is one more than the greatest `seq` among the lines of the target file whose `run_id` equals this call's — **per `run_id`, not per file**, because the measured corpus interleaves many `run_id`s in one file and `tail -1` would therefore be wrong — and is **1** when no such line exists, including when the file itself does not yet exist. Both row shapes count, since span and event rows share one counter. The scan is boundary-anchored on `{` or `,` in the same way `bin/check-run.sh`'s `key_present` and `bin/rollup-runs.sh`'s `field_str` already anchor a key, so a key that is a substring of a longer key or that appears inside a string value can never match; a line that carries this `run_id` but no parseable integer `seq` contributes nothing, which is a documented limit rather than a silent behaviour. The derived value must itself satisfy the existing `^[0-9]{1,9}$` grammar: at the ceiling, `auto` is a **validation error** (nothing written, exit 2) rather than a row carrying an out-of-grammar counter. The scan and the append happen under one acquisition of the lock, so no second writer can take the same number between them. The cost is stated honestly rather than hidden: the scan is O(file) per append, and on this repository's own machine-local corpus that file holds 1574 rows today; rotation or compaction of a growing corpus is explicitly **out of scope** and is disclosed as the cost's only real bound. A sidecar counter file is rejected with its reason: it would need its own atomicity story and would add a second piece of state that can disagree with the log it counts.

**D5 — a `seq` monotonicity lint is a non-goal, recorded as a rejected alternative.** `bin/check-run.sh` gains nothing here. Three grounds: the corpus is a record of what happened, and a lint that reddens on history already written turns a checker into a chore; `--line` mode is context-free by construction (`bin/check-run.sh:34–38`) and the writer's own post-write self-check calls exactly that mode, so any cross-line rule could only ever live in file mode and would therefore be invisible at the moment of writing — the only moment at which it could prevent anything; and adding a second new verification mechanism inside a task that is already building one doubles the risk class this repository has measured as its slowest. **Re-evaluation trigger**: revisit when a reader (a roll-up, a replay page, a retro input) is observed to produce a wrong result *because* of a duplicate or non-monotonic `seq`, rather than merely to contain one.

**D6 — the contention fixture, and a negative control that must measurably fail.** `tests/log-run/run.sh` — already CI-wired, so no workflow edit — gains a contention case: at least **8** concurrent writer processes appending at least **20** rows each to one file, each writer tagged with its own `--instance` token, all using `--seq auto`. Four assertions, each printing its own named `PASS:` token: the file's line count equals writers × rows; `bin/check-run.sh` lints the whole file clean; each writer's own row count equals its share; and the set of `seq` values for the shared `run_id` is **exactly** the expected set with no duplicate and no gap, derived at run time rather than compared against a typed literal. A fifth case asserts the D2 refusal (a pre-held lock ⇒ nothing written, exit 3), and a sixth asserts that a writer terminated while holding the lock releases it. **The negative control is the heart of the suite**: a lock-disabled mutant copy of the writer — made under `$TMPDIR`, never in the working tree — run at the same or higher concurrency with multi-kilobyte `--error` payloads (at least 16384 bytes) must **measurably fail** the same assertions. Its outcome is recorded either way, on a fixed-grammar line naming `detected` or `not-detected`; a `not-detected` outcome is disclosed as a limit in this task's provenance record and escalated, and it may never be answered by weakening a positive assertion.

**D7 — the back-compat floor, never dropped.** Three properties hold at HEAD. An **uncontended** row is byte-identical to what the branch-point writer produces for the same invocation once the timestamp field is normalized, in both span and event mode — this is the property the whole task is not allowed to trade. The machine-local corpus still lints clean under `bin/check-run.sh`, which is itself byte-identical to its branch-point blob, so one lint covers both refs rather than two lints pretending to. And every suite that touches this writer or its readers stays green.

## Input space

**Reachable input classes** — what real data and real usage in this repository and in an adopter's can produce, and which this task must handle correctly:

1. **Concurrent appends from several processes on one host to one `<loop_id>.jsonl`.** The Stage-0 case this task exists for: a Tier-1 verification fan-out emitting one span per role instance, plus the existing single-writer traffic (`bin/close-out.sh`, the orchestrator's own rows).
2. **Rows of unbounded length.** `--error` carries a captured error message and `--label` free hand-off text; both are measurably unbounded in the current writer, and the corpus's ordinary rows sit around 290 bytes, which is a sample rather than a bound.
3. **A runs file containing rows this writer did not produce.** Hand edits, rows from an older writer (no `provider`/`effort`/`adapter`/`instance` keys), rows copied in from another machine — including rows whose `seq` sits at the nine-digit ceiling and rows whose `seq` is not a parseable integer. The file is plain text in a directory an operator can edit.
4. **Several `run_id`s interleaved in one file.** Measured in the machine-local corpus: many runs share `shell-team.jsonl`, and the last line of the file routinely belongs to a different run than the one a caller is writing.
5. **A pre-existing lock artifact left by a dead process.** A writer killed with `SIGKILL` leaves the directory; every later write to that file must then refuse in a way an operator can act on.
6. **Hosts without `flock`, and hosts whose `sleep` rejects a fractional argument.** The repository's own development host is macOS with bash 3.2; adopters run these scripts in repositories this project knows nothing about.
7. **A first append, where neither the runs directory nor the file exists yet.**
8. **Callers that discard the exit status.** Every measured caller wraps the invocation in `|| true` or is prompt text instructing the same.

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect, named concretely so the boundary is falsifiable:

- **Cross-host or network-filesystem concurrency.** Two machines appending to one file over NFS or SMB, where `mkdir`'s atomicity guarantee does not hold as stated. Declined outright; the lock's correctness is claimed for a POSIX local filesystem only.
- **Concurrency degrees far beyond one orchestrator session's reach** — hundreds or thousands of simultaneous writers, or a sustained write rate. The fixture floors (8 writers × 20 rows) bound what is protected; escalating that ladder further is not a defect this spec accepts.
- **Rows engineered to exceed `ARG_MAX`** or the host's per-argument size limit. A row too large to pass as a command-line argument never reaches the append path at all.
- **Adversarial tampering with the lock while it is held** — another process renaming the lock directory, changing its permissions mid-run, or replacing it with a symlink. The never-steal rule and `rmdir`'s refusal to delete a non-empty directory are the whole of the defence; a hostile local process with write access to the runs directory is outside this task's threat model.
- **Crash consistency and durability.** Power loss, a filesystem that reorders or discards a completed write, or any claim that a returned exit 0 means the bytes survived a reboot. No `fsync` is added and none is claimed.
- **Multi-file or cross-`loop_id` transactions.** Two files updated as one unit; the lock is per file, deliberately.
- **A corpus large enough for the `--seq auto` scan's O(file) cost to matter.** Rotation and compaction are declared non-goals; the cost is disclosed rather than bounded, and a corpus that grows until the scan is slow is a future task's problem, not a defect in this one.
