## Problem

T-1094's **AC10** was originally a live execution of the shipped trial-adoption recipe in a throwaway git repository. Two consecutive spec-review rounds each landed an independently-new Major on it, its pre-commitment's Droppable-3rd fired, and the criterion was reduced to a static assertion over the shipped section's command *text* — with the behavioral execution deferred to issue #348 and both rounds' findings carried forward as that unit's requirement list. What ships today therefore proves that the recipe's words are present, not that the recipe works; and the three specific ways it could stop working — the legacy layout, a machine whose global excludes hide the base dir, and a regression dropping the second `git add` argument — are exactly the ways nothing currently watches. The retro's own framing of what is missing is the shape this task builds: "the execution obligation is already discharged once by qa-verifier's own recipe run and mainly needs a REPEATABLE form, not a NEW one."

**Its own suite, not an extension of `tests/team-init/run.sh`.** The subject under test is the *documented recipe*, not one script: the recipe spans `team-init.sh`, `team-paths.sh`, four git commands and a documented remedy, and a CI failure should name the recipe rather than the scaffolder. The suite also has to establish a scratch global-config scope and deliberately hostile global excludes, which co-located in an existing suite would perturb fixtures that have nothing to do with excludes. `tests/team-init/run.sh` is left at its existing scope, proven only to still pass unperturbed.

**The recipe is extracted from the shipped file, never retyped.** A transcribed copy drifts from the doc and then verifies a fiction — the precise failure the static half already covers. A separate, directly-invocable extractor (`tests/trial-recipe/extract-recipe.sh`) locates the section by its own `^## ` heading and prints one documented block's command lines. Extraction is **fail closed**: a heading that does not match, a fence count other than the shipped one, a block shorter than its documented floor, or a prose flag-span that is not found exactly once is an error with a diagnosis on stderr — never a silent zero-command pass. **The flag-span is defined as the invocation-form string `team-init.sh --trial-branch ` — the span the extractor pulls the one-step command from — and it is that string, not the bare token `--trial-branch`, that must be found exactly once in the section; the bare token legitimately occurs on more than one line, because the section's own intro paragraph mentions the flag descriptively before the one-step variant introduces it, and that descriptive mention is not an extraction target.** The substitution list applied to extracted text is **closed** and has exactly three members: `<integration-branch>` becomes the fixture repository's own initial branch name, captured before the trial branch exists; the bare command names `team-init.sh` and `team-paths.sh` become absolute paths into this checkout's `bin/`, because an adopter receives them on `PATH` from the loaded plugin and a fixture cannot. Nothing else in the extracted text is rewritten, and any line still carrying an unsubstituted `<…>` placeholder after substitution is an error. Git identity for the extracted `git commit` line is supplied through the environment, never by rewriting the command.

**Both documented paths are exercised, because both are documented.** The extracted setup fence *is* the manual two-command path. The one-step flag form named in the same section's prose is a second fixture, asserted to reach the same end state as the first — same branch, same scaffold, same two committed paths. Neither is a copy of the other's assertions: the end states are compared to each other.

**Both layouts, with the marker that actually fires.** The default fixture is a plain throwaway repository. The legacy fixture is seeded by copying `templates/shell-team.contract.yaml` to `tasks/loops/shell-team.contract.yaml` — the contract **file**, because the resolver keys on that file and a fixture seeding only a bare `tasks/loops/` directory resolves to the *default* layout, under which every legacy assertion would pass vacuously. That vacuity is not left as a comment: a third fixture seeded with the bare directory alone is asserted to resolve **identically** to the default fixture, which is the control proving the marker's teeth. Requirement 1's resolved-path **difference** is asserted by comparing the two fixtures' own `team-paths.sh --get` **outputs**, with no path literal typed into the assertion, together with the inequality control that the outputs genuinely differ and the structural relation — specs under base in one arm, outside it in the other — derived at run time.

**Requirement 2, in two halves.** Hermeticity first: the suite establishes its own scratch global-config scope so the operator's real global excludes cannot reach any fixture, and the mechanism is chosen by **feature detection rather than by asserting a git version** — a scratch `GIT_CONFIG_GLOBAL` where git honors it, a redirected `HOME` plus `XDG_CONFIG_HOME` otherwise — with a probe that measures whether the planted scope is actually visible to git inside a fixture. If neither mechanism can be established the suite exits non-zero naming the probe that failed; it never proceeds unisolated and never skips. The adverse half then plants, in that same scope, a global excludes file hiding the resolved base dir, and asserts three things in order: the plant genuinely has teeth (`git check-ignore` reports the base dir ignored); the recipe's plain `git add` line **refuses** — non-zero exit captured with the suite's `set +e` idiom **and** the index asserted byte-unchanged, because a refusal that staged something is not the documented behavior and an exit code alone is not the claim; and then the shipped section's own remedy, the `git add -f` form carrying both resolver arguments, **succeeds**, leaving both resolved paths staged. That is what turns the shipped remedy from a promise into a lock.

**Requirement 3, with its negative control, and with its teeth located honestly.** After the recipe's commit step, a tracked blob is asserted to exist under **each** resolved path — base and specs, separately resolved — in both layouts. In the **default** layout this criterion has no teeth by construction and the spec says so rather than implying coverage it does not have: `--get specs` resolves *under* `--get base`, so a single `git add` argument already covers both. The regression the requirement names is therefore locked in the **legacy** layout, where `docs/specs` sits outside `tasks`: a control fixture running the one-argument form is asserted to leave the resolved specs path **untracked**, proving the assertion can fail.

**Teardown is executed, not described.** The extracted teardown fence runs with `<integration-branch>` substituted by the fixture's own captured initial branch: the switch succeeds, `git branch -d` **declines** (the section's own prose claim, asserted explicitly rather than extracted, since it appears in prose and not in the fence), `git branch -D` succeeds, the resolved base dir is gone from the working tree, and the trial branch's tip commit is unreachable from the integration branch.

**Verbatim traceability into the suite itself.** The three requirements are transcribed into the suite's own header, and each is discharged by named cases whose `PASS` tokens identify which requirement they answer — so a reader of a CI failure meets the floor without opening this spec, and a future edit that quietly removes a requirement's coverage removes a named token.

## Non-goals

- **No `bin/` change of any kind**, including a new helper. The extractor lives under `tests/`. If a `bin/` change becomes necessary, these Non-goals are re-frozen first and the arm-A tamper discipline applies.
- **No prose edit to `docs/adopting.md` or `docs/adopting.ja.md`**, including adding machine-friendly anchors for the extractor. The recipe is this task's fixed input; if it cannot be extracted as shipped, the extraction layer drops (Droppable-1st) — the doc does not bend.
- **No re-litigation of T-1094's static `AC10`**, and no re-derivation of the three requirements from anything other than `.shell-team/reviews/T-1094.md`.
- **No loop run and no network operation inside any fixture** — no `push`, no `fetch`, no clone, no `gh`, no remote of any kind — and no write outside the suite's own `$TMPDIR`-backed roots.
- **No global git configuration is written or modified.** Identity is passed per command or through the environment; the global scope the suite establishes is a scratch one it creates and removes.
- **No widening of `tests/team-init/run.sh`'s existing scope.** It is run to prove it still passes unperturbed, and not edited.
- **No `CHANGELOG` entry and no release step** — this train's convention is a release-prep entry, and the sprint stacks pull requests to a batch GO.
- **No re-freezing or widening of any merged scope lock.** Any staleness the two-arm diff produces in a merge-point-scoped criterion is disclosed in `## Blast radius`, never chased.
- **No population figure written by hand.** The recipe's own command inventory is produced by `bin/derive-populations.sh` and embedded verbatim beside its `- reproduce:` line (**AC17**).
