# Run telemetry gains event rows alongside spans

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1011
**Source**: GitHub issue #77 — **Part 1 only** (Part 2 = `bin/gen-loop-replay.sh` + `templates/loop-replay.html`, Part 3 = README/docs wiring; both are T-1012)
**Base**: `develop` @ `08ebaea`
**Branch**: `feature/77-part1-telemetry-events`

## Problem

Run telemetry records only one thing: a span per sub-agent call. Everything that happens *between* the calls — the hand-off from one phase to the next, a route-back to the engineer, a gate's verdict, a human stop or GO, a release — leaves no row, so a run log cannot be read back as a sequence of what the loop did. It can be read back only as a bag of agent invocations with token counts. Issue #77's replay view (Part 2) needs the transitions, not just the calls, and no amount of post-hoc inference over span rows reconstructs "a human stopped the loop here". The row shape has to exist first.

The verbatim Part 1 scope from issue #77, which is canon for this task: *extend run telemetry with event rows. A second row shape alongside spans — e.g. `--event handoff|rework|gate|human|release` with `from`/`to`/`label` — written by the orchestrator at the same points it already logs spans (the `run` skill's telemetry section grows the matching instructions). `check-run.sh` learns the new shape fail-closed; existing span-only files stay valid (old runs remain lintable and replayable with degraded fidelity).*

## Goal

<!-- BEGIN intent-block: T-1011 -->

`bin/log-run.sh` can write a second row shape — an **event row** — into the same `<loop_id>.jsonl` it already writes span rows to, under a frozen 9-key schema and a closed 5-member event vocabulary. `bin/check-run.sh` validates both shapes, discriminating them per line, and rejects every malformed, unknown-vocabulary, or shape-mixed event row fail-closed with a reason that names what was wrong. Every telemetry file written before this task stays valid, byte-for-byte identical in how it lints and how it rolls up. The two scripts that read raw telemetry rows — `bin/rollup-runs.sh` and `bin/cluster-failures.sh` — skip event rows, so their output for a file containing event rows is byte-identical to their output for the same file with the event rows deleted. `skills/run/SKILL.md`'s Telemetry section instructs the orchestrator when to emit each event id, mapped to the points where it already emits spans.

### Settled decisions

Each decision is resolved here. Nothing below is left to implementation judgment.

- **D1 — event rows go in the SAME `<loop_id>.jsonl`, and both raw-row consumers learn to skip them.** The consumer inventory is complete and measured, not assumed: `grep -c 'field_str' bin/*.sh` returns exactly two files — `bin/rollup-runs.sh` (11 hits) and `bin/cluster-failures.sh` (5 hits) — and they are the only scripts in `bin/` that parse telemetry rows. `bin/rollup-track.sh` consumes `rollup-runs.sh`'s *stdout* (`bin/rollup-track.sh:121`, `SUMMARY="$(bash "$ROLLUP_RUNS" …)"`), never a row; `bin/retro-inputs.sh` only counts files with a `.jsonl` suffix in the runs dir (`bin/retro-inputs.sh:455`, `report_dir_input run-telemetry`), never a row. Both are therefore out of D1's blast radius, by measurement.
  - **Rejected — a sidecar `<loop_id>.events.jsonl` with the consumers untouched.** It does not work, and the reason is measured rather than aesthetic: `agents/triage-orchestrator.md` documents invoking both consumers as `rollup-runs.sh <runs>/*.jsonl` and `cluster-failures.sh <runs>/*.jsonl` (lines 33, 52, and the genericity rule at line 76). A `.jsonl`-suffixed sidecar is swept into that glob and corrupts both consumers exactly as if it had been in the same file — the sidecar buys nothing and costs a second file, a second lint entry point, and a two-file merge in Part 2's replay, which needs one totally-ordered stream.
  - **Rejected — the implicit-skip variant: give event rows no `run_id`, `status` or `verdict` so the existing consumers ignore them untouched.** `bin/rollup-runs.sh:77` already skips a row with no extractable `run_id`, and `bin/cluster-failures.sh:114` already skips a row with neither a failing `status` nor a failing `verdict`, so this would in fact work today with zero consumer edits. It is rejected because an event row must carry `run_id` to be groupable at all (Part 2's replay groups by run), and because a skip that happens by accident of field absence is precisely the silent-corruption class this decision exists to eliminate — the next field added to the event schema would silently re-break both consumers.
  - **The skip rule is fail-safe, and its wording is frozen**: a consumer treats a row as a span when the row's `kind` value is absent or `span`, and skips it otherwise — including an *unknown* `kind` value. An unknown `kind` is by definition not a span, so counting it would be the corruption; reporting it is `check-run.sh`'s job, not the reporters'.
  - **No new output from either consumer.** Neither script gains an `events: N` line or any other new output. Rejected alternative named: reporting event counts in the roll-up. `bin/rollup-track.sh` commits `rollup-runs.sh`'s stdout verbatim into a git-tracked artifact and `bin/consolidate-proposals.sh` parses that stdout's `run <id>` tokens — a new line changes a committed artifact's format and a downstream parser's input for no Part 1 benefit.
- **D2 — the discriminator is a `kind` key, and its ABSENCE means span.** `kind` is **not** added to the span row: a span row written after this task is byte-identical, key-for-key and order-for-order, to one written before it (17 keys, no `kind`). Adding `kind` to spans would invalidate every existing file the moment it became a required key, and issue #77's own Part 1 boundary excludes changing the span schema.
  - The `kind` enum is closed: `span | event`. Absent ⇒ span. `"kind":"span"` ⇒ span, validated identically to a `kind`-less row (the vocabulary word for the shape must not be illegal to write). Any other value ⇒ violation. `"kind":null` or an unquoted `kind` ⇒ violation, mirroring the existing `status must be a quoted enum value` rule.
  - **Shape mixing is a violation in both directions.** An event row must not carry any of the **13 span-only keys** (`span`, `phase`, `iteration`, `attempt`, `status`, `model`, `tokens`, `tool_uses`, `duration_ms`, `verdict`, `usd`, `error`, `parent_span_id`) — the full span key set minus the four shared keys. A span row must not carry the `event` key. The reverse direction checks `event` only, not `from`/`to`/`label`: `event` is the discriminator's partner key and can mean nothing else, whereas `from`/`to`/`label` are generic enough that a future span-side extension could legitimately claim one, and they fall under the tolerated-unknown-key rule instead.
  - **Key detection for every new event-side check is anchored to a JSON-object boundary** — the key token must be preceded by `{` or `,`, exactly as `bin/rollup-runs.sh:60`'s `field_str` already does and for the reason stated there. The existing span-side `REQUIRED_KEYS` presence test is left byte-identical: changing how span rows are detected is a span-side behavior change, which is out of scope.
- **D3 — the vocabulary and row schema are frozen exactly as issue #77 proposes them.** Event ids, closed enum, no additions: `handoff`, `rework`, `gate`, `human`, `release`. The event row is exactly these 9 keys, in this order:

  ```
  {"loop_id":"<L>","run_id":"<R>","seq":<N>,"ts":"<ISO-8601 UTC>","kind":"event","event":"<id>","from":<string|null>,"to":<string|null>,"label":<string|null>}
  ```

  `loop_id`, `run_id`, `seq`, `ts` are **shared with the span row** and carry the same meaning, and `seq` is **one monotonic counter per run, shared across spans and events**, so the rows of a run form a total order — which is what Part 2's replay requires. `from` and `to` are free-form phase-or-agent identifiers (no enum: an adopter's phase and agent names are not a closed set). `label` is free-form text.

  Per-event-id requiredness, frozen. "Required" means present and non-null; a required field that is absent, `null`, or an empty string is a violation in the checker and a usage error in the writer.

  | `event` | `from` | `to` | `label` | meaning |
  |---|---|---|---|---|
  | `handoff` | **required** — phase/agent handing off | **required** — phase/agent receiving | nullable | a forward phase transition |
  | `rework` | **required** — phase/agent that rejected | **required** — phase/agent routed back to | **required** — the flag/verdict that caused it | a backward route-back |
  | `gate` | **required** — the gate's own phase/agent | nullable | **required** — the verdict/flag | a gate judgment |
  | `human` | nullable | nullable | **required** — the human action | a human intervened |
  | `release` | nullable | nullable | nullable | a release / close-out point |

  Reasons for the three `label`-required rows: a `gate` with no verdict, a `rework` with no cause, and a `human` with no action each record that something happened without recording what — the field that carries the whole informational content of the event. `release` needs none: the id is the information.
- **D4 — what `check-run.sh` enforces and what it tolerates, enumerated.** Enforced, each exit 1 with a reason line; the reason wording is frozen so it is greppable:
  - `invalid event '<v>' (handoff|rework|gate|human|release)` — an `event` value outside the enum, including a near-miss spelling.
  - `event must be a quoted enum value` — `event` present but not a quoted string.
  - `missing required event key(s): <list>` — any of `loop_id`, `run_id`, `seq`, `ts`, `kind`, `event` absent from an event row. Deliberately distinct wording from the span side's `missing required key(s):`.
  - `event '<id>' requires non-null <field>` — a per-type required field absent or `null`.
  - `event row carries span-only key(s): <list>` and `span row carries event-only key: event` — the two mixing directions.
  - `invalid kind '<v>' (span|event)` and `kind must be a quoted enum value`.
  Tolerated, and a finding against any of these is out of contract: unknown extra keys on an event row (forward compatibility) provided they are not span-only keys; nullable fields either absent or explicitly `null`; arbitrary text in `label`/`from`/`to`, including machine tokens, non-ASCII prose, and text that mimics JSON; trailing whitespace; CRLF; blank lines; no trailing newline. Exit codes are unchanged: 0 clean, 1 violation(s), 2 unreadable file / usage error.
  - **Structure**: `REQUIRED_KEYS` stays the span array, byte-identical; the event side gets its own required-key set, its own id enum, and the span-only key list. `lint_line` runs the shape-independent checks first (object shape, quote balance — a malformed line still short-circuits exactly as today), then discriminates the shape, then branches. The span branch is the existing code, unchanged; the event branch never runs the span required-key or `status`/`verdict` checks (an event row is not a defective span and must not be reported as one).
- **D5 — the writer's CLI, and its fail-closed boundary.** `log-run.sh <loop_id> --event <id> --run-id R --seq K [--from X] [--to Y] [--label L]`. `--event` selects event mode; its absence leaves span mode byte-identical in behavior.
  - Event mode requires `<loop_id>`, `--run-id`, `--seq`, `--event`, plus the per-type flags of D3's table. `--seq` is validated by the same non-negative-integer rule as the span side.
  - **All 13 span-only flags are forbidden in event mode** (`--span`, `--phase`, `--iteration`, `--attempt`, `--status`, `--model`, `--tokens`, `--tool-uses`, `--duration-ms`, `--verdict`, `--usd`, `--error`, `--parent-span-id`) — a usage error, exit 2, **nothing written**. This mirrors D2's mixing rule 1:1 rather than deferring the rejection to the post-write lint. `--event` together with `--span` is called out by name with the frozen message `--event and --span are mutually exclusive`.
  - `--from` / `--to` / `--label` are forbidden in span mode: exit 2, nothing written.
  - An unknown `--event` value, and an empty-string value for a per-type required field, are usage errors: exit 2, nothing written. An empty string is treated exactly as absent, because `jstr` renders it as `null`.
  - The post-write self-check is unchanged in mechanism and must accept the new shape (`check-run.sh --line` on the row just written).
  - **Version skew is confirmed and re-affirmed, not redesigned**: a new `log-run.sh` writing an event row against an old `check-run.sh` gets a lint failure, so `log-run.sh` exits 1 with the row already on disk and never rolled back. That is the behavior its header already documents for every self-check failure, every in-repo caller wraps the call in `|| true`, and telemetry is best-effort by contract — so this needs no new mechanism. It must be **documented in `log-run.sh`'s header** rather than left for someone to rediscover. The reverse skew (old writer, new checker) is inert: span rows are still valid.
- **D6 — `skills/run/SKILL.md`'s Telemetry section is the only prose that changes, and the emission points are mapped to the existing span points.** `handoff` at each phase transition (the step 1→2→(3)→4→5→6→7 boundaries, where the board flag advances); `rework` when a QA `FAIL` or a Codex `REQUEST_CHANGES` routes back to `engineer` (steps 5 and 6), with the causing verdict as the label; `gate` at each gate judgment — the QA verdict, the Codex verdict, and the fail-closed pre-Validate seam gates; `human` at every human stop, GO, interruption or correction, using the existing `templates/prompt-blocks/interventions-classes.md` class slugs as the recommended label vocabulary; `release` at close-out. The `|| true` best-effort discipline and the shared-`seq` rule are stated in the same section, consistent with the span instructions above them.
  - **Rejected — per-step reminders sprinkled through steps 1–7.** One instruction copied into seven places is the drift surface `CLAUDE.md` warns about; the Telemetry section is where the span instruction already lives and where a reader already looks.
- **D7 — the line-shape discrimination stays a flat, single-line scan; no grammar-aware tool is adopted.** The question was asked explicitly before the design was settled, because this task extends a verification mechanism. Two grounds: (i) `CLAUDE.md`'s `bin/` contract is pure bash and zero-dependency, so `jq`/python is not available to a distributed plugin running in an adopter's repository; (ii) the invariant here does **not** require grammar-level state — every check is a per-line key-presence or key-value test, and `log-run.sh` is the single canonical writer whose `jesc` guarantees no bare `"` can appear inside a value, so a boundary-anchored key token cannot occur inside a string. The existing unbalanced-quote rule catches the hand-edit truncation class. The residual — a deliberately hand-forged line that fakes an escape sequence — is declared out of scope in the Input space below rather than left implicit.
- **D8 — no new test directory, no new `bin/` script, and no CI workflow change.** The new cases extend `tests/check-run/run.sh` (which already drives both `log-run.sh` and `check-run.sh`), `tests/rollup-runs/run.sh`, `tests/cluster-failures/run.sh` and `tests/machine-tokens/run.sh` — all four are already in `.github/workflows/check-handoff.yml`'s shellcheck argument list and already have their own `run:` step, so the two-coupled-lists hazard does not arise and the workflow file stays byte-identical. The event id vocabulary is a new machine vocabulary and is asserted in `tests/machine-tokens/run.sh` against the files that consume it, the same way every other token group there is.
  - **Parallel telemetry-instruction surfaces, dispositioned rather than discovered later.** Three files instruct an orchestrator to call `log-run.sh`: `skills/run/SKILL.md` (changes — issue #77 names it), `skills/goal/SKILL.md` (**no change**: the goal loop has its own phase vocabulary and defines no human/release points; its writer gains the capability regardless and nothing there breaks), `skills/review-response/SKILL.md` (**no change**: it delegates to the `run` skill's Telemetry section by reference and defines no gates of its own). Both untouched files are locked as a protected invariant below, so "you missed a parallel surface" is answered by the frozen intent instead of costing a round.

## Input space

**Reachable input classes** — what real usage produces, and the implementation must handle correctly:

- Span-only telemetry files written by any previous version of `log-run.sh`: this repository's own history and every adopter's existing runs dir. They must lint identically and roll up identically.
- Mixed files written by the new `log-run.sh`: span rows and event rows interleaved in one `<loop_id>.jsonl`, in ascending shared `seq` order, with all five event ids present, appended across many separate process invocations.
- Files containing only event rows and no span row, and files containing only span rows — both reachable, because a run can be interrupted at any point.
- Every field shape the writer can produce: each nullable field present as explicit `null`; `from`/`to` carrying arbitrary phase or agent identifiers, including an adopter's own names; `label` carrying a machine token (`PASS`, `FAIL`, `APPROVE`, `REQUEST_CHANGES`, `REWORK`, a `STOP:<reason>` string), an interventions class slug, prose in the operator's language, embedded double quotes, backslashes, and tabs/CR/LF (which `jesc` collapses).
- Hand-edited and corrupted files, which is why the checker exists: a truncated event row; an unknown event id; a near-miss id spelling (`Handoff`, `hand-off`, `handoffs`, a leading or trailing space inside the quoted value, the empty value); a required field absent or explicitly `null`; a row mixing the two shapes in either direction; `"kind":"span"`, `"kind":"bogus"`, `"kind":null`, an unquoted `kind`; an unknown extra key.
- CRLF line endings, trailing whitespace, blank lines, and a missing final newline — from a Windows editor or a CRLF-normalising tool.
- Empty files, and unreadable / non-existent / dangling-symlink paths (exit 2). `--line` mode with either shape and with no value at all.
- Multiple files passed together, including via the `<runs>/*.jsonl` glob that `agents/triage-orchestrator.md` documents, and the same `run_id` split across two files.
- Both consumers, plus `rollup-track.sh`, run over every one of the above.

**Out-of-scope synthetic extremes** — declined deliberately; a finding grounded only in one of these is out of contract:

- A deliberately hand-forged line that fakes JSON escaping to make a boundary-anchored key token appear inside a string value. `log-run.sh` is the single canonical writer and cannot produce one; the existing unbalanced-quote rule catches the truncation class; producing a *correct diagnosis* for a hand-crafted escape-forgery is not protected (D7's stated residual).
- Full JSON-grammar conformance beyond the structural lint: nested objects or arrays as field values, `\uXXXX` escapes, exponent-form or negative numbers, duplicate keys within one object, whitespace between a key and its colon. `check-run.sh` is a structural lint by its own documented design and this task does not turn it into a parser.
- Non-UTF-8 encodings (UTF-16, Shift_JIS, Latin-1 byte soup) and binary content in a `.jsonl` file. Bytes are read and a structural violation is reported; a correct diagnosis is not protected.
- Pathological scale: millions of rows, multi-gigabyte files, a single line megabytes long, thousands of distinct `run_id`s. Ever-larger sizes are not an escalating finding class.
- Concurrent writers appending to the same file and producing an interleaved partial line, and any file-locking guarantee.
- Cross-line properties: duplicate `seq`, non-monotonic `seq`, a `to` value naming a phase no span ever visited, an event with no surrounding spans. `check-run.sh` holds no cross-line state today and gains none (see Non-goals).
- Unicode whitespace lookalikes (NBSP, ideographic space, zero-width joiner) or bidi control characters inside a `kind` or `event` value. The enum comparison is byte-exact; anything else is an invalid value, full stop.
- Any second telemetry file, sidecar, index, or directory layout change.
