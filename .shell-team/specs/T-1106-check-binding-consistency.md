## Problem

`bin/check-binding.sh --verify` validates a lock's opening `binding-lock <version>` line, its `binding-lock-end` terminator, that exactly one `config-path` line is present and that exactly one well-formed `binding-hash` line is present (`read_lock()` at `:428-466`; the four assertions at `:439-444`, `:445-446`, `:462-463`, `:464-465`). The lines between those header fields and the terminator — the `schema`/`bound` rows dumped for a human reader — are **never read into anything**. The hash comparison at `:484-487` re-derives the canonical form from the *config* (`canonical_hash()` at `:423-425`), so a lock whose embedded dump has been replaced with garbage still verifies. `--verify`'s soundness is unaffected because the hash is authoritative; what is unsound is the lock's self-description, and a human or a future consumer reading the embedded dump directly is trusting bytes nothing checks (issue #219).

Separately, three of the checker's flags accept an explicit empty value and reinterpret it silently. Measured today, per flag: `--config ""` falls back to `<base>/binding.conf` (set `:200`, consumed at `:492`); `--adapters ""` falls back to the shipped registry (set `:201`, consumed at `:233`); `--verify --lock ""` and `--verify --config ""` are refused `usage` but with a message indistinguishable from omitting the flag (`:214`, `:215`); and `--lock ""` **without** `--verify` is silently accepted and ignored, because `[ -z "$LOCK_ARG" ]` at `:217` passes, whereas `--lock somepath` without `--verify` is refused. A scripted caller composing `--config "$VAR"` with an accidentally-empty variable gets a verdict about a different file than it asked about (issue #220), from a checker whose posture is fail-closed everywhere else.

Third, `--adapters PATH` is a testing affordance that lets the fixture suite exercise registry-defect refusals without touching the shipped `templates/binding-adapters.txt`; a production caller forwarding it would reopen the adapter trust boundary T-1054's blocker fix closed (issue #221). That issue predicted the residue would sit in T-1056's loop-integration wiring; measured today it does not. `bin/check-liveness.sh` contains zero occurrences of the string `check-binding` (measured by a whole-repository content search for `check-binding`, whose file list does not include that path; the only match under `tests/check-liveness/` is a comment at `:9`). The one production consumer is `bin/resolve-executor.sh:329`, which composes `--config "$CONFIG_PATH" --print-binding` and forwards nothing, and that file plus `tests/resolve-executor/run.sh` are already pinned at zero occurrences by `.shell-team/specs/T-1057-loop-integration.md` **AC3**'s check line at `:107`. What remains is narrower and different from the issue's prediction, and narrower again than the Routing Map credited: `.shell-team/specs/T-1055-adapter-envelope.md` **AC12** (`:162-163`) already asserts, over the glob `bin/*.sh` plus `skills/*/SKILL.md` plus `agents/*.md`, that the flag appears in **exactly one** file. The genuine residue is therefore not "nothing asserts the property" but **where the assertion lives**: it lives only in two merged specs' frozen `- check:` lines, which run when someone runs those specs' criteria, and in **no** fixture suite and **no** CI step. A future `bin/` script forwarding the flag reddens a criterion nobody re-runs on an ordinary pull request. Moving that property into `tests/check-binding/run.sh` — which CI executes on every pull request — is #221's remaining work.

## Non-goals

- **No hostile-forger defence.** The threat model at `bin/check-binding.sh:97-103` names the operator and the working directory as TRUSTED, and this task does not change it. The body cross-check catches an **accident** — a hand edit, a truncated write, a copy-paste of the wrong dump — and by construction cannot catch a forger who recomputes the body and its hash together.
