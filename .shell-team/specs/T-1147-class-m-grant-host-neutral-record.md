## Problem

`docs/tuning-oversight.md` tells an adopter that a standing class-M (mechanics repair) re-freeze grant is recorded "in your own checkout's `CLAUDE.local.md` (never in a shipped file)". That file is a Claude Code instruction surface: a Claude Code host loads it into the orchestrating session, and a Codex CLI host does not. On a genuine Codex-only host the Codex runbook's pointer (T-1139) therefore names a knob whose only documented home that host never reads, so the grant is a dead letter there and every class-M re-freeze costs one human GO — it fails safe, but the capability the guide describes is unreachable. The fix has to be a surface **both** hosts' orchestrators reach the same way, because this project cannot assert from its own checkout what a Codex CLI orchestrator loads as instruction.

**Design decisions, numbered, with the ground each was decided on.**

**D-1 — the grant's home is a sibling record under the base dir, not a row in `<base>/oversight.conf`.** Extending the oversight declaration was measured and rejected: `bin/check-oversight.sh:311`–`:313` refuses `unparseable-line` at exit 1 for any line whose first field is not `schema`, `profile` or `seam`, so a grant row authored for a newer plugin and read by an older installed one would refuse the freeze at `specify-seam` and refuse `bin/close-out.sh` at `pre-merge`. That is fail-closed in the wrong direction: a mixed-version adopter would be blocked from working rather than asked for a GO.

**D-2 — the grant's home is not a loop-contract field.** `budget.extension_ratifier` is the shipped prior art for an optional vocabulary-closed field, and it would be mixed-version-safe: `bin/check-contract.sh` carries zero occurrences of `unknown`, `unrecognis` or `unrecogniz`, so a newer field read by an older validator is ignored rather than refused. It is rejected on a different ground: the grant is a **per-repository** property, which is exactly what `docs/adopting.md:1101`–`:1103` already says about the oversight profile, while a contract is per-loop and this project ships three of them (`templates/shell-team.contract.yaml`, `templates/goal.contract.yaml`, `templates/loop-contract-template.yaml`), so one grant would have to be authored in each.

**D-3 — the three-way behaviour, which is the whole safety property.** *Absent* ⇒ no grant, byte-for-byte today's behaviour. *Malformed, out-of-vocabulary, unreadable, or a non-regular occupant* ⇒ the **class-M branch** is refused, never the freeze: the orchestrator falls back to the per-instance human GO and surfaces the refusal token in that escalation, so a typo costs a GO and a visible token rather than silence. *Conformant, declaring the grant* ⇒ the grant. No input resolves to a grant except a conformant declaration of one.

**D-4 — the reader's contract, because the consumer's branch condition is defined in terms of it.** `bin/check-refreeze-grant.sh --print-grant` prints exactly one line, `grant class-m` or `grant none`, on stdout at exit 0 and prints nothing to stdout on any non-zero exit; exit 1 is a content refusal (a malformed or out-of-vocabulary declaration) and exit 2 is an input that could not be evaluated at all (usage, a non-regular occupant, an unreadable file, a missing shipped default), each printing one classified token to stderr — the split `bin/check-oversight.sh:74`–`:95` already uses. The declaration path is resolved as `--config PATH`, else `--base DIR`, else `$TEAM_REFREEZE_GRANT_BASE`, else `bash <sibling>/team-paths.sh --get base`, with `<base>/refreeze-grant.conf` appended; `--base` and `--config` are testing affordances, mirroring `bin/check-oversight.sh:64`–`:71`.

**D-5 — the record's grammar is closed and never executed.** Blank lines and `#` comment lines are skipped, leading and trailing whitespace around a field does not change its meaning, and both LF and CRLF line endings are accepted — the same tolerances `bin/check-oversight.sh`'s own parser already applies at `:275`–`:279`. Exactly one `schema` line, first, with the only supported version `1`. Exactly one `grant` line whose value is closed over the pair `class-m` and `none`. Every other first field is a refusal. Values are bare tokens; the file is never sourced, evaluated as code, or executed — the contract `bin/check-oversight.sh:47`–`:48` already states for its own config.

**D-6 — the absent arm is answered by a shipped default file, not by a hardcoded string.** `templates/refreeze-grant-default.conf` declares `grant none` and is resolved from the reader's own installed directory, never from an adopter's working tree, and is parsed through the identical grammar — one grammar, one code path, and a diffable answer an adopter can read. This copies `templates/oversight-default.conf`'s shape member for member rather than inventing a second one.

**D-7 — the record is additive and never revokes.** A `grant none` record means "this file declares no grant", exactly as an absent file does; it does not revoke a grant an adopter recorded in `CLAUDE.local.md`. On a Claude Code host the instruction-file grant keeps working exactly as it does today, which is what makes this change backward compatible for every adopter already using one; an adopter who wants a single source of truth records the grant only in the host-neutral file. The class-M branch is authorized when **either** surface resolves a grant, and both surfaces are operator-authored by construction, so this widens no authority: what it does not do is let an absent or broken record be read as a grant.

**D-8 — mixed-version behaviour, in both directions.** A newer record read by an older installed plugin is simply never read, because no file shipped before this task names `refreeze-grant.conf` — pinned by **AC7** as a base-relative delta — so that adopter keeps the per-instance GO.
