# A benign post-hoc durability barrier observes, at each hand-off that claims durability, that the loop's own records actually persisted as blobs in a fixed commit

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1048
**Base**: `e2c8bd9` — relayed as this branch's branch point (the T-1047 tip this branch is stacked on). Every `git` anchor below resolves that literal, **not** `develop`, because T-1047's changes are already on this branch by construction.
**Branch**: `feature/1048-handoff-durability-barrier`

## Problem

The team loop hands off between phases via files committed to git. When a state file is silently gitignored — a stray `.gitignore` rule, a mis-resolved base dir — the "commit immediately" discipline becomes a no-op and the loop's memory is silently lost. Issue #167 asks that this never happen silently, and two prior designs failed to close it by *predicting* persistence from ignore rules at init time: rule evaluation can be fooled, and it is blind to a partial rule such as `.shell-team/*.md` that hides exactly one record while every other file in the directory keeps committing normally.

The two guards the loop has today cannot see this failure at all. Both are `git status --short` prose checks — one at the Implement→Validate seam, one as the pre-merge backstop — and an ignored file is invisible to `git status`, so in precisely the #167 case both return a clean all-clear. This task replaces prediction with **post-hoc observation**: at the hand-off, each required record is checked for actually being a blob in a fixed commit's tree, with the working file's content matching that blob. Where a rule-prediction returns a false all-clear, the observation returns the correct answer.

## Goal

<!-- BEGIN intent-block: T-1048 -->

A new checker `bin/check-durability.sh` answers one question at a hand-off: for a named phase and a named task, does every record the loop's own central record-set definition requires exist as a **blob in a fixed commit's tree**, with the working file's `git hash-object --path=<path>` matching that blob. All present and matching is `durable` (exit 0); any other outcome is a fail-closed `not-durable` verdict (exit 1) carrying a reason token from a closed set and a plain-language sentence naming the record and the ref; a checker that cannot evaluate its input at all is `usage` / `structural` (exit 2). The record set comes from a plugin-shipped registry the checker owns, never from `git status` or `git ls-files` — the ignored, untracked file at the heart of #167 is invisible to both. The fixed commit is supplied explicitly as `--ref`, never inferred from the current branch. An adopter may decline the observation by declaring `working-tree-only` in a tracked file under the resolved base dir, and the checker then says out loud that it skipped; the default is `tracked` and the check runs. The checker is wired into the two `skills/run/SKILL.md` seams that claim durability today and into `bin/close-out.sh`'s fail-closed gate ladder, alongside — never in place of — the two existing `git status --short` guards, which answer a different question. `bin/`, `tests/` and `.github/` gain exactly the new checker, its registry, its fixture suite, the close-out gate and the CI wiring, and nothing else.

**Threat model (verbatim from the design brief — load-bearing):** The threat model is this repo's trust model. The operator and the working directory are TRUSTED (repo `CLAUDE.md` security invariant). What we defend against is **accidents** (stray gitignore rules, mis-resolved base dirs), not a **hostile operator**. Hardening against hostile operators — environment-variable neutralization, shell-function override defense, `GIT_*` enumeration, exotic git object stores (`GIT_DIR` redirection, replace refs, clean-filter/LFS) — is **explicitly out of scope** and belongs to a separate hardening issue.

### Settled decisions

Each decision below is resolved; nothing here is left to implementation judgment.

- **DP1 — the central record-set definition is a plugin-shipped registry file `templates/durability-records.txt`, owned by the checker. The loop contract yaml is NOT extended.** Measured grounding: `.shell-team/loops/shell-team.contract.yaml` enumerates no records at all — its `scope:` and `report:` fields name them in prose, and in legacy-layout spellings (`tasks/todo.md`, `docs/specs/*`, `tasks/reviews/*`) that do not match the layout this repository resolves to. "Derived centrally from the phase contract" therefore cannot mean "parse that yaml as it stands". **Blast radius, stated because it is the reason for the choice.** Extending the yaml would pull in `bin/check-contract.sh`'s 8-element vocabulary, `tests/check-contract/`, and all three CI-linted templates (`templates/shell-team.contract.yaml`, `templates/loop-contract-template.yaml`, `templates/goal.contract.yaml`) — and, worse, every adopter already holds a *copy* of the contract dropped by `team-init`, so an adopter's existing copy would carry no records block and the checker would need an adopter-dependent fallback; a fail-closed checker whose record set silently degrades on older installs is the worst of both. The registry route's blast radius is confined to one new data file, the one checker that reads it, that checker's new suite, and the CI wiring: no existing script, template or adopter file changes. Precedent: `templates/prompt-blocks/registry.txt` is exactly this shape — plugin-shipped, checker-owned, whitespace-delimited, `#` comments — resolved by `bin/check-prompt-sync.sh` from its own script directory.
- **DP2 — the registry's row grammar is `<phase> <team-paths-key> <pattern>`, whitespace-delimited, `#` comments and blank lines skipped.** `<phase>` is drawn from the closed set `implement | pre-merge | close-out` — the three wiring sites this task has, not an open-ended list. `<team-paths-key>` is a key `bin/team-paths.sh --get` accepts. `<pattern>` is either the literal `-`, meaning the resolved key **is** the record path (a singleton such as the board), or a filename pattern containing the token `<task-id>`, resolved inside the key's directory. A pattern containing no glob metacharacter must resolve to exactly that one file; a pattern containing one must resolve to **exactly one** existing entry — zero is the `missing-working-file` verdict, two or more is `structural` (exit 2, ambiguous), never a silent pick. The shipped registry's rows are:

  | phase | key | pattern |
  |---|---|---|
  | `implement` | `todo` | `-` |
  | `implement` | `specs` | `<task-id>-*.md` |
  | `implement` | `provenance` | `<task-id>.md` |
  | `implement` | `interventions` | `<task-id>.md` |
  | `pre-merge` | `todo` `specs` `provenance` `interventions` | as above |
  | `pre-merge` | `reviews` | `<task-id>.md` |
  | `close-out` | `todo` `specs` `provenance` `interventions` `reviews` | as above |

  The `specs` row uses a glob because a spec file is named for its slug, not for its task id, and reading the path off the board line instead would put a second copy of `check-handoff.sh`'s line grammar inside this checker. The `reviews` row is absent from `implement` because no review record exists at that seam yet — that per-phase difference is the whole reason the phase column exists.
- **DP3 — the predicate, in three steps, each with its own verdict.** (1) The working file must exist and be a readable regular file; otherwise `missing-working-file`. (2) The record path must resolve to a blob in `<ref>`'s tree; absence is read from **empty `git ls-tree <ref> -- <path>` output** (or `git cat-file -e <ref>:<path>` exiting 128), **never** from `ls-tree`'s exit status, which is 0 for an absent path; otherwise `not-in-recorded-commit`. (3) `git hash-object --path=<path> <path>` must equal that blob OID; otherwise `uncommitted-change`. If `<ref>` resolves to no commit at all — the unborn-repository case — the whole run is `no-recorded-commit` before any record is examined.
- **DP4 — `git hash-object --path=<path>` is a benign-correctness choice, not a hardening measure.** `--path` makes git apply the attributes that path would have, so a working file that differs from its committed blob only by end-of-line normalization under a `text` gitattribute compares **equal** instead of producing a spurious `uncommitted-change`. `bin/check-intent.sh:353` and `bin/check-refreeze-class.sh:322-325` already use `git hash-object` in this repository; the `--path=` form is the one that makes a *working file versus committed blob* comparison correct. It is stated here explicitly because `--path=` also happens to engage clean filters and LFS, and a review finding framed as clean-filter or LFS **hardening** is out of scope by the Threat model and is descoped under DP10, not repaired inline.
- **DP5 — the fixed commit is an explicit `--ref` argument with no default and no inference.** B2 measured that `git branch --show-current` under a detached HEAD exits **0 with empty stdout** — a success-shaped wrong answer — while the expected branch tip stays resolvable through its explicit ref. Requiring `--ref` removes the inference rather than hardening it, and it makes every verdict line name the ref it was measured at. The checker never calls `git branch --show-current` and never calls `git symbolic-ref`.
- **DP6 — the output contract.** Success prints to stdout `check-durability: durable: <n> record(s) for phase <phase>, task <task-id>, observed in <ref>`. An explicit skip prints to stdout `check-durability: skipped: working-tree-only declared in <mode-file> — no durability observation was made`. Every failure prints to stderr a line beginning `check-durability: not-durable: <reason>: ` and ending `— this hand-off is not durable.`, where `<reason>` is from the closed set `no-recorded-commit | missing-working-file | not-in-recorded-commit | uncommitted-change | untracked-opt-out` and the sentence between them names the record path and the ref in plain language. Inability to evaluate prints `check-durability: usage: <message>` or `check-durability: structural: <message>` and exits 2, following `bin/check-provenance.sh`'s convention exactly.
- **DP7 — the opt-out lives in one adopter-owned tracked file, and the opt-out must itself be durable.** The mode file is `<base>/durability-mode`, where `<base>` is `bin/team-paths.sh --get base` — an existing key, so `bin/team-paths.sh` is not modified. Absent file means mode `tracked` and the check runs. Present, the first non-blank non-comment line must be exactly `tracked` or `working-tree-only`; any other content is `structural` (exit 2), never a silent default. A `working-tree-only` declaration is honored **only if the mode file itself resolves to a blob in `<ref>`'s tree**; an untracked mode file is refused with `untracked-opt-out`, because an untracked opt-out is precisely the silent-disable route this task exists to close. There is **no** git-config route and **no** environment-variable route: an environment variable would be both a hardening surface and a coercion of the adopter's environment.
- **DP8 — `--task` accepts `^T-[0-9]+$` only; `no-task` runs are out of scope.** A no-task run has no spec, provenance or review record to be durable by construction, and its interventions record is already covered by the existing T-1002 gate. Rejecting the shape is `usage` (exit 2).
- **DP9 — the two existing `git status --short` guards survive unchanged.** They answer "is anything uncommitted"; this checker answers "did this record persist". A record can be perfectly committed and still leave an uncommitted edit, and an ignored record leaves no `git status` trace at all. The durability call is added **alongside** each guard, and both original sentences stay in `skills/run/SKILL.md` byte-for-byte.
- **DP10 — pre-commitment, with a named drop order, fixed before the first review round.** (i) **Any** review finding framed as adversarial hardening — environment-variable neutralization, shell-function override defense, `GIT_*` enumeration, or exotic git object stores (`GIT_DIR` redirection, replace refs, clean-filter/LFS) — is descoped to the separate hardening issue and **never repaired inline**, whatever its severity label. (ii) If a **non-adversarial** same-class defect recurs across two consecutive rounds, the pre-decided drop order executes without reopening the design: the `working-tree-only` opt-out goes first (it is the droppable one because it is a convenience surface whose absence costs an adopter nothing but a passing check, while the core predicate is the whole point of #167), then the close-out wiring (a backstop behind a seam gate that already fired), retaining the core predicate at the single Implement→Validate seam. The dropped rounds' findings travel to the successor issue **as its requirement list**, not re-derived there.
- **DP11 — parallel-surface symmetry, decided site by site.** `skills/run/SKILL.md` step 4 (Implement→Validate) and step 7 (pre-merge backstop): **both** wired, because a one-sided landing would leave the seam the loop actually loses records at unguarded. `bin/close-out.sh`: wired, per the brief's "and at close-out". `skills/goal/SKILL.md`'s gate ladder: **not wired**, recorded rather than left silent — the goal loop is a separate contract with its own gate composition, and widening it is a decision this task does not take. `agents/qa-verifier.md`: **not applicable** — QA verifies a spec's acceptance criteria; this is an orchestrator seam gate, not a QA item. `.github/workflows/check-handoff.yml`: wired (suite step plus a dogfood step against this repository's own records).

## Non-goals

- **Hardening against a hostile operator, in any of its four named forms.** Out of scope by the Threat model above and routed to a **separate hardening issue, filed at close-out** (no number is invented here): (1) **environment-variable neutralization**; (2) **shell-function override defense**; (3) `GIT_*` **enumeration**; (4) **exotic git object stores** — `GIT_DIR` redirection, replace refs, and clean-filter/LFS behavior. A finding in any of these classes is descoped per DP10(i), not repaired inline.
- **Predicting persistence from ignore rules.** No `git check-ignore` call, no rule evaluation, no init-time prediction. The whole point of the reframe is that the observation is post-hoc.
- **Changing `bin/team-paths.sh`.** No new key; `base` already exists and the mode file hangs off it.
- **Changing `.shell-team/loops/shell-team.contract.yaml`, `bin/check-contract.sh`, `tests/check-contract/`, or any of the three CI-linted contract templates.** DP1's blast-radius decision.
- **Changing `bin/team-init.sh` or its suite.** The mode file's absence is a valid state (default `tracked`), so nothing needs scaffolding.
- **Replacing either existing `git status --short` guard**, or removing any existing gate from `bin/close-out.sh`.
- **Wiring `skills/goal/SKILL.md`, `agents/*`, or any adopter-facing document** (`README*`, `CONTRIBUTING.md`, `docs/`, `CHANGELOG*`). The checker's `--help` header is its documentation, as for every other `bin/` script; a documentation sweep is a separate decision.
- **Supporting `no-task` runs** (DP8), or any record set beyond the phases and keys DP2 fixes.
- **Any `.ja.md` counterpart.** Every file this task writes is agent-read or machine-read.

## Input space

**Reachable input classes** — what real usage of this loop can produce, and what the implementation must therefore handle correctly:

- **Layouts**: the default layout (`base=.shell-team`, `specs=.shell-team/specs`) and the legacy layout (`base=tasks`, `specs=docs/specs`), plus an explicit `$TEAM_RUN_BASE` override — the three rules `bin/team-paths.sh` already resolves.
- **Record states**, per record: committed and unchanged; committed and then modified in the working tree; present in the working tree but never committed because an ignore rule (whole-directory or partial, e.g. `.shell-team/*.md`) hid it; absent from the working tree entirely; and — for the `specs` glob — zero matches or two or more matches.
- **Refs and repository shapes**: a branch name, `HEAD`, and a full `refs/heads/<name>`; a detached HEAD; a linked worktree created by `git worktree add`; an unborn repository with zero commits.
- **Mode-file states**: absent; tracked declaring `tracked`; tracked declaring `working-tree-only`; present but untracked (ignored) declaring `working-tree-only`; present with content that is neither token; present with leading comment or blank lines.
- **Content encodings**: files whose working bytes differ from their committed blob only by end-of-line normalization under a `text` gitattribute — the Windows-checkout case DP4's `--path=` exists for. CRLF line endings in the mode file are in this class.
- **Task ids** matching `^T-[0-9]+$`, at three and four digits, including an id that is a prefix of another (`T-104` alongside `T-1048`) — the **hyphen** in the `<task-id>-*.md` pattern is what keeps those apart, since every spec file is named `T-NNN-<slug>.md` and `T-104-*.md` therefore cannot eat `T-1048-…`. Written without that hyphen the pattern separates nothing: `T-104*.md` matches nine files in this repository's own specs directory, this task's spec among them.
- **A task with more than one spec file.** Reachable and presently instanced: `T-1020` owns both `T-1020-lessons-supersede-sweep.md` and `T-1020-supersede-adjudication.md`, so DP2's ≥2-matches rule fires on this repository today and must be `structural`, never a silent pick of whichever the glob returned first.
- **Phases**: exactly the three the registry declares. A phase name outside that set is a reachable *caller* mistake and is a `usage` error, not a silent no-op.

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect, so that a finding escalating along any of these axes is descoped under DP10(i) rather than forward-fixed:

- **Hostile-operator manipulation of the git environment**: `GIT_DIR` / `GIT_OBJECT_DIRECTORY` / `GIT_INDEX_FILE` / `GIT_ALTERNATE_OBJECT_DIRECTORIES` redirection, `GIT_CONFIG_*` injection, `core.hooksPath` or alias trickery, a `git` shell function or a PATH-shadowing `git` binary, and any attempt to enumerate or neutralize the environment before invoking git.
- **Exotic object stores and content pipelines used adversarially**: replace refs, grafts, a gitlink/submodule standing in for a record path, and clean-filter or LFS configurations arranged so that a filtered hash agrees with a blob whose real content differs. DP4 uses `--path=` for eol correctness; making that comparison robust against an operator who *wants* it to lie is the hardening issue's problem.
- **Pathological path names**: embedded newlines, control characters or whitespace in a base dir or a record path. `bin/team-paths.sh` already rejects a base containing whitespace, and `^T-[0-9]+$` admits none, so no reachable record path carries any.
- **Scale and concurrency**: repositories with thousands of registry rows or records, deliberately corrupted object databases, a ref rewritten *while* the check runs, and a filesystem that changes a record between the working-file read and the hash computation.
- **`no-task` runs** (DP8) and any phase, key or pattern outside DP2's table.
