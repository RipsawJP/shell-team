# Codex host, slice 1: the Specify → Implement → Validate chain runs from a Codex CLI session on generated, single-source role agents

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1134

## Problem

The loop runs on exactly one host. Every dispatch in `skills/run/SKILL.md` names the Claude Code Agent tool, and the six roles exist only as `agents/*.md` files that only Claude Code discovers — so an operator working in a Codex CLI session cannot run the team at all, and the plugin's value is bound to one vendor's harness. The obvious way to unbind it is also the way that kills it: a second, Codex-shaped copy of the role prose, the board handling and the checkers, which then drifts from the first copy and doubles every future edit. The maintainer's constraint of 2026-09-06 is explicit that a Codex-specific copy of any of those three is not acceptable, so the question this task answers is whether a second host can be reached with **one** codebase.

## Goal

An operator running a Codex CLI session in an adopted repository can drive the loop's `pm-spec` → `engineer` → `qa-verifier` chain to `READY_FOR_REVIEW` with no Claude Code process anywhere in the dispatch, and the repository still holds exactly one copy of the role prose, the board handling and the checkers. ## Non-goals

- **Slice 2 in its entirety.** No Claude-backed reviewer on the Codex host, no telemetry conversion, and no both-gates operation from Codex. This slice stops at `READY_FOR_REVIEW`; `codex-reviewer`'s `APPROVE` is still produced on the Claude Code host, and the loop is not claimed to close from Codex alone.
- **No Codex-side agent for any role beyond adding a row.** `codex-reviewer`, `ui-designer`, `drift-evaluator`, `scrum-master` and `triage-orchestrator` get no generated agent here. The generator's role list is data-driven precisely so slice 2 adds a row rather than a mechanism.
- **No new manifest.** `.codex-plugin/plugin.json` is not created. Codex already resolves this plugin through the existing `.claude-plugin/plugin.json`, and a Codex plugin cannot ship a custom agent in any case, so a second manifest would buy nothing.
- **No change to the executor-binding layer.** `bin/resolve-executor.sh`, `bin/check-binding.sh`, `bin/check-adapter.sh`, an adopter's `binding.conf` and the `templates/adapters/*.txt` schemas are read and never edited. The generator is a new consumer of `--print-resolved`, not a change to it.
- **No enforcement claim about `sandbox_mode`.** The measurement in `## Assumptions` shows a child agent's declared `sandbox_mode` does not bound what it can write when the parent session runs `--sandbox workspace-write`. Nothing in this task claims otherwise, no criterion asserts enforcement, and the generated file and the documentation both say so in their own words. A role's `tools:` minimality is not enforceable through a generated TOML in this slice.
- **`agents/**` is not edited.** No role file gains Codex-specific prose, a host-conditional clause or a second variant. If a role's own text turns out to need a host qualifier, that is a finding to route back, not an edit to slip in — **AC6** makes the difference visible.
- **No change to `README.md` or `README.ja.md`.** The README's host claim is a release-facing statement; it moves with the `MINOR` that slice 2 cuts, not with an unversioned slice that ships the mechanism. `docs/adopting.md` is this task's adopter surface.
- **No new gate, status flag, board grammar or human gate.** No script gains a refusal condition other than the two new scripts' own; the board's flag enum, the freeze ritual and the human gate set are untouched.
- **No scope-lock or diff-scope-closure criterion, and no per-task full-population blast-radius sweep.** Under the operator-approved lightweight mode A2 the sprint runs one two-arm sweep at release; `## Blast radius` carries predictions until then. **AC6** is a protected-invariant negative criterion over one directory, not a scope-lock allow-list over the diff.
- No CHANGELOG entry, no version bump and no release step in this task.

## Pre-commitment

- **Never-dropped**: the generator (**AC1**, **AC3**, **AC4**), the sync checker's fail-closed behaviour (**AC2**), the per-host indirection in `skills/run/SKILL.md` together with its canonical block (**AC5**), and QA's live Codex run (**AC10**). Defeat of any one of these across two consecutive review rounds stops the task and returns it to planning rather than buying a third patch round — the operator-ratified ruling of 2026-09-06 (T-1121), cited here as an operator ruling and not as AI self-discipline.
- **Droppable-first**: any integration of the generator into `bin/team-init.sh`. It is droppable because the whole value of this task survives without it — the adopter runs one command in a repository they already trust — and because integrating it is the one option that collides with team-init's own stated single-base-dir invariant. This spec elects **not** to integrate (see **D1**), so the drop is pre-executed rather than pending; if a review round proposes integration, the fallback is unchanged and documented, and the round's findings travel to a fast-follow issue as its requirement list.
- **Trigger (same-class-2)**: two consecutive review rounds producing independent new defects in the same component. Factual condition — the same component drew a new, independent finding in each of two consecutive rounds; contextual condition — before a third repair round on that component starts. When the two disagree, the factual condition rules. Every named component here is never-dropped, so a trigger stops the task; there is no droppable component left to sacrifice instead.
- **Named fragile component, priced now rather than mid-task**: **AC10**'s live run depends on a third-party CLI's discovery rules, spawn-tool names and TOML key set, all measured on one version on one host. If the live run fails for a reason that is a property of that CLI rather than of this task's deliverable, that is a `BLOCKED` escalation with the exact error and the measured version named — never a silent narrowing of the criterion, and never a substitution of a static read for the live one.

## Input space

**Reachable input classes** — what real role files, real bindings and a real adopter repository produce, all of which the implementation must handle correctly:

1. A role file whose body contains no apostrophe run longer than two and no control character — the four shipped role files today. Generated normally, body byte-identical.
2. A body containing one or two consecutive apostrophes anywhere, including at the end of a line. Legal in a TOML multi-line literal string and must generate, which is why **AC3** carries a positive control for exactly this shape rather than refusing everything quote-shaped.
3. A body containing backslashes. Three role files outside this task's four carry them (relayed measurement); they are inert inside a literal string and must survive byte-identically if such a role is ever added to the list.
4. A body containing multi-byte UTF-8 — several role files carry Japanese prose inherited from the lessons corpus. It must round-trip byte for byte, so the generator does no case folding, no normalization and no re-encoding.
5. A body containing the three-character terminator `'''`. Refused whole-run, no output file written.
6. A source file that does not end with a newline. Refused, because that is the only shape in which a trailing apostrophe abuts the closing delimiter.
7. A source file containing a control character other than tab and newline, a lone carriage return included. Refused rather than silently emitted, since a lone `\r` is not a character a TOML literal string carries and would break the round-trip even where a parser tolerated it.
8. A role file with no frontmatter, or with an opening `---` and no closing one. Refused — never emitted as an agent whose instructions are the whole file, frontmatter included.
9. A frontmatter `description:` containing a double quote or a backslash. Refused, rather than emitted into a TOML basic string that would then be malformed or truncated.
10. A resolved binding row whose adapter is a Codex adapter carrying a real model token and a non-`-` effort. Both keys are emitted; reachable today only through an adopter's own `binding.conf`, which is why the fixture suite is where the branch runs.
11. A resolved binding row on `claude-cli`, or one whose model token is the `provider-configured` placeholder, or whose effort column is `-`. Neither key is emitted — the shipped default for all four roles.
12. An out-dir that already holds a previously generated, now stale `shell-team-<role>.toml`. The generator overwrites its own files; the checker reports drift non-zero and never repairs it.
13. An out-dir that also holds the adopter's own Codex agent TOMLs, whose names do not begin `shell-team-`. Left untouched by the generator and ignored by the checker.
14. An out-dir that does not exist yet. Created by the generator; the checker treats a missing expected file as a refusal rather than as nothing to check.
15. A repository whose Codex trust has not been granted. Project-level agents are simply not discovered — a measured property of the CLI, not a code path here — so the documentation states the precondition and no criterion claims the generator can work around it.
16. A plugin upgrade that moves `agents/*.md` under an adopter who generated earlier. The previously generated files go stale, the checker reports drift, and the documentation's re-run instruction is the remedy.
17. Either supported layout — the `.shell-team/` default and the legacy `tasks/` one — and a `$TEAM_RUN_BASE` override. The out-dir is a Codex host-configuration directory rather than a shell-team operating path, so it is unaffected by which layout resolved; the binding read the generator performs goes through the existing resolver, which honours the override as it already does.

**Out-of-scope synthetic extremes** — named concretely, and declined:

- Codex CLI versions other than the one measured. Every discovery rule, spawn-tool name and TOML key this design rests on was measured on a single version on one host, named in `## Assumptions`; a future version that renames a key or changes discovery precedence is a re-measurement, not a defect this task's criteria can anticipate. No criterion asserts forward compatibility.
- An agent-name collision between a generated `shell-team-<role>` and an identically named agent in `<home>/.codex/agents/`. The `shell-team-` prefix is the mitigation; precedence between the home-level and project-level namespaces is unmeasured, and this task declines to claim a resolution order it did not observe.
- An out-dir path that is a symlink, a dangling symlink, or a path containing whitespace or a newline. The generator performs no symlink-escape analysis and no path-shape validation beyond what the shell itself enforces; an adopter naming such a path gets whatever the filesystem does.
- Concurrent generator runs racing on one out-dir, and a generator run interleaved with a checker run on the same directory. No locking is added; the documented use is one adopter running one command.
- A role file of pathological size, a role list of hundreds of entries, or a body engineered against the awk extraction (a line that is itself `developer_instructions = '''`, for instance) placed in a source file by hand. Real role files are authored prose reviewed by this repository's own gates; a hand-crafted adversarial `agents/*.md` is an attack on a trusted instruction channel, which this repository's security invariant already treats as operator configuration rather than as untrusted input.
- Any claim that a generated `sandbox_mode` bounds what a spawned agent can write. Measured false; declined outright, and stated as declined in the generated file and in both documentation sections rather than left for a reader to discover.
- Driving the reviewer gate, telemetry conversion, or a full both-gates close from the Codex host. Slice 2's subject, and no criterion here reaches it.
