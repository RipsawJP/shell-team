# The release-notes template stops classifying its compare link as copy-unchanged boilerplate

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1062

**Base ref / branch point — one discriminator for the whole spec.** Every base-side blob read in this spec reads **the branch point**, resolved at check time as `git merge-base feature/1061-adopter-docs-gate HEAD`, and never `git merge-base develop HEAD`. The choice is stated once and applied uniformly, because two refs in one document is the inconsistency a sibling-clause cross-check exists to catch. The reason it is the correct ref here is measured rather than conventional: the one file this task edits, `docs/templates/release-notes-template.md`, was **created by T-1059 on this same stack** and has never existed at `develop`'s tip, so a base-side read at `develop` would resolve to nothing at all and every byte-identity and survival clause below would be false on arrival through no act of this task. The same holds for the board and for `.shell-team/test-recipe.md`, both last written by T-1061 at the branch point. No 40-hex literal is written into any criterion — every criterion resolves the ref itself and fails closed when it does not resolve, including after the batch merge deletes the parent branch, which is the intended behaviour for the merge-point-scoped criterion that says so in its own body.

## Problem

`docs/templates/release-notes-template.md` — shipped by T-1059 as the answer to issue #223 — tells the release preparer that "**`## Install / update`** and **`## Links`** are static boilerplate below; copy them unchanged." That is true of the two changelog links, but the same `## Links` section's last line is `- Compare: https://github.com/RipsawJP/shell-team/compare/vPREV...vX.Y.Z`, whose two version tokens are the same fill-in-the-real-value notation the template's own Title section already establishes three sections earlier. A preparer who follows "copy them unchanged" literally publishes a release whose compare link points at two tags that do not exist. The defect was found by the cross-provider reviewer at T-1059 round 1, judged Minor and dispositioned **file-an-issue** rather than fixed inline, and reaches this task as issue #240.
