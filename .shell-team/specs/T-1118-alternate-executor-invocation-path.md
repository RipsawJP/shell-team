## Problem

`README.md:207`, `README.ja.md:207`, `docs/adopting.md:267` and `docs/adopting.ja.md:280` each state, as this project's own honest boundary, that **no** alternate-executor invocation path is wired: a host's `binding.conf` changes what `bin/resolve-executor.sh` resolves and what telemetry records, and nothing about how a call is executed. That claim is true today and it is the thing #419 exists to falsify — deliberately, narrowly, and with the claim narrowed rather than deleted. Two gaps make the narrow cut worth more than documentation. First, `bin/resolve-executor.sh:495`–`:498` refuses only the `carries board-transition not-carried` case and `templates/adapters/codex-cli.txt:53` declares `file`, so resolution **passes** `engineer` bound to `codex-cli` today while a `--sandbox read-only` executor would forbid the write that role exists to make; nothing on the invoking side refuses it. Second, the trust boundary such a path stands on has a recorded incident: during T-1116's cross-provider spec review a `codex exec --sandbox read-only` pass read instruction-shaped files under the operator's home directory and stalled on their contents (#425), and the coordinating session's own first-hand probes on 2026-09-03 reclassified that as **discovery-time injection** — the Codex CLI auto-loads instruction documents before the prompt is obeyed, so a prompt-carried scope instruction is structurally later than the attack and cannot close it alone.
