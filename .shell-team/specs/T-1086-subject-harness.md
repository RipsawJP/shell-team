## Problem

Issue #307 names three preconditions before the implementation-axis tier `tier2-parallel-implementations-judge` can be measured at all. Precondition 1 reads, verbatim: "A committed, reusable subject harness — a real-shaped implementation task with its serial baseline, checked in rather than reconstructed per-pilot, so an arm has a stable subject and a recorded baseline to price against."

Nothing in this repository satisfies it. The one real-shaped subject this loop has ever run — T-1078's Tier-3 pilot subject — was deliberately never committed: that task's own Non-goals froze "The clone, its worktrees, the subject task's own files and every driver the pilot runs exist only under `$TMPDIR` and are never committed to this repository", and `docs/loop-engineering/phase-multiplexing.md`'s frozen evidence region records only the subject's one-line description and its partition. The consequence is already on the record as a measured refutation rather than a suspicion: `.shell-team/interventions/T-1079.md`'s first entry records that the routing assumption "T-1078's wordstats subject task is established and reusable, and its serial baseline already exists" was contradicted — no committed baseline, no committed harness — which is what pushed T-1079 from a pilot arm to a paper cost model.

So every future arm either re-authors a subject from scratch (making its figure incomparable with every other arm's) or gives up on measuring the tier. A cost model whose decisive parameter stays `undetermined` cannot be discharged by argument; it needs a stable subject and one baseline that later arms price against.

**Goal (one sentence).** Issue #307's precondition 1 is discharged as committed bytes: a real-shaped, unpartitioned implementation subject — its brief with its own frozen acceptance criteria, its frozen interface contract, a machine-readable manifest, an acceptance oracle and a regeneration driver — lands under `docs/loop-engineering/subjects/subject-01/` such that a deterministic, genuinely *unimplemented* venue regenerates from those bytes alone, no candidate implementation is ever committed at a subject path, and one **serial baseline** arm of a single real engineer instance implementing that subject is measured and recorded in a new note at `docs/loop-engineering/tier2-subject-harness.md` with its arm id, reps, wall-clock definition, machine-time basis, venue, host facts, safety and legitimacy conditions, and one explicit statement of what a later Tier-2 arm may and may not price against it.

**What "reusable" means here, frozen first because every criterion below depends on it.** Reusable is not a promise about the future; it is a property of the committed bytes, in four parts. **(1) Regenerable**: running the committed driver against a fresh empty directory materialises the subject's starting state, and running it twice materialises byte-identical trees — so two arms months apart begin from the same state without anybody reconstructing it. **(2) Genuinely unimplemented**: the committed oracle, run against a freshly regenerated venue, exits non-zero with at least one failing case and its own summary line present — a starting state the oracle already accepts would make every later arm's measurement meaningless, and an oracle that cannot go red is decoration. **(3) Uncontaminated**: no candidate implementation is committed at any subject path, ever, so no later candidate can read a solution out of this repository. **(4) Self-contained**: the two committed scripts reference no path belonging to this repository's own operating layout, so the harness runs from a copy anywhere without carrying `bin/`, `tests/` or `.shell-team/` behind it.

**Why the subject reuses T-1078's shape and is authored fresh anyway.** The shape carried over is structural and cost-bearing: a two-library-plus-CLI pure-bash tool with an acceptance oracle, implemented **whole** rather than partitioned. The ground is commensurability, not convenience — `docs/loop-engineering/phase-multiplexing.md` line 205's `engineer-phase-cost` (271772 ms) is the only recorded per-implementation figure this repository has, and it was measured on exactly that shape, so a subject of another shape would give a baseline that cannot be read beside it. What is **not** carried over: the partition (Tier-2 runs N whole candidates and discards N−1; it never splits a file set), and the bytes — T-1078's Non-goals kept every subject file under `$TMPDIR`, so there is nothing to copy and the files are authored new. The **domain** must differ from `wordstats`'s word-frequency domain, because that domain's description is committed prose in this repository and a subject whose solution shape a candidate can read here measures reading rather than implementing.

**The subject's own size band is an authoring target, never an acceptance threshold.** The brief targets an implementation whose serial cost lands in the same order as the recorded `engineer-phase-cost` figure. Whatever the baseline actually measures is reported honestly, in either direction, and **no criterion below gates on the measured figure falling in any band** — a criterion that did would convert the measurement into fitting.

**The arm and its unit.** The unit is one **real engineer-role Agent instance** implementing the whole committed subject from the regenerated venue's own bytes, launched by the coordinating session — never a shell-process proxy and never this task's own engineer instance. The instance's input is exactly the regenerated venue (the brief, the interface contract and the oracle copy the driver places there) plus the venue path; it is **not** given this spec, the note, the board, or any part of this repository's own task machinery. The arm id is `subject01-serial-n1`.

**Venue.** Each rep runs in its own freshly-created throwaway `git clone --no-hardlinks` under `$TMPDIR`, checked out detached at one pinned commit that already carries the harness, with the venue directory created **outside** the clone's tracked tree or under an ignored path so the instance's writes never appear as a clone-tracked change. `git worktree add` is used for no venue, because a worktree registers under `.git/worktrees` in the real checkout and turns cleanup into a destructive step this task takes no version of. Teardown removes only the throwaway clone directory; no `git worktree remove`, no `rm`, and no git verb of any kind is ever aimed at the real checkout. The real checkout is measured clean (`git status --short` and `git ls-files --others --exclude-standard` both empty) after every rep.

**Wall clock, quoted rather than re-invented.** The definition applied to the arm is `docs/loop-engineering/phase-multiplexing.md` line 257's, verbatim: t0 is the orchestrator's own launch call for that arm; the arm ends at the last completion notification plus that arm's own landing spans, and orchestrator-idle gaps between a notification and the next command are excluded. This arm performs **no landing** — nothing is composed onto a coordinator branch, because a Tier-2 baseline produces one candidate and discards nothing — so the landing term is recorded as absent with its own reason, and the disclosed consequence is that this figure sits below a T-1078-style arm by that arm's own measured landing span (sub-second: 458–490 ms measured there), which is stated in the note rather than silently absorbed.

**Basis.** Machine-time, per `docs/loop-engineering/phase-multiplexing.md` line 226 — the compute cost one implementation attempt consumes, not calendar wall-clock experienced by whoever waits. The arm is a single serial instance, so its machine-time and calendar-clock figures coincide by the same reasoning that line states for `rework-round-cost` and `judge-pass-proxy`; the note says so explicitly rather than leaving the reader to infer which basis a bare millisecond figure is on.

**Reps and what a rep does not inherit.** Two reps, same host, one continuous session, each in its own fresh clone at the same pinned commit. Sub-agent instances share no context window, so rep 2's instance carries nothing from rep 1's — the property that makes two reps of one subject legitimate at all, stated here because it is the first thing a reviewer will probe. Execution order and cache warmth are recorded. **No inferential statistics**: spread is disclosed descriptively or not at all — no significance test, confidence interval, variance model or regression anywhere in the note.

**Outcome per rep, recorded whatever it is.** Each rep records its own wall clock, the committed oracle's exit status run against that rep's produced tree, and that run's passed/failed case counts. A rep whose oracle fails is a recorded rep, not a discarded one. At least one rep with the oracle exiting 0 is what evidences that the subject is completable at all; if no rep reaches it, the licence condition `oracle-satisfiable` reads `not-met`, the readiness verdict reads `not-met`, and the note ships with that finding rather than with a re-cut subject.

**Telemetry and durability.** The runs directory is gitignored, so span rows survive only as verbatim quotes inside the tracked note: the coordinating session emits one orchestrator-written span row per rep (`--instance <role-qualified-id> --seq auto`) under one run id with the runs directory resolved by default (`TEAM_RUNS_DIR` unset), and every such row is quoted verbatim in the note's evidence section.

**Satisfiability is evidenced once and never re-derivable from committed bytes — a deliberate trade.** Proving the oracle can be satisfied would need a reference implementation, and committing one would defeat property (3) above by publishing a solution every later candidate could read. 2. **Pathological path shapes**: candidate paths containing spaces, newlines, non-ASCII bytes, or shell metacharacters. The manifest's grammar restricts every declared path to `[A-Za-z0-9._/-]`, so this class cannot arise from a conformant manifest and is not protected against a non-conformant one.
3. **Ever-larger subject inputs**: arbitrarily large corpora for the subject tool, inputs sized to expose asymptotic behaviour, or a subject scaled up until the arm's wall clock becomes the measurement's own problem. The oracle builds its own fixed inputs.
4. **Degree escalation**: N ≥ 2 concurrent candidates, a judge pass, a merge of non-overlapping candidate pieces. Out of scope here by Non-goal; that is T-1087's and T-1088's input space, not this one's.
5. **Foreign platforms and shells**: a host without `bash`, without `shellcheck`, with a case-insensitive filesystem where this host's is case-sensitive, or a non-POSIX `find`/`cksum`. 7. **A venue on a network filesystem or with the runs directory redirected** (`TEAM_RUNS_DIR` set). The arm runs with the runs directory resolved by default; a redirected corpus is a different measurement and is not priced.
