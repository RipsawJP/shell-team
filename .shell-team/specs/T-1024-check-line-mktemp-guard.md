## Problem

A spec's acceptance-criteria `check:` line that needs scratch space opens with `d=$(mktemp -d "${TMPDIR:-/tmp}/….XXXXXX"); rc=0;` and never tests whether `mktemp` succeeded. When it fails — an unwritable or missing `$TMPDIR`, a full or read-only filesystem, a sandbox denial — `$d` is the empty string and every path composed from it expands root-anchored (`"$d/raw.txt"` becomes `/raw.txt`). `bin/check-acs.sh` runs each check via `bash -c "$cmd"` with **no** `set -e` in the executed shell, so nothing in the harness rescues the line: it keeps running past the failed writes to whatever its final `test` happens to say.

The T-1019 review measured what that costs. Most such checks still fail closed by accident, because a permission error propagates into the final `test`. But the shape T-1019's own AC11 uses does not: a scope-lock check that writes intermediate files, feeds them to `comm`, and rounds each side through `grep -c . || true` reports `miss=0`/`extra=0` when the writes never happened at all, and reports `PASS`. A gate that cannot write its own scratch file announces that the diff is exactly in scope. That is a fail-open hole in the one place whose whole job is to be fail-closed.

What issue #109 asks for is not a sweep. It asks for **one inventory pass** with a per-site apply/not-apply decision, because most of these lines live inside the frozen intent block of a task that closed months of loop-time ago, where an edit would have to run the ratified re-freeze path to buy nothing — and the honest answer for those is a recorded won't-fix with a reason, not a patch.

## Goal

<!-- BEGIN intent-block: T-1024 -->

Every `- check:` line in `.shell-team/specs/*.md` that invokes `mktemp` is accounted for exactly once in a ledger-grammar audit document at `docs/loop-engineering/check-line-mktemp-guard-audit.md`, classified into one of four mutually exclusive classes whose counts reconcile to the population total under a live re-derived command, and carrying a per-file apply / not-apply / escalate decision with a one-sentence site-specific reason; the guarded idiom is applied on the only live surface (this task's own spec) and nowhere else; `.shell-team/test-recipe.md` carries a `T-1024` delta entry that hands the idiom and its reason to the next task; and not one byte inside any existing spec — frozen intent block or otherwise — changes.

### Settled decisions

Each decision below is resolved. Nothing here is left to implementation judgment. DP1–DP6 restate the tech-lead's binding constraints; DP7–DP11 are this spec's own. The apply/not-apply **rules** are this spec's decisions — the engineer applies them and records the result; the engineer does not re-open them.

- **DP1 — the population canon, fixed here.** The population is every line of every file matching `.shell-team/specs/*.md` that matches the extended regular expression `^[[:space:]]*- check:.*mktemp`. The pinned command, frozen byte for byte and required to appear in the audit document, is:

  `grep -nE -- '^[[:space:]]*- check:.*mktemp' .shell-team/specs/*.md`

  Its line count is the population total; the count of distinct paths in its first colon-field is the file total. Both are **re-derived live** by AC2 against the working tree, never copied from any number written in prose.
- **DP2 — four mutually exclusive classes, assigned by an ordered first-match-wins ladder.** For each population line, in this order: (1) is every `mktemp` invocation on the line guarded, so that a failure exits non-zero before any path composed from the resulting variable is used? ⇒ **class (a) guarded**. (2) Otherwise, is an unguarded invocation's variable composed into at least one path used later on the line? ⇒ **class (b) unguarded-path-composed** — the root-anchored-expansion shape. (3) Otherwise, is `mktemp` present with no temp-path variable composed into a later path? ⇒ **class (c) no-path-composed**. (4) Otherwise ⇒ **class (d) other**, which must be enumerated site by site with a reason rather than left as a bucket. Tie-break, stated so it is not discovered: a line carrying more than one invocation classifies by its **weakest** invocation.
- **DP3 — the accounting identity is one AC's live check.** `population == (a) + (b) + (c) + (d)`, and the same total re-derived from the per-file rows' `sites:` fields, and the file-row count equal to the file total — all of it inside AC2, one check, so the identity cannot be satisfied by one half of the document while the other half drifts.
- **DP4 — the four decision rules.**
  - **rule-1** — a site in the spec of a **closed** task is **not-apply**, on three grounds: *zero CI reachability* (`.github/workflows/check-handoff.yml` never executes a real spec's `check:` lines — it runs `tests/check-acs/run.sh`'s fixtures, re-derived live by AC4); a frozen record *documents what was verified* at the time it was verified, so editing the line cannot re-establish that verdict; and the *deferral-record precedent* T-1023 just shipped values records that stay true to their own measurements. This holds whether or not the site sits inside a `<!-- BEGIN intent-block -->` region — closed-task membership is the operative ground, and frozen-block membership only decides whether an edit would additionally owe a ratified re-freeze. (Extending rule-1 to legacy specs with no intent markers is this spec's own settlement of a gap in the routing constraint; without it every pre-attestation spec would fall to rule-4 and the task would drown in escalations that all have the same answer.)
  - **rule-2** — where the acceptance criterion's own text declares staleness or forbids re-derivation, not-apply is **strong**, not merely default. `.shell-team/specs/T-1019-is-span-row-parity.md`'s AC11 — the issue's highest-severity site — is exactly this: its own body says it is merge-point-scoped and that its base-ref resolution must not be widened or re-derived per round. Editing it would violate the criterion in the act of hardening it.
  - **rule-3** — a **live** surface is **apply**, in the guarded idiom. The only live surface in this task is this spec's own `check:` lines.
  - **rule-4** — anything the three rules above do not settle is an **escalation**, recorded as such in the document. There is no engineer discretion here: an escalation is a hand-off item, not a judgment call.
- **DP5 — the guarded idiom, fixed.** `<var>=$(mktemp -d "${TMPDIR:-/tmp}/<slug>.XXXXXX") || exit 1`, with the failure exit **before** the first composed path is used. Two further rules travel with it, because the guard alone does not close the AC11 shape: every write, `sort`, `comm` or `git` step whose failure would otherwise be invisible reflects that failure into `rc=1` explicitly; and a `|| true` may only absorb a `grep -c`'s "no match" exit status, never a producer's failure — a counted value that could be zero because the file was never written needs a positive control (`test -s`, or a known-present anchor) beside it.
- **DP6 — deliverables, exactly two artifacts plus this task's own records.** (i) `docs/loop-engineering/check-line-mktemp-guard-audit.md`, in the ledger-line grammar of `docs/loop-engineering/arith-base10-audit.md` — anchored `- key: value` lines, one row per file, machine-readable by grep and sed. (ii) A `T-1024` entry appended to `.shell-team/test-recipe.md`'s `## Appended by tasks`, written as a **delta** against the existing `T-112` mktemp entry rather than a restatement of it: the guarded idiom, and the WHY — `bin/check-acs.sh` executes each check through `bash -c` with no `set -e`, so errexit never rescues an unguarded assignment, and the AC11 shape can round a write or `comm` failure to zero and report `PASS`.
- **DP7 — the audit document's required structure**, nine headings, exact text: `## Why this document exists`, `## Terms this document uses`, `## Population — every spec check: line that invokes mktemp`, `## Classification — the four classes and the ladder`, `## Decision rules`, `## Reconciliation — the accounting identity`, `## Per-file rows`, `## Escalations`, `## What this audit does not claim`. AC1.
- **DP8 — the per-file row grammar, frozen.** One line per file in the population, all nine fields, in this order, separated by ` — `:

  `- file: <path> — sites: <N> — classes: a=<n> b=<n> c=<n> d=<n> — frozen-block: yes|no|partial — regime: attestation|legacy-carve-out — task-state: closed|open — decision: apply|not-apply|escalate — reason: <one sentence>`

  `frozen-block` is whether the file's population lines sit inside its `<!-- BEGIN intent-block: … -->` region. `regime` is `attestation` when the task's board entry carries a `freeze-attestation` sub-bullet and `legacy-carve-out` when it does not — the distinction matters because rule-1's second ground ("a frozen record documents what was verified") is strongest under the attestation regime and is a weaker, carve-out-shaped argument without it. `task-state` is `closed` when the board line is `- [x]`. A `reason:` is a sentence **about that file's sites**; a category name (`frozen`, `closed task`, `out of scope`) is not a reason and AC3 rejects it mechanically.
- **DP9 — per-site rows are required only where a count is not the answer**: every class (d) line, every escalation, and the strongest not-apply site (rule-2). Where a class is empty, the document says so with an explicit `- site: none — reason: …` / `- escalation: none — reason: …` line rather than omitting the section — an absent line and a zero count must not look identical.
- **DP10 — fidelity: no number quoted in prose is inherited.** The tech-lead's reference values (roughly 205 population lines across roughly 25 files, roughly 126 unguarded canonical, 11 guarded from T-1020/T-1023) are recorded in Assumptions as `pm-spec-taken-from-source` and are **not** frozen anywhere in this spec's intent block. Every number in the audit document is either produced by the pinned command at authoring time and re-derived by AC2, or attributed at its own claim site. The completeness claim carries the population total, the literal command, and a per-exclusion reason at the claim site.
- **DP11 — self-application is a criterion, not a courtesy.** Every `- check:` line in *this* spec that invokes `mktemp` uses the DP5 idiom (AC6). AC6 scans invocations, not mentions: a line that names `mktemp` only inside a grep pattern has nothing to guard. AC6's own check line assembles the invocation token at run time precisely so that it is not a member of the set it measures — the self-hosted-check trap, corpus entry 2026-06-18.

**Out-of-scope synthetic extremes** — declined deliberately; a finding grounded only in one of these is out of contract:

- **A `mktemp` invocation the pinned regex cannot see by construction** — spelled through a variable (`$MK -d …`), prefixed (`command mktemp`, `env mktemp`), assembled at run time, or split across lines. Escalating a hypothetical constructed form that the corpus does not contain is not a finding class here.
- **Adversarial `mktemp` behaviours**: a returned path containing whitespace or a newline, a symlink race inside `$TMPDIR`, a TOCTOU window between `mktemp` and the first write, the directory being removed concurrently.
