## Problem

Two findings from the v1.5.0 train's cross-provider rounds name a gap between what a check *claims* to establish and what it actually measures. T-1027 mechanised a batch-merge cycle-window norm into `agents/scrum-master.md`: derive `N` from the cycle's known merge count and pass an explicit `--last-n N`. But `--last-n N` is a cap on *how many* merge commits come back, never a filter on *which ones* — so on a base branch that keeps moving during a batch-merge cycle (this repository freezes `develop`; an adopter's repository need not) the agent can receive exactly `N` merge commits with the wrong membership, and the reconciliation the prompt prescribes compares only the count and passes. Separately, T-1031's two decoy fixtures guard their own non-vacuity by grepping the decoy token as a plain substring: an edit that moves the token out of the decoy-separator shape, or deletes the slot beside it, leaves the guard passing while the fixture silently stops exercising the class it was built for. Both are precision defects in a verification surface, and in both cases the surface still reports green.
