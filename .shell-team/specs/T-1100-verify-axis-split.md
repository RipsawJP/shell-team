# Split the verify-axis dispatch election by work type

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1100

## Problem

A task's `dispatch: verify` record elects one mechanism (`serial` or `tier1-fanout`) for the whole verify phase. When a task's verification duty bundles **fixture-suite work** (a small population of cases sharing one temp root, run sequentially in one bash process — correctly `serial`) with a **mechanism-class full-population two-arm diff** (every merged spec's criteria run at a base ref and again at HEAD — the mechanically-enumerable, read-only population shape the `tier1-fanout` trigger exists for), one election priced against the smaller half silently carries the larger half's fan-out-eligible work along with it. The shipped grammar makes the split unrecordable: `templates/prompt-blocks/dispatch-record.md:6` requires each axis key to appear **at most once per entry**, and `bin/close-out.sh`'s `DISPATCH_SEEN_AXES` check refuses a repeated key outright, so a literal "two `verify` rows" entry is refused by the shipped gate today. Four consecutive tasks in the 2026-08-26 cycle each recorded `verify — serial` with ground text covering only the fixture-suite half.

A task can record an **independently priced verify-axis election per work type**. The dispatcher note declares two refinement axis keys, `verify-fixture` and `verify-mechanism`, each over the same closed set `serial|tier1-fanout` as the `verify` axis they refine; an entry records **either** the parent `verify` key **or** one or more of its refinements, never both. `bin/close-out.sh` accepts a conformant refinement record, refuses an entry mixing the parent with a refinement, and keeps refusing — byte for byte, verdict for verdict — every record it refuses today; every `- dispatch:` line already on the live board produces an identical verdict under the pre-change and post-change gate. The authoring duty that a task whose verification duty contains both work types prices each half separately is stated in `agents/pm-spec.md` and in the dispatcher note's own trigger text, and every shipped sentence that assumed exactly one verify row is corrected. Observable from outside: `bash tests/close-out/run.sh` exits 0 with new cases proving both the acceptance and the new refusal; a two-arm diff over the live board's own dispatch lines shows zero verdict changes; and this task's own board entry carries the split form before it closes out.

## Non-goals

- **Building or changing any fan-out mechanism.** Tier-1 fan-out mechanics, the aggregation step, `bin/aggregate-verdicts.sh`, `bin/check-fanout-instances.sh` and the T-1069 pilot's own pricing are untouched. Only the *election record* and its gate change.
- **Mechanically enforcing "both work types are present, so both must be recorded".** That judgment is not executable from committed bytes; it stays an authoring duty in prose (DP-2, arm B). A close-out refusal for it is explicitly not built.
- **Retro-editing history.** No historical board entry, spec, review or provenance record is rewritten into the split form. Records are records, not surfaces.
- **Reshaping the four-field grammar or the ground field.** The ` — `-separated `<axis> — <value> — <modality> — <ground>` shape is unchanged, the ground stays last and free-text, and `bin/close-out.sh`'s three `sed -nE` field extractions are not re-anchored.
- **Registering `agents/pm-spec.md` as a consumer of `dispatch-record.md`.** The registry keeps exactly its current consumer set; the authoring rule lands in pm-spec's own prose.
- **Fixing `agents/tech-lead.md`'s `### Dispatch` template's pre-existing omission of the `specify` and `spec-review` axes.** Only the verify line the split itself forces is touched; the rest is filed, not folded in.
- **Discharging `record-tamper-resistance.md`'s own re-evaluation trigger**, which T-1099's third arm-A promotion already fired. That is owed at the next retro, not here.

## Input space

**Reachable input classes** — what this grammar, this gate and these criteria really encounter, and which the implementation must handle correctly:

- An entry carrying both refinement rows (`verify-fixture` and `verify-mechanism`), with the same value on both or with different values. Accepted.
- An entry carrying exactly one refinement row and no parent — an author who decided one half and has nothing to say about the other. Accepted: completeness is norm text, not the gate's business, exactly as a single-axis record already is.
- An entry carrying the bare parent `verify` row and no refinement — every board entry that exists today, and every entry an adopter writes who never needs the split. Accepted, byte-for-byte unchanged.
- An entry carrying the parent **and** a refinement. Refused: two records covering the same phase leave no fact about what was chosen, which is the same reason a repeated axis key is refused.
- A repeated refinement key (`verify-fixture` twice), typically from an edit that appended a corrected line instead of replacing the wrong one. Refused by the existing per-key uniqueness rule, unchanged.
- A value from another axis on a refinement row (`verify-fixture — tier2`, `verify-mechanism — pm-authored`) — the transposition slip the axes' shared `serial` value already makes reachable. Refused.
- An axis key the note does not define (`verify-suite`, `depth`). Refused today; conformant on the day some note defines it, with no change to this grammar.
- Whitespace variants after `dispatch:` — a tab, a doubled space, no space at all — on a refinement row. Seen by the anchored scan and refused by the strict per-field extraction, exactly as they are on the existing axes; never silently invisible.
- A tab-indented conformant refinement row, which `bin/check-handoff.sh`'s continuation canon already accepts.
- A ground field carrying explanatory prose after the priced-line id, including an em dash inside that prose; and a ground whose priced id is dropped, leaving `recommendation: ` with nothing after it. The first is accepted, the second refused.
- A hand-off sub-bullet, review record or spec that **quotes** `- dispatch: verify-fixture` mid-line inside backticks while discussing the grammar — including this very spec and this task's own board entry. Not a record; the anchored line-start match is unchanged.
- Both supported layouts (default `.shell-team/` and legacy `tasks/` + `docs/specs/`), every operating path resolved through `bin/team-paths.sh`.
- An adopter board on which no entry, past or present, carries any dispatch record at all — the ordinary state of every repository adopting this plugin after the fact.
- A board carrying CRLF line endings, which the existing board tooling already tolerates.

**Out-of-scope synthetic extremes** — inputs this spec explicitly declines to protect, because real data cannot produce them:

- A third, fourth or Nth refinement key beneath `verify` that no dispatcher note defines, and refinement chains more than one level deep (a refinement of a refinement). The family is exactly the two keys this task's note declares.
- A board entry carrying tens of refinement rows, or thousands of `- dispatch:` lines, to probe the gate's scan cost. The population is bounded by the axis keys the notes define.
- Unicode look-alike separators substituted for the em dash (en dash, hyphen-minus runs, non-breaking hyphen). A look-alike is a malformed record and the gate is free to refuse it or to report it as an unrecognised axis, without a criterion fixing which.
- A ground field megabytes long, or one carrying NUL bytes, control characters or terminal escape sequences.
- A board whose encoding is neither UTF-8 nor the CR-tolerant variant the existing tooling handles.
- A `- dispatch:` line placed inside a fenced code block **within a board entry**. The gate reads a line range and deliberately does not learn markdown fences; fenced illustrative examples belong in specs and docs, not inside a board entry's extent.
- Adversarial nesting of one task's entry inside another's, or a board with no `## Active`/`## Done` structure — refusals `bin/close-out.sh` and `bin/check-board-headings.sh` already own, unchanged by this task.
