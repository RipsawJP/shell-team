# The freeze pipeline prints its own hash, its refusals name their measured counts, and the freeze-gate sweep cross-joins disclosed reds against other criteria

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1041

## Problem

Recording a frozen intent-hash today requires whoever runs the freeze gate to
re-implement `bin/check-intent.sh`'s normalization by hand — strip CR, strip
per-line trailing whitespace, drop leading and trailing blank lines, exclude the
marker lines, then `git hash-object --stdin` — because the checker verifies a
hash it will not print. At both of this sprint's earlier freezes (T-1039 and
T-1040) the orchestrator hand-re-implemented that pipeline; it happened to match
both times, which is the failure mode rather than the reassurance: a
hand-re-implementation that silently diverges produces a recorded hash the
checker will later call drift, and nothing in the loop can tell that apart from
a real unratified edit.

Two smaller costs sit beside it. A freeze refusal prints a ready-to-adapt
sub-bullet on exactly one of its six paths, and on that one path the measured
counts and the placeholders the writer must replace are typographically
indistinguishable, so a measured `lines=12/12` reads as an example. And the
re-freeze mechanics documented in `CONTRIBUTING.md` never say where the hash
value is supposed to come from, so the hand-re-implementation is not merely
tolerated — it is the only documented route.

Separately, this sprint's own freeze gate produced a defect the gate could not
see: T-1036's engineer round ended `BLOCKED` with every splice byte-correct,
because the mutual-satisfiability sweep decomposed each criterion but never
cross-joined the set of already-disclosed reds against the requirement sets
other criteria assert. That step is missing from the sweep's own instructions.

## Goal

<!-- BEGIN intent-block: T-1041 -->

`bin/check-intent.sh` gains a `--print-hash <spec.md>` mode that prints the
frozen intent block's 40-hex hash and nothing else, so the value recorded in the
board's ledger and the value the checker verifies come from one pipeline rather
than from two independent implementations of the same normalization; the freeze
refusal that prints a ready-to-adapt record says which of its numbers were
measured; the re-freeze mechanics say where the hash value comes from; and the
freeze gate's mutual-satisfiability sweep carries an explicit step that
cross-joins the already-disclosed reds against what other criteria require.

## Input space

**Reachable input classes** — the classes real usage in this repository and in an adopter's repository actually produces, all of which print mode must handle correctly:

1. A spec file under the resolved specs directory carrying exactly one task-id-scoped marker pair, LF line endings, and between 0 and 35 `- check:` lines inside the block — 35 being the maximum measured in this repository, recorded in `bin/check-intent.sh`'s own grammar comment.
2. The same spec with CRLF line endings, from a checkout on a Windows filesystem or an editor configured for CRLF.
3. A spec whose marker pair is missing, duplicated or reversed, or whose `**Task ID**` line carries trailing garbage — the shapes a drafting error in this very role actually produces.
4. A spec argument that is a directory, a dangling symlink, or a file the invoking user cannot read.
5. A degenerate but genuinely reachable spec whose intent block normalizes to zero bytes — adjacent markers, or markers separated only by blank lines — which hashes to git's empty-blob value. Print mode reports it exactly as the two-argument mode computes it; parity is the point, and refusing it in one mode only would break the single-pipeline property this task exists to establish.
6. All three invocation styles: `bash bin/check-intent.sh`, `./bin/check-intent.sh`, and the bare name on `PATH` through a plugin-install symlink.
7. An environment where `TMPDIR` is unwritable, or a file-size quota such as `ulimit -f` is in force, or a `BASH_ENV` startup hook is inherited.
8. A board at the freeze moment with no intent-hash record and zero, one or several attestation-shaped lines, well-formed or malformed — the shapes the two refusal-readability changes are read against.
9. A stdout that is a closed or already-broken pipe (the caller piped the value into something that exited first).

**Out-of-scope synthetic extremes** — named concretely, and declined:

1. A spec carrying ten thousand or more `- check:` lines, i.e. beyond the existing four-digit grammar bound. The measured maximum in this corpus is 35; nothing here widens that bound and no fixture probes past it.
2. A spec of megabyte scale, or carrying single lines longer than any real spec's. No length bound is added and none is claimed.
3. A board carrying more than 9999 versions, ratification records or attestation records for one task.
4. Marker or task-id lines engineered specifically to defeat the exact full-line compare — embedded NUL bytes, a non-UTF-8 encoding, or bidirectional control characters. The checker's behaviour on non-text input is unspecified today and this task does not specify it.
5. A concurrent write racing this read, so that print mode observes a partially written spec. It reads whatever bytes are present, exactly as the two-argument mode does; no locking, no retry and no atomicity is added.
6. A hostile `PATH` in which `git`, `awk` or `sed` are replaced by programs producing plausible-but-wrong output. That is the trust boundary `bin/check-acs.sh` already declares over a committed, reviewed artifact, inherited here rather than closed.

## Settled decisions

**D1 — `--print-hash` takes exactly one positional argument, and mode flags are mutually exclusive.** `check-intent.sh --print-hash <spec.md>`. A board argument is a `usage` error rather than optional-and-ignored: accepting one would invite a caller to believe the board was validated when nothing about it was read. A repeated or conflicting mode flag is a `usage` error too, following `bin/team-paths.sh`:81's `set_mode` precedent, whose stated reason — a typo should be a clear error rather than a silent honouring of whichever came last — applies unchanged here.

**D2 — the judgments that run in print mode, and the ones that do not.** Run, all still fail-closed with the existing classifications and exit 2: spec argument type and readability (`-f` before `-r`, so a directory is classified by type); `**Task ID**` derivation with its line-end anchor; the marker structural checks (exactly one BEGIN, exactly one END, BEGIN strictly before END); extraction, normalization and hashing. - **Task classification, so review rigour is calibrated rather than guessed: this is verification-mechanism work.** It adds a mode to a checker and extends that checker's fixture suite. Per the corpus, this category runs long and needs the higher spec-review standard, which is why the pre-commitment above is set at the tighter default and why every readability change carries a counterfactual.
