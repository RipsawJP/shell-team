## Problem

The cross-provider reviewer states its board prohibition three times as a **capability it does not have** — "you have no board / gh / API write access", "You only read, run Codex, and write the review artifact". That premise is false: the role's frontmatter grants `Bash`, which it genuinely needs and which can redirect into any path in the checkout, and no agent in this repository carries per-path write scoping. A prohibition grounded on a capability the agent can observe it *does* have stops binding the moment it notices — which is the strongest structural explanation for the v1.4.0 incident, where this role flipped a board checkbox ahead of the merge gate and the flip had to be undone by hand. Nothing downstream caught it mechanically: `bin/close-out.sh` has no revert logic, and `bin/check-handoff.sh` validates only `- [ ]` lines in `## Active`, so a flipped line passes the lint unseen.

**Term definition, settled before the mechanism.** "Write access" has two referents in play and the whole task turns on keeping them apart.

| Candidate referent | What it names | Used in this spec? |
|---|---|---|
| **Structural capability** — whether the runtime can be made to refuse the write | the `tools:` frontmatter list, host permission settings, a sandbox | **as measured background only**; it is what D1 audits and declines to change |
| **Behavioural boundary** — what this role is instructed to write and not write | the canonical Rule this task ships | **yes; this is the deliverable's referent** |

- **D1 — the frontmatter is unchanged; the boundary lands as instruction, and the audit conclusion is recorded rather than left implicit.** `agents/codex-reviewer.md:4` is already `tools: Read, Grep, Glob, Bash`: `Edit` and `Write` are not present and never were, so the structural exclusion is already at its ceiling. `Bash` cannot be dropped — this role runs `codex exec` as a bare first-token invocation, runs `codex-capture.sh --alloc`/`--publish`, and resolves its diff scope with `git log` / `git diff` / `git rev-parse` — and any `Bash` grant admits a redirection into any writable path. Measured: no agent in this repository carries per-path write scoping (all nine `agents/*.md` `tools:` lines are bare tool-name lists). Narrowing the frontmatter is therefore not available, and the honest landing is the behavioural boundary. The conclusion **why it was not narrowed** is recorded here and in the pull-request body, so a later reader does not re-open the audit from scratch.
- **D2 — one canonical bullet, plus three minimal in-place rewrites that point at it.** The file states the prohibition three times, each time as a capability absence (lines 131, 156, 167 at the base ref). Restating the whole boundary three times would create three drifting copies; deleting two of them would strip the prohibition from the two places a reader actually meets it (the Output block's fast-follow section, and the fast-follow Rule). So: **F1** is the single canonical bullet, carrying the whole boundary, placed in `## Rules` as the physical line immediately after the first bullet, so the two write-boundary statements are contiguous; **R1**, **R2** and **R3** replace the three existing lines one-for-one, each keeping every other clause of its original sentence intact, each restating the prohibition as a rule, and each pointing at the canonical bullet by the fixed phrase `board-and-write-boundary Rule`. - **D3 — the write surface is a closed enumeration of the paths this role writes, with one bounded carve-out for the tools it must run; everything not on it is read-only.** The list is exactly: the review record `T-XXX.md` in the reviews dir `team-paths.sh --get reviews` resolves; the canonical raw-capture basenames `T-XXX-codex-primary.{txt,jsonl}` and `T-XXX-codex-adversarial.{txt,jsonl}` in that same dir (the file's existing naming Rule); the two per-invocation raw paths `codex-capture.sh --alloc` prints, including removing them in the `cleanup` block; and scratch files under `$TMPDIR`. **The carve-out is a scope statement, not a fifth member**: a state or cache directory that a tool this role is *required* to run maintains for itself — the Codex CLI's `$CODEX_HOME` (`~/.codex` when unset), which every `codex exec` invocation writes — is not a path this role writes, so the enumeration neither lists it nor forbids it.
