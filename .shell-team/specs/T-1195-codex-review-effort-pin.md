# code-reviewer effort pin: an effort named by the binding reaches every `codex exec` as `-c model_reasoning_effort=<EFFORT>`, and the review record states the effort each pass actually ran at

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1195

## Problem

The `code-reviewer` binding row has an effort column, but no `codex exec` that `code-reviewer` or `drift-evaluator` runs passes it on. The alternate-executor recipe applies a resolved effort as `-c model_reasoning_effort=<EFFORT>`, but that recipe belongs to the `sandbox-read-only` dispatch shape, and `code-reviewer` is `wrapper-hosted`: its effort column is declared and never applied. So every review runs at whatever reasoning effort the operator's own Codex configuration names, and that configuration can change outside the loop. This repository's own imported rollouts show it: the primary pass of T-1192 and the primary pass of T-1194, run on the same day with no effort pinned, ran at two different efforts. Issue #757 also reports a spec-review pass over a roughly 600-line spec that finished in about 20 seconds with an empty findings list.

The record side has no field for this at all. T-1192 added a per-pass `codex-model` line read from the rollout. Nothing records the effort a pass actually ran at, so a review run at a low effort is indistinguishable in the record from one run at a high effort.

- **D3 — observation and comparison in a deterministic script.** `bin/codex-capture.sh --publish … --thread-id <id>` and `--observe --thread-id <id>` each gain `--expect-effort <token>`, independent of `--expect-model`.
  - **Record set (closed).** The observed effort is every string value of a key named `effort` or `reasoning_effort`, at any nesting depth, read structurally with the existing tokenizer's discipline, inside a record that is either (a) a record whose top-level `type` is `turn_context`, or (b) a record whose top-level `type` is `event_msg` and whose `payload`'s own `type` is `thread_settings_applied`. Every other record type and every other `event_msg` subtype is never read, `response_item` included. Text inside a string value is never read as a key. A key whose value is an object or an array is ignored (the tool-schema decoy). A key whose value is a non-string scalar (`null`, a number, `true`/`false`) counts as malformed.
  - **Read-line hygiene.** A line the effort extraction reads (any line carrying the bytes `effort` or a backslash-u) that has an unterminated string, or that carries the depth-1 `type` key more than once, makes the observation malformed — the T-1193 rules, applied to the effort reader.
  - **Established** means at least one string value exists and all of them are one identical token matching `^[a-z][a-z0-9-]*$`. Values from both record kinds and from both keys count together, so a disagreement between them is not established.
  - **Comparison.** With `--expect-effort <e>` and `<e>` ≠ `-`, the operation refuses unless the observed effort is established and byte-equal to `<e>`. A refusal exits `3`, writes no canonical file, removes both raws on publish, and prints nothing on stdout on observe. Its stderr line contains `effort not established` and exactly one cause from the closed set: `cause=absent` (no value), `cause=inconsistent` (more than one distinct value), `cause=malformed` (as above, a string outside the token shape, or a backslash-u escape in it — such a value is never echoed) and `cause=mismatch` (established but not equal).
  - **Order.** The effort gate runs after the model gate, so a pass failing both reports `model not established` and not `effort not established`.
  - **Report-only.** With `--expect-effort -` the operation never refuses on the effort.
  - **Output.** Only when `--expect-effort` is given (any value, `-` included): the publish success summary line gains ` effort=<observed>` after its ` model=<observed>` token, and `--observe` prints a second stdout line `effort=<observed>` after `model=<observed>`. `<observed>` is the established value or `unavailable`. Without `--expect-effort`, stdout, stderr, exit status and canonical bytes are exactly the base's.
  - **Usage errors (exit `2`).** `--expect-effort` without `--thread-id`, with `--alloc`, with an empty value, or with a value that is neither `-` nor a token of `^[a-z][a-z0-9-]*$`. (**AC1**, **AC2**, **AC9**)

   - a value given as a backslash-u escape, a `null`, or out-of-shape text;

**Out-of-scope synthetic extremes**, declined explicitly:

1. Provider-side substitution behind an unchanged rollout value. This is undecidable from the client.

4. A rollout edited on disk between the end of the pass and `--publish` or `--observe`.
5. An effort key spelled through a backslash-u escape beside a plain one, or effort keys under names other than `effort` and `reasoning_effort`.
6. More than one rollout for one thread id. The existing search already refuses `matches=<n>`.
