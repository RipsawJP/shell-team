# The shape scan becomes a hand-off step in the roles that write records

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1143

## Problem

The lessons corpus has carried, since 2026-09-12, the rule that a pattern-based finding is reported by location and pattern id and never by quoting the flagged bytes into a record the same checker scans. In the cycle that followed, the retro records the class recurring at four enumerated sites across four roles while that entry was active in every playbook block, one of them a hand-off on which a same-class-2 fired. Every one of those sites carried a shape the shipped checker detects in its opt-in mode, so every one was mechanically catchable at write time by a tool that already ships and that nobody was told to run. The gap is that the discipline is stated as prose in four places and executed nowhere: no role's hand-off procedure names a command, so the only thing standing between a quoted shape and a committed record is the writer remembering a sentence.

- **Shipping a gate that refuses a hand-off.** No checker reads a hand-off for the `- shape-scan:` line, and none is built here. - **Retroactively cleaning records already committed.** No existing record, review, board line, retro or provenance file is edited to remove a shape.
- **Widening the consumer set beyond the four roles.** `agents/pm-spec.md`, `agents/tech-lead.md` and `agents/ui-designer.md` are excluded because their frontmatter `tools:` lists carry no `Bash`; `agents/triage-orchestrator.md` and `agents/drift-evaluator.md` are excluded because neither is a phase in the loop's per-round hand-off chain. `skills/*` gain nothing.

## Decision points, resolved

Design decisions are labelled `DP1`…`DP6` with no separating hyphen, deliberately: the conventional hyphenated form is itself a match for the opt-in shape this task is about, and a spec that teaches a scan while seeding its own corpus with that shape's accepted-noise population would be arguing against itself. The convention is this document's alone and nothing else depends on it.

**DP1 — the mechanism is a shared canonical prompt block in `marker` mode, not per-role prose and not a `bin/` gate.** Three grounds, in order of weight. (i) The prose form is *measured* as having failed: the rule was live in every playbook block for the whole cycle and the class still recurred at the four sites the retro enumerates, across four different roles. (ii) Four hand-written copies of one procedure drift, and the repository already has the answer — `registry.txt:57` registers `record-portability.md` in `marker` mode against six role files, so the checker, the CI dogfood step and the fixture suite that verify such a block all exist and need nothing new. (iii) A `bin/` gate is rejected on a measured property of the target rather than on cost: the opt-in rule is off by default precisely because its remaining population cannot be separated from a real key by any shape, so a gate refusing a hand-off on a hit would refuse on this repository's own design-point vocabulary. The classification is a judgement; the step is therefore a role duty whose output is a recorded, re-runnable summary line, and the mechanical part is that the duty's text is identical in four roles.

**DP2 — the prescribed mode is `--all`, not the change-scoped default.** Measured in the source: change-scoped mode reads each changed path through `git cat-file -p "HEAD:$path"`, i.e. the committed blob, while `--all` enumerates tracked plus untracked-but-not-ignored paths and reads them from disk. The step runs *before* the hand-off is written, so the records it is about are routinely uncommitted, and the default mode cannot see them at all. This is the one design decision most likely to be reversed by someone reading only the usage text, which is why **AC6**(b) pins it with a negative control rather than leaving it to the block's prose.

**DP3 — the verdict is the filtered `FINDING` lines, never the bare exit status.** `--all` exits 1 when anything anywhere in the tree matched, and with the opt-in on, this repository's corpus matches in quantity — a sibling task's own hand-off measured that population in the hundreds on the board alone, every hit accepted noise. So the block requires filtering by the `path=` field, and fixes the exit contract explicitly: `0` and `1` are scans that completed, `2` is a scan that did not, and a scan that did not complete is never an absence of findings.

**DP4 — the consumer set is the four roles with a shell.** `agents/pm-spec.md`, `agents/tech-lead.md` and `agents/ui-designer.md` carry no `Bash` in their frontmatter `tools:` list, so a duty naming a command would be unsatisfiable there — the exclusion is a measured property, not a judgement about whether those roles write records (two of them do). `agents/triage-orchestrator.md` and `agents/drift-evaluator.md` have a shell but are not phases in the loop's per-round hand-off chain; they are excluded and the exclusion is disclosed rather than silent, with **AC4** locking both classes out.

**DP5 — the adopter-facing surface is the gate's own adopter documents, not the changelogs.** `CONTRIBUTING.md` fixes that a release does not run the loop and that changelog entries are prepared by the release procedure, and both changelog files' self-descriptions say the same of themselves. A feature task adding an entry would contradict a procedure this repository shipped two tasks ago. `docs/pii-controls.md` and its Japanese counterpart are where an adopter reads what this gate is and how it is run, so that is where they read when the loop runs it.

**DP6 — the summary line's grammar lives only in the block; no role's `## Output` template is edited.** Putting `- shape-scan:` into four fenced hand-off templates would create four more copies of one grammar in four files the prompt-sync checker does not compare against each other — the exact drift the block form exists to prevent. The block states the grammar once and the role emits the line; **AC5**'s zero-deletion lock is what holds the existing templates byte-for-byte intact.
