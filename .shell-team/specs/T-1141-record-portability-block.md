# One canonical rule for naming what lies outside the repository a record lives in

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1141

## Problem

Every record this loop writes is committed, and a committed record can be read from, or copied into, a repository other than the one it was written in. Six shipped role prompts write such records, and none of them states how a record refers to a project, a tracker, a person or a machine that lies outside the repository the record lives in: `agents/scrum-master.md` carries a de-identification rule for lesson candidates only, and `agents/pm-spec.md`, `agents/engineer.md`, `agents/qa-verifier.md`, `agents/codex-reviewer.md` and `agents/tech-lead.md` carry none at all. `agents/scrum-master.md`'s `## Inputs you read` section likewise fixes what an orchestrator's relayed material may contain for nine canonical inputs, and says nothing about a relay describing a run that happened in another repository. The result is a record whose substance is correct but whose portability depends on the writer's judgement at the moment of writing.

The rule is authoring-time discipline, not detection: `bin/check-pii-shapes.sh` matches shapes, and a project name, a person's name or a machine's name is a named entity that no shape separates from ordinary prose. Stating the rule once, in one canonical place, and having a machine verify that every consumer carries the identical text, is the whole of what a mechanism can do here.

## Non-goals

- **Changing the behaviour of any checker or generator.** No file under `bin/` is edited: not `bin/check-prompt-sync.sh`, not `bin/check-retro.sh`, not `bin/check-pii-shapes.sh`, not `bin/gen-codex-agents.sh`, not `bin/gen-playbook-blocks.sh`. The rule is carried by prompt text that existing checkers already verify.
- **Shipping a detector for the rule.** No new pattern id, no new regex, no allow-list and no gate that reads free prose for a name. The rule keeps an identifying name from being written down; it does not find one already written, and nothing in this task claims otherwise.
- **Editing any committed retro.** The population under the resolved retros directory is read and validated, never rewritten.
- **Extending the block to any role beyond the six.** `agents/ui-designer.md`, `agents/triage-orchestrator.md` and every file under `skills/` are untouched, and no consumer is added to any registry row other than the one this task adds.
- **Adding, removing or editing any CI step.** Every gate this task's edits reach already has a step in the workflow.
- **Translating the block or shipping a language counterpart for it.** The block is agent-facing text, and a second copy doubles the maintenance surface without adding a reader.
- **Re-freezing, widening or repairing any merged task's frozen criterion.** Criteria this change could flip are disclosed in `## Blast radius` and never repaired here.
- **Merging.** Both gates must be green and the pull request joins the stacked train awaiting the batch GO.

## Decision points, resolved

**DP-1 — the block is hand-authored and hand-spliced, not generated.** Measured at the generator's own source: `bin/gen-playbook-blocks.sh:217` fixes `ROLES="engineer qa-verifier tech-lead pm-spec"` and the generator writes and splices `playbook-<role>.md` for exactly that list; `bin/check-prompt-sync.sh` is check-only by an explicit design decision stated in its own header. So there is no generator step for a new block: the canonical file is authored under `templates/prompt-blocks/`, the row is added to the registry, and each of the six consumers' copies is pasted by hand and verified by the checker. Any description of this work as "spliced by the existing generator" is wrong at the mechanism.

**DP-2 — `marker` mode, not `contain`.** The rule's value is that all six copies say the identical thing: a reader of any record, from any of the six roles, is subject to the same sentence. `contain` mode asserts only that each canonical line appears somewhere in each consumer, which permits six copies that diverge in structure and in the surrounding qualification while each still containing the lines. `marker` asserts region identity against the canonical file. The cost is that `agents/scrum-master.md` and `agents/codex-reviewer.md` carry no marker pair at the branch point (measured: 0 each), so the change introduces a first pair into each — a pure addition of two comment lines plus the region, refused by no checker and observed by **AC3**'s per-file assertion.

**DP-3 — the relay boundary lives in `## Inputs you read`, not in the shared block.** The four prohibited categories and the `orchestrator record` citation form are a contract about material an orchestrator passes to one role, and only `agents/scrum-master.md` receives such material; the shared block governs how any of the six roles writes about something outside the repository. Putting the relay boundary in the shared block would give five roles a duty with no carrier, which is exactly the failure mode a duty written into a shared region acquires. The section that already fixes what nine canonical inputs may contain is the scoping idiom this file uses for this situation, so the boundary is added there.

**DP-4 — the fixture is a negative control with a paired positive control, in one file.** A negative control alone proves nothing: a fixture that never reached the scan is clean for the wrong reason. The suite's own established answer is a paired assertion that the same fixture path, with the one feature that makes it a real shape restored, does report — which is why **AC8** requires both labels and why the positive control carries a named reference under the opt-in. The fixture is assembled at runtime inside the suite's existing throwaway-repository helpers, and no file is added under `tests/check-pii-shapes/`, because a stored fixture would be a byte of the very shape the checker reports.

**DP-5 — the retro template is the adopter surface.** The template ships and an adopter copies its text into every retro their loop writes, so the external-run form has to be visible there rather than only in a role prompt an adopter never opens. The template is itself linted, so the form is added beside the cycle-scope and pull-request lines while the five section markers and the ledger lines stay byte-identical — an addition to the template, never a rewrite of the structure the linter validates.

```markdown
## Record portability

- **Refer to a project, a tracker, a person and a machine outside this repository by role, never by name.** A record you write is committed, and a committed record can be read from, or copied into, another repository. Write `the adopter repository`, `the adopter's ticket`, `the operator` and `the workstation` where a repository name, a ticket key, a person's name or a machine name would otherwise go.
- **Measured values and verdicts carry the substance.** Durations, counts, exit statuses, verdict labels and executor names are what a later reader acts on; a name only says whose run it was, which is the one thing that does not travel.
- **This is an authoring-time discipline, not a detector.** It keeps an identifying name from being written down; it does not find one already written.
```
