# Parallel-by-default for mechanism-class verification sweeps, and the execution host written into the rules that govern it

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1112

## Problem

The serial-by-default habit for mechanism-class sweeps — verification units with no LLM judgment inside — reproduced inside the very task that shipped the reflection mechanism meant to catch it, and stopped only after three operator interventions (`.shell-team/interventions/T-1109.md` entries 2–4). Measured on the same population: a 6-way parallel sweep completed 113/113 two-arm member runs in ~92 minutes against a ~6h serial projection. Two days later the same class re-fired one layer up: the *execution host* of a fan-out was a free variable nothing priced, so a sub-agent-hosted fan-out was elected by division-of-labour inertia and corrected only when the operator asked what verified it (`.shell-team/interventions/T-1110.md` entries 1–5). The operator then ruled that executor configuration is either unified on one form or governed by an explicit branching rule, and that any ranking claim must be evidence-backed. Today the rules say the opposite of both findings: `docs/loop-engineering/phase-multiplexing.md`'s `verify-mechanism` axis still makes `serial` the unconditional default and `tier1-fanout` a conditional gated on a precondition that has since been discharged, and `templates/prompt-blocks/fanout-orchestration.md` still opens by declaring that no phase is rewired to fan out by default and frames the executor as "N instances of one role" — the one hosting form the operator's data rules out for mechanical units.
