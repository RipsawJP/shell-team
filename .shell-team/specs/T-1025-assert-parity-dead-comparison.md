## Problem

`assert_parity()` in `tests/is-span-row-parity/run.sh` performs three checks per class: the frozen expected answer against `bin/rollup-runs.sh` (line 94), the same frozen answer against `bin/cluster-failures.sh` (line 95), then a parity comparison between the two consumers' own classifications (line 96). Under `fail-fast` — each check is `… || fail "…"`, and `fail()` exits 1 — line 96 is unreachable dead code by transitivity: it only ever executes when lines 94 and 95 both held, and `rc_class = expected = cc_class` already implies `rc_class = cc_class`. A Codex adversarial pass on T-1019 confirmed it.

No detection power is lost by removing it: T-1019's own AC4/AC5 mutation experiments patch exactly one copy of `is_span_row` each and require the failing output to name that one script plus `kind-event.jsonl`, and lines 94/95 are what produce those messages. What is actually broken is the *documentation*: the suite's header comment ("asserted three times") and T-1019's provenance entry 1 ("THREE separate assertions") describe a structure the code no longer needs, so the next reader either believes a dead line is load-bearing or re-adds one after someone else deletes it. That is the cost this task pays down — a truthful comment plus a durable pointer, not a behavior change.

### Settled decisions

Each decision below is resolved. Nothing here is left to implementation judgment. Every measurement attributed to the tech-lead was taken from his live reading of the real files; the engineer re-verifies rather than inherits.

- **D1 — the third comparison is DELETED. Reordering is REJECTED, and the rejection is grounded twice.** Issue #108 offers "delete OR reorder-parity-first"; reorder is refused on both of the following, and both are frozen here so the argument does not have to be re-run in a review round.
  1. **Transitivity.** Under fail-fast, the three pairwise comparisons over `{rc_class, cc_class, expected}` are such that any two imply the third. Reordering therefore does not remove a dead line, it *relocates* it: parity-first makes `cc_class = expected` the unreachable one instead. The issue's own reorder suggestion does not fix the finding it reports.
  2. **Discrimination.** The parity failure message (line 96) names **both** script paths, while lines 94 and 95 each name exactly **one**. Parity-first would make T-1019's AC4 (which greps the failing output for `bin/rollup-runs.sh`) and AC5 (which greps it for `bin/cluster-failures.sh`) pass on *either* mutation direction, erasing the directional attribution D5 exists to provide. Deleting the parity line maximizes discrimination; reordering destroys it.
- **D2 — T-1019's provenance entry 1 is NOT edited, and no supersede note is added to it.** `bin/check-provenance.sh`'s schema admits only the `decision:` / `reason:` / `grounding:` triple inside the marker region, so a free annotation line there is a structural error — a supersede note is structurally impossible, not merely undesirable. The correction is recorded instead as **T-1025's own** decision/reason/grounding triple in `.shell-team/provenance/T-1025.md`, whose `grounding:` cites `.shell-team/provenance/T-1019.md` (its decision entry 1) as the record being corrected. The durable pointer for a future reader lives in `run.sh`'s rewritten comment — the transitivity reason plus the `#108` reference — so a "helpful" third comparison is not reintroduced by someone who never opens a provenance file.
- **D3 — T-1019's spec is not corrected either, because it was never wrong.** T-1019's Goal already says each class is "asserted twice"; the "three checks" claim was introduced implementation-side (the suite's comments and the provenance entry). The resolution this spec states, for the record: **agreement with a common frozen value is the stronger statement**, and parity remains asserted by implication rather than by a separate line — proven by T-1019's own AC4/AC5, which detect a one-sided drift through lines 94/95 alone. The `pass` line's wording ("`bin/rollup-runs.sh` and `bin/cluster-failures.sh` agree") therefore stays truthful and stays byte-unchanged.
- **D4 — the edit is confined to `tests/is-span-row-parity/run.sh`, and inside that file to three places.** Delete the third comparison (line 96 at the base ref). Rewrite the header comment's "asserted three times" paragraph (lines ~19–22) and the `assert_parity` doc comment's "Three checks per D4/D5" paragraph (lines ~85–88) to state: two checks, the transitivity reason the third is absent, the `#108` reference (header), and the D5 message shape (doc comment). Everything else is byte-unchanged — the `pass` line's wording, all six frozen assertion ids, both `classify_*` helpers, the `fail`/`pass` helpers, the fixture table order.
