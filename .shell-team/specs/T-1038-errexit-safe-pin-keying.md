## Problem

`tests/errexit-safe/run.sh` registers ten stderr writes in `bin/` as deliberately unguarded-exempt, and it pins each one as a `file:line:content` triple. The line field is not part of what a human reviewed — the reviewed subject is the *write*, its text and its exemption reason — but it is part of the key, so any edit anywhere **above** a pinned line shifts the number and the registry goes stale. Seven tasks have each paid a re-measurement for that (T-1006, T-1007, T-1008, T-1016, T-1017, a T-1021-adjacent lock and T-1022), and T-1022's single pin alone is coupled to **six lines / seven occurrences** in the suite. The keying is, in other words, an instance of exactly the position-pin staleness class this sprint has been closing elsewhere — living inside the mechanism that is supposed to catch staleness. The repair is not to re-measure faster: it is to stop keying on a field nobody reviewed, without weakening what the pins assert.

## Goal

<!-- BEGIN intent-block: T-1038 -->

`tests/errexit-safe/run.sh`'s `NOT_APPLY` registry keys each exemption on **the file plus the raw source line's content**, with the **declared occurrence count** carried explicitly in the record, and never on a line number. One mechanism — the declared counted-key set against the measured counted-key set — produces both the forward judgment (a candidate the registry does not account for) and the reverse judgment (a registered key whose measured count in its file no longer equals its declaration, including zero), so both of the suite's existing meanings survive the re-keying rather than being traded away. The suite proves that mechanism non-vacuous in three directions: a registered line rewritten to an unsafe shape is caught **forward and reverse at once**, a **second byte-identical unguarded line added to the same file** is caught by the count and not absorbed by a set difference, and every probe runs against a private copy of `bin/` while the real `bin/` is proved unchanged afterwards by re-derivation rather than by a restore. The seven textual occurrences of the one coupled pin collapse to a single runtime derivation from the registry, and no registry key survives as a second literal anywhere in the file. `.shell-team/test-recipe.md`'s three re-measurement procedures, which exist only because of the position field, are rewritten in the same change. Nothing else moves: `bin/` is byte-identical, and so are the suite's counterfactual, its behavioural rows and its protected-content locks.

### Settled decisions

Each decision below is resolved; nothing here is left to implementation judgment. Every text this task ships as a fixed string is frozen byte for byte in this section, and every acceptance criterion reads its expected bytes **out of this file** rather than restating them — so a criterion cannot drift from the text it guards.

- **D1 — the key is `<file>:<content>` and the judgment is declared count against measured count.** A registry record is one physical line shaped `<count><SP><file>:<content>`: an unpadded decimal integer, exactly one ASCII space, the `bin/`-relative file name, a colon, and then the source line **byte for byte**, leading whitespace included. The file name supplies the parse boundary — `bin/` names match `[A-Za-z0-9._-]+` and contain neither a space nor a colon, while contents freely contain colons — so the count is everything before the first space and the content is everything after the first colon. **No line number appears in a key, in a record, or in any assertion.**

  The judgment is a comparison of two counted sets, `comm -23` for forward and `comm -13` for reverse, exactly as today. A count change therefore surfaces on **both** sides simultaneously (`1 K` declared-only, `2 K` measured-only), which is informative rather than redundant and is what the failure messages must say.

  **The alternative was rejected on a measured decoy, not on taste.** A set difference over *deduplicated* content keys — the obvious minimal edit — loses cardinality: add a second byte-identical unguarded line to a file that already has one registered, and the deduplicated key set is unchanged, so the new site is absorbed silently and never reviewed. That is strictly weaker than the position keying it replaces, which would have shown two distinct triples. Carrying the count restores the discrimination and, unlike an occurrence-index or an anchor+content scheme, it needs no second field that a later edit can shift. An occurrence-index key (`<file>:<n-th occurrence>:<content>`) reintroduces a position-like field that reorders when an earlier occurrence is deleted; an anchor+content key needs an anchor that is itself a position pin under another name. Both were considered and both fail the same decoy less cleanly than the count does.

  **One derivation constraint is load-bearing and is not an implementation detail.** The raw derivation keeps `grep -n`'s line numbers **through** its `sort -u`, and the line field is stripped only afterwards, when the key is formed and the occurrences are counted. Two byte-identical candidate lines in one file differ only in their line numbers; dropping the line field before `sort -u` would collapse them at the source and no downstream count could recover them. Line numbers therefore remain available to the *diagnostics* — a failure message may cite them so a human can find the site — while never entering a key or an assertion.

- **D2 — reverse staleness is redefined, and the redefinition preserves the meaning.** Today's reverse check means "the line at that number changed"; it fires on a fix, a removal, a **renumbering** or a rewording. From here it means: **a registered content key's measured occurrence count in its file no longer equals its declared count, including zero.** Everything the old check caught that was ever about the exemption is still caught — a fixed or deleted line drops its count to zero, a reworded line drops the old key to zero and raises a new one — and the one thing it stops catching is renumbering, which was never a property of the exemption. The forward meaning widens correspondingly: an entry in IN_SCOPE is now *either* a candidate key the registry does not carry at all *or* a registered key whose measured count moved. Both meanings are pinned as fixed strings in the suite's own failure messages, so a later reword that quietly narrows one is caught by a positive requirement rather than only by a reviewer's reading.

- **D3 — the mutation self-check runs in three directions, over every registered record, against a private copy.** The suite's existing single mutation probe becomes three, and **there is no chosen probe target at all**: every probe iterates the registry's own records, which removes both the selection question and the last reason to name a site literally.

  **(i) content rewrite.** In a private copy of `bin/`, the record's content line is replaced — matched as an **exact whole line**, never as a regular expression — by an unsafe P1-shaped line. The re-derived counted set must differ from the registry in **both** directions: forward, because the rewritten text is an unregistered key; reverse, because the registered key's measured count fell to zero. Both are asserted; catching only one would mean the mechanism collapsed to a one-way check.

  **(ii) duplicate site.** In a private copy of `bin/`, a **byte-identical duplicate** of the record's content line is appended to the same file, and the derivation is re-run **from that copy** — that is, the mutation is applied to the candidate-derivation *input*, not to an already-counted output, so the probe exercises the real derivation including its `sort -u`. The re-derived set must differ in both directions (`2 K` measured-only, `1 K` declared-only). This is the non-vacuity proof for D1's decoy and the single most important assertion this task adds: if the counting were ever replaced by a deduplicated set difference, this probe and only this probe would go red.

## The two honest losses

**Loss 1 — within-file movement stops being detected, and abandoning it is correct.** Under position keying, moving a registered line inside its own file broke the key and fired the reverse check. Under content keying it does not, and nothing here restores that. This is not a gap to be patched later: **position was never the reviewed property.** What a human adjudicated at T-096, T-110 and T-1031 was that *this write, with this text, in this file* continues past its own failure and is therefore exempt from the `|| true` guard. Moving it up or down twenty lines changes nothing about that judgment. The old firing on movement was an accident of the derivation tool printing `grep -n`, and it produced seven false alarms — each costing a task a re-measurement — for zero true positives. Final-state semantics say the same thing more generally: the invariant worth asserting is what is true of the file now, not which sequence of edits produced it.

**Loss 2 — two byte-identical sites in one file become indistinguishable, and the guard escalates exactly that case.** Under position keying, `foo.sh:12:X` and `foo.sh:99:X` were two separate records, each individually reviewed and individually revocable. Under content keying they collapse to one key with a declared count of 2. The multiplicity guard preserves **detection** — a count that moves in either direction fails the suite — but it does not preserve **discrimination**: the registry can no longer say which of the two identical sites a reviewer approved, and a task that deletes one exempt site while adding another identical one elsewhere in the same file nets to no change at all. That is a real reduction in resolving power and it is accepted for three stated reasons: today's population has **zero** within-file content collisions, so the case is currently hypothetical rather than live; when it does arise the count moves and the suite fails loudly rather than absorbing it, which is strictly better than the deduplicated set difference this design was chosen over; and the failure message may cite the raw `grep -n` line numbers as a **diagnostic** so a human can find both sites immediately — those numbers never enter the key, so they can help a reader without staling a record. The declared behaviour for a collision is therefore escalation to human review, which is what the original pins existed to protect in the first place.
