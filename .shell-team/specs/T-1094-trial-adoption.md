## Problem

An adopter who wants to try the loop on one real ticket has no supported way to do it. The loop's gates are built on the premise that the operating files are **tracked** — the durability barrier resolves each required record through a commit's tree, the PII gate reads committed blobs, the frozen-intent ledger lives on the board, and the loop's own probe-evidence convention cites records by `git show <sha>:<path>` — so the obvious low-friction move, "just run it locally and don't commit anything", quietly disables or hollows out exactly the machinery that makes a green flag mean something. Today `docs/adopting.md` says nothing about a trial at all, and its one passage that touches the question — the paragraph presenting "keep the base dir out of git" as a neutral operator choice — names no gate consequence. The next adopter's orchestrator therefore re-derives an answer from scratch, and may re-derive the wrong one.

**Goal (one sentence).** `docs/adopting.md` and its `docs/adopting.ja.md` mirror gain one new section that gives an adopter a **supported trial route** — create a real branch, scaffold onto it with shipped mechanics, commit the operating files there, run the loop, and delete the branch afterward — states plainly what that deletion destroys and what it leaves alone, and records the **decided rejection** of an untracked local-only mode together with the named, per-gate consequences that rejection rests on, each consequence quoting a token that lives in the named checker's own bytes; the existing "keep the base dir out of git" paragraph is reconciled so it points at that decision instead of contradicting it; and the whole change ships with **no executing-surface byte**, the `team-init --trial-branch` convenience flag deferred to issue **#348**.

**The supported route, frozen as substance rather than as wording.** The route is the trial **branch**: a real, ordinary git branch in the adopter's own repository, on which the base dir is scaffolded by `team-init` and then **committed**, so every operating file the loop's gates read is tracked exactly as they assume. Two properties make it the right route rather than a compromise. First, it costs no new mechanism: `bin/team-init.sh` runs no git command at all and is branch-agnostic by construction, so `git switch -c <trial-branch>` followed by `team-init` is the complete setup, and the deferred flag is convenience over a capability that already ships whole. Second, it keeps the trial reversible without asking the adopter to weaken anything: the branch is **unmerged by design**, so nothing reaches their mainline unless they choose to bring it there, and the teardown is one branch deletion rather than a hunt for scattered files. The section states the setup commands and the teardown commands as runnable blocks, with the loop's own invocation between them.

**The teardown, stated at full precision because it is destructive advice in someone else's repository.** Deleting an unmerged trial branch destroys every commit **reachable only from** that branch — the scaffolded base dir, the board, the spec and the task's records — and nothing else: no other branch's tip moves, no mainline history changes, and no file the adopter never committed to the trial branch is touched. Because the branch is unmerged by design, git's own safety refusal makes `git branch -d` decline it and the deletion needs the force form `git branch -D`; that force flag is the **expected, non-anomalous** case here rather than a sign something went wrong, and the section says so instead of leaving the adopter to guess. The disclosure is honest in both directions: those commits stay recoverable from `git reflog` until they are garbage-collected, so the section names the reflog rather than overstating the loss.

**What "unmerged" does not buy, stated because the isolation claim rests on it.** Not merging the branch is not the same as not propagating it, and the shipped section says so rather than letting an adopter infer a guarantee git does not give. A commit made on the trial branch can still reach the mainline without that branch ever merging: an adopter or their automation can `cherry-pick` from it, or `push` it to a shared remote where someone else's pipeline or another person picks it up. So the section states the condition the isolation actually depends on — keep the trial branch **local**, and if it was pushed, delete the remote copy too when the local one goes, and do not `cherry-pick` off it while mainline isolation is the point. The safety rests on the adopter's own discipline, which is exactly why the condition is written down instead of assumed.

**The rejection, and the gate list its authority rests on.** Running the loop with the operating files never committed — git-ignored, or simply never added — is **not supported**, and the reason is stated per gate, in the failure mode each one actually has **and in the scenario that actually reaches it**, rather than as one blanket claim that they all stop working. The four claims appear in the shipped section as four consecutive passages in a fixed order — durability, PII, frozen intent, resolver — each one its own passage, which is what lets **AC3** bind a claim's direction to the gate it is about instead of accepting the same vocabulary anywhere in the section.
