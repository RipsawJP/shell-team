# The executor binding capability becomes visible to adopters, on all four adopter-facing surfaces, with its honest boundary

**Status**: READY_FOR_ARCH
**Owner**: pm-spec
**Task ID**: T-1060

## Problem

Sprint v2.0.0 shipped a host-authored executor binding: `bin/check-binding.sh` validates a `<base>/binding.conf`, `bin/resolve-executor.sh` resolves each of the six inner-loop roles' executors fail-closed against it, `bin/team-init.sh` already scaffolds an inert `<base>/binding.conf.example`, and two adapter definitions declare what effort values each executor accepts. None of that is documented anywhere an adopter reads. `README.md` mentions `binding.conf` only inside one design-choices bullet about the reviewer's own default; `docs/adopting.md` does not mention it at all, and its `<base>/` layout tree omits the specimen file `team-init` writes. The operator's ruling on issue #244 is the framing: a major version whose core capability is not shown to humans has shipped effectively nothing — so this is release-completing work rather than a documentation nicety.

## Summarized sources

- `templates/binding-default.conf` (its six `bind` rows and the comment block above them) — the distinction carried over: this file, resolved from the plugin's **own installed directory**, is where the shipped default lives; `<base>/binding.conf` is the **host override** the resolver prefers when present. The two are not the same file and the documentation must not locate the default in the override (this is the exact conflation T-1059's round-1 review found as a Major on `CLAUDE.md`). Also carried: `codex-reviewer`'s model column is the ordinary token `provider-configured`, naming the boundary that the measured Codex invocation passes no model flag at all, and a bare `-` is **not** a legal model value — only the effort column spells "unset" that way.
- `templates/binding-template.conf` (its header comment and its `schema 1` + six `bind` rows) — the distinction carried over: the grammar is one required `schema <version>` line plus exactly one `bind <role> <provider> <model> <effort|-> <adapter>` row per role; `#` comments and blank lines are skipped; row order and extra whitespace do not matter; `effort` is **positionally required** and spells "no value" as a literal `-`, never by omitting the field. Also carried: this is the file `bin/team-init.sh` copies, and the format itself enforces **no** cross-provider rule — a host is free to bind every role to one provider.
- `bin/check-binding.sh` (its `## Usage` header block and its exit-code paragraph) — the distinction carried over: the invocation surface is `check-binding.sh [--config PATH] [--adapters PATH]`, plus `--print-binding`, `--print-lock`, `--verify --lock PATH --config PATH` and `--help`; with no `--config` it validates `<base>/binding.conf` where `<base>` comes from `bin/team-paths.sh --get base`; exit `0` = valid, `1` = a content refusal, `2` = the input could not be evaluated at all. `--adapters` is a **testing affordance**, not an adopter-facing knob.
- `bin/resolve-executor.sh` (its `## Usage` block, its refusal-token block, and the occupancy lattice at lines 319-326) — the distinction carried over: `--role <role>` prints exactly one line `resolved <role> <provider> <model> <effort|-> <adapter> <probe-kind>` where probe-kind is `in-process` or `out-of-process`; `--print-resolved` resolves all six roles and runs **no availability probe at all**, printing six `resolved` rows with no probe-kind field. The closed refusal set with its exit codes is `usage` (2), `binding-unresolved` (2), `capability-unsupported` (1), `contract-violation` (1), `executor-unavailable` (1); every refusal is one token on stderr with **zero bytes on stdout**. And the fail-closed case an adopter can actually hit: a **non-regular-file occupant** at `<base>/binding.conf` (a directory, a FIFO, a dangling symlink) refuses `binding-unresolved` and is *never* silently substituted with the plugin default, which is reserved for true absence.
- `templates/adapters/claude-cli.txt` and `templates/adapters/codex-cli.txt` (their `capability effort` / `effort-mechanism` / `effort-value` rows) — the distinction carried over: each adapter declares its **own** effort vocabulary, and there is no global one. `claude-cli` declares mechanism `cli-flag` with five values; `codex-cli` declares mechanism `cli-config-override` with seven. An effort value the bound adapter does not declare is refused `capability-unsupported`. The documentation states each set as that adapter's, never as a shared list.
- `templates/binding-adapters.txt` — the distinction carried over: the adapter allowlist is two rows (`claude-cli claude`, `codex-cli codex`), resolved from the checker's own installed directory; pairing an adapter with the wrong provider is refused `provider-adapter-mismatch`. Custom adapters are explicitly out of scope for this cut and are **not** something an adopter is expected to add by editing that file.
- `templates/prompt-blocks/executor-resolution.md` (its single canonical line) — the distinction carried over, and it is the honest boundary this spec is built on: "a role's actual invocation still routes through that role's own pinned model value, not through this resolution", and "a custom binding that departs from the shipped default records the bound model as **telemetry**, not an independently verified executed one". A rebind changes what resolution reports and what telemetry records; it does not wire an alternate-executor invocation path.
- `docs/loop-engineering/task-envelope.md` `## The generalized invocation pattern` — the distinction carried over: a missing CLI or a failed auth check is `BLOCKED` with the exact error, "never a **silent substitution** of a same-family reviewer". This bounds what fails closed (a silent substitution *at invocation time*) and says nothing about the legality of a *declared* same-family binding. The documentation must not flatten those into "same-family review is impossible".
- `bin/team-init.sh` (its `BINDING_TPL` assignment at line 149, the `copy_template` call at line 261, and the completion message at lines 281-282) — the distinction carried over: the scaffolded specimen is written **inert** as `<base>/binding.conf.example` from `templates/binding-template.conf`, precisely so the resolver's `<base>/binding.conf` lookup never finds it; an adopter opts in by **renaming** it. Copying the template by hand is therefore only needed where `team-init` has not run. This is why the how-to's first step is a rename rather than a copy.
- `bin/team-paths.sh` (`--get base`, line 184) — the distinction carried over: `<base>` is resolved, never hardcoded; two layouts are supported and a hardcoded path is correct in at most one of them.
- `README.md` line 208 and `README.ja.md` line 208 (the reviewer design-choices bullet delivered by T-1059) — the distinction carried over: that bullet already states the **reviewer row's** default and its rationale (a model reviewing output from its own family shares its blind spots) together with the rebind consequence. The new section is the **six-role mechanism**; the bullet stays the reviewer row's default-and-why. No contradiction, no duplication.
- `docs/adopting.md` lines 19-32 and `docs/adopting.ja.md` lines 20-33 (the `<base>/` layout tree) — the distinction carried over: the tree is already an **abridged** listing (it omits `provenance/` and `interventions/`, which `team-init` also scaffolds), so adding `binding.conf.example` is this task's own scope and not a completeness repair of the tree.
- `README.md` `## Layout` (lines 111-150) — the distinction carried over: that tree is the **plugin repository's** own tree, already abridged (`bin/` lists eight of forty-one scripts), not the adopted `<base>/` tree. It is therefore *not* a same-class site for the `binding.conf.example` gap, and this task leaves it alone deliberately rather than by omission.
- `bin/check-readme-version.sh` (its header, lines 1-34) and `.github/workflows/check-handoff.yml` line 111 — the distinction carried over: the only mechanical reader of a README edit is the badge/manifest comparison, wired in CI as `bash bin/check-readme-version.sh README.md README.ja.md`, and it looks **only** at the static version badge. Its suite is `tests/check-readme-version/run.sh`. No suite reads `docs/adopting.md` or `docs/adopting.ja.md` at all (measured: those paths appear in no file under `tests/`).
- `.shell-team/specs/T-1057-loop-integration.md` **AC16** / **AC18**, `.shell-team/specs/T-1058-telemetry-binding.md` **AC7**, `.shell-team/specs/T-1059-docs-release-notes.md` **AC7** / **AC8** / **AC10**, and the six `- population:` declarations across `.shell-team/specs/` — read first-hand for `## Blast radius`; the distinction carried over is which clause of each this task's diff reaches, and specifically that **only T-1059's declared population of 64 still equals the live corpus count**, so it is the only population criterion this task's new spec file newly reddens.

## Goal

<!-- BEGIN intent-block: T-1060 -->

All four adopter-facing surfaces — `README.md`, `README.ja.md`, `docs/adopting.md`, `docs/adopting.ja.md` — carry a section, at the same heading ordinal in each language pair, that shows the v2.0.0 executor binding capability: that each of the six inner-loop roles' executors is host-assignable through a `<base>/binding.conf`; a three-step how-to (rename the scaffolded `binding.conf.example`, edit the `bind` rows, validate with `check-binding.sh` and inspect with `resolve-executor.sh --print-resolved`); a grammar example that the real validator accepts; and, on the adopter-workflow pages, what the no-config default gives you, the fail-closed refusals an adopter will actually see with their exit codes, and each adapter's own declared effort values. Every statement of fact about the mechanism is derived from the shipped files rather than restated from memory, and every surface states the same honest boundary: a rebind changes which executor resolution reports and which value telemetry records, and does **not** wire an alternate-executor invocation path — two separate limits, stated separately on every surface: a role's invocation still takes its **model** from that role's own `agents/<role>.md` pin rather than from the resolved row, and issue #236 is the tracked retirement of those pins for the five `claude-cli`-bound roles only, `codex-reviewer` deliberately excluded; and which **executor** a role is invoked through is not routed by resolution at all, with no issue tracking that. The change is purely additive prose: no behaviour, no config grammar, no checker, no suite and no CI step moves.

## Non-goals

- **No behaviour change, and no change to the binding config grammar.** Nothing about what `check-binding.sh` accepts, what `resolve-executor.sh` resolves, or what a `bind` row means is altered, extended or narrowed by this task. The documentation describes the mechanism that already shipped.
- **No checker, no test suite and no CI step is added, edited or removed *by this task*.** There is no doc-content checker for these four files today and this task ships none; the acceptance criteria below are this task's own verification surface.
- **No edit *by this task* to any of the eight canonical sources** — `templates/binding-default.conf`, `templates/binding-template.conf`, `templates/binding-adapters.txt`, `templates/adapters/claude-cli.txt`, `templates/adapters/codex-cli.txt`, `templates/prompt-blocks/executor-resolution.md`, `docs/loop-engineering/task-envelope.md`, and the two resolver/validator scripts `bin/resolve-executor.sh` / `bin/check-binding.sh`. The prose derives from them; it does not amend them.
- **No edit *by this task* to any `agents/*.md`, any `skills/*/SKILL.md`, anything under `bin/`, `tests/`, `templates/`, or `.github/`, and none to `CLAUDE.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `CHANGELOG.ja.md` or `.claude-plugin/plugin.json`.** Phrased as a claim about **this task's own edits** rather than about the tree's state, because this branch is the first of a stacked sprint and a tree-state phrasing would be the wrong shape to reuse later in the stack.
- **No version bump, no badge move, no CHANGELOG entry.** Those belong to the release procedure, not to this task.
- **No `README.md` `## Layout` edit.** That tree is the plugin repository's own, already abridged by design, and is not the adopted `<base>/` tree this task documents.
- **No completeness repair of the `<base>/` layout tree in the adopting docs.** Exactly one line is added to it — `binding.conf.example`. The tree's other omissions (`provenance/`, `interventions/`) are pre-existing, out of scope, and left as they are.
- **No rewrite of the reviewer design-choices bullet at `README.md` / `README.ja.md` line 208.** It is T-1059's delivered text, it states the reviewer row's default and its rationale, and this task's section neither repeats that rationale nor contradicts it.
- **No adopter-docs acceptance-criteria standing gate.** Issue #244's requirement 4 states the process half is a separate task (T-1061); nothing here creates, proposes or pre-shapes that gate.
- **No repair, widening or annotation of any merged criterion**, including the ones this task's diff reddens. Every red is disclosed in `## Blast radius` and differenced; none is fixed, and no merged spec gains a `- stale-at:` line from this task.
- **No claim, anywhere on the four surfaces, that rebinding routes an invocation.** Equally, no claim that a same-family binding is impossible or refused. Both directions of that line are forbidden, not just the over-claim.

## Round-4 design note — the claim→source table

**This section is outside the intent-block markers.** Nothing in it is frozen, it adds no acceptance criterion, and it changes no `- check:` line. It exists because the same defect class has now been drawn three review rounds running and a fourth prose patch is not a response to it.

### The failed premise, named

Rounds 1-3 all failed the same way. The four sections' behavioural sentences about `bin/resolve-executor.sh` and `bin/check-binding.sh` were **hand-authored from a paraphrase of the mechanism**, and the acceptance criteria that guard them (AC3, AC4, AC7) check *tokens and exit codes*, never *claim semantics*. A sentence can therefore carry every anchor those criteria require and still say something the shipped code contradicts — which happened three times: `contract-violation` presented as adopter-reachable (r1), `binding-unresolved` presented as having one cause when the resolver folds two adopter-reachable ones into it (r2), and `--role <role>` presented as verifying availability when its in-process arm is a literal no-op for five of the six default roles (r3).

The premise that failed is **authorship**. Every one of those three sentences was *plausible*, none was *transcribed*, and no gate in this loop reads the source file and the sentence side by side — the reviewer does, which is why it kept being the reviewer who found them, one per round, after the fact.

Round 4 therefore changes the engineer's job from **authoring behavioural prose** to **transcribing from the table below**. The table is the design deliverable; the docs are its rendering.
