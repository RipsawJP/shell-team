#### Major

1. **Trial-branch isolation doesn't warn against propagation, only against merge.** (mandate (a); Goal / "The supported route", Input space) The route's safety rests on the branch staying unmerged, but "unmerged" does not by itself prevent an adopter (or their CI/automation) from cherry-picking commits off the trial branch, pushing it to a shared remote, or otherwise propagating its content before deletion — any of which would carry the scaffolded operating files onto the mainline the route exists to protect, without the branch itself ever merging. The shipped section states the branch is "unmerged by design" but names no such propagation risk.
   - Suggestion: add one explicit sentence to the teardown or supported-route prose: keep the trial branch local (or, if pushed, delete the remote copy too) and don't cherry-pick from it if mainline isolation is the point.

2. **AC3's `check-durability.sh` claim conflates the default failure with the opt-out failure.** (mandate (c); Rejection paragraph, `bin/check-durability.sh:31-45`) The checker's own comment is precise: `untracked-opt-out` fires only when a `<base>/durability-mode` file itself declares `working-tree-only` but is not durably committed (a missing blob or content mismatch for *that mode file*). An adopter who commits nothing at all — no mode file, no opt-out attempt — defaults to `tracked` mode and fails as `not-in-recorded-commit` / `missing-working-file`, never `untracked-opt-out`. The spec's sentence "an untracked base dir yields `untracked-opt-out` instead" reads as the general-case verdict when it is actually the specific-attempted-opt-out verdict.
   - Suggestion: split the claim — "an adopter who tries the opt-out without committing the mode file gets `untracked-opt-out`; an adopter who commits nothing at all gets `not-in-recorded-commit`."

3. **AC3's `check-pii-shapes.sh` claim overstates what `--all` rescues.** (mandate (c); Rejection paragraph, `bin/check-pii-shapes.sh:489`) `--all` mode enumerates `git ls-files -z --others --exclude-standard`, and `--exclude-standard` excludes gitignored files. This task's own reconciled paragraph (`## Where the operating files live`) names git-ignoring the base dir as the concrete way an adopter keeps it out of git — and for exactly that adopter, `--all` mode does **not** read the record either: a gitignored record is unread in both modes. Presenting `--all` as "the named exception" without this qualifier reads as "run `--all` and you're covered," which is false for the spec's own primary rejected scenario.
   - Suggestion: state plainly that `--all` catches untracked-but-not-ignored files only, and that a gitignored record is unread by either mode.

4. **AC3's `check-intent.sh` claim names the wrong git operation.** (mandate (c); Rejection paragraph) "A working-tree reset takes the ledger with it" — but `git reset --hard` does not delete untracked files; only `git clean` or a fresh checkout/clone removes an untracked spec/board. As written this could send an adopter looking at the wrong command to understand why (or how) the ledger disappears.
   - Suggestion: name the actual operation (a fresh checkout/clone, or `git clean`), not "reset."

5. **AC3 is a token-presence instrument, not a behavioral one, and it already missed three imprecisions.** (mandate (2), the criteria-test-the-right-thing item) AC3 verifies only that named vocabulary co-occurs in the prose and in each checker's bytes — it cannot tell that a token sits on the code path the prose describes, or that reversing a claim ("refuses loudly" ↔ "passes silently") would fail the same check. Findings 2-4 above are not hypothetical: three of AC3's five gate-list claims turned out imprecise on a direct read of the checkers it cites, which is exactly the failure mode a grep-for-co-occurrence instrument cannot catch.
   - Suggestion: for at least the durability/PII/intent claims, add a small scratch-repo probe (reusing AC10's venue) that actually runs the named checker against an untracked/gitignored base dir and asserts the *documented verdict token appears on the tool's own stderr* — moving from "the word occurs in a file" to "the word is what the tool says when you do the thing."

6. **AC10 doesn't exercise the Input space it claims to cover.** (mandate (2); `## Input space`, **AC10**) The Input space's reachable classes explicitly include "Both supported layouts" (default and legacy `tasks/`+`docs/specs/`) and "An adopter who has already git-ignored `.shell-team/` globally," both stated as things "the change must handle correctly." **AC10** exercises exactly one scenario: a fresh `git init` repo, default layout, no global excludes. Its own body's claim that paths are "resolved through `bin/team-paths.sh`... including in **AC10**'s own scratch run" is true but establishes only that the *default* layout resolves correctly — it never forces the legacy arm or a global-excludes config, so it cannot show the recipe (or the checkers it invokes) behaves the same way under either declared class.
   - Suggestion: add a second scratch case under the legacy layout (a `tasks/loops/shell-team.contract.yaml` marker) or a `core.excludesFile` set to hide `.shell-team/`, or narrow the Input space's own claim to name which class **AC10** actually exercises versus which is left to QA's manual judgment.

#### Minor / nits

1. **Teardown "destroys" framing, precision only (downgraded from a primary-pass Blocker — see ledger).** `git branch -D` deletes a ref; it does not itself destroy commit objects — they become unreachable and are later garbage-collected. The frozen prose already states this correctly ("destroys every commit **reachable only from** that branch," "stay recoverable from `git reflog` until they are garbage-collected"), so the core claim is honest; the residual gap is that **AC10** verifies only that the *one other branch in its 2-ref scratch repo* is unmoved (`git rev-parse HEAD == $O`), which is a complete check within that scratch repo's own scope but does not generalize to "no other branch moves" in an adopter's repo with many branches.
   - Suggestion: no prose change needed; optionally note in **AC10**'s own body that its "no other branch moves" check is scoped to the one control branch its scratch repo creates.
2. **Orphan-branch comparison's "cannot carry them in by accident" is a defensible, already-bounded claim.** A deliberate `--allow-unrelated-histories` merge, a cherry-pick, or a copy could still carry the operating files across even from an orphan branch — but the frozen text already scopes its claim to "by accident," so this is a reminder rather than a correction: a reader should not treat either route's isolation as absolute.
3. **AC11's above-ceiling owner, a naming nuance.** "the operator (this repository's maintainer)" is a reasonable convention for this train's own residual-verification bookkeeping, but the criterion's subject sentence is phrased in terms of "an adopting organization" — worth one clarifying word that the named owner is shell-team's own maintainer dogfooding the recipe, not every adopting organization's own operator.
4. **AC5 doesn't (and doesn't claim to) verify `.ja` semantic equivalence.** Already correctly assigned elsewhere: the spec's own `## Verdict scope` names "clause-by-clause semantic equivalence against the English" as the delivered-change review's component-3 depth, not **AC5**'s mechanical job. Flagged here only so QA/engineer know the three-token check alone will not catch a materially incomplete Japanese teardown or rejection paragraph.
5. **AC1's `- above-ceiling: ` presence check doesn't bind the marker to AC11 by name.** Low risk given the spec is hand-authored with exactly one such line by construction, but the instrument only counts occurrences anywhere in the file rather than confirming the one line sits under **AC11** specifically.
