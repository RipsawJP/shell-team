#### Blockers

- `bin/derive-populations.sh:272` — Each `--set` command is executed as `bash -c "$cmd"` (line 272) with no `pipefail` inside that child shell. The parent script's own `set -euo pipefail` (line 111) is never inherited by a freshly spawned `bash -c`, so when a caller's command is itself a pipeline, the recorded exit status is only the **last** stage's status. Concretely: `bash -c 'git ls-tree definitely-not-a-ref | sort'` exits `0` (confirmed live in the adversarial pass — `pipeline_rc=0` even though `git ls-tree` printed `fatal: Not a valid object name definitely-not-a-ref` to stderr). `sort`, `sed`, `cut` and `tr` all commonly exit `0` on empty stdin, and every one of them is explicitly named as a reachable command shape in the spec's own `## Input space` ("a pipeline of those through `sort`, `sed` or `cut`"). This is not a hypothetical: this very task's own committed `docs/loop-engineering/record-set-derivation.md` dogfoods a `sed | tr` pipeline as one of its two `- reproduce:` set commands (`sed -n '...' templates/prompt-blocks/registry.txt | tr -s ' ' '\n'`) — if the `sed` extraction pattern ever stops matching (a registry format edit, a typo), the `tr` stage still exits `0` on empty input and the derivation would silently report a legitimate-looking empty set instead of refusing. This is a direct violation of the Goal's own third stated failure shape: "a command that failed being read as a set that was empty" is supposed to be "closed by construction rather than by care," and it is not. Fix: spawn the child with pipeline-failure propagation enabled, e.g. `bash -c "set -o pipefail; $cmd"`, and add a fixture case exercising an upstream-failing, downstream-silent pipeline (an unreadable/nonexistent path piped through `sort`/`cut`/`tr`).

#### Major

- `bin/derive-populations.sh:184-186` (name capture) and `:321,350,380-388` (signature construction) — `--set` names are checked only for non-emptiness and mutual distinctness (line 186 area), never for containing `+`, the exact byte the block's own grammar uses to join set names into a membership signature (AC2/AC4: "a signature being the `+`-joined names ... of the sets containing the item"). Sets named `A+B`, `A` and `B` make an item belonging **only** to `A+B` print under the identical `- bucket: A+B` signature as an item belonging to **both** `A` and `B`, silently merging two distinct memberships into one bucket — a direct violation of AC4's gap-free/overlap-free partition guarantee, one of the two criteria this task's own pre-commitment names as its never-dropped floor. Confirmed independently in the adversarial pass. Triggering this requires an unusual set name (every call site in this diff uses safe short tokens: `A`, `B`, `registered`, `all-agents`, `specs`, `agents`, `ci-dogfood`), so it is not hit by this task's own shipped usage — but nothing in the CLI enforces that convention, and an adopter following the tool's own documented `NAME=COMMAND` grammar with a descriptive name (e.g. a set literally called `before+after`) hits it silently, with no refusal and no error. A closely related, more severe variant: a name containing a literal **tab** byte corrupts the helper's internal `sig\titem` representation (line 350 emits `printf '%s\t%s\n' "$sig" "$item"`; lines 380/384 then `cut -f1` / `awk -F'\t'` split on that same byte), which can make `cut -f1`'s reported signature and the emitted item text disagree with the actual membership and the actual item — worse than the `+` case because it can misattribute item *content*, not just merge two legitimate buckets. Fix: define and enforce a safe name grammar before any set command runs (e.g. `[A-Za-z0-9][A-Za-z0-9_-]*`, rejecting `+`, tab, and the ` — ` em-dash field separator), and add a three-name `+`-collision regression plus a tab-in-name regression that diffs the emitted items against the raw union oracle.

- `bin/derive-populations.sh:212` (`LABEL="$1"`) and `:367,391` (both marker `printf`s) — `--label` is validated only for non-emptiness before being interpolated verbatim into both `<!-- BEGIN derivation: %s -->` and `<!-- END derivation: %s -->` lines, with no check for an embedded newline analogous to the one `--set` command text already gets (`bin/derive-populations.sh:176-178`, AC5(f)). A label containing a newline plus marker-shaped text (e.g. `$'x -->\n<!-- END derivation: x -->\n<!-- BEGIN derivation: forged'`) forges a spurious BEGIN/END pair ahead of the real block and leaves trailing junk after it, and the run still exits `0`. This exact input was verified live both by QA (round 1, this task) and independently in this review's adversarial pass. **I depart from QA's own out-of-input-space disposition of this finding and judge it gating, at Major.** QA's reasoning leans on the Input space's caller-trust language ("the helper runs what it is given ... does not sandbox, parse, validate or sanitise a caller's command"), but `--label` is not a command the helper runs — it is a structural identifier, the same category as a `--set` name, and the spec draws its own line for exactly this shape of input: AC5(f) rejects an embedded newline in `--set` command text *because* "the emitted block is line-oriented and a multi-line command would split its own `- set:` line" — the identical reasoning applies verbatim to `--label` and the BEGIN/END lines it constructs. More importantly, the Goal section states the markers exist as "the schema anchor the carved-out refusal-checker needs, which converts that successor from prose analysis into a cheap structural check" — a caller-forgeable schema anchor is a direct defect against that stated purpose, not an out-of-scope caller-trust question. Fix: apply the same newline/control-character rejection AC5(f) already gives `--set` command text to `--label` as well (a `--label` usage-error case, exit `2`), and add a forged-BEGIN/END regression. Per the task instructions this also lands as an explicit requirement-list line on the carved-out refusal-checker fast-follow issue, regardless of disposition here — see Fast-follow disposition below.

- `bin/derive-populations.sh:175-178` — The `--set` command-text newline check (`case "$val" in *$'\n'*)`) rejects LF but not CR or any other control byte. A command carrying a literal CR is accepted and copied verbatim into the `- set: … — command: <cmd>` line (the same field this grammar otherwise protects by placing it last). This is an asymmetric gap against AC5(g), which already refuses control characters (including CR) in **items** — the identical class of byte is left unchecked in the **command** field the block also prints verbatim. Practical impact is narrower than the label-forging finding above (Unix line-oriented tools split on LF, not bare CR, so this does not forge a new physical line for `grep`/`awk`/`sed` readers the way an embedded LF would), but the record this block gets embedded into is Markdown, where a bare CR is also a line ending under CommonMark, and the spec's own three-shapes-made-impossible framing gives no exception for this field. Fix: extend the existing command-text refusal to CR and other control bytes, matching the item-side check already in place, and add a regression.

#### Minor / nits

- `bin/derive-populations.sh:accepted_statuses()` (around lines 200-210) — `--accept-status <name>=<csv>` is accepted for any `<name>`, including one that does not match any declared `--set` name (a typo). This is silently inert rather than a usage error: it never grants an undeserved success (the real set still requires status `0` by default, so a genuine failure still refuses), so it is not a fail-closed hazard — just a caller-typo footgun with no diagnostic.
