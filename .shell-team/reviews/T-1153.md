#### Major

- `agents/code-reviewer.md:104` (the perspectives-file construction paragraph, R7) — class `ledger-format-not-required-of-the-file-it-builds`. The paragraph fixes *what topics* the perspectives file must carry (T1-T5, S-AC, S-RD, S-IS, S-R) but never instructs the file to itself request the `#### Evidence ledger` grammar (the exact table header, the closed `holds | defect | not-applicable` vocabulary, the anchor rule) that Codex's response needs to carry for the reviewer to build a complete ledger. This is exactly the gap both this round's primary pass (P2) and its own evidence pass (T1/T3/T4/S-RD rows, independently) converged on. Practically: this round only produced a complete, well-formed 23-row ledger because *this reviewer* chose, on its own judgment, to embed the exact table-and-vocabulary ask into the perspectives file — following `## Assumptions`' M2 precedent narrowly cited only for the file's *first line*, not for this. A less careful construction (a future round, or a different executing model) could easily produce a perspectives file that elicits free-form prose from Codex instead of a parseable ledger, forcing a spurious `BLOCKED — review not established` even when the underlying diff is fine — or worse, tempting a less scrupulous reviewer to fabricate ledger cells from loose prose. The spec's own `## Review depth` prices this exact question ("whether the refusal rule is decidable by the role from its own inputs every time") as full-strength scrutiny for this round (S-RD row above). Note also the cross-host asymmetry this creates: `templates/prompt-blocks/host-dispatch.md:24`'s Claude-host recipe *does* state the grammar explicitly in its own template sentence ("...return the `#### Evidence ledger` table... one row per perspective"), so only the native Codex-exec path (the one this very round runs under) has the gap.
  - Suggested fix: add one sentence to the construction paragraph, e.g. "and states the exact `#### Evidence ledger` grammar this file's own `## Output` section fixes (the header row, the closed `holds | defect | not-applicable` vocabulary, the repo-relative anchor rule), so Codex's response arrives in a directly transcribable shape." Cheap, in-scope (touches only `agents/code-reviewer.md`, already on the AC11 allow-list), and closes the asymmetry with `host-dispatch.md` without touching that file.
- `agents/code-reviewer.md:74,104` — class `spec-text-becomes-live-instructions`. Recommended (not required) low-cost hardening in the same patch as the fix above: add a one-sentence data/instruction scope rule to the perspectives file's own first line, mirroring the Claude-host template's existing sentence — this does not touch `bin/`, does not expand scope, and directly narrows a risk the spec already flags as live.
- `bin/goal-state.sh:123,128` — class `constant-token-population-degrades-no-progress-signal`. `goal-state.sh signature` computes the no-progress fingerprint by extracting the *set* of `AC[0-9]+` tokens (plus the verdict label) appearing anywhere in the verdict text via `grep -owiE 'REQUEST_CHANGES|APPROVE|PASS|FAIL|AC[0-9]+'`. Before this task, that set varied round to round with whichever ACs a reviewer's prose happened to name. After this task, every `code-reviewer` round for every task now carries an Evidence-ledger `S-AC` row for *every* acceptance criterion in the spec, every round, regardless of whether that criterion holds or is a defect — so the raw token population is a constant function of the spec's own AC count, not of what changed between rounds. This directly risks a false `STOP:no_progress` (or a missed one) on a genuinely-progressing task, for every task using this reviewer from now on — a real, cross-cutting regression in an unrelated, already-shipped safety mechanism, not something this diff's own tests can catch (per this task's own Non-goals, `bin/` is untouched and no fixture reads `goal-state.sh`). The spec's own `## Review depth` names `goal-state.sh`'s signature as a focus item for this exact round (S-RD row above), so this is squarely in scope for this review to report even though fixing it is not.

This does **not** block this round's merge (blocking would require asking the engineer to violate a frozen, never-dropped Non-goal); it is a fast-follow issue against `goal-state.sh`'s own signature logic (e.g., folding the per-row `result` value into the extracted token, or excluding ledger-interior AC ids from the no-progress fingerprint entirely and relying on the verdict label plus the Blockers/Major sections instead).
