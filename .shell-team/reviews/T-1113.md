#### Domain-premise findings (mandate item 1 — is the checker's trust argument sound)

- **Major** — The TRUST BOUNDARY paragraph this spec requires (AC9) is asserted "on exactly the `bin/check-acs.sh:15`-`:31` trust basis", but the artifact being executed against differs in provenance from what grounds that basis. `check-acs.sh` runs `check:` lines out of a **spec file** — a document this repository's own convention treats as reaching "trusted, committed, reviewed" status through the freeze/review gates before `check-acs.sh` is normally invoked against it. `check-count-claims.sh`'s live mode (DP-4, "live execution by explicit invocation only") instead runs commands out of a **task board entry** — a hand-off record that any role can edit at any point across a task's lifecycle, with no per-edit review gate; only the whole task passes through gates at specific seams (READY_FOR_REVIEW, READY_FOR_MERGE), not each board edit. A human or QA invoking live mode mid-task (before any review of that hand-off text has happened) would be executing shell commands sourced from unreviewed prose. The spec's reuse of `check-acs.sh`'s justification does not address this timing/provenance difference, and neither AC9's required literals nor its check exercise it. This is not a reason to redesign DP-4 (it is `Never-dropped`-adjacent, not `Never-dropped` itself, and Droppable-3rd already covers a fallback), but the header's TRUST BOUNDARY paragraph should say plainly that a board entry can be live-executed before any review of the entry itself has occurred, rather than silently importing a stronger provenance claim by citing `check-acs.sh`. (My own finding this round; not independently cross-checked by the narrowed Codex pass, which was scoped to three other questions — see below.)

#### Domain-premise findings (mandate item 2 — do the ACs test the right thing), cross-checked against the narrowed Codex pass

Both findings below were reached independently by first-hand reading of the spec, the referenced `bin/` sources and `tests/close-out/run.sh`, and then confirmed by a second, independent Codex pass (`.shell-team/reviews/T-1113-codex-specreview.txt`) asked the same two questions cold.

- **Major — AC3's near-miss coverage is not exhaustive against the exact defect class the spec names as most likely.** The frozen collect-wide stem is `^[[:space:]]*-[[:space:]]+count[[:space:]]*:[[:space:]]*` — a lowercase, ASCII-only literal match on the field name `count`. A row spelled `- Count:` (capitalized) or using a full-width colon (`count：`) matches **neither** this stem **nor** the strict grammar, so it is read as the conformant zero-row case (`AC4`'s vacuous pass) rather than collected-and-refused (`AC3`'s contract) — this is exactly the "stem net narrow enough that a malformed line matched neither" failure mode the spec's own Trap #1 names as the class that defeated `check-entry-mode.sh` three times. Neither shape is in AC3's fixture list (doubled space after dash, space before colon, doubled space in separator, missing command field, label with space/`+`/leading underscore, non-numeric value, interior-signed value, empty command). Confirmed independently by the narrowed Codex pass ("`- Count:` and `- count：` fail the literal lowercase/ASCII collection stem and can be silently treated as zero rows. Neither is in AC3's fixture list."). *Suggestion*: add both shapes as AC3 fixtures and widen only the collect-wide stem's field-name match (e.g. tolerate case) while keeping the strict grammar exactly as frozen — the same asymmetric fix `check-entry-mode.sh:309`-`:310`'s own history used.
- **Major — AC10 verifies the `close-out.sh` delegation only structurally, never behaviorally.** AC10's check is entirely `grep`/`cmp`-based: literal occurrence counts, the `--no-exec`/`--board`/`--task` three-literal co-occurrence on one line, the missing-sibling refusal literals, and that the two **existing** suites (`tests/close-out/run.sh`, `tests/check-entry-mode/run.sh`) still exit 0 unchanged. No criterion actually runs `close-out.sh` **live** against a fixture board carrying a malformed or value-mismatched `- count:` row to prove the new delegation's exit code maps correctly to a board-content `fail` (rather than an environment `die`, or silently passing). This is a real gap relative to precedent: the existing spec-review delegation this task is explicitly told to copy ("in the shape its existing spec-review delegation already uses") **is** exercised this way — `tests/close-out/run.sh` carries `SPEC_REVIEW_SENTINEL` fixture cases that run `close-out.sh` live against boards with malformed/absent spec-review records and assert the resulting stderr sentinel and exit code. AC10 has no equivalent for the new delegation, and AC17(a)'s own list of pre-committed mutation self-checks for AC10 (drop `--no-exec`; drop the missing-sibling refusal) does not include mutating the exit-code mapping (e.g. swapping the `1→fail`/`*→die` case arms) either — so a wiring bug in that mapping would pass every acceptance criterion in this spec undetected. Confirmed independently by the narrowed Codex pass ("AC10 uses static checks and only asserts existing suites exit successfully; it does not run `close-out.sh` live with malformed or mismatched count rows."). *Suggestion*: add one behavioral case to `tests/close-out/run.sh` (or a new AC10 sub-check) mirroring the `SPEC_REVIEW_SENTINEL` shape — a fixture board with a malformed `- count:` row, run through `close-out.sh` live, asserting exit 1 and a stderr sentinel naming the task.

#### Minor findings

- **Minor — value-shape coverage gap (`-0` and whitespace-padded output).** No AC exercises a declared or measured `-0`, and none exercises a command whose numeric output carries surrounding whitespace (e.g. `printf '  6  '`) despite the Input space section's own claim that such output "is trimmed." Confirmed by the narrowed Codex pass (labelled "medium" in its native vocabulary, normalized to **minor** per this role's severity map). *Suggestion*: add one live fixture per case to AC2/AC6.
- **Minor — DP-3's phrasing names the wrong existing gate as the unconditional precedent.** DP-3 says the new delegation is "copying the spec-review delegation shape … Unconditional rather than election-scoped for the reason the adjacent oversight gate states." But the spec-review gate (`bin/close-out.sh:509`-`:536`) is itself election-scoped (`if [ "$SPEC_REVIEW_ELECTION" = "cross-provider" ]`) — the gate that is actually unconditional, and whose "no per-task election to read" reasoning DP-3 quotes, is the oversight-profile gate immediately below it (`:540`+). What DP-3 means (read charitably, and consistent with AC10's own check) is: reuse the *resolve-sibling / refuse-if-missing / re-print-stderr / map-exit* structure both gates share, but wire it unconditionally as the oversight gate is, not the spec-review gate. AC10's own check disambiguates this correctly for a checker, so this is not a functional defect, but the prose as written could send an implementer to the wrong of the two existing blocks as "the shape to copy." *Suggestion*: name the oversight gate, not the spec-review gate, as the unconditional-wiring precedent, and name the spec-review gate only for the shared resolve/refuse/re-print/map structure.
- **Minor — AC9's "echoed before it runs" claim is asserted by the header but not proven as an ordering.** AC9's behavioural probe uses `command: false`, which produces no stdout of its own, so the test can only show the echo line eventually appears in the combined output when the command fails — it cannot distinguish "echoed before execution" from "echoed after, as part of error handling." A stronger probe (a command that itself prints a distinguishable line, with the check asserting the echo line's line-number precedes the command's own output line-number) would actually verify the ordering the header text promises.
- **Nit — AC3 calls the value `3-` an "interior sign"; it is a trailing sign** (the grammar's actual gap is a suffix that isn't a leading `[+-]?`). No functional effect — the fixture and the assertion are still correct — but the description misnames the shape.

#### Judgment on the grammar's fail-closed completeness

Not complete as frozen. The `<value>`/`<cmd>` halves of the grammar (numeric strictness, signed/zero handling, free-form command-last field-forgery resistance) are well defended and AC2/AC3/AC5/AC6/AC8 exercise them thoroughly and correctly — the em-dash-forgery-in-`<cmd>` discipline in particular holds under inspection (the label and value sub-patterns are strict enough that the two real `—` separators are located unambiguously regardless of how many more appear inside the free-form command tail). The **field-name half of the collect-wide stem is the weak point**: it is a literal, case-sensitive, ASCII-only match on `count`, and it inherits none of the collect-wide breadth the rest of the grammar earns through its Non-goals/Input-space discussion. Given this is precisely the failure class (T-1096/T-1109) the spec's own Notes for engineer names as "the defect class this checker is most likely to reproduce," and given AC3's own fixture list does not include a shape that exercises this exact stem boundary, the fail-closed claim ("every near-miss row is collected and refused, never read as the conformant zero-row case") is not yet demonstrated for the one shape most likely to recur.
