### My own synthesis of Codex's findings

**Finding 1 — downgraded to minor, fast-follow.** The generalization concern is real in form but the substance is already sound: "removes config-declared plugins/hooks" is a claim about what the `--ignore-user-config` flag *does* (skip loading one named file, unconditionally on content), which is host-independent by construction, not a claim inferred from one host's config contents. The part that is genuinely host-specific — the one residual document — is already disclosed as `undetermined`, never claimed closed, and the closing mechanism (clean `CODEX_HOME`) is explicitly filed forward with its own named measurement (DP-f, Non-goals). Worth a one-sentence tightening (state explicitly that the "measured effective" claim is about the flag's mechanism, not about this host's particular config, to pre-empt exactly this reading) but not blocking.

**Finding 2 — upheld as major, the round's most consequential finding, and independently re-derived rather than taken on Codex's word.** This lands squarely on domain premise 3, the one the whole election was priced on. Traced by hand: `payload-identity` is derived from two SHA-256 values — the run's own self-reported `payload-sha256` and the coordinating session's independent `shasum -a 256` of the same absolute path — and only their equality licenses any claim about `tech-lead` (Goal, "Why the payload…", third consequence). Nothing in AC22 or AC23 requires the reported hash to be traceable to an actual `shasum`/`sha256sum` invocation inside the run's own `read-scope-audit` / `- executed-command:` list; the field is accepted as free-form text the run asserts about itself. This is exactly the class of defect this repository's own T-1116 spec-review round 1 (Finding 2, "launch-outcome bijection doesn't bind recorded primitive fields to an actual raw reply") already flagged and fixed a sibling instance of — a mechanically achievable binding is simply absent here, and the spec's own text ("the run reports the digest of the payload file it actually read") treats the report as fact rather than flagging it as self-attested. The general "authenticating the executor's own words is out of scope" disclosure (Input-space item 5) is written specifically about `injection-observed`, not about `payload-identity`, and `payload-identity` is not one of the fields Input-space item 5 or the evidence-boundary's required literal list ties to "self-report" by name — the evidence-boundary line's `self-report` literal is satisfiable entirely by the `injection-observed` line alone. This is a disclosure gap on the mechanism the spec itself elevates as "only `match` licenses any claim about `tech-lead`" (the stale-snapshot discriminator), not a hidden design flaw — the fix is cheap (require `- executed-command:` to include the literal hash-computation command whose output the `payload-sha256` field must equal, or at minimum extend the evidence-boundary's required content to name `payload-identity` specifically as self-reported and not independently authenticated) but it is currently absent and it bears directly on the domain premise this election exists to interrogate.

**Finding 3 — downgraded to minor.** The prose already substantially requires this: "The evidence boundary, on exactly one line" (spec body, ~line 136) explicitly requires the section to name "that reads are unconstrained by the CLI's own design… so this path's read scope is audited after the fact by the `command_execution` items and enforced by nothing" — which is precisely Codex's ask. AC23's mechanical check only greps for the nine required literals, none of which pins this exact "audited after the fact… enforced by nothing" framing, so there is a real gap between the spec's stated intent and what AC23 mechanically enforces — but the intent itself is not absent, only under-mechanized. This is a check-completeness nit on an already-honest disclosure, not a fresh domain-premise gap.

**Finding 4 — upheld as major.** Independently confirmed by re-reading AC13(ii) and AC14's own shell bodies: AC13(ii) mutates the `bind` line to point `engineer` at `codex-cli` and appends a `wires-role codex-cli engineer` line, but never touches the `admits-authority codex-cli none` line that is what actually makes the refusal fire — the arm tests "a wired-but-unauthorized role", never "an authority declaration that is missing, duplicated, or malformed on an otherwise-valid recipe." AC14's exit-2 arms mutate `invocation-recipe`, `--role`, and delete the whole recipe file, but no arm removes or corrupts `admits-authority` specifically. This is exactly the shape of gap the Verdict scope calls out by name ("whether `authority-incompatible` is bypassable on any branch"), and it targets the one property the spec's own `## Pre-commitment` lists as never-dropped. Concrete and fixable: add AC14 arms for a recipe with zero `admits-authority codex-cli` lines, a duplicated/conflicting pair, and a malformed one (missing third field or an out-of-vocabulary value) — each must exit `2` (unparseable) or `1`/`authority-incompatible` (parseable-but-refused), and none may admit.

**Finding 5 — upheld as minor, fast-follow.** The distinction Codex draws (final-state identity vs. edit-then-revert-within-the-PR) is technically correct but the practical risk is close to zero for a PATCH-tier internal mechanism: an edit-and-revert of a byte-identity-locked file accomplishes nothing on its own, the final tree is what every downstream consumer and every other criterion sees, and this repository's own commit-review practice (human GO before merge, per-PR diffs) is an out-of-band check on intermediate history that this criterion was never designed to replace. Auditing every intermediate commit in the branch-point-to-HEAD range for nine locked files would be disproportionate scope for this task.

**Finding 6 — downgraded to minor, matching direct precedent.** Codex's own text already concedes the disclosure exists ("not a hidden limitation"). This is the identical self-attestation-boundary class this role's own T-1116 spec-review round 1 downgraded (Finding 1, "freeze/execution-provenance self-attestation") for the same reason: every specific gap named (fabricated evidence, no independent proof a provider call occurred) is already explicitly named in this spec's own text — Non-goals item 11, Input-space item 11, and the evidence-boundary's required `self-attestation` literal — and it is the identical boundary every freeze-then-run gate in this repository already accepts. Not a new gap this task introduces.

**Finding 7 — downgraded to minor.** The design already separates the two readings by construction, not merely by luck: the `stream-and-usage` channel is explicitly pinned "licensing for the trust-boundary reading and non-licensing for the path verdict, stated on its own line in exactly those terms" (AC23), and the Goal's own "What the run measures, and what it cannot" paragraph states plainly that the verdict "measures nothing about planning quality" and is scoped to mechanics. A reader who conflates `path-wired` with "safe" is contradicting text the spec already states, not filling a gap it left open. A one-sentence addition to the evidence-boundary ("`path-wired` is a mechanics verdict, never a security or isolation clearance") would remove even that residual reading risk cheaply, and is worth taking in the same pass as Finding 2's fix since both touch the evidence-boundary's required content.
