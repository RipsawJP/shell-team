## FAIL driver: `--last-n 0` crashes the script under BSD `head` (macOS), violating its own documented exit-code contract

`bin/retro-inputs.sh`'s own header states the exit-code contract precisely:

```
# Exit codes:
#   0  success (including every degenerate-history / gh-absent case...)
#   2  argument / usage error
```

`--last-n` accepts any non-negative integer per the script's own validation (`*[!0-9]*` rejects only non-digit characters; `"0"` passes). `0` is not an out-of-scope synthetic extreme — it is the ordinary zero-boundary value of a documented, in-input-space flag (AC11), exactly the "resource / budget competition (zero remaining budget)" class the adversarial-fixture checklist calls for, and it was not in the shipped test suite (which only exercises `--last-n 1`).

### Reproduction

```
$ mkdir -p /tmp/repro && cd /tmp/repro
$ git init -q -b main && git config user.email t@e.com && git config user.name T
$ printf x > f && git add f && git commit -qm init
$ git checkout -qb feat && printf y >> f && git commit -qam feat
$ git checkout -q main && git merge -q --no-ff -m "Merge pull request #1 from example/feat" feat
$ bash /path/to/shell-team/bin/retro-inputs.sh --base main --last-n 0
```

Observed:
```
## Retro inputs
head: illegal line count -- 0
$ echo $?
1
```

Expected (per the script's own contract): exit 0, with a complete 8-line ledger reporting `cycle-window` as `read` with 0 merge commits shown and the cap declared (analogous to the `--last-n 1` case, just capped to zero), never a bare exit 1 with a truncated one-line ledger and no closed statuses for the other seven inputs.

Root cause: `bin/retro-inputs.sh:224` — `shown="$(printf '%s\n' "$log_out" | head -n "$last_n")"`. On BSD `head` (macOS, confirmed on this machine: `head -n 0 </dev/null` → `head: illegal line count -- 0`, exit 1), `-n 0` is rejected outright, unlike GNU `head` where `-n 0` is legal and simply emits nothing. Under `set -euo pipefail`, the failing `head` in the pipeline aborts the whole script immediately (mid-emission — only the `## Retro inputs` heading had been printed), so every field after `cycle-window` (all seven remaining inputs) never gets reported at all — a materially worse failure than "one field wrong," since the ledger stops being a ledger.

This is `bin/`-scripted, adopter-facing (macOS is a normal dev platform for this project — this very sandbox is Darwin), and squarely inside the reachable input space AC11 declares (`--last-n N` is a documented, un-excluded flag). It is a genuine regression risk: a caller who passes `--last-n 0` (a plausible mistake, or a deliberate "give me nothing, just the shape" call) gets a crash instead of the documented soft-degradation behavior, on any platform with BSD coreutils.

### Suggested next step

Guard the cap arithmetic so `head` is never invoked with `-n 0` — e.g. skip the `head` call entirely when `last_n` is `0` and set `shown=""` directly (mirroring the zero-merge branch's `CW_MATERIAL=""` handling), or use a portable line-count-limiting idiom that both BSD and GNU `head` accept for the zero case. Add a `--last-n 0` case to `tests/retro-inputs/run.sh` (on a repo with ≥1 merge commit, to actually cross the boundary — a fixture that never reaches the cap does not prove the boundary is handled) so this class of zero-budget input is locked going forward.
