## FAIL driver: `--last-n 0` crashes the script under BSD `head` (macOS), violating its own documented exit-code contract

`bin/retro-inputs.sh`'s own header states the exit-code contract precisely:

```
# Exit codes:
#   0  success (including every degenerate-history / gh-absent case...)
#   2  argument / usage error
```

`--last-n` accepts any non-negative integer per the script's own validation (`*[!0-9]*` rejects only non-digit characters; `"0"` passes). `0` is not an out-of-scope synthetic extreme — it is the ordinary zero-boundary value of a documented, in-input-space flag (AC11), exactly the "resource / budget competition (zero remaining budget)" class the adversarial-fixture checklist calls for, and it was not in the shipped test suite (which only exercises `--last-n 1`).

### Reproduction

```
$ mkdir -p /tmp/repro && cd /tmp/repro
$ git init -q -b main && git config user.email t@e.com && git config user.name T
$ printf x > f && git add f && git commit -qm init
$ git checkout -qb feat && printf y >> f && git commit -qam feat
$ git checkout -q main && git merge -q --no-ff -m "Merge pull request #1 from example/feat" feat
$ bash /path/to/shell-team/bin/retro-inputs.sh --base main --last-n 0
```

Observed:
```
## Retro inputs
head: illegal line count -- 0
$ echo $?
1
```

Expected (per the script's own contract): exit 0, with a complete 8-line ledger reporting `cycle-window` as `read` with 0 merge commits shown and the cap declared (analogous to the `--last-n 1` case, just capped to zero), never a bare exit 1 with a truncated one-line ledger and no closed statuses for the other seven inputs.

Root cause: `bin/retro-inputs.sh:224` — `shown="$(printf '%s\n' "$log_out" | head -n "$last_n")"`. On BSD `head` (macOS, confirmed on this machine: `head -n 0 </dev/null` → `head: illegal line count -- 0`, exit 1), `-n 0` is rejected outright, unlike GNU `head` where `-n 0` is legal and simply emits nothing. Under `set -euo pipefail`, the failing `head` in the pipeline aborts the whole script immediately (mid-emission — only the `## Retro inputs` heading had been printed), so every field after `cycle-window` (all seven remaining inputs) never gets reported at all — a materially worse failure than "one field wrong," since the ledger stops being a ledger.

This is `bin/`-scripted, adopter-facing (macOS is a normal dev platform for this project — this very sandbox is Darwin), and squarely inside the reachable input space AC11 declares (`--last-n N` is a documented, un-excluded flag). It is a genuine regression risk: a caller who passes `--last-n 0` (a plausible mistake, or a deliberate "give me nothing, just the shape" call) gets a crash instead of the documented soft-degradation behavior, on any platform with BSD coreutils.

### Suggested next step

Guard the cap arithmetic so `head` is never invoked with `-n 0` — e.g. skip the `head` call entirely when `last_n` is `0` and set `shown=""` directly (mirroring the zero-merge branch's `CW_MATERIAL=""` handling), or use a portable line-count-limiting idiom that both BSD and GNU `head` accept for the zero case. Add a `--last-n 0` case to `tests/retro-inputs/run.sh` (on a repo with ≥1 merge commit, to actually cross the boundary — a fixture that never reaches the cap does not prove the boundary is handled) so this class of zero-budget input is locked going forward.

#### Blockers

- `bin/check-retro.sh:160` (rule 4, ledger-section detection) — The anchored pattern `/^## Retro inputs$/` used to open the ledger region is **not CRLF-tolerant**, unlike rule 2's heading checks, which were deliberately rewritten to use the CRLF-tolerant `has_exact_line()` helper for exactly this reason (see this task's own provenance decision on `has_exact_line()`). On a CRLF-terminated retro file, `$0` for the heading line is `"## Retro inputs\r"`, which the anchored `$`-terminated pattern never matches, so `seen` is never set to `1`. Two direct consequences, both reproduced: (1) every line inside the section is treated as ordinary prose rather than parsed as a ledger line, and (2) the `END` block's missing-id sweep is itself gated on `if (seen)`, so it is skipped entirely. **The result is that rule 4 — the entire mechanism this task exists to build — becomes a silent no-op for any CRLF-terminated retro.** Reproduction: a deliberately malformed ledger (one line, `- input: cycle-window` with no status/detail fields, the other 7 ids entirely absent) correctly produces 9 violations and exit 1 under LF line endings; the byte-identical content converted to CRLF (`sed 's/$/\r/'`) produces **zero violations and exit 0**. AC16's own "case: a ledger with CRLF line endings still passes" fixture only exercises a *well-formed* CRLF ledger, so it passes for the wrong reason (the check never ran) and never caught this. Fix: extend `has_exact_line()` (or an equivalent CR-stripping compare) to the `## Retro inputs` region-open pattern, the same way rule 2 already handles CRLF.
  - Suggested fix: change the awk pattern from `/^## Retro inputs$/` to a CR-tolerant match (e.g., strip a trailing `\r` from `$0` before testing, mirroring `has_exact_line()`'s own normalization), and add a fixture case asserting that a **malformed** CRLF ledger fails, not only that a well-formed one passes.

- `bin/retro-inputs.sh:293-313` (`report_dir_input()` / `count_files()`) — A directory that is **readable but not searchable** (POSIX mode `0400`: the `r` bit is set, but the missing `x`/search bit prevents traversing or `stat`-ing entries) passes the `[ ! -r "$dir" ]` guard, then `count_files()`'s glob silently expands to zero matches (nullglob, no error), so the input is reported as **`empty`** — even though the directory demonstrably holds files that could not be enumerated. This is the exact central invariant this whole task exists to guarantee (never report `empty` when the truth is `unavailable`), violated for a directory-permission cause rather than a git-history cause. Reproduction: a throwaway repo with `.shell-team/reviews/` containing two real `.md` files, `chmod 0400` applied to the directory itself → `bin/retro-inputs.sh --base main` reports `- input: review-artifacts — status: empty — detail: 0 review artifacts in .shell-team/reviews`. The adversarial pass independently flagged the same root cause from a different angle (TOCTOU: the pre-condition checks and the enumeration are two separate operations, so *any* enumeration failure after the checks — not just the missing-execute-bit case — collapses to the same false `empty`); both point at the same underlying defect: `count_files()` has no channel to report "enumeration failed" distinct from "enumeration found 0 entries."
  - Suggested fix: check search/execute permission explicitly (or, better, capture the exit status of the enumeration itself — e.g. via `find "$dir" -maxdepth 1 ...` with its exit code checked — rather than trusting the glob's silent zero-match behaviour), and report `unavailable` whenever enumeration cannot be proven to have succeeded, not just when the pre-condition checks fail.

- `bin/retro-inputs.sh:190-195` (`compute_cycle_window()`, shallow detection) — Shallow-repository detection resolves `gitdir="$(git rev-parse --git-dir)"` and then tests `"$gitdir/shallow"`. Inside a **linked worktree** (`git worktree add`), `--git-dir` returns the worktree-*private* git directory (e.g. `.git/worktrees/<name>`), which never carries the `shallow` marker — the marker lives only in the *common* directory (`git rev-parse --git-common-dir`), per git's documented repository layout. Reproduced directly: in a `git worktree add --detach` checkout of a repo carrying a simulated `.git/shallow` marker, `--git-dir` and `--git-common-dir` diverge as described, and `git rev-parse --is-shallow-repository` (a worktree-aware plumbing command) correctly reports `true` where the script's own `"$gitdir/shallow"` check would find nothing. Run from inside such a worktree, the script silently computes `shallow=0` for a genuinely shallow history, again risking the exact `empty`-for-`unavailable` substitution (or a `read` status that omits the truncation warning) this task exists to prevent — the same central invariant as the two blockers above, just gated behind a less common combination (shallow clone **and** linked worktree together), which is why this is Major rather than Blocker.
  - Suggested fix: use `git rev-parse --is-shallow-repository` (or resolve the shallow marker via `git rev-parse --git-path shallow`, never by hand-appending `/shallow` to `--git-dir`).

#### Minor / nits

- `bin/retro-inputs.sh:240-244` — When a repository is **both** shallow **and** the requested `--last-n` cap is smaller than the merges visible within the boundary, only the "shallow clone truncates history at the boundary" qualifier is emitted; the "capped at --last-n N" qualifier is silently dropped (the `if`/`elif` chain only ever emits one). Reproduced: a 3-merge shallow repo with `--last-n 2` reports `2 merge commits ... shallow clone truncates history at the boundary`, with no mention that `2` came from the cap, not the boundary. `CW_STATUS` stays correctly `read` either way, so this is an informational precision loss, not a status misclassification.
- `bin/retro-inputs.sh:210-249` — The "`develop` not found locally, fell back to HEAD" qualifier is appended only in the non-zero-merge (`read`) branch of `compute_cycle_window()`; the zero-merge (`empty`) and shallow-zero (`unavailable`) early-return branches never declare that the ref used was a fallback rather than an explicit ask. Reproduced: a `develop`-less, zero-merge repo reports `0 merge commits reachable from HEAD ..., not a truncation` with no fallback note. AC11's own fixture case ("no develop branch falls back to HEAD and declares the fallback") is built only against a merge-having repo, so this gap is invisible to the shipped suite.
- `bin/check-retro.sh:160` (region-open logic) — A **second** `## Retro inputs` heading later in the same document is never re-opened for validation (`!seen` blocks it permanently once the first section has been seen and closed), so a duplicated or forged second ledger is silently skipped. Grounded out-of-input-space: the spec's own Non-goal/Out-of-scope item 3 explicitly declines to harden the section parser against "a retro crafted to defeat the section parser," and this is not reachable via untrusted git/PR content — `sanitize()` already prevents a forged raw `##`-prefixed line from ever being emitted from merge-subject/PR-title material (it is only ever embedded as an indented sub-bullet). Downgraded to minor per the input-space rule; see ledger.
- `bin/check-retro.sh:201` — The detail-emptiness check only rejects a zero-length string (`de == ""`); a detail consisting entirely of whitespace passes. Not reachable via `retro-inputs.sh`'s own output (every emitted detail carries substantive text) or via untrusted git content; only a hand-crafted malformed document could trigger it.
- `bin/retro-inputs.sh:176` — The default-`develop` probe (`git rev-parse --verify --quiet`) does not distinguish "ref genuinely absent" from "an operational git error" before falling back to `HEAD`; both take the same "else" branch. The practical blast radius is narrow: if git itself is broken (`safe.directory` refusal, unreadable object store), the very next line re-verifies `HEAD` with the same command and correctly reports `unavailable` when that also fails, so the only scenario this actually loses precision on is a narrow ambiguous-ref case where `develop`'s probe fails for a reason other than absence while `HEAD` resolves fine.
- `bin/retro-inputs.sh:140-144` (`sanitize()`) — Strips CR, LF, TAB, backtick, and replaces the em-dash separator, but not other Unicode line-separator or bidi-control characters (U+2028, U+2029, ESC, bidi overrides) from untrusted merge-subject/PR-title text. Confirmed this does **not** defeat `bin/check-retro.sh`'s machine parsing (awk's record splitting is unaffected by non-ASCII "line-like" characters, so the ledger stays structurally correct), but is a legitimate hardening gap for the same prompt-injection-adjacent concern this file already names for PR bodies, since the sanitized material sub-bullets are read directly by the scrum-master LLM agent.
