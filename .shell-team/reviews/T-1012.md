**One nuance found and judged not to rise to a FAIL, disclosed for the
reviewer:** the design note's §5 acceptance hook says a null `model`/`verdict`

`field != null ? field : "—"` in **both** `showTip()` and `drawMiniCard()`'s
single-span branch. Reading the shipped code: `drawMiniCard()`'s `model`/
`tokens`/`tool_uses`/`duration` correctly use that exact ternary-to-`"—"`
pattern (line ~1130-1133); but `drawMiniCard()`'s `verdict` (line 1134) and
**both** of `showTip()`'s `model`/`verdict` lines (lines 947, 951) instead use
an "omit the whole line if falsy" guard — which never prints the literal word
`null` (satisfying the AC's core safety requirement) but also never shows a
`—` placeholder (not matching the design note's literal instruction). Tracing
`showTip()`'s only live call site (line 1412, fed exclusively by
`nodeTipData()`, which returns `{label, outcome, agentId}` — never
`model`/`verdict`/`tokens`), this appears to be dead/vestigial code left from
before `nodeTipData` replaced the tooltip's data source; a user's actual path
to seeing a span's `model` is the detail panel's stat grid
(`current.model || "—"`, line 935, **pre-existing, unedited, ratified code**),
which already shows `—` correctly. I could not visually confirm this reading
(no browser), so I record it as a risk note rather than a FAIL: **the
literal word "null" never appears anywhere I traced**, but the tooltip/
mini-card verdict placeholder does not match the design note's letter. A
human/reviewer with browser access should hover a span with a null model in
practice to settle this beyond code-reading.
