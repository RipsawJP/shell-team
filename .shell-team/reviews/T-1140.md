### Mandatory class-M item (AC11 residual-filter re-freeze v1→v2)

Confirmed mechanics-only: `git show 52c81b1` touches only
`.shell-team/interventions/T-1140.md`, the one `- check:` line under AC11 in
the spec, and the board's re-freeze bookkeeping — no Goal/Non-goals/
criterion-prose/Input-space line moved, matching `refreeze-class: mechanics`.

The delta widens AC11's residual-candidate exemption from `\.local\.`
(dot-led continuation only) to `\.local[.A-Za-z0-9-]` (dot, letter, digit,
**or hyphen**). The intervention's own stated cause (`.shell-team/todo.md`
`intent-ratified (v1→v2)` line, and the engineer's `## Notes from engineer`)
is that the *old* filter didn't exempt letter-led continuations
(`window.localStorage`, `mail.localhost`) — it says nothing about needing to
exempt a **hyphen**-led continuation. I built the check the class-M item asks
for — comparing the repaired filter against the real `RE_HOST_LOCAL`'s own
boundary — and it is **not** meaning-preserving:

```
$ printf 'see host.local-foo here\n' > f.txt
$ grep -E -- '[A-Za-z0-9-]\.local' f.txt | grep -vE '\.local[.A-Za-z0-9-]'
(no output — v2's AC11 filter now treats this as a non-issue)
$ grep -E -- '[A-Za-z0-9][A-Za-z0-9-]*\.local($|[^A-Za-z0-9.])' f.txt
see host.local-foo here      # MATCHES — the real shipped RE_HOST_LOCAL fires on this
```

So the just-repaired AC11 audit line and the shipped `RE_HOST_LOCAL` it exists
to independently confirm now **disagree** on the identical hyphen-continuation
shape: production fires, the audit's own residual-candidate filter treats it
as exempt. Whichever side is "correct" (see the Major below — I think the
production side is closer to the design's own model, since the same
character class already treats hyphen as a legitimate name character on the
*left* of `.local`), the audit-line half of AC11 no longer proves what it
claims to prove for this shape, though `AC6`'s independent `--all` run
remains a real backstop today (no such token currently exists in the tree, so
`--all` stays clean and the substantive property AC11 exists to protect is
not currently defeated in practice). Scored Tier 2 (spec-inline check line) —
a real instrument defect, not adversarial guard-mutation completeness — so
**Major**, not Blocker, and not gating on its own.

### Findings

#### Blocker

- **`bin/check-pii-shapes.sh` (`RE_TRACKER_KEY`, the `report_pattern_lines
  tracker-key` call site) — missing left-word-boundary defeats the declared,
  load-bearing digit-bearing-namespace exclusion (DP-2, AC5, Out-of-scope
  item 3).** `RE_TRACKER_KEY="${RE_TRACKER_KEY_NAMESPACE}-[0-9]+"` carries no
  left anchor at all (unlike every other composed rule in this file, e.g.
  `RE_HOME_PATH_BOUNDARY='(^|[^A-Za-z0-9.-])'`). Confirmed live against the
  real, unmodified shipped checker:
  ```
  $ git init -q repo && cd repo && git config user.email a@b.c && git config user.name x
  $ printf 'note: A1BC-2 is just a line-range style reference, not a tracker key\n' > f.md
  $ git add f.md && git commit -q -m init
  $ PII_CHECK_TRACKER_KEY=1 bash bin/check-pii-shapes.sh --all
  FINDING pattern=tracker-key path=f.md line=1
  ```
  `A1BC-2` has a digit-bearing namespace (`A1BC`) — Out-of-scope item 3 and
  DP-2's table both declare this class must stay silent by construction
  ("36 measured line-range and label references... excluded by the outline
  itself"), and it does not: `grep -oE '[A-Z]{2,10}-[0-9]+'` on `A1BC-2`
  returns the substring `BC-2`, because nothing requires the match to start
  at the beginning of the alnum run. The population analysis in `## Blast
  radius` that grounds this whole design decision (DP-1, DP-2) was itself
  measured with `bin/derive-populations.sh`'s **word-boundary-anchored**
  PCRE patterns (`-P '\b[A-Z]{2,10}-[0-9]+\b'`), but the shipped detection
  regex carries no equivalent boundary — so the approved 48/84/36-token
  population counts do not describe what the shipped rule will actually match
  in the field. I did not find any of the 36 currently-tracked digit-bearing
  tokens that happen to trigger this specific bypass today (all end directly
  in a digit before the hyphen, e.g. `AC4-13`, `L194-199`) — this is
  incidental to the current corpus's exact spelling, not a property of the
  regex, and the very next digit-bearing token an adopter's tree acquires
  could trip it. Given tracker-key is the pre-commitment's own
  `droppable-1st` component, this is exactly the class of defeat that
  disposition anticipates — but it is round 1, so the two-consecutive-round
  factual-trigger has not fired; I'm reporting it as a Blocker on its own
  substance rather than invoking that disposition myself.
  - **Suggested fix**: add an explicit left-boundary requirement to
    `RE_TRACKER_KEY` (or to `RE_TRACKER_KEY_NAMESPACE`), mirroring
    `RE_HOME_PATH_BOUNDARY`'s `(^|[^A-Za-z0-9.-])` convention, e.g.
    `RE_TRACKER_KEY="(^|[^A-Za-z0-9])${RE_TRACKER_KEY_NAMESPACE}-[0-9]+"` (and
    account for the boundary consuming a character in
    `report_pattern_lines`'s line-number-only reporting, which does not
    depend on match offset, so this is safe to add without touching the
    reporting path).

#### Major

- **`bin/check-pii-shapes.sh` (`RE_TRACKER_KEY`) — missing right-word-boundary
  after the digit run produces false positives outside the declared shape.**
  `AB-123abc` reports `AB-123` even though the full token continues past the
  digit run — not a genuine tracker key by the shape AC1 declares ("an
  upper-case letters-only namespace..., a hyphen, and a digit run"), and not
  covered by the declared accepted-noise class either (that class is
  specifically "standards identifiers of the same outline", not arbitrary
  compound tokens that merely contain a tracker-key-shaped prefix). Same root
  cause as the Blocker above (no boundary anchoring at all on this rule,
  neither side) but a distinct manifestation not covered by either named
  exclusion. Confirmed via direct reproduction:
  ```
  $ printf 'note AB-123abc trailing\n' | grep -oE -- '[A-Z]{2,10}-[0-9]+'
  AB-123
  ```
  The trailing `abc` is simply left unconsumed by the pattern rather than
  disqualifying the match, so the substring `AB-123` is still reported. The
  same missing-anchor root cause also lets an over-length (>10-letter)
  namespace still fire via a truncated substring match — `ABCDEFGHIJK-1`
  (11-letter namespace) reports as `BCDEFGHIJK-1` rather than being excluded
  for exceeding the declared 2-10 character range; AC14's own family test
  only exercises the long end at exactly 10 letters, never 11+, so the suite
  does not catch this.
  - **Suggested fix**: same left-boundary fix as the Blocker, plus a
    right-boundary requirement after the digit run (end-of-line or a
    non-alnum character), matching the shipped `RE_HOME_PATH`-style
    two-sided boundary convention.

- **`bin/check-pii-shapes.sh` (`RE_HOST_LOCAL`) — the right-side boundary
  treats a hyphen as a valid terminator, so `host.local-suffix` fires as a
  `host-local` finding, and this is now inconsistent with the just-repaired
  AC11 audit line (see the class-M item above), which treats the identical
