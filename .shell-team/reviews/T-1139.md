#### Blockers
- `docs/adopting.md:571-574` / `docs/adopting.ja.md:577-580` (gap 3, D4) — The new sentence states "the session pushes the branch and opens the pull request against the base the spec names; the merge itself, and the merge GO, stay the human's" — i.e. only merge is human-gated. This contradicts this project's own shipped default loop-contract template: `templates/shell-team.contract.yaml:24` ("must not merge or push without a human gate (see human_gate below)") and `:43-45` (`human_gate: [merge, push]`), mirrored in `templates/goal.contract.yaml:27,46`. D4's own reasoning (`docs/tuning-oversight.md:99`, "the first stop fires on whether the merge changes what runs") never cross-checked itself against the contract template's own explicit inclusion of `push`, even though this task's own AC9 locks `templates/` unedited — so the new sentence ships a firm claim in an area two of this project's own normative artifacts disagree on. `human_gate` is documented as advisory/unenforced metadata (`templates/loop-contract-template.yaml:63-68`, "ignored by the linter"; `bin/loop-guard.sh` never reads it) rather than a machine gate, but that does not rescue the claim: the runbook is telling the reader what the loop *does*, and the shipped default contract an adopter actually gets from `team-init` says push is gated too. This is exactly the "sentence contradicting the shipped … human GO" class of defect this review was briefed to watch for. Fix: either soften the claim to point at the operator's own oversight configuration (`docs/tuning-oversight.md`) for whether push/PR-open needs a stop, or reconcile it explicitly against `human_gate: [merge, push]` rather than asserting push is unconditionally automatic.

#### Major
- `docs/adopting.md:399-408` / `docs/adopting.ja.md:406-414` (gap 1, D1) — The new version-check sentence sits in the same numbered step as, and directly after, "Skip this step if the plugin already shows `installed, enabled`." The sentence itself is technically unambiguous on a full read ("even when STATUS already reads `installed, enabled`" explicitly negates the skip), and the remedy for a still-stale VERSION after running `upgrade` is already covered by the retained `step 2` cross-reference (consistent with D1's no-duplication ruling) — so this is not a factual error. But placing the fix immediately after a "skip this step if X" trigger, for a reader who matches X, creates a real risk of exactly the skim-and-move-on failure this whole task exists to close (b run #4's own operator missed a materially similar staleness gap on a first read-through). Recommend moving the sentence to open with its own clause rather than trailing the skip-condition paragraph, so a reader who correctly determines "skip the install commands" is not also primed to stop reading the paragraph before the version-check instruction.
- `agents/pm-spec.md:16` vs `agents/pm-spec.md:58` (gap 2 authoring site, AC6 — the pre-commitment's droppable item) — Item 3 of `## Your job` now requires `<specs dir>/<task-id>-<slug>.md`, but the `## tasks/todo.md entry format` template a few lines below still shows the legacy `spec: docs/specs/<slug>.md` unedited. Before this task the two lines matched exactly; this diff is what introduces the divergence, and AC6's own body explicitly permits leaving it (a reasoned, but incomplete, tradeoff — `.shell-team/provenance/T-1139.md` entry 3 weighs the `board-line-format.md` two-fragment hazard but never checks this specific downstream consumer). Traced independently and confirmed by the adversarial pass: `bin/check-oversight.sh:644-658` extracts the board's own literal `spec:` pointer via regex and runs `git log -1 --format=%H -- "$SPEC_PATH"`; for a path that does not exist, that command exits 0 with empty output, so the `[ -n "$LAST_TOUCH" ]` guard is false and the pre-merge freshness check silently no-ops rather than failing. This only bites a host that has opted into the `governance-controlled` oversight profile (the shipped default `autonomous` never reaches this code path) and requires `pm-spec` to copy the stale literal template rather than substitute the path it actually used — a real but narrow risk, not a certain one. Recommend a one-line fix to the `:58` template now that the risk is concretely traced, rather than leaving it for a future same-class-2 trigger.
