#### Blockers

- `bin/check-durability.sh:219-224` (DP7's opt-out honor check) — The tracked-ness test only confirms that **some** blob exists at `$MODE_FILE`'s path in `--ref`'s tree (`git ls-tree "$REF" -- "$MODE_FILE"` non-empty); it never confirms that blob's **content** is the `working-tree-only` value being acted on. `MODE` itself is parsed from the **working-tree** copy of the file. Consequence: if the mode file is committed as `tracked` (or absent) and then, **without committing**, edited in the working tree to `working-tree-only`, the checker honors the skip and exits 0 — even though the declared opt-out itself never durably persisted. This is exactly the class of accident the Threat model names ("a stray gitignore rule, a mis-resolved base dir") applied to the opt-out file itself, and it directly contradicts DP7's own frozen sentence: "A `working-tree-only` declaration is honored **only if** the mode file itself resolves to a blob in `<ref>`'s tree" — read in light of DP7's lead sentence "the opt-out must itself be durable," presence-of-any-blob is not the same test as durability-of-the-declared-value. Reproduced live in this session (fixture: mode file committed as `tracked`, provenance record deleted, mode file locally edited to `working-tree-only` with no commit) — `check-durability.sh --phase implement --task T-900 --ref refs/heads/main` printed `check-durability: skipped: ... — no durability observation was made` and exited 0, despite `git status --short` showing both the modified mode file and the deleted record. At the two `skills/run/SKILL.md` seams this is partially mitigated by the pre-existing T-073 `git status --short` guard running first (it would already flag the modified mode file) — but **`bin/close-out.sh` has no such companion check anywhere in its gate ladder** (`grep -n 'git status' bin/close-out.sh` returns nothing), so at the close-out gate — DP11's third wiring site, and the last checkpoint before the board moves to Done — this bypass is completely unguarded. AC4 never exercises this state: its three sub-fixtures (a: committed-and-declaring `working-tree-only`, b: untracked, c: no-file-plus-env-vars) never test "committed as one value, working tree edited to the other value." Confirmed independently by both a Codex primary-pass finding (P1) and a targeted adversarial pass (`severity: high`).
  - Suggested fix: apply the same DP3-style content-durability check to the mode file that ordinary records already get — read the blob's actual content from `$REF` (e.g. via `git cat-file -p "$REF:$MODE_FILE"`, or a `git hash-object --path=` comparison against the recorded OID) and require the **committed** value to be `working-tree-only`, not merely that some blob exists at the path. Add a regression fixture: mode file committed as `tracked` (or absent), then edited in the working tree only to `working-tree-only`, with a genuinely non-durable record present — must fail closed (not `skipped`).

- `bin/close-out.sh:334-338` wiring vs. `close-out.sh`'s pre-existing `$TEAM_TODO` / `$TEAM_INTERVENTIONS_DIR` override precedence — `close-out.sh` has always supported resolving the operative board (and, since T-1017, the operative interventions record) from these two env-var overrides in preference to `team-paths.sh`'s own resolution (documented in this file's own header: "The board path comes from `$TEAM_TODO` if set, else the sibling team-paths.sh resolves it"). The **existing** T-1017 interventions gate respects this precedent correctly, because `close-out.sh` resolves `$INTERVENTIONS_DIR`/`$RECORD` itself and hands the checker a concrete path to validate. The **new** T-1048 durability gate breaks that pattern: it passes only `--phase close-out --task <id> --ref HEAD` and lets `check-durability.sh` resolve every record path **independently** via its own internal `team-paths.sh --get <key>` calls — which never consult `$TEAM_TODO` or `$TEAM_INTERVENTIONS_DIR` at all (confirmed by reading `bin/team-paths.sh`'s own precedence chain: it only ever consults `$TEAM_RUN_BASE`). Consequence: if an operator legitimately invokes `close-out.sh` with either override set to something other than `team-paths.sh`'s own default resolution, the durability gate silently observes a **different file** than the one `close-out.sh` is about to move to `## Done` — it could pass (default-layout board happens to be durable) while the actual, overridden board was never committed, or refuse a close-out that should have succeeded. This is squarely a "mis-resolved base dir" accident, the Threat model's own named example. None of the ~30 pre-existing `$TEAM_TODO`-override fixtures in `tests/close-out/run.sh` exercise this interaction in non-opt-out mode (they all get the auto-stamped `working-tree-only` skip per this task's own fixture-retrofit decision), and the three dedicated `closeout-durability-*` fixtures all use the default (non-overridden) layout — so this gap ships untested. Flagged independently by the adversarial Codex pass (`severity: high`).
  - Note: this can't simply be "add a path override to `check-durability.sh`" — the spec's own Notes for engineer are explicit that `--records` is "the ONE override flag the fixture suite needs... do not add a second override for anything else," and DP1/DP2 deliberately keep record-path resolution centralized. The fix more likely belongs on the `close-out.sh` side: either refuse to run (or explicitly flag) the durability gate when `$TEAM_TODO`/`$TEAM_INTERVENTIONS_DIR` diverge from `team-paths.sh`'s own resolution, or document the limitation plainly in `close-out.sh`'s header so an operator using these overrides knows the durability observation does not track them.
