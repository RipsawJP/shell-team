#### Major

- **`tests/bin-exec-bit/run.sh:63`** — `POP="$(git -C "$REPO_ROOT" ls-files -s -- bin/ 2>/dev/null || true)"` discards `git`'s own exit status and judges the population solely by whether stdout is non-empty. A `git ls-files` invocation that prints a plausible (even fully clean) listing and then exits nonzero is read as a valid, passing population — the exact "fails closed, never a clean pass" guarantee DP2 states in the frozen intent block, and the repo's own Working rule ("Suppressing a non-zero exit status … converts a real failure into a false pass") for this exact lock. **Live-reproduced**: a `git` PATH shim that printed a single clean `100755 … bin/install` line and then `exit 1` made the suite print `PASS: rule: every one of 1 tracked entries under bin/ … reports mode 100755` and exit 0 — a silently-truncated 1-of-36 population read as clean. Not covered by any Input-space Out-of-scope line (the declared out-of-scope classes are a hostile `$TMPDIR`, a hanging `git`, concurrent invocations, and an unpreserved exec bit on the filesystem — none of these is "a `git` that prints then fails"; the Reachable class this task explicitly commits to handling is "an empty or unavailable git output," and this is the sub-case of "unavailable" the implementation does not actually cover). Suggested fix: capture the exit status explicitly (the same idiom `check-refreeze-class.sh` itself now uses for `cmp_rc` in DP9) — e.g. `rc=0; POP="$(git -C "$REPO_ROOT" ls-files -s -- bin/ 2>/dev/null)" || rc=$?; if [ "$rc" -ne 0 ] || [ -z "$POP" ]; then …fail…; fi`.

- **`bin/check-intent.sh:172-178` vs `:267-275`, and the analogous `bin/check-refreeze-class.sh:122-128` vs `:277-284`** — a real, live-reproduced temp-file leak on signal delivery, in both hardened scripts, inside the exact subsystem DP10-DP12 exist to close. In `check-intent.sh`, the `HUP`/`INT`/`TERM` traps are installed early (line 176-178), but `tmp_region`'s `EXIT`-trap-based cleanup isn't registered until several lines later (line 275) — a signal delivered in that window fires `on_signal`'s `exit "$2"` with no `EXIT` trap yet installed, leaking the temp file `mktemp` already created. In `check-refreeze-class.sh` the `EXIT` trap (`cleanup_tmp_files`) is registered early, but each `mktemp` result is only appended to `TMP_FILES` on the line immediately after — a signal firing between the `mktemp` call and that append leaves the temp file un-tracked, so `cleanup_tmp_files`'s `rm -f "${TMP_FILES[@]}"` never reaches it. **Live-reproduced on both scripts**: a `mktemp` PATH shim that sleeps before delegating to the real `mktemp` (widening the window so a `SIGTERM` sent while the shim sleeps lands exactly in this gap — bash defers the pending trap until the command substitution returns, then dispatches it before the next statement runs) left a real 0-byte `check-intent-region.*` / `check-refreeze-class-region.*` file behind in a private `TMPDIR` in both cases, while the script correctly exited `143`. This directly contradicts the "no temp-file residue behind" promise stated in AC9's own prose (though AC9's own *check clause* doesn't happen to probe this exact window — its blocking-`git` probe fires later, after registration completes, so AC9 as literally written still passes).
