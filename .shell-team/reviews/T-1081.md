In a fresh clone, a CI checkout, or an adopter repo where the still-open predecessor branch exists only as `refs/remotes/origin/<predecessor>` (or is simply not fetched), this test fails even though the predecessor is genuinely still open and unmerged, and the expression silently takes the fallback `git merge-base "<integration-branch>" HEAD` arm. That arm is not the branch point — it resolves further back, before the predecessor's own changes — so every base-side-blob read this discriminator is meant to anchor (scope-lock allowlists, blast-radius sweeps, byte-identity diffs) is silently corrupted with no error or warning. Neither the item's disclosed residual case ("a predecessor branch deleted without being merged") nor the spec's own `## Input space` reachable-input list names either sub-case. Suggested fix: broaden the existence test to also recognize a remote-tracking ref (or state a fetch precondition explicitly), and extend the disclosed residual-case language to cover a rewritten-history predecessor rather than only a deleted-unmerged one.
