#### Major

- `agents/pm-spec.md:92` (mirrored in `skills/run/SKILL.md:48`, `docs/adopting.md:335`, `docs/adopting.ja.md:336`) — the shipped stacked-branch base-ref discriminator's branch-existence test is hardcoded to `refs/heads/<predecessor-branch>` (local branch heads only): `git show-ref --verify --quiet refs/heads/<predecessor-branch>`. In a fresh clone, a CI checkout, or an adopter repo where the still-open predecessor branch exists only as `refs/remotes/origin/<predecessor>` (or is simply not fetched), this test fails even though the predecessor is genuinely still open and unmerged, and the expression silently takes the fallback `git merge-base "<integration-branch>" HEAD` arm. That arm is not the branch point — it resolves further back, before the predecessor's own changes — so every base-side-blob read this discriminator is meant to anchor (scope-lock allowlists, blast-radius sweeps, byte-identity diffs) is silently corrupted with no error or warning. A second, related gap surfaced under adversarial stress-testing: the item's own rationale for using `merge-base` rather than `rev-parse` on the first arm explicitly covers the append-only case (a rework round that adds commits to the predecessor after the child branch was cut) but says nothing about a predecessor branch that is rebased, force-pushed, or squash-merged after the cut — in that case `merge-base` can resolve to a point *before* the predecessor's changes landed on either branch, for the same underlying reason (git's ancestor search assumes append-only history). Neither the item's disclosed residual case ("a predecessor branch deleted without being merged") nor the spec's own `## Input space` reachable-input list names either sub-case. Suggested fix: broaden the existence test to also recognize a remote-tracking ref (or state a fetch precondition explicitly), and extend the disclosed residual-case language to cover a rewritten-history predecessor rather than only a deleted-unmerged one.
