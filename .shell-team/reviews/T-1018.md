#### Blockers

- **`bin/check-intent.sh:606`** — the freeze-attestation record's `P + F == ran` cross-check crashes on a grammar-conformant, entirely plausible hand-typed record and silently never runs, letting an internally self-contradictory attestation pass as `aligned`. `ATTEST_FULL_RE`'s `lines=`/`verdict=` fields are unrestricted `[0-9]+` (D4: "Every count is `[0-9]+`"), so a value like `verdict=08P/00F` or `lines=09/09` is a well-formed record. The check itself is `if [ "$((ap + af))" -ne "$ar" ]; then` — a bare arithmetic expansion, with no `10#` base-10 prefix (unlike the file's own established convention for `hash_version` two call sites away, `declared_n=$((10#$hash_version))` and `version_int=$((10#$hash_version))`). Bash's `$(())` treats a leading-zero digit string as octal, and `08`/`09` are invalid octal literals, so the expansion throws `value too great for base` — an unclassified stderr line with no `check-intent: <token>: ` prefix at all.
  The critical question is what happens next, and I resolved a direct three-way disagreement between my own first pass, Codex's primary pass, and Codex's own adversarial pass by re-running the real script twice:
  - Minimal isolated reproduction (`if [ "$((ap + af))" -ne "$ar" ]; then … fi; echo after`) under `set -euo pipefail`: prints the raw error, then **still prints `after`** — the script does not abort. This is correct, documented POSIX/bash behavior: `-e` is explicitly not applied to a command that is the condition of `if`/`while`/`until`.
  - Full reproduction against the shipped `bin/check-intent.sh`, with a real board carrying `- intent-hash (v1): <hash>` and `- freeze-attestation (v1, 2026-08-03): lines=1/1 sweep=mutual-satisfiability verdict=08P/00F owner=coordinating session` (an attestation that is arithmetically bogus on its face — 8 + 0 ≠ 1): **`exit=0`, stdout prints `check-intent: aligned: T-902 v1 (...) matches ...`**, stderr carries only the raw, un-namespaced `value too great for base` line.
  This is a genuine fail-open in the enforcement mechanism this entire task exists to add (D4's own framing: "the arithmetic and the count cross-check ... is what makes the record more than a rubber stamp"), reachable with zero exotic input — a two-digit count with a leading zero is an entirely ordinary thing for a hand-typed or padded record to contain, is not listed in the spec's Input space "Out-of-scope synthetic extremes" (which names only `v1.2`/`v01`-style *version* strings, 10 000-digit counts, and similar genuine extremes — never a two-digit `lines=`/`verdict=` value), and directly contradicts this repo's own "checkers must fail closed" contract (`CLAUDE.md`) as well as this very checker's own header ("every stderr write ... must have a classified exit path available").
  **Suggested fix**: mirror the file's own existing convention — `if [ "$((10#$ap + 10#$af))" -ne "$ar" ]; then` — a one-line change consistent with how `hash_version` is already parsed twice in this same file.

#### Major

- **`skills/run/SKILL.md`'s new `attestation` branch cannot be followed to completion for the ratified-re-freeze case the spec explicitly declares reachable.** The branch's final sentence says: "...re-run `check-intent.sh`, and only once it now reports the bootstrap `structural` shape compute and append the `- intent-hash (v1): <40-hex>` sub-bullet exactly as the bootstrap branch above does...". The instruction's own attestation half is correctly parameterized (`v<N>`, "the version about to be recorded"), but its hash-recording half is hard-coded to `v1` and gated on a `structural` outcome that is unreachable in this scenario — so an operator or orchestrating agent following the text literally either stalls waiting for an outcome that will not arrive, or, if pushed through anyway, appends a spurious second `- intent-hash (v1)` line onto a board that already has `- intent-hash (v2)`, which `bin/check-intent.sh` row (4) (`hash_valid_count -ge 2`) then permanently refuses as `structural` until someone manually removes the bad line.
  I weighed this against Codex's own two takes: the primary `codex exec review` pass tagged it `[P1]`; the adversarial pass, after directly cross-referencing the actual fixture lines in `tests/check-intent/run.sh`, judged it `Major` and confirmed the scenario's reachability while noting the very worst outcome (the corrupting duplicate write) requires the operator to push past the instruction's own natural stopping point (arriving at `aligned`) rather than being an unconditional certainty on every re-freeze.
