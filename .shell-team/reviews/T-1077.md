#### Blockers

- `bin/land-worktree.sh:519-538` — The composition loop resolves each worker-claimed path with `git ls-tree -z "$W" -- ":(literal)$p"` and then treats whatever it gets back as a blob/symlink cache entry (`git update-index --add --cacheinfo <mode> <sha> <path>`) without checking the entry's *type*. Input space item 5 ("A directory replaced by a file, or a file replaced by a directory") is declared a **reachable** input class this mechanism must handle correctly (not an out-of-scope synthetic extreme), and D5 promises the composed tree equals the coordinator tip's tree with exactly the worker's claimed paths substituted. I independently reproduced both directions in scratch git repos (not merely relaying Codex's report):
  - **file→directory** (base has file `x`; worker replaces it with directory `x/y`): `ls-tree` returns `040000 tree <sha>  x` for the claimed path `x`; the code blindly stages mode `040000` via `--cacheinfo` as if it were a blob. This **lands successfully (exit 0)** but the resulting tree is corrupted — `git ls-tree -r onto` shows both the correct `x/y` entry *and* a bogus extra entry literally named `xy` (no slash) at the same blob SHA, alongside a `warning: index entry is a directory, but not sparse` on stderr. This is **silent data corruption behind a green exit code**, not a refusal — it directly contradicts `skills/run/SKILL.md`'s own frozen `- invariant-lock: fail-closed-checkers — implemented — ... refuses ... rather than ever landing a partial, colliding or diverged result` line (SKILL.md:186), which this input class falsifies.
  - **directory→file** (the reverse): the composition step fails with `git update-index`'s own `'x' appears as both a file and as a directory` / `cannot add to the index` error, surfacing as `land-worktree: structural: failed to stage a changed path into the scratch index: x` (exit 2). At least fail-closed here, but misclassified — this is a content/composition defect (D6's exit-1 territory), not an invocation/usage problem (D6's exit-2 territory), and it wrongly consumes the `structural` class D6 reserves for input that "is not there or not usable."
  - AC2's `overlap-dir-file-replacement` token does **not** cover either direction: reading `tests/land-worktree/run.sh:372` and its `run_overlap_case` helper (lines 335-362) confirms that fixture only exercises **cross-worker overlap detection** (an early worker lands `x` cleanly; a late worker's own diff touches `x/y`, refused as `overlap` via the directory-prefix relation *before* composition is ever reached) — never a single worker's own directory↔file replacement composing with nothing else already landed, which is the path this bug lives in. Repro:
    ```
    # file -> directory (base: x is a file; worker: x becomes a directory containing x/y)
    git init -q repo && cd repo && git config user.email a@b.c && git config user.name a
    printf 'file content\n' > x && git add x && git commit -q -m base
    BASE=$(git rev-parse HEAD); git branch onto "$BASE"
    git rm -q x; mkdir x; printf 'nested\n' > x/y; git add x/y; git commit -q -m worker

    bash bin/land-worktree.sh --base "$BASE" --onto onto --worker "$WORKER"   # exit 0, but `git ls-tree -r onto` shows a corrupt extra "xy" entry
    ```
