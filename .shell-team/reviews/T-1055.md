All 16 frozen `- check:` lines were independently re-run live and PASS (matches the engineer/QA hand-off exactly); `bash tests/check-adapter/run.sh` (65/65), `shellcheck` on both new files, and `bin/check-intent`/`check-provenance`/`check-interventions` were also independently re-confirmed clean. Issues #203 and #221 were opened live this round (`api.github.com`) and match the spec's characterization of design points 1/4/5 and DP9 respectively — no issue-canon disclosure is needed this round.

The problem is not in what the frozen criteria test — it's in what they don't. This is verification-mechanism work whose entire value proposition is "never returns success on input it could not fully evaluate," and a battery of direct reproductions against `bin/check-adapter.sh` (mine) plus an independent adversarial Codex pass (which converged on several of the same gaps and surfaced others) show that guarantee does not hold in several concrete, reproducible ways.

#### Blockers

- `bin/check-adapter.sh:262-266` (`load_adapters_registry`) — A malformed row in `templates/binding-adapters.txt` (T-1054's shipped, plugin-owned adapter allowlist, read by every mode of this checker) is **silently skipped** rather than refused: `[ "${#f[@]}" -eq 2 ] || continue`. No character-class check, no duplicate-adapter-token check. Reproduced against the **real shipped file**: appending `claude-cli claude extra-junk` to `templates/binding-adapters.txt` and running `bash bin/check-adapter.sh` still prints `check-adapter: valid: ...` and exits `0`, while `bash bin/check-binding.sh --config templates/binding-template.conf` (parsing the *identical* file) correctly refuses `registry-malformed` at exit `2`. This is exactly DP12's own stated threat model ("a stray edit" to a plugin-shipped file) and directly contradicts the Goal's central claim. Fix: mirror `check-binding.sh`'s strict two-token/character-class/duplicate validation of this same file (folding into the existing `contract-unreadable` token per provenance decision #1's own precedent, or a symmetrical extension of `contract-malformed`, is enough — no 22nd token is obviously required, but the spec's "closed 21-token" freeze means this needs a provenance-recorded decision, not an ad hoc fix).

#### Major

- `bin/check-adapter.sh:365-372` (`load_contract`'s completeness gate) — Only `field`, `channel`, and per-role `role-board-authority` non-emptiness are enforced. `error-class` rows and the mandatory `none` `effort-mechanism` row have **no enforced minimum** at all. Reproduced: stripping every `error-class` line from a copy of `templates/task-envelope.txt` and running `--contract` against it still validates `0`. Nothing in the checker itself protects the "four required error classes" / "one `effort-mechanism none` row" invariants AC2's frozen test currently only happens to observe because the *shipped* file is correct today.
- `bin/check-adapter.sh:318-320` (`schema` parsing) — No `SUPPORTED_SCHEMA_VERSIONS` allowlist analogous to `check-binding.sh`'s `schema_version_supported()`. Reproduced: a scratch contract with `schema 2` plus matching `envelope-schema 2` definitions validates cleanly even though this script's own logic is schema-1-specific. A future, genuinely incompatible schema bump that happens to keep the existing row shapes would pass silently.
- `bin/check-adapter.sh:533-545` (`validate_all_definitions`) — Default (no `--adapter`/`--binding`) validation only checks whatever `*.txt` files are *present*, never that the file set equals T-1054's two-row allowlist. Reproduced: a definitions directory containing only `claude-cli.txt` (i.e. `codex-cli.txt` accidentally deleted) still validates `0`. This directly **falsifies the spec's own `## Input space` claim** ("no definition file for a bound adapter... is reachable and fails closed") for exactly this mode — it fails closed for `--adapter`/`--binding` (which look up a specific file), but not for the default whole-directory mode AC2 and the CI dogfood step actually exercise.
- `bin/check-adapter.sh:506-511` (`field-coverage-gap`) — Only checks that a `carries` row *exists* for each field, never that a **required** field's declared channel is meaningfully carried. `not-carried` is a legitimate channel value (correctly, for genuinely-uncarried fields), but nothing stops a definition from mapping every required `in` field — `task-id`, `role`, `request` — to `not-carried` and still passing. Reproduced against `claude-cli.txt` with `task-id` remapped to `not-carried`.
- `bin/check-adapter.sh:578-594` (`--binding` mode) — The delegated canonical binding from `check-binding.sh --print-binding` is trusted for shape: non-`bound` lines are silently skipped, and there is no re-assertion of "exactly six unique-role rows." Currently unreachable via the real, correctly-tested sibling script, but this is exactly the delegation-confusion class the review was asked to probe — a future bug in `check-binding.sh` that emitted a truncated or partial `bound` set would produce a false-successful cross-check here rather than a refusal.
- **AC8's "two-directional set equality" is materially weaker than DP2 claims.** It compares only the *field-name* token set between the prose and the registry — never each field's declared direction or requiredness, and never the `channel`/`error-class`/`effort-mechanism`/`role-board-authority` tables at all. Reproduced live: editing the doc's `task-id` bullet from `(in, required)` to `(out, required)` (registry unchanged) left `AC8: PASS` — a genuine drift between the two contract forms that the review specifically asked about, undetected. (Change reverted immediately after the test; `git status --short` confirmed clean before and after.)
- **The `status` field's "closed vocabulary" has no machine form at all.** `docs/loop-engineering/task-envelope.md:76-79` promises status comes "from the contract's closed status vocabulary," but unlike `channel`/`error-class`/`effort-mechanism` (each a real, extensible directive type in `templates/task-envelope.txt`), there is no `status-value` directive anywhere — confirmed by grep (`CONTRACT_DIRECTIVES` has no such entry, and `templates/task-envelope.txt` has no such rows). T-1056 will have to reopen this contract (add a new directive type to both the registry and the checker) to get concrete status tokens, exactly what this task's own stated purpose was to prevent.
- **The per-adapter `carries` mapping cannot correctly express `board-transition` across all roles an adapter may legally bind to.** `role-board-authority` is role-scoped (`writes` vs `proposes`); `carries` is adapter-scoped. Nothing in `check-binding.sh`'s grammar restricts which of the six roles may bind to which adapter (only provider/adapter pairing is checked) — reproduced: a binding config assigning `codex-reviewer` (a `proposes`-authority role) to `claude`/`claude-cli` is accepted by both `check-binding.sh` and `check-adapter.sh --binding`. `templates/adapters/claude-cli.txt` unconditionally declares `carries board-transition board` (i.e. this adapter *writes* the board itself), which is simply wrong for a `proposes` role bound to it. This is a real, currently-reachable cross-cutting gap between two of the contract's own design axes, not a hypothetical.

#### Minor / nits

- `bin/check-adapter.sh:338,344,350,482` — Duplicate `channel`/`error-class`/`effort-mechanism`/`effort-value` rows are silently deduplicated (`in_list ... || SET+=(...)`) rather than refused, unlike `role-board-authority`'s explicit duplicate check a few lines below. Low-severity but inconsistent within the same file.
- `bin/check-adapter.sh:567-568` (`--binding`) — Any nonzero exit from `check-binding.sh --print-binding` — a genuine content refusal *or* an unrelated internal crash (e.g. its own `team-paths.sh` becoming unreadable) — is collapsed uniformly into `binding-invalid`. Fine and well-tested for genuine refusals (DP10/AC7); would mislabel an unrelated infrastructure failure as a host config mistake. Low likelihood given the sibling script's own maturity.

#### Adversarial findings

An independent adversarial Codex pass (devil's-advocate framing, same files) converged on 6 of the 8 Major findings above without prompting (the malformed-registry-row gap, the schema-version gap, the whole-directory-completeness gap, the vacuous-`not-carried`-coverage gap, the delegated-output-shape-trust gap, and AC8's weak field-tuple comparison — the last extended to note the `channel`/`error-class`/`effort-mechanism`/`role-authority` tables aren't cross-checked between prose and registry at all, beyond field names) and additionally surfaced the `board-transition`/role-authority cross-cutting mismatch and the duplicate-row dedup minor, both folded in above. No adversarial finding was rejected; all were corroborated either by my own direct reproduction or by code reading matching the described mechanism exactly.
