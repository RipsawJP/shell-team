#### Major
- `bin/team-paths.sh:84` and `bin/team-init.sh:87` (mirrored) — **M1: pathspec metacharacters in `$base` defeat the tracked-file and ignore checks.** `validate_base` explicitly permits glob-shaped names (its own comment: "a base like 'a*' is safe" — true for shell word-splitting, not for git). Live repro: a repo where `abc/file.txt` is tracked and a directory `a-star-dir/` is the *actual* ignored, untracked target — `git ls-files -- "a*"` returns `abc/file.txt` (an unrelated tracked file), making `tracked` non-empty and silently suppressing the notice; independently, `git check-ignore -q -- "a*"` itself answers "not ignored" (exit 1) even though `a-star-dir/` really is. Suggested fix: force literal pathspec interpretation (`:(literal)$base` or `-c core.literalPathspecs=true`) in both scripts' `ls-files` and `check-ignore` calls.
- `bin/team-paths.sh:74-84` and `bin/team-init.sh:77-87` (mirrored) — **M2: `git rev-parse --is-inside-work-tree`'s exit status alone is not a reliable N2/N3 discriminator.** The probe only checks the command's exit status and discards stdout. Live repro: inside a **bare** repository, `rev-parse --is-inside-work-tree` exits 0 while printing `false` — the probe treats this as "inside a work tree," falls through to `check-ignore`, which then fails with exit 128 ("fatal: this operation must be run in a work tree"), landing in the `*)` branch and emitting **N3** ("undeterminable") instead of the correct **N2** ("outside a git work tree"). The same unchecked-exit-status logic runs the opposite direction for "dubious ownership" / permission-denied / corrupted-repo failures: those make `rev-parse` exit non-zero for a reason that is *not* "outside a work tree," yet the current `case` sends every non-zero exit straight to N2, misclassifying an undeterminable state as a definite one. Suggested fix: capture and check stdout (`out=$(git ... rev-parse --is-inside-work-tree 2>/dev/null); rc=$?`) — treat `rc=0 && out=true` as inside, `rc=0 && out=false` as N2, and any other outcome as N3 rather than N2.
- `bin/team-paths.sh` (`--print`, line ~88) — **M3: `--print` silently misses the docs/adopting.md-recommended directory-form ignore rule when the base dir does not yet exist on disk.** Live repro: a fresh repo whose committed `.gitignore` reads `.shell-team/` (the directory form D6/AC7's `LA4` fixture and `docs/adopting.md` both recommend) — `git check-ignore -q -- ".shell-team"` returns exit **1** ("not ignored") when the `.shell-team` directory has not been created yet, and exit **0** once it exists. `bin/team-init.sh`'s call site is immune by construction (D9: probed *after* scaffolding creates the dir), but `--print` has no scaffolding step and can genuinely be invoked before the base dir exists (e.g., an operator inspecting a fresh clone). AC7's own `LA4` fixture always `mkdir -p`s the directory before invoking `--print`, so this gap is untested as well as unfixed — this is exactly the "silence means not ignored" failure mode mandatory item (a) asks this review to rule out, and it is not ruled out for the one documented, recommended ignore-rule form. Suggested fix: normalize the check-ignore query to an explicit directory form regardless of on-disk existence (e.g. `check-ignore -- "./${base%/}/"` or a synthetic descendant probe), and add a fixture where the base dir is absent.
- `bin/team-paths.sh:99` / `bin/team-init.sh:102` (the frozen N1 body) — **M4: N1's "specs" claim is false for the legacy split layout.** In legacy mode `BASE="tasks"` while `SPECS="docs/specs"` (a sibling top-level directory, confirmed at `bin/team-paths.sh:203-205`) — the *only* one of the five nouns N1 lists that is not always `"$BASE/…"`. If only `tasks/` is ignored (and nothing under it tracked) while `docs/specs` is not, the fired N1 notice still asserts "...the board, specs, provenance, interventions and review records written there cannot be committed..." — false for specs in exactly this state. `bin/team-init.sh` itself already carries adjacent, specs-split-aware logic a few lines below this same call site (line 311-312's `if [ "$TEAM_SPECS_DIR" != "$TEAM_RUN_BASE/specs" ]` printing a separate "legacy split-root layout" line), so the codebase is demonstrably aware of exactly this split — the new notice just doesn't consult it. Because D8 freezes N1's bytes verbatim across both scripts with no room for conditional wording, a clean fix touches frozen intent-block text (class-B/re-freeze territory) rather than being a same-round drop-in patch — flagging for a scoped decision (re-freeze N1's wording, or split the message to name only records actually rooted under `$base`) rather than prescribing the byte change from this role.

#### Minor / nits
- `bin/team-paths.sh:84` / `bin/team-init.sh:87` — `git ls-files`'s own errors are discarded (`2>/dev/null || true`), so an unreadable/corrupt index could in principle produce a false N1 (if `check-ignore` then answers 0) or a false silence (if it answers 1) rather than N3. Downgraded from Codex's adversarial-pass "high" tag: triggering it requires an already-broken git index/permission state that would likely break many other git operations in the same repo first, so the blast radius beyond this probe is limited.
- `bin/team-paths.sh` / `bin/team-init.sh` — a tracked symlink or submodule gitlink placed exactly at the resolved base path can make `ls-files -- "$base"` register an entry that is not really "a tracked file under the base" (or, for an untracked symlink plus a directory-only ignore rule, make `check-ignore` answer from the symlink's own index shape rather than the directory it points through). Downgraded from "high": no documented `TEAM_RUN_BASE` example is a symlink or gitlink, and an operator would have to deliberately construct this base-dir shape.
- `bin/team-paths.sh` / `bin/team-init.sh` — the tracked-file check and the `check-ignore` call are two unlocked reads; a `git add`/`.gitignore` edit landing between them could combine into a state that never really existed. Advisory-only feature, no security boundary, and the window is a few milliseconds within one already-fast script invocation.
- `bin/team-paths.sh` / `bin/team-init.sh` — ambient `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS` etc. in the caller's environment could redirect which repository/index the probe actually inspects. Requires an already-unusual invocation environment; no adopter-facing guidance suggests exporting these around a shell-team invocation.
