#### Blockers

- **The enrollment itself has no durability or monotonicity, and the gap is undisclosed.** The occupancy lattice (DP-1, AC1, AC2, AC13) deliberately resolves an *absent* `<base>/oversight.conf` to `autonomous`, matching `bin/resolve-executor.sh`'s binding-config precedent. That precedent is sound for a config nobody has ever authored. It is not sound once a repository has declared `governance-controlled`: deleting the file, renaming it, letting a symlink's target drift to a different (or absent, or `autonomous`) file, or redirecting resolution via `--base` / `--config` / `TEAM_OVERSIGHT_BASE` all land on the same "absent" arm and resolve silently back to `autonomous` — indistinguishable from a repository that was never enrolled. No criterion (AC1–AC20) tests for this present-then-absent transition; AC5/AC6 fail-close only the malformed-vs-valid axis (directory, dangling symlink, unreadable, grammar faults) for a file that is *present*, never the enrolled-vs-never-enrolled axis. The five-item duty-C disclosure (no authentication, one party writes both fields, substance unreadable, gate-ran unverifiable, undetermined efficacy) does not name this hole, and neither does any Non-goal or Input-space line — "no `oversight.conf` at all" is listed only as an ordinary reachable class, not distinguished from a prior-governance de-enrollment.
  - This is exactly the domain-premise class the task's own dispatch line elects a cross-provider review for ("a wrong premise ships a control an auditor would reject while every gate stays green"), and it compounds with the record-durability disclosure at Goal:69 (the board sub-bullet is git-tracked, but the *declaration that governance applies at all* carries no equivalent tracked or tamper-evident anchor — a `governance-controlled` `oversight.conf` need never be committed at all, and even if it is, standard git history operations available to the same party the mechanism constrains — force-push, rebase, squash, gc on an uncommitted config — leave no trace that governance was ever in force).
  - Ran a parallel adversarial pass specifically on this claim (`.shell-team/reviews/T-1103-codex-adversarial.txt`): the strongest defense offered is that this is a deliberate, coherent design tradeoff mirroring `binding.conf`'s snapshot-oriented default. That defense explains *why* the current shape was chosen; it does not show the residual is disclosed anywhere the spec's own "disclosed, not closed" idiom (duty C, Non-goals) would put it. 5 of 8 adversarial angles sharpened the critique further (rebase/squash/gc erasing evidence; `--config` naming a valid `autonomous` file even though an *absent* explicit path fails; "No per-task profile override" blocking only a task-level selector, supplying no repository-level memory).
  - **What would close or at least honestly bound this**: either (a) an explicit disclosure — a sixth duty-C-style item or a Non-goal — stating plainly that de-enrollment (by deletion, redirection, or history rewrite) is indistinguishable from never-enrolled and is not detected, so an adopter relying on this mechanism must pair it with their own git branch-protection/commit-signing/retention controls; or (b) a design change making enrollment sticky (e.g., refusing "absent" once the board or a tracked marker shows the repository was ever declared `governance-controlled`). Either is acceptable; shipping neither is not, because the current text lets a reader believe "the profile persists" when nothing in the design or the criteria backs that belief.

#### Major

- **A conformant approval record is not bound to the content it approves.** `record=<locator>` is free-form and unvalidated, the date carries only day precision, and no criterion requires the record to name a commit, tree, spec hash, or diff range. AC3 checks only that the four fields are present, well-formed, and carry two distinct handles — not that the recorded approval still corresponds to the artifact at the seam it gates. A record approved once, then left untouched through further rework rounds that materially change the spec or the diff, still reads as conformant at every later seam invocation. This is a different axis from duty-C(iii)'s disclosed "presence check is satisfied by a record nobody thought about" — that residual is about whether the approver *read* the artifact; this one is about whether the artifact the approver read is *still the one being gated*. Recommend either disclosing this explicitly (a sixth duty-C item, or folding it into the existing one with sharper wording) or requiring the record to carry a content anchor the checker can at least assert is non-empty and distinct per rework round.

On inspection this is substantially already covered by duty C(i) (no ownership proof) and C(ii) (one party can write both fields) — the spec already discloses that nothing verifies either handle corresponds to a real party. **What is not closed**: the sticky-enrollment evidence is scoped to **the current task's own single board entry**, not to the repository's board as a whole (verified against the Goal's stickiness paragraph, DP-11, and AC21's own check line, which reads only the `--task`-named entry). The profile itself is declared a **per-repository** property (Goal, one-sentence summary: "a host selects an oversight profile for its own repository"). This creates a scope mismatch: a brand-new task's very first `specify-seam` crossing — before that specific task has recorded its own first approval — still silently falls back to `autonomous` if `oversight.conf` is deleted or redirected at that exact moment, regardless of how many prior tasks on the same board carry conformant approval records. Duty C **(vi)**'s own prose ("a repository that enrolls and de-enrolls before **its board** carries any approval record") reads as repository-wide and does not disclose that the actual mechanism looks only at the invoked task's own entry — an adopter reading that sentence could reasonably believe the check considers the repository's accumulated history, when it does not.

This is a genuine, previously-unidentified gap in the round-2 correction, confirmed independently by the dedicated Codex pass (`.shell-team/reviews/T-1103-codex-specreview-r2.txt`). It is materially narrower than round 1's Blocker — the exposure window is bounded to a task's pre-first-approval period rather than being open indefinitely for the whole repository — so I am not re-opening it at Blocker severity. It is a **Major**, and it has two independent cheap fixes, either of which would close it: **(a)** widen AC21's evidence read from the invoked task's own entry to a scan of the whole resolved board (`## Active` and `## Done`) for any `- oversight-approval (` record anywhere, so the stickiness genuinely reflects repository-wide governed-operation history; or **(b)** if per-task scope is the intended, accepted design (a defensible position — the profile applies repository-wide but the *evidence* the checker can cheaply gather is necessarily per-invocation), correct duty C **(vi)** and the Goal's stickiness paragraph to say so explicitly ("this task's own prior approval," not "its board" read repository-wide), so the disclosure matches the mechanism rather than overclaiming it.

#### Round-1 Major (content binding) — closed for `pre-merge`, reopened for `specify-seam` by an undisclosed gap

AC22's `pre-merge` anchor (object-exists, ancestor-of-`HEAD`, spec-precedence) is sound: because a commit id is a real, immutable git object, there is no way to fabricate a "future" or nonexistent anchor that still passes the checks, and duty C **(x)**'s disclosed residual (commits added on top don't invalidate) is an honest, necessary tradeoff given close-out's own commit lands after approval. This half is genuinely closed.

The `specify-seam` anchor is not. The refusal fires only when **the board's recorded version is greater than N** (`approves=v<N>`) — deliberately `>` rather than `>=` so a first-freeze `v1` approval passes before any `- intent-hash` line exists. But nothing bounds `N` from above: an approval recorded as `approves=v999` passes at first freeze (board records no version, or `v1`, neither exceeds 999) and continues passing through every subsequent ratified re-freeze (`v2`, `v3`, …), because the board's version will in practice never exceed an arbitrarily large `N`. A party who can already write both `approver=` and `producer=` (duty C **(ii)**'s disclosed exposure) can, with the same one-time act, write an inflated `approves=` value that permanently defeats the exact staleness check AC22 was built to close — the round-1 Major's own defect, reopened through a different door. This is not named anywhere in duty C's ten items or the Non-goals; it is a fresh, sharp gap in the correction itself, confirmed independently by the dedicated Codex pass. **Major.** The fix is cheap and stays within the design's own stated shape: require `N` to equal the board's current recorded version exactly (treating "no `- intent-hash` recorded" as the pre-v1 case requiring `N = 1`), rather than merely "not exceeded by" it — closing the loophole without touching the `pre-merge` half or the `>` vs `>=` reasoning, which remains correct for the case it was written for.

#### Fresh defect (b) — the sticky-scan grammar and AC13's own proof-of-safety grammar are not the same pattern
