#### Major
- `skills/run/SKILL.md:137-141` / `docs/loop-engineering/telemetry-span-discriminator.md:104-114` — the rehydration-checkpoint convention's own literal, `--parent-span-id <the span it belongs to>`, names no resolvable value. The row schema has no `span_id` field at all (confirmed: the frozen 21-key span row carries only `parent_span_id`, never a `span_id`); `span` is a repeatable role label, not a unique identifier, so two rows sharing one `--span` value in the same run (already reachable today across retries/iterations of one role, and squarely reachable once the fan-out this task's own discriminator exists for lands) cannot be told apart by this pointer. As written, a reader cannot actually reconstruct which specific parent span row a rehydration child belongs to — the convention promises a resolvable parent-child edge over an existing field and, as specified, does not deliver one. This maps to the pre-commitment's droppable **D5** (AC11); this is round 1 of that trigger. Suggested fix (cheap, text-only): point the placeholder at a composite that already exists on every row — the parent's own `run_id`+`seq` pair (e.g. `--parent-span-id <parent's seq value in this run_id>`) — rather than a bare role name.
- `templates/loop-replay.html:413-439,1104` — the new gate/orchestration-cost convention's literal, `--span orchestrator --phase gate`, collides with an explicit, load-bearing invariant this already-frozen (Non-goal, byte-identical per AC7) template documents about itself: *"orchestrator/human stay structural, never derived, since they are this loop's topology and emit no spans themselves"* (line 413-415). `RING_AGENTS`/`ringSeen` are seeded only from `KNOWN_RING_AGENTS`, which deliberately excludes `"orchestrator"`; a span row with `span:"orchestrator"` (which `adaptRow` turns into a `type:"work", agent:"orchestrator"` event at line 394) is not yet `ringSeen`, so it gets pushed into `RING_AGENTS` as a *dynamically discovered* ring agent (line 435-437) — even though `"orchestrator"` is already a fixed structural node. `ALL_NODE_IDS = RING_AGENTS.concat(["orchestrator","human"])` (line 1104) then lists `"orchestrator"` twice with no dedup; both entries resolve to the same `worldPos("orchestrator")===ORCH_POS`, so the first real gate-span row this convention produces draws two overlapping/duplicate orchestrator circles (duplicate hit-targets too) and inflates `RING_AGENTS.length`, skewing `RING_ANGLE_STEP` and therefore the screen position of every other legitimate ring agent (tech-lead/pm-spec/engineer/qa-verifier/codex-reviewer/ui-designer). This is a genuine, deterministic regression the first time the convention this task ships is actually followed — not a hypothetical fan-out scenario — and it was not caught by **AC7**, which only proves byte-identity plus a `rollup-runs.sh`/`cluster-failures.sh`/`check-run.sh` behavioral check; it never exercises `gen-loop-replay.sh`/`templates/loop-replay.html` against the new *span-name value* this task introduces (the spec's own Reader-inventory/Non-goals reasoning for this file is scoped to "an unknown **key**", never to "a new **value** of the existing `span` field"). This maps to the pre-commitment's droppable **D3** (AC10), gated behind D4+D5 already having gone; this is round 1 of the D3/D4/D5 trigger, reported now rather than waiting. Fixing this without touching the frozen template means choosing a convention span-name that isn't a reserved structural id (e.g. `orchestrator-gate` instead of `orchestrator`) — which touches the frozen Goal/AC10 literal and would need the ratified class-B re-freeze path; alternatively, disclose the limitation explicitly and fast-follow a `loop-replay.html` fix.
