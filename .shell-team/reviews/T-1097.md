#### Major

- `bin/team-init.sh:235` — A bare `git switch -c "$TRIAL_BRANCH"` inherits the caller's `branch.autoSetupMerge` config. Verified live: with `git config branch.autoSetupMerge always` set in the target repo (a real, documented git setting some adopters carry globally, not a synthetic extreme), the new trial branch comes out with `branch.<name>.remote`/`.merge` pointing at the branch HEAD was on — i.e. upstream tracking got set. This directly contradicts the spec's own Scope boundary ("It does not... set upstream tracking") and Non-goals ("No `git add`, `git commit`, `git push`, upstream tracking..."). Fix is a one-token addition: `git switch -c --no-track "$TRIAL_BRANCH"` (`--no-track` is a real, current flag — reconfirmed against installed git 2.53.0's own `git switch -h`).
- `bin/team-init.sh:216-217` — `git check-ref-format --branch "$TRIAL_BRANCH"` runs without `-C "$TARGET"`, so it validates against the *invoking shell's own repository* (e.g. this checkout, if `team-init.sh` is invoked from inside it), not the target — and its stdout, which for git's ref-shorthand forms (`@{-1}`, `-`, etc.) is the *expanded* branch name, is discarded. Verified live with `--trial-branch '@{-1}'`: the format check passed silently (it was resolving *this* repo's previous branch, not the target's), then `show-ref --verify --quiet "refs/heads/@{-1}"` — a literal ref path that can never exist — also passed silently, skipping the intended "already exists" refusal entirely; only `git switch -c "@{-1}"`, run correctly `-C $TARGET`, caught the real collision (the target's *own* previous branch, name `other`, already existed) and failed with git's raw, un-controlled message rather than the script's own "already exists" wording. In a target repo whose own `@{-1}` does *not* collide with an existing name, this path would create a branch under a name nobody asked for (the expansion of the shorthand) rather than refuse or literally name it `@{-1}` — a correctness gap in the one validation step the spec explicitly delegates to git's own verdict ("`git check-ref-format`'s own verdict is the boundary"). Fix: run the check `-C "$TARGET"`, capture its (expanded) stdout, and use *that* value for every subsequent `show-ref`/`switch` call instead of the raw `$TRIAL_BRANCH`.
- `bin/team-init.sh:222,226,232,235` — All four `-C "$TARGET"` git calls, plus the un-scoped `check-ref-format` call above, inherit `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` from the invoking shell's environment. Verified live: with `GIT_DIR=<a real repo>/.git` and `GIT_WORK_TREE=<the intended target, itself not a git repo at all>` exported, the script's own validation reports the target as a legitimate work-tree top level (because `GIT_WORK_TREE` overrides what `show-toplevel` answers), then `git switch -c` runs against `GIT_DIR` — a **different, real, unrelated repository** — moving *that* repository's HEAD to the new branch, while team-init separately (git-independently) scaffolds `.shell-team/` into the *target* directory that was never a repository at all. Net effect: exit 0, "success", and an unrelated real repository's HEAD silently moved. The spec's own `## Input space` names this exact env-var class as an out-of-scope synthetic extreme ("declined"), but per this round's own mandatory-probe instruction that declared-out-of-scope classes are "notes, not verdict-gating" here — and given the demonstrated, concrete impact is precisely the single worst thing this flag's whole refusal design exists to prevent (moving the wrong repository's branch), I am not downgrading it. This is exploitable by nothing more exotic than a stale exported `GIT_DIR`/`GIT_WORK_TREE` left over from unrelated tooling in the same shell — a real, if uncommon, operator mistake, not an attacker model. Fix: reject the run (or explicitly unset these three vars for team-init's own git calls) whenever any of them is set in the environment, before the validate-and-switch block runs.
