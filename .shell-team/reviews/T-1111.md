### Independent primary reading — is the differential design now actually sound?

Read the full rewritten Venue, Arms, Discriminator, Verdict, Input-space and Non-goals prose (lines 91–236) and **AC4**–**AC9**'s check bodies directly, attacking the redesign's own central claim: "the comparison is **within-venue and differential**" (Goal, "Why the measurement question is closed").

**That claim is no longer literally true, and the gap it opens is round 1's Blocker surviving in a new shape.** The redesign moved from "the previous design's... one clone" (spec's own words, "Arms" paragraph) to **one throwaway `git clone` per arm** — three separate clones, not one shared venue. **AC4** verifies only that each clone's `rev-parse HEAD` equals the resolved branch point (content/commit identity); no criterion, and no **AC16(a)** mutation probe, verifies that the three clones are equivalent in filesystem permissions, mount, or per-invocation sandbox writeability. This reopens exactly the class of confound round 1's Blocker named — a non-role-scoped denial producing a false positive — under a **differential** rather than **uniform** shape: round 1's uniform-denial case (every clone denied) is correctly forced to `undetermined` by the four-branch coupling (verified: with all artifacts `absent`, the `plugin-role-confirmed`/`contradicted`/`declared-label-only` branches are jointly unreachable). But a **differential** denial — the control's clone happens to stay writable while the subject arms' clones happen not to, for a reason having nothing to do with the launched `subagent_type` (a race during clone creation, a transient sandbox-state difference between per-invocation launches, a quota crossed between the second and third arm) — produces exactly the `control-present`/`subject-absent` signature the design reads as `plugin-role-confirmed`, and nothing in **AC4**, **AC7**, or the mutation checklist would catch it. Compounding this: nothing freezes or records the three arms' **launch order or concurrency relative to each other** (only each arm's own three instances are launched "as parallel `Agent` tool calls inside one orchestrator message" — the three arms themselves are three separate messages, unordered and unrecorded), so a time-varying condition (anything that changes between the first and third arm's launch) could correlate with role rather than cause it. Neither gap is hypothetical-only: the spec's own "Input space" already treats "a venue that denies every write regardless of the declared type" as genuinely reachable — the differential (per-clone, per-time) variant of that same reachable class is simply not named or guarded. Note also that nothing in the design *requires* three separate clones: the per-instance filename already encodes both arm id and instance id (`probe-write-<arm-id>-<instance-id>.txt`), so a single shared clone would preserve the stray-write-detection property the spec cites as the reason for per-arm clones, while genuinely delivering the "within-venue" claim the prose makes. **Verdict on this item: the differential design closes round 1's specific self-attestation vacuity but does not yet carry the evidential weight its own "within-venue" claim asserts — a new Blocker, continuous with round 1's rather than independent of it.**

Two further items, both verified directly against the check bodies, both genuine but narrower:

- **AC7's `declared-label-only` branch is disconnected from AC5's arm-execution record.** The branch requires only `WG = 0` and `TG = 0` (zero total write-artifact and tool-probe lines) — it does not check whether **AC5** recorded the three arms `executed` or `declined`. A note could report all three arms `executed` (satisfying AC5) while supplying zero discriminator evidence and still legitimately claim `declared-label-only`, which AC7's own prose calls "the honest value when the arms were dropped" — but nothing ties that value to arms actually being dropped rather than executed-but-unreported. Major.
- **AC8's `- batch-timestamp:` completeness requirement is `>= 1`, not "exactly one per arm."** Verified against the check body: the per-arm loop only walks whatever `- batch-timestamp:` lines are present in the note; an arm's line can simply be omitted, and the declared `- launch-latency:` (claimed "the maximum... over the arm's own per-instance timestamps") would then be computed and verified only over whichever arms happen to have a line — silently excluding the arm with the largest true latency from the margin-factor ≥ 3 frozen-condition check, which is precisely the post-hoc-fitting risk **AC8**'s own re-derivation exists to close. A secondary, lower-severity gap in the same criterion: `- unit-timing:`'s command is not verified to be the fixed production unit, and `- batch-vs-sum:`'s `sum_ns` is not re-derived from any raw per-instance duration (only `batch_ns` is anchored).
