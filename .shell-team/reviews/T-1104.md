#### Major

- **The verbatim `executor-invocation` field is a real, if partially disclosed, PII residual, and the spec's own citation of its mitigation is incomplete.** `## Goal`'s "highest-value PII surface" paragraph names `bin/check-pii-shapes.sh`'s shape set as `home-path`, `home-path-win`, `home-encoded`, `temp-session` and `email-nonnoreply` (five classes) — but that script's own header (read first-hand at `bin/check-pii-shapes.sh:15`–`:83`) documents **seven**, including a `private-key` shape and a `token` shape (GitHub `gh[oprs]_`, AWS `AKIA`, OpenAI-style `sk-`) that are exactly the two most relevant to a field whose whole content is a real argv. Because the spec's own inventory of its cited mitigation is incomplete, its residual-risk reasoning is under-informed by its own primary source — the exact "factual claim not verified against the primary document" class this round's mandate asked to sweep for. A dedicated devil's-advocate pass on this specific claim (`.shell-team/reviews/T-1104-codex-adversarial.txt`) confirmed the practical effect: the *narrow* claim ("no mechanical protection exists at all") is defeated — known-shape credentials and PEM headers genuinely are caught by the existing diff-scoped CI gate — but the *broader* claim survives: the spec's field contract never states that this protection is a **finite known-shape screen, not comprehensive secret detection**, and the Goal's eleven-item disclosure enumeration has no item naming the residual that actually remains (an unsupported secret prefix, an arbitrary internal API key/password/webhook/bearer token, a token body below the regex's own length minimums, an `sk-` token missing its required left-hand boundary, or a non-PEM private key — all named directly by the adversarial pass's own `residual_after_defense`). This residual is also unlike the raw-capture files this same mechanism deliberately keeps untracked: it lands the invocation string in **permanently tracked** git history rather than a gitignored temp dump.
  - Fix: correct the `## Summarized sources` citation to name the full seven-shape set (or at minimum `token` and `private-key`), and add a twelfth disclosed-not-closed item stating precisely what the diff-scoped shape scan does and does not catch, in the same enumeration style items (i)–(xi) already use.

- **`AC17`'s own pure-insertion premise is factually wrong at the declared base ref, and the corresponding `## Assumptions` row asserts the same false zero.** Measured directly: `git show "$(git merge-base feature/1103-oversight-profiles HEAD):.shell-team/todo.md"`'s `## Active` section carries **two** existing `- [ ] **T-` entries (`T-1089`, `T-1086`, both `BLOCKED`), not zero. `## Assumptions` row 20 states "the board's `## Active` section carries **zero** `- [ ]` top-level entry lines at the branch point, so this task's entry is a pure insertion and AC17's `+1` delta is exact" — that premise is false as written. AC17's own check line is not literally broken by this (it computes both sides at run time as `AB`/`AH` rather than hardcoding a `0`, so the `+1` relative delta still holds regardless of `AB`'s real value), but the false "pure insertion" framing hides a real coverage gap Codex's own reading of AC17 independently raised: a net `+1` cannot distinguish "one entry added" from "one existing entry removed and two added" — and now that the base genuinely carries other live entries this task's own diff must not touch, that ambiguity is a reachable failure mode rather than a theoretical one.
  - Fix: correct row 20's premise to state the true count (two), and strengthen AC17 to assert that every one of the base's existing `## Active` entries still occurs at HEAD (a superset check), not only a net `+1` count.

#### Domain-premise questions answered directly (per this round's mandate)

1. **Blast radius of amending `agents/codex-reviewer.md:212` against unmeasurable adopter-side reliance.** Adequately, honestly bounded. 2. **Verbatim-invocation safety in adopter environments.** Partially bounded — see the Major finding above. This is a real, fixable gap, not a foot-gun shipped with no mitigation at all.
3. **Does the closed four-field grammar make the three T-1086 gaps checkable after the fact?** Partially, and unevenly across the three. Gap 1 (briefing not reaching the primary pass) and gap 2 (confirmation vs. seeded pass indistinguishable) become genuinely, mechanically legible from committed record bytes — the `briefing-fidelity` and `pass-role` fields plus the checker's grammar validation are real, verified teeth for those two. Gap 3 (raw captures overwritten across rounds) is only partly closed: the naming-rule amendment (`AC11`) closes the *structural cause* of the overwrite independently of the checker, and `AC7`'s collision/prefix check catches an accidental same-stem duplicate inside one record — but neither catches a cross-record collision (already disclosed, item viii) nor a case where the recorded stem is distinct while the underlying raw was itself overwritten by an unrelated bug. The Goal's own one-sentence framing ("checkable after the fact") should distinguish "recorded and legible" from "verified," specifically for gap 3.
4. **Is duty C's arm-B disposition honestly disclosed, and is AC7 sufficient teeth?** Yes, honestly disclosed, at the same standard this repository's own convention already applies to duty-C-shaped residuals elsewhere (T-1103's own duty C was accepted at this standard). AC7's collision/prefix check is real, if modest, mechanical teeth against the narrowest slice of gap 3 (the same-record duplicate case) — the Goal's summary sentence is the only place worth tightening, per point 3 above.
