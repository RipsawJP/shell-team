  - Fix: track each field's owning section (the heading immediately preceding that specific field line) at capture time, and require, for the id credited with a section's ownership, that all four of its field lines resolve to that same section — not only the earliest one.

#### Minor / nits

- **Bracket-class charset checks (`[a-z0-9-]+` for the pass id, implicitly ASCII-only intent elsewhere) run without forcing `LC_ALL=C`, unlike this repository's own established precedent for the same hazard** (`bin/close-out.sh:150`, `bin/check-oversight.sh:176`–`:181` both wrap a bracket-class test in `LC_ALL=C`). In a locale where POSIX bracket-range collation differs from the C locale, `[a-z0-9-]+` can admit bytes outside plain ASCII lowercase-alphanumeric-hyphen. Low practical likelihood in this repository's own CI (which does not set a non-C locale), but a real inconsistency against a precedent this same codebase already established for the identical hazard class.
  - Fix: `export LC_ALL=C` near the top of the script, alongside the existing `set -euo pipefail`.
- **Several `2>/dev/null || true` suppressions collapse "no match" and "grep/pipeline failed" into the same silent-pass outcome**, e.g. `:177` (the whole-record field scan), `:202` (the heading scan), `:278` (the collision `sort | uniq -d` pipeline).   - Fix: distinguish grep's own exit 1 (no match, expected) from a higher exit status (a real error) before treating an empty result as conformant.
- **The board-and-write-boundary Rule's closed write list at `agents/codex-reviewer.md:206` still names only the bare `T-XXX-codex-primary.{txt,jsonl}` / `T-XXX-codex-adversarial.{txt,jsonl}` / `T-XXX-codex-specreview.{txt,jsonl}` basenames, while the amended naming rule at `:212` (this task's own change) requires the suffixed `T-XXX-<pass-name>-r<N>` form from a task's second round of a given pass family onward and forbids the bare form at that point.** Read literally, a reviewer's second-round write of `T-XXX-codex-primary-r2.txt` is not one of the paths `:206` enumerates as the closed write surface, creating a textual self-inconsistency between two Rules bullets in the same file — though a reasonable reading resolves it (`:206`'s list names the closed *pass-name family*, and `:212` governs the per-round suffix mechanics within it), and `AC11`'s own anchoring explicitly locks `:206` as one of the base-blob lines this task must not touch, so this is very likely a deliberate, already-considered scoping choice rather than an oversight. Downgraded from the primary Codex pass's own P1/blocker framing on that basis: no acceptance criterion or fixture is affected, and the ambiguity is resolvable by any careful reader without contradiction.
  - Fix (non-blocking): a one-clause addition to `:206` acknowledging the per-round suffix (e.g. "...in that same dir, in either the bare or the `-r<N>`-suffixed form the naming rule above defines...") would remove the ambiguity outright without touching the locked base-blob line count, if `pm-spec`/the coordinating session judges it worth a follow-up edit.
