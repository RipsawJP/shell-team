## 5. Human-judgment item — emission wording vs. `flagFromLabel` side by side

Read `skills/run/SKILL.md`'s Telemetry section (the `handoff`/`rework`/
`gate`/`human`/`release` bullets) against `templates/loop-replay.html`'s
`flagFromLabel`/`adaptRow`.

**Found one real, subtle asymmetry, matching exactly the class D2's
symmetry table warns is invisible to grep.** D2's table row "uniform across
event kinds (D1)" requires: *emission wording* — "the rule is stated for
the label, not per event id"; *match rule* — "the derivation sits in the
`kind === 'event'` branch, not in a per-id case." The match rule side is
correct and independently confirmed (`adaptRow` derives `flag` in every one
of the five `case` branches, uniformly — and the `rail-uniform-kind`
assertion above proves a bare token on a `human` row really does derive a
flag). The **emission wording side does not match this requirement as
written**: the "put the token here" instruction is placed exclusively
inside the `handoff` bullet ("put it on this same `handoff` event's
`--label`..."), not stated generally for "the label" independent of which
event kind carries it. The separate `human` bullet gives its own,
different recommended label vocabulary (the interventions-class slugs, a
bare `GO`, a `STOP:<reason>`) and never mentions that a bare `READY_FOR_*`
token written there is *also* a legitimate, recognised way to record the
flag — even though D1's own rejected-alternative reasoning is built
explicitly around exactly that scenario ("a human settling the board flag
directly... is exactly the kind of row an operator writes"), and the
fixture's own uniformity-probe row (seq 22) is a `human` event carrying a
bare token for precisely this reason.

Practical consequence: an orchestrator reading `SKILL.md` literally would
learn only one place to put a flag token (`handoff`) and would not learn
that the implementation's deliberate uniformity (D1) also makes a `human`
row's bare token work — the intended breadth of D1's own design goes
under-communicated at the one place a reader would look. This does **not**
break any AC: AC5/AC15 only assert that the two frozen phrases and the five
tokens are present verbatim somewhere in the file, which they are, and the
code's actual behaviour is correct and uniform regardless of what the prose
emphasises. **Not FAIL-driving** — recording it here as the residual
judgment call the spec assigns to QA, for the reviewer/human to decide
whether it merits a documentation fast-follow (a one-clause addition to the
`human` bullet, or a general note above the per-event-id list, would close
it without touching AC5/AC6's additive-only constraint materially).
