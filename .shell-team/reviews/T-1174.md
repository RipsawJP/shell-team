#### Major (verdict-gating)
1. **Decision 3 / AC4, R3 never-dropped: the re-include derivation is unsound for a rule that also matches the directory's contents.** The predicate "the same rule matches the directory itself and no parent is ignored" holds for a global excludes rule `*` (it matches `.shell-team/` and `.shell-team/todo.md`). Reproduced here: with a global excludes file holding `*` and a root `.gitignore` holding `!.shell-team/`, `git check-ignore -v` still reports `.shell-team/todo.md` as ignored by the global rule (exit 0), so the printed one-line fix does not work. A trailing-slash negation unignores the directory only; files stay governed by whichever rule also matches them. The re-include line must be printed only when it is provably effective for the required paths, and the probe for the board and a `.md` probe under each directory must be re-evaluated against the derived rule: the rule must match the directory but must not match the probe file beneath it (otherwise omit the `!` line and name the source rule). AC4/AC5 need a fixture with a global `*` (or `.shell-*`-style rule that also matches file names) asserting no backticked `!` line.
2. **Decision 3 / AC3 / AC6, R3: the `Already in place:` predicate for the base directory checks only that the board file is in `HEAD`.** In the legacy layout (`tasks/` base, `docs/specs/` specs) a committed `tasks/todo.md` with an untracked, not-ignored `docs/specs/.gitkeep` satisfies every stated condition, so the base-directory line is reported under `Already in place:` while the specs directory is uncommitted; the Goal sentence and the Notes say both directories must be committed. The positive branch must also require a tracked anchor in the specs directory when it sits outside the base (and the `git add` command must name it when that anchor is absent from `HEAD`); AC6 needs the "board committed, specs untracked" fixture. An unborn `HEAD` must be stated as "not committed" (see minor 5).
3. **Decision 4 / AC7 / AC18 P1, honesty rule: a `codex *` entry found in a settings file is reported as a condition already in place, but file contents are not evidence that the entry applies.** Claude Code documents (per the cross-provider reviewers, not verifiable in this checkout) that project and local `excludedCommands` entries are ignored when an administrator requires the sandbox, and an entry is moot when `sandbox.enabled` is not true; managed settings or `--settings` can establish either state, and both are outside the three-file read set. Decision 4 and AC18 P1 assert "an entry found in any one of them is in effect"; the spec itself routes that assertion to this review as unconfirmed. The line under `Already in place:` therefore claims more than the evidence. Either word it as what was read ("found `codex *` in <file>; whether the session applies it was not determined", still outside `Remains the operator's decision:`), or restrict the positive branch to what the reader can establish and leave project/local entries and a missing `sandbox.enabled: true` undetermined. The same applies to a linked worktree whose local settings may be read from the main checkout (unverified here).
