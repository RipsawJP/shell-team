### My own synthesis of Codex's findings

**Finding 1 — upheld as major, and independently re-derived above (Independent primary reading, final paragraph) before I opened Codex's output.** This is the round's most consequential finding. Traced by hand against the actual `- check:` bodies: AC7 verifies `bin/resolve-executor.sh`'s field-5 resolution in isolation; AC1/AC3/AC4 verify the recipe's prose in isolation; the `probe-protocol`'s frozen command shapes (spec lines 74–79) use the literal `-c model_reasoning_effort=low`, not a value obtained by running the resolver against a scratch `codex-cli` binding and threading its output into the invocation. The protocol's own text ("the argv the evidence records is the argv the recipe composes") asserts the insertion *position* matches, which is true and independently verifiable — but the Goal's claim is about the *resolved value* reaching the invocation, and no criterion or evidence-boundary line closes that specific seam. This does not undermine the shipped mechanism's likely correctness (the position claim is genuinely verified, and an agent composing the invocation by reading the prose is the same self-attestation act every other freeze-then-run gate in this repository already accepts) — but the gap is currently **unnamed**, and the evidence-boundary's required-content list (five specific items) does not include it. Cheap to close either way: add one evidence-boundary line naming this seam as self-attested rather than mechanically bound, or strengthen the live-run protocol so the in-set arm's `-c` value is obtained from an actual `bin/resolve-executor.sh --role tech-lead --print-resolved`-style read against a scratch `codex`/`codex-cli` binding rather than a hand-picked literal.

**Finding 2 — downgraded to minor, largely already addressed.** Re-reading DP-i, the Goal's "What the run measures, and what it cannot" paragraph, and AC4's required literals (`not observable`, `what was passed`, `reasoning tier`) together: the spec is unusually careful to define "applied" as "reaches the invocation and is accepted by the provider" and to state the corollary — the telemetry value is "an observation of what was passed, never of what the provider did" — in the shipped prose itself, not only in this spec's internal reasoning. AC11's per-adapter window test requires both the `applied` and `recorded` words to co-occur, which is the mechanical form of forcing this exact two-sided honesty into the adopter docs. Codex's finding restates a distinction the spec already draws explicitly and requires the shipped prose to draw too; it is not a hidden overclaim. Worth one clarifying note if pm-spec wants extra insurance (e.g., an explicit sentence in the release-note or DP-i stating "applied" means "passed to the provider", never "executed at that tier"), but not blocking on its own.

**Finding 3 — downgraded to minor, largely already disclosed.** The "newly accepted value" scenario Codex raises is not a safety gap: an adopter setting an effort value the local adapter file does not yet declare is refused at resolution (`capability-unsupported`, before any invocation), which is the conservative, safe-by-design direction — nothing runs at an unintended tier. The "changed `-c` semantics" scenario (the flag's meaning itself shifting, not just the accepted-value enumeration) is a genuinely unmeasured risk, but it is the same adopter-host/later-version premise `## Input space` item 5 and A-17 already name and explicitly decline to assume closed ("unmeasured either way and is stated as such rather than assumed"). This is a real but already-disclosed premise, not an undisclosed one — the mandate here is whether the evidence boundary is honest and complete, and on this specific point it already is.

**Finding 4 — upheld as minor.** Re-checked against AC11's actual window test (spec lines 172–173): the 400-character flowed window around the first `cli-config-override` occurrence must contain both adapter tokens and both verb words, order-free — genuinely satisfiable by prose that names both adapters and both outcomes but pairs them backwards (e.g., attributing "applied" to `claude-cli` and "recorded" to `codex-cli`). This is a plausible authoring accident during a prose rewrite, not merely a hostile-adversary construction the spec's Non-goals item 9 correctly declines to defend against — and `## Verdict scope` places the four adopter documents at full adversarial depth, where "whether the amended prose overshoots in either direction" is explicitly named as in-scope. Codex's inclusion of **AC4** in this finding does not hold up on inspection: AC4's required literals (`BLOCKED`, `capability-unsupported`, `never a retry at a different tier`, etc.) are global escalation-rule statements with no per-adapter attribution to swap, so AC4 is not exposed to this failure mode — narrowed to AC11 alone.
