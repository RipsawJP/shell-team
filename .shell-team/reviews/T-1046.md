## Findings

### 1. `V1`'s committability claim is false for a previously force-added, already-tracked file
- **File**: `bin/team-init.sh` (the `emit_ignored_base_v1` body, transcribing the spec's frozen `V1`) / `.shell-team/specs/T-1046-ignored-base-verdict.md` D4(ii)
- **Acquisition layer?** No — this is a message-wording defect. The channel read (`check-ignore` exit 0) and its classification (`DT5` → IGNORED) are both correct; the frozen *text* asserted for that classification overclaims.
- D4(ii) argues `V1` "stays true even when the base dir has been force-added," reasoning that the message only reports "what git answered." Reading `V1`'s actual body shows this is only true of its first line (`git reports the resolved base dir as ignored: <base>`); the next four lines assert a consequence — "everything the loop writes under it ... **cannot be committed** ... will report success **having committed nothing**." Live repro: `git init` a fixture, ignore `.shell-team/`, force-add `.shell-team/todo.md`, modify it, then `git add` it with **no** `-f` — the add succeeds (git prints the "ignored" advisory but the file **is** staged, confirmed via `git status --short` showing a staged `M`), and `git commit` succeeds, landing both the original and the modified content in `HEAD`. So for that specific already-tracked file, the loop's commit step does **not** "report success having committed nothing" — it genuinely commits it. `V1`'s blanket "everything ... cannot be committed" is false in this reachable state.
- **Severity: Major.** Real, live-verified, and the same *class* of defect as T-1042's M4 (a frozen message asserting something false in a specific reachable state) — but narrower in practical blast radius, since it requires an adopter to have deliberately force-added a file under an otherwise-ignored directory, which is not the documented remedy (`docs/adopting.md` documents a repo-level `!<base>/` re-include, not per-file force-adds).
- **Suggested fix**: either narrow the wording to "new records the loop writes there" rather than "everything the loop writes," or drop the committability prediction from `V1` entirely and keep only the first line's factual claim ("git reports the resolved base dir as ignored") — which is what D4(ii) says the reword already did, but the shipped text does not.

### 2. `docs/adopting.md` (and its `.ja` mirror) describes `V2` firing for a state that actually routes to silence
- **File**: `docs/adopting.md:64-66` (and `docs/adopting.ja.md`'s mirror paragraph)
- **Acquisition layer?** No — a documentation-accuracy defect. The classification itself (`DT4`: nonzero `rev-parse` → SILENCE) is correct and matches the frozen table exactly; the *documentation describing* that classification is wrong.
- The document states: "If git itself can't give a documented ignored/not-ignored answer (a corrupt or unreachable repository, for instance), `team-init` says so rather than guessing." A corrupt-or-unreachable repository is exactly the state a nonzero `rev-parse --is-inside-work-tree` exit reports — and per `DT4`, that state routes to **SILENCE**, not to `V2`. Live repro: a stubbed `git` on `PATH` that fails `rev-parse` with a fatal, non-"not a git repository" message (simulating a corrupt/unreachable repository) — `bash bin/team-init.sh` against that stub produces **zero** `WARN:` lines. The document promises a notice for exactly the scenario the implementation deliberately silences.
- **Severity: Major.** A user-facing document making a false claim about the tool's own behaviour is a real defect (an adopter reading this text and trusting a notice that will not fire), though — like finding 1 — it does not affect the channel-reading mechanism itself.
- **Suggested fix**: reword the sentence to name the actual `V2`-triggering condition (`check-ignore` itself failing with an unexpected exit status while inside a genuine work tree — a narrower, rarer state than "corrupt or unreachable repository"), or state plainly that a corrupt/unreachable repository is silent rather than reported, matching `DT4`.

### 3. The frozen twelve-variable neutralization list omits `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`, letting the ambient environment inject an arbitrary `core.excludesFile` and flip the verdict
- **File**: `bin/team-init.sh`'s `git_probe()` / `.shell-team/specs/T-1046-ignored-base-verdict.md`'s "Neutralized environment" invocation constraint (D8)
- **Acquisition layer? YES.** This is exactly the invocation-constraints half of the acquisition layer the spec's own pre-commitment gives a one-round trigger.
- `git-config(1)`'s ENVIRONMENT section documents `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` as a way to inject arbitrary configuration pairs — including `core.excludesFile` — "for cases where you want to spawn multiple git commands with a common configuration but cannot depend on a configuration file"; these override values in configuration files. None of the three is in `git_probe()`'s `env -u` list (nor in the spec's own frozen twelve-variable list). Live repro, with the repo's own `core.excludesFile` config **correctly persisted to `/dev/null`** and a clean, non-ignored fixture confirmed silent as a baseline: exporting `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.excludesFile GIT_CONFIG_VALUE_0=<a hostile excludes file naming the base dir>` into `bin/team-init.sh`'s environment — with **zero** change to the repo's own config, `.gitignore`, or any file on disk — turns the same, otherwise-silent fixture into a full `V1` firing (8 `WARN:` lines). The ambient environment alone flips the verdict, through a channel the spec's own admissibility framing never considered: not a diagnostic string, not a merged stream, not an unnormalized pathspec — a config-injection mechanism sitting one level below the channel the emitter reads.
- The adversarial pass separately named `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`, `GIT_CONFIG_NOSYSTEM` and `GIT_FLUSH` as further gaps in the same list; these were not independently re-verified by this reviewer (time-bounded), but the one verified instance is sufficient to establish the class.
- **Severity: Major**, and — because it sits on the acquisition layer — **this fires the spec's own one-round same-class-2 pre-commitment on this, the first cross-provider round.**
- **Not grounded in the spec's own Input Space out-of-scope list**: the Input Space's "ambient environment" bullet enumerates exactly the twelve frozen variables plus locale — it does not affirmatively declare `GIT_CONFIG_*`/`GIT_COMMON_DIR`/etc. out of scope, it simply omits them from the enumeration. Per this role's own severity-grounding rule, a downgrade requires a *cited* out-of-scope line; there is none to cite here, so the finding keeps its Major severity rather than being downgraded for falling outside an incomplete list.

2. **(b) Answer #167 with documentation, ship no probe at all.** This is the only disposition that closes finding 3 completely, because it removes the attack surface (there is no probe left to manipulate). 3. **(c) Move the check into an opt-in, fail-closed `bin/check-ignored-base.sh`.** Does not close finding 3 by itself — the checker would read the identical two channels and inherit the identical gap — but a *checker*, unlike an advisory, is the natural place to make "cannot trust the ambient environment enough to answer" a first-class exit-2 (undeterminable) outcome by design, which is arguably the more defensible long-term shape for this specific vulnerability class (an environment-injection attack against git's own configuration is a different threat model than a merged stream or an unnormalized pathspec, and a checker's fail-closed contract handles "I don't trust my inputs" more naturally than an advisory's silence-or-warn contract does).

None of the three, taken as originally worded, closes finding 3 without an additional change (widening the neutralization list at minimum, in dispositions (a) and (c)). This reviewer's read: whichever disposition is chosen, the neutralization list itself needs to grow to at least cover `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>` (and the adversarial pass's other named candidates, independently verified before being added) — but the choice among (a)/(b)/(c) is pm-spec's/the coordinating session's to make, not this role's.
