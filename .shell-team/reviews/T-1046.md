### 1. `V1`'s committability claim is false for a previously force-added, already-tracked file
- **File**: `bin/team-init.sh` (the `emit_ignored_base_v1` body, transcribing the spec's frozen `V1`) / `.shell-team/specs/T-1046-ignored-base-verdict.md` D4(ii)
- **Acquisition layer?** No — this is a message-wording defect. The channel read (`check-ignore` exit 0) and its classification (`DT5` → IGNORED) are both correct; the frozen *text* asserted for that classification overclaims.
- D4(ii) argues `V1` "stays true even when the base dir has been force-added," reasoning that the message only reports "what git answered." Reading `V1`'s actual body shows this is only true of its first line (`git reports the resolved base dir as ignored: <base>`); the next four lines assert a consequence — "everything the loop writes under it ... **cannot be committed** ... will report success **having committed nothing**." Live repro: `git init` a fixture, ignore `.shell-team/`, force-add `.shell-team/todo.md`, modify it, then `git add` it with **no** `-f` — the add succeeds (git prints the "ignored" advisory but the file **is** staged, confirmed via `git status --short` showing a staged `M`), and `git commit` succeeds, landing both the original and the modified content in `HEAD`. So for that specific already-tracked file, the loop's commit step does **not** "report success having committed nothing" — it genuinely commits it. `V1`'s blanket "everything ... cannot be committed" is false in this reachable state.
- **Severity: Major.** Real, live-verified, and the same *class* of defect as T-1042's M4 (a frozen message asserting something false in a specific reachable state) — but narrower in practical blast radius, since it requires an adopter to have deliberately force-added a file under an otherwise-ignored directory, which is not the documented remedy (`docs/adopting.md` documents a repo-level `!<base>/` re-include, not per-file force-adds).
- **Suggested fix**: either narrow the wording to "new records the loop writes there" rather than "everything the loop writes," or drop the committability prediction from `V1` entirely and keep only the first line's factual claim ("git reports the resolved base dir as ignored") — which is what D4(ii) says the reword already did, but the shipped text does not.

### 2. `docs/adopting.md` (and its `.ja` mirror) describes `V2` firing for a state that actually routes to silence

## Codex's findings (native labels, before normalization)
Codex returned a JSON array of three items, tagged with its own severity vocabulary — normalized per this role's fixed map (P1 → blocker, P3 → minor):

1. **[Codex: P1]** `bin/team-init.sh:254` — an ambient, exported Bash function named `env` intercepts `git_probe()`'s bare `env -i ...` call, because Bash's command lookup checks shell functions *before* `$PATH`, independent of what `$PATH` contains. ## Independent live reproduction (this role, against the real working tree, before keeping either finding)

**Finding A (`env`-function shadowing) — reproduced, confirmed exploitable.** Built a fixture whose repo-local `.gitignore` holds only `build/` (i.e., genuinely *not* ignoring the base dir, `core.excludesFile` pinned to `/dev/null`) and confirmed the baseline is silent. Result: **`V1` fires in full** (the "resolved base dir as ignored" anchor line appears) against a fixture that is, by its own repo configuration, genuinely not ignored — the allow-list is not merely bypassed for one variable, it never executes at all, because the sanitization step itself was intercepted before `git` was ever reached. This requires nothing beyond the ability to set an environment variable ahead of `team-init.sh`'s invocation — the *identical* threat-model tier already established as in-scope by round 1's finding 3 (which also flipped the verdict via an ambient environment variable). The same root cause (Bash resolves shell functions before `$PATH` for every bare command word) would identically let an exported function named `git` bypass the mechanism even more directly, without touching `env` at all — not a separate finding, the same defect.

**Finding B (system-scope config) — reproduced, confirmed real, but at a different privilege tier.** Confirmed this machine has a live, currently-read system-scope config (`git config --system --list --show-origin` → `/opt/homebrew/etc/gitconfig`, owned and writable by the invoking user, not root) and that `env -i PATH=... git config --system --list` **still reads it** — `env -i` clears environment variables, not git's compiled-in system-config file path. Separately (without touching the real system file — that would mutate live host state outside this task's scope) proved via `GIT_CONFIG_SYSTEM=<scratch-file>` that a `core.excludesFile` entry at system scope is honored by `check-ignore` identically to repo-local or global scope (`rc=0`, ignored). Combining the two: anyone with write access to the *actual* system-scope config path — which, on a typical Homebrew-managed macOS dev machine (the exact platform this task was measured on), is the invoking user's own account, not an elevated one — can flip the verdict with zero dependency on any of the four allow-listed names. Unlike Finding A, this requires filesystem write access to a specific path rather than pure environment-variable control, and the spec's Input space already treats one class of "the operator's own configuration" (a legitimate global `core.excludesFile` reached through `HOME`) as an accepted, intentionally-honored source rather than an attack surface — but it names that reasoning only for `HOME`-reached global scope, never for system scope, and the Input space's four-source ignore-rule enumeration ("the repo's `.gitignore`, `.git/info/exclude`, a `core.excludesFile` (repo-local, or global reached through `HOME`...), and a re-include negation") omits system scope entirely. No fixture, AC or lock (unlike `HOME`'s row E / AC21) exercises this scope at all.

**Finding C (`TMPDIR`) — no route found, and I found none either.** No git mechanism consults `TMPDIR` for configuration or ignore-rule resolution to my knowledge, and I could not construct one. Treated as answered, not as an actionable finding.
