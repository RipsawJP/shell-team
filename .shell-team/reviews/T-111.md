Confirmed via the suite and independently: clean → 0; a finding → 1; unresolvable

**One risk note, not a blocking finding**: `bin/check-pii-shapes.sh:407-410`
reads committed content via a bare `git cat-file -p "HEAD:$path" > "$CONTENT_FILE"
2>/dev/null` statement, followed on the next line by `rc=$?; if [ "$rc" -ne 0 ]...
fail_structural ...`. Under `set -euo pipefail`, a plain simple-command
statement (not part of an `if`/`&&`/`||`) that fails triggers `errexit`
*before* `rc=$?` is ever assigned — I confirmed this empirically by patching a
scratch copy so the `cat-file` invocation targets a deliberately-bogus object
name and running it against a real throwaway repo: the script exits with
`rc=128` (git's own raw exit code) and **no stderr message at all** (the
`2>/dev/null` on the same line discards git's own error too), rather than the
intended classified `structural: ...` exit-2 message. This means the `die()`
classification path for a `cat-file` failure is dead code — unreachable given
bash's errexit semantics — so if this branch is ever legitimately hit, the exit
code would not match AC2's `0/1/2` contract (though it would still be
non-zero, so it does not convert a real failure into a false "clean" pass; the
core fail-closed invariant is not violated, only the precision of the
classification). I could not construct any realistic trigger for this
branch within the spec's declared reachable Input space (every path
`git diff --name-status` reports as non-deleted between two fixed commits does
resolve via `HEAD:$path`) — my only reproduction required directly patching
the checker's own source to reference a nonexistent object, which is outside
the declared input space rather than a real trigger. Per the QA verifier's
input-space exemption rule, this does not by itself justify a FAIL, but it is
worth the reviewer's attention as a fragility: if this branch is ever
naturally reachable, the exit-code contract will read the git tool's own exit
code instead of `2`.
