#### Blockers

- **`bin/check-pii-shapes.sh:210`（`RE_NOREPLY_DOMAIN='(^|\.)users\.noreply\.github\.com$'`）** — DP-9 は「ドメインが GitHub noreply ドメインと **EXACTLY**（end-anchored）一致する場合のみ除外する」と明記しているが、実装の `(^|\.)` は「ドット区切りの任意のサブドメインプレフィックス」も無条件に許容してしまう。ローカル部に実名を持つメールボックス形状の文字列が、`users.noreply.github.com` で終わりさえすれば **どんな捏造ドメインでも** 除外され、必須チェックが clean を返す。実機（自分の regex 単体実行、および Codex primary/adversarial の両方の独立実行）で確認済み:
  ```
  fixture:   Contact <login>+<name>@anything-at-all.users.noreply.github.com
  candidate: <login>+<name>@anything-at-all.users.noreply.github.com
  domain:    anything-at-all.users.noreply.github.com
  → RE_NOREPLY_DOMAIN にマッチ → excluded=1（除外・未検出）
  ```
  この構文はGitHubの実際のDNSゾーン外の任意の文字列であり、実在の配送可能なメールボックスである必要はない——チェッカーは形状のみを見る設計なので、これは「実在の人物名を含むメールボックス形状の文字列」（Input space reachable class 5、class 1の実名プロースと組み合わせ）が、必須ゲートを通過してしまう本物の bypass である。AC10 の mutation テストは `RE_NOREPLY_DOMAIN` を丸ごと無効化するのみで、サブドメイン付きの negative fixture は一つも存在しない（AC6 の3つの negative もすべて `users.noreply.github.com` そのもので、プレフィックスなし）——このバグはテストで一度も踏まれていない。

#### Major

- **`bin/check-pii-shapes.sh:407-410`（`git cat-file -p "HEAD:$path" ... ; rc=$?; if [ "$rc" -ne 0 ]; then fail_structural ...`）** — QA round 2 はこの経路を「`set -euo pipefail` 下では `rc=$?` に到達する前に errexit が発火する dead code」と記録し、「spec の Input space 内で現実的なトリガーを構築できなかった」としてブロック要因にしなかった。今回、**現実的で敵対的意図を全く必要としないトリガー**を構築して実機確認した: 通常の `git submodule add` でサブモジュール（gitlink、mode 160000）を変更パスに含めると、`git cat-file -p "HEAD:sub"` は `fatal: Not a valid object name HEAD:sub`（rc=128）で失敗し、`rc=$?` 行に到達する前にスクリプトはそのまま **rc=128 で、診断メッセージなしに** 終了する（`check-pii-shapes: structural: ...` は一切出力されない）。私自身の実機実行（`$TMPDIR` の使い捨てリポジトリで `git submodule add` → `bash check-pii-shapes.sh --base <before>` → `EXIT=128`）と Codex adversarial パスの両方で確認済み。fail-closed の核心（0を返さない）は破られていないため blocker ではないが、AC2 が明記する 0/1/2 の契約には違反しており、サブモジュール追加という通常の git 操作だけで CI が無説明のまま壊れる。Codex はさらに、スーパープロジェクトのオブジェクトDBにサブモジュールの参照コミットがたまたま存在する場合、`cat-file -p` がそのコミットオブジェクトをシリアライズして返し、それがそのまま「ファイル内容」としてスキャンされてしまう副次的な問題も指摘した(未検証だが機構的には筋が通る)。
  - 提案: 変更パスの列挙時に mode 160000（gitlink）を検出して明示的にスキップするか、`git cat-file -p ... || fail_structural ...` の形（同一行での `||` 連結）に直して errexit の影響を受けないようにする。
- **`bin/check-pii-shapes.sh:201-204`（`RE_HOME_PATH_BOUNDARY='(^|[^A-Za-z0-9])'`）と `docs/pii-controls.md:69` / `docs/pii-controls.ja.md:64`** — DP-5 および両言語ドキュメントの正準行は「URL の中に書かれた home-path 形状は報告しない」と明言しているが、実装の境界規則は「英数字以外なら何でも境界として許容する」ため、この主張は複数の現実的なクラスで**成立していない**。実機確認済み（自分の regex 単体実行、および Codex primary/adversarial の両方が独立に同じ結果を得た）:
  - `file:///Users/<name>/secrets.txt`（3スラッシュ形式）→ `/Users` 直前の文字は `/` であり非英数字 → **マッチしてしまう**（`FINDING pattern=home-path`）。
  - Markdown リンク `[local notes](file:///home/<name>/private.txt)` → 同様にマッチ。
  - Codex adversarial が追加で発見: IPv6 URL 権限部 `https://[2001:db8::1]/Users/<name>/secrets.txt` → `/Users` 直前の文字は `]` で非英数字 → マッチ。
  これは DP-5 が意図的に閉じた http(s) 権限部の誤検知（`example.com/home/products` のように直前が英数字になるケース）とは異なる方向の問題——「ドキュメントが約束する非検出」が実際には保証されておらず、通常の技術文書に file:// URL や Markdown リンクや IPv6 リテラルを書いただけで必須チェックが false positive で red になり得る。DP-5 自身が述べる通り「必須ゲートでの false positive は些末な問題ではない——著者が言い換えでしか直せず、それは統制が権威を失う典型的な経路」に該当する。
  - 提案: 境界の非マッチ対象文字クラスに `/` と `]` を加える（あるいは「直前2文字がスラッシュ+スラッシュ」「直前が `]`」等、URL権限部の終端を明示的に判定するロジックに変更）か、ドキュメントの記載を「http(s) の権限部直後のみ非検出、file:// やMarkdownリンク中は検出対象」と正確化する。
- **`docs/pii-controls.md:53-57` と `docs/pii-controls.ja.md:50-54`（"## Running it" の `--all` 説明文）** — 「`--all` を実行すると、`tests/` 配下の意図的なPII形状の敵対的フィクスチャを必ず報告するため、このリポジトリで実行すれば常に何かを検出する」という記述は、DP-8 の `KNOWN_SHAPE_PATHS`（5ファイル除外）と AC16 が要求する「`--all` はこのツリー上で exit 0 clean」という、実際にテストされ出荷されている挙動と正面から矛盾する。QA round 2 は独立に `bin/check-pii-shapes.sh --all → exit 0` を確認済み。この一文は AC20 の正準行（frozen、byte-unchanged）ではなく "## Running it" セクションの自由記述プロースであり、DP-8 導入前（`--all` が本当に常に何か検出していた頃)の記述が更新されずに残ったものと見られる。両言語とも同じ誤りを持つ。
