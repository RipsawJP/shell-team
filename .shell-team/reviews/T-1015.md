#### Blockers

- **`develop` を promote 前に fetch/更新する指示が無い(adversarial パスで新規発見)。** 「Promote `develop` to `main` from a throwaway `release/vX.Y.Z` branch cut from `develop`.」は `develop` から分岐せよと書くのみで、**ローカルの `develop` 参照を最新化(fetch/pull)してから分岐せよとは一度も書いていない**。直前の準備 PR が GitHub 上でマージされた直後、ローカルの `develop` ブランチポインタが自動的には動かない(リモート操作でマージした場合、ローカル clone 側で明示的に fetch/pull しない限り古いコミットを指したまま)。この状態で `release/vX.Y.Z` を分岐すると、マニフェストの version bump・両 README のバッジ・CHANGELOG の新エントリが**全て欠けたまま**のツリーから release ブランチが作られ得る——マニフェストとバッジは分岐元の古い状態のまま**互いに整合している**ため `bash bin/check-readme-version.sh` も CI も検知できず、operator がそのまま v1.2.0 として tag・promote・publish してしまう経路が現実に存在する。**これはまさにこのタスクが直そうとしている #75 のクラス(head branch が削除される)と同じ「git 状態の遷移で踏む古典的な罠」であり、しかも1箇条後の「Tag the merge commit on main with an annotated tag...**`Fetch main first`**...tag that commit rather than a local approximation of it」ではまさにこの同じリスククラス(ローカルの近似値でタグを打つ危険)を明示的に警告・対処しているのに、1つ前の develop 分岐のステップだけ同じ対処が抜けている**という内部的な非対称性がある。CONTRIBUTING.md/CLAUDE.md 全体を grep しても「fetch」を要求する一般規約は他に存在せず、他所でカバーされてもいない(自分で確認済み)。修正: 「Promote develop to main...」の箇条に、develop を fetch/更新してから(あるいは分岐元を準備 PR のマージコミット SHA で明示して)release/vX.Y.Z を切る旨を明記する。B9 が自らの1箇条前で示している用心と対称にする。
