### My own synthesis of Codex's findings

**Finding 1 (rename-source invisibility) — upheld as Major, and this is the load-bearing finding of this round.** My own independent testing above reproduces every claim in Codex's finding 1 exactly, including the specific point that the identical gap exists in the *committed-range* read (`base...HEAD`), which Codex's own tool trace also verified live rather than reasoning about it abstractly. Codex's generalization beyond my own initial framing — that a **disallowed-source-to-allowed-destination** rename is the sharper attack shape (a task quietly moves/deletes a file it was never permitted to touch, and the union reports a clean scope because the source vanishes) — is correct and is the more dangerous of the two directions, since it hides an unauthorized deletion rather than merely under-reporting a benign one. The spec is not unaware of rename-source visibility in general (**A-7** and **AC16(a)** both name the question, and **AC5**'s own prose explicitly notes "the disallowed destination is present either way" as the reason its own specific test is unaffected), but neither **A-7** nor **AC16(a)** as worded requires testing the **reverse** direction specifically — AC16(a)'s six named mutation cases include only "a staged rename" (singular, undifferentiated by direction), and AC5's own live proof only exercises the allowed→disallowed direction. A diligent engineer following AC16(a) literally could reasonably conclude, from AC5's own successful test, that no `--no-renames` change is needed — and never discover the reverse-direction gap, because nothing in the spec's frozen text asks for it. This is squarely a mandate item 1 concern ("is the fixed union complete") and the Goal's own closing claim — "so the union is complete rather than merely wider" — is not fully supported as written; that exact phrase, plus "unbroken chain," ships verbatim into `agents/pm-spec.md` (required literals on **AC1**'s shipped bullet), so this is not merely a spec-review nitpick but prose that will become permanent, adopter-facing authoring guidance overclaiming completeness it does not fully have.

**Finding 2 (config-independence / `core.excludesFile`) — downgraded from Major to Minor, folded into finding 1's ledger row rather than treated as an independent gap.** Two reasons. First, the spec's own `- verification-ceiling:` declaration (line 42) **already, explicitly and by name** discloses exactly this question — "how the widened union behaves under an adopter's own git configuration (`diff.renames`, `core.excludesFile`) in a repository this project cannot read... is deliberately asserted by no criterion at all, and is instead the declared `domain-premise` ground on which the `spec-review` axis elects `cross-provider`" — so "no criterion exercises this" is not an oversight Codex discovered; it is the precise reason this review round exists, and the honest thing to do with it is render the judgment the spec is asking for, not restate the absence as if newly found. Second, having rendered that judgment independently (see testing above): the `diff.renames` axis does **not** introduce additional risk beyond finding 1 — the *default* setting (`diff.renames` unset/true) is the **most restrictive** case (fewest paths reported), and is exactly what AC5 already tests; every other adopter setting (`--no-renames`, `diff.renames=false`) only **adds** visibility, never removes it. So variation in `diff.renames` across adopters does not create a new failure mode — the failure mode already exists at git's own default, which is finding 1, not a second one. The `core.excludesFile` axis is a **pre-existing, unchanged** risk: the untracked read (`git ls-files --others --exclude-standard`) is not touched by this task at all (candidate 2 only adds two new reads; the untracked read is inherited byte-identical from the old norm), and the spec's own Input space explicitly treats gitignored invisibility as an intended design property ("must stay invisible to all four reads so a build artifact or a local cache cannot fail a lock"), not a defect. A misconfigured `core.excludesFile` hiding a governed untracked file is a real but *pre-existing* corpus-wide risk this task neither introduces nor worsens, and fixing it is outside this task's Non-goals (no change to the untracked read). Recorded as Minor: the norm's adopter-facing prose could usefully say a sentence about `core.excludesFile` risk being inherited/unchanged, but this is not a blocking gap this task created.
