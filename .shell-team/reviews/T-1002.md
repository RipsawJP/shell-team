#### Blockers

- **`skills/run/SKILL.md:28`** — the standing "Interventions producer discipline" paragraph never states the entry's actual grammar: it names the seven class tokens but never mentions the `<!-- BEGIN interventions: <id> -->` / `<!-- END interventions: <id> -->` markers or the required indented `date:` / `summary:` / `effect:` fields that `bin/check-interventions.sh` enforces. Worse (adversarial pass), its literal instruction — "append the entry at that moment" — is actively wrong the first time a task transitions from the zero-entry sentinel to a real entry: AC5 rejects the sentinel and an entry coexisting in either order, so blind appending after an existing `no interventions occurred` line trips a `schema` violation. Because the gate at line 60 is explicitly unconditional and forbids auto-retry ("nothing is auto-retried... escalate immediately to the human"), an orchestrator following only this paragraph is very likely to hit a human escalation on the very first real intervention of essentially every future task — the mechanism's core, everyday case, not an edge case. Suggested fix: give the paragraph (or a nearby fenced example) the literal marker + field template, and an explicit branch for "the file currently holds the sentinel: replace it, don't append after it."

- **`skills/goal/SKILL.md:78`** (compare `skills/run/SKILL.md:28`) — the `/goal` completion gate checks `check-interventions.sh` for conformance, but no paragraph in `skills/goal/SKILL.md` mirrors the producer discipline that tells the orchestrator *when* to append an entry (trigger 1 mid-tick, or triggers 3/5 at phase checkpoints). The spec's own "Mirroring symmetry audit" claims the goal loop "has the same seam and the same producer" as `skills/run/SKILL.md` and states as its own premise that "nothing is silently omitted," but only the gate (AC23) was mirrored — the producer discipline (AC19) was not, and no Non-goal names this omission. In practice an autonomous `/goal` tick can satisfy the gate by writing (or leaving) the zero-entry sentinel with no standing instruction ever prompting the orchestrator to notice a real trigger during the tick, silently defeating the mechanism for this operating mode. Suggested fix: mirror an equivalent producer-discipline paragraph (or an explicit cross-reference to `skills/run/SKILL.md:28`) into `skills/goal/SKILL.md`.

#### Major

- **`bin/check-interventions.sh:162-166`** — `--task`'s validation is incomplete in two related ways, both silently defeating DP-4's wrong-file protection (`conformant`, exit 0, no error): (a) an explicitly empty value (`--task ""` or `--task=`) leaves `TASK=""`, and the later `[ -n "$TASK" ]` guard then treats the flag as though it were never given; (b) a repeated `--task` flag lets the last value silently win with no duplicate-detection. Reproduced directly:
  ```
  $ check-interventions.sh --task "" <file-for-T-900>
  check-interventions: conformant: ... (0 entries, 1 sentinel)   # should reject as usage
  $ check-interventions.sh --task T-999 --task T-1002 <T-1002-file>
  check-interventions: conformant: ... (0 entries, 1 sentinel)   # T-999 silently dropped
  ```
  Suggested fix: reject an explicitly empty `--task` value and a repeated `--task` flag as `usage` (exit 2).

- **`bin/check-interventions.sh:218-233`** — the END-marker uniqueness check is structurally asymmetric with the BEGIN check: BEGIN is matched by a generic any-id regex (`BEGIN_ANY_RE`), so a second BEGIN of *any* id is caught, but END only counts lines matching the literal string derived from the already-resolved BEGIN id — an extraneous, well-formed END marker for a *different* id trailing after the true END line is never counted and never flagged. Reproduced:
  ```
  <!-- BEGIN interventions: T-900 -->
  no interventions occurred
  <!-- END interventions: T-900 -->
  <!-- END interventions: T-901 -->
  ```
  reports `conformant`, both with and without `--task T-900`. This is exactly the class of hand-edited/copy-pasted marker corruption the spec's own Input space class 4 declares reachable and in-scope, and it contradicts the checker's own documented "exactly one marker pair" claim underlying AC6. Suggested fix: count all lines matching a generic END-any-id regex, require exactly one, and only then compare its captured id against `begin_id`.

- **`skills/run/SKILL.md:58,60`** (adversarial pass) — the T-073 "no uncommitted implementation diff" guard and the new interventions gate share the same Implement→Validate seam, but nothing in this diff specifies whether/when an orchestrator-authored interventions-file edit (made "at that moment," possibly after the engineer's own commit) must itself be committed relative to the T-073 check. As written, T-073's check is over the whole working tree ("`git status --short` shows nothing to commit"), so an uncommitted interventions append at that exact moment would make the check non-empty for a reason the guard's own prose does not name. (In this task's own commit history the orchestrator handled this correctly — see `1e391e4`, its own atomic commit for a mid-task intervention entry — but nothing in the shipped instructions guarantees a future orchestrator repeats that discipline.) Suggested fix: add one sentence disposing of the interaction (e.g., "commit the interventions-file edit immediately, the same way the engineer commits its own work, before this check").

- **`skills/goal/SKILL.md:78`** (adversarial pass) — the phrase "you resolve yourself... before the next tick" implies a record-only interventions fix should not need a fresh implement pass, but the loop's own "Each tick" structure has no branch to skip re-invoking `engineer` (step 1) when the *only* non-green completion-gate layer was the interventions check. A documentation-only fix therefore consumes a full iteration against `loop-guard.sh`'s budget, risking a spurious `STOP:no_progress` / `STOP:max_iterations_reached` for a gap unrelated to the code under test. Suggested fix: describe a same-tick repair-and-recheck path for this layer specifically, or exempt it from the next tick's implement-pass requirement.
