#### Major

- `bin/gen-codex-agents.sh:241-243` — **the control-character refusal omits
  NUL (0x00), so a role-file body containing a NUL byte is silently accepted
  and copied into `developer_instructions`, producing an invalid,
  unparseable TOML file.** Reproduced independently (not accepted from
  Codex's report): appended `a\x00b\n` to a scratch copy of
  `agents/pm-spec.md`, ran `bin/gen-codex-agents.sh` against it — exit 0,
  4/4 files written, the NUL byte present in the emitted
  `shell-team-pm-spec.toml` (confirmed byte search), and
  `python3 -c "import tomllib; tomllib.load(...)"` on that file raises
  `TOMLDecodeError("Found invalid character '\x00' ...")`. The character
  class in the script is `[\x01\x02...\x1f\x7f]` — it starts at `\x01` and
  never includes `\x00`. This is a genuine violation of the spec's own
  Input space class 7 ("A source file containing a control character other
  than tab and newline... Refused rather than silently emitted") and of
  AC3's own text ("the class, not one reported case"), and it lands on
  AC3 — a **never-dropped** component per this spec's Pre-commitment. It is
  not covered by the Non-goals' "hand-crafted adversarial `agents/*.md`"
  carve-out, because that carve-out is about deliberately adversarial
  engineering against the extraction mechanism (a line that is itself
  `developer_instructions = '''`, for instance) — a stray NUL byte from an
  editor/encoding mishap in an otherwise ordinary role file is exactly the
  "lone carriage return"-shaped accidental-corruption class the same
  Input-space item already commits to refusing.
  - Suggested fix: extend the byte-range check to include `\x00`
    (`[\x00\x01...\x1f\x7f]`), and add a fixture for it alongside the
    existing form-feed/carriage-return probes.

#### Minor / nits

- `bin/gen-codex-agents.sh` — the control-byte check is not a UTF-8
  validator; an invalid high-byte sequence (e.g. a lone `0xFF`) round-trips
  into the TOML unrefused, at which point Codex-side TOML parsing would
  fail on the invalid encoding. Judged **out of the frozen Input space** as
  currently scoped — the repository's own stated security invariant treats
  `agents/*.md` as a trusted instruction channel (operator configuration),
  and the Non-goals' "hand-crafted adversarial `agents/*.md`... an attack
  on a trusted instruction channel" carve-out reads naturally onto
  malformed-encoding injection the same way it does onto a
  `developer_instructions = '''` line planted by hand. Recording as a
  fast-follow rather than a Major, since real shipped role files are
  reviewed prose and are not the threat model this task declines to
  defend.
- `bin/gen-codex-agents.sh:190,273-304` — `--roles` is word-split
  (`ROLES_ARR=($ROLES)`) with no validation of individual tokens; an
  adopter's own malformed override (a token containing a glob character, a
  path separator, or a quote) could produce a surprising filename or
  destination. Low severity because `--roles` is supplied by the same
  local operator who already controls `--root`/`--out-dir` on their own
  machine — a self-inflicted risk shape, not a remote/adversarial-input
  one — but worth a token-shape validation as low-cost hardening.
- `bin/gen-codex-agents.sh:301-304` — the final install loop writes each
  role's file with a direct `cat > destination` per role, sequentially,
  rather than staging into a sibling temp dir and swapping in atomically.
  A mid-loop physical I/O failure (disk full after role 2 of 4) would
  leave a partial out-dir with a nonzero exit — a narrow reliability edge,
  self-recovering because `check-codex-agents.sh` already treats a missing
  expected file as a violation on the next run. Not the class AC3's
  no-partial-output text targets (that text is about *validation*
  refusals, which are already fully resolved in pass 1 before any write in
  pass 2), so not scored as a Major, but a reasonable hardening
  fast-follow (build into a scratch dir, `mv` into `--out-dir` only once
  every file is staged).
- `bin/gen-codex-agents.sh:304` / `bin/check-codex-agents.sh:116,128-129` —
  neither script special-cases a destination or comparison target that is
  itself a symlink (a redirect-through-symlink write in the generator; a
  dangling-symlink extra file silently skipped by the checker's `[ -e ]`
  glob-guard). Judged **out of the frozen Input space**: the spec's own
  Out-of-scope list already declines "An out-dir path that is a symlink...
  The generator performs no symlink-escape analysis... an adopter naming
  such a path gets whatever the filesystem does" — the same reasoning
  reads naturally onto an individual file inside an otherwise-ordinary
  out-dir. Recording as a fast-follow for anyone who later wants tighter
  guarantees, not a defect against this spec.
- `bin/gen-codex-agents.sh:218-226` — a role file with a missing or
  malformed `tools:` field silently derives `sandbox_mode = "read-only"`
  rather than refusing. This is the *safe* direction (fails toward the more
  restrictive declarative value, and the value is declarative-only per
  `D3-sandbox`/AC4's own "not an enforcement boundary" comment), and none
  of the four shipped role files are missing this field — not scored as a
  defect, noted for completeness.
- `docs/adopting.md`/`.ja.md` — a Codex adversarial-pass claim that the
  "no flags at all" parenthetical in step 1 instructs running a bare
  `gen-codex-agents.sh` (relying on `PATH`, which the same section already
  says is false) does **not hold up on a direct re-read**: the parenthetical
  describes the flag *defaults* ("`gen-codex-agents.sh`'s own `--root`
  default is its own plugin root...") rather than presenting a copy-paste
  command that drops the `bash "<plugin root>/..."` prefix shown just
  above it. Verified by reading `docs/adopting.md` lines 375-408 directly;
  rejected as a finding (see the ledger below).
- `docs/adopting.md`/`.ja.md` — step 5's checker example
  (`bash "<plugin root>/bin/check-codex-agents.sh"`) omits `--out-dir` and
  does not restate that it must be run from the adopted repository's own
  root (the checker's own default is `$PWD/.codex/agents`, mirroring the
  generator's default, so an unstated cwd assumption carries over from
  step 1's context but is not repeated). A clarity nit, not a functional
  gap.
- `docs/adopting.md`/`.ja.md` — the regeneration triggers named (a role
  edit, a plugin upgrade) do not mention a `binding.conf`/`TEAM_RUN_BASE`
  change, even though the generator's `model`/`model_reasoning_effort`
  emission depends on the resolved binding. Mechanically harmless —
  `check-codex-agents.sh` already detects this as ordinary drift on its
  next run, since it always regenerates fresh against the current binding
  before comparing — so this is a completeness nit in the trigger list,
  not a gap in the mechanism.
- `docs/adopting.md`/`.ja.md` — the "Honest limits" paragraph states the
  `sandbox_mode` non-enforcement disclosure but does not separately spell
  out that the shipped default binding likewise emits no `model`/
  `model_reasoning_effort` key, so a generated agent inherits the parent
  Codex session's own model rather than any Claude-family pin named
  elsewhere in the document. True and already stated in the generator's
  own header comment and in AC4/D3-model; a documentation clarity
  fast-follow, not a defect.
