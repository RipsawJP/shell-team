#### Blockers

- `bin/resolve-executor.sh:286-291` — **a non-regular occupant at `<base>/binding.conf` (a dangling symlink or a directory) silently falls through to the plugin-shipped default instead of refusing.** `[ -f "$HOST_CONFIG" ]` is false for both a dangling symlink and a directory at that exact path, so `CONFIG_PATH` silently becomes `templates/binding-default.conf` and the resolver succeeds against it. Reproduced live in this round with both occupant types: `ln -sfn /nonexistent .ops/binding.conf` and `mkdir .ops/binding.conf`, each followed by `--print-resolved`, both resolve at exit `0` against the plugin default with no diagnostic at all. Contrast: an *unreadable regular file* at the same path (`chmod 000`) correctly refuses `binding-unresolved` — the gap is specifically the type check, not readability. This is a live, present-day violation of never-dropped item 1's own words ("an unresolvable binding... produces a refusal... never a substituted default") — the host clearly authored *something* at that path, and treating "something broken" identically to "nothing at all" is exactly a silent default substitution for what should be a refusal. It requires no adversarial trickery — a botched deployment script, an orphaned symlink from a prior config-management step, or a stray `mkdir -p` typo are all ordinary accidents squarely inside DP13's own threat model. Confirmed independently by Codex's primary pass (`P2`) and adversarial pass (`high`) — this reviewer escalates both to Blocker on the strength of the live reproduction and the direct clash with the never-dropped item's literal wording (see ledger). Suggested fix: check `[ -e "$HOST_CONFIG" ]` first; if it exists and is not a readable regular file, refuse `binding-unresolved` before falling to the default.

- `bin/resolve-executor.sh:387-394,429` (`carries_board_transition_channel`) — **a malformed or unrecognized board-transition channel value is treated as "carrying" (safe) rather than refused, silently bypassing the authority rule.** The reader validates the value only against the loose shape `^[a-z][a-z0-9-]*$` — any lowercase-token-shaped string satisfies it — and the authority join at L429 only branches on exact equality to the literal `not-carried`; every other value, including a plain typo, is implicitly treated as "board-transition is carried" and a `writes`/`proposes` role resolves successfully. Reproduced live in this round: mutating the shipped `claude-cli.txt`'s `carries board-transition stdout` to the one-character typo `carries board-transition not-caried` and resolving `engineer` (role-board-authority `writes`) against it succeeds at exit `0` rather than refusing `contract-violation` or `binding-unresolved`. `templates/task-envelope.txt` already declares a **closed** channel vocabulary (`argv`, `prompt`, `stdin`, `stdout`, `stderr`, `file`, `exit-status`, `not-carried`, plus the retired `board`) inside the very `CONTRACT_OUT` text this resolver already holds in memory — the fix needs no new sibling call, only validating membership against that already-fetched set instead of a bare shape regex. This is a second, independent, live-reproduced violation of never-dropped item 1: an accident (a one-character typo in a shipped or host-edited adapter definition) silently defeats the exact rule DP4 exists to enforce, on a writes-authority role, with the ambiguity resolved in the *wrong* direction (unrecognized treated as safe rather than refused). This is Codex's adversarial pass's own fourth-class finding (tagged `high`), which this reviewer independently reproduced and escalates to Blocker on the same grounds as the previous item (see ledger).

#### Major

- `bin/resolve-executor.sh:359-398` (`role_board_authority_for`, `capability_effort_for`, `carries_board_transition_channel`, `effort_value_declared`) — **the delegated contract's `role-board-authority` rows and a bound adapter's own `capability effort` / `carries board-transition` / `effort-value` rows are re-asserted for value membership but never for field count**, so a row with an extra trailing field (`role-board-authority engineer writes extra-field-here`, `capability effort supported extra-token`) is silently accepted rather than refused as malformed. Reproduced live against both surfaces this round: a stub `check-adapter.sh` emitting the mutated authority row, and a direct mutation of the shipped `claude-cli.txt`'s `capability effort` line — both resolve successfully. DP2 states explicitly that "the same discipline [re-asserting the delegated form before trusting it] applies to `bin/check-adapter.sh --print-contract`, whose `role-board-authority` rows DP4 consumes" — the BINDING's canonical form gets exactly this discipline (AC8's eight-shape stub-sibling suite), but the CONTRACT's rows and the adapter definition's own two fields do not get an equivalent test or an equivalent field-count check, which is an asymmetry in both the implementation and the frozen AC coverage (no AC and no fixture stubs `check-adapter.sh` the way AC8 stubs `check-binding.sh`). Confirmed by Codex's primary pass (`P2`) and adversarial pass (`medium`, disagreeing on magnitude — see ledger). Practical exploitability today is narrow (requires a regressed/mismatched sibling or a host hand-editing a shipped definition, both accidents per DP13's threat model, and the extra field does not change the *value* actually read) but the gap is real and the fix is cheap (require exact field counts in each of the four narrow readers). Suggested fix: add an explicit `NF==3` (or `NF==2` for `effort-value`) check inside each predicate, refusing `binding-unresolved` on mismatch.

- `templates/prompt-blocks/executor-resolution.md:1` + DP6 (`.shell-team/specs/T-1057-loop-integration.md`) — **the canonical block's unqualified telemetry claim ("the resolved binding is the source of record for every bound role's model") can record a model or provider that never actually ran, and nothing detects the divergence.** This is not a re-litigation of the Non-goal that no invocation mechanism changes (that boundary is explicit, deliberate, and correctly disclosed, and this reviewer does not fault it) — it is a narrower finding about the telemetry instruction's own honesty relative to what is actually enforced. Two convergent facets: **(a)** DP6 Branch B's "two-directional equality lock between each pin and the shipped default's model token... neither side can move alone" is, in the mechanism actually shipped, only `AC5`'s own one-time frozen spec assertion — no CI-wired suite (confirmed: `tests/resolve-executor/run.sh` contains no comparison of `agents/*.md` against `templates/binding-default.conf` at all) continuously re-verifies this equality after merge, which is this repository's own established convention for merged-spec criteria going stale (e.g. AC16's own "merge-point-scoped and expected to go stale after merge") — so the rhetorical strength of "lock"/"neither side can move alone" overclaims relative to the mechanism's actual, one-time-only enforcement. **(b)** Independently of any future drift, `## Input space` explicitly lists "any legal permutation of the two shipped adapters across the six roles — including `codex-reviewer` bound to `claude`/`claude-cli`" as a reachable input this task's deliverables must handle correctly *today*; for such a binding, the resolver happily resolves and the loop's telemetry would report the bound provider/model, while the role's actual invocation mechanism (the Agent tool + its unconditional frontmatter pin, or `codex-reviewer`'s hardcoded `codex exec` shell-out) is completely unaffected — so telemetry can misreport from the very first use of the feature the Problem statement's own first gap names ("a host can author a binding today and no run behaves differently, so the config is a document rather than a control"), for the provider/model axis specifically. Confirmed independently by this reviewer's own analysis and by Codex's primary pass (`P1`) and adversarial pass (`high`) — this reviewer downgrades primary's `P1`/blocker mapping to Major (see ledger): the shipped default has zero divergence today (verified), and the harm is telemetry inaccuracy rather than an unauthorized invocation or a failure to refuse. Suggested fix (not required to be resolved this round, but recommended): either add a small CI-wired equality check between the live `agents/*.md` pins and `templates/binding-default.conf` (cheap, no intent-block edit needed since it lives in the suite), or soften the prompt block's / DP6's language to state plainly that the telemetry claim holds only when the bound provider/model matches what the role's own invocation mechanism actually applies.
