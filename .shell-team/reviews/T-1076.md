#### Blockers
- `bin/log-run.sh:519-561` (the `LOCK_ACQUIRED` guard flag around the mkdir-acquire and `rmdir`-release paths) — Two independent, narrow-but-real Bash trap-timing races on the single `LOCK_ACQUIRED` flag that guards `release_lock()`:
  (a) **acquire-side** — Bash defers a trapped INT/TERM signal received while waiting on the external `mkdir` until that command returns; if the signal lands after `mkdir` succeeds (loop exits, D2's bounded wait ends) but before the very next statement `LOCK_ACQUIRED=1` executes, `on_lock_signal` fires with the flag still `0`, so `release_lock()` skips its `rmdir` and the lock directory is orphaned permanently — an ordinary INT/TERM can now produce the same stale-lock outcome the spec's own D3 discloses as a **SIGKILL-only** residual case, not a signal the writer is supposed to handle cleanly.
  (b) **release-side, worse** — inside `release_lock()` itself, if a signal lands after `rmdir "$LOCK_DIR"` succeeds but before the following `LOCK_ACQUIRED=0` reset, a re-entrant `on_lock_signal` call sees the flag still `1` and calls `rmdir` again — on whatever now occupies that path, which by then can be a **different process's freshly-created lock directory** (a successor that acquired the instant this process's own lock was freed). That is a direct violation of D3's "never steal" invariant: this writer would delete another live writer's lock out from under it, defeating the exact interleaved-append failure this whole task exists to prevent.
  The adversarial pass reproduced both stale-flag states with deterministic trap probes rather than reasoning about them abstractly; `tests/log-run/run.sh`'s own `lock-released-on-signal` fixture (`:424-455`) injects its `sleep 5` delay *after* `LOCK_ACQUIRED=1` is already set, so it structurally cannot exercise either window.
  - Suggested fix (Codex's, which I find sound): make the acquire/release-ownership transition itself signal-safe — an explicit acquiring/held/releasing state machine, or defer INT/TERM delivery across the single `mkdir`-then-flag and `rmdir`-then-flag transitions and re-deliver any pending signal once the flag is consistent. Add a probe that signals from the acquire and release commands themselves before they return, including a waiting successor during the release-side probe.

#### Major
- `bin/log-run.sh:400-417` (`compute_auto_seq`) — The per-`run_id` scan matches the file's **jesc-escaped** stored `run_id` text against the caller's **raw, unescaped** `$RUN_ID`. A `run_id` containing a backslash or double-quote is captured doubled/truncated by the boundary-anchored regex and can never equal the raw comparison value, so `--seq auto` silently restarts at `1` for that run instead of continuing the count — the exact "no duplicate, no gap" guarantee D4/AC2 exist to provide, defeated silently rather than refused loudly. `--run-id` carries no character-class validation anywhere in the script (only non-empty), unlike `--instance`/`--provider`/`--adapter`/`--effort`, which all reuse `BINDING_TOKEN_RE`. Confirmed not reachable through any *current* in-repo caller (`bin/close-out.sh` uses a generated safe id + explicit `--seq 1`; `skills/run/SKILL.md` recommends timestamp-style ids and still uses explicit numeric `seq`), but reachable by a direct adopter invocation or a future `--seq auto` caller the moment one exists, and nothing in the Input space's "Out-of-scope synthetic extremes" names this as declined — it isn't a declared boundary, it's an unnoticed gap.
  - Suggested fix: compare against the escaped form (re-derive it with `jesc` before comparing), or decode the captured value before comparing, rather than comparing raw-vs-escaped.
- `tests/log-run/run.sh:356-377` (`run_contention_writer`) — The bare `wait` at the end of the helper discards each background writer's individual exit status; a writer that fails outright (argv/process-launch/filesystem failure — plausible given the negative control's own 16 KiB `--error` payload) would still let the helper return cleanly, and a resulting short line count would then be classified as **the mutant's** detection rather than as a broken fixture. This doesn't put this task's own recorded outcome in doubt — the `seq-set-mismatch` the engineer, QA and the adversarial pass all independently reproduced is a genuine TOCTOU signature, not a line-count artifact — but AC10's own "measurably fail, judged honestly" contract is weaker than it should be for future runs of this suite.
  - Suggested fix: track each background writer's PID and require every exit status to be zero before classifying the run; treat any non-zero as a fixture failure distinct from `detected`/`not-detected`.

#### Blockers
- `tests/log-run/run.sh:752-757` (`relrace_choreograph`, the new `signal-race-release-side` regression added this round to pin round 1's Blocker fix) — `kill -TERM "$p1_pid"` fires the instant P1's post-`rmdir` marker is observed, **without first confirming P2 has actually reacquired the just-freed lock path**. The subsequent "give the successor a moment" wait (line 756) runs only *after* the kill, so it cannot retroactively fix the ordering. Traced by hand and independently confirmed by the adversarial pass: whether the OLD-shape mutant's reentrant `rmdir` actually steals a *live* P2 lock (the assertion at line 775 requires `survives=0`) depends on whether P2's own 1-second poll cadence happens to have already grabbed the path in the window between P1's `rmdir` and the test's kill — a window whose width is itself governed by the test's own 1-second marker-poll granularity. Both timing sources are on the same ~1-second scale with no synchronization between them, so this is not a rare corner case: it is close to a coin flip on every invocation. When P2 has *not* yet reacquired, P1's second `rmdir` finds nothing to steal, P2 subsequently acquires the now-genuinely-free path undisturbed, and the test's own theft assertion fails — a `FAIL:` line in a CI-wired suite (T-1076 spec's own Summarized sources item confirms `tests/log-run/run.sh` is already a wired CI step) produced by scheduling alone, on code that is behaving exactly as intended. This is precisely the kind of harness soundness gap round 1's Major #2 was about, but for the fixture that is supposed to demonstrate round 1's Blocker fix itself, and its failure mode is a spurious red on an otherwise-correct implementation rather than a missed real regression — no less disruptive to a repo whose whole discipline is fail-closed, measured checks.
  - Suggested fix (Codex's, which I agree is the right shape): have P2 write its own explicit "I hold the lock now" marker (or poll `$lockdir`'s presence with a barrier the test waits on) *before* `kill -TERM` is sent to P1, so the choreography stops depending on two independent, unsynchronized 1-second poll cadences landing in the right relative order.

#### Major
- `tests/log-run/run.sh:843-858` (AC10's negative-control token derivation, re-examined this round) — the lock-disabled mutant arm has no explicit barrier forcing two of its 8 concurrent writers through the scan-then-append window at the same instant; the race that produces `detected` is scheduling-dependent rather than structurally guaranteed. **AC10**'s own check line re-runs `tests/log-run/run.sh` live and requires the freshly-measured token to equal the token already committed in `.shell-team/provenance/T-1076.md` (`detected`) — so a future re-run of this exact suite, on this exact code, that happens not to hit the race would fail **AC10** outright, not because anything regressed but because a nondeterministic fixture disagreed with a static record of one earlier outcome. In practice I judge this **low-probability**, not urgent: 8 processes doing 20 rounds each of an unsynchronized read-scan-then-append cycle against one shared file, with zero serialization (the mutant is `if true; then` — no lock attempt at all), makes at least one collision across 160 total appends close to certain on a real multi-core host, and the provenance record already reports it was observed on two independent runs. The frozen spec's own D6/AC10 text explicitly anticipates and provides a disposition for the opposite failure mode (a permanent `not-detected`, escalated via a `- limit:` line) — it does not anticipate flakiness in the other direction (an intermittent `not-detected` after `detected` was already recorded), which is the gap Codex is naming. Worth closing in the same pass as the Blocker above since both are in the same file and the same general area, but not, on its own, forcing this verdict.
  - Suggested fix: add an explicit synchronization barrier (e.g., all N writers block on a shared marker/FIFO until every one has performed its own scan, then release them to append together) so the race is structurally forced rather than probabilistically likely; or, short of that, note the residual nondeterminism explicitly in the provenance record's own text.

#### Minor / nits
- `bin/log-run.sh:526-528` (`lock_mtime`) — on GNU/Linux, `stat -f '%Sm' "$d"` does not fail as the header comment assumes: GNU `stat` parses `%S` as one directive (filesystem block size, valid in `-f` mode) and treats the trailing `m` as a literal character, so the command **succeeds** with a nonsensical value (e.g. `4096m`) instead of falling through to the correct GNU-form `stat -c '%y'` line below it. This is real (I traced GNU `stat -f`'s own format-string grammar to confirm it) and would make the refusal message's "existing lock mtime" field garbled on the project's own CI host (Linux), rather than a real timestamp or the honest `unknown` fallback. I am downgrading this from Codex's own P2/major rating (see ledger): it is a best-effort diagnostic field only, no acceptance criterion inspects its content (**AC5**'s stderr assertion checks only for the lock path string), it carries no security or correctness consequence, and the remedy the message exists to convey (the lock path plus the `rmdir` command) is printed correctly regardless. Worth a one-line fix (capture the BSD probe's own exit status and only use its output on success) but not blocking.
  - Suggested fix: `local m; m="$(stat -f '%Sm' "$d" 2>/dev/null)" && { printf '%s' "$m"; return 0; }; stat -c '%y' "$d" 2>/dev/null && return 0; printf 'unknown'` (or equivalent) — capture-then-check rather than relying on `stat`'s own exit status to discriminate the two format dialects.
- `bin/log-run.sh:400-417` (`compute_auto_seq`'s widened extraction regex, re-examined this round) — the adversarial pass and I independently traced `jesc`'s own two-step transform (backslash-double, then quote-escape) against `(\\.|[^"\\])*` and found no defect: every stored escape shape `jesc` can actually emit (doubled backslashes, escaped quotes, any run of consecutive backslashes) is consumed correctly, and a malformed odd-length trailing-backslash JSON string is not a shape `jesc` can produce. This closes round 1's Major #1 cleanly. The one open item is coverage, not correctness: the new `seq-auto-escaping` regression covers `a\b`, `a"b`, `a\"b`, `a\\b` but not a run_id ending in two or three consecutive raw backslashes — worth pinning as a fast-follow, not a defect.
- `bin/log-run.sh:567-603` (the `trap '' INT TERM` masking, adversarial angle) — the mask is correct for the intended (local POSIX filesystem) case: `mkdir`/`rmdir` are each inside an `if`/guarded context with no early-exit path that could strand the mask, and clearing `LOCK_ACQUIRED` before `rmdir` creates no new window (a successor cannot see the path as free until `rmdir` itself completes, by which point the flag is already correctly cleared). The adversarial pass's one caveat — an external `mkdir`/`rmdir` that blocks indefinitely on an unhealthy NFS/FUSE mount would inherit `SIG_IGN` and become uninterruptible for that duration — is real but squarely inside the frozen spec's own declared boundary: `## Input space`'s first "Out-of-scope synthetic extremes" line names exactly this ("Cross-host or network-filesystem concurrency... Declined outright; the lock's correctness is claimed for a POSIX local filesystem only"), so I record it here for completeness rather than as a scored finding.
