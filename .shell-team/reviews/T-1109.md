#### Major

- **`bin/check-entry-mode.sh:387-403` — the coverage check is one-directional: dispatch-axes ⊆ reflection-axes is enforced, but reflection-axes ⊆ dispatch-axes never is.** A `- dispatch-reflection:` row naming an axis the entry's own `- dispatch:` rows never recorded slips through, and duty B's own comparison computes a trivially-satisfiable verdict for it (`own_value` is empty since the axis was never recorded, so `differs` is always the "expected" verdict against any non-empty predecessor value). Reproduced directly: an entry recording only `dispatch: specify` plus a spurious `dispatch-reflection: verify — T-900 — differs — ground` (T-900 genuinely records `verify`) exits **0**.
  - Suggested fix: require axis-set equality in both directions between `ENTRY_DISPATCH_AXES` and `REFL_AXES`, not only entry-axes-covered.

- **`bin/check-entry-mode.sh:324-347, 405-429` — nothing enforces that all reflection rows on one entry name the same predecessor id, and nothing rejects the current task naming itself.** `resolve_predecessor_entry()` is invoked independently per row with no cross-row consistency check and no `r_pred != TASK` guard. Reproduced directly: (a) a self-referencing row (`dispatch-reflection: specify — T-901 — repeat — ground` on entry T-901 itself) exits **0** — trivially "passes" duty B since an entry's own value always equals itself, without ever reading a real predecessor; (b) an entry naming two different, unrelated existing tasks for two different axes exits **0**, contradicting the Goal's own "the immediately preceding task" (singular) framing and the Non-goals' "one hop" premise.
  - Suggested fix: collect every row's `r_pred` first; require exactly one distinct value across the whole family (or explicit design sign-off that per-axis predecessors are intentionally allowed, which the current prose does not state); reject `r_pred == TASK`.

- **`bin/check-entry-mode.sh:309-310` (`dispatch_value_for_axis`) — silent first-match (`head -1`) on duplicate/conflicting `- dispatch:` rows for the same axis, on both the predecessor's entry and the current entry.** Reproduced directly: (a) a predecessor still in `## Active` (an explicitly reachable Input-space case) carrying two conflicting `- dispatch: verify` rows resolves via its first row, silently masking the inconsistency; (b) the **current** entry carrying two conflicting `- dispatch: verify` rows likewise resolves via the first, and a reflection row matching only that first value exits **0** even though the entry's own record is internally contradictory.
  - Suggested fix: require exactly one matching row per axis before extracting a value; refuse (fail-closed) on more than one.

- **`bin/check-entry-mode.sh:297-298` (`refl_stem_re`) — the T-1096 "invisible-variant" defense this task's own Notes-for-engineer claims to have closed for this family is incomplete: it only widens the spacing between the bullet dash and the field name, not between the field name and the colon.** Reproduced directly: `- dispatch-reflection : specify — T-900 — repeat — ground` (a space before the colon) matches neither `refl_stem_re` nor `refl_full_re`, so the whole line is invisible to the family scan and the entry — which does carry a (malformed) reflection line — passes under the validate-if-present empty-family path, exit **0**. This is the identical defeat class **AC8**'s own doubled-space case is written to close (an implementation whose stem net misses a variant sees an empty family and passes) — just at a different spacing position the stem net does not cover.
  - Suggested fix: widen `refl_stem_re` to tolerate whitespace on both sides of the colon too (or drop the colon requirement from the stem and re-anchor after collection), matching the discipline already applied to the dash-to-fieldname gap.

#### Minor / nits

- **`bin/check-entry-mode.sh:306` (`ENTRY_DISPATCH_LINES`) — a malformed (e.g. doubled-space) `- dispatch:` row on the CURRENT entry is silently invisible to the axis set used for reflection coverage, letting that axis escape the "no cherry-picking" requirement entirely.** Reproduced directly: a malformed `verify` dispatch row plus only a `specify` reflection row exits **0** (no complaint that `verify` is uncovered). Related to, and compounds, the coverage-asymmetry Major above. Downgraded to Minor because it inherits an equivalent, pre-existing weakness in `bin/close-out.sh`'s own `'^[[:space:]]*- dispatch:'` anchor (also single-space-only, also silently blind to this exact variant) — not a novel class T-1109 introduces on its own, and `close-out.sh`'s own gate would already miss the same malformed row at actual close time.
  - Suggested fix: apply this task's own wide-stem-collect/strict-parse-refuse discipline (already used for `refl_stem_re`/`refl_full_re`) to `ENTRY_DISPATCH_LINES` too, now that a fail-closed judgment depends on reading it correctly.

- **`bin/check-entry-mode.sh:313` — `resolve_predecessor_entry()` verifies only that the named id resolves to exactly one top-level entry somewhere on the board, never that it is the *immediately preceding* task.** An arbitrary existing (or even a much older, already-merged) task id passes duty B's resolution step as readily as the true predecessor. This is the same root cause as the self-reference/cross-row Major above (nothing establishes *which* task is the true predecessor) rather than an independent gap, so it is not double-counted in severity — noted here because the spec's own Non-goals explicitly decline to add a machine-readable predecessor-relationship key, which is the only structural fix that would let the checker verify adjacency rather than mere existence; absent that, the prose's "immediately preceding" framing is aspirational rather than enforced.

- **`skills/run/SKILL.md:45-46` — the pre-existing "Board transcription order" bullet's own invocation trigger ("run `check-entry-mode.sh` … right after those sub-bullets land") was not updated to reference the newly-added reflection sub-bullets, even though the new "Cross-task dispatch reflection" bullet asserts "the same invocation … already covers this family too."** As written, correctness depends on the coordinating session reading the whole numbered step before acting (so that reflection, prescribed to land *before* dispatch rows by the later bullet's own prose, actually lands before the check-triggering event described by the earlier bullet) rather than executing bullet-by-bullet in document order.   - Suggested fix: reword the "Board transcription order" bullet's own invocation trigger to explicitly include the dispatch-reflection sub-bullets (forward-referencing the next bullet is unusual but resolves the ambiguity directly), or restructure so the reflection bullet's prose is self-contained about when the check runs rather than relying on the earlier bullet's unchanged wording.
