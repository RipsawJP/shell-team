#### Blockers

- **`bin/check-binding.sh:122-143,217-222` — the adapter-registry trust boundary (DP6, a "never dropped" property per this spec's own pre-commitment section) is defeated by an ordinary ancestor-directory symlink, reproduced directly, not merely theorized.**
  The existing symlink-chasing loop (lines 122-136, ported verbatim from `bin/check-durability.sh`) only follows a symlink on the *final* path component (`BASH_SOURCE[0]` itself); `SCRIPT_DIR` (line 139) and `TEMPLATES_ROOT` (line 217) are then derived with plain `pwd` (logical), never `pwd -P`/`cd -P`, and no code checks whether any *ancestor* directory in the resolved path is itself a symlink. The script's own header comment shows the authors anticipated symlink-based exposure ("a plugin install may expose bin/ scripts on PATH via a symlink") — but only handled the file-level case, not the directory-level one.

  I reproduced this end to end: created `plugin/bin/{check-binding.sh,team-paths.sh}` + `plugin/templates/binding-adapters.txt` (the real, shipped two-row registry), then `adopter/bin -> plugin/bin` (a directory-level symlink — the shape a monorepo or vendored-tooling layout produces without any adversarial intent) plus a decoy `adopter/templates/binding-adapters.txt` (`my-cli claude`, one row). Running `(cd adopter && TEAM_RUN_BASE=.shell-team bash bin/check-binding.sh)` against a config binding **all six roles** to the decoy-only adapter `my-cli` returned `check-binding: valid: schema 1, 6 role(s) bound`, **exit 0** — the decoy was consulted and legitimized an adapter token the real, plugin-shipped registry does not contain. This directly contradicts DP6's stated guarantee ("A checked-out repository cannot register an adapter... the registry never resolves from the adopter's tree") and the identical claim on the board and in `templates/binding-adapters.txt`'s own header comment.
  I verified the minimal fix closes this exact reproduction: patching line 139 to `SCRIPT_DIR="$(cd -P "$script_dir_raw" && pwd -P)"` (and the equivalent for `TEMPLATES_ROOT` at line 217) makes the same scenario correctly refuse `unknown-adapter`, exit 1.
  This is squarely in-scope under this repo's own stated threat model (DP10: "the threat model is accidents") — a directory-level symlink requires no hostile action, and the code's own comments show it was an anticipated deployment shape, just incompletely defended. It is not excluded by any listed `## Input space` "Out-of-scope synthetic extreme," and even if it were borderline, this is a trust-boundary finding, which this review's own governing rule never downgrades on input-space grounds.
  **Caveat surfaced by the adversarial pass, folded into this same blocker rather than scored separately**: `cd -P`/`pwd -P` closes the symlink-chain variant I reproduced, but does not by itself close every possible aliasing mechanism (hardlinks, bind mounts, overlay/mount-namespace aliases of the script or the registry file) — those require deliberate low-level filesystem construction closer to DP10's excluded "hostile operator" category, and I did not reproduce any of them. The fix should close the reproduced case and add a regression for it; whether a fully hostile-proof registry-identity mechanism is warranted is a separate, larger design question I am not scoring as blocking here.
  **Required before merge**: fix the resolution to use physical canonicalization (`cd -P`/`pwd -P`) for `SCRIPT_DIR` and `TEMPLATES_ROOT`, and add a regression case to `tests/check-binding/run.sh` covering the ancestor-directory-symlink shape (the existing `cb-decoy-registry-ignored*` cases only vary invocation cwd through the *real* absolute script path — they never exercise a symlinked `bin/`, so they could not have caught this).

#### Minor / nits

- **`bin/check-binding.sh:409-447` (`read_lock`) — the lock's embedded canonical body (the `schema`/`bound` rows dumped between `binding-hash` and `binding-lock-end`) is never parsed or cross-checked against the recorded `binding-hash`; only the header/terminator/field-count structure is validated.** I reproduced this: a lock whose embedded body I replaced with a single garbage line (keeping the header, the correct `binding-hash`, and the terminator intact) still verified successfully (`check-binding: verified`, exit 0) against the unchanged config, because `--verify`'s actual pass/fail decision is driven entirely by re-deriving the hash from the *config* and comparing it to the lock's `binding-hash` line — the embedded dump plays no role in that decision. Codex's primary pass scored this `major` and framed it as "malformed input reaching exit 0"; I disagree with that framing and downgrade it (see ledger): the security-relevant property (has the binding changed since the lock was taken) stays sound regardless, since the embedded dump is never trusted for it. This is a self-description/audit-integrity gap (a human or a future consumer reading the lock's embedded body could be shown something inconsistent with the hash it certifies), and AC10's own text explicitly disclaims completeness over "every possible malformation," scoping itself to three measured shapes. Worth strengthening before a future consumer starts reading the embedded body directly, but not before this PR merges.
- **`bin/check-binding.sh:184` (`--help` short-circuit) and `bin/check-binding.sh:473-481` (`--config ""`)** — `bash bin/check-binding.sh --help --some-unknown-flag` exits 0 (help wins before the rest of argument parsing runs), and `--config ""` (an explicit empty value) is treated identically to "no `--config` given" and silently falls back to the resolver-derived default rather than refusing. Neither is a security or fail-closed-completeness issue (both are standard CLI-ergonomics territory, and the empty-`--config` fallback still validates whatever it resolves to), but both are minor argument-parsing edge cases worth tightening.
- **`bin/check-durability.sh:124-145,190-198`** carries the byte-identical `SCRIPT_DIR`/logical-`pwd` bootstrap this task's own provenance record says it ported from — confirmed by direct `grep` (the same `readlink`/`dirname`/`cd && pwd` shape) — so the same ancestor-symlink escape almost certainly applies to its own `durability-records.txt` registry resolution too. I did not reproduce it against that script specifically (out of this review's scope), but flag it because it changes the disposition: this is a **pre-existing, shared-pattern defect**, not one T-1054 introduced, and fixing it there is out of this task's own scope-lock (`AC13` forbids editing any other `bin/` file, and Non-goals forbid it explicitly). It needs its own follow-up task.
- **`--adapters PATH` is a testing affordance with no mechanical guard against production forwarding.** Nothing in `bin/check-binding.sh` itself stops a future caller (i.e., T-1056's loop-wiring) from passing this flag in a real invocation, which would let a checked-out repository become its own adapter-registry authority. Not a defect of this task's own shipped surface — T-1054 ships zero consumers of `check-binding.sh` (Non-goals: "no agent, skill, adapter or phase transition reads it") — but worth recording as an explicit constraint for whoever writes T-1056.
