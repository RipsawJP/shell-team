#### Major
- `agents/qa-verifier.md:72` (the new Rule's own wording) — "fill that section in yourself first if it is still empty" does not plainly cover the case where the `## CI parity` heading is **absent from the recipe entirely**, not merely present with unfilled placeholders. Spec Input space class 9 requires the Rule to "still apply" for "an adopter repository scaffolded before this task, whose recipe has no `## CI parity` section" — precisely because `## Non-goals` forbids retroactively updating an already-scaffolded recipe. A literal reading of "still empty" naturally means "the section exists but its placeholders are unfilled," not "the section does not exist yet"; a QA agent that greps for the heading, finds nothing, and concludes the CI-parity duty has no data to act on would silently skip the lint/format/static verification for exactly this real, spec-mandated, non-exempted input class — the opposite of what "never a silent skip" (the same Rule's own clause, two clauses earlier) requires. This is the AC7 text-sufficiency judgment this round's verdict scope assigns, coming back negative for one enumerated Input-space class. Fix: reword to plainly cover both cases, e.g. "if the section is absent or empty, derive the commands from the workflow files yourself and write the section in before running them."
- `agents/engineer.md:18` (the added sentence at the end of Inputs item 5) — goes beyond what the frozen Goal authorized. The Goal's Body directive for this file is narrow: "`agents/engineer.md`'s existing recipe append-back duty **names** the new recipe section" (Body-to-AC row 6: "The engineer's append-back duty names the new recipe section → **AC2**"), and AC2's own check asserts only that three literals coexist on one line — it does not test for an operational duty. The delivered sentence instead adds an unconditional new engineer precondition — "fill it in on first use ... **and run those commands yourself before setting `READY_FOR_QA`**" — that (a) duplicates the independent execution the new qa-verifier Rule already performs, without being reconciled against it (nothing states which side's run is authoritative if they disagree, or what happens if the engineer's run diverges from QA's re-run); and (b) carries none of the qa-verifier Rule's own carve-outs — no exception for a step that cannot be run locally (a deploy, a cloud-credentialled test, a container build), which the QA-side Rule explicitly permits recording rather than executing. Read against `## Non-goals`' "No new gate ... the change lives inside the existing QA gate, the existing recipe file, and one existing summary block" — this sentence puts a new, unscoped precondition on the engineer's own hand-off gate (`READY_FOR_QA`), which is a fourth surface beyond the three the Non-goals name. Fix: either scope this sentence back to naming the section (matching the Goal's own stated intent), or explicitly bound the engineer duty to locally-runnable commands with the same "record what could not run, and why" carve-out the QA Rule carries.
- `templates/test-recipe.md:38` (the `## CI parity` section's three placeholder fields) — the section provides only "Workflow file(s)", "Lint/format commands" and "Pinned versions"; there is no field for a **static-analysis** command, despite the qa-verifier Rule's own scope being explicitly "the lint/format/**static** steps those workflows run" (`agents/qa-verifier.md:72`) and the spec's own Goal sentence naming "lint/format/static steps" as the covered class. A repository whose CI runs a type-checker, a security scanner or any other static-analysis step that is neither a linter nor a formatter has no place in the recipe to record it; because the qa-verifier Rule's stated command source is this same section (see the first Major above), a static step risks going both unrecorded and unverified, silently narrowing the delivered coverage below what the Rule text and the Goal both promise. Fix: add a fourth field (e.g. "Static-analysis commands") or broaden the existing "Lint/format commands" field's label and comment to explicitly cover all three categories the Rule names.

On a freshly scaffolded repository, a future task appending its own environment procedure by writing at true end-of-file would land its content under `## CI parity` instead of under the append-only log it is meant to extend.
