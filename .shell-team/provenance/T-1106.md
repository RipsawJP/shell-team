- decision: the lock's embedded body is located by tracking the exact array index of the single matched `config-path` line and the single matched `binding-hash` line during the same pass that counts `cp_count`/`bh_count`, then excluding those two indices (plus index 0 and index n-1) from the body — rather than re-scanning the candidate body lines a second time and excluding any line that merely matches the `config-path `/`binding-hash ` patterns.
  reason: both approaches satisfy every fixture this spec's own check lines exercise (including the reordered-header case), but they diverge on an input the spec explicitly does not test: a body line that happens to collide with one of the header-field patterns (e.g. a body row starting with the literal token `config-path`). A content-re-match exclusion would silently drop such a colliding body line from the hash input even though `cp_count`/`bh_count` already fixed which single line is the real header field; an index-based exclusion cannot make that mistake, because it acts on the specific line the earlier pass already identified, not on every line sharing its shape. This is a correctness property of the checker's own refusal behaviour (does a hostile-looking but otherwise well-formed body get silently truncated before hashing), so it is observable and worth recording even though no shipped fixture currently probes it.
  grounding: `bin/check-binding.sh`'s `read_lock()` function, the "embedded-body cross-check (T-1106, issue #219)" comment block — the `cp_index`/`bh_index` variables set in the same loop that increments `cp_count`/`bh_count`, then read by the body-reconstruction `for ((i = 0; i < n; i++))` loop; `.shell-team/specs/T-1106-check-binding-consistency.md` Goal sentence ("defined by exclusion as the lock's lines minus the first line, minus the located config-path line, minus the located binding-hash line and minus the terminator") — the spec fixes that the exclusion must happen but not how the located line is identified at reconstruction time, which is the free choice this decision resolves.

- decision: the new `--help` prose documenting the empty-value refusal is written as "Every value-taking flag ... requires a non-empty value: an explicit empty string ('') is refused `usage`, the same as an omitted operand. That is distinct from leaving the flag off entirely ...", deliberately avoiding every one of the four words `fallback`/`alternate`/`retry`/`default` anywhere in the sentence, rather than the more natural phrasing "an empty value silently falls back to the default" the spec's own `## Notes for engineer` names as the trap.
  reason: two phrasings were genuinely available to describe the same behaviour (the natural one using "falls back"/"default", and a circumlocution avoiding those words), and the choice is observable in a shipped script's `--help` output that both adopters and CI read (`cb-help-sane`'s merged fixture greps that exact output for the four forbidden words with no path escape hatch). The circumlocution was verified, not assumed: the header-extraction-plus-grep command was run against the drafted text before commit and confirmed 0 matches, after an earlier draft using the word "default" was caught by the same command and rewritten.
  grounding: `bin/check-binding.sh`'s header comment, the paragraph immediately following the `Usage:` block (the "Every value-taking flag ..." paragraph); `tests/check-binding/run.sh`'s `cb-help-sane` assertion (`grep -cE 'fallback|alternate|retry|default'` over `--help`'s output must be `0`); `.shell-team/specs/T-1106-check-binding-consistency.md` `## Notes for engineer`, trap 1 ("The natural sentence for the new refusal — 'an empty value silently falls back to the default' — breaks a merged fixture.
