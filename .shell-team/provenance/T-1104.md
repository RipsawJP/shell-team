- decision: the checker's `--task`-only auto-resolution path treats two conditions leniently (exit 0) that the checker's own Goal-level fail-closed contract would otherwise cover strictly — a resolved reviews directory that does not exist at all (as opposed to one occupied by a non-directory), and a per-task record file that does not exist at the resolved `<reviews>/<task>.md` path. Both leniencies apply ONLY to the auto-resolution path; an explicit `--record` pointing at an absent path, a directory, or a dangling symlink still refuses `record-unreadable` exactly as AC2 requires.
  reason: `bin/close-out.sh`'s new gate is unconditional (DP-3's own precedent for the oversight gate), and it invokes the checker with `--task "$TASK"` only, no `--record`. Running the real `tests/close-out/run.sh` suite before this change showed every `dispatch_case`/`spec_review_case`/`oversight_case` fixture set up no `.shell-team/reviews/` directory at all (or, for `spec_review_case`'s empty-body cases, a directory with no file for the task), so an unconditional strict refusal on either absence would have broken every one of those pre-existing fixtures the moment this gate became unconditional — reproduced live (`interventions-resolver-failure-exit2 positive control` failed with `check-review-input: cannot resolve the reviews directory (team-paths.sh unavailable)` before this leniency, and separately with `check-review-input: record-unreadable` before the file-absence half of it). Neither the Goal's prose nor any AC actually requires strictness for this specific auto-resolved sub-case: AC2's five refusal cases all use either an explicit `--record` or a `$TEAM_REVIEWS_DIR` occupied by a *regular file* (never an absent path), so this leniency closes a real fixture-suite compatibility gap without contradicting any frozen criterion.
  grounding: `.shell-team/specs/T-1104-review-input-fidelity.md` AC2 (its five cases, none of which exercises an absent-but-otherwise-valid `--task`-only resolution target) and DP-3 (the oversight gate's own unconditional-but-cheap precedent, "the checker's own resolution keeps the caller cheap"); `tests/close-out/run.sh`'s pre-existing `dispatch_case`/`spec_review_case` fixtures (none of which creates a `.shell-team/reviews/` directory, or writes a per-task file inside one, for most of their cases) and its `interventions-resolver-failure-exit2 positive control` fixture, whose live failure and fix are recorded in `.shell-team/test-recipe.md`'s T-1104 entry.

- decision: per-pass-id validation runs in a fixed sequential order — missing-field check, then duplicate-field check, then pass-id charset, then (only if all three pass) executor-invocation non-emptiness, pass-role vocabulary, briefing-fidelity vocabulary, and raw-capture task-id-prefix — before any cross-id raw-capture-collision check runs, which itself runs before the per-section completeness check.
  reason: no acceptance criterion constructs a record violating two of these classes at once for the same pass id, so the order is a design choice rather than one a specific fixture forces. The chosen order proceeds from the coarsest structural fact (does this id even have all four fields, exactly once) to the finest content judgment (does this specific field's value satisfy its vocabulary or prefix rule), and defers the two record-wide judgments (collision, section-completeness) until every individual pass id has already been confirmed structurally sound — so a collision or incompleteness verdict is never reported ahead of a more fundamental grammar defect on the same or an earlier pass id.
  grounding: `.shell-team/provenance/T-1103.md`'s own precedent decision ("within the approval-record validation for a declared seam, refusals are checked in this order... coarsest structural judgment... to the finest content judgment", the same coarse-to-fine shape `bin/check-binding.sh` already uses); manually verified against every one of AC2/AC4/AC5/AC6/AC7/AC8/AC9's fixtures via `bash tests/check-review-input/run.sh` (58/58 cases passing) and the spec's own inline `- check:` lines via `bash bin/check-acs.sh`, none of which constructs a record violating two of these classes simultaneously for one pass id.

- decision: a pass id's section ownership, for the per-section completeness check (AC4), is determined by the SMALLEST line number among that id's four field lines — the section anchored by the nearest preceding verdict heading to that minimum line number — rather than by, say, the field lines' majority section or an explicit per-block boundary marker.
  reason: the record grammar has no explicit block-boundary marker (a pass block is just four consecutively-or-not field lines sharing one id), and every corpus fixture and every AC fixture writes a pass id's four field lines contiguously immediately after one verdict heading and before the next, so the id's earliest field line is always inside the section it actually belongs to. Using the minimum rather than, e.g., the maximum avoids a pathological case where a stray later field line for the same id (which would in practice already be caught as `field-duplicate` before this check ever runs) could shift the computed owner into a later section.
  grounding: `.shell-team/specs/T-1104-review-input-fidelity.md` AC4's four fixtures (`one.md`, `gap.md`, `both.md`, `two.md`), each of which writes one pass id's whole block contiguously within one section; `bin/check-spec-review.sh`'s own design-note precedent for column-zero/stem-anchored section detection, cited in this spec's `## Notes for engineer` Gotcha on the verdict-heading anchor.

- decision: field-line extraction and per-line parsing use bash's native `[[ =~ ]]` regex matching with `BASH_REMATCH` capture groups (applied only to lines already pre-filtered by a `grep -nE` pass over the whole record), rather than an `awk` implementation using capture-group extensions or a bash associative array keyed by pass id.
  reason: `.shell-team/test-recipe.md`'s T-1028 entry fixes this repository's shipped compatibility bar for every `bin/`/`tests/*/run.sh` script — indexed arrays only, no associative arrays, no `mapfile` — because the host's stock `/bin/bash` is 3.2.57, which lacks `declare -A` entirely (verified live: `bash -c 'declare -A x'` errors `declare: -A: invalid option` on this exact host). `[[ =~ ]]` and `BASH_REMATCH` are available since bash 3.0, so per-line regex capture is portable to that floor; grouping and counting by pass id is instead done with `awk`/`sort`/`uniq`/`cut` (POSIX external tools whose own native associative-array behavior is unaffected by bash's own array restriction) reading from a small on-disk intermediate file, never a bash hash structure held in memory.
  grounding: `.shell-team/test-recipe.md`, the T-1028 entry ("The classifier's own bash-3.2 compatibility bar (indexed arrays only — no associative arrays, no `mapfile`) applies to this suite too"); live verification on this host (`bash --version` reports `3.2.57(1)-release`; `bash -c 'declare -A x'` fails).

- decision: the field-line extraction reads the whole record via `grep -nE` first (a single pass over the record's raw bytes) and only then loops (`while IFS= read -r`) over `grep`'s own captured output — never over the record file directly with a raw `while read` loop.
  reason: `bin/check-spec-review.sh`'s own header states the EOF-safety discipline this design copies: a `while IFS= read -r line` loop reading a file directly drops a final line that has no trailing newline (the read's own non-zero exit status ends the loop before that line's content is used), and a review record's last line — exactly where a late append lands — is the highest-risk spot for this. `grep`'s own stdout always ends in a newline after its last matched line regardless of whether the source file's corresponding line had one, so looping over the grep output (rather than the record itself) is EOF-safe by construction, following the identical "extract with grep/sed, then only loop over the extracted output" shape this task's own Notes for engineer names as prior art to copy.
  grounding: `bin/check-spec-review.sh`'s header ("the whole file is read with grep/sed, never a while IFS= read -r line loop, which drops a final line carrying no trailing newline"); `.shell-team/specs/T-1104-review-input-fidelity.md` `## Notes for engineer`'s "Prior art to copy rather than reinvent" bullet, which names this exact discipline.

- decision: (rework round 2, supersedes the "smallest line number" section-ownership decision above) a pass id's block is now credited to a section ONLY when ALL FOUR of its field lines resolve to the SAME owning section — never from the id's earliest field line alone. When the four lines resolve to more than one distinct section, the id is credited to no section at all.
  reason: the codex round-1 implementation review's Major 4 live-reproduced the earliest-line-only design as a defeat — a record with one field of a pass id under one verdict heading and the other three fields of that same id under a second heading (which itself carries a complete block of its own, from a different id) was credited as "complete" to the FIRST heading purely because that pass id's earliest field line sat there, even though three of its four required fields were never actually written under that heading. Two designs were available: (a) require unanimous section agreement across all four field lines (the one taken), or (b) require only a plurality/majority. (b) was rejected because a 2-2 split has no majority and a 3-1 split would still credit a section that holds only 3 of 4 required fields, which is exactly the defect being closed — the Goal/DP-4's own re-scoped text ("all four of whose field lines sit inside that same section") requires unanimity, not a majority.
  grounding: `.shell-team/reviews/T-1104.md`'s `## Codex review` section, Major 4 ("Section-ownership is not actually verified to be section-scoped..."), with its own live-reproduced fixture; `.shell-team/specs/T-1104-review-input-fidelity.md`'s v2 Goal grammar sentence ("all four of whose field lines sit inside that same section") and AC4 case 5; `tests/check-review-input/run.sh`'s new "section-scoped ownership" fixture, independently confirmed via a mutation self-check (reverting to earliest-field-line credit turns both AC4's own check line and this fixture red; restoring turns both green).

- decision: (rework round 2) a literal tab byte inside a captured pass id or field value is rejected outright, at capture time, with the existing `field-grammar` refusal token — rather than switching the internal tab-delimited work-file transport to a different delimiter (e.g. NUL-separated records) that the captured bytes cannot forge a column boundary in.
  reason: the codex round-1 review named both repairs as valid ("do not round-trip captures through a tab-delimited transport; reject any capture containing a literal tab or newline outright... or switch the intermediate representation"). Reject-outright was chosen because it closes the defect at the earliest possible point (before any column-shifting corruption can occur in ANY of the five columns the work file carries, including the newly-added owner column this round adds), requires no change to the existing `awk -F'\t'`/`cut -f` extraction idiom the rest of the script already uses, and treats an embedded tab as a shape violation consistent with the field contract's own spirit ("the field contract already forbids control-character content in spirit") rather than silently accepting and re-encoding it. A NUL-delimited transport was considered and rejected: it would require rewriting every `awk -F`/`cut -f` call site to a NUL-aware form, is a larger, riskier diff for a fix this task's own Reviewer-scope prices as a real instrument defect rather than scope for a redesign, and NUL cannot appear in a bash variable at all, so a NUL-delimited fix would have had to solve a problem (surviving in a bash variable) that a reject-outright fix does not need to solve.
  grounding: `.shell-team/reviews/T-1104.md`'s `## Codex review` section, the tab-injection Major and its own "Fix" line naming both repairs; `bin/check-review-input.sh`'s five-column `$WORK/fields` work file (line/field/id/value/owner, tab-delimited); `tests/check-review-input/run.sh`'s two new tab-injection fixtures (id and value), independently confirmed via mutation self-check (removing the rejection turns the value-tab fixture red with a different, corrupted-column failure mode rather than a clean pass, and restoring the check turns it green again).

- decision: (rework round 2) the dangling-symlink fix for the two `--task`-only auto-resolution leniencies (the reviews directory, the per-task record path) is implemented as an added `[ ! -L "$PATH" ]` conjunct alongside the existing `[ ! -e "$PATH" ]` test, rather than switching to a single `stat`/`readlink -e`-based existence probe.
  reason: `[ -e ]` already correctly reports false for a dangling symlink (this IS the bug: a broken link reads as "does not exist"), and `[ -L ]` is true for a symlink regardless of whether its target resolves — so `[ ! -e "$PATH" ] && [ ! -L "$PATH" ]` is true only when nothing, not even a broken link, occupies that path, which is exactly the leniency's own stated scope ("a reviews directory that does not exist AT ALL"). This keeps both fall-through branches (the `-d` test for the reviews dir, the `-f`/`-r` test for the record) doing the actual fail-closed work they already do for every other refusal shape, rather than introducing a second existence-probing mechanism (`stat`, `readlink -e`) that would need its own portability check against this repo's bash-3.2/coreutils floor (`.shell-team/test-recipe.md`'s T-1028 entry).
  grounding: `.shell-team/reviews/T-1104.md`'s `## Codex review` section, the dangling-symlink Major and its own "Fix" line ("replace both `[ ! -e ... ]` tests with a check that distinguishes 'no path component exists there at all' from 'an occupant exists but is broken/unreadable'... e.g. `[ ! -e "$PATH" ] && [ ! -L "$PATH" ]`" — the literal form this decision adopts verbatim); `tests/check-review-input/run.sh`'s two new dangling-symlink fixtures, independently confirmed via mutation self-check (dropping the `[ ! -L ]` conjunct on the reviews-dir test turns its own fixture red; restoring turns it green).

- decision: (rework round 2) `export LC_ALL=C` is added once, near the top of the script (immediately after `set -euo pipefail`), rather than scoping `LC_ALL=C` locally to only the bracket-class charset test (`[[ ! "$id" =~ ^[a-z0-9-]+$ ]]`) the way `bin/close-out.sh:150` and `bin/check-oversight.sh:176`–`:181` scope it per-invocation (`printf ... | LC_ALL=C grep ...` / a dedicated `lower_ascii()` helper piping through `LC_ALL=C tr`).
  reason: this script's own reviewer-cited hazard class ("bracket-class charset checks... run without forcing LC_ALL=C") is not confined to the one `[[ =~ ]]` charset test — the script also runs `sort`, `cut`, `grep -F`/`grep -E` and shell `case` glob matching throughout its per-section and per-pass logic, several of which are collation-sensitive in a non-C locale. A single top-of-script export closes the whole class in one line rather than requiring a `LC_ALL=C` prefix at every one of those call sites (a repeat-the-fix-N-times shape this task's own same-class discipline disfavors), at the cost of applying the locale override to the whole process rather than scoping it narrowly — an acceptable trade for a script whose entire job is byte-level grammar validation with no legitimate locale-dependent behavior anywhere in it.
  grounding: `.shell-team/reviews/T-1104.md`'s `## Codex review` section, the `LC_ALL=C` Minor and its own "Fix" line ("`export LC_ALL=C` near the top of the script, alongside the existing `set -euo pipefail`" — the literal form this decision adopts verbatim); `bin/close-out.sh:150` and `bin/check-oversight.sh:176`–`:181`, read as the repository's existing narrower-scoping precedent and distinguished from it above.
