- decision: build the #189 reproduction listing as one two-record synthetic `git ls-files -s`-shaped string carrying both a space-containing path field and, in the second record, a path field with embedded literal tab characters (more adversarial than a plain space, and more adversarial than anything real `git ls-files -s` output would ever carry, since git itself C-quotes a raw tab in a path) — rather than two separate single-record listings, or a listing exercising only the space case the issue's own wording names.
  reason: DP7 requires the reproduction to actually exercise the suite's own field-extraction logic (`count_non_100755`'s mode-prefix test and `count_tests_violations`'s `mode`/`rest`/`sha` positional extraction) rather than merely re-derive the same conclusion this role already reached by reading the code (Assumption 4). A single space-only record would leave the embedded-tab case — the shape closest to genuinely defeating a naive positional split — untested, and the spec's own Assumption 4 and `## Summarized sources` entry for `tests/bin-exec-bit/run.sh` both name the TAB as the actual field separator the parse relies on, so the adversarial case worth exercising is a path that itself contains that separator character, not merely whitespace of any kind. Combining both into one listing (rather than two separate runs) lets the record show, in one place, that neither shape reaches `mode` or `sha`, without multiplying the frozen record's own surface.
  grounding: `.shell-team/specs/T-1050-check-layer-fast-follow.md`'s `## Summarized sources` entry for `tests/bin-exec-bit/run.sh` (the TAB-bounded positional-extraction distinction) and Assumption 4 (the reading-only measurement DP7 requires this role to confirm or contradict by execution); DP7 itself ("the task therefore produces a reproduction record ... before any transport is rewritten").
- decision: recommend, in the reproduction record's `disposition` field, that #189 be **closed** with a comment citing the method and fields measured here, rather than recommending it be narrowed to a smaller premise.
  reason: DP7 offers both dispositions ("a narrowed or closed #189") and leaves the choice to what the reproduction actually shows. The measured fields show that no byte the path field carries — regardless of its exact shape — can reach `mode` or `sha`, because both are bounded by fixed field positions that sit before the record's own separating TAB; there is no narrower premise within this suite's actual parsing behavior for a follow-up issue to stand on, and filing a narrowed issue against a defect that cannot occur would misdirect whoever holds network access to file it.
  grounding: the `## Issue 189 reproduction record`'s own `- fields:` entry (both records' extracted `mode`/`sha` values, correct in both cases); DP7's disposition clause naming both options as the reproduction's own call to make.
