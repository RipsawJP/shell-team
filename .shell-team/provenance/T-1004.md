- decision: The install snippet's JSON shape registers the hook as `"hooks": { "UserPromptSubmit": [ { "hooks": [ { "type": "command", "command": "..." } ] } ] }` — a matcher-less event key mapping to an array of one object, each carrying its own nested `hooks` array of `{type, command}` entries — rather than a flatter shape such as `"UserPromptSubmit": [ { "type": "command", "command": "..." } ]` with no inner `hooks` wrapper.
  reason: The spec's own external-hook-contract Assumption states the shape was "verified against the official Claude Code hooks documentation … on 2026-07-30" but does not itself pin the JSON literal, so the exact nesting was mine to get right rather than invent freely — a flatter shape is a plausible-looking guess that does not match the real settings-file schema, and shipping a copy-paste snippet an adopter cannot actually register would defeat AC15's "copy-ready" requirement.
  grounding: .shell-team/specs/T-1004-optin-hook-sample.md Assumptions ("The external hook contract, recorded as an external assumption … verified against the official Claude Code hooks documentation (hooks reference + hooks guide) on 2026-07-30"); AC15's pinned JSON literal now present in docs/tuning-oversight.md and docs/tuning-oversight.ja.md.

- decision: `docs/interventions-reminder-hook.sample.sh` drains stdin (`cat >/dev/null 2>&1 || true`) as its very first executable statement, unconditionally, before the resolver call and every board check — rather than draining only on the path that reaches the final `printf`, or only after the resolver/board checks have already decided the outcome.
  reason: DP-4 establishes THAT stdin must be drained (so a harness write never lands on a closed pipe); it does not fix WHERE in the script's control flow the drain happens. Placing it last, or only on the emit path, would leave every early-exit no-op path (missing resolver, absent board, unreadable board) never touching stdin at all — exactly the state that risks a harness write landing on a still-open-but-unread pipe on the majority of real invocations, since Input space class 5 ("the hook not installed") and class 4 ("plugin not enabled") are the common case, not the exception, for a user-wide hook.
  grounding: .shell-team/specs/T-1004-optin-hook-sample.md DP-4 ("stdin is drained rather than ignored so the harness's write never lands on a closed pipe"); Input space classes 4 and 5 (the resolver-absent and hook-not-installed states are the dominant reachable classes for a user-wide registration); docs/interventions-reminder-hook.sample.sh's `cat >/dev/null 2>&1 || true` as the first statement after `set -u`.

- decision: `tests/interventions-reminder/run.sh` asserts `command -v team-paths.sh` (the anti-vacuity positive control) not only before the four cases the spec's Notes for engineer name explicitly ("before each emit case") but also before several no-op cases (the Done-only board, the non-conforming `- [ ]` line, the unreadable board, and the directory-typed board path) — omitting it only for the one case where the resolver's absence IS the condition under test.
  reason: Without this control on a no-op case, a silent-no-op result caused by a broken resolver shim (a suite bug, not a sample bug) would be indistinguishable from the correct no-op the case is meant to prove — the same anti-vacuity risk the spec names for emit cases applies symmetrically to no-op cases whose shim setup is otherwise identical, and the Notes' "before each emit case" wording states a floor, not a ceiling.
  grounding: .shell-team/specs/T-1004-optin-hook-sample.md Notes for engineer, "Traps measured in advance" ("Assert `command -v team-paths.sh` under the modified `PATH` before each emit case"); tests/interventions-reminder/run.sh `assert_resolver_reachable` call sites in every case except case 2 ("no board at all", where no shim-bearing PATH claim is made) and case 8 ("the resolver missing from PATH", where unreachability is the condition under test) — including the no-op cases 3, 9, 10 and 11.
