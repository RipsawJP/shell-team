# T-112 decision provenance

<!-- BEGIN provenance: T-112 -->

- decision: `bin/check-commit-identity.sh` requires `--base <ref>` as a mandatory argument (missing => usage error, exit 2), rather than falling back through a default chain (env var / `origin/$GITHUB_BASE_REF` / `develop`) the way `bin/check-pii-shapes.sh`'s DP-2 does.
  reason: DP-1 defines the range purely in terms of "the merge-base of `<base>` and `HEAD`" and never describes a default-resolution chain the way T-111's spec's DP-2 does for `check-pii-shapes.sh`; CI's own required step passes `--base` explicitly either way (AC20), so a default chain would add interface surface with no AC exercising it.
  grounding: spec section "DP-1 — commit range, and the merge-commit / web-flow disposition" (defines the range via `<base>`, no default-chain language); AC20 check: `bash bin/check-commit-identity\.sh --base` in `.github/workflows/check-handoff.yml`.

- decision: AC12's vacuity guard neutralises the ALLOWED-identity regexes (`NOREPLY_ID_RE`, `NOREPLY_PLAIN_RE`, rewritten in a throwaway copy to match any string), and proves the already-established author-identity/committer-identity POSITIVE fixtures then report NOTHING against that copy — rather than mutating a separate "finding" regex the way T-111's `bin/check-pii-shapes.sh` mutation guard does.
  reason: this checker is allow-list-based (a finding is "identity does not match the allowed set"), not deny-list-based like T-111's PII-shape patterns, so there is no separate finding-producing regex to neutralise; making the allow-set match everything is the equivalent "break the one piece of logic that produces findings" mutation for an allow-list detector, and it demonstrably collapses detection for both sides (verified by hand: the suite goes red on this exact mutation, then green again on restore).
  grounding: spec AC12 ("the suite produces a copy of the checker with the allowed-identity rule neutralised ... requires the copy to report nothing"); tests/check-commit-identity/run.sh section "mutation: identity pattern is load-bearing".

- decision: AC13's "neutralised positive fixture" reuses the already-built NEG (conformant) repo/base from each side's own AC5/AC6 POS/NEG pair, rather than authoring new pattern-specific "broken positive" fixtures for the meta-assertion.
  reason: same T-111 precedent (`.shell-team/provenance/T-111.md`'s equivalent decision) applies here for the same structural reason: the NEG fixture already IS the POS fixture's identity replaced by a conformant one, which is exactly the object AC13 describes, so authoring a second, separate fixture pair would duplicate coverage without changing the assertion's meaning.
  grounding: spec AC13 ("a neutralised fixture (one whose identity has been replaced by a conformant one)"); tests/check-commit-identity/run.sh section "meta: neutralised positive fixture makes the assertion FAIL", reusing `AUTH_NEG_REPO`/`COMM_NEG_REPO`.

- decision: AC19's legacy-layout coverage in `tests/gitignore-raw-dumps/run.sh` is a resolver-correctness assertion (`bin/team-paths.sh --root <legacy-fixture> --get reviews` reports `tasks/reviews`), not a duplicate git-ignore semantic lock for a legacy-layout raw-dump convention.
  reason: the raw-review-dump patterns this suite locks (`.shell-team/reviews/*.txt` etc., `.codex-review.json`) live only in this repo's own default-layout root `.gitignore` — a self-hosting-specific addition, not part of the shared, layout-agnostic `templates/shell-team.gitignore` (which ships only `runs/` and `reviews/.codex-capture.*`); inventing an equivalent ignore file for a hypothetical legacy-layout adopter would be designing a new `.gitignore` pattern, which the spec's Non-goals rule out for this task.
  grounding: spec Non-goals, "Designing new `.gitignore` patterns. Item 2 is a lock, not a design."; `templates/shell-team.gitignore` (contents: `runs/`, `reviews/.codex-capture.*` only); AC19 check: `grep -qF 'team-paths.sh' ... && grep -qF 'legacy' ...` (a textual, not semantic, requirement).
