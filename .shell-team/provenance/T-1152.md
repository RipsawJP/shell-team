- decision: The round-2 (R3'') gate's JSON field reader is a single-pass awk tokenizer that splits each rollout line into JSON string-literal tokens (matching `"(\\.|[^"\\])*"`) and structural single-character tokens (`{ } [ ] : ,`), tracks nesting with a unified push/pop stack for both objects and arrays, and classifies a string token as a "key" purely by lookahead — the very next token being `:` — rather than by explicitly modelling "am I inside an object or an array right now".
  reason: A lookahead-based key/value classification is correct for this schema without needing to distinguish object-mode from array-mode: a bare string is followed by `:` only when it sits as an object key, never as an array element (this rollout schema has no array of strings that is itself followed by a colon), so tracking depth alone (for building the dotted path `payload`/`payload.item`) is sufficient and simpler than a two-mode parser, and it was verified line-by-line against all fifteen of AC6's synthetic fixtures in an isolated scratch harness before being wired into the script (14 of 15 fixtures matched exactly; see the next entry for the fifteenth).
  grounding: .shell-team/specs/T-1152-codex-sandbox-hotfix.md — AC6's prose ("Fields are read token-structurally … a field counts only as a key/value pair at its structural position") and `## Notes for engineer`'s "Gate (R3'', AC6)" bullet; bin/codex-capture.sh — the `--publish --thread-id` gate's `tokenize`/`fullpath_of`/`is_key_lookahead` awk functions.

- decision: AC6's own `- check:` line is internally unsatisfiable for its fourteenth `cs()` sub-case (the one using the `$UK` fixture, intended per the criterion's prose as "the `\u`-escaped `error` key, refused as not parseable").   reason: A byte-for-byte comparison shows `$UK`'s definition in the frozen check line is identical to `$ER`'s (both `{"timestamp":"t","ordinal":2,"type":"event_msg","payload":{"type":"task_complete","last_agent_message":"x","error":{"message":"boom"}}}`) — `$UK` carries no `\u` escape at all. The same check line's seventh `cs()` sub-case feeds the identical three-line rollout (`$M $X $ER`) and requires exit 3 with `review did not run (… error=present)`; the fourteenth sub-case feeds the byte-identical rollout (`$M $X $UK`) and requires exit 3 with a *different* message, `rollout not parseable (… cause=unicode-escape)`. Since the gate is a pure function of the rollout file's content (by design — the synthetic thread id is never itself part of the JSON payload the gate reads), no implementation can return two different classifications for byte-identical input; this was confirmed live, running both fixtures through the shipped script in an isolated `$CODEX_HOME`: both classified as `review did not run (… error=present)`, exit 3 (reproduction below). Hard-coding a match against this one test's literal bytes (or its synthetic thread id, which is generated from the `cs()` harness's own call-count, `0000bbbb-1111-7222-8333-%012d`) would be dishonest test-gaming with no relationship to genuine `\u`-escape detection, and would *still* fail case 7, which demands the identical bytes classify the other way. The correct fix is a class-B re-freeze of AC6's check line, redefining `$UK`'s content to carry a genuine `\u` escape distinguishable from `$ER` — for example spelling the key itself as `"error"` (legitimate JSON, decodes to the same semantic key `error`) instead of `"error"`.
