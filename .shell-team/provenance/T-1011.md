- decision: `bin/check-run.sh`'s `lint_line` treats an invalid/malformed `kind` value (a quoted value outside `span|event`, an unquoted value, or JSON `null`) as falling back to the SPAN branch's validation (running the pre-existing `REQUIRED_KEYS`/status/verdict checks in addition to the `kind` enum violation itself), rather than skipping both shape-specific branches entirely for such a row.
  reason: D2 freezes that "any other value ⇒ violation" and that `"kind":null`/unquoted `⇒ violation`, but does not itself specify which (if either) shape-specific branch should still run afterward. A row with a garbage `kind` is not thereby exempted from being a defective span or a defective event — reporting *only* the kind violation and suppressing every other structural check on that same line would under-report a line that has multiple independent problems, and would diverge from the existing pre-T-1011 precedent that a `status`/`verdict` enum violation does not short-circuit the rest of `lint_line`'s checks. Falling back to the span branch (rather than the event branch) matches D2's own framing ("kind absent means span") — a row whose `kind` cannot be resolved to `event` is, for validation purposes, closest to "not a recognized event," so it is validated as a span. This choice is exercised by AC17's `kb`/`kn` cases (a garbage-`kind` row built from an otherwise-valid span fixture), which only require the kind-violation message and exit 1 — they do not assert on, and are not broken by, the span branch also running silently and finding nothing further wrong.

- decision: `lint_span_line` and `lint_event_line` in `bin/check-run.sh` each end with an explicit `return 0`, even though every violation-emitting statement inside them already reports via the global `emit()`/`violations` side channel and their own final line looks like it "returns nothing useful" on its own.
  reason: Found empirically while testing the fixture `tests/check-run/fixtures/valid-events.jsonl` (a genuinely clean file): the whole script exited 1 with **zero** stderr output — a silent, unreported failure. Root cause: under `set -euo pipefail`, a standalone `cond && action` statement that is the LAST command executed in a function, with `cond` false (the common, no-violation case), returns that function with exit status 1; if that function call is itself the final, unguarded statement of its caller (here, `lint_span_line`/`lint_event_line` called from `lint_line`'s `if/else`), the failure propagates and `set -e` aborts the entire script before it ever reaches its own `exit 0`/`exit 1` — with no `emit()` ever firing, so the failure is silent. Reproduced in isolation (`bash -c 'set -e; f(){ local x=""; [[ -n "$x" ]] && echo hi; }; f; echo "after: $?"'` exits 1 with no "after" printed) and confirmed the fix (adding a trailing `return 0`) makes the identical pattern reach "after: 0". This is exactly why the pre-existing (pre-T-1011) `lint_line` already ended with an explicit `return 0` — a discipline my new helper functions needed to inherit, not one I could infer from the base file's span-only code path alone (which happened not to end on a bare `cond && action`).
  grounding: bin/check-run.sh functions lint_span_line / lint_event_line, trailing `return 0` lines; base ref `08ebaea:bin/check-run.sh` function `lint_line`'s own trailing `return 0` (the precedent this decision inherits); reproduction transcript (`set -e; f(){ local x=""; [[ -n "$x" ]] && echo hi; }; f` exits 1 with no output; adding `return 0` after the `&&` line makes it reach the following statement) — re-run any time via that exact one-line repro.
