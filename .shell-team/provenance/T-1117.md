- decision: implement `--help` as the file's own leading `#`-comment header block, read by `print_help()`'s `awk 'NR==1{next} /^#/{...}'` idiom (ported from `bin/check-binding.sh`), rather than a `cat <<'EOF' ... EOF` heredoc.
  reason: AC6 strips only lines whose first non-blank character is `#` before scanning the checker's "code lines" for forbidden literals (`resolve-executor`, `--print-resolved`, `team-paths`, `provider-configured`, `codex`, `binding.conf` unprefixed, every role name read live from the conf, and any comparison against the literal population size). A heredoc's content lines do not start with `#`, so they would be swept into that "code lines" scan along with the rest of the script — the engineer notes explicitly named this as a live trap ("AC6 treats every non-# line of the checker as code, including a --help heredoc"). Two implementation shapes were available for satisfying AC3's help-content requirements: (a) a heredoc, simpler to write but exposed to the AC6 scan; (b) the comment-header idiom, which places the entire help text outside AC6's scan by construction, matching the precedent `bin/check-binding.sh` and `bin/resolve-executor.sh` already establish (also named in the spec's "Prior art to read before writing" note). (b) was chosen — it is strictly safer and is the idiom the spec itself points at, so this was not a close call, but it is recorded because the alternative was genuinely available and a plausible-looking heredoc draft would have silently failed AC6 on a forbidden literal appearing in prose (there are none currently, but the risk is structural, not incidental).
  grounding: `.shell-team/specs/T-1117-pin-default-equality-lock.md` AC6's own check line (`grep -v '^[[:space:]]*#' "$C" > "$T/code"`) and its "Notes for engineer" bullet ("Prior art to read before writing... the print_help idiom that prints the file's own header comment... which is what makes AC3's header the adopter surface rather than a second copy of it"); `bin/check-binding.sh:173-176`'s `print_help()`.

- decision: on encountering a population row whose agent file cannot be fully evaluated (missing/unreadable, more than one `model:` line, or a `model:` line with an empty value), exit 2 immediately rather than continuing to scan the remaining population rows first.
  reason: DP-4's condition table lists each of these as an independent `2` arm, but does not itself state an ordering rule for a hypothetical input carrying both a `2`-class problem on one row and a `1`-class mismatch on another. Two designs were available: (a) scan every population row unconditionally, accumulate all findings, and only then decide the overall exit code by priority (2 dominates 1 dominates 0); (b) exit immediately the first time a `2`-class problem is found on any row, since "cannot evaluate" is an absolute condition that does not become more or less true by inspecting further rows. Design (a) is what the mismatch-accumulation loop actually does for `1`-class violations (it does not exit early on a mismatch, so a later `2`-class row is still caught) — but design (b) was chosen specifically for `2`-class problems, because once the checker is fail-closed at that severity there is no additional information a later row could add that would change the verdict, and (b) is simpler to reason about (the DP-4 priority is enforced structurally: no `1` exit path can be reached until every row has cleared every `2`-class check). No AC's fixtures exercise a mixed multi-row scenario (each mutation case touches exactly one row), so this choice is unconstrained by the check lines themselves and is a genuine judgment call about fail-closed ordering under an input space the fixtures do not directly probe.
  grounding: `.shell-team/specs/T-1117-pin-default-equality-lock.md`'s `## Decision points` DP-4 (the condition table and the three-way exit split, `2` = "cannot evaluate at all") and the general fail-closed convention stated repeatedly across `bin/check-binding.sh` and `bin/resolve-executor.sh` ("no input this script cannot fully evaluate is ever accepted").
