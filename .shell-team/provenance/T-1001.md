- decision: `bin/check-retro.sh`'s new `## Retro inputs` ledger rule treats ANY non-blank, non-indented, non-`- input: ` line inside the section as a violation ("unrecognised line") — it does NOT exempt blockquote (`> `) description lines the way rule 3's Lesson-候補 check silently skips any line not starting with `- `.

- decision: rule 4's field extraction uses leftmost `match()` on the ` — status: ` and ` — detail: ` markers (via `substr`), not a naive `split(line, parts, " — ")` into exactly three fields.
  reason: AC16's second runtime-generated case requires that a `detail:` value which itself quotes the ledger grammar (e.g. describing an older ledger line) is "not miscounted as a second ledger line" — a naive three-way split would count every ` — ` occurrence and reject such a line as malformed (more than 3 fields) even though it is a single, well-formed physical line. Leftmost `match()` finds only the FIRST occurrence of each marker (which is always the real field separator, since it appears earlier in the line than anything quoted inside the free-text detail), so everything after the first `— detail: ` — including further `— status: `/`— detail: ` substrings — is correctly treated as detail text.
  grounding: docs/specs/T-1001-retro-input-acquisition.md AC16 ("a detail: that quotes the ledger grammar is not miscounted as a second ledger line"); `tests/check-retro/run.sh`'s runtime-generated "case: a detail that quotes the ledger grammar is not a second ledger line".

- decision: rule 2's KPT/Traps heading checks (`$KEEP`/`$PROBLEM`/`$TRY`/`$TRAPS`) were changed from `grep -qxF` to a new CRLF-tolerant `has_exact_line()` awk helper; the `$KEEP`/`$PROBLEM`/`$TRY`/`$TRAPS`/`$LESSON_PREFIX` variable ASSIGNMENTS themselves are untouched.
  reason: AC16's first runtime-generated case requires "a ledger with CRLF line endings still passes" for the retro as a whole, but `grep -qxF` treats a trailing `\r` as part of the line content and would never match a CRLF file's heading line — yet AC17 locks the five heading constants byte-identical. Changing only the COMPARISON mechanism (an awk pass that strips a trailing `\r` before comparing), while leaving the `KEEP='...'` etc. assignment lines byte-for-byte unchanged, satisfies both constraints: the pinned constants never move, and the checker becomes CRLF-tolerant.
  grounding: docs/specs/T-1001-retro-input-acquisition.md AC16 ("case: a ledger with CRLF line endings still passes") and AC17 ("All five decorated heading constants are byte-identical"); `bin/check-retro.sh`'s `has_exact_line()` function and the unchanged `KEEP=`/`PROBLEM=`/`TRY=`/`TRAPS=`/`LESSON_PREFIX=` lines.

- decision: a shallow repository is detected purely by the EXISTENCE of a `.git/shallow` file (via `git rev-parse --git-dir`), and the fixture suite simulates it by creating an empty dummy `.git/shallow` file inside a normally-built throwaway repo rather than performing a real `git clone --depth`.
  reason: the spec's own Assumptions section names `.git/shallow`-file-existence as a usable simulation technique specifically because `git clone --depth` has been denied by sandbox policy in this repository before; detecting on existence-only (not parsing the file's content, which lists shallow-boundary commit hashes) is sufficient because the classification only needs to know "this history may be truncated," never which commits are at the boundary.
  grounding: docs/specs/T-1001-retro-input-acquisition.md, "## Assumptions" (".git/shallow is a usable way to simulate a shallow repository in a fixture... avoids git clone --depth, which has been denied by sandbox policy in this repository before"); `tests/retro-inputs/run.sh`'s shallow-repository cases (`: > "$dir/.git/shallow"`).

- decision: `bin/retro-inputs.sh`'s optional `gh pr list` enrichment query passes NO `--base`/branch-scoping flag at all (only `--state merged --limit N --json ...`), rather than reusing the resolved cycle-window ref as the PR-list's base branch.
  reason: `gh pr list --base` requires an actual branch name, but the resolved cycle-window ref can be `HEAD`, an arbitrary SHA, or any `--base` value a caller supplies — none of which `gh` accepts as a `--base` argument — and threading that through correctly (falling back only when the ref happens to be a real branch name) would reintroduce exactly the kind of branch-coupling AC5 exists to remove, for a marginal filtering benefit on an already-optional enrichment line. Dropping the flag entirely keeps the enrichment simple, correct in every case, and unconditionally free of a second hardcoded-or-derived branch assumption.
  grounding: docs/specs/T-1001-retro-input-acquisition.md AC5 ("The hardcoded release-branch query is gone from the whole operative surface") and AC10 (the six-field gh contract, silent on `--base`); `bin/retro-inputs.sh`'s pr-metadata block (`gh pr list --state merged --limit "$PR_LIMIT" ...`, no `--base`).

- decision: (round-1 rework, QA FAIL driver) `--last-n 0` is handled as an explicit branch inside `compute_cycle_window()` (`shown=""` when `last_n -eq 0`) rather than always piping through `head -n "$last_n"`; the `--last-n` boundary was otherwise reviewed and left as-is — negative values and non-integers were already rejected pre-fix by the arg-parse regex (`case "$LAST_N" in *[!0-9]*) die ... ;; esac`, which rejects a leading `-`), and an arbitrarily large `--last-n` was already safe pre-fix because the capping branch (`[ "$total" -gt "$last_n" ]`) is never entered when the requested cap exceeds the actual merge count, so `head` is never called with it.
  reason: QA reproduced and confirmed BSD `head -n 0` exits 1 ("illegal line count"), which the arg-parse regex accepts as a valid non-negative integer, so under `set -euo pipefail` the unguarded `shown="$(... | head -n 0)"` assignment aborted the function mid-way, leaving `emit_ledger` for `cycle-window` never called and the ledger incomplete (7 of 8 lines, then exit 1) — violating both the documented exit contract (0 or 2 only) and the ledger-completeness invariant this whole task exists to guarantee. The fix keeps `0` inside the SAME "declared cap" branch the ledger already uses for cap `>0` (status `read`, `capped=1`), rather than inventing a fourth status or a special-cased detail string, so a 0-commit cap reads exactly like any other cap (just capped at 0) and is never confusable with the pre-existing "0 merge commits, no cap requested" (`empty`) or "shallow boundary, 0 merges visible" (`unavailable`) cases, which differ by `CW_STATUS`, not by the digit alone. I judged that fixing 0 specifically is sufficient and did not widen `--last-n`'s validation further: negative and oversized values were independently confirmed (this round) to already be safe (negative: exit 2 at arg-parse, before `compute_cycle_window` is ever called; oversized: the capping branch's own `-gt` guard is never true, so `head` is never invoked with it), so there is no second crash-shaped gap in the same class to close. A cosmetic, non-crashing quirk was also observed and deliberately left alone: a zero-padded value like `--last-n 007` is accepted (the regex has no leading-zero rule) and echoed verbatim in the ledger detail ("...capped at --last-n 007...") rather than normalized to "7" — harmless (the ledger stays well-formed and the digit-in-`read`-detail rule is still satisfied), and normalizing it is a distinct, non-blocking polish item outside this FAIL driver's scope.
