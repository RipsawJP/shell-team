- decision: (v3) the capped-window pipeline was rewritten from `printf '%s\n' "$log_out" | head -n "$last_n"` to `awk -v n="$last_n" 'NR <= n' <<< "$log_out"` — a here-string into `awk`, not a different flavour of pipe into `head` or a `head`-with-different-flags variant.
  reason: the coordinator measured the trigger as bytes (~64KB, the pipe buffer), not merge count, and traced the mechanism precisely: `head` can exit (having read enough lines) before its upstream writer (`printf`/the earlier `git log` in the pipeline it depends on) has finished writing, and once the unread data exceeds the pipe's buffer the writer receives SIGPIPE, which under `pipefail` fails the assignment and triggers `errexit`. Any replacement piping INTO a command that can exit early carries the same structural risk regardless of which reader is used; a here-string has no live writer process on the other end to receive a signal at all (bash fully materialises the string before the reader starts), which removes the SIGPIPE exposure structurally rather than relying on the specific reader's flush timing. `awk` was chosen over other here-string-compatible line-counters only because it is already a hard dependency of this script (used extensively elsewhere) — no new tool is introduced. This also let the pre-existing `--last-n 0` special case be deleted entirely: `NR <= 0` is never true for any line (`NR` starts at 1), so a cap of zero naturally yields an empty result with no separate branch, which is one fewer conditional for the same correctness the two-branch version had.
