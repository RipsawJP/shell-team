- decision: (round-1 rework, QA FAIL driver) `--last-n 0` is handled as an explicit branch inside `compute_cycle_window()` (`shown=""` when `last_n -eq 0`) rather than always piping through `head -n "$last_n"`; the `--last-n` boundary was otherwise reviewed and left as-is — negative values and non-integers were already rejected pre-fix by the arg-parse regex (`case "$LAST_N" in *[!0-9]*) die ... ;; esac`, which rejects a leading `-`), and an arbitrarily large `--last-n` was already safe pre-fix because the capping branch (`[ "$total" -gt "$last_n" ]`) is never entered when the requested cap exceeds the actual merge count, so `head` is never called with it.
  reason: QA reproduced and confirmed BSD `head -n 0` exits 1 ("illegal line count"), which the arg-parse regex accepts as a valid non-negative integer, so under `set -euo pipefail` the unguarded `shown="$(... | head -n 0)"` assignment aborted the function mid-way, leaving `emit_ledger` for `cycle-window` never called and the ledger incomplete (7 of 8 lines, then exit 1) — violating both the documented exit contract (0 or 2 only) and the ledger-completeness invariant this whole task exists to guarantee. The fix keeps `0` inside the SAME "declared cap" branch the ledger already uses for cap `>0` (status `read`, `capped=1`), rather than inventing a fourth status or a special-cased detail string, so a 0-commit cap reads exactly like any other cap (just capped at 0) and is never confusable with the pre-existing "0 merge commits, no cap requested" (`empty`) or "shallow boundary, 0 merges visible" (`unavailable`) cases, which differ by `CW_STATUS`, not by the digit alone. I judged that fixing 0 specifically is sufficient and did not widen `--last-n`'s validation further: negative and oversized values were independently confirmed (this round) to already be safe (negative: exit 2 at arg-parse, before `compute_cycle_window` is ever called; oversized: the capping branch's own `-gt` guard is never true, so `head` is never invoked with it), so there is no second crash-shaped gap in the same class to close. A cosmetic, non-crashing quirk was also observed and deliberately left alone: a zero-padded value like `--last-n 007` is accepted (the regex has no leading-zero rule) and echoed verbatim in the ledger detail ("...capped at --last-n 007...") rather than normalized to "7" — harmless (the ledger stays well-formed and the digit-in-`read`-detail rule is still satisfied), and normalizing it is a distinct, non-blocking polish item outside this FAIL driver's scope.
  grounding: the coordinator's rework message (measured: BSD `head -n 0` -> exit 1; reachability via `[ "$total" -gt "$last_n" ]` requiring >=1 merge commit); `bin/retro-inputs.sh`'s `compute_cycle_window()` (the `if [ "$last_n" -eq 0 ]` branch and its comment); `tests/retro-inputs/run.sh`'s new "case: --last-n 0 is a degenerate but valid cap and must not crash" (built against `MAIN_REPO`, which has 2 merge commits, so the capping branch is genuinely reached — mutation-tested by the engineer: reverting the branch reproduces exit 1 on this case, restoring it turns the case green again).

- decision: (v2, design-premise reversal) the whole v1 defence structure — a single formatter accepting any status from any caller, defended by N independently hand-written guards, one per adverse condition — is replaced with an inverted default: every ledger line initialises to `unavailable`, and `read`/`empty` can only be produced by the two `promote_read()`/`promote_empty()` functions, called from exactly eight enumerated (`DS-1`..`DS-8`) sites, each with a decision-site inventory row and a fixture that makes its own determination impossible. This is a redesign, not a third patch on top of the first two.
  reason: rework-digest flagged `same-class-repetition` and the coordinator's own diagnosis is the direct cause: the CRLF-unaware section detection, the read-permission-only directory guard, and the git-dir-based shallow probe were three INDEPENDENT hand-written guards, and all three failed the same way — an unevaluable condition silently read as benign, because "benign" was the default and each adverse condition needed its own guard to override it. Patching a fourth site (fixing only the three named defects) would leave the SAME structural gap for the next unenumerated adverse condition nobody thought to guard; the class is an omission class, and an omission class is only closeable by making the omission itself impossible to introduce silently — i.e. by making `unavailable` the thing that happens when nothing else was DONE, rather than something a guard has to actively produce. The maintainer's own instruction ("reconsider-design-premise... this is not '3 箇所を直す' — this is a design-premise reversal") is exactly this judgment, and I did not treat it as three more if-branches to bolt onto the v1 structure.
  grounding: docs/specs/T-1001-retro-input-acquisition.md, "What v1 of this task got wrong, and why v2 exists" and DP-2 ("a formatter that accepts any status from any caller is not a chokepoint — it is a funnel with no filter"); the coordinator's rework message ("これは「3 箇所を直す」ではなく設計前提の反転です"); `bin/retro-inputs.sh`'s `promote_read()`/`promote_empty()` chokepoint and the `DS-1`..`DS-8` inventory in its header.

- decision: the eight DS numbers are assigned so that each of the two failure TECHNIQUES available for a given input (e.g. lessons: unreadable-file vs. not-a-regular-file; pr-metadata: auth-gate failure vs. list-command failure; directory: has-a-match vs. has-no-match) is deliberately split across the read/empty pair for that input, even though a single failure mode would in each case have blocked BOTH promotions equally (both a promotion is inherently unreachable once its shared precondition fails).
  reason: with only two functions and eight call sites, no failure technique is exclusive to "only the read half" or "only the empty half" of a promotion pair — any precondition failure blocks the whole probe, not one branch of it. Given that, I chose to demonstrate a genuinely DIFFERENT failure point in the pipeline for each DS number rather than reusing the identical technique twice (e.g. gh-unauthenticated for both DS-7 and DS-8), so that AC4's "one fixture per DS that makes THAT site's determination impossible" is answered with eight distinct, individually informative reproductions instead of four techniques each asserted twice. This is a legitimate editorial choice, not a forced one — the spec names the eight sites and requires one fixture each, but leaves the specific blocking technique per site to the implementer.
  grounding: docs/specs/T-1001-retro-input-acquisition.md AC4 ("one case per DS-n that makes that determination impossible") and the "Notes for engineer" worked outline (the eight sites named as pairs: "cycle-window read, cycle-window empty, directory read, directory empty, lessons read, lessons empty, pr-metadata read, pr-metadata empty"); `tests/retro-inputs/run.sh`'s eight `case: DS-N` blocks, each using a distinct technique (unanswerable shallow probe / shallow-with-zero-merges / non-traversable-with-a-match / non-traversable-without-a-match / unreadable-file / directory-as-path / gh-unauthenticated / gh-pr-list-failure).

- decision: three `cmd; rc=$?`-shaped statements in `probe_cycle_window()` (the default-ref probe, the unified ref-verify, and the shallow-probe command substitution) were rewritten as `if cmd; then rc=0; else rc=$?; fi`, because the bare form aborts the ENTIRE script under `set -euo pipefail` the instant the wrapped command exits non-zero — before `rc=$?` on the next line ever runs. Separately, `count_dir_entries()`'s iteration over the enumerated-names array is now guarded by `[ "$DIR_N_NAMES" -gt 0 ]` before expanding `"${names[@]}"`.
  reason: both are real, reachable crashes I found and fixed while implementing the inverted design, not stylistic cleanups. The `cmd; rc=$?` shape is exactly the pattern the coordinator's own FAIL driver from round 1 turned on (`head -n 0`) — every git probe that can legitimately fail (a missing ref, an old git that cannot answer `--is-shallow-repository`) needed the SAME fix, and I found it empirically: the DS-1 fixture (an unanswerable shallow probe) silently killed the whole script with no output at all until this was fixed, which is a worse failure than "wrong status" — it is "no ledger at all", the exact inverse of what an inverted default is supposed to guarantee. The array-guard fix addresses a separate, unrelated defect: bash 3.2 (macOS's default `/bin/bash`, confirmed the version this sandbox runs) throws "unbound variable" under `set -u` when expanding `"${arr[@]}"` on a genuinely empty array — a bug fixed in bash 4.4 but still live wherever a repo ships bash 3.2 as `/bin/bash`, which this project already treats as a live compatibility target (no `declare -A` anywhere in `bin/`).
  grounding: `bin/retro-inputs.sh`'s `probe_cycle_window()` (the three `if cmd; then rc=0; else rc=$?; fi` blocks and their comments) and `count_dir_entries()` (the `if [ "$DIR_N_NAMES" -gt 0 ]` guard and its comment); empirically reproduced by the engineer: `bash tests/retro-inputs/run.sh` failed with no FAIL/PASS output and a bare "unbound variable" / silent-exit-1 before each fix, and passed cleanly after.
