- decision: the home-path boundary rule (DP-5) treats only a letter or digit as a character that "can continue a host name" — hyphen, dot and underscore are all treated as valid boundaries (the shape still matches immediately after one of them), not only whitespace/quote/line-start.
  reason: the one required negative fixture (AC28, "a home-path-looking segment inside a URL is not a finding") only needs an alphanumeric character excluded, since every realistic domain label ends in a letter or digit right before the path's leading slash (e.g. `example.com/home/...`, preceded by `m`). Choosing the narrower alnum-only exclusion class — rather than also excluding hyphen/dot/underscore — keeps the pre-existing, already-tracked fixture `tests/rollup-track/fixtures/pii.jsonl` (whose `phase` field carries a hyphen-prefixed label directly abutting a `/Users/<name>/`-shaped segment, so the character right before the leading slash is a hyphen, not an alphanumeric) still reported as a home-path finding, consistent with DP-8's own accounting of "five tracked files under tests/rollup-track/fixtures/" that deliberately carry a shape. A wider exclusion class would have silently shrunk that count to four without any test or doc flagging the drift.
  grounding: AC28 ("a line containing an ordinary documentation URL whose path carries a home-directory-looking segment is not a finding"); DP-5 ("a character that cannot continue a host name"); DP-8 Assumptions ("eight tracked paths carry a shape... Five tracked files under tests/rollup-track/fixtures/"); empirically confirmed by running `bin/check-pii-shapes.sh --all` before and after the boundary rule landed and observing `tests/rollup-track/fixtures/pii.jsonl` stay a reported home-path finding under the alnum-only class.

- decision: the home-path-win pattern (`RE_HOME_PATH_WIN`) is not given the same preceding-character boundary guard as the POSIX home-path pattern.
  reason: DP-5's boundary rule exists specifically to close a URL-authority false positive (`https://host/home/...`), and a backslash-delimited Windows path never appears as a URL authority or path segment — there is no reachable false-positive class for this form in the Input space, and no fixture in the spec exercises one. Adding an unused guard would be speculative complexity with no fixture to prove it correct, which the spec's own "no synthetic extremes" framing counsels against.
  grounding: Input space reachable classes (the URL false positive is scoped to "a URL whose path contains a home-directory-looking segment", never to a Windows-style path); Notes for engineer's self-check question ("is the boundary rule applied to both home-path patterns") is answered here in prose rather than in code, since AC10's nine-rule enumeration lists "the home-path boundary rule" as a single exclusion, not two.

- decision: the known-shapes list (DP-8) carries five entries — `tests/rollup-track/fixtures/pii.jsonl`, `winpath.jsonl`, `secret-aws.jsonl`, `secret-github.jsonl`, `secret-openai.jsonl` — not the four that would follow from a naive reading of which fixtures "obviously" still carry a shape after DP-7's reserved-domain exclusion.
  reason: `pii.jsonl`'s mailbox-shaped value is at a reserved (RFC 2606) domain, so it is excluded by DP-7 and is genuinely clean, but its hyphen-prefixed home-path-shaped value (see the first decision above) still fires under the boundary rule as designed — so the file needs the exclusion for a different reason than a first read of DP-8's background prose suggests. Listing it here, rather than silently narrowing the count, keeps the honest-bookkeeping invariant (AC16, "`--all` exits 0 on this tree") true without weakening the boundary rule just to make the fixture clean for free.
  grounding: DP-8 Assumptions ("Five tracked files under tests/rollup-track/fixtures/ deliberately carry shapes"); AC16 ("no tracked path carries an unaccounted shape"); empirically confirmed — `bin/check-pii-shapes.sh --all` reported `pattern=home-path path=tests/rollup-track/fixtures/pii.jsonl` before this file was added to `KNOWN_SHAPE_PATHS`, and reported clean after.

- decision: each of the nine mutation-testable rules (five patterns, four exclusions) lives on its own single-line variable assignment, and the four exclusions are each a *separate* regex variable from the pattern they modify (e.g. `RE_HOME_PATH_BOUNDARY` and `RE_HOME_PATH_RAW` are two lines, concatenated once into `RE_HOME_PATH`, rather than one combined literal) — never inline conditionals or a shared multi-purpose regex.
  reason: AC10 requires each of the nine rules to be independently neutralisable, with a *different* expected effect for a pattern (its own positive fixture goes unreported) versus an exclusion (that exclusion's own negative fixture becomes a finding). A `sed` rewrite of one assignment line is the mechanism the fixture suite already used pre-v4 for patterns; splitting the boundary rule and the domain-based exclusions into their own dedicated lines is what makes that same single-line-rewrite mechanism apply uniformly to exclusions too, without a bespoke code-shape per rule.
  grounding: AC10 ("nine rules... Neutralising the domain-anchored rule must flip all of its negatives, the format-placeholder fixture included"); verified by hand before writing the fixture suite — `sed "s/^RE_HOME_PATH_BOUNDARY=.*/RE_HOME_PATH_BOUNDARY=''/"` on a throwaway copy flips the AC28 URL fixture from clean to a finding, and `sed "s/^RE_HOME_PATH_RAW=.*/RE_HOME_PATH_RAW='NEVER_MATCH'/"` on a throwaway copy makes the AC4 positive fixture go unreported, confirming the two lines are independently load-bearing for the two different AC10 sub-claims.

- decision: text/binary detection (AC27) is implemented as `LC_ALL=C tr -d '\000' < file | cmp -s - file` (a NUL byte is present iff stripping it changes the content), not `grep -P '\x00'` or a `[:print:]`-based heuristic.
  reason: `grep -P` (PCRE) is not guaranteed available in every grep this repo's CI and local dev runs (portability, and `bin/` stays "pure bash, zero-dependency" per CLAUDE.md); a `[:print:]`-based heuristic is the exact defect DP-4/AC27 replaces, since it misclassifies ordinary multi-byte UTF-8 (Japanese prose, em-dashes) as binary. `tr`+`cmp` are POSIX-standard, available everywhere `git`, `sed` and `grep` already are, and directly encode git's own "does this blob contain a NUL byte" convention.
  grounding: AC27 ("Text or binary is decided by the presence of a NUL byte... never by a printable-character heuristic"); CLAUDE.md "bin/ stays pure bash, zero-dependency"; verified directly — a UTF-8 file carrying full-width Japanese punctuation and a home-path shape is reported as a home-path finding in both diff-scoped and `--all` mode (`tests/check-pii-shapes/run.sh`, "text-vs-binary" section), and a file with embedded NUL bytes is skipped with an explicit stderr announcement rather than silently or misreported.

- decision: every `grep -nE` / `grep -noE` / `grep -qoE` invocation whose pattern argument is a shell variable is written with an explicit `--` before that variable (`grep -nE -- "$re" "$file"`), even at call sites whose specific pattern does not currently begin with a literal `-`.
  reason: `RE_PRIVATE_KEY`'s value begins with `-----BEGIN`, and without `--` grep parses that value as a run of short options and exits 2 with a usage error instead of scanning — reproduced directly while building the private-key POS/NEG fixture, before any AC required it. Since `report_pattern_lines` and `scan_email_candidates` are shared, generic call sites (the pattern is always a caller-supplied variable), guarding every such call site uniformly is cheaper and more robust than guarding only the one pattern known to need it today.
  grounding: `bin/check-pii-shapes.sh`'s `report_pattern_lines` and `scan_email_candidates` functions (the `--` immediately before `"$re"` / `"$RE_EMAIL_BASE"`); this repo's own `.shell-team/test-recipe.md` T-111 entry documents the identical `grep -qxF` leading-hyphen defect class for `check:` lines, which is the same root cause reproduced here on a different grep invocation.

- decision: the pre-existing false-positive finding in `.shell-team/test-recipe.md` (a printf format-string literal split across a markdown line wrap, so this checker's own line-oriented scan saw an incomplete noreply domain on one line) is fixed by rewriting the sentence to describe the shape in words instead of transcribing the literal domain across the wrap point — not by adding `.shell-team/test-recipe.md` to the known-shapes list.
  reason: the task's own instructions single out `.shell-team/reviews/` as "exactly where raw cross-provider output lands" and forbid listing it there; `.shell-team/test-recipe.md` is the same class of first-party process artifact (an append-only lessons log this task is explicitly allowed to edit), so the same discipline applies by extension — DP-8's list is reserved for fixtures belonging to *another guard's* suite, never for this project's own prose. The finding was genuinely a false positive on prose describing a bug (not a real identity), so rewriting the artifact is the correct one of the two legitimate responses DP-4's "Honest cost" section allows.
  grounding: DP-8 ("never for a document, spec, review record or provenance file"); DP-4 "Honest cost, recorded rather than hidden" ("fix the pattern if it was a false positive, or normalise the artifact... if it is one of this project's own records"); empirically confirmed — `bin/check-pii-shapes.sh --all` reported `pattern=email-nonnoreply path=.shell-team/test-recipe.md` before the rewrite and reported that path clean after, with no change to the rule set or the known-shapes list.

- decision: round 3 blocker fix — `RE_NOREPLY_DOMAIN` is changed from `(^|\.)users\.noreply\.github\.com$` to `^users\.noreply\.github\.com$` — full-string equality, anchored at both ends, with the "or a dotted-subdomain prefix" alternative removed entirely.
  reason: round 3 cross-provider review reproduced a genuine required-check bypass — a mailbox-shaped string whose domain merely ENDED WITH the noreply domain, prefixed by a dotted label (e.g. a fabricated `<label>.users.noreply.github.com`), was silently excluded, because the `(^|\.)` alternative treats "preceded by a literal dot" as equivalent to "is the domain itself". DP-9's own recorded intent says the match must be EXACTLY the GitHub noreply domain; GitHub does not hand out subdomains of this zone (unlike the reserved-domain case, RFC 2606, which legitimately reserves the whole zone under `example.com` and where the equivalent `(^|\.)` shape is therefore correct and was deliberately left unchanged — see the anchoring inventory comment in `bin/check-pii-shapes.sh`). No existing fixture reached this class: every prior negative used the bare domain with no prefix, so AC10's mutation test for this rule never exercised it. Re-examining every other regex in the file under the same "does this anchor/boundary admit more than it should" question found this to be the only rule with the bug — `RE_NOREPLY_PLAIN` is already a full-string equality against the whole address, and `RE_RESERVED_DOMAIN`'s equivalent shape is correct for the RFC-grounded reason above. A dedicated positive fixture (a dotted-subdomain address, expected to now fire) locks the regression.
  grounding: DP-9 ("a mailbox shape whose domain is EXACTLY ... the GitHub noreply identity domain"); the round 3 review section of `.shell-team/reviews/T-111.md` ("RE_NOREPLY_DOMAIN の... サブドメイン過剰除外バイパス"); `tests/check-pii-shapes/run.sh`'s "positive: a dotted subdomain of the noreply domain still fires (round 3 blocker regression lock)" fixture; empirically confirmed — the fixture reported clean under the old regex and a finding under the new one.

- decision: round 3 major fix — the `git cat-file` failure path is changed from a bare command followed by a separate `rc=$?; if [ "$rc" -ne 0 ]; then fail_structural ...` to a single-line `git cat-file -p "HEAD:$path" > "$CONTENT_FILE" 2>/dev/null || fail_structural ...`; separately, changed-path enumeration switches from `git diff --name-status` to `git diff --raw` (and, for `--all`, from `git ls-files --cached` to `git ls-files -s --cached`) specifically to read each entry's file MODE, and a gitlink (mode 160000) is now detected and skipped — announced on stderr, never scanned, never handed to `cat-file` at all.
  reason: under `set -euo pipefail`, a failing simple command that is not part of an `if`/`&&`/`||`/negation immediately triggers errexit — so the original two-line form never reached its own classified `fail_structural` call; the script instead exited with git's raw exit status (128 for `cat-file`'s "Not a valid object name" on a gitlink) and no `check-pii-shapes:` token at all, breaking the documented 0/1/2 exit-code contract even though it never produced a false "clean" (fail-closed's core guarantee held, but the classification contract did not). An ordinary, non-adversarial `git submodule add` reproduces this via a ordinary gitlink entry. Two independent fixes were needed: the same-line `||` closes the general case (ANY `cat-file` failure now lands on the classified path), and the explicit gitlink skip closes the SPECIFIC case cleanly (avoiding the same-line `||`'s fallback message for a condition that has a clear, intentional disposition) and also avoids a secondary risk review raised — `cat-file` succeeding by coincidence and returning an unrelated commit object's serialised content if that object happens to exist in the same repository's object database, which would then be scanned as if it were the gitlink path's "content".
  grounding: `bin/check-pii-shapes.sh`'s `git cat-file ... || fail_structural ...` (same-line form) and the gitlink-mode-160000 skip in both the diff-scoped and `--all` enumeration blocks; the round 3 review section of `.shell-team/reviews/T-111.md` ("git cat-file の失敗経路は dead code AND reachable"); `tests/check-pii-shapes/run.sh`'s "gitlink: a submodule reference is skipped, never scanned, never a raw unclassified exit" section (both diff-scoped and `--all` fixtures); empirically confirmed — a throwaway repo with a gitlink entry (added via `git update-index --add --cacheinfo 160000,<sha>,<path>`, no network dependency needed) now exits 0 with an explicit skip announcement in both modes, where it previously exited 128 (diff mode) or failed on `cp` (an initialised submodule directory, `--all` mode) with no classified message.

- decision: round 3 major fix, supersedes the boundary-class reasoning in the first decision above — `RE_HOME_PATH_BOUNDARY` is widened from `(^|[^A-Za-z0-9])` to `(^|[^]/A-Za-z0-9])` — a valid boundary is now start-of-line or any character that is not a letter, digit, `/`, or `]`.
  reason: round 3 cross-provider review found the alnum-only class left three reachable false positives open, all of which the frozen (AC18/AC19) doc line "a home-path shape written inside a URL is not reported" claims are closed: a file://-style triple-slash authority (`file:///Users/<name>/...`, the character right before the path is the SECOND `/` of the empty-authority marker), the same URL wrapped in a Markdown link (identical root cause), and an IPv6 literal authority (`https://[::1]/Users/<name>/...`, preceded by `]`). Since the doc line is inside the frozen intent-block and cannot be reworded, the only legitimate fix is to make the code true to the existing claim — widening the excluded-boundary class to also cover `/` and `]` closes all three reported subclasses. Verified this does not regress any existing positive/anti-swallow fixture: none of them are preceded by `/` or `]` (they are preceded by a space, a quote, a hyphen, or full-width Japanese punctuation, none of which are in the newly excluded set).
  grounding: DP-5 ("a character that cannot continue a host name"); the frozen doc line in `docs/pii-controls.md` / `docs/pii-controls.ja.md` ("A home-path shape written inside a URL is not reported..."), pinned verbatim by AC18/AC19; the round 3 review section of `.shell-team/reviews/T-111.md` ("home-path boundary rule's docs claim overreaches"); `tests/check-pii-shapes/run.sh`'s three new "boundary: ... (round 3 regression lock)" fixtures (file://, Markdown-wrapped file://, IPv6 literal authority); empirically confirmed — all three fixtures reported a finding under the alnum-only class and reported clean under the widened one, while the original AC28 fixture and every existing home-path positive/anti-swallow fixture were re-run and confirmed unaffected.
