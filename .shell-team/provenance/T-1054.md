# T-1054 decision provenance

<!-- BEGIN provenance: T-1054 -->
- decision: a schema line whose field count is not exactly 2 (`schema <version>`) is refused `unparseable-line` rather than a dedicated new token or `unsupported-schema`.
  reason: the spec's own `## Refusal matrix` states `unparseable-line`'s condition as "a non-blank, non-comment line whose first field is neither `schema` nor `bind`, or a `bind` row whose field count is not six" — it names the `bind` row's field-count case explicitly but is silent on a malformed `schema` line's field count. `unsupported-schema` is defined as "the version is not in the supported set", which presumes a version token exists to look up; a schema line with the wrong field count may have no such token at position 2 at all, so folding it into `unsupported-schema` would compare an absent value against the supported set rather than refusing the row's shape. `unparseable-line` is the only token in the closed set whose condition is about a line's shape not fitting either directive's grammar, which is exactly this case's own shape, so it is the correct member of the closed set to route through rather than inventing an unlisted token (Goal: "every refusal is one token from a closed set").
  grounding: `.shell-team/specs/T-1054-binding-config.md` `## Refusal matrix` (the `unparseable-line` and `unsupported-schema` rows' own condition text); `bin/check-binding.sh`'s `validate_config` pass-1 block (the `schema_fieldcount -eq 2` assertion, immediately before the `schema_version_supported` call).
- decision: the adapter/provider registry lookup order inside `validate_config` is adapter-known, then provider-known, then pairing-match — never provider-first.
  reason: AC6 tests three cases independently (adapter unknown with a valid provider; provider unknown with a valid adapter; both individually known but paired wrongly) and never combines two defects in one row, so no test forces one order over the other. The order is still an observable contract choice: a future config carrying both an unknown adapter AND an unknown provider on the same row would report whichever token this order picks first, and the two orders disagree on that case. Adapter-first was chosen because the adapter is DP6's primary allowlisted noun ("hosts select from allowlisted adapters") and the provider is described relative to it ("the adapter composes ... for a provider"), so checking the adapter's own membership before asking what it implies about the provider follows the format's own stated hierarchy.
  grounding: `.shell-team/specs/T-1054-binding-config.md` DP6 ("hosts select from allowlisted adapters, the adapter composes the executable ... for a provider"); `bin/check-binding.sh`'s `validate_config` pass-2 block (`adapter_known` checked immediately before `provider_known`, both before the `adapter_registered_provider` pairing compare).
- decision: `--verify` checks `path-mismatch` before ever opening or validating the `--config` file the caller gave it, when that path differs from the lock's recorded `config-path`.
  reason: AC10's own text states the refusal happens "without following it", read here as: the lock's recorded path is never dereferenced as a filesystem read (true regardless of ordering), but also that a `--config` value differing from the recorded one should not need to survive its own content's validation before the path question is even asked — the two questions ("is this the same file the lock describes" and "is this file's content still valid") are independent, and asking the first one first avoids validating a file already known to be evaluated against the wrong lock. The alternative (validate first, compare paths after) was rejected because it would let a malformed decoy file's OWN refusal token (e.g. `bad-token`) mask `path-mismatch` for a caller who supplied the wrong `--config` value entirely by mistake — the more informative refusal for that mistake is that the paths disagree, not that the wrong file happens to also be malformed.
  grounding: `.shell-team/specs/T-1054-binding-config.md` AC10 ("refuses ... `path-mismatch` ... without following it"); `bin/check-binding.sh`'s verify-mode dispatch block (the `CONFIG_DISPLAY != LOCK_CONFIG_PATH` compare precedes the `[ -f "$CONFIG" ]` / `validate_config` calls).
- decision: the lock document's `config-path` and `binding-hash` lines are located by pattern match over every line, never by fixed position — so a hand-built lock with the two swapped still verifies identically.
  reason: the spec's Notes for engineer spell a fixed canonical ORDER for `--print-lock`'s own OUTPUT ("binding-lock 1, config-path ..., binding-hash ..., the canonical form verbatim, then binding-lock-end"), but says nothing about whether `--verify`'s READER must enforce that same order on an arbitrary lock it is given — those are two different questions (what this script emits vs. what it accepts). A position-independent reader was chosen over a position-fixed one because the lock is explicitly "self-describing" (Goal) and because DP7's whole point is that non-binding variation (comment placement, whitespace, row order) in the CONFIG must not trip integrity — a reader that additionally required the LOCK's own two header fields to sit in one exact order would be a second, narrower place for exactly the kind of accidental-edit false stop DP7 exists to rule out, for no compensating benefit (both fields are still validated to exist exactly once each).
  grounding: `.shell-team/specs/T-1054-binding-config.md` `## Notes for engineer` ("The lock is `binding-lock 1`, `config-path <path>`, `binding-hash <40-hex>`, the canonical form verbatim, then `binding-lock-end`.") and DP7 ("A comment reflow, an added blank line, a CRLF conversion or a reordering of rows therefore does not trip the integrity check"); `bin/check-binding.sh`'s `read_lock` function (the `for l in "${lock_lines[@]}"` scan matching `config-path ` and `^binding-hash ...$` independently of index); `tests/check-binding/run.sh`'s `cb-lock-fields-reordered` case (a hand-built lock with the two fields swapped, proven to still verify).
- decision: no `HUP`/`INT`/`TERM` signal-trap machinery was ported into `bin/check-binding.sh`, unlike `bin/check-intent.sh`/`bin/check-refreeze-class.sh`'s convention.
  reason: two valid precedents exist in this repository and they disagree — `bin/check-intent.sh` and `bin/check-refreeze-class.sh` install classified signal traps; `bin/check-durability.sh` (this task's own primary cited precedent, per DP1/DP2/DP6/DP9's direct citations and the spec's own "prior art to read" list naming it "in full") installs none. Since `bin/check-durability.sh` is the sibling this task's own design decisions are explicitly grounded against, and the "prior art to read" note cites `bin/check-intent.sh` narrowly for its normalize-then-hash pipeline (lines 284–410) rather than for its signal handling, this script follows the more directly-cited precedent's simpler shape rather than importing machinery from a script cited for an unrelated reason. This affects observable behavior only under signal delivery mid-run (untested by any acceptance criterion), not the normal refusal contract.
  grounding: `.shell-team/specs/T-1054-binding-config.md` `## Summarized sources` (`bin/check-durability.sh — primary, header and resolver section read` — cited for DP1/DP2/DP6/DP9) and `## Notes for engineer` ("Prior art to read before starting: `bin/check-durability.sh` in full ... `bin/check-intent.sh` lines 284–410"); `bin/check-durability.sh` (no `trap ... HUP|INT|TERM` anywhere in the file, confirmed by reading it in full).
