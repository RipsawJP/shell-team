- decision: the never-stealing lock is a single, fixed-name directory (`land-worktree.lock`) under the absolutized shared git directory, not parameterized by `--onto` (one lock per repository, not one per coordinator branch).
  reason: D3 states the lock's location and never-steal contract but names no per-branch scoping requirement, and the Goal describes "a single serializing coordinator" (singular) rather than N independent per-branch coordinators; a fixed name is the simplest reading that satisfies every frozen criterion, and a caller landing onto two different coordinator branches concurrently is exactly the kind of unscoped serialization D3's own "single serializing coordinator" framing anticipates rather than forbids.
  grounding: .shell-team/specs/T-1077-worktree-reconcile.md D3 ("the lock's location is decided against a measured constraint... under the shared git directory") and the Goal's own "a single serializing coordinator"; bin/land-worktree.sh's `LOCK_DIR="$GCD/land-worktree.lock"` line.
- decision: chose whole-second `sleep 1` retry granularity for the lock's bounded-wait polling loop (mirroring `bin/log-run.sh`), rather than adopting the fractional `sleep 0.1` this session measured to work on this host.
  reason: the Assumptions section states the measured fractional-sleep availability "widens the engineer's choice... without obliging it," and whole-second polling is simpler, needs no portability measurement of an adopter's own `/bin/sh`, and is sufficient for the default 10s bound and for every fixture's own timing assertion (`lock-timeout-refusal` only requires the refusal to land within roughly the bound, not on a sub-second cadence).
  grounding: .shell-team/specs/T-1077-worktree-reconcile.md Assumptions ("MEASURED BY THE FREEZE RUN... fractional sleep works... widens the engineer's choice... without obliging it"); bin/land-worktree.sh's lock acquire loop comment ("Whole-second retry granularity... matches bin/log-run.sh's own chosen portability bound").

- decision: absolutize both the coordinator's own shared-git-directory path and a `--worker-tree`'s shared-git-directory path with `cd ... && pwd -P` (physical, symlink-resolved), rather than plain `pwd` (logical).
  reason: measured live, this session, on this host (macOS, where `/tmp` is a symlink to `/private/tmp`): a repository reached through a path that traverses that symlink resolves `git rev-parse --git-common-dir` to a RELATIVE path, which `cd ... && pwd` (logical) then re-expands back through the SAME symlinked form, while a linked worktree created via `git worktree add` records its OWN git-common-dir as git's already-canonicalized (physical) absolute path — the two strings differ for the identical directory, and a plain string-equality identity check (`--worker-tree is a worktree of this repository`) false-refuses a perfectly ordinary linked worktree. `pwd -P` resolves both sides through the same physical form, closing the mismatch at its root rather than working around it with a looser comparison.
  grounding: bin/land-worktree.sh's GCD and WT_GCD resolution blocks and their header comments (the `pwd -P` calls and the stated symlink reasoning); reproduced live via a standalone debug harness before the fix (`--worker-tree is not a worktree of this repository` on an unmodified worktree) and confirmed closed after it (the `diverged-worker-tree-dirty` fixture correctly reaches its own `diverged` refusal instead).
- decision: derived each claim set's directory-prefix overlap test (D7b) via a pure substring/length comparison (`${b:0:${#a}}` plus a following `/` check) rather than a bash `case "$b" in "$a"/*) ... esac` glob pattern.
  reason: interpolating a real (adversarial) path into a `case` pattern's literal position would let any glob metacharacter the path itself contains (`*`, `?`, `[`) be reinterpreted as a wildcard rather than matched literally, which a length-bounded substring compare never does; this closes a class of adversarial-path mismatch the Input space's own space/tab/newline classes make plausible, even though no single named fixture forces exactly this character.
  grounding: bin/land-worktree.sh's `is_prefix` function and its header comment; `.shell-team/specs/T-1077-worktree-reconcile.md` Input space class 2 ("Paths carrying a space, a tab or a newline... producible by an ordinary editor or a generated file").
- decision: resolved each changed path's tree entry via `git ls-tree -z <tree> -- ':(literal)'"$path"'` (the `:(literal)` pathspec magic) rather than a bare `-- "$path"` pathspec.
  reason: a bare pathspec argument is subject to git's own glob-pathspec magic by default, so a real filename containing `*`/`?`/`[` would be silently reinterpreted as a wildcard rather than matched exactly — `:(literal)` disables that interpretation unconditionally, which is the composition step's only path-resolution call and therefore the one place this class of mismatch could silently corrupt a landing.
  grounding: bin/land-worktree.sh's composition loop (the `git ls-tree -z "$W" -- ":(literal)$p"` call); git's own documented pathspec-magic default (`man gitglossary`, `pathspec`).

- decision: (round 2, Codex review round 1 Blocker — Finding 1, entry-type-unaware composition) rewrote the composition loop as a two-pass, entry-type-aware procedure — pass 1 removes every claimed path that is absent OR resolves to a TREE at the worker tip; pass 2 adds every claimed path that resolves to a blob/symlink — rather than the original single interleaved pass that staged whatever `ls-tree` returned without checking its type.
  reason: Codex's own live reproduction showed the interleaved, order-dependent single pass corrupts the tree silently (exit 0) composing file->directory (the old leaf's now-wrong TREE-typed `ls-tree` result was staged via `--cacheinfo` as if it were a blob) and refuses with the wrong D6 class composing directory->file (`update-index --add` failing on a stale sibling entry that hadn't been removed yet, depending on which path git's diff happened to list first). Input space item 5 declares directory<->file replacement a REACHABLE class this mechanism must compose correctly, not merely fail closed on — the frozen D5 text is the contract, and the fix therefore had to change the composition METHOD (as the spec's own Notes for engineer anticipate — "if `update-index --cacheinfo` cannot express a cell, change the composition method... rather than narrowing the guarantee"), not add a narrower guard. Running every removal (for the WHOLE claim set) before any addition is what makes the result order-independent: `git diff --name-only` always reports a directory<->file replacement as two separate leaf-path entries (the disappearing old leaf, the appearing new leaf), and passing over the FULL claim set once for removals and once for additions — rather than interleaving remove/add per path in array order — means neither direction depends on which of the two entries git happened to list first. Verified live, both directions, in throwaway scratch repos (not merely the new suite fixtures): file->directory now lands with `git ls-tree -r onto` showing exactly one entry (`x/y`, no stray `x` blob, no `xy` phantom); directory->file now lands with exactly one entry (`x`, a blob, `x/y` gone) — both previously either corrupted or refused.
