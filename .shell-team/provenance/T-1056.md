# T-1056 decision provenance

- decision: an inability to resolve the shared path resolver next to `bin/check-liveness.sh` (the sibling missing/unreadable, or the resolver itself failing a `--get` call) is refused with the `usage` token, and an inability to resolve the templates directory one level above the script's own installed location (used only when loading the reason registry) is refused with `registry-unreadable`, rather than either being folded into a distinct new refusal token.
  reason: the spec's closed 19-token refusal vocabulary (`## Refusal reason tokens`) has no dedicated entry for "cannot resolve a sibling script" or "cannot resolve the templates root above this script" — both are untested corners (no `- check:` line drives the resolver or the bootstrap itself to fail). Two existing tokens are semantically closest: `usage` ("absent, unknown, conflicting or partially-supplied arguments") already covers "the invocation cannot be honored" in this repository's sibling checkers' own convention (`bin/check-durability.sh`'s `fail_structural`/`fail_usage` split collapses to `usage` in scripts with a flatter vocabulary), and `registry-unreadable` ("the shipped reason registry cannot be read from the script's own installed directory") already names exactly the templates-root-then-registry-file resolution path DP3 describes. Splitting sibling-resolver failure into `usage` (an installation/invocation-environment problem, not a data-input problem) and templates-root failure into `registry-unreadable` (since the only caller of that resolution is the registry loader) keeps every refusal inside the closed set without inventing a 20th token for a corner no criterion reaches.
  grounding: `.shell-team/specs/T-1056-loop-liveness.md` `## Refusal reason tokens` (the closed 19-token table, and the absence of a dedicated sibling/templates-root token); `bin/check-durability.sh`'s `fail_structural`/`get_path` resolution pattern (the precedent this classifier's `resolve_team_paths`/`get_path`/`load_reason_registry` functions in `bin/check-liveness.sh` follow).
- decision: a human-gate declaration's `task` field is required to exist exactly once and be non-empty (a structural presence check), but its VALUE is never cross-checked against the invoking `--task` argument or against any field the state file carries.
  reason: DP3 states the declaration carries "one each of `task`, `reason`, `run-epoch` and `declared-epoch`" but names no cross-check on `task`'s value — the only run-identity check DP3/AC6 specify is `run-epoch` against the state file's `start_epoch` (`declaration-foreign-run`). No acceptance criterion mutates or asserts on the `task` field's VALUE (AC6's declaration-defect table has no `task`-value-mismatch row), only on its presence/absence/duplication (folded into `declaration-malformed`). Adding an unrequested cross-check would be scope creep past what DP3/AC6 actually specify, and — since `--task` mode already composes both paths from the same task id that would appear in the declaration's own `task` field — a mismatch there is definitionally unreachable in that mode; a direct `--state`/`--declaration` invocation with a deliberately mismatched `task` value is a hostile-input shape this spec's own `## Input space` "out-of-scope synthetic extremes" section declines to protect against (a hostile operator hand-forging a declaration).
  grounding: `.shell-team/specs/T-1056-loop-liveness.md` DP3 ("one each of `task`, `reason`, `run-epoch` and `declared-epoch`") and AC6 (the declaration-defect table's condition list, which names no `task`-value check) and `## Input space`'s "A hostile operator" out-of-scope bullet; `bin/check-liveness.sh`'s `parse_declaration` function (the `DECL_TASK` field is parsed and required present, never compared to `$TASK`).
- decision: the four required declaration field lines (`task`, `reason`, `run-epoch`, `declared-epoch`) are accepted in ANY order relative to each other between the version line and the terminator — the parser is order-independent among them, not fixed to the sequence DP3's prose lists them in.
  reason: DP3's own prose lists the four fields in a fixed sequence, but neither DP3 nor AC6's mutation table asserts an ORDER requirement — every AC6 mutation targets a field's presence, duplication or value, never its position relative to a sibling field. Requiring a fixed order would be an unrequested additional constraint on the accepted grammar that no criterion tests for and that DP3's own wording ("one each of…") reads as a set requirement, not a sequence requirement — the declaration-write choke point (this task's own canonical prompt block) does not commit to writing them in one particular order either. Order-independence is the more permissive, meaning-preserving reading of "one each of" and costs nothing to implement (the parser already loops over the middle lines classifying each by its own key).
  grounding: `.shell-team/specs/T-1056-loop-liveness.md` DP3 ("one each of `task`, `reason`, `run-epoch` and `declared-epoch`" — a set phrasing) and AC6 (no order-dependent mutation case); `bin/check-liveness.sh`'s `parse_declaration` function (the `for ((i = 1; i < n - 1; i++))` loop classifies each middle line by its own `key`, independent of position).
- decision: the computed derived quantities `A_STATE` (now minus the state file's mtime) and `A_GIT` (now minus `HEAD`'s committer epoch) are checked for non-negativity only — never additionally width-bounded against a `^[0-9]{1,9}$`-shaped regex the way every FIELD READ FROM AN EXTERNAL SOURCE (an epoch, a threshold) is.
  reason: DP5 states "every threshold and age `^[0-9]{1,9}$`" as part of the width-bound-then-`10#`-normalize discipline, which read literally could be taken to include these two DERIVED quantities. But DP5's own stated purpose for that discipline is protecting arithmetic performed on a value READ from a file, flag or environment variable, where a leading zero could be misread as octal by an unguarded `((...))` — a hazard that applies to a raw string being cast into arithmetic, not to a value ALREADY produced by prior arithmetic on two already-normalized 10#-cast operands (which bash's own `$((...))` never re-parses as a string). Regex-validating `A_STATE`/`A_GIT` after computing them would also risk a real false rejection: AC9's own fixture for the one `S2`×`G0` cell a fresh file cannot reach backdates a state file to the year 2000, which against this repository's own age (its earliest commits post-date that) already produces an age within a few million seconds of the 9-digit boundary, and any future clock difference could push a wholly legitimate `STALLED`/`DEAD` fixture across a self-imposed 9-digit ceiling that has no basis in the spec's own boundary tests (AC8's boundary proofs are all in the hundreds-to-thousands-of-seconds range, never near `10^9`). Non-negativity is what DP2/DP5 actually gate verdicts on (`clock-skew`); a width ceiling on a derived age is not one of the closed 19 tokens' conditions.
  grounding: `.shell-team/specs/T-1056-loop-liveness.md` DP5 ("every epoch is width-bounded... and every threshold and age... each normalized with `10#` immediately after its bound proves it a bounded digit string") and AC9 (the back-dated-to-2000 `S2`×`G0` fixture, and its own precondition assertion that the gap exceed one year) and `## Refusal reason tokens` (`clock-skew`'s condition is "now earlier than..." — non-negativity, not a width ceiling); `bin/check-liveness.sh`'s `A_STATE`/`A_GIT` computation sites (`[ "$A_STATE" -ge 0 ] || refuse clock-skew ...`, no regex re-validation after computing).
- decision: `tests/check-liveness/run.sh` builds no `git init` scratch repository anywhere; every git-band case (`STALLED` via a stale state file against a live `HEAD`, `DEAD` via both clocks stale) instead measures this checkout's OWN real `HEAD` committer epoch live, at run time, and derives `$LIVENESS_NOW` relative to it.
  reason: the spec's own `## Notes for engineer` suggests this suite "should" build a scratch git repository, since "the `S2`×`G0` matrix cell and the `G0` band generally are cleanest to reach with a scratch repository carrying a fresh commit." But this repository's own `.shell-team/test-recipe.md` (the T-1001 entry, restated and extended by the T-1044 entry) documents a real, previously-hit sandbox restriction: a fixture suite that creates a real `git init` repository under this checkout's own working tree fails with "Operation not permitted" copying `.git/`'s hook templates in a sandboxed run. Since `$LIVENESS_NOW` is fully overridable and the classifier's own `git log -1 --format=%ct HEAD` call resolves against whatever directory the classifier is invoked from, measuring THIS checkout's real, already-existing `HEAD` epoch live (`git -C "$REPO_ROOT" log -1 --format=%ct HEAD`, captured fresh at suite-run time rather than hardcoded) and computing `$LIVENESS_NOW` as an offset from it reaches the identical `S2`×`G0` and `S2`×`G1` cells a scratch repository would, with strictly less fixture machinery and none of the sandboxed-git-init fragility. This is a deliberate, disclosed departure from the spec's own suggestion (not a requirement — the spec says "should", not "must"), verified live: the suite's own precondition assertion (`[ "$((HC - OM))" -gt 31536000 ]`) proves the measured gap is genuinely in the dead band before either cell is judged.
  grounding: `.shell-team/specs/T-1056-loop-liveness.md` `## Notes for engineer` ("this suite does not build `git init` repos under it for the frozen criteria — but the suite itself should"); `.shell-team/test-recipe.md`'s T-1001 entry ("must NOT create it under `$HERE/tmp` inside this repo's own working tree — the sandbox denies writes to a NESTED `.git/`") and T-1044 entry (the same restriction restated for the choice between a `$TMPDIR`-only root and a `$HERE`-fallback root); `tests/check-liveness/run.sh`'s `cl-stalled-s2g0`/`cl-dead-s2g1` cases and their shared precondition assertion.
- decision: the `--out` verdict document's `reason` line reads `none` for an absent declaration and `superseded` for a superseded one on every ladder verdict (`RUNNING`/`STALLED`/`DEAD`), rather than always writing a fixed placeholder or omitting context for the non-`WAITING` verdicts.
  reason: AC11 only pins the `--out` document's STRUCTURAL shape (a `reason` line must exist, matching `^reason `) and never asserts its VALUE for a ladder verdict — its own fixtures write `--out` only alongside a fresh declaration (`WAITING`) and alongside an absent one (`STALLED`), and check the `reason` key's presence, not its content, in the latter case. Since DP3 already treats a superseded declaration as "context printed on stderr beside a ladder verdict, not a refusal," carrying that same context into the `--out` document's own `reason` line (rather than a generic `none` that would erase the distinction between "no declaration ever existed" and "one existed but its wait had already ended") keeps the document genuinely self-describing, matching DP9's stated goal ("a self-describing verdict document"), at no cost since the value was already computed for the stderr write.
  grounding: `.shell-team/specs/T-1056-loop-liveness.md` AC11 (the `--out` shape clauses: `grep -qE "^$k "` for `reason`/`state-age`/`git-age`, never a value assertion) and DP3 ("a superseded declaration is therefore not an error — it is an uncleaned file whose wait provably ended") and DP9 ("a self-describing verdict document"); `bin/check-liveness.sh`'s `DECL_CTX` variable (set to `superseded` or `none` before every `emit_final RUNNING|STALLED|DEAD` call, and passed through to `write_out`'s `reason` parameter).
- decision: the `--out` write's `write_out` function refuses (`out-unwritable`) when the target's parent directory does not already exist, rather than creating it (`mkdir -p`) on the classifier's behalf.
  reason: DP9 describes `--out`'s write as "a self-describing verdict document... composed in a guarded `mktemp` sibling and moved into place" — it does not say the classifier may create directories, and the Goal sentence's scope list is explicit that this script "writes nothing except an optional `--out` verdict file": creating a parent directory is an additional filesystem side effect beyond writing the one named file, and AC11's own no-`--out` case proves the classifier must leave an empty scratch directory in exactly the state it found it. A caller (the external timer this script does not ship) that wants `--out` under a directory that does not yet exist is expected to create it once, the same way any other CLI tool that writes to `--out PATH` assumes the parent exists; refusing rather than silently creating a directory tree is also the more fail-closed reading when the intended parent turns out to be a typo'd path.
  grounding: `.shell-team/specs/T-1056-loop-liveness.md` Goal ("writes nothing except an optional `--out` verdict file") and DP9 ("the classifier creates nothing at all" with no `--out`) and AC11 (the empty-scratch-dir-stays-empty clause); `bin/check-liveness.sh`'s `write_out` function (`[ -d "$outdir" ] || return 1`, no `mkdir -p`).
