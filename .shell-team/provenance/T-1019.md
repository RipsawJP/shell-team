- decision: `assert_parity()` structures each of the six classes as THREE separate assertions — the frozen expected answer checked against `bin/rollup-runs.sh` alone, the same frozen answer checked against `bin/cluster-failures.sh` alone, and a third comparison of the two consumers' own classifications against each other — via two small `classify_rollup`/`classify_cluster` helpers that reduce each consumer's raw stdout to one of `counted`/`skipped`/`other`, rather than a single combined check per fixture that inspects both consumers' raw stdout inline.
  reason: two structurally valid designs existed. (a) One combined check per fixture: grep both scripts' raw stdout directly for the two frozen substrings/sentinels in one code block, with no intermediate classification step. (b) Reduce each consumer's stdout to a three-value classification first, then compare that value both against the frozen expected answer and against the sibling consumer's classification. (b) was chosen because the Goal explicitly requires the per-class judgment to be made twice — "once per consumer against the frozen expected answer, and once as a parity comparison between the two consumers" — and D5 additionally requires an unexpected observation (neither counted nor skipped) to be treated as a failure of that consumer rather than a silent skip. A three-value classification makes the parity comparison a plain string-equality check independent of the oracle comparison, so the two required assertions (oracle-match, cross-consumer parity) are genuinely separate code paths rather than one grep incidentally implying the other, and an "other" observation flows through the same equality check as counted/skipped without a bespoke branch.
  grounding: .shell-team/specs/T-1019-is-span-row-parity.md Goal ("every class's classification is asserted twice: once per consumer against the frozen expected answer, and once as a parity comparison between the two consumers") and D5 ("An observation that is neither counted nor skipped ... is a failure of that consumer ... never a skip"); tests/is-span-row-parity/run.sh, the `classify_rollup`/`classify_cluster`/`assert_parity` functions.

- decision: the five `kind-*` fixtures' base probe row is written as the minimal three-key object `{"run_id":"RUN-ISR-PARITY","status":"error","phase":"implement"}` (plus the `kind` field where applicable), rather than a full 17-key row matching `bin/log-run.sh`'s real span-row shape for every field.
  reason: two structurally valid fixture designs existed. (a) Give all five `kind-*` files the same full real-shaped payload `valid-span.jsonl` already carries (every schema key present), differing only in the `kind` field. (b) Give them a minimal row carrying only the fields the two consumers' extractors actually read (`run_id`, `status`, `phase`) plus the `kind` field under test. (b) was chosen because D4 itself declares `valid-span.jsonl` as sitting "outside that family on purpose: it is the realism control" — the full-shape coverage is `valid-span.jsonl`'s job specifically, not the five `kind-*` files' job, whose stated purpose is that "a classification difference is attributable to the `kind` field alone." A minimal shared base keeps the five files' only-varying content to exactly the `kind` field, matching AC1's mechanical delete-`kind`-and-compare check with no incidental noise from unrelated fields, and avoids six files that would need to be kept byte-identical across 16 non-`kind` keys instead of 3.
  grounding: .shell-team/specs/T-1019-is-span-row-parity.md D4 ("`valid-span.jsonl` sits outside that family on purpose... proving the harness reports `counted` for a genuine row and not only for a stripped-down probe") and "Everything except the `kind` field is well-formed and identical across the five `kind-*` files"; tests/is-span-row-parity/fixtures/kind-absent.jsonl through kind-malformed.jsonl.

- decision: the suite file's header comment describes D3's black-box constraint as "never any dynamic command construction" rather than the more direct, and originally drafted, "never `eval`".
  reason: the drafted wording contained the literal token `eval` bounded by non-alphanumeric characters (a backtick before, a period after), which is exactly the shape AC9's negative lock scans for — `bash -c` (the invocation `bin/check-acs.sh` and CI both actually use) runs the check against the file with the host's real `grep`/`bash`, unlike an interactive shell session where a `grep` wrapper function can mask the match; the two environments gave different answers for the identical command, and the `bash -c` answer is the authoritative one since that is what actually gates AC9. Two fixes existed: (a) keep the sentence and manually verify AC9 continues to pass, since the checker's own comment says its scope is "the whole file" so a match anywhere is a genuine failure, not a false positive to special-case; or (b) reword the comment to drop the literal token while preserving the documented intent (no dynamic command evaluation of any kind). (b) was chosen — the token itself is what AC9 is designed to catch, and the design intent (documenting that no extraction-then-evaluate path exists) does not require spelling the forbidden mechanism's name.
  grounding: .shell-team/specs/T-1019-is-span-row-parity.md AC9 ("the suite contains no `eval` ... check: ... grep -qE '(^|[^[:alnum:]_])eval([^[:alnum:]_]|$)' \"$S\""); tests/is-span-row-parity/run.sh, the D3 header comment, before/after this correction (measured live via `bash -c 'grep -qE ... tests/is-span-row-parity/run.sh'`, which failed before the wording change and passes after).
