# T-1076 decision provenance

<!-- BEGIN provenance: T-1076 -->
- decision: split the contention suite's two arms so only the AC10 negative control carries the 16384+-byte `--error` payload, while the AC9 positive/main 8x20 arm carries no `--error` value at all (both arms share the same N=8/M=20 writer/row floors, and the single printed `contention-parameters` line reports `payload_bytes=16384` — the value the negative control actually uses — rather than a value the positive arm also carries).
  reason: measured live (this session, this repo's own stock bash 3.2.57 dev host) that `bin/check-run.sh`'s own unbalanced-quote detection (`unq="${line//\\\\/}"; unq="${unq//\\\"/}"; quotes="${unq//[!\"]/}"`) exhibits a severe super-quadratic slowdown once a JSON string field passes a few kilobytes — direct isolated benchmarks of that exact substitution chain: 500B→0.03s, 1000B→0.13s, 2000B→0.82s, 4000B→5.7s (third stage) / 8000B→20s (second stage, tested separately), 16384B→did not complete within 120s. `bin/check-run.sh` is Non-goal'd (must stay byte-identical to its branch-point blob, AC13/AC15) so this cannot be fixed here. D6's own text scopes the multi-kilobyte payload requirement to the negative control's own sentence ("run at the same or higher concurrency with multi-kilobyte --error payloads"), not to the main case, so keeping the positive arm's rows small is a reading the frozen text itself supports, and it is what keeps `bin/check-run.sh bash tests/log-run/run.sh`'s `contention-check-run-clean` assertion computationally tractable (the positive arm's file is the one actually linted for that assertion). The negative control's own detection logic never invokes `bin/check-run.sh` at all (line count + derived seq-set exactness only), for the identical reason.
  grounding: bin/check-run.sh:205-207 (the three-stage unbalanced-quote substitution); `.shell-team/specs/T-1076-log-run-locking.md` D6 ("run at the same or higher concurrency with multi-kilobyte --error payloads (at least 16384 bytes)"); `.shell-team/test-recipe.md`'s T-1076 entry (the measured benchmark numbers, recorded there for the next task that touches this writer or its readers).
- decision: gave INT/TERM their own `on_lock_signal` handler that calls `exit "$2"` explicitly (mirroring `bin/check-intent.sh`'s and `bin/check-refreeze-class.sh`'s existing `on_signal` shape), rather than a single combined `trap release_lock EXIT INT TERM`.
  reason: measured live that the combined-trap form is a real, reproducible bug, not a style preference — bash's own documented trap semantics mean a caught INT/TERM signal that does not call `exit` inside its handler only RUNS the handler and then RESUMES the script from where it was interrupted; a `sleep 5` injected right after lock acquisition (this task's own `lock-released-on-signal` fixture) proved this directly: with the combined-trap form, `kill -TERM` on the holder released the lock immediately (correct) but the script then continued past the interrupted `sleep`, computed `--seq auto` and appended a row anyway — the fixture's own "the killed holder should not have appended a row" assertion caught it on the first run, before the fix.
  grounding: bin/log-run.sh's `on_lock_signal` function and its `trap 'on_lock_signal INT 130' INT` / `trap 'on_lock_signal TERM 143' TERM` lines; `bin/check-intent.sh:198-204` and `bin/check-refreeze-class.sh:133-139` (the pre-existing repo convention this reuses); `tests/log-run/run.sh`'s `lock-released-on-signal` case (the fixture whose failure, before this fix, is what surfaced the bug).
- decision: `TEAM_LOG_LOCK_TIMEOUT` follows `bin/check-acs.sh`'s own `CHECK_ACS_TIMEOUT` shape exactly — an UNSET value is substituted with the default via `${VAR:-10}` before validation ever runs (silent, no warning), while a PRESENT value that fails validation (non-integer, zero, or negative) falls back to the same default but additionally warns on stderr naming the variable — rather than warning on every invocation that simply never sets the variable at all (which D2's own prose, read most literally, could be taken to require, since it lists "absent" alongside "non-integer, zero or negative" as values that "fall back... and emit a warning").
  reason: D2 itself names `bin/check-acs.sh`'s own shape as the model to follow ("following the same shape bin/check-acs.sh already uses for CHECK_ACS_TIMEOUT"), and that script's own `acs_timeout="${CHECK_ACS_TIMEOUT:-120}"` line conflates "absent" with "already the default" before its validation `case` ever runs, so an absent value never reaches the warning branch there either; matching that precedent literally means an ordinary invocation that never sets `TEAM_LOG_LOCK_TIMEOUT` (which is every invocation in this repository today — no caller sets it) does not print a stderr line on every single append. No `- check:` line in the frozen spec asserts silence on the absent case one way or the other, so this is a genuine implementation choice between two readings of one prose sentence, resolved in favor of the shape the sentence itself names as the model.
  grounding: `.shell-team/specs/T-1076-log-run-locking.md` D2 ("following the same shape bin/check-acs.sh already uses for CHECK_ACS_TIMEOUT"); `bin/check-acs.sh`'s `acs_timeout="${CHECK_ACS_TIMEOUT:-120}"` line and its adjacent invalid-value `case` block.
- decision: chose whole-second `sleep 1` retry granularity for the lock's bounded-wait polling loop, rather than measuring and adopting a fractional-second granularity.
  reason: D2 explicitly leaves this as the engineer's choice ("the engineer either measures that it works and records the measurement, or uses whole-second steps"); whole seconds are simpler, need no portability measurement of this repo's own `/bin/sh` or of an adopter's, and are sufficient for the acceptance criteria's own bounds (AC6 requires only that a `TEAM_LOG_LOCK_TIMEOUT=1` refusal return within 10 wall-clock seconds, which whole-second polling satisfies with room to spare). Measured separately, for the record only (not load-bearing for this choice): fractional `sleep 0.2` does work on this session's own sandboxed bash 3.2.57, but the choice was made for portability toward an unknown adopter host, not because fractional sleep was unavailable here.
  grounding: `.shell-team/specs/T-1076-log-run-locking.md` D2 ("Retry granularity is measured on the host, not assumed... the engineer either measures that it works and records the measurement, or uses whole-second steps"); `.shell-team/test-recipe.md`'s T-1076 entry (records the fractional-sleep measurement and the whole-second choice together).
