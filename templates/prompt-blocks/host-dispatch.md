**Two hosts, one dispatch decision (T-1134).** This loop's Specify → Implement → Validate chain runs from either of two hosts: a **Claude Code** session, using the Claude Code Agent tool to dispatch each bound role in-process, or a **Codex CLI** session, using Codex's own `spawn_agent` tool to dispatch a generated Codex custom agent for that role. Both hosts read the identical `agents/<role>.md` prose — the Claude Code host through the Agent tool's own role-file read, the Codex CLI host through a Codex custom agent `bin/gen-codex-agents.sh` derives from that same file, byte-identical after its frontmatter — so this file's own dispatch instructions state the host-conditional mechanism rather than assuming the Claude Code Agent tool unconditionally.

On the **Claude Code** host: dispatch a bound role with the Claude Code Agent tool, exactly as the numbered phase list above and the Executor resolution paragraph already do — nothing about that dispatch changes because this paragraph exists.

On the **Codex CLI** host: dispatch a bound role by spawning its generated Codex custom agent — named `shell-team-<role>`, discovered from `<repo>/.codex/agents/` only when the repository is Codex-trusted — with Codex's own `spawn_agent` tool, never with the Claude Code Agent tool, which this host does not have. Slice 1 (T-1134) wired the `pm-spec` → `engineer` → `qa-verifier` chain (plus `tech-lead`) to `READY_FOR_REVIEW` this way; slice 2 (T-1135) adds `codex-reviewer` as a fifth generated role and dispatches it the same way, closing the remaining gap by running its review on Claude instead of Codex — see the paragraph below for that recipe — so a Codex CLI run of this loop now reaches `READY_FOR_MERGE`, both gates green. Before starting a Codex CLI session in which a dispatched role — `engineer` in particular — is expected to commit, grant the parent session's sandbox write access to `.git` (measured: `codex exec --sandbox workspace-write` otherwise refuses every write under `.git/`, `Operation not permitted`, exit 128) — see `docs/adopting.md`'s "Using shell-team from Codex CLI" section for the exact invocation. The same sandbox refuses creating or writing `.codex/` itself, which blocks Codex from running `bin/gen-codex-agents.sh` inside the session rather than from your own shell (the default path) — that same docs section names the writable-roots form covering `.codex` too, for when Codex must run it in-session. `bin/check-codex-agents.sh` never creates or writes `--out-dir` — it only reads it to compare against a scratch regeneration — so it needs no such grant, in-session or not.

**The review step, on the Codex CLI host (T-1135).** `codex-reviewer` is generated and spawned exactly like the other four roles — same `spawn_agent` dispatch, same unmodified `agents/codex-reviewer.md` prose — but reviewing through Codex again would not carry the cross-provider property this role exists for, since Codex is already the host. So when the spawned `shell-team-codex-reviewer` agent reaches its review pass, it runs a single `claude -p` invocation instead of its file's own `codex exec` block, reading the same `<repo>` root and the same review scope the Codex path already resolves:

claude -p "<PROMPT>" --output-format stream-json --verbose --no-session-persistence --permission-mode dontAsk --setting-sources "" --strict-mcp-config --tools Read Grep Glob Bash --allowedTools "Bash(git diff:*)" "Bash(git log:*)" "Bash(git rev-parse:*)" --disallowedTools Write,Edit,NotebookEdit < /dev/null

`<PROMPT>` is the review instruction, substituted as a literal string exactly like `<RAW_OUT>`/`<RAW_JSONL>` below, and it MUST be placed immediately after `-p` — before every flag — never appended at the end of the line. Measured: `--tools`, `--allowedTools` and `--disallowedTools` each take a variadic list of following tokens, so a prompt placed after them (or last on the line, with nothing to stop the list) is silently swallowed into that flag's own value list instead of being read as the prompt, and the invocation then refuses with `Input must be provided either through stdin or as a prompt argument when using --print` even though a prompt was in fact supplied. Every flag's effect below is the measured one (Claude Code CLI 2.1.268, three live probes recorded in `.shell-team/provenance/T-1135.md`), not one inferred from `--help` text — an earlier shape of this line rested on the latter and was measured wrong before this one shipped. `--tools` names the built-in tool set the pass may use at all — `Read Grep Glob Bash`, which is where `Bash` is granted in the first place, and which excludes the Agent tool, `Write`, `Edit` and `NotebookEdit` by simply never naming them. `--allowedTools "Bash(git diff:*)" "Bash(git log:*)" "Bash(git rev-parse:*)"` is the git-only permission-rule allowlist that narrows `Bash` itself to those three subcommands; `--allowedTools` alone does **not** deny every other `Bash` call — measured: with `--allowedTools` present but no permission mode set, an unlisted `Bash` call still ran, because the adopter's own permission-mode setting decided it. `--permission-mode dontAsk` is what turns any tool call outside that allowlist into a harness denial instead — measured: the identical unlisted `Bash` call was refused under this mode, with the refusal recorded in the run's own `permission_denials` field, and this is the actual read-only-confinement mechanism, not `--tools`/`--disallowedTools` alone. `--strict-mcp-config` excludes every MCP server from the adopter's own configuration — measured: without it, every one of the operator's claude.ai connector tools stayed exposed to the pass, GitHub `push_files`/`merge_pull_request`, Gmail send, Slack send and Jira/Confluence write among them, none of which `--tools` touches, since MCP tools are not part of its built-in vocabulary at all. `--setting-sources ""` excludes the adopter's own user, project and local settings files from loading (the counterpart of the Codex recipe's `--ignore-user-config --ignore-rules --ephemeral`). `< /dev/null` closes stdin so the pass never waits on it. `--no-session-persistence` leaves no session state behind. **No `--model` is composed on this path** — the reviewer's model is whatever the host's own Claude Code installation is configured for, `provider-configured`-honest exactly as the shipped binding's Codex-path row already is; #431 remains the issue for the binding-row grammar. Disclosed rather than engineered around: Claude Code's own sandbox layer can fail to initialize when this invocation itself runs inside a Codex sandbox (`Sandbox is enabled but failed to initialize … Sandboxing is disabled for the rest of this session`, measured on this host) — the permission-mode/allowlist/strict-MCP combination above is the confinement this recipe actually relies on, never that inner sandbox, so its failure to initialize changes nothing about what confines this pass. Capture reuses the unmodified `codex-capture.sh` the Codex path already calls: `codex-capture.sh --alloc --stem <stem>` prints the `.out` and `.jsonl` raw paths, the `claude -p` invocation's stdout is redirected into the `.jsonl` raw, the `.out` raw is filled from that same file's own final `"type"`-carrying event line, and `codex-capture.sh --publish --stem <stem> --publish-out "<RAW_OUT>" --publish-jsonl "<RAW_JSONL>"` validates and publishes the pair — exactly the alloc/run/publish shape the Codex read paths already follow. A non-zero exit from `claude` is handled exactly as a non-zero exit from `codex` already is: diagnose, cleanup, skip publish, report `BLOCKED` with the exact error — the network-refused `Not logged in` symptom (see `docs/adopting.md`'s "Using shell-team from Codex CLI" section) is the one this path is measured to actually produce at the sandbox's default network setting.

**Recording the reviewer's span (T-1135).** Log this pass with `bin/log-run.sh`, filling its span flags from the same Claude JSON result the `stream-json` capture's final event line already carries: `--tokens` from that result's `usage` field, `--duration-ms` from its `duration_ms` field, `--usd` from its `total_cost_usd` field, `--provider claude` — because the span records the executor that actually ran, not the role's historical `codex-reviewer` name — and `--adapter claude-cli`. `--model` stays `provider-configured`, matching the no-`--model`-composed choice above.

Three mechanisms named elsewhere in this file have **no Codex CLI counterpart in this slice**, and are Claude-Code-host mechanisms only: the `isolation: worktree` Agent-invocation parameter (the Claude Code Agent tool's own isolation control), the `<usage>` block an Agent tool result carries (Codex CLI's own telemetry surface is its `--json` event stream, read differently), and the alternate-executor invocation recipe (T-1118) as a whole — its parent process IS the Codex CLI on that host, so there is nothing left for it to dispatch *into*. The `in-process` admission token used elsewhere in this file names the host's own in-process sub-agent dispatch, whichever host is running: the Claude Code Agent tool on a Claude Code host, a spawned Codex custom agent on a Codex CLI host.
