**The admissibility gate, `bin/check-invocation-path.sh --role <role>`, answers exactly two questions and composes no argv, calls no provider and writes nothing:** whether a shipped recipe exists for this role's effective resolved adapter token, and whether this role's `role-board-authority` is admitted under that recipe's sandbox mode. A registered adapter token carrying no shipped `invocation-recipe` row refuses `no-recipe`; a shipped recipe that does not wire this role refuses `role-not-wired`; a wired role whose `role-board-authority` this recipe's `admits-authority` set does not carry refuses `authority-incompatible`. An unknown or unregistered adapter token never reaches this recipe lookup at all — resolution refuses it further upstream. Whatever the gate cannot evaluate at all is refused rather than guessed. Before the `wires-role` question, for a role whose resolved adapter's recipe is `sandbox-read-only`, the gate additionally derives admissibility from that role's own shipped definition rather than from this recipe's declarations: a role whose `agents/<role>.md` itself hosts a bare, first-token `codex exec ` call is a Claude-hosted wrapper — its write authority stays with that wrapper and the read-only recipe never receives it — and the gate admits it `wrapper-hosted`, naming the agent file it read, without widening `wires-role` or `admits-authority` for it.

**Run this gate immediately before invoking any bound role, and never invoke that role through any other path first** — the identical discipline the adjacent Executor resolution (T-1057) paragraph already states for `resolve-executor.sh`. Treat every refusal as a blocker that stops the phase and escalates to the human, quoting the refused token verbatim as `BLOCKED` on the board with the gate's exact stderr, and never substitute another executor for a role whose admissibility check refused. On exit `0`, dispatch on the admission token the gate's own stdout names — never on the resolved adapter's sandbox mode alone, since `wrapper-hosted` and `sandbox-read-only` share an adapter but not a dispatch shape: `in-process` — invoke the role with the Agent tool exactly as for any other bound role, nothing about this invocation changes; `wrapper-hosted` — invoke the role with the Agent tool exactly as for any other bound role, because that role's own `agents/<role>.md` already hosts the `codex exec` wrapper call itself and this recipe's read-only sandbox never receives its write; `sandbox-read-only` — do not invoke the role with the Agent tool at all, and instead run the dispatch procedure above. And at the invocation site, exactly as for any other bound role, an unavailable or unauthenticated executor is `BLOCKED` with the exact error and never a substitution.
