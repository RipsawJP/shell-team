## When the full loop fits (task aptitude)

**First branch — does the final verification surface close inside the loop?**

- **Closes inside the loop** (correctness is settled by *mechanical* verification — tests, lint, execution/output comparison): the full PM → Engineer → QA → Codex loop **fits**. QA and Codex can confirm the acceptance criteria empirically and statically, so a FAIL is caught inside the loop rather than after a human looks at the result.
- **Does not close inside the loop** (the final gate is *human visual inspection, a real renderer, or subjective evaluation* — e.g. slide/PDF layout, pixel-level UI polish, prose tone): the full loop is a **poor fit, or fits only in a limited way**. QA cannot substitute for the human eye, and the loop only surfaces the human visual gate at the very end, so a visual FAIL costs a whole round-trip and can churn the same code path for many rounds (observed in this loop's own history: 10+ rework rounds, final score 70/100).

**Provisional operation for visual-output tasks** (a stop-gap until a dedicated short-cycle / variant loop is built — roadmap #138): do **not** put such a task on a single full-loop pass. Instead run a short manual cycle (implement, render, human check) where the human views the real rendered output each turn; keep spec / QA in a supporting role rather than as the completion gate.

> This first branch is the same shape as the future v0.3.0 grounded-AI-evaluator's OOD-novelty / human-gate criterion (see docs/loop-engineering/v0.3.0-oversight-model-evolution.md §7): a verification surface that cannot be mechanically grounded escalates to a human, and the same signal will later feed that evaluator's decision.

**The execution host.** A mechanism-class fan-out — the `verify-mechanism` refinement's own population — runs as N harness-tracked background shell slices launched by the coordinating session over isolated staged worktrees, one base and one head per slice, and is never sub-agent-hosted: sub-agent hosting has zero completed runs on this population, couples every slice to one stall-prone parent as a single point of failure, and stays prohibited until a pilot measures it.

- **The grammar.** One indented sub-bullet per axis under the task's own top-level board entry, ` — ` (space, em dash, space) as the field separator: `- dispatch: <axis> — <value> — <unconditional|conditional> — <ground>`.
- `<axis>` is an axis key that some priced dispatcher note's own `- dispatch-axis:` line defines. Each axis key appears at most once per entry, and every axis any such note defines is recorded — so a later axis joins by adding its own key, never by reshaping this grammar.
- `<value>` is bound to that axis's own closed set: `implement` over `serial|tier2|tier3`, `verify` over `serial|tier1-fanout`, `verify-fixture` over `serial|tier1-fanout`, `verify-mechanism` over `serial|tier1-fanout`, `specify` over `pm-authored|operator-authored`, `spec-review` over `none|cross-provider`. A value belonging to another axis is a malformed record, not a routing choice.
- **Refinements (T-1100).** `verify-fixture` refines `verify`, and `verify-mechanism` does too: each is its own axis over the same closed set `serial|tier1-fanout`, priced and recorded independently so a task whose verification duty bundles a fixture-suite half (a small population sharing one temp root, run sequentially) with a mechanism-class full-population diff can record each half's own election instead of one election silently carrying both. An entry records **either** the parent `verify` key **or** one or more of its refinements, **never both** — `bin/close-out.sh` refuses an entry carrying the parent alongside a refinement, the same reason a repeated axis key is already refused. Whether a task whose work has both halves actually records both is an authoring duty in prose, not a gate: a single refinement with no sibling still validates.
- `<unconditional|conditional>` is the modality of the rule that was actually applied, taken from that axis's own rule line.
- `<ground>` opens with a priced line id that axis's own note already records — `saving: <id>`, `recommendation: <id>`, `break-even: <id>` or `cost-input: <id>` — optionally followed by explanatory text, so a routing choice cites a recorded price and never an invented one.
- An indented line whose first non-space characters are `- dispatch: ` is a record wherever it sits in the entry; prose that wants to mention this grammar quotes it mid-line instead of opening a line with it.
- **Validation.** `bin/close-out.sh` validates this record when it is present: every `- dispatch:` sub-bullet on the entry being closed must match the grammar above, and no axis key may appear twice, or the close-out refuses. An entry carrying none of them passes — presence is this norm's requirement, not the script's, so a board written before this record existed still closes out.
- **Cross-task dispatch reflection (T-1109).** Before transcribing the `- dispatch:` rows above, skim the immediately preceding task's own entry and record, per axis, whether this task repeats or diverges from what it elected: `- dispatch-reflection: <axis> — <predecessor> — <repeat|differs|no-predecessor-row> — <ground>`, one row per axis this entry itself records, written in the same window and before the `- dispatch:` rows themselves — so the skim informs the elections it is about, rather than rationalizing them afterward. Where the task has no predecessor at all, write the single line `- dispatch-reflection: all — no-predecessor — no-predecessor-row — <ground>` instead of one row per axis, and never both forms on one entry. `bin/check-entry-mode.sh` validates this family when it is present, the same validate-if-present shape as the `- dispatch:` family above: every axis this entry's own `- dispatch:` rows record must carry a matching reflection row, no axis key may appear twice, and a stated verdict must agree with the immediately preceding task's own recorded value for that axis — the predecessor resolved to exactly one top-level board entry in either `## Active` or `## Done`. An entry carrying no reflection line at all still passes.
- **Verification-avoidance rule (issue #399 part 1, T-1112).** Citing the same unverified precondition three or more times across dispatch reflections without ever discharging it is itself verification avoidance, and the recurring precondition becomes its own backlog item at that point rather than being cited a fourth time.
- **Corrected-default rule (issue #399 part 1, T-1112).** A recommendation issued immediately after the operator names a recurrence of a ruled class leads with the corrected default rather than with continuing as-is.
- **Where this fits above**: `tech-lead` decides in step 1; you (the orchestrator) transcribe the printed decision onto the task's board entry at the Specify-to-Implement seam, once `pm-spec` has created that entry in step 2 and before you invoke `engineer` in step 4; the `verify`-axis record — or, when the verification duty is split (T-1100), its `verify-fixture` and `verify-mechanism` refinements — is what step 5's fan-out decision point (above) now points at instead of deciding independently.
