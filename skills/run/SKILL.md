You are coordinating the AI dev team — the plugin's `agents/` sub-agents (`tech-lead`, `pm-spec`, `ui-designer`, `engineer`, `qa-verifier`, `codex-reviewer`). The user's request follows below. (`ui-designer` participates **only** for UI work — see the conditional Design phase.)

## When the full loop fits (task aptitude)

**First branch — does the final verification surface close inside the loop?**

- **Closes inside the loop** (correctness is settled by *mechanical* verification — tests, lint, execution/output comparison): the full PM → Engineer → QA → Codex loop **fits**. QA and Codex can confirm the acceptance criteria empirically and statically, so a FAIL is caught inside the loop rather than after a human looks at the result.
- **Does not close inside the loop** (the final gate is *human visual inspection, a real renderer, or subjective evaluation* — e.g. slide/PDF layout, pixel-level UI polish, prose tone): the full loop is a **poor fit, or fits only in a limited way**. QA cannot substitute for the human eye, and the loop only surfaces the human visual gate at the very end, so a visual FAIL costs a whole round-trip and can churn the same code path for many rounds (observed in issue #171: 10+ rework rounds, final score 70/100).

**Provisional operation for visual-output tasks** (a stop-gap until a dedicated short-cycle / variant loop is built — roadmap #138): do **not** put such a task on a single full-loop pass. Instead run a short manual cycle (implement, render, human check) where the human views the real rendered output each turn; keep spec / QA in a supporting role rather than as the completion gate.

> This first branch is the same shape as the future v0.3.0 grounded-AI-evaluator's OOD-novelty / human-gate criterion (see docs/loop-engineering/v0.3.0-oversight-model-evolution.md §7): a verification surface that cannot be mechanically grounded escalates to a human, and the same signal will later feed that evaluator's decision.

**Step 0 — resolve the operating-file paths.** This repo's shell-team files may live under `.shell-team/` (default), a legacy `tasks/` layout, or a `$TEAM_RUN_BASE` override — `team-paths.sh` decides (on PATH when the plugin is loaded; else `bin/team-paths.sh`). Run `team-paths.sh --print` once to read the resolved paths (`TEAM_TODO`, `TEAM_LOOPS_DIR`, `TEAM_RUNS_DIR`, `TEAM_RETROS_DIR`, `TEAM_REVIEWS_DIR`, `TEAM_SPECS_DIR`, `TEAM_RUN_BASE`).

Because **the Bash-less agents (`tech-lead`, `pm-spec`) cannot resolve paths themselves**, prepend one line to each sub-agent's prompt, substituting the resolved values:

> Operating paths for this repo — board: `<resolved todo>`, specs dir: `<resolved specs>`, loop contract: `<resolved loops>/shell-team.contract.yaml`, reviews dir: `<resolved reviews>`, base dir: `<resolved base>`. Use these exact paths.

⚠️ **Env vars do NOT persist across separate Bash tool calls** (each call is a fresh shell). Do not `export` a path in one call and expect `$TEAM_*` in another — when a later Bash call needs a path, resolve it *in that same call* with `$(team-paths.sh --get KEY)` (see the loop-guard step). `log-run.sh` self-resolves its runs dir, so telemetry needs no path from you.

**Language — mirror the user.** Also prepend one line to each sub-agent's prompt telling it to **respond in the same language the user is conversing in** (mirror it; default to English if the language is unclear). This is zero-config — no language config file and no environment variable; you simply pass the conversation language you already observe. **But machine-parsed tokens stay verbatim in English**: status flags (`READY_FOR_ARCH` / `READY_FOR_ENG` / `READY_FOR_QA` / `READY_FOR_REVIEW` / `READY_FOR_MERGE` / `BLOCKED` / `REWORK`), verdict labels (`PASS` / `FAIL` / `APPROVE` / `REQUEST_CHANGES`), and each agent's fixed hand-off headings/keys. Prose and explanations follow the conversation language; the contract tokens do not (they are grepped by `check-handoff.sh` / `goal-state.sh` / `check-acs.sh` — translating them breaks the pipeline).

**Interventions producer discipline (T-1002)** — a standing instruction for every task, across all phases: interventions are captured by **you, the orchestrator**, not the engineer (interventions arrive in the main conversation, which only you can see; `agents/engineer.md` gains no obligation for this file). When a user message arrives during an active task and it interrupts, corrects, or stops the work (issue #37 trigger 1), append the entry at that moment, before you act on the message, to the task's interventions file (`team-paths.sh --get interventions`; use `no-task.md` when no board task is active) using one of the seven classes below. A routine gate response — a plain GO, an approval, or an answer to a question you asked — is not an intervention and gets no entry. Two more triggers are self-checked rather than conversation-triggered, rather than waiting for a message: append an `assumption-contradicted` entry when a measurement contradicts an assumption you have stated, and append a `work-deferred` or `work-abandoned` entry when work is deferred, abandoned or reverted. Self-check at each phase transition, at every `STOP:` escalation, and when a task is aborted. A file with nothing to record carries the zero-entry sentinel `no interventions occurred` rather than being empty — do not fabricate an entry to avoid it. Every append to an interventions file is committed immediately, as its own commit, at the moment of recording — at every recording point, not only at the Implement-to-Validate seam. (T-1002 rework2: the append and the commit are one atomic act, so no recording point ever depends on a later gate to notice an uncommitted edit before it can be lost from a normal PR.)

Recognized classes (`templates/prompt-blocks/interventions-classes.md` — the single canonical source):
- intervention: human-interrupt
- intervention: human-correction
- intervention: human-stop
- intervention: assumption-contradicted
- intervention: work-deferred
- intervention: work-abandoned
- intervention: unclassified

Execute these phases **in order**, invoking the named sub-agent at each step. Do not skip a phase, and do not advance to the next phase until the previous phase's status flag is set in the board (`$TEAM_TODO`).

4. **Implement** — invoke `engineer` to write code + tests (for UI work, the engineer reads the design note as the design contract). Wait for `READY_FOR_QA`.
   - **Isolation (T-055)**: the engineer runs **non-worktree by default** — its edits land directly on the current feature branch HEAD of your checkout, so no reconcile step is needed. Opt into isolation **only for parallel implementations** (multiple engineers editing concurrently within one task) by passing `isolation: worktree` on the Agent invocation; in that case, and only then, reconcile the worktree back: commit the spec + board first, have the engineer reset its work branch onto the designated base SHA and add exactly one commit, then verify blob/tree equality and merge `--ff-only`. **This reconcile recipe is proven for a single opt-in worktree only** — integrating 2+ concurrent worktrees into one branch is NOT covered (after the first `--ff-only` merge advances HEAD, later branches reset to the same base can no longer fast-forward) and needs its own design when parallel implementation is actually attempted. Do **not** try to control isolation via prompt text — the harness honors the invocation parameter, not prose (proven twice: #144/#154).
   - **Preserve the implementation across the seam (T-073)**: the engineer commits its implementation and tests before it sets `READY_FOR_QA`; as a second-layer guard, before you advance from Implement to Validate, confirm there is no uncommitted implementation diff before invoking `qa-verifier` (`git status --short` shows nothing to commit). This protects the engineer's work from any later destructive step in the Validate phase. When you (the orchestrator) edit the task's interventions file at this same seam under the producer discipline below, commit that edit immediately — the same way the engineer commits its own work — before this check runs: this check is over the whole working tree, so an uncommitted interventions append at that exact moment would otherwise make it non-empty for a reason this guard's own prose does not name (T-1002 rework1 fix).
   - **Provenance gate at the Implement-to-Validate seam (T-075)**: the engineer records the target task's decision provenance file `tasks/provenance/<task-id>.md` (decision/reason/grounding triples, or the zero-decision sentinel) before it sets `READY_FOR_QA` (per `agents/engineer.md`'s T-074 producer discipline). Before you advance from Implement to Validate, confirm that file **exists** and that `check-provenance.sh tasks/provenance/<task-id>.md` (on PATH when the plugin is loaded; else `bin/check-provenance.sh`) reports `conformant` (exit 0). This gate is **fail-closed**: a missing file (usage exit 2 — the engineer forgot to record) or a non-conformant file (schema exit 1 / structural exit 2) blocks the seam — **do not start Validate, and do not silently auto-retry.** Instead, **immediately escalate to the human**, quoting the checker's classification line (`check-provenance: usage:` / `schema:` / `structural:`) so a person decides how to resolve it (have the engineer fix/record the provenance file, or investigate). The gate stays fail-closed until the provenance file is conformant — QA does not begin while it is unresolved. There is deliberately **no automatic route-back and no stateful retry bounding here**: that bounded auto-retry variant of this gate — with per-failure-mode distinct sentinels, a new shell-team persistent iteration counter, and check-acs exit-2 handling — was evaluated as fast-follow issue #234 and, per T-077, the human-escalation simple form is confirmed as the Phase A permanent design (T-077); a stateful bounded-retry variant would be reconsidered only if (i) the S4 drift/alignment evaluator begins consuming provenance and an auto-retry need is measured, or (ii) human-escalation frequency becomes a measured operational burden. It is a deterministic pre-check placed alongside the T-073 uncommitted-diff guard, and does not replace `qa-verifier`'s own provenance verification item in Validate. Unlike the frozen-intent confirmation (opt-in per spec), this gate is unconditional — the provenance file is mandatory for every task under the T-074 discipline.
   - **Interventions gate at the Implement-to-Validate seam (T-1002)**: before advancing from Implement to Validate, resolve the task's interventions file at `<dir>/<task-id>.md` (where `<dir>` is `team-paths.sh --get interventions`'s output; use `no-task.md` in place of `<task-id>.md`, and correspondingly `no-task` in place of `<task-id>` in the `--task` flag below, when no board task is active) and run `check-interventions.sh --task <task-id> <dir>/<task-id>.md` (on `PATH` when the plugin is loaded; else `bin/check-interventions.sh`) — it must report `conformant`; this gate is **fail-closed** and **unconditional**, so on any other outcome (`usage` / `structural` / `schema`) you do not start Validate, nothing is auto-retried, and you escalate immediately to the human quoting the checker's **classification** line, because the **orchestrator** (not the engineer) is the producer of this record — interventions arrive in the main conversation, which only the orchestrator sees.
   - **Interventions entry template, and this gate's loop-machinery interactions (T-1002 rework1)**: Entry template: `<!-- BEGIN interventions: <id> -->` opens the region and `<!-- END interventions: <id> -->` closes it with the same `<id>`; each entry is a `- intervention: <class>` line followed by indented `date: <YYYY-MM-DD>`, `summary: <one line>` and `effect: <one line>` fields. If the file currently holds the sentinel `no interventions occurred`, the first real entry REPLACES that line rather than being appended after it — the sentinel and an entry cannot coexist in either order (AC5). Like the T-075 provenance gate above, this pre-check happens before any Validate attempt exists, so a failure here never contributes to `loop-guard.sh`'s `--iteration` count (that count is completed implement→verify cycles, and none has occurred yet this attempt) and is never itself a loop-guard `STOP:<reason>` — the escalation above is direct-to-human, the same distinction the T-075 provenance gate draws.
5. **Validate** — invoke `qa-verifier`. If the verdict is FAIL, ask the loop guard whether to retry before routing back to `engineer`:
   - Run `loop-guard.sh "$(team-paths.sh --get loops)/shell-team.contract.yaml" --iteration <implement→verify cycles completed so far> --verdict-hash <short hash/summary of this QA verdict> --prev-verdict-hash <the previous cycle's verdict, if any>` — the `$(…)` resolves the contract path in the same shell call (a prior `eval`-exported `$TEAM_LOOPS_DIR` does NOT survive into a separate Bash call).

Do not re-describe the digest format by hand — the script is its single source of truth.

   - **Fallback (AC4)**: if `loop-guard.sh` is not callable (plugin not loaded / script removed), fall back to the previous behavior — **max 2 retries before escalating to the user**.
   - **Detection lens**: `qa-verifier` verifies empirically/by execution — does the change actually run, and does it actually produce the claimed output. This is a different detection surface from `codex-reviewer`'s formulaic/static checks in step 6 (below) — a QA PASS is not redundant with a Codex APPROVE, and vice versa.
   - **Frozen-intent check item (conditional)**: when the spec carries an intent block (T-071/T-072), `qa-verifier` includes `check-intent.sh <spec> <board>` aligned (exit 0) as a verification item — a non-aligned result is a FAIL, not a pass with a note. Skip when the spec has no intent block.
   - **Same-class-2 rule**: classify each rework finding `qa-verifier` reports by root-cause class. Once the same class reaches 2 cumulative occurrences (counted within this round or across rounds of Validate/Review), switch the instruction you give `engineer` from "fix the reported spots" to "inventory every site this class applies to, then apply the fix to all of them in one pass." The inventory is **repo-wide and cross-file**, enumerated by mechanical means (`grep` / AST search) — never confined to the flagged file or function — and the rework hand-off must include the **inventory list** (each enumerated site with an apply / not-apply decision per site) so `qa-verifier` / `codex-reviewer` can audit that coverage was complete. For tasks with **parallel implementations** (one discipline that must be replicated identically across multiple output surfaces/media), also require a per-fix **mirrored-application checklist** in the hand-off: did this fix get mirrored to every parallel surface, not just the one that was flagged?
   - **Early escalation branch (T-100, distinct from the STOP escalation above)**: the moment the same class reaches 2 cumulative occurrences — in addition to switching the engineer instruction to full-inventory-bulk-apply — run `rework-digest.sh` with the same per-round records, but with `--trigger same-class-2` in place of `--stop-reason` (no loop-guard `STOP:` is required to run it). This surfaces the `recommended-action` block to the human **pre-STOP**, leading with reconsider-the-design-premise, without waiting for a retry-cap/no-progress STOP. Paste its stdout as-is — the script's stdout is the single source of truth for the choice text, same discipline as the STOP-mode digest above; this early call does not replace the STOP-mode digest, which still runs if a `STOP:` is later reached.

**Telemetry (Observe)** — emit one span row per sub-agent call, from *here* (the orchestrator), not from the agents (an agent cannot see its own token/duration usage). Once at the start, choose a `run_id` (e.g. the UTC start time plus a short suffix) and a span counter `seq` starting at 1. After **each** sub-agent returns, record a row:

```
log-run.sh shell-team --run-id <run_id> --seq <next seq> --span <agent> --phase <phase> \
  --iteration <loop-guard iteration> --attempt <retry # within this iteration> \
  --status <success|error|timeout|skipped|stopped> \
  [--model <routed model>] [--tokens <subagent_tokens from the result's <usage> block>] \
  [--tool-uses <…>] [--duration-ms <…>] [--verdict <PASS|FAIL|APPROVE|REQUEST_CHANGES>]
```

Read `--tokens`/`--tool-uses`/`--duration-ms` from the `<usage>` block on the Agent tool result; omit any field you don't have (it records as `null`). `--model` is the exception — always pass it explicitly (the routed tier, i.e. the sub-agent's `model:` frontmatter value): an omitted `--model` records `null` and corrupts the tier telemetry that model-tiering reviews rely on (recurring gap; root-caused in retro 2026-07-20). `--usd` is untracked (omit). **Telemetry is best-effort: if `log-run.sh` is not callable or exits non-zero, ignore it and carry on — it must never stop the loop.** Invoke it so a failure cannot abort the phase, e.g. append `|| true`:

```
log-run.sh shell-team --run-id <run_id> --seq <seq> --span <agent> --phase <phase> --iteration <n> --attempt <a> --status <status> [usage flags…] || true
```

**Event rows (T-1011)** — alongside the span row above, also emit an EVENT row at the points below: the transition, hand-off, gate verdict, human intervention or release itself — not the sub-agent call. Same `--run-id`, the same shared monotonic seq counter (increment it for the event row too), and the same `|| true` best-effort discipline:

```
log-run.sh shell-team --run-id <run_id> --seq <seq> --event <handoff|rework|gate|human|release> [--from <phase/agent>] [--to <phase/agent>] [--label <text>] || true
```

Emit one at each of these points, mapped 1:1 to the phase steps above:

- `--event handoff --from <phase> --to <phase>` at every phase transition (the step 1→2→(3)→4→5→6→7 boundaries above, wherever the board flag advances) — `--label` is optional here.
- `--event rework --from <phase> --to implement --label <FAIL|REQUEST_CHANGES>` when a QA `FAIL` (step 5) or a Codex `REQUEST_CHANGES` (step 6) routes back to `engineer` under a `REWORK` — `--label` carries the causing verdict, so a `rework` row is never recorded without recording *why*.
