## Attribution and de-duplication rules

The telemetry schema (`.shell-team/runs/shell-team.jsonl`) carries **no task-id field of any kind**. Every per-task figure below rides the `run_id` naming convention alone, so the rule that convention is read by has to be stated, not assumed.

- rule: a `run_id` is **task-attributed** if it matches the ERE `(^|-)t[0-9]+$` (the dominant `<UTC-timestamp>Z-t<digits>` suffix form, e.g. `20260813T150636Z-t1065`) **or** `^t[0-9]+-` (a slug-first form, e.g. `t1061-20260812T003839Z`); the task number is the matched digit run. A `run_id` matching neither is classified `non-task-runs` rather than guessed at — measured at 6 in this corpus (`pii`, `i23`, `i24`, `i25`, `i26`, `v170`).
- rule: the **truncated form** `20260804T-t1024` (no time-of-day component after the `T`) is handled by the same suffix rule as every other `-t<digits>` `run_id` — it attributes to `T-1024` and is not treated as a parse failure or dropped.
- rule: the **slug-first form** `t1061-20260812T003839Z` is handled by the prefix rule above. A naive suffix-only pattern (matching only `-t[0-9]+$`) would misclassify this `run_id` as `non-task-runs`, which is exactly the convention break this second rule exists to catch — measured directly: `echo 't1061-20260812T003839Z' | grep -E '(^|-)t[0-9]+$'` matches nothing, `grep -E '^t[0-9]+-'` matches.
- rule: two rows sharing one `run_id` can share one `seq` value — a **duplicate seq** — while differing only in `ts` and `model`, or only in `ts`. Measured directly in the resolved telemetry file: `run_id` `20260802T052149Z-t1016` carries two rows at `seq:1` (`ts` `2026-08-02T05:24:17Z` / `2026-08-02T05:24:22Z`, `model` `null` / `"opus"`), and `run_id` `20260803T121547Z-t1022` carries two rows at `seq:1` (`ts` `2026-08-03T12:15:47Z` / `2026-08-03T12:15:57Z`, otherwise byte-identical). Any sum over span rows de-duplicates on the composite key **(`run_id`, `seq`, `span`)**, keeping the first-encountered row and discarding the later one; this is the key used everywhere below a sum is taken.
  - command: `grep '"run_id":"20260802T052149Z-t1016"' "$T/corpus" | grep '"seq":1,'` / `grep '"run_id":"20260803T121547Z-t1022"' "$T/corpus" | grep '"seq":1,'`
  - result: two lines each, confirming both named duplicate-`seq` pairs are still present in the resolved telemetry file at report time.
  - command: extract each of the 570 span rows' `run_id`, `seq` and `span` values with three independent `grep -o` passes (the same field-splitting technique `## Metrics`' `duration-per-1k-tokens` block uses, so no command line here juxtaposes the `run_id` and any other field-name-plus-quote fragment the way a pasted telemetry row would): `grep -v '"kind":"event"' "$T/corpus" > "$T/spans"; grep -o '"run_id":"[^"]*"' "$T/spans" | sed 's/"run_id":"//;s/"$//' > "$T/col_runid"; grep -o '"seq":[0-9]*' "$T/spans" | sed 's/"seq"://' > "$T/col_seq"; grep -o '"span":"[^"]*"' "$T/spans" | sed 's/"span":"//;s/"$//' > "$T/col_span"; paste "$T/col_runid" "$T/col_seq" "$T/col_span" > "$T/joined3"`, then de-duplicate on the composite key with `LC_ALL=C awk -F'\t' '{key=$1"\t"$2"\t"$3; val[key]=$0; order[++n]=key} END{for(i=1;i<=n;i++){k=order[i]; if(!(k in seen)){print val[k]; seen[k]=1}}}' "$T/joined3" | wc -l`

## Rigor vs raw latency

The numbers above bear on issue #248's own reading rule ("a rising ratio with flat tokens indicates raw latency; rising tokens/criteria with a flat ratio indicates rigor growth"). Applying it honestly requires a stated numeric meaning for "flat" and "rising" applied the same way everywhere the rule is invoked below — round 1 of this note used the word "flat"/"roughly flat" informally at different, inconsistently-implied thresholds in different places, which a round-2 review measured and named as the defect.

**Stated convention (chosen here, applied uniformly to every span of every length below, with no exceptions): flat** = a relative change of **≤10%**, measured as `(max−min)/min` over **every date inside the span** (not only its endpoints, so a dip-then-recover inside a span is not miscounted as flat); **rising**/**falling** = an **endpoint-to-endpoint** change of **more than 25%** in that direction (start date's value to end date's value); anything between 10% and 25% is **ambiguous** and is not claimed as either. A single-day transition (a 2-date span) has only one interior comparison; for the non-decreasing case (the shape both known `Shape B` hits are) its endpoint change and its internal spread agree, though the two are not the same computation in general (the spread's denominator is always the smaller of the two values, the endpoint change's is always the start value) — this convention subsumes round 2's single-day-only sweep rather than replacing it with a second, differently-defined method: round 3's engineer verified this by re-running the all-spans sweep below restricted to 2-date spans only and confirming it reproduces round 2's own 18-row single-day table exactly (2 `Shape B` hits, 0 `Shape A` hits, same two dates each).

**Rigor-side reading.** `criteria-count` and `runtime-duty-items` do not climb monotonically across `P13-window`: `criteria-count` peaks at T-1056/T-1057 (19) — the loop-liveness/loop-integration pair, both explicitly building new mechanism — and sits lower on either side (10 at T-1053, 7 at T-1062, 12 at T-1065). `freeze-versions` spikes hard at two outliers (T-1055 at v7, T-1060 at v5) against a **v1–v4** baseline everywhere else in `P13-window` (re-derived from the metric's own result line rather than eyeballed: excluding the two outliers, the remaining 11 tasks' values run T-1053=1, T-1054=1, T-1056=2, T-1057=2, T-1058=2, T-1059=1, T-1061=3, **T-1062=4**, T-1063=1, T-1064=1, T-1065=1 — minimum 1, maximum 4); both spikes correspond to tasks this repository's own project memory records as unusually contested (T-1055 the adapter-envelope contract, T-1060 adopter-facing binding docs), not to a background trend across `P13-window`. Read together, rigor **is not a steady climb** across `P13-window` — it is dominated by a small number of individually hard tasks, and a metric that averaged across the window would hide that rather than show it.

**Latency-side reading, swept over every contiguous span of every length — the enumeration domain is stated explicitly, so the word "mechanically" below covers exactly what the command's domain covers and no more.** The domain is **every contiguous date range** in a by-date series of `N` dates — `C(N,2) = N(N−1)/2` spans, from every adjacent 2-date step up to the single span covering the whole series — not single-day transitions plus a hand-picked longer example (round 2's gap) and not a length bound chosen after seeing which spans produce a hit (which would reintroduce the same gap in a new shape). ## Limits and what is not computable

- `tokens`, `tool_uses` and `duration_ms` are read, per `skills/run/SKILL.md`, "from the `<usage>` block on the Agent tool result" for the sub-agent invocation **as a whole** — spanning that agent's own turns, tool calls and context re-reads, never a single model call. This makes `duration_ms` per 1k `tokens` an invocation-level throughput proxy and **not an ask-independent raw-latency measure**: a longer, more complex ask inflates both the numerator and the denominator together, and the ratio cannot separate "the executor is slower per unit of work" from "this particular invocation was asked to do comparatively more."
- Telemetry logging is explicitly **best-effort** (`skills/run/SKILL.md`: "if `log-run.sh` is not callable or exits non-zero, ignore it and carry on — it must never stop the loop"), so a missing row — T-1059's zero `engineer` spans and zero `codex-reviewer` spans, despite a merged spec and a review record existing for that task — is not evidence that no work happened; it is evidence only that this particular row was not logged.
- No field in the recorded schema decomposes `duration_ms` into model-inference time versus API/connection-retry time — isolating the two is unavailable in principle from this data (this task's own Input space rules it out of scope).
- `overhead-share` is declined above for the same structural reason: the schema records no orchestration/gate span with a `duration_ms` at all.
- `rounds-to-approve` is read from the git-tracked reviews corpus, not telemetry, precisely because telemetry disagrees with it on `T-1058` and `T-1059`: telemetry's last recorded `codex-reviewer` row for `T-1058` carries verdict `REQUEST_CHANGES` (an over-counted, unrelated later row — see the metric's own result above) and `T-1059` carries no `codex-reviewer` row at all (an under-count), even though both tasks show `APPROVE` in the git-tracked reviews corpus and `READY_FOR_MERGE` on the board. Telemetry's best-effort logging is the source of the disagreement, not the reviews corpus, which is why the reviews corpus is canonical for this metric rather than a fallback used only when telemetry is silent.
- No inferential-statistics claim (p-value, significance test, regression) is made anywhere in this note over this 13-task, non-experimental, single-repository sample.
