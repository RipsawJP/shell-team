## What you are scoring

You are scoring N candidate implementations of `docs/loop-engineering/subjects/subject-01/` (`csvstats`, a per-column CSV summarizer), each produced independently from the same regenerated venue. Your job is to read the inputs below for each candidate, compute the four ranked scores, apply the comparison-and-tie rule, and record one disposition — `pick`, `merge` or `none` — with its rationale. Everything you need to do that is inside this region.

## The four judge inputs (quoted verbatim from `docs/loop-engineering/phase-multiplexing.md` lines 173–176; `candidate-handoff` optional, the other three required)

- judge-input: candidate-handoff — optional — the candidate's own hand-off narrative (claimed changes, self-reported test results); read for context, since a hand-off is a claim and the diff is the artefact.
- judge-input: candidate-diff — required — the candidate's full diff against the one shared base every candidate started from, the artefact the judge actually scores.
- judge-input: frozen-criteria — required — the task's own frozen spec acceptance criteria, read verbatim, never re-derived or loosened by the judge.
- judge-input: check-results — required — the per-candidate check results already run against `frozen-criteria`; a candidate whose check results cannot be produced at all (a broken check line, an unrelated checker failure) scores as failing `ac-pass-completeness` below rather than being silently skipped, since a check that could not run is not a check that passed.

## The four ranked criteria, in one total order (quoted verbatim from `docs/loop-engineering/phase-multiplexing.md` lines 178–181)

- judge-criterion: ac-pass-completeness — 1 — the fraction of `frozen-criteria` this candidate's own check results actually pass; ranked first, since a candidate that does not satisfy the spec's own contract is never preferred over one that does, on any other axis.
- judge-criterion: test-depth — 2 — whether the candidate's own added or updated tests map onto the acceptance criteria they claim to cover, beyond the happy path.
- judge-criterion: scope-discipline — 3 — whether the candidate's diff stays confined to the task's own declared scope (its allow-list, its Non-goals) rather than carrying speculative refactors or unrelated changes.
- judge-criterion: hygiene — 4 — whether the candidate's diff is free of PII-shaped content, stray debug output, and tool-wrapper residue.

## The five judge outputs (quoted verbatim from `docs/loop-engineering/phase-multiplexing.md` lines 187–191; `merge-set` optional and present only when `disposition` reads `merge`, the other four required)

- judge-output: candidate-id — required — which candidate this verdict line concerns.
- judge-output: disposition — required — one of `pick`, `merge` or `none`: `pick` selects exactly one candidate whole; `merge` composes non-overlapping pieces of two or more candidates, bounded below; `none` is used when zero candidates are worth taking, so the judge is never forced to select the least bad tree.
- judge-output: per-criterion-score — required — the four `judge-criterion` scores, in their own rank order, that produced the disposition.
- judge-output: rationale — required — the reasoning tying the scores to the disposition, so a rework round or a human reviewer can audit the pick without re-scoring from scratch.
- judge-output: merge-set — optional — present only when `disposition` reads `merge`: the disjoint path sets actually merged, one line per contributing candidate.

## What you are forbidden to do (quoted verbatim from `docs/loop-engineering/phase-multiplexing.md` lines 195–197)

- judge-forbidden: writes-code — the judge produces no implementation and no fix of its own; every byte of code it ever lands is a candidate's own, never its own patch.
- judge-forbidden: edits-candidates — the judge never modifies a candidate's own tree or hand-off narrative; a candidate it finds lacking is scored as such, never repaired by the judge itself.
- judge-forbidden: judges-own-candidate — the judge never runs as its own candidate: an evaluator that can also produce the artefact it scores has no separation left to lose, which is the specific failure mode this forbidden exists to close.

## The bounds this scoring stays inside, none of them loosened (quoted verbatim from `docs/loop-engineering/phase-multiplexing.md` lines 199–201; all three read `retained`)

- judge-bound: path-disjointness — retained — bounded by `bin/land-worktree.sh`'s own machine-checked disjointness class (exact path equality, directory-prefix containment, and ASCII case-fold equality all count as overlap): a `merge` disposition is legal only when every pair of merged candidates' own claimed paths clears that class.
- judge-bound: interface-independence-gap — retained — `bin/land-worktree.sh`'s own guarantee is **path-level and textual only** — its own header says so — and does not guarantee semantic or interface independence: one merged candidate may change a signature another calls from a file it never touched, and both would land; this gap is named here, not closed.
- judge-bound: phase-position — retained — the judge runs after the implement fan-out and **before Validate, never after**, since Validate and Review already gate on one committed tree per the `both-gates-green` invariant above; where in `skills/run/SKILL.md` a future task inserts this step is not decided here.

## The score domain, closed for all four criteria

- score-domain: ac-pass-completeness — the two integers on the oracle's own `acceptance: <n> passed, <n> failed` summary line, printed by `docs/loop-engineering/subjects/subject-01/acceptance.sh`, read verbatim for this candidate rather than re-counted or hand-typed; per `check-results`'s own clause above, a candidate whose check results could not be produced at all is scored as failing here rather than silently skipped.
- score-domain: test-depth — one closed ordinal value: `full`, `partial`, or `absent`, anchored below at `- score-anchor: test-depth — <value> — …` — the same three-value scale used for `scope-discipline` and `hygiene`, never a private scale of its own.
- score-domain: scope-discipline — the same closed ordinal set (`full`, `partial`, `absent`), anchored below at `- score-anchor: scope-discipline — <value> — …`.
- score-domain: hygiene — the same closed ordinal set (`full`, `partial`, `absent`), anchored below at `- score-anchor: hygiene — <value> — …`.

**Anchors for `test-depth`** (an observable property of the candidate's own `check/` directory, never an adjective about how thorough the tests feel):

- score-anchor: test-depth — full — the candidate's own `check/` directory contains at least one test file whose text names three or more distinct `- subject-ac:` ids other than `5` (the core happy-path columnar-output case), including at least one of the boundary-heavy ids `1`, `3`, `4`, `6`, `7`, `8` (unreadable-path error, field-count-mismatch skip, zero-usable-rows error, non-numeric-column omission, exit-0-with-empty-stdout, sign-safe decimal parsing).
- score-anchor: test-depth — partial — the candidate's own `check/` directory exists and contains at least one test file, but that file names fewer than three distinct non-happy-path `- subject-ac:` ids, or exercises more than the single happy-path case without naming any id explicitly.
- score-anchor: test-depth — absent — the candidate's tree carries no `check/` directory at all, or a `check/` directory containing zero files.

**Anchors for `scope-discipline`** (an observable property of the candidate's own diff against the shared base, never an adjective about how disciplined it feels):

- score-anchor: scope-discipline — full — the candidate's diff against the shared base writes only paths that are members of `manifest.txt`'s three `candidate-path:` values (`lib/csvparse.sh`, `lib/colstats.sh`, `cli/csvstats`) plus files under the single `candidate-extra-dir: check` — nothing else appears in the diff.
- score-anchor: scope-discipline — partial — the diff carries exactly one file outside those paths, and that file is inert (an empty placeholder, a `.gitkeep`, a comment-only stray) rather than functional code the CLI reads at runtime.
- score-anchor: scope-discipline — absent — the diff carries one or more files outside the manifest paths and `check/` that contain functional content (code, data, or configuration the CLI actually reads).

**Anchors for `hygiene`** (an observable property of the candidate's own tree, never an adjective about how clean it feels):

- score-anchor: hygiene — full — none of the three `candidate-path:` files nor any file under `check/` contains a PII-shaped byte sequence (an email-shaped string, a home-directory absolute path), a stray enabled debug statement (an uncommented `set -x`, a leftover `echo DEBUG`-style line), or a tool-wrapper residue line (a stray closing tag or protocol artefact left behind by an agent tool call).
- score-anchor: hygiene — partial — exactly one of those three named defect classes (PII-shaped content, stray debug output, tool-wrapper residue) appears, exactly once, in exactly one file among the three `candidate-path:` files and `check/`.
- score-anchor: hygiene — absent — two or more of those three named defect classes appear, or the same class appears in more than one file.

**The order the comparison below applies at each ordinal rank, fixed rather than left to inference:** for `test-depth`, `scope-discipline` and `hygiene` alike, `full` outranks `partial`, which outranks `absent` — the same direction in all three, since all three anchors are written so that `full` names the cleanest observable state and `absent` names the worst. For `ac-pass-completeness`, more of the oracle's own `passed` count outranks less (equivalently: fewer `failed` outranks more) — though among candidates that clear the `floor` below, this value is always identical (the oracle exits `0` only when all eleven enumerated cases passed), so `ac-pass-completeness` is a pure eligibility gate rather than a discriminator once the floor has already been applied, and the comparison in practice starts deciding at rank 2 for any two floor-eligible candidates.

## The comparison, the tie-break, the id grammar, the floor, and the `none` disposition — each stated once

- selection-rule: comparison — strict lexicographic precedence over the four `judge-criterion` ranks, in rank order: rank 1 (`ac-pass-completeness`) decides between any two candidates whose values there differ; only when two candidates hold the identical value at rank 1 does rank 2 (`test-depth`) decide; then rank 3 (`scope-discipline`); then rank 4 (`hygiene`) — never a sum, an average, or a weighting nobody assigned, since the contract fixes one total rank order and lexicographic precedence is the only comparison that respects a total order without inventing a weight.
- selection-rule: tie-break — applied only once every one of the four ranks above compares equal between two or more candidates (the strict lexicographic comparison found no difference): quoted verbatim from `docs/loop-engineering/phase-multiplexing.md` line 183 — "the judge picks the candidate whose check results completed first (the earliest recorded completion for its own hand-off); if that is also tied, the judge picks the lexicographically lowest candidate id — deterministic in both steps, never a random or unstated choice."
- selection-rule: candidate-id-grammar — a `candidate-id` has the fixed shape `candidate-NN`, where `NN` is a two-digit, zero-padded decimal ordinal (`01`, `02`, … up to the firing's own N, never exceeding `99`); under this shape, ordinary byte-wise (`LC_ALL=C`) lexicographic order over `candidate-id` strings is total — no two distinct ids of this shape ever compare equal, and every pair compares in exactly one direction, which is what makes the `tie-break` line's second step decidable rather than undefined.
- selection-rule: floor — a candidate is eligible for `pick` only if `docs/loop-engineering/subjects/subject-01/acceptance.sh`, run against its own committed path (never a candidate's venue copy — see `candidate-rule-map: oracle-not-edited` below), exits `0` for that candidate: the single-bit floor the instrument itself computes, since it exits `0` exactly when zero of its eleven enumerated cases failed, and a failed enumerated case is a violation of a frozen `- subject-ac:` line; a candidate below this floor is never eligible for `pick`, regardless of how it scores on any of the four ranked criteria above.
- selection-rule: none-disposition — when every candidate in the firing falls below the `floor` line above, the disposition is `none`: a legitimate, pre-declared measured outcome of a Tier-2 firing, never a failure of the judge and never license to select the least-bad candidate that still failed to clear the floor. The judge records `disposition: none`, the per-criterion scores of every candidate considered (for audit), and a rationale stating that no candidate cleared the floor; at N=2 a `none` outcome yields no `tier2-rework-rounds-avoided` datapoint for that firing — a disclosed consequence, never smoothed over.

## What `check-results` actually claims, carried undiluted (quoted verbatim from `docs/loop-engineering/tier2-subject-harness.md`, never softened into a hedge)

- oracle-claim: enumerated-case-instrument — quoted verbatim: "`acceptance.sh` verifies that a candidate reproduces the exact stdout bytes, stderr bytes and exit code its eleven enumerated cases specify, for the inputs those cases construct, and nothing beyond them. It is not a decision procedure for conformance to `interface.md`'s frozen contract: a candidate can pass every enumerated case and still violate the contract on an input no case constructs, and that possibility is a property of every finite instrument, not a defect to be patched away. What the instrument is for is supplying the judge contract's `check-results` input at a fixed, reproducible strength, and a judge reading those results is entitled to know the strength it is reading — which is what the three named limits below give it." A judge reading an `11 passed, 0 failed` `check-results` line has **not** been shown full conformance to `interface.md` — only conformance to the eleven enumerated cases actually run.
- claim-limit: contract-conformance-unbounded — quoted verbatim: "a candidate that passes all eleven enumerated cases can still violate `interface.md`'s frozen contract on an input no case constructs (a `+`-prefixed integer, an integer beyond 64 bits, a CRLF line ending, a duplicate header name, a quoted CSV field, a Unicode digit — each real, each declined here). Every such finding is answered by this limit, never by a twelfth case: adding one more fixture per finding is exactly the unbounded loop T-1086's own pre-commitment fired on, so a review round naming an unenumerated violator is a report about this limit's own scope, not a defect in the oracle to be patched. Any residual conformance obligation this limit discloses but does not close travels to issue #307 as still owed."
- claim-limit: zero-padded-arithmetic-class — quoted verbatim: "the frozen pattern `^-?[0-9]+$` (`README.md` subject-ac 5) admits zero-padded spellings whose bash-arithmetic value silently differs from their decimal reading, or errors outright, measured on the operator host: `$((010))` → `8` (silent octal reinterpretation); `$((08))` and `$((09))` → the arithmetic error `value too great for base` — a *different* failure mode from the silent one, so "octal" alone would describe only half the class; `$((-010))` → `-8`; `$((00))` → `0`. The identical two-mode danger recurs for a naive `10#`-prefixed signed reading, measured on the same host: `$((10#-010))` → `-8`, silently wrong (the correct decimal reading is `-10`); `$((10#-08))` → the arithmetic error `value too great for base`, the same hard-error mode as the unsigned `$((08))`. None of the eleven enumerated cases exercises a zero-padded value, so a naive `sum=$(( sum + value ))` implementation — signed or not — is unverified against this class by the oracle alone; `README.md`'s own decimal-reading obligation (subject-ac 8, below) is a contract requirement this instrument does not itself enforce."
- claim-limit: case-set-versioning — quoted verbatim from `docs/loop-engineering/tier2-subject-harness.md`'s own `## Baseline analysis and provenance` section: "an eleven-case oracle and a seven-case oracle are two distinct instruments, not two measurements of the same one: `## Baseline analysis and provenance` above already discloses that the baseline's two reps were originally scored against the seven-case version while every future Tier-2 candidate faces this eleven-case version, mitigated there by a retained-tree re-score rather than assumed away. This limit generalizes that instance: any future strengthening of this oracle again produces a new, distinct instrument version, and a score is comparable only to another score measured against the same version — never assumed comparable across a version change without an explicit re-score, the way the baseline's own reps were re-scored here."

## Why `disposition: merge` is structurally unreachable for subject-01, derived rather than merely asserted

`docs/loop-engineering/subjects/subject-01/manifest.txt` fixes exactly three `candidate-path:` entries — `lib/csvparse.sh`, `lib/colstats.sh`, `cli/csvstats` — identical for every candidate of this subject, because the manifest is one committed file, not a per-candidate one. This alone does not force every candidate to write all three: `paths-confined-to-manifest` bounds only what a candidate may **not** write, and an honestly-incomplete candidate (ran out of budget, crashed partway) could legitimately submit a proper subset without violating any of the four enforced `- candidate-rule-map:` rules — so the unreachability below is derived from what the `floor` and `check-results` themselves force, not from an assumption that every candidate writes everything. Two halves, each independently sufficient:

**(a) Every floor-eligible candidate necessarily writes `cli/csvstats`.** `docs/loop-engineering/subjects/subject-01/acceptance.sh` resolves the CLI path it invokes directly from the committed `manifest.txt` (`cli_rel="$(sed -nE 's/^candidate-path: (cli\/.+)$/\1/p' manifest.txt | head -n 1)"`, then `cli="$venue/$cli_rel"`) and every one of its eleven enumerated cases runs that exact path (`run_cli` calls `bash "$cli" …`); a candidate that did not write `cli/csvstats` has no file there for `bash` to run, so it cannot pass a single enumerated case and cannot reach the `acceptance: 11 passed, 0 failed` the `floor` above requires. Therefore any two floor-eligible candidates both wrote `cli/csvstats`, they overlap on at least that one manifest-fixed path, and `- judge-bound: path-disjointness` (retained above, exact path equality counted as overlap) is unclearable between them — `merge` cannot legally combine two floor-eligible candidates of this subject.

**(b) A merge cannot manufacture eligibility out of ineligible parts.** For any candidate below the floor, `docs/loop-engineering/subjects/subject-01/acceptance.sh` did not produce a passing result for it, and the contract's own `check-results` clause above — "a check that could not run is not a check that passed" — means a merged tree assembled from such a candidate's pieces inherits no `check-results` of its own that the judge can score; nothing in the region licenses fabricating a fresh oracle run over an assembled `merge-set` in place of the per-candidate `check-results` the `judge-input` above defines. So `merge` cannot be used to promote two below-floor, proper-subset-writing candidates into one eligible selection either.

Therefore, `merge` is structurally unreachable for subject-01: (a) closes the case where both candidates clear the floor, (b) closes the case where either does not, and together they cover every candidate pair a firing of this subject can present — so a judge scoring this subject should never take the `merge` branch. This unreachability is never repaired by loosening `path-disjointness`, which stays `retained` above; the residual case this derivation does not itself construct a check for — a proper-subset-writing candidate that is *also* floor-eligible — cannot arise, since (a) already shows floor-eligibility forces `cli/csvstats` to be present, which is what makes (a) and (b) jointly exhaustive rather than merely two separate observations.
