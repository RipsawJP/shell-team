## Why this document exists

A spec's acceptance-criteria `- check:` line that needs scratch space commonly opens `d=$(mktemp -d "${TMPDIR:-/tmp}/….XXXXXX"); rc=0;` and never tests whether `mktemp` succeeded. `bin/check-acs.sh` runs every check through `bash -c "$cmd"` with **no** `set -e` in the executed shell, so nothing in the harness rescues an unguarded assignment: on failure the temp-dir variable is empty and every path composed from it (`"$d/raw.txt"`) expands root-anchored (`/raw.txt`). The T-1019 review measured what this costs concretely: most checks of this shape still fail closed by accident (a permission error propagates into the final `test`), but a scope-lock check that writes intermediate files, feeds them to `comm`, and rounds each side through `grep -c . || true` reports `miss=0`/`extra=0` — and `PASS` — when the writes never happened at all. GitHub issue #109 asked for one inventory pass over every `- check:` line in `.shell-team/specs/*.md` that invokes `mktemp`, with a per-site apply/not-apply decision and a one-sentence reason, rather than a sweep that edits every site it finds. This document is that pass.

## Terms this document uses

- **population line** — one line matched by the pinned command below: a `- check:` line in `.shell-team/specs/*.md` whose text contains the substring `mktemp`, whether or not that substring names a real invocation.
- **invocation** — a `mktemp` occurrence in command position: immediately preceded (skipping whitespace) by the start of the line, `;`, `&`, `|`, or `(` — the shapes bash actually treats as "run the `mktemp` command here." A line can carry zero, one, or more invocations.
- **mention** — a `mktemp` occurrence that is *not* an invocation: inside a quoted grep pattern (`grep -qF 'mktemp' …`), inside a filename that merely contains the substring (`check-line-mktemp-guard-audit.md`), or inside a heading's own prose text. A mention has nothing to guard, by construction.
- **guarded** — an invocation whose failure exits non-zero before any path composed from its result is used — either the canonical DP5 idiom (`… || exit 1`), or any other construct with the same effect (a `&&` chain immediately following the assignment also has this property, since the assignment's own exit status equals `mktemp`'s and a failed left side of `&&` short-circuits the right side).
- **composed path** — a later use of the invocation's captured variable with a path segment appended (`"$d/file"`, `"${d}/file"`). A bare reference to the variable itself (`cd "$d"`, `rm -rf "$d"`) is not a composed path.
- **the four classes (DP2)** — **(a) guarded**: every invocation on the line is guarded. **(b) unguarded-path-composed**: an unguarded invocation's result is composed into at least one later path — the root-anchored-expansion shape the issue names. **(c) no-path-composed**: `mktemp` is present (as an invocation or a mention) but no unguarded invocation's result is composed into a later path. **(d) other**: neither of the above — enumerated site by site rather than left as a bucket.

## Classification — the four classes and the ladder

DP2's ladder is ordered and first-match-wins, applied once per population line: (1) is every invocation on the line guarded? → **(a)**. (2) Otherwise, does an unguarded invocation's result get composed into a later path? → **(b)**. (3) Otherwise, is `mktemp` present (invocation or mention) with no unguarded invocation composed into a path? → **(c)**. (4) Otherwise → **(d)**, enumerated site by site. Tie-break: a line carrying more than one invocation classifies by its weakest invocation (severity order for the tie-break only: (b) worse than (c) worse than (a)).

## Decision rules

- rule-1: a site in the spec of a closed task is not-apply, on three grounds — zero CI reachability (`.github/workflows/check-handoff.yml` never executes a real spec's check: lines), a frozen record documents what was verified at the time it was verified so editing the line cannot re-establish that verdict, and the deferral-record precedent (T-1023) shows that a shipped record stays true to its own measurement rather than chasing a later one; this holds whether or not the site sits inside a frozen intent block, because closed-task membership, not frozen-block membership, is the operative ground.
- rule-2: where an acceptance criterion's own text declares staleness or forbids re-derivation, not-apply is strong rather than the plain default rule-1 would give it — T-1019's AC11 is exactly this and is the issue's own highest-severity site: its own body says it is merge-point-scoped and that its base-ref resolution must not be widened or re-derived per round, so editing it to harden it would violate the very criterion being hardened.
- rule-3: a live surface is apply, in the guarded DP5 idiom — the only live surface this task touches is this spec's own check: lines, which is why exactly one row below carries the apply outcome and every other row carries not-apply.
- rule-4: anything the three rules above do not settle is an escalation, recorded explicitly as such rather than resolved by engineer discretion — no site in this live population needed this rule, so the section below states an explicit empty set rather than omitting itself.
- strongest-not-apply: .shell-team/specs/T-1019-is-span-row-parity.md AC11 — rule-2's ground is verified against the source text rather than asserted: the file's own body says it is merge-point-scoped and forbids widening or re-deriving its base-ref resolution per round, and `git diff --quiet 1e31600` confirms the file is byte-identical to the authoring ref `1e31600` at the time of this audit.
