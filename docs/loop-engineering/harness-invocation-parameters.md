# Harness per-invocation parameter surface for a plugin-role sub-agent launch (T-1116)

## Terms and closed vocabularies

Two closed vocabularies govern this note's verdicts, both total functions evaluated over the raw evidence in `## Probe evidence` and recomputed by the note's own acceptance criteria rather than trusted as labels.

**The model verdict** — one of `routed-on-plugin-role` | `not-routed-on-plugin-role` | `instrument-inadmissible` | `undetermined`, derived by the frozen priority function in `## Probe protocol (frozen before execution)`'s "Closed vocabulary — the model verdict" paragraph.

**The effort verdict** — one of `present` | `absent` | `undetermined`, derived by the frozen priority function in the same section's "Closed vocabulary — the effort verdict" paragraph, pinned by the coordinating session's own first-hand schema reading.

**Channels, six, each pinned to exactly one role so promoting a channel is a mechanical failure rather than a matter of prose:**

- channel: capability-differential — question=model — primary — the graded pass/fail differential between `plug-haiku` and `plug-opus`, the only evidence that can license a routing conclusion.
- channel: launch-acceptance — question=model — non-licensing — whether a launch was `accepted`, `refused` or `not-run`; withholds a claim (clause 0 of the model total function, `matrix-complete`, the two arm-execution ids) but never supports one.
- channel: model-self-report — question=model — non-licensing — an instance's own unauthenticated belief about which model it is; recorded on every accepted launch, never read by any verdict branch.
- channel: model-schema-read — question=model — non-licensing — the Agent tool's own closed `model` enum, read first-hand; establishes which tokens are accepted, never whether the override is honored.
- channel: effort-schema-read — question=effort — primary — the Agent tool's own parameter list, read first-hand; answers whether an effort-shaped key exists at all.
- channel: effort-attempt — question=effort — corroborating — a real launch-side attempt carrying an effort-shaped key where the schema read finds one; answers only whether a key that exists changes anything.

**Subject role and calibration role.** Every plugin-arm launch uses `subagent_type=shell-team:tech-lead`. Every calibration-arm launch uses `subagent_type=general-purpose`, a role whose own override behaviour is not the question and which does hold tools — which is exactly why the `tool_uses=0` validity guard below is load-bearing rather than decorative. Whether any result extends to another plugin role, another harness version or another machine is `unobserved` and is recorded as such, never inferred.

**Venue: an instruction plus an after-the-fact measurement, not an enforcement.** There is no cwd parameter on the Agent tool (**A-3**, relayed), so a sub-agent runs in the coordinating session's own cwd whatever path a briefing names; a throwaway clone would enforce nothing and would add a moving part, and none is cut. The venue protection is exactly three things: the briefing forbids tool use outright; any launch whose `<usage>` reports `tool_uses` other than `0` **voids** that rep; and the real checkout's cleanliness is read after every launch — `git status --short` and `git ls-files --others --exclude-standard` — and recorded on **exactly one** `- probe-writes: none — <text>` line whose text quotes both commands. `git clone` and `git worktree add` appear on no `- command:` line in the note, and no `- clone-ref:` line exists anywhere in it. Any absolute path the note prints is written as the placeholder `<repo-root>`, never a real home-directory path.

**Conditions, reps and frozen launch ids.** Five conditions, three reps each, fifteen launches, each a single `Agent` tool call carrying the byte-identical briefing below, differing **only** in `subagent_type` (per arm) and `model`:

- `cal-haiku` — `subagent_type=general-purpose`, `model: haiku` — ids `cal-haiku-rep1`, `cal-haiku-rep2`, `cal-haiku-rep3`
- `cal-opus` — `subagent_type=general-purpose`, `model: opus` — ids `cal-opus-rep1`, `cal-opus-rep2`, `cal-opus-rep3`
- `plug-base` — `subagent_type=shell-team:tech-lead`, **no `model` parameter passed** — ids `plug-base-rep1`, `plug-base-rep2`, `plug-base-rep3`
- `plug-haiku` — `subagent_type=shell-team:tech-lead`, `model: haiku` — ids `plug-haiku-rep1`, `plug-haiku-rep2`, `plug-haiku-rep3`
- `plug-opus` — `subagent_type=shell-team:tech-lead`, `model: opus` — ids `plug-opus-rep1`, `plug-opus-rep2`, `plug-opus-rep3`

The `isolation` parameter is **omitted** on every one of the fifteen launches and is recorded as the literal `omitted` on each launch line rather than as a value. Launches are identified by the coordinating session's own call order; no launch id appears inside the briefing.

**The item, frozen in two versions before any launch.** Both candidate items are frozen here, each with its expression, its declared answer and the one-line command that recomputes that answer, so that the one permitted substitution below is a **selection between two pre-registered items** rather than a free choice made after seeing a failure:

- **Item A** — expression `8237 * 6491`; declared answer **`53466367`**; recompute command `echo $((8237 * 6491))`.
- **Item B** — expression `9431 * 7283 - 6127 * 3559`; declared answer **`46879980`**; recompute command `echo $((9431 * 7283 - 6127 * 3559))`.

Both are multi-step exact integer arithmetic, solvable by exact reasoning without any tool, memorized by nobody, and stated as expressions a reader can recompute. Item B is the **harder** of the two, and the direction is deliberate and pre-registered: the likelier admission failure for an item of this family is under-discrimination — a weak tier passing it too — so the substitute is harder rather than easier. Where the calibration instead fails because the strong tier misses, a harder substitute cannot rescue it and the honest outcome is `instrument-inadmissible` — a distinction the substitution paragraph below states as an exact predicate over the superseded reps and **AC9**(ii) recomputes, rather than one this paragraph merely describes. The item in force is recorded on exactly one `- item-in-force: <A|B> — answer=<digits> — <text>` line whose text carries that item's expression and its recompute command verbatim.

**Grading, fixed as a mechanical rule over one recorded line, and that line is itself recorded.** The grading target is the **reply's final non-empty line**, and that line is transcribed verbatim onto the outcome record as its terminal field `final-line=`, with control characters stripped and nothing else altered — where a reply carries no non-empty line at all, the field is present and empty. The three graded fields are then **derived from that recorded line** rather than reported alongside it: `final-shape=conforming` iff the recorded `final-line` begins with the literal `answer=`; `integers=<digits>` is the count of maximal `-?[0-9]+` runs on it; `value=<integer|none>` is that single run where `integers` is `1` and the literal `none` otherwise. The verdict is then **derived, not chosen**: `na` where `final-shape` is `non-conforming` **or** `integers` is not `1`; otherwise `pass` where `value` equals the item in force's declared answer and `fail` where it does not. An `na` rep is **void** and is never counted as a `fail`, so format-following can never masquerade as capability and non-compliance can never masquerade as incapacity. **AC8** recomputes all three fields, and then the verdict, from the recorded `final-line` alone, so a mistranscribed or invented primitive fails there instead of sailing through a chain that recomputes only the last step. What this closes and what it does not is stated rather than left to a reader: `final-line` is the coordinating session's **transcription of the tool result**, exactly the same trust boundary every other evidence field on the page stands on, so the property gained is that each grade is **recomputable from a recorded observable** — not that the observable is authenticated. No artifact-reading check can authenticate a reply, and none is invented for it; the recorded line is what **AC18**(h) reports and a reader audits.

**Validity and voidness.** A rep is **void** iff any of: its launch `status` is not `accepted`; its graded verdict is `na`; or its launch line reports `tool_uses` other than `0`. The count of void reps across all fifteen is recorded on exactly one `- void-reps: <digits> — <text>` line and is recomputed by **AC8** rather than trusted. The `tool_uses` clause is the guard that keeps the differential a measurement of capability rather than of tool access, and it is required of every graded rep in both arms.

**N and the threshold, priced as arithmetic before any launch, and the figure a reader should price named as such.** **N = 3** reps per condition, and the threshold is **unanimous in the licensing direction with zero void reps** (3/3) for both the calibration admission and the plugin differential. The ground is arithmetic under an explicit independence null — equal per-attempt pass probability `p` in both tiers, independent reps — and is not a measurement: spurious separation of **one** arm pair is `p³(1−p)³`, maximized at `p = 0.5` at **1/64 ≈ 1.6%**. That 1/64 is **the operative figure**, and it is the one this threshold buys: the priority function's clause 1 treats the calibration admission as a **hard gate** rather than as a second noisy coin to multiply against, so the risk a reader should price for a recorded `routed-on-plugin-role` is the plugin arm pair's own spurious-separation probability **conditional on a genuine admission** — 1/64 at the worst-case `p`, not less. The compounded `(1/64)² = 1/4096 ≈ 0.024%` is arithmetically correct only for the strictly narrower case where **both** arm pairs are null — nothing discriminates anything and the whole protocol separates twice by chance — which is a worst-case sanity bound on the protocol as a whole and **not** the protection a positive result carries; quoting it as that protection overstates it by roughly two orders of magnitude, so this spec quotes it only with that scope attached. The same arithmetic prices the rejected alternatives at the same per-arm-pair scope: majority-of-3 gives `0.5 × 0.5 = 25%`, and an existential-of-2 gives `0.75 × 0.75 ≈ 56%` — so unanimity-at-3 is the best available at this sample size, which is what makes 1/64 a floor rather than a defect. This arithmetic prices the **threshold choice at freeze**; the note draws **no** post-hoc inference of any kind from the observed tallies, and no significance test, confidence interval, variance model or regression is computed anywhere.

**Calibration admission, the two confounds it carries, and what it does not establish.** Admission requires `cal-opus` unanimous `pass` and `cal-haiku` unanimous `fail`, each with zero void reps, and is recorded on exactly one `- calibration-verdict: <admitted|not-admitted> — <text>` line, recomputed by **AC9**. Admission is a **conjunction** — the item discriminates between the tiers **and** the harness honors the override for at least one `subagent_type` — so a non-admitting result is confounded between a dud item and a globally unhonored override. That confound gets its own verdict value (`instrument-inadmissible`) rather than being folded into `undetermined`. A second confound is disclosed at the same width, because it is not removable inside this design: the arm runs `general-purpose`, so admission establishes discrimination **under the calibration role's own system prompt** and never under `shell-team:tech-lead`'s. Its direction is fixed rather than unknown: the subject role's prompt can only make the item harder to meet, and only commonly across `plug-haiku` and `plug-opus` since `model` is their sole difference, so the outcomes it can manufacture are `undetermined` and `not-routed-on-plugin-role` — both Branch B — and never a false `routed-on-plugin-role`. Two further distinctions the line's own value does not carry alone: a `not-admitted` value is the admission **rule's output**, which reads the same whether the item failed or the arm never ran, so the "never ran" case is carried by `calibration-arm-executed` reading `not-met` and by clause 0 of the model verdict's total function, not by this line; and which side of the non-admission occurred — under-discrimination or a strong-tier miss — is what the substitution trigger below reads.

**The one permitted substitution, calibration-only, on a trigger that is exact and recomputed.** A substitution is permitted **only** on the under-discrimination side of a non-admission, and the trigger is stated as a mechanical predicate over the superseded round's own six reps rather than as a reason someone gives: substituting Item A → Item B is permitted **iff** the superseded calibration shows `cal-opus` **3/3 `pass` with zero void reps** *and* `cal-haiku` with **at least one `pass` that is itself not void** — accepted launch, `tool_uses=0`, graded `pass` against Item A's recomputed answer, the same void exclusion the `cal-opus` half states, so a void `cal-haiku` rep can no more license a substitution than it can license an admission. The shape this admits is under-discrimination: the item was too easy and the weak tier cleared it. Any `cal-opus` rep that is not `pass` — a `fail` or a void of any kind — means the strong tier missed, which a **harder** substitute cannot rescue; that outcome is `instrument-inadmissible` **directly, with no substitution**, and a substitution recorded over it reddens **AC9**. The substitution is decided and recorded **before any plugin-arm launch runs**, on exactly one `- substitution: from=A — to=B — superseded-briefing-sha256=<64-hex> — <text>` line, with the superseded round's six reps published on `- superseded-calibration:` lines carrying their own status, `tool_uses`, graded fields and verbatim `final-line=` — so the substitution's evidentiary history is recomputed exactly like the in-force round's rather than asserted as prose. `- item-in-force:` reads `B` iff that line exists and `A` iff it does not. A second non-admission is `instrument-inadmissible`. This is the protocol's only substitution allowance, beside the invalid-evidence rule's at-most-one whole-matrix re-probe.

**The briefing, byte-frozen here in two versions so it cannot be fitted to a result.** The bytes sent as the `prompt` parameter on every launch are exactly the lines strictly between the marker pair for the item in force, as they appear in this spec at the recorded intent hash; their SHA-256 is recorded on exactly one `- briefing-sha256: <64-hex> — <text>` line and is one value shared by all fifteen launches. The briefing states the item first and asks for the model self-report only afterwards, as an explicitly non-licensing line, so the self-report cannot prime the answer.

**Closed vocabulary — the model verdict, and the total function that derives it.** Exactly one `- model-parameter:` line, from the closed four-value set below. Its value is not a label the note chooses but the output of this frozen priority function over the recorded evidence, evaluated in this order and recomputed by **AC10**:

0. **no** `cal-*` launch line reads `status=accepted` — the calibration was never executed, so the instrument was never tested ⇒ `undetermined`
1. else calibration not `admitted` — it was executed and did not discriminate ⇒ `instrument-inadmissible`
2. else `plug-opus` unanimous `pass` **and** `plug-haiku` unanimous `fail` ⇒ `routed-on-plugin-role`
3. else some side `s` in {`pass`, `fail`} for which `plug-haiku`, `plug-opus` **and** `plug-base` are all unanimous on `s` ⇒ `not-routed-on-plugin-role`
4. else ⇒ `undetermined`

Clause 0 exists because `instrument-inadmissible` is a claim **about the instrument** — that it was put to the test and failed to discriminate — and an unexecuted calibration arm supports no such claim; it is also what makes the pre-commitment's third drop derivable by this same function rather than asserted beside it. The two are distinguished on the recorded evidence and not on anyone's account of it: clause 0 reads whether any calibration launch was ever `accepted`, clause 1 reads the admission tallies. Clauses 2 and 3 are disjoint by construction: 2 requires the two override arms on opposite sides, 3 requires them on the same side. Everything else — any void rep, any within-condition split, any condition whose reps did not run, and a baseline disagreeing with two agreeing override arms — falls to `undetermined`, which is where the baseline anomaly is additionally recorded on its own line. `honored-frontmatter-vocabulary`, `honored-qualified-id-only`, `accepted-but-unhonored` and `refused` are **deleted**, not corroborated: the first is renamed to what the differential can actually claim, the second and fourth are unreachable in-vocabulary because an out-of-enum value never launches, and the third measured schema validation rather than routing.

**Closed vocabulary — the effort verdict, its total function, and why `present` is reachable exactly when it is true.** Exactly one `- effort-parameter:` line from `present` / `absent` / `undetermined`, derived from the schema read and an attempt that carries an observable-effect field, and recomputed by **AC12**: `present` iff the schema read is `present` **and** the attempt is `accepted` **and** `effect=observed`; `absent` iff the schema read is `absent` **and** the attempt is `not-attempted` **and** `effect=na`; `undetermined` in every other case. The effort question gets **no live arm under the expected premise**: its primary evidence is the Agent tool's own closed parameter list, read first-hand by the coordinating session and recorded on exactly one `- effort-schema-read: <present|absent> — <text>` line as a **harness-surface** reading rather than a repository file. The two channel roles the pinning paragraph fixes are consistent with that function and the reason is stated rather than left to a reader: `effort-schema-read` is **primary** because it answers whether the parameter exists at all, `effort-attempt` is **corroborating** because it answers only whether a parameter that does exist changes anything, and `present` requires both — so `primary` names which channel carries the question's principal evidence and never claims that channel is *sufficient*, since a schema read alone cannot license `present`.

**That one schema read is the branch selector, and it is what keeps `present` reachable exactly when it is true.** Which shape the attempt takes is decided by that first-hand reading and by nothing else — not by a pre-commitment disposition, not by a second call:

- `- effort-schema-read: absent` — the relayed premise **A-3** stands and the parameter list carries no effort field. There is no key to attempt, so `- effort-attempt:` reads `not-attempted` with `effect=na`, which is the **fixed recorded value** under this premise, and the function yields `absent`. An attempt of any other shape recorded beside an `absent` read is a contradiction and reddens **AC12**, since a key the schema does not carry cannot have been passed.
- `- effort-schema-read: present` — premise **A-3** is **falsified by the reading itself**, which is the outcome this channel exists to be capable of producing. The coordinating session names the key it found, and `- effort-attempt:` becomes a **real launch-side attempt** — one launch actually carrying that key — recorded as `accepted — effect=<observed|none>`, or as `refused — effect=na` where the launch carrying it was rejected anyway, or as `not-attempted — effect=na` where no attempt was made at all. `present` is therefore recorded exactly when the harness genuinely exposes **and** honors an effort parameter; `undetermined` is the honest reading when the key exists but no effect could be observed, when the launch was refused, or when nobody attempted it.

**Channels and their pinned roles.** Exactly six `- channel: <id> — question=<model|effort> — <primary|corroborating|non-licensing> — <text>` lines, with every role pinned here so that promoting a channel is a mechanical failure rather than a matter of prose: `capability-differential` — model — **primary**; `launch-acceptance` — model — **non-licensing**; `model-self-report` — model — **non-licensing**; `model-schema-read` — model — **non-licensing**; `effort-schema-read` — effort — **primary**; `effort-attempt` — effort — **corroborating**. Three of the ten ids carry a frozen definition here, because the pre-commitment's drops turn on exactly what they mean and a drop that flipped one of them the other way would foreclose a verdict this design says stays reachable. **`matrix-complete`** is a claim about the **record**, not about the execution: `met` iff every one of the fifteen frozen launch ids carries a `- launch:` line and the launch↔outcome bijection holds on every one of them — so a condition recorded as `status=not-run` leaves the record complete, and what did or did not run is carried by the two execution ids instead. **`calibration-arm-executed`** is `met` iff **at least one** `cal-*` launch line reads `status=accepted`, and **`baseline-arm-executed`** iff at least one `plug-base` launch line does — the ids name **execution**, so "the arm ran" is what they assert and not "every rep of it succeeded", which is separately carried by the admission tallies and by voidness. ## Limits and what is not computable

- evidence-boundary: a separating differential proves a change in capability tier and never a model identity; the system prompt actually loaded and any behaviour not expressed through the frozen item are unobserved; for an in-vocabulary token, "silently ignored" is not a channel this design can read but a verdict value, not-routed-on-plugin-role, reachable only through the differential — and this run never reached that branch, since the calibration was not admitted on either frozen item; the result, had it been reached, would have been scoped to shell-team:tech-lead, to this harness version and to this machine; a subject-role reply shape driven by its own system prompt would void reps commonly across both override arms, so it can only produce a null and never a false positive; and the admission that was sought was to be earned on general-purpose, so even an admitted calibration would establish the item's discriminating power under the calibration role's own system prompt and not under the subject role's — moot here, because neither Item A nor Item B was admitted on either tier's own reps.

Beyond that one line, three further limits are stated rather than engineered around. First, every `- capability-outcome:` and `- superseded-calibration:` `final-line=` field is the coordinating session's transcription of a tool result, the same trust boundary every other evidence line on this page stands on: this note's own acceptance criteria close the gap between a grade and its recorded observable, never the gap between the observable and the wire, and no artifact-reading check can authenticate a reply. Second, commit ancestry and the byte-identity checks over the frozen `probe-protocol` region establish that the freeze preceded the probe in DAG structure, not in wall-clock time; no cryptographic or externally-timestamped proof of ordering exists anywhere in this repository's checks, and building one is outside a `no-mechanism` task. Third, whether any part of this result generalizes to a plugin role other than `shell-team:tech-lead`, a harness version other than the one recorded on the `- harness-version:` line, or a machine other than this one is `unobserved` by construction and is not claimed.
