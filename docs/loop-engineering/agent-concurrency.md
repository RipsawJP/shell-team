The isolation position is quoted verbatim from the primary source rather than paraphrased from memory. `skills/run/SKILL.md` states: "integrating 2+ concurrent worktrees into one branch is NOT covered" and, at the T-073 pre-Validate guard, "this check is over the whole working tree." **What a reconcile design closing the 2+ worktree gap would have to do, in prose, building nothing.** The engineer's own reconcile recipe today is proven for exactly one opt-in worktree: commit the spec and board first, reset the worktree's own work branch onto the designated base SHA, add exactly one commit, verify blob/tree equality, and merge `--ff-only`. That recipe breaks the moment a *second* worktree exists, because after the first `--ff-only` merge advances `HEAD`, a second worktree reset onto the *same* original base SHA can no longer fast-forward — its own one commit now sits on a stale parent. Closing this gap, described only in prose here, would need: (1) a single serializing coordinator — exactly the merge-queue shape named in `## Prior art (external)` — that processes pending worktrees one at a time rather than concurrently; (2) for each pending worktree in turn, a rebase of its one commit onto the *current* tip (not the original base), producing a fresh commit; (3) re-running the *same* verification (qa-verifier and codex-reviewer, or whichever gate the reconcile design chooses) against that rebased commit before advancing, because a rebase changes the tree's own parent and, in principle, the diff a reviewer or a checker sees; (4) only then a `--ff-only` merge, advancing `HEAD` for the *next* pending worktree's own rebase. This is materially more than the proven single-worktree recipe: it needs new orchestration state (a queue of pending worktrees, tracked across an unknown span of wall-clock time), a policy for what happens when a rebase invalidates an *already-approved* verdict from step 3, and the same `board`/`test-recipe`/`shared-git-index` contention this note's own inventory above already found `serialize` for concurrent writers — which is exactly why `intertask-pipelining`'s own safety precondition above states this design does not exist yet.

## Invariants that must not loosen

- invariant-lock: both-gates-green — running qa-verifier and codex-reviewer concurrently changes only *when* each verdict is computed, never whether the loop requires both; a task cannot reach `READY_FOR_MERGE` without qa-verifier's own subsequent `PASS`, even if codex-reviewer's concurrent pass happened to `APPROVE` a commit QA later rejects — the reconcile-at-join cost above is exactly the price of that ordering still holding.
- invariant-lock: fail-closed-checkers — no checker's own semantics move under any candidate above; qa-verifier would still run the same existing fail-closed checks (`check-acs.sh`, `check-pii-shapes.sh`, and the rest) it already runs today, and codex-reviewer would still perform its own existing static-only review (per `agents/codex-reviewer.md`'s own default mode, which does not execute the test suite the way qa-verifier does — **corrected this round, Codex round-1 Minor**: round 1 wrongly stated both roles "run the same checks," which overstates the parity between the two verification depths) — concurrency changes only the invocation's timing for each role's own existing, unchanged verification depth, never what either checks.
- invariant-lock: bin-pure-bash — this investigation ships no mechanism (`- verification-class: no-mechanism`); nothing under `bin/` is added or edited by this task, and any future staged-adoption work inherits the same repository-wide constraint (pure bash, zero-dependency, shellcheck-clean) every existing script already meets.
- invariant-lock: human-gate-set — the three human gates (the sprint's own batch GO, planning approval, and confirmation before a destructive or irreversible operation) are untouched; concurrency changes which sub-agent phases overlap, never which decisions require a human, and merge still waits for the sprint's own batch GO exactly as today.
- invariant-lock: frozen-intent-no-concurrent-attest — a spec's frozen intent block is still attested by exactly one role at one point in time, at Specify, before Implement/Validate/Review begin; nothing about overlapping later phases touches the freeze/attestation flow, and no candidate above proposes attesting a frozen intent block from two concurrent readers.
- invariant-lock: handoff-attributable — even when qa-verifier and codex-reviewer run concurrently, each still writes its own uniquely-attributable record (qa-verifier's board append; codex-reviewer's own `reviews/T-NNN.md`) — `per-task-records` stays `partition-safe` by construction (unique per-task filenames), so every hand-off remains attributable to the specific role and round that produced it, never to a shared or ambiguous write target.
