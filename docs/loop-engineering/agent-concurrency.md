## Isolation and reconcile

The isolation position is quoted verbatim from the primary source rather than paraphrased from memory. `skills/run/SKILL.md` states: "integrating 2+ concurrent worktrees into one branch is NOT covered" and, at the T-073 pre-Validate guard, "this check is over the whole working tree." - command: `B=29c35d97ed1c9468cc82c38598f75f4be1d842ab; T=$(mktemp -d "${TMPDIR:-/tmp}/t1068iso.XXXXXX") || exit 1; git show "$B:skills/run/SKILL.md" > "$T/skill"; grep -qF -- 'integrating 2+ concurrent worktrees into one branch is NOT covered' "$T/skill" && echo present-1; grep -qF -- 'this check is over the whole working tree' "$T/skill" && echo present-2`
- result: both literals present at the base-ref blob (`present-1`, `present-2`), matching this section's own quotation exactly, including the `2+` and the capitalised `NOT`.

**What a reconcile design closing the 2+ worktree gap would have to do, in prose, building nothing.** The engineer's own reconcile recipe today is proven for exactly one opt-in worktree: commit the spec and board first, reset the worktree's own work branch onto the designated base SHA, add exactly one commit, verify blob/tree equality, and merge `--ff-only`. That recipe breaks the moment a *second* worktree exists, because after the first `--ff-only` merge advances `HEAD`, a second worktree reset onto the *same* original base SHA can no longer fast-forward — its own one commit now sits on a stale parent. Closing this gap, described only in prose here, would need: (1) a single serializing coordinator — exactly the merge-queue shape named in `## Prior art (external)` — that processes pending worktrees one at a time rather than concurrently; (2) for each pending worktree in turn, a rebase of its one commit onto the *current* tip (not the original base), producing a fresh commit; (3) re-running the *same* verification (qa-verifier and codex-reviewer, or whichever gate the reconcile design chooses) against that rebased commit before advancing, because a rebase changes the tree's own parent and, in principle, the diff a reviewer or a checker sees; (4) only then a `--ff-only` merge, advancing `HEAD` for the *next* pending worktree's own rebase. This is materially more than the proven single-worktree recipe: it needs new orchestration state (a queue of pending worktrees, tracked across an unknown span of wall-clock time), a policy for what happens when a rebase invalidates an *already-approved* verdict from step 3, and the same `board`/`test-recipe`/`shared-git-index` contention this note's own inventory above already found `serialize` for concurrent writers — which is exactly why `intertask-pipelining`'s own safety precondition above states this design does not exist yet.

  - command: `find tests -type f -name "*.sh" | wc -l; find tests -type f -name "*.sh" -exec grep -l "mktemp" {} \; | wc -l; T=$(mktemp -d "${TMPDIR:-/tmp}/t1068ts.XXXXXX") || exit 1; find tests -type f -name "*.sh" -print0 | xargs -0 -I{} sh -c 'grep -vE "^\s*#" "{}" | grep -q "mktemp" && echo "{}"' | LC_ALL=C sort > "$T/withmktemp"; wc -l < "$T/withmktemp"`

- serialization-point: full-population-diff-cpu — hard — a full-population diff or a whole-CI-equivalent re-run (every spec's criteria, run at base and head) is bound by the CPU this repository's own operator machine has, not by a design gap: running two such sweeps concurrently on one machine does not reduce total CPU-seconds, it only interleaves them, and on a single non-distributed machine this can regress wall-clock through cache and scheduler contention rather than improve it. This is a genuine physical resource constraint, not a software reconcile gap a design could close the way `test-suite-scratch-paths` above already is.

Substrate — what this loop's own harness already provides versus what a scheduler would additionally need, issue #252 item 6, each line's own evidence stated:

- substrate: background-agent-launch — provided — this role's own Bash tool exposes a `run_in_background` parameter, exercised directly in `## Pilot probe` below (two concurrent background jobs, joined via `wait`, both completing with correct exit codes); `## Prior art (external)`'s `harness-concurrency` entry additionally reports native concurrent background sub-agents at the Agent-tool level, a claim this role's own tool set cannot exercise directly (no Agent-launching tool is available to this role — see `## Pilot probe`'s own disclosed hazard).
- substrate: completion-notification — provided — a backgrounded job delivers a completion signal (an exit code on `wait`) when it finishes; demonstrated directly in this task's own pilot probe.
- substrate: inter-agent-message — absent — `CLAUDE.md`'s own "Working rules" state verbatim: "Sub-agents do not share a context window; everything that has to survive a hand-off passes between them through files in the repo." No git-tracked agent definition (`agents/*.md`) or skill (`skills/*/SKILL.md`) implements or references a peer-to-peer channel between two sub-agents; every hand-off in this loop passes through a git-tracked file, never a direct message.
- substrate: watchdog — absent — a grep of every agent definition, skill and `bin/` script for the word "watchdog" returns zero occurrences (`grep -rn "watchdog" agents/*.md skills/*/SKILL.md bin/*.sh | wc -l` → `0`); no stall-detection or timeout mechanism is part of this shipped loop. `completion-notification` above fires only on genuine completion and, by its own nature, cannot distinguish a still-running agent from a silently stalled one.
- substrate: shared-state-lock-primitive — absent — a repository-wide grep for `flock` or a `lockfile` idiom across all of `bin/` returns zero occurrences (measured under `telemetry-seq` above); no generic mutex any task could call before writing a shared file (the board, the telemetry file) exists today.
- substrate: ready-queue — absent — `bin/discover-work.sh` is explicitly read-only: it "NEVER writes any file and NEVER mutates tasks/todo.md," printing candidate lines for a human to promote. No component claims a unit of work, marks it in-progress, or advances a state machine on its own; the orchestrator's own judgement fills this role today, not a mechanism.

## Invariants that must not loosen

- invariant-lock: both-gates-green — running qa-verifier and codex-reviewer concurrently changes only *when* each verdict is computed, never whether the loop requires both; a task cannot reach `READY_FOR_MERGE` without qa-verifier's own subsequent `PASS`, even if codex-reviewer's concurrent pass happened to `APPROVE` a commit QA later rejects — the reconcile-at-join cost above is exactly the price of that ordering still holding.
- invariant-lock: fail-closed-checkers — no checker's own semantics move under any candidate above; qa-verifier and codex-reviewer would each still run the same existing fail-closed checks (`check-acs.sh`, `check-pii-shapes.sh`, and the rest) against the same frozen commit, and concurrency changes only the invocation's timing.
- invariant-lock: bin-pure-bash — this investigation ships no mechanism (`- verification-class: no-mechanism`); nothing under `bin/` is added or edited by this task, and any future staged-adoption work inherits the same repository-wide constraint (pure bash, zero-dependency, shellcheck-clean) every existing script already meets.
- invariant-lock: human-gate-set — the three human gates (the sprint's own batch GO, planning approval, and confirmation before a destructive or irreversible operation) are untouched; concurrency changes which sub-agent phases overlap, never which decisions require a human, and merge still waits for the sprint's own batch GO exactly as today.
- invariant-lock: frozen-intent-no-concurrent-attest — a spec's frozen intent block is still attested by exactly one role at one point in time, at Specify, before Implement/Validate/Review begin; nothing about overlapping later phases touches the freeze/attestation flow, and no candidate above proposes attesting a frozen intent block from two concurrent readers.
- invariant-lock: handoff-attributable — even when qa-verifier and codex-reviewer run concurrently, each still writes its own uniquely-attributable record (qa-verifier's board append; codex-reviewer's own `reviews/T-NNN.md`) — `per-task-records` stays `partition-safe` by construction (unique per-task filenames), so every hand-off remains attributable to the specific role and round that produced it, never to a shared or ambiguous write target.

## Limits and what is not computable

- The per-round `duration_ms` series this note cites (the reconcile-at-join proxy under `validate-parallel-review`, and `docs/loop-engineering/context-lifecycle.md`'s own T-1060 figures this note does not repeat) is a single-task **n=1** observation whose primary record is the board (`.shell-team/todo.md`, T-1067's own entry), not `docs/loop-engineering/effort-time-trend.md`, which publishes only totals and averages. no corpus-level round-1 dominance is claimed anywhere in this note.
- `duration_ms`-per-token or `duration_ms`-per-round is an invocation-level throughput proxy, not an ask-independent latency measure, per `docs/loop-engineering/effort-time-trend.md`'s own inherited bound — a task whose round asked for more naturally costs more, and this note's own per-task figures above cannot separate "the executor is slower" from "this task's own round was asked to do more."
- The pilot probe's own measured wall-clock (`## Pilot probe`) is a mechanical-safety demonstration, not a magnitude estimate: its two-reader shell-job proxy substitutes a few milliseconds of `grep` for what is, in the real `qa-verifier`/`codex-reviewer` roles, several minutes to tens of minutes of sub-agent invocation — the gap this note's own `validate-parallel-review` saving prices as `modeled`, never `measured`, for exactly that reason.
- Whether this harness genuinely runs two concurrent Agent-tool sub-agent invocations from one orchestrator session is **not verified** by this task — this role's own tool set carries no Agent-launching tool, so only Bash-level background concurrency was exercised. `## Prior art (external)`'s `harness-concurrency` entry cites this capability; it is not measured here, per DP7's own one-way boundary.
- `implement-tail-parallel-qa` and `intertask-pipelining`'s own savings are `undetermined` because no recorded telemetry field isolates the durations either needs (an engineer's own tail-verification sub-phase; two different tasks' overlapping wall-clock) — this is a reachable and expected outcome of this task's own Input space, not a gap this note estimates around.
- No inferential-statistics claim (a significance test, a confidence interval, a regression) is made anywhere in this note over the 11–12-task, non-experimental, single-repository telemetry sample it reads, and no dollar cost, vendor price model, or synthetic N-agent load figure is estimated anywhere in this note.
- `## Prior art (external)`'s own citations are search summaries over a US-only index, not full-text reads, per the digest's own disclosed caveat; every S/M/L cost and every saving figure in this note is drawn from an internal measurement or an internal design description, never from one of those citations.
