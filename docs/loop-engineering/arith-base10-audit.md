## Why this document exists

`bin/check-intent.sh` shipped a fail-open hole inside a fail-closed gate (T-1018): a grammar-conformant leading-zero count (`verdict=08P/00F`) crashed a `$(( ))` expansion **inside an `if` condition** — a position `set -e` does not cover — so a cross-check was silently skipped and a self-contradictory attestation passed as `aligned`. One line was fixed there. This document is the answer to "does the same shape exist anywhere else in `bin/`" — every one of bash's eight arithmetic-evaluation contexts (D1), across all 35 files directly under `bin/`, reconciled so no occurrence is unaccounted for.

## Terms this document uses

- **arithmetic context** — one of the eight bash constructs in the table below that evaluates an operand as an arithmetic expression, and therefore applies bash's leading-zero-means-octal rule.
- **a site** — one arithmetic-context *occurrence* whose operand set contains at least one variable or command-substitution term, addressed `<file>:<line>`. A wholly-literal-operand occurrence (`${BASH_REMATCH[1]}`, `${BASH_SOURCE[0]}`, a literal `${v:0:1}` offset) is **not** a site — it is counted and excluded at reconciliation.
- **untrusted digits** — a digit string produced by a regex capture, a file read, an environment variable, or a command-line argument — never the script's own counter or a canonical-decimal producer.
- **canonical-decimal producer** — `grep -n`, `cut -d: -f1` over `grep -n` output, an `awk` integer `print`, `${#var}`/`${#arr[@]}`. File-derived, but structurally unable to carry a leading zero or a sign.

### D1 — the eight arithmetic contexts

| # | context | label used below |
|---|---|---|
| 1 | arithmetic expansion | `$(( ))` |
| 2 | arithmetic command | `(( ))` |
| 3 | arithmetic `for` | `for (( ))` |
| 4 | `let` builtin | `let` |
| 5 | indexed-array subscript (`a[i]`, `${a[i]}`, `a[i]=`) | `array subscript` |
| 6 | substring expansion (offset/length are arithmetic) | `${v:off:len}` |
| 7 | bash's `[[` arithmetic binary operators | `[[ -eq ]]` |
| 8 | bash `printf`'s numeric conversion | `printf '%d'` |

`[[ … -eq … ]]` is in scope and `[ … -eq … ]` / `test … -eq …` is **not** — the distinction is the `[[` command, not the operator name (bash's manual: *"When used with the `[[` command, arg1 and arg2 are evaluated as arithmetic expressions"*). This widening is grounded by live execution, not citation — see the two `- probe:` lines below (AC19): `[[ 010 -eq 8 ]]` and `[ 010 -eq 8 ]` disagree on exit code, which is the whole evidence the two constructs are different contexts.

Classification (D2) is an ordered, first-match-wins ladder, so every site lands on exactly one of four values:

1. Can untrusted digits reach this operand? No ⇒ **`NOT-REACHABLE`**.
2. Otherwise: does the operand enter arithmetic without base-10 normalization at this occurrence? Yes ⇒ **`NEEDS-10#`**.
3. Otherwise (already normalized): does its grammar admit a digit string wide enough to cross bash's signed 64-bit range and change a comparison's answer? Yes ⇒ **`NEEDS-WIDTH-BOUND`**.
4. Otherwise ⇒ **`NORMALIZED`**.

**How `NEEDS-10#` is read in this document.** A site's class describes the finding, not merely a snapshot of today's text: `NEEDS-10#` marks the exact arithmetic-expansion occurrence where an untrusted, not-yet-normalized digit string first enters a `$(( ))`/`(( ))` context — the occurrence whose `10#` prefix (now present, as the fix) is load-bearing, in the sense that reverting it at that exact address reproduces the historical re-basing bug (this is exactly what the mutation self-checks in the hand-off exercise). A *downstream* occurrence that consumes the resulting already-normalized local (for example `bin/goal-state.sh`'s `delta=$(( n - start ))`, using the `n`/`start` normalized one line above) carries no vulnerability of its own at that address and is classified `NORMALIZED`, even though it sits in the same execution path. This reading is what makes `NEEDS-10#` and `NORMALIZED` co-exist along one data flow without contradiction, and it is why a `NEEDS-10#` row's `lock:` field names the regression test that would fail if that row's own `10#` were removed.

**`NEEDS-WIDTH-BOUND` reads the same way.** It marks the occurrence whose grammar was tightened as the fix — the arithmetic site that consumes a capture whose regex now carries the width bound — even though the bound itself lives in the regex definition, not in the arithmetic line's own text (`bin/check-intent.sh`'s `HASH_FULL_RE`/`ATTEST_FULL_RE`, Codex round1 rework). A downstream occurrence whose own operands are already bounded elsewhere (`bin/check-intent.sh:654`'s `$((ap + af))`, `:682`'s `$((version_int - 1))`) cannot itself overflow and stays `NORMALIZED`/`width: none`, by the same co-existence logic `NEEDS-10#` uses above.

**Two exclusion rules that keep the sweep tractable.** `${BASH_REMATCH[1]}`-shaped literal-index subscripts dominate context 5's raw hits and every `${v:off:len}` in `bin/` carries a literal offset (context 6) — both are excluded as wholly-literal-operand occurrences, counted at reconciliation, never silently dropped. Text that *looks* like a bash arithmetic context inside a single-quoted `awk` program (`bin/close-out.sh:333`, `bin/gen-project-status.sh:112-144`) is awk's own arithmetic, evaluated by awk, not bash, and is excluded with that reason (D1).

## AC19 — live grounding for the `[[ -eq ]]` / `[ -eq ]` widening

- probe: [[ 010 -eq 8 ]] — exit: 0
- probe: [ 010 -eq 8 ] — exit: 1

Both forms were run against the identical `010 -eq 8` operand. `[[ 010 -eq 8 ]]` evaluates its operands arithmetically (leading-zero-as-octal: `010` = 8), so the comparison is *true*, exit 0. `[ 010 -eq 8 ]` — the single-bracket `test` builtin — parses base 10 only (`010` = 10), so the comparison is *false*, exit 1. The two constructs disagree on the same input, which is the whole evidence D1's widening (inventorying `[[ -eq ]]` while excluding `[ -eq ]` / `test -eq`) is correctly drawn.
