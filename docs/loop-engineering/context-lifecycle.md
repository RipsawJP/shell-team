**Task**: T-1067 · **Base ref**: `3d72e5b125f88094298aa6875dc62bbf27488cd4` (`git merge-base feature/1066-effort-time-telemetry HEAD`) · **Run context**: this repository's checkout root, plugin not on `PATH`; every command below is written to run from the repo root exactly as shown. Two different corpus kinds are read below, and every `- source:` line names which one: **machine-local** (the transcript corpus and `.shell-team/runs/*.jsonl` — gitignored, exist only on the operator's own machine, carry no git ref of their own, and grow while this task itself runs) and **git-tracked** (the board, the reviews corpus, the interventions corpus — read at the base ref above wherever a `- command:` line invokes `git`, and at the working tree otherwise, per this task's own AC8 git-form allow-list). This task's own telemetry rows and transcripts are excluded from every count below — see the `- self-measurement-exclusion:` line in `## Limits and what is not computable`.

This note answers issue #249: does running several issues as one continuous sprint accumulate context in a way worth resetting, and if so, where and at what cost? `docs/loop-engineering/effort-time-trend.md` built the work-volume/wall-clock baseline; this note builds the causal accounting that baseline was meant to serve.

## Accumulation sites

Three places accumulate context across a sprint run under this loop, and they are different things with different costs, growth behaviour and resets (issue #249's own first refinement). Every measured figure and every comparison sentence below carries exactly one of the three labels defined here.

- site: S1-orchestrator-session — the orchestrator's own Claude Code session, continuous across every task the current sprint train runs; nothing in this loop resets it between tasks today.
- site: S2-resumed-subagent — a sub-agent's own transcript, growing across a single task's rework rounds because the same sub-agent invocation is *resumed* (a rework round, a `SendMessage`) rather than launched fresh each round.
- site: S3-launch-brief — the launch prompt the orchestrator writes into each newly-launched agent (a spec, board content, prior task context) at the start of a phase; what S3 must carry grows as the sprint's own board and reviews corpora grow.

**Relation between the sites, stated explicitly.** S1 and S2 are independent: a freshly-launched sub-agent starts with a clean S2 regardless of how large its parent S1 has grown (issue #249's own second refinement, restated in `## Reset options and their cost`), so S1's own growth does not, by itself, imply S2 growth for the next task. S3 sits between them — it is written by the orchestrator, drawing on S1's own accumulated judgement of what to include, and read into a fresh S2 at the start of every phase — so a change to what S3 carries is the one lever that touches both a fresh sub-agent's own starting cost and, indirectly, what the orchestrator's own S1 has to track.

## Attribution and measurement rules

No transcript path component encodes a task id, a role or a round: an orchestrator-session file is named only for its own session id, and a sub-agent file is named only for its own agent id under that session's own directory. The telemetry schema (`.shell-team/runs/shell-team.jsonl`) carries the same gap from a different angle — its `span` field names a role but no row carries a task-id field of any kind. The measured property that makes an attribution rule necessary at all: no task id, no role and no round survives in any transcript path or telemetry row, so every per-task or per-role figure below rides a stated rule rather than the filesystem.

The transcript root is not resolvable through `bin/team-paths.sh` (no `transcripts` key exists); every command below derives it with the environment-independent expression `T="$HOME/.claude/projects/$(pwd | sed 's/[\/_]/-/g')"` rather than a literal path.

- rule: an orchestrator-session transcript file is attributed to a calendar-day window by its own mtime, never by its path — the path carries no task id, no role and no round to read instead.
- rule: within one session, a sub-agent file's own specific role (engineer vs. qa-verifier vs. codex-reviewer, etc.) is not recoverable from its path (named only `agent-<hex>.jsonl`), its size, or its mtime alone; per-file role attribution is explicitly declined for every sub-agent transcript this note reads, in favour of the telemetry `run_id`+`span` route for a per-role, per-task figure, and a distribution-only (aggregate count/size) reading for the corpus-wide S1/S2 figures.
- rule: a telemetry `run_id` is task-attributed by the same suffix/prefix convention `docs/loop-engineering/effort-time-trend.md`'s own `## Attribution and de-duplication rules` states (`(^|-)t[0-9]+$` or `^t[0-9]+-`); a `run_id` matching neither is `non-task-runs`, not guessed at.
- rule: `.shell-team/runs/close-out.jsonl`'s `run_id` (`co-<YYYY-MM-DD>-T-NNNN`) carries the task id directly and is used here only to bound a task's close-out in calendar time, cross-checked against a candidate session's own mtime window (`## What was measured`) — never as a cost figure, since every cost field on it is `null`.
- exception: a transcript file's own role cannot be recovered without opening its content, which is a Non-goal; every per-role transcript-file figure in this note is therefore reported as unattributed-by-role rather than guessed at (see the "nine rounds, multi-MB" reading in `## What was measured`).
- exception: a session directory's own task attribution rests on mtime overlap with a candidate task's own telemetry timestamp range — a correlation, not an identity. Two tasks whose work overlapped the same calendar day would be indistinguishable by this rule alone; no figure in this note actually depends on disambiguating such a pair (each session-directory reading below is checked, at the point it is used, against exactly one candidate task's own telemetry window with no second candidate present on the same day), so this exception is disclosed but does not weaken any figure this note reports.
- exception: this task's own transcripts and telemetry rows are excluded from every count in this note (the self-measurement exclusion, `## Limits and what is not computable`) rather than resolved by the rules above — they are removed, not attributed.

This note's measurement design is **cross-sectional**: every reading below is a final size, a final count, or a final `tokens` figure read at report time and compared against a canonical round count taken from the git-tracked reviews corpus's own `^### Codex Review verdict` heading count — never a reconstruction of what a growing transcript or a resumed sub-agent's context held at an earlier round. Put plainly: no longitudinal growth curve is constructed here — a transcript file, once appended to across nine rounds, is legible only at its current size, not at the size it held after round three, so this note does not attempt to plot one.

## Cross-PR consistency test

Issue #249 asks this to be tested rather than assumed: does cross-PR consistency ride git-tracked files and machine gates, or does it depend on an agent remembering an earlier task's own decision? This test counts, mechanically, how often a drift the loop actually caught — an `assumption-contradicted` intervention, a case where a relayed premise or an earlier reading turned out false — was caught because a machine-checkable artefact (an acceptance criterion, a named `check-*.sh` script, or a checker/criterion/suite) surfaced it, versus some other way.

- population: every `- intervention: assumption-contradicted` entry in `.shell-team/interventions/T-NNNN.md` for the 13 tasks of `docs/loop-engineering/effort-time-trend.md`'s own `P13-window` (`T-1053`–`T-1065`).

- command: extract each entry's own `effect:` line and test it against the fixed ERE `AC[0-9]+|check-[a-z-]+\.sh|checker|criterion|criteria` (an acceptance-criterion reference, a named checker script, or the word "checker"/"criterion"/"criteria"), a rule and a majority-vote reading fixed before this count was run: `T=$(mktemp -d "${TMPDIR:-/tmp}/t1067ct.XXXXXX") || exit 1; for t in T-1053 T-1054 T-1055 T-1056 T-1057 T-1058 T-1059 T-1060 T-1061 T-1062 T-1063 T-1064 T-1065; do f=".shell-team/interventions/$t.md"; [ -f "$f" ] && LC_ALL=C awk '/^- intervention: assumption-contradicted$/{grab=1;next} grab && /^  effect: /{print; grab=0}' "$f"; done > "$T/effects"; wc -l < "$T/effects"; grep -cE 'AC[0-9]+|check-[a-z-]+\.sh|checker|criterion|criteria' "$T/effects"; rm -rf "$T"`

## Reset options and their cost

Each of issue #249's three named options is priced on the same three axes — orchestrator tokens, sub-agent wall-clock, and rehydration cost (the axis a reset argument usually omits) — using only what `## What was measured` and `docs/loop-engineering/effort-time-trend.md` already establish; no axis is filled with an estimate this note's own Non-goals forbid.

- option: per-issue-orchestrator-reset — undetermined
  - axis-orchestrator-tokens: the schema records no orchestration/gate span at all (`docs/loop-engineering/effort-time-trend.md`'s own `overhead-share` decline, reconfirmed here), so the orchestrator's own token cost — before or after a per-issue reset — cannot be read from telemetry in either state; the only available proxy is S1's transcript-size distribution above (34 sessions, up to about 14.9 MiB each), which is bytes, not tokens, and does not decompose into "session-continuity overhead" versus "the genuine work the session did."
  - axis-subagent-wall-clock: this option touches orchestrator continuity only; it does not change how or when a sub-agent is launched, so no measured figure above moves under it.
  - axis-rehydration: real but unpriced from recorded fields — a freshly-started orchestrator session would need to re-load whatever substrate it currently carries across a whole sprint, and no span in the schema times that load at all; S1's own size distribution bounds how much substrate exists to reload without pricing the reload itself.
  - disposition-reason: neither the cost this option avoids (S1's growth) nor the cost it pays (orchestrator-side rehydration) is priced in the recorded fields, so no disposition stronger than undetermined is defensible from what this note can measure.
- option: per-round-fresh-subagents — undetermined
  - axis-orchestrator-tokens: unaffected — this option changes sub-agent launch pattern, not orchestrator session continuity, so S1 does not move under it.
  - axis-subagent-wall-clock: measured directly from `duration_ms` on the corpus's own highest-round task (`## What was measured`) — round 1 (4979526 ms) is the maximum of the 9 recorded rounds, and rounds 2–9 are each substantially lower, averaging 705751 ms. This is directional and confounded, not a clean floor: round 1 is where the bulk of a task's *original* implementation work happens, so its high `duration_ms` mixes genuine new-work time with whatever substrate-reading a from-scratch launch requires, and the two cannot be separated from this field alone. Nothing in the recorded series shows a from-scratch pass costing *less* than a resumed one, but the reverse (that it costs strictly *more*, causally because it is from-scratch) is equally unestablished — round 1's cost is at least as well explained by "round 1 does more original work" as by "round 1 pays a rehydration tax."
  - axis-rehydration: confounded, not a clean floor — this note's own `## Limits and what is not computable` already states that `tokens` cannot separate carried-context cost from new-work cost, and the round-1 `tokens` figure (385176) is exactly a confounded reading of that kind, not an isolated rehydration cost. The naive extension — multiply round 1's total by the round count to price "repeating the floor every round" — does not settle the direction either: `385176 × 9 = 3466584` tokens, which is **less** than `6054319` tokens, the sum this note's own `tokens` series (`## What was measured`) actually reaches across the resumed session's 9 rounds — so a literal floor-repeated reading argues *against* this axis costing more under fresh relaunches, not for it. That comparison is itself naive in the other direction, though: a genuinely fresh round 5, with no resumed context at all, would need the orchestrator to write a materially longer S3 launch brief to substitute for what a resumed session's own history already carries (the current implementation state, prior review findings) — an inflation this note has no recorded field to measure and does not estimate (DP10). Neither reading is decisively supported by what is recorded; this axis is reported confounded/undetermined rather than as a clean cost this option pays.
  - disposition-reason: re-derived from the axes as they now honestly stand, after round 1 of this rework corrected the wall-clock axis and this round corrected the rehydration axis: axis-orchestrator-tokens is neutral; axis-subagent-wall-clock is confounded (directionally consistent with a rehydration cost, but equally explained by round 1 simply doing more original work); axis-rehydration is confounded (the same tokens-based confound this note's own Limits section already names, and the naive floor arithmetic above does not settle a direction — it points the opposite way from what this note's own round-1 rework claimed). No axis here independently and uncontradictedly supports either `recommended` or `not-recommended`, so `undetermined` is the disposition the axes as measured actually support. This is a genuine change from this note's own prior rounds, not a restatement: both prior rounds asserted `not-recommended` on evidence that, read honestly against `duration_ms` and against this note's own stated confound, does not decide the direction.
- option: status-quo-carry-everything — recommended
  - axis-orchestrator-tokens: S1's own accumulation is real and measured in bytes (up to about 14.9 MiB per session, about 111 MiB total across 34 sessions net of this task's own exclusion), but no recorded field ties that growth causally to added sub-agent cost — `docs/loop-engineering/effort-time-trend.md`'s own `## Rigor vs raw latency` found no persistent one-directional latency trend across its own telemetry-bearing window, and issue #249's own second refinement states a freshly-launched sub-agent starts clean regardless of the orchestrator's own S1 size.
  - axis-subagent-wall-clock: this is what is actually happening today, unmodified — the corrected `duration_ms` series `## What was measured` records for T-1060 (round 1 = 4979526 ms, rounds 2–9 averaging 705751 ms) and `docs/loop-engineering/effort-time-trend.md`'s own recorded wall-clock totals for these two tasks. The corrected reading is more favourable to status quo than round 1 of this note's `tokens`-labelled figure suggested: `duration_ms` does **not** climb as a resumed session's own `tokens` total climbs — rounds 2–9 are each *lower* than round 1, not higher — so there is no wall-clock evidence in this corpus that a resumed session's own growing context is making later rounds progressively slower. Whether round 1's own high cost is substrate-reading overhead or simply more original work cannot be decomposed from the recorded fields (`docs/loop-engineering/effort-time-trend.md`'s own `## Limits and what is not computable`, inherited here), so status quo's own cost on this axis is real (round 1 is expensive) but not attributable to *accumulation* specifically — and the growth this note's round 1 mistakenly cited under this axis's name simply does not appear in the wall-clock field at all.
  - axis-rehydration: zero, by construction — nothing is ever reset under status quo, so no site ever pays a re-read-the-substrate cost; this is the axis where status quo's advantage over both alternatives above is unambiguous rather than merely undetermined.
  - disposition-reason: re-read against the corrected `duration_ms` series (unchanged disposition, strengthened reasoning): `## Cross-PR consistency test` above found that cross-PR correctness already rides files and machine gates rather than retained context (`supported`), so no correctness argument compels a reset; the corrected wall-clock reading removes rather than adds a reason to reset, since no *sustained* round-over-round wall-clock growth tied to accumulated context is observed — round 1 is the maximum and rounds 2–9 fluctuate without a consistent upward trend (two local increases exist within that range, round 3→4: 539159→889445 ms and round 6→7: 536832→852735 ms, but neither reaches round 1's level and the series does not climb monotonically nor end higher than it starts). Round 1 is expensive on its own terms, not because later rounds carry more accumulated context than earlier ones did.
