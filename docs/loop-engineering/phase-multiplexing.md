## Tier inventory and cost model

Each tier occupies exactly one `- tier: ` line and exactly one paired `- saving: ` line.

- tier: tier1-verification-fanout — mechanical — M — fan out an existing phase's own mechanically-enumerable, read-only verification work (e.g. a full-population blast-radius sweep, one `bash bin/check-acs.sh <spec>` run per spec) across N instances of one role, aggregating N partial verdicts into one authoritative verdict before that phase's own existing, unchanged gate.
- saving: tier1-verification-fanout — measured — this pilot's own serial arm (`n=1`) averaged 297164683500 ns across 2 reps; the fastest swept arm (`n=9`) averaged 166883349000 ns — a 43.84% wall-clock reduction (`(297164683500-166883349000)/297164683500`) — with all five `- measured-label: ` conditions below `met`.
  - removes-phase: the wait for one worker to sequentially run `bash bin/check-acs.sh` once per spec across an independent, read-only spec population — the same phase shape T-1062's own engineer-phase blast-radius sweep exercised in production.
  - saving-cap: bounded below by this population's own single most expensive unit, `.shell-team/specs/T-1044-test-infra-bundle.md`, measured alone at 142965525000 ns (≈48.1% of the serial total) — no degree of fan-out below sub-dividing that one spec's own AC-level checks can push the wall clock under that unit's own serial cost, which is exactly what this sweep observed (the wall clock plateaus at `n≥4`: 171141504500 ns, then 167382372500 ns, then 166883349000 ns, never approaching zero).
  - precision-cost: the deterministic-selection judgment this pilot itself performed (choosing and fixing the population before any arm ran, per DP-C) is the concrete unit here; a real per-instance agent fan-out additionally multiplies the `S3-launch-brief` accumulation site above by N, since N agent instances each need their own launch brief rather than one shared verification-phase brief.
  - token-cost: undetermined — this pilot's own units are shell processes running an existing checker, not N agent invocations; no telemetry field isolates a verification-only agent's own token cost from a full phase's recorded total, so the real per-instance token multiplier a true agent-level fan-out would carry is not observed here.
  - rework-amplification: undetermined — no fan-out of any kind has ever run in this repository's own history; no recorded field measures whether decomposing verification work across N instances raises or lowers the `rounds-to-approve` series `docs/loop-engineering/agent-concurrency.md` publishes from the git-tracked reviews corpus.
- tier: tier2-parallel-implementations-judge — design-judgment — M — run 2+ independent engineer attempts at the same task concurrently, then a new judge role picks (or merges non-overlapping pieces of) one candidate before Validate — discarding the losing attempt(s) rather than reconciling them, so it does not need the multi-worktree merge Tier 3 needs.
- saving: tier2-parallel-implementations-judge — modeled — priced from this repository's own recorded corpora rather than from a pilot arm (D1, D6): `## Tier-2 judge design and cost comparison` below builds a break-even model from six `- cost-input: ` figures and solves it for the threshold number of rework rounds a task would need to avoid, at N=2 and at N=3, since the parameter carrying the tier's actual bet has no recorded field behind it.
  - removes-phase: a single first-shot implementation that fails Validate/Review and must be reworked — N parallel competing implementations, scored by the judge design below before Validate, would in principle let a stronger candidate be picked before that failure occurs, removing some fraction of the `rounds-to-approve` rework this task inherits from the sibling note's own series.
  - saving-cap: bounded by this task's own break-even model, not by a pilot: solving the inequality below for the threshold rounds a task would need to avoid gives ≈0.74 rounds at N=2 and ≈0.93 rounds at N=3 — both below the smallest value this corpus's own `rounds-to-approve-series` has ever recorded (1) — a favorable arithmetic property of the recorded inputs, not an empirical bound on how often a judge actually avoids rework, which no historical run measures.
  - precision-cost: the judge role and its mechanical scoring contract this section now specifies precisely (`- judge-input: `, `- judge-criterion: `, `- judge-output: `) — a contract this task designs, not builds, so the precision cost is a design cost only; running it against N candidate diffs remains a `no-mechanism` gap.
  - token-cost: at minimum an N-times multiple of one task's own engineer-phase token cost, since N full independent implementations must be produced before any judging can occur; the recorded `engineer-phase-cost` cost-input below (271772 ms per implementation, this repository's own T-1078 scale) prices the wall-clock half of that multiple, but no telemetry field isolates a candidate implementation's own token cost from a phase total, so the token/dollar half stays out of scope (Non-goals).
  - rework-amplification: undetermined — no historical run of this tier exists to measure whether judging shifts or reduces rework rounds; the cost model below assumes a positive rounds-avoided quantity without asserting one occurs, which is exactly why this sub-bullet is not upgraded by the arrival of a cost model that does not measure it.
- tier: tier3-work-splitting — design-judgment — L — partition one feature's own implementation across N engineers each owning a disjoint file set, landing all N onto one branch — the true engineer×N split issue #253 names as lowest-value, research-grade, blocked on the same 2+ concurrent-worktree reconcile `skills/run/SKILL.md` itself declares NOT covered.

The corrected `- break-even-condition:` below states exactly how the owner-count fact (2-of-2) and the whole-round ms figure enter that inequality's own terms, consistent with D5's own owner-count definition of this quantity, rather than leaving the two figures to stand side by side unreconciled.

## Tier-2 judge design and cost comparison

This section turns the paper disposition above into an implementable contract (D2–D5) and prices it against a break-even model built from this repository's own recorded corpora (D6–D7), without building any mechanism (`- verification-class: no-mechanism`): no `agents/judge.md`, no scoring script, no run-skill step exists after this section, only prose plus the new closed line grammars declared in `## Terms and closed vocabularies` above.

**What the judge reads and scores (D2, D3).** Four inputs, ranked over four scored criteria in one total order so two candidates cannot tie on precedence:

- judge-input: candidate-handoff — optional — the candidate's own hand-off narrative (claimed changes, self-reported test results); read for context, since a hand-off is a claim and the diff is the artefact.
- judge-input: candidate-diff — required — the candidate's full diff against the one shared base every candidate started from, the artefact the judge actually scores.
- judge-input: frozen-criteria — required — the task's own frozen spec acceptance criteria, read verbatim, never re-derived or loosened by the judge.
- judge-input: check-results — required — the per-candidate check results already run against `frozen-criteria`; a candidate whose check results cannot be produced at all (a broken check line, an unrelated checker failure) scores as failing `ac-pass-completeness` below rather than being silently skipped, since a check that could not run is not a check that passed.

- judge-criterion: ac-pass-completeness — 1 — the fraction of `frozen-criteria` this candidate's own check results actually pass; ranked first, since a candidate that does not satisfy the spec's own contract is never preferred over one that does, on any other axis.
- judge-criterion: test-depth — 2 — whether the candidate's own added or updated tests map onto the acceptance criteria they claim to cover, beyond the happy path.
- judge-criterion: scope-discipline — 3 — whether the candidate's diff stays confined to the task's own declared scope (its allow-list, its Non-goals) rather than carrying speculative refactors or unrelated changes.
- judge-criterion: hygiene — 4 — whether the candidate's diff is free of PII-shaped content, stray debug output, and tool-wrapper residue.

**Tie-break (`tie-break`), stated once so the contract is implementable rather than a coin flip.** When two or more candidates score identically on every one of the four ranked criteria above, the judge picks the candidate whose check results completed first (the earliest recorded completion for its own hand-off); if that is also tied, the judge picks the lexicographically lowest candidate id — deterministic in both steps, never a random or unstated choice.

**What the judge emits (D2, D3).** One machine-parseable verdict line per candidate, over five closed output fields; the verdict line's own grammar is fixed in `## Terms and closed vocabularies` above and is never instantiated in this note:

- judge-output: candidate-id — required — which candidate this verdict line concerns.
- judge-output: disposition — required — one of `pick`, `merge` or `none`: `pick` selects exactly one candidate whole; `merge` composes non-overlapping pieces of two or more candidates, bounded below; `none` is used when zero candidates are worth taking, so the judge is never forced to select the least bad tree.
- judge-output: per-criterion-score — required — the four `judge-criterion` scores, in their own rank order, that produced the disposition.
- judge-output: rationale — required — the reasoning tying the scores to the disposition, so a rework round or a human reviewer can audit the pick without re-scoring from scratch.
- judge-output: merge-set — optional — present only when `disposition` reads `merge`: the disjoint path sets actually merged, one line per contributing candidate.

**What bounds a merge of non-overlapping pieces (D4), and what the judge is forbidden to do (D5).**

- judge-forbidden: writes-code — the judge produces no implementation and no fix of its own; every byte of code it ever lands is a candidate's own, never its own patch.
- judge-forbidden: edits-candidates — the judge never modifies a candidate's own tree or hand-off narrative; a candidate it finds lacking is scored as such, never repaired by the judge itself.
- judge-forbidden: judges-own-candidate — the judge never runs as its own candidate: an evaluator that can also produce the artefact it scores has no separation left to lose, which is the specific failure mode this forbidden exists to close.

- judge-bound: path-disjointness — retained — bounded by `bin/land-worktree.sh`'s own machine-checked disjointness class (exact path equality, directory-prefix containment, and ASCII case-fold equality all count as overlap): a `merge` disposition is legal only when every pair of merged candidates' own claimed paths clears that class.
- judge-bound: interface-independence-gap — retained — `bin/land-worktree.sh`'s own guarantee is **path-level and textual only** — its own header says so — and does not guarantee semantic or interface independence: one merged candidate may change a signature another calls from a file it never touched, and both would land; this gap is named here, not closed.
- judge-bound: phase-position — retained — the judge runs after the implement fan-out and **before Validate, never after**, since Validate and Review already gate on one committed tree per the `both-gates-green` invariant above; where in `skills/run/SKILL.md` a future task inserts this step is not decided here.

## Tier-3 feasibility and break-even model (evaluated — T-1078 pilot)

No experiment was run for this tier (Non-goals); issue #253 itself asks for a written feasibility verdict only, in three parts.

**Multi-worktree integration sketch.** `docs/loop-engineering/agent-concurrency.md`'s own `## Isolation and reconcile` section already describes, in prose, what closing the 2+ concurrent-worktree gap `skills/run/SKILL.md` itself declares NOT covered would require: a single serializing coordinator (the same merge-queue shape that note's own `## Prior art (external)` names) that processes pending worktrees one at a time, rebasing each pending worktree's own commit onto the *current* tip rather than its original base, re-running the same verification gate against the rebased commit before advancing, and only then merging `--ff-only` before the next pending worktree's own rebase. Tier 3's own engineer×N split needs exactly this reconcile, because unlike Tier 2, every one of the N engineers' own work is meant to land, not be discarded — the reconcile is not optional scaffolding for Tier 3, it is the mechanism that makes N-way landing possible at all.

**Spec-partition grammar.** pm-spec would need a new authoring discipline before any split could run safely: non-overlapping file sets assigned per engineer instance, and pre-agreed interfaces recorded as frozen spec artefacts (so that engineer A's own work does not silently assume a function signature engineer B's own work changes). No spec in this repository has ever been authored this way; this is a written requirement, not a built grammar.

**Break-even model**, every parameter labelled with its own confidence word, at least one `undetermined`:

- break-even: engineer-phase-duration — undetermined — `docs/loop-engineering/effort-time-trend.md`'s own per-task wall-clock series describes tasks of arbitrary shape and size, not specifically partition-eligible features, and nothing in that series or in this pilot establishes that a Tier-3-eligible feature's own serial engineer-phase duration tracks that general distribution; substituting it as this inequality's own serial baseline by default carryover would be an unearned transfer rather than a model, so it is disclosed as undetermined rather than asserted.
- break-even: partition-overhead — measured — priced as D5's own two separately-measured components: the serialization half is the landing spans themselves, well under one second per landing at this repository's scale (7 landings measured directly at 458–490 ms; the eighth's own timer was lost to a shell error and is disclosed only as a bound, under 1000 ms, never a specific figure — see `partition-overhead, serialization half` above); the authoring half is reported as an upper bound, not a point estimate — 139 s measured between the adjacent commits bounding the venue-setup interval, which also contains the clone operation itself and one denied-command retry not separately instrumented, so 139 s over-states the authoring cost proper rather than under-stating it (see `partition-overhead, authoring half` above).
- break-even: reconcile-cost — measured — the shipped mechanism composes each worker's changed paths onto the coordinator branch's current tip and writes a two-parent commit through `bin/land-worktree.sh`; the two agent gates run once, against the final composed tip, never once per landing. Priced directly from this pilot's own 8 landings: sub-second every time (7 measured directly at 458–490 ms, the eighth bounded under 1000 ms rather than observed), so the reconcile step itself is not this tier's cost driver — `partition-overhead` and `rework-amplification` are.
- break-even: rework-amplification-input — modeled — the canonical `rounds-to-approve` series `docs/loop-engineering/agent-concurrency.md` publishes from the git-tracked reviews corpus (`T-1056` 3, `T-1057` 2, `T-1058` 1, `T-1060` 9, `T-1061` 3, `T-1062` 4, `T-1063` 2, `T-1064` 1, `T-1065` 4, `T-1066` 5, `T-1067` 3) remains the base rate for real-gate-driven rework, unchanged by this pilot — this line is not redefined, updated, or superseded by anything below. This pilot's own seeded arm (2 of 2 owners reworked, both parallel reps, versus 1 of 1 in each serial rep — see the `- saving: tier3-work-splitting` block's own `rework-amplification` sub-bullet) licenses `measured` for the seeded class only, per D5, and is deliberately not substituted into this generic, real-gate-driven parameter: the corrected `- break-even-condition:` below names the identical symbolic term, `rework-amplification-input`, but instantiates it at a second, distinct, pilot-specific value — this pilot's own worked substitution only — never a redefinition of the generic parameter on this line.

- break-even-condition: breaks even when the split's own **N-way critical-path implement cost** (`max_i` over workers of that worker's own implement wall clock — the slowest single worker, never a sum, since implementation runs concurrently while landing runs sequentially) plus `partition-overhead` (the partition-authoring cost plus the landings' own serialization cost) plus `rework-amplification-input`, **for this pilot's own worked substitution only**, priced as the seeded rework round's own measured whole wall clock rather than a synthetic per-owner delta (the generic, real-gate-driven `rework-amplification-input` parameter above stays `modeled` and unchanged by this substitution — the same symbolic name, two distinct, clearly scoped instantiations, never a redefinition of the parameter line) — D5 defines the term by the owner-count fact itself, "reworks one owner or N", and when N owners are genuinely forced the round's own critical path is bounded by all N of them together, so the round's raw wall clock is the honest ms carrier of that fact here, not a subtraction — stays below the sum of the single-engineer serial implement wall clock and the wall clock the same seeded defect would have cost that one serial engineer to rework alone. Two defects are fixed here, not one: issue #277's recorded erratum (the sum omitted `partition-overhead` and `rework-amplification-input` while citing the first as the reason the model was unevaluable) and a second, independently-found defect this task's own first corrected draft introduced — it dropped the implement-phase term entirely rather than correcting it from the base model's naive N-way *sum* to the critical-path *max* that concurrent implementation actually requires. This pilot's own measured substitution of every term (worked immediately below, outside this note's own byte-frozen evidence region) finds the condition **unmet**: the split's own combined cost exceeds the serial cost rather than staying below it (see `- saving: tier3-work-splitting` above).

**Worked substitution (shown so the conclusion is checkable against the line's own numbers, not merely asserted).** Every figure below is either read directly from this pilot's own measured lines above, or — where the pilot did not observe a figure — stated as a bound, never a point value, per this spec's own frozen Non-goal ("a value the pilot did not observe is `undetermined` with its reason, never a number"). ms throughout.

## Invariants that must not loosen

- invariant-lock: both-gates-green — fanning a phase's own verification work across N instances changes only how many workers produce partial verdicts before they are aggregated into one board-visible verdict, never whether a task still needs `qa-verifier`'s own subsequent `PASS` and `codex-reviewer`'s own subsequent `APPROVE` before `READY_FOR_MERGE`; this pilot's own aggregation proof (a byte-identical verdict multiset across every swept arm) is exactly what a real adoption would need before reducing N partial verdicts to the one authoritative verdict that unchanged gate reads.
- invariant-lock: fail-closed-checkers — every worker in this pilot ran the identical, unmodified `bash bin/check-acs.sh`; no checker's own semantics moved, and a real fan-out would still run each unit through that same unmodified check — concurrency changes only which process runs which unit, never what any unit checks.
- invariant-lock: bin-pure-bash — this task ships no mechanism (`- verification-class: no-mechanism`); nothing under `bin/` was added or edited, and this pilot's own worker/driver scripts exist only inside the throwaway clone under `$TMPDIR`, never committed to this repository.
- invariant-lock: human-gate-set — the three human gates (the sprint's own batch GO, planning approval, and confirmation before a destructive or irreversible operation) are untouched; within-phase width scaling changes how many workers a phase's own work is split across, never which decisions require a human.
- invariant-lock: frozen-intent-no-concurrent-attest — a spec's frozen intent block is still attested by exactly one role at one point in time, at Specify, before Implement/Validate/Review begin; nothing about fanning a later phase's own verification work out across N instances of one role touches the freeze/attestation flow, which happens earlier in the loop and is structurally unaffected by width-scaling a downstream phase.
- invariant-lock: handoff-attributable — every pilot worker wrote its own per-worker output file, merged only after every worker in that arm had exited, never appending to one shared file two workers could race on (`- pilot-safety: per-worker-output-files` above); a real N-instance fan-out inherits the same shape for its own scratch state, and the seventh invariant below is exactly what closes the remaining gap — attributing the *merged*, board-visible hand-off record itself to the instance that produced each of its parts, not merely keeping scratch files apart.
- invariant-lock: per-instance-telemetry-discriminator — named as a follow-up only (DP-F): no discriminator is designed, no telemetry schema changes, and no `bin/` script is touched by this task. A real N-instance fan-out would need one so that a hand-off record stays attributable to the specific instance that produced it, exactly as issue #253's own invariants paragraph asks; this task's own `no-mechanism` class forbids building it here.

## Limits and what is not computable

- This pilot's own population is a 9-file, stride-9 subset of a 73-file corpus, on one operator machine, at one point in time; the knee measured here is a property of this machine's core count, not a portable constant, and the specific plateau point (`n≥4`) is additionally a property of this population's own cost distribution (one outlier unit dominating), not a property of `check-acs.sh` or of concurrency in general.
- An initial stride-5 selection (15 files) was tried first and abandoned mid-run once its own serial pass exceeded this pilot's own wall-clock budget; this was a budget decision made before any of that attempt's own AC verdicts were read or compared, never a re-selection made after seeing a verdict, and none of that attempt's own data is used anywhere in this note.
- No spec in this pilot's own 9-file population happened to carry the fence-unawareness hazard `.shell-team/test-recipe.md` documents (a duplicate-labelled AC from a fenced illustrative example); this pilot's own aggregation method is designed to survive that hazard (value-matched, never positional, pairing), but the hazard itself was not exercised by this specific run, which is a gap in coverage, not a claim that the hazard cannot occur.
- `implement-tail-parallel-qa`-style precision costs are not modeled for either Tier 2 or Tier 3 beyond what is stated above; no recorded telemetry field isolates a partitioned or duplicated engineer sub-phase's own token cost from a whole-task engineer phase's total, the same decomposition gap `docs/loop-engineering/agent-concurrency.md` names for its own `implement-tail-parallel-qa` candidate.
- No inferential-statistics claim (a significance test, a confidence interval, a regression) is made anywhere in this note over the sweep's 2 reps per arm or over the 11-task `rounds-to-approve` series it cites; both are small, non-experimental, single-repository samples, and spread is disclosed descriptively only.
- No dollar cost, vendor price model, or estimated/interpolated value is reported anywhere in this note; every figure is either read from a git-tracked source and named, or measured live on this pilot's own host and labelled as such.
- Whether this harness genuinely runs N concurrent Agent-tool sub-agent invocations from one orchestrator session is not verified by this task, exactly as `docs/loop-engineering/agent-concurrency.md` already discloses for the depth axis; this task's own pilot exercised only shell-process-level concurrency inside a throwaway clone.
- This pilot ran on a host where `command -v timeout` and `command -v gtimeout` both resolve to nothing; a host where `timeout` is available would let a real adoption bound each unit's own worst case directly, a control this pilot's own measurement could not exercise.
- This pilot's own Tier-3 result is one subject task, of one partitionable shape, measured on one host, in one continuous session, on one day; nothing here generalises to "features" in the plural, exactly as D1(a) discloses for the choice of subject.
- `rework-amplification` is measured for this pilot's own one seeded cross-partition defect only; real-gate-driven rework rates for any Tier-3 split remain `modeled`, against the same canonical `rounds-to-approve` series the paper model already cited, never re-derived or replaced by this pilot's own seeded-class result.
- This pilot measures the cost of the partition it actually authored — a moderately imbalanced two-file-versus-three-file split of one subject — not the cost of an optimally-balanced partition of the same or any other feature; whether a more careful partition would have changed the direction of the result is not measured, modeled or estimated here.
- No inferential statistic (a significance test, a confidence interval, a regression) is computed over this pilot's own two reps per arm; every spread reported above is descriptive only.
- One of the eight landing durations lost its own timer to a shell error and is reported as an mtime-approximation rather than an exact measurement (`landings` above); it is disclosed as such rather than silently treated as an exact figure, and every conclusion above rests on the seven exactly-measured landings plus this one disclosed approximation, never on the approximation alone.

- The Tier-2 cost model's own decisive parameter, `tier2-rework-rounds-avoided`, is `undetermined`: no historical run of this tier exists anywhere in this repository, so whether a judge's own pick decisions ever avoid rework — let alone at the rate the computed break-even threshold above would need — is neither measured nor modeled here, and empirical judge accuracy is declined outright (Non-goals).
