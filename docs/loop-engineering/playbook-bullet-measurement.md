# Playbook bullet measurement — a design for finding out what each lesson still prevents

**Task**: T-1199 (issue #782). **What this is.** A design note. It describes how the four generated playbook blocks could be measured one lesson at a time, what the measurement would cost, and how a result could reach a removal decision. It runs no measurement and no model, it removes nothing, and it edits no lesson, block, agent or script.

The machinery inventory (`docs/loop-engineering/machinery-inventory.md`) marks all four blocks `verdict: unknown` because the live value of each bullet is not separately measured. Removing bullets by impression or by age is ruled out; this note is the step that makes a later, evidence-based decision possible.

## Unit measured

**The unit is the lessons entry** — one `## <date> — <title>` section of `.shell-team/lessons.md` — and not the rendered bullet and not the category.

- **Why not the rendered bullet.** `bin/gen-playbook-blocks.sh` emits one `Rule` line per qualifying entry into each role's block. An entry with `Applies-to: all` therefore appears as four bullets, one per block, and an entry with a comma list appears once per listed role. These renderings are copies of one decision. Every lever the corpus has acts on the entry: `Status`, `Scope` and `Superseded-by` live on the entry, and `bin/check-playbook.sh` validates entries. A measured result on a single rendering has no lever of its own to act on.
- **Why not the category.** `Category` is a small closed taxonomy (process, tooling-ci, security-pii and so on). A category bundles lessons that prevent unrelated failures, so a category-level result cannot say which lesson to keep. It is useful only as a reporting group.
- **Per-role strata.** An entry shared by several roles is measured once per role it renders into, because the same rule can matter to one role and be inert for another. The result is a vector of per-role outcomes for one entry. The entry-level rule is conservative and is the same rule `## Still prevents versus no longer needed` applies: removal of an entry with `Applies-to: all`, or of any multi-role entry, may be proposed only when **every** role it renders into has been measured and shows no effect. A role stratum that was not measured, or that was measured and came back `not-elicited`, `inconclusive` or any non-candidate verdict, keeps the whole entry. Narrowing `Applies-to` is held to the same conservative rule: it is not proposed from a partial measurement. It can be proposed only when every role the entry renders into was measured and the effect shows in some roles and not others, as an edit of the entry subject to the same approval path.
- **Entries that appear in several blocks.** The issue #268 entry at `.shell-team/lessons.md` (the one whose digest ends "This entry retires when script-generated record tables (issue #268)") is one entry with `Applies-to: all`, rendered into all four blocks and into four agent files. It is one unit with four strata, not four bullets.

## How an effect is observed

Three evidence tiers, cheapest first. A lesson is carried as far down the tiers as its failure shape allows.

**Tier A — recorded-failure replay (no model run).** Each entry names its incident in `Source`, `Why` and its `Rule`. For each entry, read the telemetry after the entry's promotion date and ask whether the failure class the entry names has recurred: `rework` events (a review or QA bounce back to implementation) and `gate` events (a blocked or failed gate) in `.shell-team/runs/shell-team.jsonl`, joined to the board and review records of the same run. This tier cannot show that a lesson prevents anything: a quiet period is equally explained by the model no longer making the mistake and by the lesson working. What it can do is the reverse: it finds entries whose failure class **recurred despite** the lesson (the lesson is not sufficient, and is a candidate for strengthening, not removal) and it ranks the rest so that Tier B is spent where a with/without difference is plausible. Note that the runs file is gitignored in this repository (`.shell-team/.gitignore` lists `runs/`), so Tier A runs only on a checkout that holds the operator's own telemetry; a fresh clone has none.

**Tier B — single-entry ablation on a fixed task set.** Three arms for one role and one entry:

- control-none: the role's block with **no** playbook bullets at all;
- full: the role's current block;
- minus-one: the current block with exactly one entry removed.

The control-none and full arms do not depend on the entry, so they are run once per role and shared by every entry measured in that role; only minus-one is run per entry. Each run is scored by a detector written beforehand for **that entry's named failure shape** (for example, "the hand-off states a count with no command beside it"), which yields a binary result per run (shape seen or not), plus the subject's own oracle for pass/fail; a run whose oracle errors out or does not finish is invalid and is not counted in its arm. The scratch install used for the arms **copies** the plugin files rather than linking the checkout, so an arm that rewrites a block edits the copy only.

**The repetition rule and its error bound.** The detector is binary, so what the arms give is a count of runs showing the failure shape out of n runs per arm. Suppose an entry still prevents its failure: removing it makes the shape appear in a run with probability p. With n runs of minus-one, the chance of seeing it zero times is `(1-p)^n`. The design fixes the smallest effect it claims to detect at p = 0.3 and requires that a lesson with that effect show at least one failure in minus-one with probability at least 0.95. That needs `n >= ln(0.05)/ln(0.7)`, about 8.4, so **n = 9 runs per arm** (miss probability 0.7^9, about 0.04). The consequence is stated openly: three repetitions would miss an effect of p = 0.3 about a third of the time (0.7^3 = 0.343), so they cannot support a removal proposal. The bound is power at p of 0.3 or more only. It says a lesson whose omission fails at 0.3 or more per run is caught 95 times in 100. It says nothing stronger about weaker effects: at p = 0.1, nine runs miss it about 39 times in 100 (0.9^9 is about 0.387). The two errors do not go the same way. A false alarm (a single failure in nine runs can be chance) moves a verdict toward keeping the entry. A **miss does not**: an effect below the design minimum can show zero failures in minus-one and, with a control-none failure and a clean full arm, lands in `covered-by-others`, which can be proposed for removal. That is accepted by design, because every removal proposal still passes operator approval (`docs/loop-engineering/machinery-inventory.md`, `## Verdict scope`, which says follow-up issues are filed only after review), and the proposal record must carry the observed counts for all three arms out of their valid runs, so the approver sees how strong the evidence is rather than a bare verdict.

**Reuse candidates, each read before being described here.**

- `docs/loop-engineering/tier2-subject-harness.md` — reused as the fixed subject for Tier B. It is a committed engineer-role implementation subject with an oracle and one recorded serial baseline (two repetitions, large spread between them). It is the only fixed task set the repository has, which is why Tier B is scoped to the engineer role. The pm-spec, qa-verifier and tech-lead strata have no fixed subject, so Tier B does not cover them without new subjects (new infrastructure, below). It is also the primary price basis (see `## Cost of one measurement`).
- `.shell-team/runs/shell-team.jsonl` — reused as the Tier A source and as the secondary cost range. Span rows carry `tokens` and `duration_ms`, but not always as numbers; how often is measured under `## Cost of one measurement`.
- `bin/rollup-runs.sh` — reused to fold span rows into per-run token and duration totals when pricing a pilot after the fact. It skips event rows by design, so it cannot supply the Tier A `rework` and `gate` signal; that part is a direct read of the event rows.
- `bin/rollup-track.sh` — reused only as the way to persist one dated roll-up of a pilot's cost under the base directory as a dated file, since it wraps `bin/rollup-runs.sh` unchanged. It adds nothing to the measurement itself.
- `bin/derive-populations.sh` — reused for any set statement the result record makes (which entries were measured, which were Tier C, which were candidates): the record embeds its derivation block beside a `- reproduce:` line rather than counting entries by eye.
- `bin/gen-loop-replay.sh` — not evaluated: it renders one run's rows as an HTML replay page for a human to watch. It is a viewer, not a source of a with/without difference, so the design has no use for it.

## Still prevents versus no longer needed

Verdicts are per entry and per role stratum, read from the failure counts out of n = 9 valid runs per arm. Write F for "the named failure shape appeared in at least one run" and 0 for "in none". The arm order is control-none / full / minus-one. The rows are tested in order and the first that matches is the verdict, so the table has no overlap.

| control-none | full | minus-one | verdict | reading |
|---|---|---|---|---|
| any arm has fewer than nine valid runs | | | inconclusive | the error bound is not claimed on a short arm |
| at least two fewer failures than full | F | any | block-failure | the block itself introduced or worsened the failure; keep the entry, record it as a block-level observation (see `## Relation to the block-size deferral`). The margin is two runs because one run of nine can be chance, and this verdict can feed a claim about reopening the deferral, so it is held to a higher bar than a verdict that only keeps an entry |
| F, and within one failure of full or higher | F | any | not-sufficient | the failure persists with the block present, or the block is at most one run worse than none (flagged weak when exactly one worse); keep the entry, a candidate for strengthening, never for removal |
| F | 0 | F | still-prevents | removing the entry brings the failure back; it is part of what keeps the block working. One failure in nine is flagged weak |
| F | 0 | 0 | covered-by-others | the subject elicits the failure, and the full block and the block without this entry both avoid it: whatever covers the ground is not this entry alone. Its marginal effect is below the design minimum of p = 0.3; it is not shown to be zero. A removal candidate as a proposal only, with the three observed counts attached for the approver |
| 0 | 0 | 0 | not-elicited | the subject never provoked the failure. This also holds when the model avoids the mistake with no bullets at all. Stays `unknown`, never a candidate |
| 0 | 0 | F | inconclusive | a failure with the entry removed but none with no bullets at all points to an interaction between bullets, not to a clean effect; kept |

Plainly, what the design can and cannot reach.

- It **can** reach `still-prevents`, and `covered-by-others` as a removal candidate. It **cannot** reach "the model avoids this mistake entirely on its own, so the entry is no longer needed": that case shows up as `not-elicited`, indistinguishable from a subject that simply never provokes the failure. Tier B therefore never identifies an entry as no-longer-needed in the model-internalised sense. For this design, "no longer needed" means `covered-by-others` and nothing more.
- `covered-by-others` does not say **which** entry or what else covers the ground. If a `Superseded-by` successor is wanted, it needs a further arm that removes the suspected covering entry together with this one; that arm is a possible extension and is not priced here.
- A failure that the block introduces never disappears into `not-elicited`: it is caught by the `block-failure` row before `not-elicited` is tested, and `not-sufficient` is likewise tested first.
- Under a binary detector, `inconclusive` means a pattern the table does not resolve (a short arm, or failures only where no cause is visible). It does not mean "no effect". It keeps the entry and is reported as unresolved.

An entry is promoted from Tier B to a removal proposal only when **every** role stratum it renders into was measured and returned `covered-by-others`, and a Tier A reading shows no recurrence of the failure class since the rule was last extended. A stratum that was not measured, or any other verdict, keeps the whole entry.

- not-a-criterion: age — an entry's age says nothing about whether the current model still makes the mistake it names; an old rule can still bind and a recent one can already be redundant, so neither the date in an entry's heading nor the time since its last `Extended by` is evidence for or against keeping it.

## Cost of one measurement

**Comparability across a long sweep.** The shared control-none and full arms are compared with minus-one runs made days later in a sweep, so a plugin, model or CLI change in between would break the comparison. The design keeps it two ways: the shared arms are re-run once per batch of ten entries and a batch is judged only against its own shared arms, and the plugin version, model identifier and CLI version are pinned for a batch and recorded on every run. The re-runs are priced in the sweep figures below (the sweep run count includes the per-batch shared arms); a pilot is one batch.

**Price basis.** The design reuses the tier-2 subject, so the primary price is that subject's own measured baseline: one engineer run of the subject, recorded in the committed harness note and reproducible from a fresh clone. The telemetry mean from the runs file is given only as a secondary range, because the runs file is gitignored (a fresh clone cannot reproduce those lines) and because the `tail -n 200` window moves every time a span row is appended, so its figures drift. Every product below multiplies a per-run figure by a run count, and the run count follows from the arms and the repetition rule: per role, one shared control-none arm of nine runs, one shared full arm of nine runs, and nine minus-one runs for each entry measured.

The two runs behind the primary baseline are a sample of two with a large spread (the harness note records them), and the detector pass and any judging add cost not priced here, so both prices are estimates of the run itself.

**What the cost says, and it is a finding for the operator.** A pilot that can support a removal proposal is on the order of thirteen to twenty-three serial hours and ten to eighteen million tokens for ten entries in one role, and a full sweep of the engineer role is on the order of five to nine serial days and ninety-six to one hundred and fifty-four million tokens, before any of the missing components exist. That is large for the benefit of trimming a block, and that is the honest reading: unless the operator wants a measured answer for specific entries, Tier A alone is nearly free and Tier B should be reserved for a small set of entries chosen by Tier A.

**What the host does.** Approves the planning of the three missing components (one approval each), approves launching a pilot, and later approves or declines each removal proposal it produces (see `## From result to removal decision`). Nothing is typed, pasted or run by the host in between; the person starting a run is the coordinating session, not the host. The host's cost is the reading of a results table.

**New infrastructure, stated plainly.** Tier A needs none beyond a short query over the existing telemetry and lessons file. Tier B needs three things that do not exist today, each its own task: a scratch-install builder that copies the plugin tree and removes one entry's bullet from one block; a per-entry failure-shape detector (for each measured entry, a command that reads a run's outputs and says whether the named failure appeared); and a driver that runs the arms in a fixed order and records the scores. The pm-spec, qa-verifier and tech-lead strata additionally need fixed subjects of their own. None of this is built here.

## From result to removal decision

A measurement result is a proposal. The path from a proposal to a change:

1. **The measurement record** lists, for each measured entry and role stratum, the verdict word from `## Still prevents versus no longer needed`, the run records behind it, and the derivation blocks for every set claim.
2. **The operator approves or declines each proposed removal or narrowing.** The approval comes first. The inventory's own rule (`docs/loop-engineering/machinery-inventory.md`, `## Verdict scope`) is that follow-up issues are filed only after review, one per approved removal or simplification; a measured candidate gets no earlier or looser treatment than an inventory verdict does.
3. **The record kept** is the measurement record plus one line per decision (approved or declined, by whom, on what date), in the task's own spec or board entry, so that a declined candidate is not re-proposed without new evidence.
4. **Only then** is an issue filed for the approved change, and the change is made by the ordinary promotion path (human-approved, schema-checked, regenerated blocks).

**The retirement-schema gap.** The existing retirement mechanism is `Status: superseded` with a `Superseded-by` pointer that names an `active` entry covering the same ground. `bin/check-playbook.sh` refuses a `superseded` entry whose `Superseded-by` is missing or empty ("a retired entry must name its replacement"), and also a dangling pointer, a self-reference, or a chain into another superseded entry. The checker also refuses a `Scope: loop` entry that points at a `Scope: maintainer` successor, because a shipped rule may not be retired in favour of a rule that never ships; so a `covered-by-others` removal whose only covering entry is maintainer-scoped has no conforming `Superseded-by` either. What the checker never checks is that the named target actually covers the same ground: it resolves the pointer by equality against another active entry's key and stops there, so whether the successor covers the ground is a human judgment made at approval time. So a lesson judged **no longer needed**, because the model avoids the mistake on its own, has no successor entry to point at, and has no conforming retirement path today. `covered-by-others` can map onto it only if one single active entry actually covers the ground. This note describes that gap and does not close it. A schema change (for example a retirement status that needs no successor) is a possible future option, stated as such, and it would be its own approved task.

**`Scope: maintainer` is the other existing lever.** An entry moved to `Scope: maintainer` stays in the corpus bound to a repository-local file and is never emitted into a shipped block, so it leaves every generated block without being deleted from the log. It fits an entry that is still true for this repository's own maintainers but no longer helps adopter roles. It is an edit of the entry and goes through the same approval path.

## What this cannot measure

- **Rare, severe failures.** A lesson that guards against a leak, a destructive command or a secret in history has a base rate that a handful of scratch runs will never elicit. Zero occurrences across the arms says nothing about it. These entries are Tier C by construction.
- **Behaviour outside the fixed subject.** The only fixed subject is an engineer-role implementation task. Lessons about spec writing, QA verification, board edits, dispatch discipline, review briefings, human gates or record formats cannot be elicited by it, and the other three roles have no fixed subject at all.
- **A single model on a single day.** Any result describes the model that ran. A different model, or the same one after an update, can change every verdict, so a result has a shelf life it cannot state.
- **Small effects.** With nine runs per arm the design catches an entry whose removal makes the failure appear in at least three runs in ten, and nothing weaker with the stated confidence. An entry with a real effect below that (at p = 0.1 the chance of seeing no failure in nine minus-one runs is about 0.39) can read `covered-by-others` and so be proposed for removal while still doing some good. The design accepts that: the removal still needs every role stratum to agree, the operator's approval, and a record carrying the observed counts so the approver can weigh them. `not-elicited` and `inconclusive` keep the entry.
- **Interaction between bullets.** One-entry removal measures an entry's marginal effect given the other bullets. Two entries that each cover for the other would each read `covered-by-others`, and removing both is not tested by removing either.
- **Dilution of the whole role.** The control-none against full pair is a whole-block observation, but only for the one failure shape the detector names on one subject and one model; it does not measure how a block degrades a role's behaviour in general, and removing a single bullet changes the block too little to show dilution. See `## Relation to the block-size deferral` for what an observation from that pair means.
- **Cost in the other direction.** The design measures what a bullet prevents; it does not price the tokens the bullet costs on every dispatch beyond the cost lines above.
- **Telemetry coverage and reproducibility.** A substantial share of recent span rows carry a null token count (a cost line above shows how many), the runs file is gitignored so a fresh clone holds none of it, and the sampled window drifts. This is why the primary price comes from the subject's committed baseline.
- **Roles outside the four.** Only the four roles that receive a generated block are in scope; no result speaks for any other role.

## Verdict scope

The consumer of this note is the operator and the planning that decides whether to run a measurement and what to remove afterwards. It is an internal design note: no adopter executes it and no gate reads it. It runs no measurement and no model; every figure it gives is either derived by the command beside it or labelled an estimate with its basis. Any measurement result the design describes is a proposal: a verdict word is a reading of runs under stated conditions, never a decision, and an approved removal is a separate step with its own record. The cost-line derivation commands prove their own form here; whether one reproduces its value is a reading item for whoever re-runs it.

## Relation to the block-size deferral

`docs/loop-engineering/playbook-block-size-deferral.md` records that the line-count warning on the generated blocks was twice checked for retirement stock without finding any, and that block-size harm was never measured. This note is consistent with its claims 1 to 5 and does not reopen them.

- **What this measures.** The effect of each entry: whether removing it changes what the role does. It is not a third sweep of the corpus for entries that dominate each other (claim-3), and it does not defend or replace the line threshold (claim-2) or the choice of quantity the warning counts (claim-4). Re-evaluation stays signal-driven (claim-5).
- **claim-1 and signal-1.** claim-1 reads: "The dilution that the 40-line threshold proxies for is a real mechanism, but its harm was unmeasured and unobserved at the pre-publication re-evaluation, and the T-1020 adjudication of 2026-08-03 measured nothing about it either — at neither point was it measured and found to be small." signal-1 is "an injected playbook block is measured to degrade the behaviour of the role it is injected into".
- **A by-product, stated plainly.** Tier B runs the control-none arm (no bullets) and the full arm (the whole block) on the same subject, so it produces a whole-block comparison as a by-product. When the full arm shows an entry's failure shape more often than control-none does, that is the `block-failure` verdict, and it is a signal-1-type observation: an injected block measured to worsen the behaviour it was meant to protect, on one subject and one detector.
- **What the operator does with it.** Such an observation is recorded as a proposal that signal-1 may have fired, together with its run records. Under claim-5 the deferral reopens on a fired signal, so the operator decides, with the record in hand, whether this one observation is enough to reopen it or only a reason to measure more. Nothing in this note says signal-1 has fired, and a run that never shows `block-failure` leaves the deferral exactly as it stands. Such an observation would be the first measurement of that harm. claim-1 describes the state at the two earlier points ("at neither point was it measured and found to be small"), and a later measurement does not contradict a statement about what had not yet been measured; claims 2 to 5 are untouched.

## Bullets that state their own retirement condition

Some entries carry the condition under which they should go. The one on record is the issue #268 entry: its `Rule` ends "This entry retires when script-generated record tables (issue #268) remove the recall-written numeric prose it guards", and the sentence is rendered into each of the four blocks and four agent files (it is a single `Applies-to: all` entry; see `## Unit measured`).

The design places such a bullet **outside** the ablation path. Its retirement is decided by whether the stated condition has come true, which is a fact about the repository (is the numeric prose it guards now produced by a script?) and not an effect to be measured on a model. It is checked by reading, at approval time, and is a proposal like any other. Measuring it as well would be redundant, and a quiet ablation could not distinguish "the condition holds" from "the subject did not elicit the mistake". When the condition holds, the entry is a retirement proposal; until it holds, it is excluded from Tier B and kept. Whether the entry would then retire through `Superseded-by` or through `Scope: maintainer` depends on whether a successor entry exists, which is the schema gap described under `## From result to removal decision`.
