# 歴史 — shell-team はどう進化したか

[![English](https://img.shields.io/badge/lang-English-lightgrey?style=flat-square)](history.md)
[![日本語](https://img.shields.io/badge/lang-日本語-1f6feb?style=flat-square)](history.ja.md)

このページは shell-team が単発パスのエージェントテンプレートから、Spec 駆動・別プロバイダレビュー付きの開発ループへ、そして自前の運用規律を持つに至るまでの経緯を語る。リリースごとの箇条書きログは [CHANGELOG.ja.md](../CHANGELOG.ja.md) を参照。本ページはその背後にあるナラティブ。

## 起ち上げ（2026-04-29）

shell-team は 2026-04-29 にテンプレートリポジトリとして起ち上げられた: 単発パスパイプライン（Tech Lead オーケストレータ・PM・Engineer・QA・軽量なレビューステップ）で、各適用先リポへファイルをコピーして配布していた。プラグインもなく、共有マーケットプレイスもなく、パイプラインそのものを包む運用ループも無かった——あるのはエージェント間のハンドオフ契約だけだった。

## プラグイン化、そして Loop Engineering（v0.1.0）へ進化

プロジェクト最初の大きなピボットは「リポにコピーするファイル群」から、正式な Claude Code **プラグイン**への移行だった: 一度インストールすればすべてのリポで使え、チームのエージェント・スキル・ヘルパースクリプトは中央で保守される。このピボットと同時に、プロジェクトはそれ以降ずっと進化し続ける長期方向を定めた——**Loop Engineering**: 単なるエージェントパイプラインではなく、明示的な BUDGET/STOP ガード・テレメトリ、そして将来的にはステップ別モデルルーティングと自己検証ランタイムループを備えた運用規律の *outer loop* をその外側に被せる方向だ。この章は **Loop Engineering（v0.1.0）** という作業ラベルを持っていた: エージェントパイプラインは **inner loop** として扱われ、このリリースはその外側に最初の outer-loop プリミティブを被せた——Loop 契約（TRIGGER/SCOPE/ACTION/BUDGET/STOP/REPORT を宣言し、専用 linter で検証）・BUDGET/STOP を fail-closed な kill-switch として強制する実行時ガードレール・フェーズ別テレメトリ・そしてボードを一切編集せず作業を*提案*するだけのオプトイン read-only triage スキル。当時、モデルルーティングと run ロールアップ機構はまだロードマップ上だった。両方とも後に v0.2.x ラインの成熟とともに実現した。

## 痕跡の集約（v0.2.0）とループの深掘り（v0.2.x）

v0.2.0 は、per-repo の運用ファイルすべてを host リポのツリー内に散らばらせるのをやめ単一の base directory へ集約し、host 自身の設定ファイルへの改変も止めた——これが安定した基線となり、v0.2.x ラインはこの上でループを深掘りしていった: Loop 契約のメタデータ・運用上の「罠」を明示的な規律へ転換・Claude 以外のどのツールでもチームの作業状態を見つけられる cross-tool state ファイル・そして自己検証ランタイムループ（フルチームループと同じガードレールで bound された、単一タスクを独自のケイデンスで完了まで駆動する仕組み）。v0.2.x ラインの間には、会話言語ミラーリング・跨-run failure clustering・役割別プロンプトダイジェストを再生成する機械検証済み structured lessons playbook・新しいモデル世代が登場するたびのモデル tier 再編・PR に返ってきたレビュー指摘をトリアージするハイブリッド review-response ワークフロー・QA の敵対的 fixture 規律の拡充も加わった。並行配布の仕組みにより、次のメジャーラインの開発中、安定ラインと pre-release の次期メジャーラインの 2 系統を単一プラグイン名の下で並行配布しつつ、インストールは相互排他のまま保った——adopter はどの marketplace ref を使ったかによって、どちらか一方の系統だけを得た。

## Oversight モデル進化（v0.3.0）

v0.3.0 ラインはより難しい問いを立てた: チーム自身の出力が増えるにつれ、完了は今も特定の人間が生成コードを継続的に読み続けることに依存しなければならないのか？ v0.3.0 は完了ゲートの中核契約を、*人間の持続的な comprehension* から *機械強制された接地ナレッジ＋独立した cross-provider AI evaluator* へ移設した——evaluator が接地できない事柄については、人間を out-of-distribution 例外の回路遮断器として残しつつ。全 5 段階で出荷された: この転換が守るべき新しい失敗モード（チームが機械速度で自分自身に同意してしまう）を命名する oversight doctrine。タスクの Goal と受入条件を hash-pin し後の drift を機械的に検知可能にする凍結 intent 機構。非自明な実装判断がその理由と接地根拠を伴って記録される decision-provenance 記録。何かが接地できないときだけ人間へエスカレーションする独立した drift/alignment evaluator。そして最後に、チーム自身の retro プロセスを「人間よ、この問いに答えよ」から、retro を書くエージェントが直接エビデンスを読み自ら attest する形へ移すこと。この全過程で autonomy は意図的に控え目なまま維持された: すべてのマージは今も人間の「go」を必要とする——evaluator はその判断を後押しするが、置き換えるものではない。

## ステータス

v0.3.0 が現行のリリースラインである。プロジェクトは board・spec・review をバージョン管理下に置き、コードだけでなく運用の経緯とその判断理由も検査可能な状態に保っている。
