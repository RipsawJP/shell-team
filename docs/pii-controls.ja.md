# PII 対策

[![English](https://img.shields.io/badge/lang-English-lightgrey?style=flat-square)](pii-controls.md)
[![日本語](https://img.shields.io/badge/lang-日本語-1f6feb?style=flat-square)](pii-controls.ja.md)

shell-team は公開の場で開発しているため、PII の混入は一度きりの移行リスクでは
なく、コミットのたびに発生し得るリスクになる。`bin/check-pii-shapes.sh` は
このリスクに対する機械的なゲートである。既定ではベース参照に対して変更が触れた
各パスの**コミット済みの内容全体**を読む（ツリー全体は見ない）。fail-closed
であり、入力を評価できなかった実行が clean と報告することは無い。`git diff` の
テキスト表現は一切解析しない — 変更されたパスは git 自身の機械可読な出力から
列挙し、内容は `git cat-file` を通して読む。そのため色設定・外部 diff ドライバ・
diff の記法に似ただけの内容が判定を変えることはない。

## 何を検出するか

汎用で公開可能な形状を、それぞれ安定したパターン id で識別する:

- `home-path` — 実在の名前セグメントを持つ POSIX のホームディレクトリ絶対パス
  （プレースホルダ形式 `/Users/<name>/` は意図的に非一致。後述）。URL 権限部分
  では成立しない境界でのみ一致するため、ドキュメント URL は誤検知しない。
- `home-path-win` — Windows の `C:` ユーザーディレクトリ形式
  （`C:\Users\<name>\`、同じプレースホルダの慣習）。
- `home-encoded` — ホームディレクトリパスの区切り文字がハイフンまたは
  アンダースコアの繰り返しに置き換えられた形状で、上記 2 形状が要求する
  リテラルの `/Users/` や `/home/` は現れない（プレースホルダ形式
  `-Users-<name>-` と `_home_<name>_` は同じ慣習で意図的に非一致）。
  区切り文字・ルートのどちらの組み合わせでも発火する。境界ガードは無い —
  区切り文字で置換された形状には URL 権限部分の誤検知クラスが存在しない
  ため、発火に偏るこのゲートの方針をそのまま適用する。
- `temp-session` — マシンローカルな一時/セッションルート
  （`/private/tmp/`、`/tmp/`、`/var/folders/`）にダッシュ区切りの
  8-4-4-4-12 桁 16 進 UUID 形状のセグメントが続く形状。大文字・小文字の
  どの表記でも発火する。UUID 形状のセグメントを伴わない一時/セッション
  citation は非一致であり、プレースホルダ形式（セッションセグメントを
  `<session-uuid>` と書く）も意図的に非一致である。
- `email-nonnoreply` — 配送可能な実在メールボックスを持ち得るドメインの
  メールボックス形状の文字列。ローカル部の形ではなくドメインで除外する: GitHub
  の noreply 識別子の 2 形状（`<id>+<login>@users.noreply.github.com` — ローカル
  部が何であってもドメインを末尾一致で判定、と素の web-flow 形式
  `noreply@github.com`）、およびドキュメント・テスト用に予約されたドメイン
  （RFC 2606 / RFC 6761）。
- `private-key` — PEM 形式の秘密鍵ヘッダー行。
- `token` — 実際の鍵本体と言えるだけの長さを持つ資格情報トークンのプレフィックス
  （GitHub の `gh[oprs]_`、AWS のアクセスキー ID、OpenAI 形式の `sk-` キー）。
  `sk-` 形式はさらに、直前が行頭であること、またはクラス `[^A-Za-z0-9]` に含まれる
  1 文字であることを境界として要求する。その
  ため s+k の 2 文字がハイフンの前で終わるだけの識別子チェーン——このプロジェクト
  自身のラベル慣習もその一つ——は、末尾がどれだけ長くても一致しない。
  `gh[oprs]_` と `AKIA` にはこの境界ガードは無い。受け入れ済みの開示された例外:
  同じ `[^A-Za-z0-9]` の境界は、区切り文字を挟まずに英数字の直後に置かれた本物の
  `sk-` キーも同様に抑制する。左側 1 文字の文脈だけではこの 2 つを区別できない
  ためであり、このゲートが検出する他の境界はすべて引き続き発火する。
- `host-local` — machine-local 形式のワークステーションのホスト名: 名前
  トークンの直後に `.local` サフィックスが続く形状（プレースホルダ形式
  `<host>.local` は意図的に非一致）。出荷時の既定で有効。
  `<name>.local.<ext>` の形のリポジトリ内設定ファイル名は、名前の一覧では
  なく名前付きクラスで除外する。
- `tracker-key` — issue tracker のキー: 大文字のみからなる 2〜10 文字の
  namespace、ハイフン、数字列。出荷時の既定では無効（有効化は後述）。
  1 文字の namespace と数字を含む namespace は形状自体で除外する。これが
  このリポジトリ自身のタスク id 慣習を構造的にクリーンに保つ。

## 実行方法

```bash
bin/check-pii-shapes.sh                 # 既定のベースに対する change-scoped
bin/check-pii-shapes.sh --base develop  # 明示した参照に対する change-scoped
bin/check-pii-shapes.sh --all           # フルツリー監査（後述）
```

`tracker-key` は出荷時の既定では無効である。1 回の実行で有効にするには、
環境変数 `PII_CHECK_TRACKER_KEY` に空でない値を設定する:

```bash
PII_CHECK_TRACKER_KEY=1 bin/check-pii-shapes.sh
```

終了コード: `0` clean、`1` 1 件以上の検出、`2` 使用法/構造エラー（解決不能な
ベース参照、読み取り不能な入力、未知のフラグ、`--all` と `--base` の併用）。
検出結果は一致したテキストそのものを出力しない — パターン id・パス・（可能な
場合の）行番号だけを報告する。これにより公開 CI ログにゲートを発火させた
バイト列が載ることはない。

`--all` はフルツリーの監査モードであり、必須の CI チェックではない。チェッカー
のソースにある短い test-locked の一覧が、別のガード自身のスイート
（`tests/rollup-track/run.sh`）が必要とする意図的な PII 形状のフィクスチャの
パスを名前で除外しているため、現時点でこのリポジトリでは `--all` は `0`
（clean）で終了する — それ以外の場所に新たに形状を持つパスが加われば、そこは
引き続き検出される。現在の変更より広く掃きたい時にローカルで使う。

## ループがこれを走らせる時点

シェルを持つ 4 つの記録執筆ロール — engineer・QA・scrum-master・cross-provider
reviewer — は、自分のハンドオフを書く直前にもう一度このチェッカーを自ら走らせる:
`PII_CHECK_TRACKER_KEY=1 bin/check-pii-shapes.sh --all`。opt-in を有効にし、
change-scoped の既定でなく `--all` モードで走らせる。`--all` は作業ツリーを
読むモードで、ハンドオフの時点でその round が書いた記録がまだコミットされて
いるとは限らない。change-scoped の既定は変更されたパスのコミット済み blob を
読むため、まだコミットされていない記録を見ることができない。

ロールは実行結果の `FINDING pattern=<id> path=<path>` 行を、その round に
自分が書いた・編集したパスへ絞り込み、自分のファイルへの検出はハンドオフを
書く前にその場で直す。結果は 1 行の `- shape-scan:` としてハンドオフに引用し、
検出件数と実行した正確なコマンドを添える。この手順は CI には配線されていない
（`.github/workflows/check-handoff.yml` は `PII_CHECK_TRACKER_KEY` を一切
設定しない）——したがって opt-in 形状に対する唯一の機械的な捕捉であり、この
ゲートが扱う他のすべては、あらゆる pull request で走る change-scoped の
無条件チェックが別に担っている。

## このゲートが扱わないもの
- 固有名詞（顧客名・内部ホスト名・プロジェクトコード）は形状では一致させられないため、このゲートの対象外である。
- 固有名詞に一致させるためのパターン自体が機密であるため、この公開リポジトリには置けない。リポジトリ外のオペレータ手元のチェックに置く。
- tracker-key の規則は出荷時の既定では無効であり、明示的に有効化する必要がある。このプラグイン自身が教えるラベル規約が同じ形状を共有するためである。有効にすると、同じ形状を持つ標準識別子（文字コードやダイジェストの名前、日付形式や脆弱性 id、RFC や HTTP ステータスの表記）は許容される雑音として報告される。解消は書いた場所での仕分けであって、このチェッカーに接頭辞の許可リストを置くことではない。
- <name>.local.<ext> の形の設定ファイル名はホスト名としては報告しない。また machine-local の接尾辞を伴わない裸のホスト名は対象外である。
- tracker-key と host-local の規則が一致させるのは汎用的な形状であって固有名詞ではない。特定の顧客名・ホスト名・プロジェクト名を名指しするパターンはこのリポジトリには置かないため、上の固有名詞に関する制限はそのまま成り立つ。
- 意味的な機微さ（設計判断や文脈から読み手が業務上の関係を推測できてしまう類）は PII の形状ではなく、対象外である。
- 画像の内容は検査しない。検査するとしてもメタデータのみである。
- commit identity のゲートは pull request が追加する非マージコミットだけを見る。マージコミットの identity はマージした側が決めるものであり、変更の作者には直せないため対象外とする。
- このゲートは前向きの制御であり、すでに公開されたコミットの identity メタデータは取り除かない。過去の露出に対する是正はリポジトリの変更ではなくオペレータ側のアカウント設定で行う。
- ファイル名やパス自体に含まれる PII 形状は検査しない。このゲートはファイルの内容だけを読む。
- URL に隣接する形やログ接頭辞の付いた形は、個人データを含まないのに報告されることがある。file スキームの URL、markdown のリンク記法で囲まれたパス、IPv6 の authority に続くパスが該当する。1 文字の後読みではこれらを散文中の実際のパスと区別できないため、この雑音は意図して受け入れる。解消はプレースホルダ形で書くことであり、抑制範囲を広げることではない。
- home-path の形状は ASCII の保守的な名前セグメントにだけ一致する。非 ASCII の名前や Windows 形式の異なる大小文字表記は対象外である。
- マシンローカルな一時/セッションパスの外にある単体の UUID は対象外である。このゲートが一致させる形状はパスであり、単体の UUID ではない。
- 一時/セッションルートと UUID の間のパスセグメントに埋め込まれた空白文字は対象外である（埋め込まれた `=` は対象内）。空白を許すと、UUID に到達する前に同じ行の無関係な単語をまたいで一致が広がってしまい、文字を 1 つ追加するのとは質的に異なる大きな誤検知面を生むため、意図的に追わない。このリポジトリの手の届く範囲にあるどのジェネレータも、そこに空白を出力しない。
- `home` ルートを綴ってしまうハイフンまたはアンダースコア区切りの英語の複合語（例えば長い kebab-case や snake-case の識別子の一部）は、個人データを含まないのに報告されることがある。解消はプレースホルダ形で書くことであり、抑制範囲を広げることではない。
- 配送可能なメールボックスが存在し得ないドメインのメールアドレス形状は報告しない。ドキュメントおよびテスト用に予約されたドメインと、GitHub の擬名 identity 用 noreply ドメインが該当する。除外ドメインの一覧はチェッカーのソースにある。
- このゲートは変更が触れた各パスのコミット済み内容を、base ref に対して解決して読む。ワーキングツリーにだけある変更は検査せず、ワーキングツリーを読むのは --all のモードである。
- 別のガードが必要とする fixture として意図的に形状を持つパスの短い一覧を、名前で除外する。一覧はチェッカーのソースにあり、その正確な内容はテストスイートが検証する。

このゲートは形状だけを見る。PII 対策として完全ではなく、通過したことは変更に PII が含まれないことの証拠にはならない。
