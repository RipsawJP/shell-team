# Moving an existing repository to local record mode

This page is for an adopter who already runs shell-team in a repository. It covers what this release changes for an existing setup, how to stay as you are, how to move one clone to local record mode, how to go back and how to check the result. The adopting guide holds the overview of the mode and the table of what setup reports; this page links to them and does not repeat them.

## What changed in this release

The default is unchanged: a clone with no `shell-team.mode` key is in `tracked` record mode, the mode the loop has always run in, and `local` record mode is opt-in per clone.

The new key is `shell-team.mode`, set per clone in its own git config. The adopting guide's section [Keeping the records out of git: local record mode](adopting.md#keeping-the-records-out-of-git-local-record-mode) is the one place that describes the mode and the table of what setup reports, so this page links to it instead of repeating it.

What an existing adopter may notice:

- `bin/team-setup.sh` reports the base dir by mode: in `local` mode it names an ignore line to append (none for a base path with a character outside `A-Za-z0-9._/-`), lists an ignored base dir under `Already in place:`, or, for a base dir already committed in HEAD, lists it under `Remains the operator's decision:`; its report in `tracked` mode is unchanged.
- `bin/team-init.sh` now prints two lines about record mode, in every mode, just before its closing `Next:` line: one says the operating files are committed by default (mode `tracked`), the other gives `git config shell-team.mode local` for a clone that should keep them out of git.
- `bin/check-pii-shapes.sh --paths <file>…` scans exactly the files you name. In `local` mode the roles use it for their records, because the default and `--all` modes do not read an ignored, untracked base dir and would report clean without having read a record.
- In `local` mode the hand-off writes the board, specs and review records into the working copy and never commits them, while the engineer's implementation and tests are still committed.
- `bin/team-commit.sh` refuses any named path under the base dir in `local` mode, and `bin/check-durability.sh` prints a `skipped:` line instead of checking whether the records were committed.
- `isolation: worktree` and `bin/land-worktree.sh` are unsupported in `local` mode, because an ignored base dir does not travel into a linked worktree. The limit is stated in the run skill and the adopting guide; `bin/land-worktree.sh` does not read the mode, so nothing in that script refuses on it, and avoiding the combination is up to you.
- On a Codex CLI host, the role prompts changed in this release, so `.codex/agents/shell-team-*.toml` generated by an earlier version no longer match a fresh generation: `bin/check-codex-agents.sh` reports each as drifted until `.codex/agents` is regenerated.
- Two prompts drive the setup: `update shell-team` in a repository that already has shell-team and `set up shell-team` in one that does not. Both run the same flow, which does not change your mode and edits no ignore line for the base dir; on a Codex CLI host it also appends `.codex/agents` to the clone's `info/exclude` when that path is not already ignored, reported under `Done:` (when it is already ignored, nothing is appended and the report says `Already in place:`).

## Staying in tracked mode

To stay in `tracked` mode, do nothing about the mode: a clone with no `shell-team.mode` key, or with any value other than exactly `local`, is `tracked`.

Upgrade the plugin on your host, then type `update shell-team` in each repository where you use shell-team; the commands for both hosts are in the [update section of the distribution guide](distribution.md#update), and a second run of the prompt leaves everything unchanged.

On a Codex CLI host the prompt also regenerates a drifted `.codex/agents`; by hand, run `bash "<plugin root>/bin/gen-codex-agents.sh" --out-dir .codex/agents` from the repository's root, then confirm with `bash "<plugin root>/bin/check-codex-agents.sh"`, as the distribution guide describes.

In `tracked` mode a base dir that is committed and holds no ignored files needs nothing else, and the durability gates keep checking that the records were committed; an uncommitted base dir, an ignored one or one holding ignored files still gets a `Required:` item.

## Moving a clone to local mode

Do this in each clone that should keep its records out of git, in this order. Every step is per clone.

1. Declare the mode once, from inside the clone, with `git config shell-team.mode local`. The value is stored in the clone's own `.git/config`; a value in your global or system git config never selects `local`.
2. Add the ignore line to the clone's `info/exclude`, the file that `git rev-parse --git-path info/exclude` names. For the default base dir the line is `/.shell-team/`, and `printf '%s\n' '/.shell-team/' >> "$(git rev-parse --git-path info/exclude)"` appends it. A root `.gitignore` line is the alternative, but it is shared: every clone that inherits it must also declare `local`, and a clone that has the line without the declaration is a `tracked` clone with an ignored base dir, which setup reports as a blocking rule while the base dir is not yet committed.
3. Type `update shell-team`. Its report now follows the mode: a base dir that is not in HEAD is listed under `Already in place:` when it is ignored and otherwise as a `Required:` item that names the line to append (no line when the path has a character outside `A-Za-z0-9._/-`), and a base dir already committed is covered in the next section.
4. From then on the loop writes its records into the working copy and does not commit them, while the engineer's implementation and tests are still committed. Do not request `isolation: worktree`, which is unsupported in `local` mode; the default non-worktree engineer path is unaffected.
5. If the base dir is not in HEAD, the records now exist only in this working copy: a fresh clone starts without them, and starts in `tracked` mode. If it is committed, a fresh clone still contains the committed records, as the next section describes.

## When the base dir is already committed

Ignore rules do not apply to files git already tracks, so in a clone whose base dir is committed in HEAD an `info/exclude` line leaves the tracked records visible (an edit shows as modified) and hides only new, untracked records under the base dir; what happens to the tracked ones is therefore your decision.

In `local` mode, `update shell-team` lists such a base dir under `Remains the operator's decision:`. The item says that the directory is tracked and that whether to keep tracking it is your decision; it prints no `info/exclude` line and names no command, and neither does this page.

If you keep tracking it, your edits to the tracked record files show in `git status` as modified, new records under the base dir show as untracked unless an `info/exclude` line hides them, and `bin/team-commit.sh` refuses to commit any path under the base dir while the mode is `local`, tracked or not (class `local-mode`, exit 2, nothing staged), so the loop never commits them.

If you stop tracking it, that is a change you make and commit yourself; the plugin makes none. Once the directory is no longer tracked and HEAD no longer contains it, an `info/exclude` line hides it, and setup lists the directory under `Already in place:`; records already committed stay in history and in clones made before that commit.

## Teams where not everyone uses shell-team

Where only some members use shell-team, each of them declares `shell-team.mode local` in their own clone and keeps the ignore line in their own `info/exclude`: both are per clone, and neither is pushed.

As long as nobody commits the base dir, the shared repository does not contain it, so a member who does not use shell-team sees no record files, and a fresh clone starts in `tracked` mode with nothing to ignore.

Put the ignore line in a root `.gitignore` only if every member will declare `local`: the line is shared, and a clone that inherits it without the declaration is a `tracked` clone with an ignored base dir, which setup reports as a blocking rule while the base dir is not yet committed.

## Going back to tracked mode

Declare the default mode again in that clone:

```bash
git config shell-team.mode tracked
```

Any value other than exactly `local` reads as `tracked`, so setting the value is enough; the key itself can stay.

Back in `tracked` mode, a base dir that is ignored and not yet committed is reported by setup as a blocking rule under `Required:`: the ignore source and line, the `git add` command, and, where it applies, a re-include line. Decide whether to change your ignore line or to add the re-include setup names, then commit the records with the `git add` command it prints; setup commits nothing. If the base path has a character outside `A-Za-z0-9._/-`, the `Required:` item says the path cannot be quoted safely and prints no `git add` command for it.

Records written while the clone was `local` stay in the working copy, and nothing committed them; they enter git only when you commit them. In `tracked` mode `bin/check-durability.sh` runs at once and reports a record that is uncommitted, or changed since its commit, as `not-durable`.

## Checking the result

Read the declared mode with `bin/team-mode.sh`: it prints `local` or `tracked`, and exits 2, which stops the loop `BLOCKED`, when git cannot read the config.

```bash
bash "<plugin root>/bin/team-mode.sh"
git status --short
```

`git status` shows no entry for the ignored records; in a clone whose base dir is committed it marks each edited tracked record as modified, and a new record shows as untracked unless an `info/exclude` line hides it.

In `local` mode `bin/check-durability.sh` prints `check-durability: skipped: shell-team.mode is local — no durability observation was made` and exits 0 when given its usual `--phase`, `--task` and `--ref` arguments; skipped means nothing was observed, not that the records are durable.

Type `update shell-team` again: `Already in place:` for the base dir in `local` mode means git ignores it, and a second run changes nothing.

On a Codex CLI host, `bin/check-codex-agents.sh` reports `.codex/agents` as in sync once you have regenerated it, unless the directory also holds an extra `shell-team-*.toml` the generator does not own: the checker names that file and does not report `in sync` until you deal with it by hand.
